# lcp-cli 010.3.3: TUI task & assignment panels + chat output polish

Part 3 of the 010.3 lcp-cli improvements (map: `010.3 - lcp-cli improvements for
tasks and assignments.md`). Depends on `010.3.1` (the `POST /api/task/:id/cancel`
path) and `010.3.2` (the task SSE endpoint, the multi-list panel model, and
`TASK_LIST_ENTRY_MAX_LINES`).

> **Recommended implementing model: Opus.** New interactive panels, live SSE,
> colour attributes, and real-widget tests.

## Goal

1. **Task panel** — opened by selecting a task in the company panel; shows the
   task and its assignments, live via the task SSE, with an in-view cancel
   shortcut.
2. **Assignment chat panel** — opened by selecting a begun assignment; a
   read-only view of that assignment's conversation, live if still running.
3. **Chat output polish (TUI side)** — echo the user's own prompt into the pane
   log, and mark blank responses `(blank)`.

All paths under `apps/lcp-cli/src/lib/tui/` unless noted.

---

## 1. Task panel

Selecting a task entry in the company panel (the tasks list from `010.3.2`) opens
a new pane. Add a `TaskPane` (subclass of `Pane` in `panes.ts`, non-talkable);
open it via the existing pane-management path (`Tui.addPane`-style, like the
help/chat panes), selectable back to the company panel with Tab/Shift-Tab.

Layout:

```
Id:     <task id>
Prompt: "<task prompt in full, word-wrapped, each subsequent line indented>"

Assignments

> 1. <role> <status> "<full prompt when highlighted>"

  2. <role> <status> "<truncated prompt>"
  3. ...
```

- `Id:` / `Prompt:` header (reuse `renderPaneHeading`-style helpers; word-wrap the
  prompt, indent continuation lines).
- **Assignments** as a `SelectableList` (the `010.3.2` model) — ordered plan
  assignments by `orderIndex`, then the rest by `createdAt` (the ordering
  `GET /api/task/:id` already returns).
- Each row: `n. <role> <status> "<prompt>"`, truncated with ellipsis; when
  highlighted, expand + word-wrap the prompt up to `TASK_LIST_ENTRY_MAX_LINES`
  with spacing (same behaviour as the company task list).
- **Status colours** (terminal-kit markup like the existing grey reasoning
  style): waiting = grey, in-progress = cyan, succeeded = green, failed = red,
  cancelled = yellow. Put the status→colour map in `tui-format.ts` (shared with
  the company task list's state indicator).
- **Selectability**: only assignments that **have begun** (status not `ready` /
  waiting) are selectable — mark not-yet-begun rows non-selectable in the
  `SelectableList` so the `>` skips them.

### Live updates

Open the **task SSE** (`GET /api/task/:id/events`, `010.3.2`) when the pane opens
(reuse the shared SSE-reader helper). On `task_changed` / `assignment_changed`,
update the in-memory task/assignments and redraw if active. Close on pane/TUI
close.

### Cancel from the task panel

- A cancel keyboard shortcut (pick a free key in `Tui.handleKey`; document it):
  calls `POST /api/task/:id/cancel` (`010.3.1`) for the panel's task.
- Show the shortcut in the bottom hint bar **only while the task is running**
  (active status), via `fitHints`; always show it in `HELP_TEXT`.
- After cancel, the SSE stream drives the panel to the cancelled state (no manual
  refetch needed).

### Tests

- `tui-format.spec`: task-panel header/prompt wrapping; assignment row rendering,
  truncation, highlight expansion; status→colour mapping.
- `tui.spec` (real widgets → `ScreenBuffer`): opening a task panel from the
  company list; `>` skips not-yet-begun assignments; status colours via
  `attrAt`/`get()`; the cancel shortcut appears only when running and issues the
  request (mock the API); an SSE `assignment_changed` updates the row.

## 2. Assignment chat panel

Selecting a **begun** assignment in the task panel opens a **read-only** chat
panel for that assignment's conversation.

- Reuse `ChatPane` / `PaneEntryLog` rendering, but **without an input box**
  (`talkable = false`) — a read-only scrollback.
- Source the conversation: the assignment's working agent id (from the
  assignment record). If the assignment/agent is **still running**, follow the
  existing per-agent SSE (`GET /api/agent/:id/events`, reuse `session.ts`
  `streamAgent` / the shared reader) so it stays live; if complete, render its
  final state (fetch the historical events — use the `010.3.1` history endpoint,
  `GET /api/agent/:id/history`, mapped into the same `AgentEvent` shapes, so a
  completed assignment still shows its full conversation).
- Back to the task panel with Tab/Shift-Tab.

### Tests

- `tui.spec`: opening an assignment chat panel from a task panel; a running
  assignment streams events into the read-only pane (no input box rendered); a
  completed assignment renders its history.

## 3. Chat output polish (TUI side)

Mirror the non-TUI fixes in `010.3.1 §4` so both renderers behave the same.

- **Echo the user's prompt.** On submit, the TUI passes the message to
  `submitHandler` → `session.runTurn` but never appends the user's text to the
  pane log. Append it as a new `PaneEntry` (new style, e.g. `user`) with a
  distinct indicator + colour, and the standard inter-item spacing
  (`PaneEntryLog.render` already inserts a blank line before each entry after the
  first). Do the same for consulted-agent follower panes where a prompt is shown.
- **Blank responses.** When a `response` entry's text is empty or
  whitespace-only, render the header as `hh:mm:ss | response | (blank)` in
  `PaneEntryLog.renderEntry` (`tui-format.ts` ~L186) instead of an empty body.
  Share the "is-blank" check with `render.ts` if practical (one small helper);
  otherwise a `// ponytail:`-noted two-line guard in each is fine.

### Tests

- `tui-format.spec`: a `user` entry renders with its indicator/colour and
  spacing; a whitespace `response` renders `(blank)`.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.
- Do not add dependencies unless truly needed; if unavoidable, latest version,
  license/health checked. Do not update existing dependencies. No unrequested
  changes outside this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Never `--no-verify`.

Write unit/integration/e2e/API tests alongside each unit of code — main, edge,
and failure cases. TUI tests drive **real** terminal-kit widgets into a
`ScreenBuffer` and assert via `dumpChars()`/`get()` — never fake the widget API
(see the project's terminal-kit testing note). Update existing tests as code
changes.

Documentation:

- `docs/lcp-cli.md`: the TUI task panel, assignment chat panel, their shortcuts
  (jump-between-lists, cancel), and the user-prompt/blank-response output.

Standing instructions:

- If the work becomes exceedingly complex or a problem resists solution, HALT
  and inform the user.
- If you discover a beneficial alteration to this plan, HALT and inform the
  user before proceeding.
- Document any agreed deviations by appending dated notes to this file.
