Please prepare a plan for the changes below, following the conventions of the `010.2.*` plans as: `docs/prompts/010.3.1 - task orchestration: lcp-cli task interactions.md` - include sufficient detail for Sonnet/Opus (the model you determine best for the task) to implement it completely.

## Entity ids

In some places, the `lcp-cli` verbs use `--role-id`, `--role-slug`, `--company-id`, `--company-slug`, and in others they use `--role`, `--company` and distinguish between them automatically. Please ensure that all verbs offer all variants of each entity they use (role/company).

## TUI: Company task lists

The lcp-cli TUI should offer a selectable and grouped list of the company's tasks, on the company panel.

This means that the selection indicator (`>`), which can be moved up and down, should also be able to pass down beyond the roles list and into the tasks lists, and so forth - cycling back to the top when it goes off the bottom of the last list. Generalise: it should be possible to show multiple lists in a panel, and for the selection indicator to move between them. It should also be possible to jump between lists with an intuitive shortcut which can be shown in the bottom-bar (if it will fit) and the help panel.

The lists should be grouped as:

1. active tasks first, in descending chronological order (most recent first)
2. completed/failed tasks, in descending chronological order

Each entry should have:

1. Date and time of the task in format: `yyyy-MM-dd HH:mm:ss`
2. Current task state eg. `(in progress)`
3. Completed assignments of total assignments, eg. `3/5`
4. Initial prompt for the task, filling the remainder of the line (truncate with ellipsis)

eg. `2026-07-13 11:15:00 (in progress: 2/3) "Write a short story about a cat."`

When highlighted the prompt should expand, if it was truncated and word-wrap - covering `const TASK_LIST_ENTRY_MAX_LINES` lines (derived from config variable that can come from a cli parameter or env variable, or a default if neither is provided), with a space between it and other items in the list.

The list should update whenever a task changes state. At current time, there may not be an SSE endpoint for company-wide events. This is something any UI will need - so lets implement it now.

## TUI: Task panel

On selecting a task, a new panel should open showing the task. Again this will need an SSE endpoint for the task, so that it can be updated as its state changes.

Content of the task panel:

```
Id:     <task id>
Prompt: "<task prompt in full (word wrapped, each subsequent line indented by 'Prompt: '.length)>"

Assignments

> 1. <role> <status> "<full prompt>"

  2. <role> <status> "<truncated prompt>"
  3. ...etc.
```

Again, each entry that was truncated shows up to `TASK_LIST_ENTRY_MAX_LINES` when highlighted.

There should be an intuitive way to cancel the task from this view, with a keyboard shortcut shown in the bottom bar (if the task is running) and always in the help text.

Colour scheme for entries:

- waiting: grey
- in-progress: cyan
- succeeded: green
- failed: red
- cancelled: yellow

Only entries that have begun should be selectable.

Selecting an entry should open a read-only panel of the chat for that assignment (regardless of whether it has completed or not). If it has not completed, then the TUI should use the SSE endpoint for that conversation to ensure it keeps track of the conversation.

## Chat output

In non-TUI mode, chat should always show the input from the user with stderr (this is currently missing), with an indicator and colour indicating that it's from the user.

In TUI mode, similarly, prompts from the user should be shown, with indicator and colour.

Spacing between items in the chat output should also be applied to these entries.
