Please make a plan to add an 'add new' control to the company page. It lets a user start a new task or a new chat.

Follow [ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md) and [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md).

The work is small and well specified. Sonnet can do most of it. Opus should review the submenu's keyboard behaviour and decide the modal problem below.

## Outcomes

- A prominent 'add new' control on the company page.
- It offers two actions:
  - **Create a new task** — opens the task creation dialog.
  - **New chat** — opens a submenu of the company's roles. Choosing a role opens the chat dialog on a new conversation with that role.
- It works fully by keyboard, including the submenu: open, move, enter and leave the submenu, choose, and dismiss with escape.
- A long role list stays reachable (no running off screen, scrollable by keyboard). Filtering is not needed.
- A company with no roles says so, rather than showing an empty submenu.
- While a new chat is starting, the chosen menu item shows that it is pending. If it fails, the control shows the error.
- When a dialog closes, focus returns to the control.
- A user can start a second chat or task while a dialog is already open (see below).

## What already exists

- **Chat:** `useChat()` in `src/components/ChatDialog/useChat.ts` gives `startChat({ companyId, roleId, roleName })`. It returns a promise that settles when the chat is open, or rejects with an `ApiError`. `ChatProvider` is already mounted in `AppShell`.
- **Task creation:** `src/components/CreateTaskDialog/CreateTaskDialog.tsx` takes `{ companyId, onClose }`. It has no trigger yet. Mount it from local state, as `TasksList.tsx` does for the task dialog.
- **Menu:** use React Aria Components' menu button and submenu. Don't hand-roll either. The pattern makes its own announcements, so no live region is needed.

## The modal problem

The chat and task dialogs are React Aria `Modal`s. While one is open, the page behind it is inert — including this control. So a user cannot start a second chat or task without closing or minimising the first. The task dialog cannot be minimised at all.

Solve this in the plan; don't just note it. Options include a 'new' entry point inside each dialog, or making the dialogs non-modal. The second reopens ADR-026's focus-trapping choice, so treat it as an ADR decision and discuss it with the user.

## Testing

- Component tests, queried by role and accessible name.
- Keyboard tests for the whole interaction.
- Each action opens the right dialog and moves focus into it. Focus returns when it closes.
- A long role list, and no roles at all.
- Accessibility checks with the menu open and the submenu open, not only closed.
