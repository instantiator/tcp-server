### What exploration found (the bug)

The cause is **not proven yet**. The user believes the planner had really started. The worker writes `running` first, before any LLM call (`apps/backend/apps/tcp-agent/src/agent/agent-loop.service.ts` `run()`), so a started planner should have shown. Candidates, all confirmed in code:

- **Q. Queued behind the one worker slot.** `AGENT_WORKER_CONCURRENCY=1` in `.env.dev:68`. The task goes to `planning` (`SRV/api/task-orchestration.service.ts:86`) before the agent row exists, and the agent sits `idle` until the job runs.
- **C1. No event when an agent is created.** `agent-db.service.ts:83-92` creates it silently, and the assignment's `agentId` back-link (`task-orchestration.service.ts:367`) publishes nothing either. The client only learns of the agent from its first `running` event, which triggers a list invalidate (`FE/events/cache.ts:116-117`). That explains "appeared late".
- **C2. A refetch can land after a live patch.** `applyEvent` (`FE/events/cache.ts:94`) patches rows but doesn't cancel an in-flight list fetch. A response read before the DB write then overwrites `running` with `idle`, and it stays that way until the next agent event. That is "one step behind".
- **C3. The agent stream's replay treats `Idle` as terminal.** `SRV/api/api.agent.controller.ts:203-237` reads the DB at subscribe time. Its synthetic `idle` goes through `applyEvent` (`FE/events/useEventStream.ts:40-43`), and it can land after a real `running`.
- **C4. Priming gap on reconnect.** `api.company.controller.ts:305-320` awaits `prime()` before it observes live events.
- **Silent or misordered writers:**
  - QA hand-off pause publishes nothing (`assignment-completion.service.ts:234`).
  - Cancel publishes nothing (`task-failure.service.ts:222`).
  - Resume publishes `running` before the write (`agent-orchestration.service.ts:236-242`).
  - Chat start has no `entity` (`api.agent.controller.ts:113-120`).
  - Chat failure publishes before the write (`chat.service.ts:333-340`).
- **Office mapping:** `activityOf` (`VIS/rules/companySnapshot.ts:163-199`) maps only `running` to `working` (the whiteboard). `idle` maps to `atDesk`.
- **TUI:** `apps/backend/apps/tcp-cli/src/lib/tui/session.ts:113-133` ignores every entity except `task`, and task panes never show agent status.

### Decisions I've taken (repeat at the end)

1. **Finishing agent:** the avatar dissociated most recently from the task, tracked by a world counter. It carries outputs only when the task **succeeded**. Failed or cancelled tasks leave as they do today. If no avatar is left, nobody carries.
2. **Archive room** takes fixed slot 2, so dynamic rooms start at 3 and `corridorColumns` starts at 2.
3. **Silo link:** the new runtime config `storageConsoleUrl` and `storageBucket` come from `MINIO_CONSOLE_URL` and `MINIO_BUCKET_PREFIX` through `docker/nginx/10-tcp-init.sh`. The link is `${console}/browser/${bucket}/${base64(prefix)}`, and stage 9 verifies that format against the running Silo. With no config, rows show as plain text. The console has its own login, and the link exposes only a path.
4. **Waiting to start** is `agent.status === 'idle'` on a task (non-chat) assignment that is `in-progress`. Stage 1 confirms idle has no other meaning for task agents.

#### As found (stage 1)

**Set-up.** A separate stack (project `tcp-s1`, a scratch copy of `.env.testing`), so the `tcp-dev` volumes were not touched. Stub-llm with the global `minDelay` 250 / `maxDelay` 350, so each LLM call took about 18 s. The planner never calls `create_plan`, so it runs three calls and then fails. No per-rule delay was needed. One recorder logged the company stream, each agent's stream (opened as soon as the agent row appeared), the DB rows every 250 ms and the REST agent list every 1 s. Times are ms from the recorder's start.

**Run (a): one task on an idle system.** The agent was created without an event, and started 250 ms later.

```text
3387 COMPANY task planning (summary)
3399 COMPANY assignment dispatched (plan), no agentId
3443 DB      agent 6fb275b9 = idle              ← no event
3444 DB      assignment agentId=6fb275b9       ← no event
3467 AGENT   replay idle                        (true at the time)
3699 DB      agent = running
3767 COMPANY agent running                      ← first time a client hears of it
6267 AGENT   llm_request
```

**Run (b): a second task while the first agent runs.** The second agent sat `idle` for 52 s while its task read `planning`. Its listen-in showed only the replayed `idle`. It started only when the first agent's job ended.

```text
 9969 COMPANY task B planning; assignment dispatched (plan)
10116 DB      agent 89b63abb = idle            ← no event
10124 AGENT   replay idle                       (true: DB idle)
  …   52 s: no event about 89b63abb; DB and REST both say idle
62681 DB      agent 6fb275b9 (task A) = failed
62749 COMPANY agent 89b63abb running            ← worker slot freed
63901 AGENT   llm_request
```

**Which causes occurred:**

- **Q: yes.** This is the user's report. The task reads `planning` as soon as it starts, but its agent waits for the one worker slot. The agent really is idle. The listen-in is really empty. The office is not one step behind: it shows `idle` because that is true.
- **C1: yes.** No event when an agent is created, or when the assignment is linked to it. A client first hears of the agent at its `running` event (0.4 s in run a, 52 s in run b). It can only see an idle agent through an unrelated refetch: a window-focus or mount refetch (`staleTime` is 0), or a company-stream re-prime. That is "appeared late, then idle".
- **C2: not seen.** On a new agent's first event, the row is not cached, so `applyEvent` invalidates, and that cancels any in-flight fetch. Nothing refetched the agent list while a patch landed in either run. It is still possible after a focus refetch; stage 3 can harden it, but it did not cause this report.
- **C3: not seen.** Both replays were `idle` while the DB was idle. A running agent's stream replays nothing.
- **C4: not seen.** The company stream did not reconnect.

**Other things seen:**

- Cancel published no agent event. The agent went `cancelled` in the DB with no agent `state_change`, only the assignment and the task. This confirms the silent cancel writer.
- The cancelled agent's stream still sent LLM deltas 50 ms after the cancel.
- There were 2.5 s between `running` and the first `llm_request`. A listen-in shows nothing in that gap.
- `AGENT_WORKER_CONCURRENCY` is not passed to the `tcp-agent` container in `docker-compose.yml`. So `.env.dev:68` does nothing, and the worker runs at the default of 1 anyway.
- Resume publishes `running` as soon as the job is queued. With one worker, a resumed agent queued behind another job reads `running` while the DB still says `paused`. Stage 2 already removes this early event.

**What `idle` means on a task agent.** Only two writers set `idle`: the column default when the row is created, and the end of a chat turn (`chat.service.ts:297`, chat agents only). Every other change is `running`, `paused` or a terminal status. A resume or a QA hand-off leaves the agent `paused` until the worker writes `running`. A task recovery creates a new agent, which starts `idle` like any other. So on a non-chat agent, `idle` means only "created, not started yet". Decision 4 holds.

### Stage 3: Client races (Opus)

_As built (Opus, inline):_ only the C2 guard. `applyEvent` invalidates when a fetch for the entity is in flight, and a test proves it fails without the fix. Stage 1 saw neither C3 nor C4. Both are narrow windows, so they go to unresolved notes rather than rework of the agent-stream replay or priming (ADR-025).

- `FE/events/cache.ts` `applyEvent`: after patching, if `queryClient.isFetching({queryKey:[entity]}) > 0`, invalidate that entity. The default `cancelRefetch` drops the stale in-flight fetch and refetches after the write.
- Agent-stream replay: stop a subscribe-time `idle` read from overwriting a newer live status. Preferred server fix: subscribe to live first, then emit the replay only if no live `state_change` has arrived yet. Keep transcript termination for chat agents.
- C4, only if stage 1 saw it: subscribe before priming, and buffer. Revisit ADR-025 if so.
