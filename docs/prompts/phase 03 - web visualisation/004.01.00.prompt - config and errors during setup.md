Please prepare a plan to make the following improvements...

I ran the setup wizard with `scripts/setup-wizard.sh` from 0 and it did a great job with a few exceptions. I'd like to improve this, for a great user experience. If you see any other opportunities to improve the setup UX while planning, please suggest them.

## LLM providers

During setup, it asked about the LLM provider, but it wasn't as helpful as it could be. The user should understand what it means to have an application level provider (eg. "This will be the default provider for each company you set up. It can be overridden at a company level, and a role level, as needed.") When asked if they want to set it up at application level, default to yes.

The setup wizard should offer configurations for popular inference providers out of the box.

- Offer a choice between some 'templated' providers or allow the user to enter their own details
  - remote...
    - OpenAI
    - Anthropic
    - Google
    - Amazon (ie. Bedrock)
    - Azure (what's their service called?)
    - Some other popular service providers?
  - local...
    - LM Studio
    - Ollama
    - Some other popular local LLM providers?

For instance, if the user chooses OpenAI, they should be able to enter their API key and that should be all they need to provide (the rest should be known).

That said, model context sizes aren't easily known until the model is chosen - and the user may not know what to put. Do most services make context size discoverable?

In the future we'll implement the ability for a user to select from known available models at their provider, too (or enter their own details).

Is there a library we can use that has provider and model data? That way it should be reasonably straightforward to keep our data up to date? If not, please store data for the common providers in a shared location, as we'll want to offer this templated configuration through the CLI, TUI, and web interface, in future, as well as the setup wizard.

If the user selects a local provider, the wizard should ask if it's already installed and setup before proceeding. If not, it should offer some installation guidance, and some steps they should take (eg. for LM Studio, they need to enable the server, download and load a model, set up an API key, and discover their base URL). Recommend a small model (eg. a variant of gemma) that is likely to work, so they can get started.

If the user provides a `localhost` or `127.0.0.1` base url, consider that this may need to be replaced with `host.docker.internal` because the service runs inside a docker container. If they enter one, the setup wizard should offer to convert it (and explain why).

### Embedding providers

For the embedding provider config, please follow a similar pattern - it should also be possible to use either remote or local services (although, frustratingly, not all service providers offer an embeddings model!)

Again, if they choose a local provider, share some installation steps to help them get started.

Suggest a good embeddings model that will help the user get started. (We're using `text-embedding-nomic-embed-text-v2-moe` on this machine... actually, is that a good choice?)

Again, if there's data available for this through a library, please use that. Otherwise we'll need to keep it in shared code so it's accessible to all the tools in future.

If the user chooses not to set up an embeddings provider, We should warn them that without one they won't be able to upload knowledge documents for roles.

## Testing the connection

Setup wizard offers a connectivity check for the LLM provider.

Let's add a `--test-config` parameter that, when set, tests all connection configurations, eg. the LLM provider, but also OIDC, and document storage, and any MCP services etc. (instead of going through the setup sequence).

## Error whilst setting up companies and the `test` user

I saw this error message during setup on a fresh machine:

```text
[tcp-cli] Building tcp-cli...
jq: parse error: Invalid numeric literal at line 2, column 2
```

It didn't recur when I ran setup again later. It was a little confusing (ie. didn't really explain what the issue was).

Ideally we should fix whatever caused this. The best clue I have is that it came right after `Building tcp-cli...` and was a use of `jq`.

Even if we can't figure out the cause right now, we should offer a better error message than just `jq`'s error - ie. explain what we were trying to do, and maybe print the value that `jq` was trying to parse (if it's not JSON it might be a useful error message).

For errors, it's worth explaining what went wrong, and what the user can do to resolve the issue.

Please also sweep for other points where there's risk of errors. Step through the setup process, and where there's a risk of an error, catch it, and generate a meaninful message for the user.
