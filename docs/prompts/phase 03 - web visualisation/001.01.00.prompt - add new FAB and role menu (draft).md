## Goal

The entry point to the two things a user can start from the live activity view. Deliberately built **last** in the 008 series, because it only opens dialogs that already exist.

## Requirements

- A prominent 'add new' control on the live activity view.
- It offers two actions:
  - **Create a new task** — opens the task creation dialog (008.05)
  - **New chat** — offers a submenu of the company's roles; choosing one opens the chat dialog (008.02) on a new conversation with that role
- Fully usable by keyboard, including the submenu.
- Handles a company with many roles without becoming unusable.
- **The opener API already exists.** `useChat()` from `src/components/ChatDialog/useChat.ts` gives `startChat({ companyId, roleId, roleName })` for a new chat and `openChat({ agentId, roleName, reference })` for one that already exists. `ChatProvider` is already mounted in `AppShell`, so this menu needs no provider of its own. `startChat` returns a promise that settles once the chat is open, or rejects with the `ApiError` that stopped it — its pending and failure states are this control's to show, beside whichever menu item was pressed, not the dialog's.
- **The chat dialog cannot be reached while it is already open, and this prompt has to solve that, not just notice it.** React Aria's `Modal` correctly makes everything behind it inert while a dialog is showing — including this control, if it sits on the page the dialog covers. 008.02 built chat around minimise-then-reopen: a second conversation can only be started by minimising the first, and both then show together once the dialog is back. That is a real limitation of a modal dialog, not a bug, and this control is the first thing that has to reach past an open chat to start another one. Either give the chat dialog its own 'new chat' entry point that works while it is open, or stop the chat dialog being modal — which reopens [ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md)'s choice of a focus-trapping library and needs deciding as such, not worked around here.
- **The task dialog has the same modal-inert limitation, and no minimise to route around it.** Carried forward from 008.03: while the task dialog is open, the tasks list behind it is inert (same React Aria `Modal` behaviour as the chat dialog above), so nothing on the page can open a second task. Unlike the chat dialog, the task dialog cannot be minimised and parked — it only closes. Whatever this prompt does to reach past an open chat dialog has to separately cover the case of this control being reached past an open task dialog too; the two dialogs don't share one fix.
- **This control replaces nothing that already exists.** Carried forward from 007.01: the live activity view ships with no 'add new' surface at all — both actions it would offer open dialogs that did not exist yet (008.02, 008.05), so 007.01 deferred the whole control here rather than shipping a menu whose every item was inert.
- **The task creation dialog is already built, and this control is its only missing piece.** Carried forward from 008.04: `src/components/CreateTaskDialog/CreateTaskDialog.tsx` takes `{ companyId, onClose }`, is mounted-to-open like the task dialog (`{open && <CreateTaskDialog …/>}` from local state — no provider, and it deliberately does **not** open the task it creates), and is fully covered by its own tests through a harness. It has **no trigger anywhere in the application**, on purpose: a half-wired control left behind is worse than none, and the trigger is this prompt's. Wiring it is one `useState` and one conditional mount, following `TasksList.tsx`'s pattern. The modal-inert problem in the two bullets above applies to this dialog exactly as it does to the other two.
- **Reuse `ActivityList` (`src/pages/CompanyPage/activity/ActivityList.tsx`) for any further live list this control or its targets need.** Carried forward from 007.01: it is the shared four-state frame — region, heading, item count, and the mutually exclusive loading/error/empty/populated states — built so the activity view's four lists cannot drift apart. Reuse it rather than restating its contract in a new component.

## Implementation notes

- Use React Aria Components' menu-button pattern, including its submenu support. **Don't hand-roll it** — the keyboard interaction and screen reader semantics are exactly what the pattern already solves, and the submenu is where hand-written menus most often break.
- Because the pattern handles its own announcements, this control needs **no live region and no explicit announcements** ([ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md)).
- Roles come from the company's roles endpoint. Consider whether the list needs loading up front or only when the submenu opens.
- **Think about a long role list.** A company can have many roles; a submenu that runs off the screen or can't be scrolled by keyboard is a real failure. Filtering isn't required by the MVP, but the list must at least remain reachable.
- Handle the empty case: a company with no roles should say so rather than showing an empty submenu.
- Focus behaviour matters throughout: opening the menu, moving into and out of the submenu, choosing an item, and dismissing with escape.
- **Focus hand-off is already decided by the dialogs themselves, not this prompt's to design.** `openChat` moves focus into the conversation's panel once it mounts, and React Aria's `Modal` returns focus to whatever control opened it when the dialog closes. That means the control this prompt builds — the menu button, or the submenu item chosen — has to stay mounted for as long as the dialog it opened might still be open, or the returning focus has nowhere to land.

## Testing

- Component tests queried by role and accessible name.
- **Keyboard tests covering the whole interaction**: open, move through items, enter and leave the submenu, choose, and dismiss with escape.
- A test that each action opens the right dialog, and that focus moves into it.
- A test that focus returns to the control when a dialog closes.
- A test with a long role list, and one with no roles at all.
- Accessibility assertions with the menu open and with the submenu open — **not just closed**, which is the state that usually gets tested and the one where nothing can be wrong.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- No hardcoded user-facing strings, and no literal values in stylesheets.
