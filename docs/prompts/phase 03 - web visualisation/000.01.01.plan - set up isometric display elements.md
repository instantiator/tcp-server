# 000.01 — Animated isometric company view

## Context

`CompanyPage`'s first tab shows `CompanyVisualisation`: a Phaser 4 canvas with random green rectangles for agents. Roles and tasks are sent to the scene but nothing draws them, and the click handlers are TODO stubs. This prompt turns it into an isometric office:

- Rooms appear and disappear as tasks and consultations start and end.
- Agent avatars walk to places that show what their agent is doing.
- Roles, agents and tasks can be hovered (tooltip) and clicked (a live side tray).
- The view scrolls with buttons and keys, can follow an object, and double-click toggles full screen.

Frontend root: `apps/frontend/tcp-frontend` (called FE below). All new code lives under `FE/src/visualisation/isometric/company/`.

## Decisions taken before planning (user, 2026-09-26)

1. **Agent E2E: unit and component tests only.** The browser-tier deployment has no LLM (stub-llm only runs under the `integration` compose profile), so no agent ever runs there. Avatar rules and motion are pure functions with thorough unit tests. A component test drives live events through the whole React pipeline. The browser tier covers roles, task rooms and every interaction with real Phaser. The gap goes in unresolved notes.
2. **Keyboard route: a details picker.** A React Aria `Select` in the toolbar ("Show details for…") lists roles, tasks and agents, and choosing one opens the tray. This meets WCAG 2.1.1, and it gives the browser tier a reliable way to reach the tray and to "follow" an object to the centre of the view.
3. **Agents with no task.** Consultees and chat agents walk in from the office door. A consultee goes to a 1:1 room with its caller. A chat agent stands at the mail room's pigeonholes. Both leave by the door when done.

## Where this plan departs from the prompt (say so to the user again at the end)

1. **One `world-changed` bus event replaces the twelve `create-*`, `update-*` and `remove-*` events.** React now works out the whole office, and the scene syncs to it by id. The DTO diffing in `TcpPhaserVisualisation` goes away.
2. **The mail room exists from the start**, beside the rec room. That is simpler than creating it on demand.
3. **Rooms are fixed-size slots along one corridor.** A removed room frees its slot for the next one. The corridor never shrinks during a session, so a wall never appears under a walking avatar.
4. **A task room is removed once all its avatars have left the office**, not just the room. Rooms are dead ends, so nobody walks through a closing room, and removing it later is always safe.
5. **Consultation and "messaging the user" are read from the consultee assignment and the enquiry, not `agent.pauseReason`.** The cache only patches `status` on live agent events, so `pauseReason` goes stale (see memory "Live agent rows carry no summary").
6. **The clickable "task" object is the task room's whiteboard.** Room floors stay background, so a double-click on a floor toggles full screen.
7. **Keyboard panning is handled by React on the focused stage, and Phaser's keyboard plugin is turned off.** Phaser listens on `window` and captures arrow keys, which would steal them from the page and from React Aria Tabs.
8. **The art is placeholder shapes** (Phaser 4 `isobox`, polygons), with no asset files. Walls are short, so they never hide an avatar. The canvas colours don't follow the high-contrast theme (unresolved note).
9. **Reduced motion, simple version now:** avatars jump straight to their targets, and camera follow has no easing. This meets ADR-026's "honoured from the start" and keeps the browser tests exact. A fuller design is left to a follow-up prompt, written in Step 11a (user, 2026-09-26).
10. **An avatar with no agent** (one that finished its assignment and is waiting at its desk) shows and opens its role.
11. **Page load:** avatars that exist in the first snapshot start at their targets instead of walking in from the door. Switching to the Activity tab unmounts the view, so coming back rebuilds it the same way.
12. **A full-screen toggle button** sits in the toolbar alongside double-click, for keyboard users.
13. **The old TODO(000.01) handlers** (open task dialog, start chat) are replaced by the tray. Actions in the tray are carried forward to `deferred-work.md`.

## What the Phaser guide gives us

The guide at `/Users/lewiswestbury/src/learning/phaser` was reviewed.

**Useful:**

- §09 tile-by-tile movement.
- §10 a hand-written A*.

**Not useful:**

- §06 Tiled maps, because our map is generated at runtime.
- §08 arcade physics, because the example only uses it as a weak safety net.

What we take and what we fix:

- **Maths.** Tiles are 64×32 (2:1).
  - Tile centre: `sx = (x - y) * 32`, `sy = (x + y) * 16`.
  - Inverse: `x = floor(wx/64 + wy/32 - 0.5)`, `y = floor(-wx/64 + wy/32 + 0.5)`. The review checked that it inverts exactly.
  - We write both as pure functions and don't use Phaser tilemaps. The map changes at runtime, and a tilemap layer has one depth, so avatars couldn't sort between walls and furniture.
- **A\*:** 4-way moves with a Manhattan heuristic, and a sorted-array open list (`ponytail:` ceiling note; switch to a binary heap past about 2000 tiles). Fixes to the example:
  - The start tile always counts as walkable, because a map change can put a wall under an avatar.
  - A blocked avatar re-plans on a timer, not every frame.
  - An avatar reserves the next tile before stepping onto it. The example let two avatars enter the same tile.
  - No "step aside" logic: the example's version could hijack a busy avatar.
- **Movement:** interpolate in tile space, then project to the screen. Screen-space movement makes speed uneven by direction. Depth is the continuous screen `y`, so it doesn't lag behind the step.
- **Camera pitfall:** when the camera bounds are smaller than the viewport, `BaseCamera.clampX` pins the map to the top-left. Pad the bounds by the viewport size.
- **Guide errors to ignore:**
  - Shape objects are _not_ removed in v4; `add.isobox` exists.
  - `camera.worldToScreenX` doesn't exist. Use the pointer's own `x`/`y` for tooltip placement.
- **Reference:** Phaser 4 docs ship in `node_modules/phaser/skills/`, and they are more reliable than the guide.

## Architecture

```text
live hooks (roles, agents, tasks, assignments, awaiting_user enquiries)
   │ buildCompanySnapshot()                      rules/companySnapshot.ts   (pure)
   ▼
officeReducer(state, action) → applyRules()      world/officeReducer.ts, rules/*  (pure)
   │ OfficeWorld (rooms, furniture, avatars + targets)
   ▼  bus: 'world-changed'
TcpCompanyScene: renderRegion() → draw; walkers → move; A*        scene/*, motion/* (motion pure)
   │  bus: 'avatar-arrived' | 'avatar-exited' → reducer
   │  bus: 'hover' | 'select' | 'follow-stopped' → CompanyVisualisation (tooltip, tray, picker)
```

- **Who owns what:** React owns _where each avatar should be_ (its target). The scene owns _where it is now_ (live position, route, occupancy), and reports back only on arrival or exit.
- **Rules run while the view is mounted:** `useOfficeWorld` dispatches a new snapshot whenever live data changes. Arrivals and exits re-run the rules too.

### Data structures (Step 1, Opus writes `world/types.ts`; the sketch below is binding)

```ts
Tile { x; y }            Bounds { x; y; width; height }
RoomPurpose = 'rec' | 'mail' | 'corridor' | 'task' | 'oneToOne'
Room { id; purpose; slot: number | null; bounds; door: Tile | null; taskId?: string; closing: boolean }
FurnitureKind = 'desk' | 'whiteboard' | 'sofa' | 'pigeonholes' | 'table' | 'officeDoor'
Furniture { id; kind; roomId; tile; ownerAvatarId?: string }          // ownerAvatarId: desks only
AvatarTarget = { kind:'furniture'; furnitureId } | { kind:'avatar'; avatarId } | { kind:'tile'; tile } | { kind:'exit' }
Avatar { id; kind:'role'|'agent'; roleId; agentId: string|null; assignmentId: string|null; /* current, or last once dissociated */
         taskId: string|null; deskId: string|null; location: Tile; target: AvatarTarget; placeAtTarget: boolean }
OfficeWorld { rooms; furniture; avatars; layoutVersion: number; nextAvatarNumber: number; corridorColumns: number }
Cell { floor: RoomPurpose | 'outside' | null; wall: boolean; walkable: boolean }
Mob  { kind:'furniture'; furniture } | { kind:'avatar'; avatar }
Region { origin: Tile; cells: Cell[][] /* [row][col] */; mobs: Mob[] }
```

**Ids are deterministic:**

- Rooms: `rec`, `mail`, `corridor`, `task:<taskId>`, `oneToOne:<consulteeAssignmentId>`.
- Furniture: `<roomId>:whiteboard`, `<roomId>:desk:<n>`, and so on.
- Avatars: `role:<roleId>` and `agent-avatar:<n>`, where `n` comes from `nextAvatarNumber`. Avatars outlive agents, so an agent id can't be the avatar id.

`layoutVersion` bumps whenever a room or piece of furniture is added or removed. The scene rebuilds the static layer only when it changes.

### Layout scheme (Step 1 writes the constants into `world/layout.ts`)

- **Slots:** `ROOM_W = 9`, `ROOM_H = 7`, both including walls.
  - Slot `i` is in column `c = floor(i/2)`, at `x0 = 2 + c*ROOM_W`.
  - Even slots are north (`y0 = 0`). Odd slots are south (`y0 = ROOM_H + 2`).
- **Corridor:** floor rows `ROOM_H` and `ROOM_H + 1`, from `x = 1` to the end of the last column ever used.
  - Where a column has no room, the corridor's edge rows (`ROOM_H - 1` and `ROOM_H + 2`) are drawn as wall.
  - A wall column closes the east end.
- **Door gap:** each room's wall facing the corridor has a gap at `x0 + 4`.
- **Outside:** tiles at `x = 0` on the corridor rows. This is where avatars spawn, and the exit target.
- **Office door:** `officeDoor` furniture at `(1, ROOM_H)`. It is walkable.
- **Fixed slots:** slot 0 is the rec room, slot 1 the mail room. Task and 1:1 rooms take the first free slot from 2.
- **Furnishing:** positions are defined for a north room and mirrored in `y` for a south room. "Back wall" means the wall away from the door.
  - rec: two sofas along the back wall. Role spots are the other interior tiles in row-major order, keeping the door column clear.
  - task: a whiteboard at the centre of the back wall. Desks go at an ordered list of 8 positions.
  - mail: pigeonholes at the centre of the back wall.
  - oneToOne: a table at the centre.
- **Ceilings** (each gets a `ponytail:` note plus an unresolved note):
  - Role spots in the rec room (about 20). Overflow roles are not placed.
  - Eight desks per task room. An avatar with no free desk has `deskId: null` and stands by the whiteboard.

### Activity mapping (Step 1, Opus; `rules/companySnapshot.ts`)

`CompanySnapshot`:

- `roles`: `{id, name}`.
- `tasks`: `{id, shortcode, request, finished, step, steps}`.
  - `steps` is the task's implement-mode assignments.
  - `step` is how many of those have succeeded.
  - `finished` means the status is succeeded, failed or cancelled.
- `agents`: `{id, roleId, assignmentId, taskId, activity}`.
  - `taskId` comes from the assignment.

`activity` takes the **first** row that matches:

| #   | Condition                                                                                                                               | activity                                                      |
| --- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 1   | agent status is completed, failed or cancelled; or its assignment is succeeded, failed or cancelled                                     | `finished`                                                    |
| 2   | an enquiry with `status === 'awaiting_user'` has this `agentId` (re-filter client-side: a live patch can close a row still in the list) | `messagingUser`                                               |
| 3   | assignment mode is `chat`                                                                                                               | `messagingUser`                                               |
| 4   | assignment mode is `consultee` (and active)                                                                                             | `consulting`, with `oneToOneId` = own assignment id           |
| 5   | an active consultee assignment has `parentAssignmentId === agent.assignmentId`                                                          | `consulting`, with `oneToOneId` = that assignment's id        |
| 6   | mode is `qa` and the agent is `running`                                                                                                 | `reviewing`, with `reviewedAssignmentId = targetAssignmentId` |
| 7   | agent is `running`                                                                                                                      | `working`                                                     |
| 8   | anything else (idle, paused otherwise)                                                                                                  | `atDesk`                                                      |

Use `ACTIVE_*_STATUSES` from `FE/src/api/statuses.ts`. The list endpoints return every row ever, so filter client-side, as the activity view does.

### Rules (`rules/applyRules.ts` runs them in this order; each is `(world, snapshot, ctx) → world`)

1. **roleRules:** one role avatar per role, at the next rec-room role spot. `target` is `{tile}` and `placeAtTarget` is true. Avatars for removed roles are dropped.
2. **taskRoomRules.open:** every unfinished task with no room gets a task room, furnished with a whiteboard.
3. **oneToOneRoomRules.open:** every `oneToOneId` in the snapshot with no room gets a 1:1 room with a table.
4. **agentAvatarRules:**
   - **Unfinished agent with no avatar, belonging to a task:**
     - Skip it until the task room exists.
     - Otherwise reuse an avatar in that task with the same `roleId` and `agentId === null`.
     - Otherwise create one at the outside tile (or with `placeAtTarget` on the first snapshot), and claim the first free desk in the room or add a new one.
   - **Unfinished agent with no avatar and no task:** create one at the outside tile with no desk.
   - **Avatar whose agent has finished or gone:** dissociate it (`agentId: null`, keep `assignmentId`). A task avatar targets its own desk; a no-task avatar targets `exit`.
5. **avatarTargetRules**, for each avatar that still has an agent:

   | activity        | target                                                    | fallback   |
   | --------------- | --------------------------------------------------------- | ---------- |
   | `working`       | its task room's whiteboard                                | desk       |
   | `reviewing`     | the avatar whose `assignmentId` is `reviewedAssignmentId` | whiteboard |
   | `consulting`    | the table in the `oneToOne:<id>` room                     | —          |
   | `messagingUser` | the mail room's pigeonholes                               | —          |
   | `atDesk`        | own desk                                                  | whiteboard |

   Keep the old object when nothing changed, so reference equality holds.

6. **taskRoomRules.close:** a finished task with a room is marked `closing`. Every avatar with that `taskId` is dissociated and targets `exit`.
7. **cleanup:**
   - A 1:1 room whose id is no longer in the snapshot closes. It is removed once no avatar's `location` is inside it and no avatar targets its furniture.
   - A closing task room is removed once no avatar has its `taskId`. Its desks go with it, and its slot is freed.

**Reducer actions:**

- `snapshot`: stores the snapshot, then runs the rules. `ctx.firstSnapshot` is true when no snapshot was stored before.
- `avatarArrived(avatarId, tile)`: sets `location`, then runs the rules.
- `avatarExited(avatarId)`: removes the avatar and frees its desk, then runs the rules.

### Motion policy (`motion/`, constants written by Step 1)

- **Walking:** 4-way moves at `WALK_TILES_PER_SECOND = 3`, interpolated in tile space.
- **Walkable tile:** it has a floor, isn't a wall, and holds no furniture. The office door is the exception and is walkable.
- **Occupancy:** each walker holds its current tile and reserves its next tile before stepping.
- **When blocked:**
  - Wait.
  - Every `REROUTE_MS = 600`, re-plan with the other avatars' tiles treated as walls.
  - After `GHOST_AFTER_MS = 4000` still blocked, take the next step ignoring other avatars (`ponytail:` a deadlock escape; the proper fix is priority yielding).
- **Resolving a target to a tile:** breadth-first search out from an anchor to the first walkable tile nobody occupies or has claimed.
  - `furniture`: the furniture's tile is the anchor.
  - `avatar`: that avatar's live tile is the anchor. Re-resolved on every re-plan.
  - `tile`: that tile itself.
  - `exit`: the outside tiles.
- **Arrival:** the scene emits `avatar-arrived` once per target. For `exit` it emits `avatar-exited` instead.
- **Reduced motion or `placeAtTarget`:** move the sprite straight to the resolved tile, then emit.

### Event bus (`TcpPhaserEventBus.ts`, keeping the existing mapped-type pattern)

`SelectionTarget = { kind: 'role' | 'agent' | 'task'; id: string }`.

- **React → scene:**
  - `world-changed: OfficeWorld`
  - `camera-pan: {dx, dy}` (screen px)
  - `camera-follow: SelectionTarget | null`
  - `motion-preference: {reduced: boolean}`
- **Scene → React:**
  - `scene-ready: void`
  - `avatar-arrived: {avatarId, tile}`
  - `avatar-exited: {avatarId}`
  - `hover: {target, x, y} | null` (canvas-relative px)
  - `select: SelectionTarget`
  - `follow-stopped: void`
- **Selection for an avatar:** an agent avatar gives `{agent, agentId}`. With no agent, or for a role avatar, it gives `{role, roleId}`. A whiteboard gives `{task, taskId}`.
- **Where listeners live:** React-side listeners only in `TcpPhaserVisualisation`. `CompanyVisualisation` may _emit_ (`camera-pan`).

## Discovered during implementation

- **Step 1:** `Avatar` has one `assignmentId` (its current assignment, or its last one once it has no agent), not `lastAssignmentId` beside a current one. It is one field fewer for the rules to keep in step, and `agentId === null` already says the avatar has no agent.

- **Step 7a:** `setRoute` no longer clears the time spent blocked. The scene re-plans a blocked walker every `REROUTE_MS`, so clearing it there meant `GHOST_AFTER_MS` could never be reached and a boxed-in avatar would wait forever. Only starting a step clears it now, and a test covers re-planning while blocked.
- **`SPAWN_TILE`** was added to `world/layout.ts` (`{ x: OUTSIDE_X, y: CORRIDOR_Y }`), so the agent rules and the scene share one spawn point.
- **Creating a task publishes no live event** (found by the Stage B browser spec). `TaskService.create` saves the row and records nothing, so an open page sees a new task only when it is started (`planning` is published) or on reload. That affects the Activity tab for other viewers too. The user chose to record and defer it (2026-09-26). The browser spec creates its task before opening the page and tests live _removal_. Step 11 writes this into phase 03's unresolved notes and carries it into a backend prompt: publish a `ready` state_change from `TaskService.create`.
- **`hosting.spec.ts` fails under `--dev-web`** by design (it only holds for a built bundle). It is not a regression; the full browser tier in Step 12 must run against a built deployment.
- **Walking logic lives in `motion/crowd.ts`, not the scene** (Step 7b). Occupancy, target resolution, re-routing and arrivals are one pure class with its own tests, and the scene only draws positions and forwards events. The plan had put that logic in the scene, where jsdom can't reach it.
- **The stage's focus decision was taken before Step 9**, because Step 8b needs it. `jsx-a11y` flags every non-widget role with `tabIndex` and key handlers, including `application` and `region`. The stage stays `role="group"` ("Office view"), gets `tabIndex={0}`, and pans with arrow keys and WASD only while focused (WCAG 2.1.4). The two rule disables carry a reason. Key handling is not on the whole section, because React Aria's `Toolbar` already uses arrow keys to move between its buttons.
- **The full-screen toggle loaded pressed** (found by checking Stage D in a real browser). `useFullscreen` compared `document.fullscreenElement === ref.current`, and on a first render both are `null`. jsdom hid it, because it leaves `fullscreenElement` undefined where a browser reports null. It is fixed, and two tests guard it: the hook with an empty ref, and the component with a browser-like `null`. Both were checked to fail against the old code.
- **The tooltip's `max-inline-size: 16rem` was a literal value**; it is now the `--tcp-visualisation-tooltip-max-width` token.
- **Checked in real Chromium:**
  - Following a role centres it, and hovering it gives the pointer cursor and "Role: Coder".
  - Clicking opens its tray, and closing the tray focuses the stage.
  - Following a task centres its whiteboard, and its tooltip shows "Task: (0/0)" and the request.
  - Double-clicking an empty corner enters full screen (headless Chromium allows it).
- **Opening or closing the tray shifted the whole view sideways** (found by the Step 10 journeys). The stage changes width with the tray, and a Phaser `RESIZE` keeps the camera's left edge, so the view jumped by half the change and a centred object drifted off centre. `CameraController` now keeps the view's centre across a resize. The journey that closes the tray and clicks the same avatar again guards it.
- **Under StrictMode (dev only) two canvases exist for a moment after load.** Browser specs wait for the stage's description before touching the canvas, which also waits that out.
- **`company-activity.spec.ts` had a slug race** (found while hunting a flake). Its `beforeAll` named companies by `Date.now()` alone, and `fullyParallel` runs that hook per test, often in the same millisecond, so creation hit the slug's unique constraint (a 500). The new tests made it more common. It now has the same random suffix as `company-visualisation.spec.ts`, and both specs passed 8 runs out of 8 at 1 and at 8 workers afterwards.
- **One unexplained browser flake:** a redirect to Zitadel's login form mid-test, seen once in about thirteen runs. It is recorded in phase 03's unresolved notes; it is in the sign-in harness, not the office view.
