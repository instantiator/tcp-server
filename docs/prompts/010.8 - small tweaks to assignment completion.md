## assignment completion

I've seen agents iterate once or twice trying to complete assignments when calling the assignment completion MCP tool.

`working-file-path` and `inline-text` don't seem to work nicely for them - and they intuitively seem to choose `file` and `text` for those types. That's reasonable, they're hard to guess even if they're more specific.

1. Do we state acceptable values for `type` when describing the use of the assignment completion tool? (ie. before they make their first mistake)
2. Let's switch to `file` and `text` (and update all supporting text used to tell the LLM how to use the tool)
   - Can we also modify the tool to accept synomyms, such as `working-file`, `inline-text`, `path`, `filename`

More generally, do we state the acceptable values for all enumerate properties across all the MCP tools we provide? Can we generalise the generation of descriptions for all MCP tool input types/interfaces so that they're consistent and automatically created? (Hopefully there's a nice way to do that for enumerated / string union types.) It'd be nice to have that generated by a single shared utility function.

Ideally, the LLM would be furnished with everything they need to make a good call first time. (Weaknesses of smaller local LLMs notwithstanding, of course.) They won't always get it right - so giving them a clear explanation of which properties they got wrong and what the acceptable values are after they make a mistake is valuable, too.

(The above assumes this doesn't already happen - so please also confirm the current state as a part of the plan.)

## assignment QA

The assure assignment tool accepts values of `accept` and `reject`. I saw an agent at least once submit `Accept` and have to go round again.

In the case where a value is from an enum or a union type of string literals, or can only be specific values, do we _always_ tell the agent exactly what the acceptable values should be? Do we also indicate to the LLM ahead of time what the acceptable values are? (ie, in the tool description?)

Let's either:

1. add a short note in the prompt for every mode stating that tool calls are case sensitive, or
2. modify tool calls to accept case variants for required strings

What do you think is best? Although this came up in a QA assignment, it should really apply to all modes and tool calls.
