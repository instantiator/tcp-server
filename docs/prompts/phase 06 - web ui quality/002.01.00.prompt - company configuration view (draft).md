## Goal

> **This is post-MVP.** It's recorded here so the deferred components aren't lost, not because it's next.

[ADR-020](../../ADRs/ADR-020-web-ui-mvp-scope.md) deliberately left configuration out of the MVP: `tcp-cli` already handles company and role configuration well, and the first release focused on the thing the CLI _can't_ do — watching a company live. This prompt closes that gap, and removes the need to reach for the CLI to onboard.

## Requirements

- A new tab in the company view. Since 005.01 (phase 03) the tabs live in `CompanyTabs.tsx`: the office view, then one tab per activity list, each selected by its URL hash (`#tasks` and so on). Adding this one is a new `Tab` and `TabPanel` there, with its own hash id. Decide whether it is force-mounted like the activity tabs (hidden but live, which keeps its state across a switch) or not, like the office view. Extend the keyboard test in `CompanyPage.test.tsx` to reach it.
- **The entity routes are properly typed as of 006.01**, so this view can read the full company shape from the generated client rather than working around gaps in it. But `GET /api/company/{id}` answers **200 with a JSON `null`** for a company the caller cannot see, and the generated types do not say so — they describe the body as a company that is always present. `CompanyPage.tsx` collapses that into `undefined` rather than trusting the declared type; do the same here rather than reading a field off `null`.
- **Roles**: a list, filterable by name, with a dialog per role showing its details.
- **Role knowledge**: per role, list its documents with upload, download and delete, plus the current indexing status. **The read hooks already exist** — `useRoleKnowledge`, `useRoleKnowledgeStatus`, `useRoleKnowledgeSearch` (`src/api/queries.ts`, 005.01). Use them for the list and status views; upload and delete are mutations this prompt still has to write.
- **Company knowledge**: the same for company-wide documents, plus the ability to trigger a re-index. **The read hooks already exist here too** — `useCompanyKnowledge`, `useCompanyKnowledgeStatus`. The two `GET .../knowledge/{filename}` download routes were **deliberately** left without a query hook in 005.01: they return a file, not cacheable JSON, and want a direct `api.GET` call rather than a `useQuery` wrapper.
- **Company users**: a list, with a dialog to add or edit one.
- A way to start a chat with a role from its dialog.
- **The ADR-011 permission flags, inherited from 002.05.** That prompt enforced _membership_ — a caller reaches only companies they belong to — and deliberately did not build the five permission flags (`create_tasks`, `initiate_conversations`, `access_storage`, `modify_company`, `define_agent_roles`), because there was no surface to set them. This view is that surface. Doing it means: a migration adding `permissions` to `CompanyUser`; a defaulting policy (a `creator` holds all of them; decide what a new `member` gets, and record the decision); a `@RequirePermission()` guard declaration per route, following the `@CompanyScope` pattern `002.05` established in `apps/backend/apps/tcp-server/src/auth/`; and the editing controls here. Until it lands, **any member of a company may take any action within it** — say so in the users list rather than implying the roles column restricts anything.

## Implementation notes

- **Reuse `ActivityList` for every list here.** `ActivityList` in `pages/CompanyPage/activity/` is the shared frame for a live list (region, heading, count, and the loading, error, empty and populated states) that 007.01 built. Carried from 007.01: no list has been built since, so this is the first chance to reuse it rather than re-implement its four states.
- Check `tcp-cli`'s corresponding commands for the real fields and behaviours rather than guessing: role management, knowledge upload and retrieval, index status, and company user management.
- **File upload is new to this application.** Progress, failure and cancellation all need handling, and the accessible upload control is the part most likely to be got wrong.
- Uploads have server-side type restrictions. Surface them before a user picks a file, not only after a rejection.
- Indexing is asynchronous. Decide how status updates reach the user, and whether re-indexing gives feedback beyond "started".
- The API returns soft data-quality warnings on some create and update routes. Surface them.
- **Editing company users is permission-relevant, and `002.05` has landed.** Membership is now the access control, so this view edits the thing that grants access: adding a row grants a person the whole company, removing one locks them out, and `CompanyUser.identifier` is an OIDC `sub` **or** an email address — a row added with the wrong form silently grants nobody anything. Make which one is being entered unambiguous. Removing the last `creator` is the obvious footgun. See [ADR-011's 002.05 amendment](../../ADRs/ADR-011-authentication-authorization.md#amendments-as-implemented-00205) and `route-audit.spec.ts`, which every new route must satisfy.
- Reuse the MVP's dialogs, states, announcer and transcript components. Don't build parallel versions.
- Deleting knowledge is destructive — confirm first, and manage focus afterwards.

## Testing

- Component tests for every list, dialog and form, queried by role and accessible name.
- Tests for the role name filter, including no matches.
- **Upload tests**: success, rejected file type, failure mid-upload, and cancellation.
- Tests for download and delete, including the delete confirmation and where focus lands after.
- Tests for indexing status display and for triggering a re-index.
- Tests for company user create and edit, including validation errors associated with their fields.
- **A test that the tab component now works with two tabs**, including keyboard navigation between them.
- Accessibility assertions on every view, dialog and form, including error and in-progress states.
- **Announcement tests using `spokenPhraseLog()`** for anything that updates asynchronously, especially indexing status.
