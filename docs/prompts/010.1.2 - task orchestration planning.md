# Task orchestration

## Role modes

Each agent is given a role, and should also be given a mode. The 3 main modes are:

- `plan`: a new mode, permitting extended access to the planning MCP service (all agents have limited access to the planning service if they have an assignment)
- `implement`: the mode that best represents the _current_ implementation (eg. initiated through chat) - for implementing an assignment
- `qa`: a new mode, which permits an agent, given materials and the wording of a prompt, to use the planning MCP service to accept / reject the materials

As discussed elsewhere, the `implement` mode with a default assignment should be used for:

- non-task conversations (eg. intiated through lcp-cli)
- conversations initiated by agent-to-agent consultation

The mode determines which type of assignment will be generated for the agent to fulfil. Agents will always be given an assignment. (This is new - at the moment, agents do not have an assignment. The assignment provides information like: the prompt, role, and other expectations - such as materials artifacts that the agent is guided towards using, and expected artifacts that the agent is expected to provide.)

### `plan` mode

When a task is created, it is handed to an `LcpAgent` with a role specified in the request or the planner role defined on `LcpCompany`, and the `plan` mode.

The agent is given an N-part prompt (very similar to the regular multi-part agent prompt) instructing it to create a full plan. It has access to all other feature available to `LcpAgent` - eg. it can consult with other roles or query users as a part of its process.

We should break out the N-part prompt provision into separate, clean, business logic that can generate the prompts for `plan`, `implement`, and `qa` modes.

When an `LcpAgent` is started in `plan` mode, it is given a planning prompt instead of the system prompt. This describes how to construct a plan using a new planning MCP service.

### `qa` mode

When an `LcpAgent` is started in `qa` mode, it is given a QA prompt instead of the system prompt.

## MCP service: `lcp-mcp-tasks`

The `lcp-mcp-tasks` MCP service can expose different tools to an `LcpAgent` depending on the `mode` that the agent is launched with.

### Mode prompts

The `lcp-mcp-tasks` MCP service is responsible for providing the prompt explaining how to operate in `implement`, `plan`, and `qa` modes - ie. it is the source of a mode prompt. Examples (but these should be strengthened or modified for the clarity that LLMs need, and corrected for the actual implementation):

> You are in `plan` mode. Use the `create_plan` tool to design a plan that will achieve the task prompt. A plan is an ordered list of assignments. Each assignment is a prompt, a role to give it to, and a set of expected outputs. Each assignment will automatically be directed towards materials that have been output from all assignments that came before, plus any specified here. You must call the `create_plan` tool before completing this chat. Use the `describe_service` tool on the tasks service for more information about how to do this when you are ready.

> You are in `implement` mode. Follow the instructions or answer the question in your assignment prompt. Some materials are highlighted for you in the assignment materials list, but you may explore the shared storage if necessary to find other related material. You must complete the assignment before closing the chat. To complete an assignment, you must perform the actions required by the assignment, and then call the `complete_assignment` tool. Provide all items to list as complete. These must meet or exeed the list of expectations in the assignment. Use the `describe_service` tool on the tasks service for more information about how to do this when you are ready.

> You are in `qa` mode. Review the assignment prompt and the list of complete artifacts. Read each artifact listed as complete, and verify that it meets the needs of the assignment prompt. Use the storage service to read artifacts. Confirm whether the goal of the assignment prompt is complete, or if there's more to do. Use the tasks service to submit your assurance (either accept, or reject with feedback).

### Tools

| Tool                  | Available in modes | Required in modes | Purpose                                                                                                 |
| --------------------- | ------------------ | ----------------- | ------------------------------------------------------------------------------------------------------- |
| `describe_service`    | \*                 | -                 | Provides a short description of available tools, and enables those tools (for limited iterations[^mcp]) |
| `create_plan`         | `plan`             | `plan`            | Creates a plan from a list of assignment details                                                        |
| `complete_assignment` | `implement`        | `implement`       | Completes an assignment with a list of artifacts to list as complete                                    |
| `assure_assignment`   | `qa`               | `qa`              | Marks an assignment approved or rejected (with feedback), resumes the assignment's agent with feedback  |

[^mcp]: similar to how this is done with other mcp services and their tools

#### Required tool calls

The required tool calls should also be provided by the `lcp-mcp-tasks` MCP service per mode, eg.

- `plan` mode: `create_plan`
- `implement` mode: `complete_assignment`
- `qa` mode: `assure_assignment`

### Planning tools

All agents:

- The `LcpAssignment` is provided as part of the N-part prompt, with a prompt relating to the agent's mode, providec by the `lcp-mcp-tasks` service.
- `LcpAgent.requiredToolCalls` should be set appropriately from

All agents may:

- get a description of the tools provided by the service (similar to the other MCP services)

The planner may:

- construct a simple linear plan by specifying a list of the basics of the assignments, eg. with params `{ prompt: string, role: string, expected: LcpExpectedArtifact[] }[]`

> [!NOTE]
> For now, the agents may not review the contents of the plan, or modify the plan after creation. This is desirable in future - but complicates the initial implementation.

### Assignment tools

All agents may:

- declare their assignment complete by providing a list of complete artifacts, eg. with params `{ type, value }[]`

A QA agent may:

- accept all of an assignment's complete artifacts
- reject some of an assignment's complete artifacts with feedback (this will cause the orchestration to resume the previous assignment with an additional prompt explaining that the artifacts are not considered sufficient, and appending some feedback explaining what needs to be done)

eg. This could be done with an assurance tool, with `{ qa: 'accept' } | {qa: 'reject', feedback: string }`

NB. We should migrate the current task completion tool to lcp-mcp-assignment, and modify the way regular conversations work to _be_ a simple 'orphan' assignment (ie. without a supporting task / plan).

## Interfaces

The interfaces below _illustrate_ how tasks and assignments could fit together. Please propose the implementation to use as a part of the plan.

- Tasks (`LcpTask`) are at the top level of a process.

- Each `LcpTask` points to an `LcpAssignmentPlan` (a list of assignments for the task).

- Each `LcpAssignment` is for a specific role, states the prompt and expected artifacts to be output from the assignment. Each assignment is provided with a (deduplicated) superset of all _approved_ artifacts from previous assignments, plus the initial set of materials on the task.

```ts
interface LcpTask {
  request: string;
  plannerRole: LcpRole;
  status: 'ready' | 'in-progress' | 'succeeded' | 'failed' | 'cancelled';
  materials: LcpMaterialArtifact[]; // artifacts provided for the task: of type `materials-path` only
  expected: LcpTaskCompletedArtifact[]; // artifacts expected to be included in the output of the task
  completed: LcpTaskCompletedArtifact[] | null; // artifacts marked as the output of the task
  plan: LcpAssignmentPlan; // an ordered list of assignments
}

type LcpAssignmentPlan = LcpAssignment[]; // for now, this is an ordered list of assignments

interface LcpAssignment {
  task: LcpTask | null; // not all assignments are associated with a task
  prompt: string;
  role: LcpRole;
  status:
    | 'ready'
    | 'in-progress' // enters 'in-progress' when an agent is assigned, or when qa causes the assignment to be resumed
    | 'in-qa'
    | 'succeeded'
    | 'failed'
    | 'cancelled';
  agent: LcpAgent | null; // must be set when the assignment is 'in-progress'
  materials: LcpMaterialArtifact[]; // hints of artifacts the agent might refer to, to complete its assignment
  expected: LcpAssignmentWorkingArtifact[]; // artifacts expected to be included in the output of the assignment
  prepared: LcpAssignmentWorkingArtifact[]; // artifacts for the output of the assignment, ready for QA
  approved: LcpAssignmentCompletedArtifact[]; // artifacts marked as the output of the assignment after QA
  qa: {
    status: 'accepted' | 'rejected';
    feedback: string | null;
  } | null; // qa is set to null when an assignment enters 'in-progress' state
}

interface LcpArtifact {
  /**
   * - `task-materials-path` describes a path which will be prefixed with: `{company_slug}/tasks/{task_id}/materials/`
   * - `task-completed-path` describes a path which will be prefixed with: `{company_slug}/tasks/{task_id}/completed/`
   * - `assignment-working-path` describes a path which will be prefixed with: `{company_slug}/tasks/{task_id}/assignments/{index}/working/`
```

## State management

Tasks and assignments can be in a number of states:

`LcpAssignment` states:

- `ready` - default state
- `in-progress` - an `LcpAgent` has been created for this assignment, and is in progress
- `in-qa` - an `LcpAgent` is currently in `qa` mode and assessing the outputs from the assignment
- `succeeded` - the prepared assignment artifacts have passed QA, are copied to the completed directory, and the `approved` property lists them
- `failed` - the completed assignment artifacts have failed QA after N successive attempts
- `cancelled` - a user has cancelled this assignment before it could start or complete

`LcpTask` states are updated whenever an assignment related to the task changes state:

- if any assignment is in one of these states, the task enters the same state: `failed`, `cancelled`
- if not, then if any assignment is in state `in-progress` or `in-qa`, the task should be in state `in-progress`
- if not, then if all assignments are in state `succeeded`, the task should be in state `succeeded`
- if no other rules apply, the task should be in state `ready`

> [!NOTE]
> Future work:
>
> - A separate user action, initiated through a new lcp-server endpoint, will be used to cancel all remaining `pending` / `in-progress` assignments from a task
>   - lcp-cli does not yet support listing, inspection, and management of tasks and assignments, but will do so in future
>   - Cancelling an `in-progress` assignment will also halt its running agent

## Completed materials

As an assignment enters `succeeded` state (ie. after QA), the working materials are _copied_ into the completed directory: `{company_slug}/tasks/{task_id}/assignments/{index}/completed/` and the assignment's `approved` property is updated to reference the completed versions of all `prepared` items (inline-text items are copied from the `prepared` list to the `completed` list).

## Special assignments

### Initial planning

A planner agent is given a planning prompt (alongside the rest of the N-part prompt) instructing it to plan out a task, and giving it infomation about how to do that. This agent is required to call the `create-plan` tool, which accepts information to create an `LcpTask` with an `LcpAssignmentPlan`, materials, and expectations.

### Assignment QA

After each assignment in the task plan completes, an agent runs against the assignment in `qa` mode. It has the `qa` prompt, which instructs it to evaluate the items in `prepared` and approve or reject the assignment (with feedback) if the items do not meet requirements.

NB. The mechanical gate of "do the `prepared` items meet or exceed the `expected` items?" should already have been passed. An assignment should fail to complete and enter `in-qa` state if anu `expected` artifacts are not found in the `prepared` list.

TODO: Should the agent be forced to evaluate each individual item, one at a time? ie. Should there be a fully different agent loop to do it? This feels sensible - each could then be individually marked as sufficient (or not) - and this would allow for small agents with small context windows to help prevent them from being overwhelmed.

However it's implemented the agent should:

- review all items to establish if they contain expected content for the assignment
- determine if the assignment is accepted or rejected (with feedback)
- approve or reject the assignment using the assurance tool based on these findings

If approved, the assignments files should be copied to `completed/` directory for the assignment, and the `approved` list on the assignment (and `inline-text` items should be copied from the `prepared` list to th `approved` list).

### Finalisation

This will be developed in a future piece of work. The finalisation involves identifying and copying appropriate outputs from the assignments to the task output.

For now, if the final assignment of a task completes successfully, all `completed/` files from all assignment in the task should be copied to the task's `completed/` directory.

## Materials

Materials provided to each assignment on starting, in the `materials` property:

- materials on the task (if a task is associated with the assignment)
- completed items from each assignment that came before it in the task plan

NB. for an `assignment-completed-path`, the actual path is derived from the most recent assignment that included the path in its `completed` list - ie. even if a file is updated several times (and so it appears in the `completed` list of several assignments), the most recent version is used.
