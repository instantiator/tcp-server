## Entity ids

In some places, the `lcp-cli` verbs use `--role-id`, `--role-slug`, `--company-id`, `--company-slug`, and in others they use `--role`, `--company` and distinguish between them automatically. Please ensure that all verbs offer all variants of each entity they use (role/company).

Ideally: `--company` and `--role` distinguish between slugs and ids automatically, but I'd like to be able to still offer the `-id` and `-slug` suffix variants in every place these appear.

Roughly:

- if it matches a UUID regex, it's _probably_ an id, check the ids for a match
- if not, it's _probably_ a slug, check the slugs for a match
- if neither matches, then this entity is not found

I appreciate this makes things slightly complex in implementation, especially as it's needed for a variety of verbs, but it simplifies the user experience a little - so I think it's worth it.

Find a way to DRY this as far as possible, ie. a way to express a parameter like `--role`-or-`--role-slug`-or-`--role-id` as simply as possible when defining a command's parameters.

## TUI: Company task lists

The lcp-cli TUI should offer a selectable (and grouped) list of the company's tasks, on the company panel.

This means that the selection indicator (`>`), which can be moved up and down, should also be able to pass down beyond the roles list and into the tasks lists, and so forth - cycling back to the top when it goes off the bottom of the last list. Generalise: it should be possible to show multiple lists in a panel, and for the selection indicator to move between them. Lists should have a title, and group titles when items are grouped. It should also be possible to jump between lists with an intuitive shortcut which can be shown in the bottom-bar (if it will fit) and the help panel.

The lists should be grouped as:

1. active tasks first, in descending chronological order (most recent first)
2. completed/failed tasks, in descending chronological order

Each entry should have:

1. Date and time of the task in format: `yyyy-MM-dd HH:mm:ss`
2. Current task state and completion indicator eg. `(in progress: 3/5)`
3. Initial prompt for the task, filling the remainder of the line (truncate with ellipsis)

eg. `2026-07-13 11:15:00 (in progress: 2/3) "Write a short story about a cat."`

When highlighted the prompt should expand, if it was truncated and word-wrap - covering `const TASK_LIST_ENTRY_MAX_LINES` lines (derived from config variable that can come from a cli parameter or env variable, or a default if neither is provided), with a space between it and other items in the list.

The list should update whenever a task changes state. At current time, there may not be an SSE endpoint for company-wide events. This is something any UI will need - so lets implement a version of it now that updates for:

- changes to the company
- changes to the company's tasks

## TUI: Task panel

On selecting a task, a new panel should open showing the task. Again this will need an SSE endpoint for the task, so that it can be updated as its state changes.

Content of the task panel:

```
Id:     <task id>
Prompt: "<task prompt in full (word wrapped, each subsequent line indented)>"

Assignments

> 1. <role> <status> "<full prompt>"

  2. <role> <status> "<truncated prompt>"
  3. ...etc.
```

Again, each entry that was truncated shows up to `TASK_LIST_ENTRY_MAX_LINES` when highlighted.

There should be an intuitive way to cancel the task from this view, with a keyboard shortcut shown in the bottom bar (if the task is running) and always in the help text. (See 'Task cancellation' also in this prompt.)

Colour scheme for status:

- waiting: grey
- in-progress: cyan
- succeeded: green
- failed: red
- cancelled: yellow

Only entries that have begun should be selectable.

Selecting an entry should open a read-only panel of the chat for that assignment (regardless of whether it has completed or not). If it has not completed, then the TUI should use the SSE endpoint for that conversation to ensure it keeps track of the conversation.

## Chat output

### Show user prompts

In non-TUI mode, chat should always show the input from the user with stderr (this is currently missing), with an indicator and colour indicating that it's from the user.

In TUI mode, similarly, prompts from the user should be shown, with indicator and colour.

Spacing between items in the chat output should also be applied to these entries.

### Blank responses

Sometimes we see a log of a blank response printed by the tool: `hh:mm:ss | response |`

In those special cases, where the response is whitespace or blank, please modify the tool to print `hh:mm:ss | response | (blank)`

## CLI commands for orphaned assignments

Orphaned assignments are intentionally created when initiating a chat through lcp-cli. There's currently no way to see those, or to understand what's currently going on in the company other than by looking at tasks.

Please add a `list-agents` verb, which:

- shows all agents for a given role (if a `--role` variant is set)
- shows all agents for a given company (if a `--company` variant is set)
- accepts 0 or more filters:
  - `--filter status=<status>` (defaults is currently active agents)
  - `--filter role=<role-slug-or-id>`
  - `--filter assignment=<assignment-id>`

Please add a `list-assignments` verb, which:

- shows assignments for a given task (if `--task-id` is set)
- shows all assignments for a given company (if a `--company` variant is set)
- accepts 0 or more filters:
  - `--filter status=<status>`
  - `--filter task=<task-id>`
  - `--filter task=null` (special case, filters to orphaned assignments)
  - `--filter role=<role-id-or-slug>`

Please add an `eavesdrop` verb which gives a view of what came before and what's happening now:

- select an entity to eavesdrop on by providing `--agent-id` / `--assignment-id` / `--task-id`
- `--show-history` shows historical events, state changes, chat messages etc.
  - reconstruct from audit logs
  - use the same formatting as `chat`
  - print everything to stdout (not just the final response)
- follows the planning assignment (if a `--task-id` given)
- follows QA assignments and the finalisation assignment (if a `--task-id` given)
- follows consultations
- `--tail` shows current events, reasoning, state changes, messages etc.
  - warns and exits if the conversation / assignment / task is not complete
