# Memory and knowledge: overview (010.7.0)

This document is the map for the memory-and-knowledge work requested in
`010.7 - exercise memory and knowledge.md`. It is **not** an implementation
prompt. The work is divided into four ordered, self-contained sub-plans —
each implemented in its own session with the instruction "Please implement
the plan laid out at: `<path>`", following the same structure as the
`010.2.x` task-orchestration series.

## Sub-plans, in order

| #   | File                                                                             | Focus                                                                              | Model  |
| --- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------ |
| 1   | `010.7.1 - memory and knowledge: wider ingestion and OKF generation.md`          | Multi-format knowledge upload (md/txt/html/pdf/docx/csv/json/yaml), OKF generation | Sonnet |
| 2   | `010.7.2 - memory and knowledge: index status verb.md`                           | `get-knowledge-index-status` verb + supporting server endpoint                     | Sonnet |
| 3   | `010.7.3 - memory and knowledge: manual RAG query.md`                            | No-LLM manual RAG-query CLI verb + supporting server endpoint                      | Sonnet |
| 4   | `010.7.4 - memory and knowledge: automated testing and mcp-memory migrations.md` | Round-trip tests for knowledge + memory; fixes a real e2e test-infra gap           | Sonnet |

All four are well-specified and pattern-following (extend existing services,
mirror existing CLI/API conventions) — Sonnet is recommended throughout.

1 and 4 are the largest. 2 and 3 are independent of each other and of 1 (they
add new read-only endpoints/verbs), but are sequenced after 1 since 010.7.4's
knowledge round-trip test is most useful once 1 has landed. 010.7.4's MCP
round-trip test only depends on the migrations-in-test-setup fix, not on 1–3.

## Shared context (established during planning — do not re-derive)

- **"OKF" in this codebase today is minimal**: `libs/lcp-shared/src/storage/validation/okf-validator.ts`
  only requires YAML front-matter with a non-empty `title` field. There is no
  vendored copy of the external OKF spec and no support for richer sections/
  metadata. Do not invent new required front-matter fields as part of this
  work — match what's actually enforced.
- **Zero LLM calls exist anywhere in ingestion today.** `EmbeddingService`
  (`libs/lcp-shared/src/rag/embedding.service.ts`) only calls an embeddings
  endpoint (OpenAI-compatible: LM Studio or OpenAI, per `LlmConfig.provider`
  — not "Anthropic embeddings API", which doesn't exist; this is a pre-existing
  inaccuracy in `docs/ADRs/ADR-006-agent-memory-architecture.md`'s Decision
  section, corrected in 010.7.1). OKF titles for converted documents are
  generated by heuristic (first heading → filename), **not** by an LLM call —
  keep ingestion LLM-free.
- **Library decision**: do not add `@nanocollective/get-md` (checked during
  planning: MIT-licensed and real, but 77 GitHub stars, 1 open issue, ~1,068
  weekly npm downloads, v1.6.0 shipped days before this plan was written).
  Compose the underlying, individually mature libraries directly instead —
  `turndown`/`turndown-plugin-gfm`/`cheerio` (HTML), `pdf-parse` (PDF),
  `mammoth` (DOCX) — each with 6-27 million weekly downloads. `.csv`/`.json`/
  `.yaml` get a hand-rolled wrap-in-fenced-code-block converter (no new
  dependency).
- **RAG retrieval already exists as an internal-only service.**
  `RagRetrievalService.retrieve` (`apps/lcp-server/src/rag/rag-retrieval.service.ts:53-89`)
  and its lcp-agent duplicate (`AgentRagService.retrieve`) are only ever
  called from the prompt-assembly path — no HTTP endpoint exposes them today.
  010.7.3 exposes `RagRetrievalService` directly (it is already LLM-free —
  embedding-only).
- **`KnowledgeIndexState` has no count/size columns** (`generation`,
  `fingerprint`, `updatedAt` only) — 010.7.2 derives document count/size from
  `StorageService.listKnowledgeFiles` and chunk count from a new `COUNT(*)`
  query, rather than adding new state columns.
- **The lcp-mcp-memory e2e migrations gap is a test-infrastructure issue, not
  an application bug.** `apps/lcp-mcp-memory/src/app.module.ts` deliberately
  runs no migrations of its own — same pattern as `apps/lcp-agent/src/app.module.ts`,
  whose comment states "migrations are lcp-server's responsibility" (single
  migration owner; in real deployments lcp-server runs first). The gap is
  that `test/e2e/lcp-mcp-memory/*.e2e-spec.ts` boots lcp-mcp-memory's
  `AppModule` in isolation against a fresh testcontainers Postgres with no
  migrations ever run against it, so `knowledge_chunk`/`episodic_memory`
  don't exist — this is why today's `mcp.e2e-spec.ts` only tests transport
  (initialize/405s) and never calls a real tool. 010.7.4 fixes this in the
  **test setup** (run lcp-server's migrations against the shared test
  database before exercising lcp-mcp-memory's tools), not by giving
  lcp-mcp-memory's own `AppModule` a migrations array.

## Deferred (out of scope for all sub-plans)

- Adopting more of the real external OKF spec (structured sections, ids,
  relations) beyond `title` — noted as a future option if richer metadata is
  ever needed.
- Memory consolidation and the memory scrubbing API (already deferred per
  ADR-006; untouched by this work).
- A persisted "default company" CLI context (raised and explicitly deferred
  during 010.2.1; still not needed here).
