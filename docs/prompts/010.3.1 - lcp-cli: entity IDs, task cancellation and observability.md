# lcp-cli 010.3.1: entity IDs, task cancellation & observability verbs

Part 1 of the 010.3 lcp-cli improvements (map: `010.3 - lcp-cli improvements for
tasks and assignments.md`). Parts 2–3 (`010.3.2`, `010.3.3`) add SSE endpoints
and the TUI panels; this part is the CLI-and-backing-REST layer they build on.

> **Recommended implementing model: Opus.** Most of this is careful
> transcription against existing patterns, but two areas are subtle — the
> cross-process cancellation propagation (§2) and the audit-log history
> reconstruction for `eavesdrop` (§3). Section 1 (entity-ID DRY) is
> mechanical and Sonnet-suitable in isolation, but it is a prerequisite for the
> new verbs, so keep it in this part.

## Goal

Three independent improvements to `lcp-cli` and the REST API behind it:

1. **Entity-ID DRY.** Every verb that takes a role or company should accept all
   of `--role` / `--role-id` / `--role-slug` (and the company equivalents), with
   `--role`/`--company` auto-distinguishing a UUID from a slug. Consolidate the
   three overlapping resolvers that exist today into one small module.
2. **Task cancellation.** A `POST /api/task/:id/cancel` endpoint, propagation to
   any running agent, and a `cancel-task` verb.
3. **Observability verbs.** `list-agents`, `list-assignments`, and `eavesdrop`,
   plus the backing list/history REST endpoints they need.

Plus a small **non-TUI chat-output** fix (§4): echo the user's own prompt, and
mark blank responses.

No TUI changes in this part.

## 1. Entity-ID resolution (DRY) — do this first

### The problem

Three resolvers do overlapping work today:

- `apps/lcp-cli/src/lib/core/resolve-identifiers.ts` — split flags
  `--company-id`/`--company-slug`/`--role-id`/`--role-slug`; `resolveCompanyId`,
  `resolveRoleId`. No UUID sniffing (the flag name declares the type).
- `apps/lcp-cli/src/lib/core/resolve-knowledge-scope.ts` — combined
  `--role`/`--company`; holds the **only** `UUID_RE` in the CLI and sniffs
  UUID-vs-slug, returning a knowledge path segment.
- A third copy of the sniff helper inside `apps/lcp-cli/src/lib/tasks/task.action.ts`
  (used by `create-task`/`list-tasks`/`get-task` for `--company`/`--planner-role`).

Different verbs use different conventions; the prompt wants **all variants
available everywhere**.

### The target

New `apps/lcp-cli/src/lib/core/entity-ref.ts` — the single home for entity
identifier options and resolution. It exports:

```ts
/** UUID sniff — the one canonical copy (moved from resolve-knowledge-scope.ts). */
export const UUID_RE =
  /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;

/** Every entity-identifier option a verb might accept. All optional; the
 *  resolvers enforce "at least one" and give clear errors. */
export interface EntityRefOpts {
  company?: string; // --company <slug-or-id>
  companyId?: string; // --company-id <uuid>
  companySlug?: string; // --company-slug <slug>
  role?: string; // --role <slug-or-id>
  roleId?: string; // --role-id <uuid>
  roleSlug?: string; // --role-slug <slug>
}

/** Commander option-builders — one call adds all variants to a command. */
export function addCompanyOptions(
  cmd: Command,
  opts?: { required?: boolean },
): Command;
export function addRoleOptions(
  cmd: Command,
  opts?: { required?: boolean },
): Command;

/** Resolve to a company UUID. Precedence: --company-id → --company-slug →
 *  --company (UUID_RE ⇒ id-as-is, else slug → GET /api/company/:slug). */
export async function resolveCompanyId(
  api: ApiOptions,
  opts: EntityRefOpts,
): Promise<string>;

/** Resolve to a role UUID. Precedence: --role-id → --role-slug → --role
 *  (UUID_RE ⇒ id-as-is; slug ⇒ requires a resolvable company, then
 *  GET /api/company/:companyId/roles/by-slug/:slug). */
export async function resolveRoleId(
  api: ApiOptions,
  opts: EntityRefOpts,
): Promise<string>;
```

Design rules to encode:

- **Precedence is fixed**: explicit `-id` beats explicit `-slug` beats combined
  `--role`/`--company`. If both an explicit variant and the combined form are
  given and they disagree, that's not worth detecting — precedence wins silently
  (keep it lazy; note it in a `//` comment).
- `--company` / `--company-id` are used **as-is** without a lookup when they look
  like a UUID or are passed to a company route (the server accepts a slug on
  company routes), but resolve `--company-slug` locally so slug-only flows fail
  fast with a CLI error instead of a deep 404 — this preserves the existing
  `resolve-identifiers.ts` behaviour and rationale.
- Role slugs are unique only within a company → a slug (from `--role-slug` or a
  non-UUID `--role`) requires a resolvable company; reuse the existing error
  wording.
- Reuse `apiRequest` and the existing endpoints
  (`GET /api/company/:slug`, `GET /api/company/:companyId/roles/by-slug/:slug`).

`addCompanyOptions`/`addRoleOptions` replace the copy-pasted `.option()` blocks.
Example migration for `chat`:

```ts
// before: four hand-written .option() lines for company/role id+slug
// after:
addRoleOptions(addCompanyOptions(program.command('chat')));
```

Keep the short flags the verbs already advertise (`-c` for company, `-r` for
role) where they exist. Where a verb previously used `-r` for something else
(e.g. `create-task` uses `-r, --request`), do **not** collide — that verb keeps
`--planner-role` via `addRoleOptions` mapped to the role trio, and its
`--request` stays as-is. Audit each verb's existing short flags before wiring.

### Migration checklist

Migrate **every** verb that takes a company or role to the new options +
resolvers, keeping all suffix variants working:

- `chat` (`src/lib/chat/*`), `estimate-context-window`, `set-role`,
  `delete-role`, `set-company`, `delete-company`.
- Knowledge verbs (`get-/list-/store-/delete-knowledge`, `reindex-knowledge`):
  these resolve to a **path segment** (`role/<id>` or `company/<slug-or-id>`), not
  a bare id. Keep a thin `resolveKnowledgeScopePath(api, opts)` **in
  `entity-ref.ts`** built on top of `resolveRoleId`/`resolveCompanyId` (so the
  UUID_RE and lookups aren't duplicated). Delete the old
  `resolve-knowledge-scope.ts`.
- Task verbs (`create-task`, `list-tasks`, `get-task`): replace the local sniff
  helper in `task.action.ts` with `resolveCompanyId`/`resolveRoleId`.
- Delete `resolve-identifiers.ts` and `resolve-knowledge-scope.ts`; update all
  imports. Grep before deleting: `resolveRoleId`, `resolveCompanyId`,
  `resolveKnowledgeScopePath`, `CompanyIdentifierOpts`, `RoleIdentifierOpts`,
  `KnowledgeScopeOpts` — across `src/` **and** every `test/` dir (per the
  grep-test-dirs-on-refactor rule).
- Update `src/lib/chat/flags.ts` validation to the unified option set (still
  reject nonsensical combinations, e.g. a role slug with no company).

### Tests

- Unit `entity-ref.spec.ts`: precedence table (id > slug > combined), UUID vs
  slug sniff, slug-without-company error, both resolvers, and
  `resolveKnowledgeScopePath` path shaping. Mock `apiRequest`.
- Update each migrated verb's existing CLI test to exercise at least the
  combined `--role`/`--company` form once (proves the wiring), plus keep the
  suffix-variant coverage that already exists.

### Docs

- `docs/lcp-cli.md`: document that role/company accept `--x`, `--x-id`,
  `--x-slug` everywhere, with the UUID-vs-slug rule stated once.

## 2. Task cancellation

### API — `POST /api/task/:id/cancel`

We use **POST** (a state transition to `cancelled`, not resource removal —
mirrors the existing `POST /api/task/:id/start`; the cancelled task stays
listable/inspectable). DELETE is deliberately not used.

- Controller: add `cancelTask` to `apps/lcp-server/src/api/task.controller.ts`
  (JWT-guarded, Swagger-decorated like `startTask`), returning **202** with the
  updated task.
- Service: `TaskService.cancel(id)` in `task.service.ts`:
  - Atomic guard using the `claimStatus` pattern already used by `start`: only
    transition a task in a **non-terminal** status (`ready | planning |
in-progress | finalising`) → `cancelled`. If the task is already terminal
    (`succeeded | failed | cancelled`) → **409**. Unknown id → **404**.
  - Cascade: set every **non-terminal** assignment of the task to `cancelled`,
    and each such assignment's working agent (if any) to the new
    `AgentStatus.Cancelled`. Route these through
    `TaskOrchestrationService.recordTaskState` / `recordAssignmentState` so the
    existing audit entries fire (and so the SSE emit points added in `010.3.2`
    pick them up automatically). Spell out the ordering explicitly: **task →
    assignments → agents**, and make the whole operation **idempotent** (a
    second cancel on an already-cancelled task is a 409, and re-running the
    cascade is a no-op on rows already terminal).

### Live-agent propagation

The agent loop (`apps/lcp-agent/src/agent/agent-loop.service.ts`) already stops a
running agent by re-reading its DB row each iteration (`checkTerminalStatus`,
which today treats `Paused`/`Completed` as terminal).

- Add `Cancelled = 'cancelled'` to the `AgentStatus` enum
  (`libs/lcp-shared/src/models/LcpAgent.model.ts`).
- Extend `checkTerminalStatus` to treat `Cancelled` as terminal (stop the loop,
  do not mark the agent `failed`/`completed`).
- Not-yet-started BullMQ jobs need no special handling — dispatch already checks
  task status before starting work, so a cancelled task's queued assignments are
  skipped.
- `// ponytail:` note the mechanism: cancellation of a _running_ agent is
  observed on the next loop iteration via the DB status poll (bounded by one
  iteration's latency); a cross-process abort into `AgentRegistryService`'s
  `AbortController` is the upgrade path if instant interruption is ever needed.
  Do **not** build the abort path now.

### CLI — `cancel-task`

- New `src/commands/cancel-task.ts` + `src/lib/tasks/*.action.ts`:
  `cancel-task --task-id <uuid>` → `POST /api/task/:id/cancel`, print the updated
  task as JSON. Register in `main.ts`.

### Tests

- e2e (`test/e2e/lcp-server/task.e2e-spec.ts`): cancel a `ready` and an
  `in-progress` task (202 + assignments cascade to `cancelled`); cancel unknown
  (404); cancel an already-terminal task (409); double-cancel (409, idempotent).
- Unit: extended `checkTerminalStatus` recognises `Cancelled`.
- CLI test for `cancel-task`.

### Docs

- `docs/lcp-cli.md` (verb) and the task doc / ADR-010 amendment (dated): the
  cancel path, the cascade order, and the new `AgentStatus.Cancelled`.

## 3. Observability verbs & backing endpoints

### Backing REST endpoints

Mirror the existing filtered-list pattern
(`apps/lcp-server/src/api/conversation.controller.ts` `list` →
`?companyId=&status=`). JWT-guarded, Swagger-decorated, DTO-validated query
params. Filter over the already-indexed columns.

- **Agents list** — extend `api.agent.controller.ts` (+ a `listAgents` in the
  service / `DbService`): `GET /api/agent?companyId=&roleId=&assignmentId=&status=`.
  Require at least a `companyId` or `roleId`. Default (no status filter) →
  currently-active agents (`running`/`paused`); `status=` overrides.
- **Assignments list** — new `apps/lcp-server/src/api/assignment.controller.ts` +
  `assignment.service.ts`: `GET /api/assignment?companyId=&taskId=&roleId=&status=`.
  Special-case `taskId=null` (literal string) → orphan assignments (`taskId IS
NULL`). Require `companyId` or `taskId`.
- **Task history (audit replay)** — new read endpoint over `AuditEvent`:
  `GET /api/task/:id/history` (and, for a single agent/assignment,
  `GET /api/agent/:id/history`). Query rows via the composite index
  (`WHERE companyId=? [AND agentId IN (…)] ORDER BY timestamp ASC`) and **map each
  `AuditEvent` back into the `AgentEvent` shapes the live SSE stream already
  emits** (so the CLI renders history and live output identically). Put the
  mapping in a pure, unit-tested helper (e.g.
  `libs/lcp-shared/src/events/audit-to-agent-event.ts`): `llm_request`/
  `llm_response` → `llm`, `decision`/`state_change` → the matching discrete event,
  `tool_call`/`tool_result` → appropriate kinds, `agent_loop_completion` →
  `completed`/`failed`. For a task, gather the agent ids of its planning, QA,
  finalise, and consultation assignments so the replay covers them all.

New/extended services must not duplicate filter logic — one query builder per
entity, parameterised.

### Verbs

All use `entity-ref` options (§1). `--filter key=value` is **repeatable**; parse
into query params (reuse a small shared parser — one helper, not per-verb).

- `list-agents`
  - `--role` (any variant) → agents for that role; `--company` (any variant) →
    agents for that company.
  - `--filter status=<status>` (default: currently active), `--filter role=<slug-or-id>`,
    `--filter assignment=<assignment-id>`.
  - → `GET /api/agent?…`, print JSON.
- `list-assignments`
  - `--task-id <uuid>` → assignments for that task; `--company` (any variant) →
    all company assignments.
  - `--filter status=<status>`, `--filter task=<task-id>`,
    `--filter task=null` (orphans), `--filter role=<slug-or-id>`.
  - → `GET /api/assignment?…`, print JSON.
- `eavesdrop` — the Opus-heavy verb.
  - Target: exactly one of `--agent-id` / `--assignment-id` / `--task-id`.
  - `--show-history`: fetch from the history endpoint and print the full
    reconstructed history to **stdout** (everything, not just the final
    response), rendered with the existing `src/lib/core/render.ts` `createRenderer`
    so it matches `chat`. For a `--task-id`, include the planning assignment, QA
    assignments, the finalisation assignment, and consultations.
  - `--tail`: follow live via the existing per-agent SSE
    (`GET /api/agent/:id/events`, reuse `streamAgent`/`parseSseBuffer`). For a
    `--task-id`, follow the planner + QA + finalise + consultation agents. If the
    conversation/assignment/task is already complete, **warn and exit** (nothing
    to tail).
  - `--show-history` and `--tail` may be combined (print history, then follow).

### Tests

- e2e: each endpoint's filters (company/role/task/status, `taskId=null` orphans)
  and failure codes (400 missing required filter, 404 unknown).
- Unit: the `audit-to-agent-event` mapping (every `AuditEventType`), the
  `--filter` parser.
- CLI tests for the three verbs (mock the endpoints); at least one asserts
  `eavesdrop --show-history` renders via `createRenderer`.

### Docs

- `docs/lcp-cli.md`: the three verbs with their `--filter` keys.
- The events/SSE doc + ADR-008 amendment: the new audit **read** endpoints
  (previously audit was write-only).

## 4. Non-TUI chat output (`render.ts`)

`apps/lcp-cli/src/lib/core/render.ts` `createRenderer` renders the linear
(non-TUI) chat. Two fixes here; the **TUI** equivalents live in `010.3.3`
(cross-referenced) so the behaviour is consistent across both renderers.

- **Show user prompts.** The user's own submitted message is currently never
  echoed. Emit it to **stderr** with a distinct indicator + colour (follow the
  existing `Reasoning:`/`Agent state:` stderr styling), with the same inter-item
  spacing the other blocks use. Wire it where the query/message is sent
  (`src/lib/chat/session.ts` `runTurn`).
- **Blank responses.** When a `response` event's text is empty or
  whitespace-only, render the marker `(blank)` instead of an empty body (the
  `hh:mm:ss | response | (blank)` form is the TUI's; in `render.ts` use its
  `Response:` prefix style with `(blank)` as the body). Do this in one shared
  spot if `render.ts` and the TUI can share a "blank?" check helper — otherwise
  a two-line guard in each is fine (`// ponytail:` if duplicated).

### Tests

- `render.spec` (or the existing renderer test): user-prompt echo goes to stderr
  with the marker; a whitespace `response` renders `(blank)`.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.
- Do not add dependencies unless truly needed; if unavoidable, latest version,
  license/health checked. Do not update existing dependencies. No unrequested
  changes outside this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Never `--no-verify`.

Write unit/integration/e2e/API tests alongside each unit of code — main, edge,
and failure cases; verify HTTP response codes explicitly. Update existing tests
as code changes (grep `test/` directories by class/function name when changing
constructors or behaviour).

Standing instructions:

- If the work becomes exceedingly complex or a problem resists solution, HALT
  and inform the user.
- If you discover a beneficial alteration to this plan, HALT and inform the
  user before proceeding.
- Document any agreed deviations by appending dated notes to this file.
