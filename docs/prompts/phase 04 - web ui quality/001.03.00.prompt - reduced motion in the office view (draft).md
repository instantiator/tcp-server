# 000.02 — Reduced motion in the office view

## Goal

000.01 shipped a simple, honest reduced-motion mode, on purpose: avatars jump
straight to their targets and the camera follows with no easing, so
`prefers-reduced-motion` was honoured from day one and the browser tier could
still assert exact pixel positions. That was step 9 of "Where this plan departs
from the prompt" in [000.01's plan](./000.01.01.plan%20-%20set%20up%20isometric%20display%20elements.md),
and it deliberately left the fuller design to this prompt.

This prompt asks for that plan. It does not build anything itself, and it does
not answer the design questions below — settling them, with the user, is part
of the plan it produces.

## Requirements

- **What 000.01 leaves in place, for the plan to build on:**
  - `apps/frontend/tcp-frontend/src/visualisation/isometric/company/motion/crowd.ts`
    is where reduced motion currently takes effect. `Crowd.sync` and
    `Crowd.planOrJump` send a newly-targeted avatar to `jumpToTarget` instead of
    `plan` whenever `reducedMotion` is true — the walker is recreated straight
    at the resolved tile and an arrival is reported immediately. There is no
    fade, glide or other transition anywhere in this path.
  - `apps/frontend/tcp-frontend/src/visualisation/isometric/company/scene/CameraController.ts`
    fits and centres the camera today. A parallel change is adding a
    `follow(target, reduced)` method that calls Phaser's `startFollow` with
    `lerp` set to `1` when `reduced` is true (no easing) and a small `lerp`
    otherwise — treat that as the 000.01 outcome this plan starts from.
  - `apps/frontend/tcp-frontend/src/visualisation/isometric/company/TcpPhaserVisualisation.tsx`
    carries the `motion-preference` bus event: it emits `{ reduced }` once on
    `scene-ready` and again whenever the `reducedMotion` prop changes.
    Whatever reads the OS setting and whatever the new toggle looks like both
    have to keep feeding that same prop.
  - `apps/frontend/tcp-frontend/test/browser/company-visualisation.spec.ts`
    is the constraint on all of the above. It emulates
    `reducedMotion: 'reduce'` so avatar and camera positions are exact and the
    tests aren't flaky against an animation's timing. **Any change here must
    keep an exact, deterministic mode the browser tier can still rely on** —
    a fuller motion design cannot come at the cost of making positions
    unpredictable when reduced motion is on.
- **The plan must settle these questions, not just list them:**
  - Should an avatar fade in or take a short glide to its target, instead of
    jumping, when motion is reduced?
  - Should a room appearing or disappearing get a transition? What does that
    transition look like in reduced motion — nothing, a fade, something else?
  - Should manual panning (the toolbar buttons and arrow keys) glide to its
    new position, or jump, when motion is reduced?
  - Should there be an in-view motion toggle that overrides the OS setting?
    If so:
    - Does it persist per viewer, the way the theme choice does
      (`apps/frontend/tcp-frontend/src/theme/storage.ts`,
      `apps/frontend/tcp-frontend/src/theme/useTheme.ts`)? ADR-026 already
      settled this shape for theme and contrast: the OS setting seeds the
      first visit, and an explicit user choice is then persisted and never
      overridden by the OS again. Decide whether the same pattern fits
      motion, or whether motion is different enough to need its own answer.
    - Where does it live in the UI, and how is it reached by keyboard?
  - Does any of this need an amendment to ADR-026, following the anchor
    convention already used there (`<a id="amendments-as-implemented-…">`,
    per memory "ADR amendment anchors")?

## Implementation notes

- Read `motion/crowd.ts`, `scene/TcpCompanyScene.ts` and `scene/CameraController.ts`
  in full before planning — the fuller design has to slot into the existing
  `sync`/`tick` split (React decides targets, the crowd decides routes and
  timing) rather than work around it.
- Any new timing or easing maths belongs in `motion/`, as a pure function with
  its own unit tests — the same rule 000.01 followed throughout that
  directory (no React, no Phaser imports).
- If a toggle is chosen, follow the existing theme-control pattern's shape
  (context + hook + a small storage module) rather than inventing a new one,
  unless the plan has a specific reason not to.
- Whatever is decided still has to satisfy ADR-026's "honoured from the
  start" instruction and ADR-027's position that nothing announces avatar
  movement — a fuller reduced-motion design is about how things look, not
  about adding announcements.

## Testing

- Component tests for the toggle itself (if one is built) and for how the
  view reacts to a changed motion preference, whichever way it changes.
- Unit tests for any new pure timing or easing logic added under `motion/`.
- Browser-tier journeys run both with `emulateMedia({ reducedMotion: 'reduce' })`
  and without it, so both the reduced and the full-motion paths are proven,
  not just asserted by omission.
- `axe` on any new control the plan introduces.
