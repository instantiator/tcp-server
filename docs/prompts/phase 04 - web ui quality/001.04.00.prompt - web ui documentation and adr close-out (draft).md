# 001.03 — Web UI documentation and ADR close-out

Create a plan to document the finished web application and bring phase 02's ADRs up to date with what was actually built.

> **Branch:** `p02/009_testing-and-a11y`, off `phase-02` — one branch per major index; see [the workflow](../phase 02 - web ui/README.md)
> **Follows:** [ADR-020](../../ADRs/ADR-020-web-ui-mvp-scope.md) – [ADR-029](../../ADRs/ADR-029-spa-hosting-and-runtime-configuration.md) (all of phase 02)
> **Needs first:** 001.02 (accessibility audit)

## Standing instructions

**Sub-agents are allowed, without asking each time.** Delegating a step to a
sub-agent is the normal way to work here, not an escalation — see
[model allocation](../phase 02 - web ui/model-allocation.md). Prefer Sonnet or Haiku wherever one can
do the step correctly, and keep for Opus the work that document reserves for it.

**Write in simple, clear language.** This covers the plan, the code comments,
the documentation, any ADR amendment, and anything said back to the user. Short
sentences, plain words, and say the thing rather than framing it. Where a
concept is genuinely hard, explain it — do not compress it into jargon.

## Model allocation

**The plan must open with a section allocating work between models**, following
[model allocation](../phase 02 - web ui/model-allocation.md): default to the cheapest model that can do
each step correctly, spell out the detail a Sonnet or Haiku step needs, and let
Sonnet be the reviewer of record for the mechanical ones.

Good Sonnet candidates: drafting the user-facing and operator documentation, and sweeping docs for stale references. **Opus should decide each ADR's status and write the amendments**, since that means judging what actually got built against what was decided.

## Plan storage

NB. The plan's implementation phase should start with a directive to store the plan as `xxx.xx.xy.plan - ******** plan.md` reflecting the prompt's three-part index with the third number incremented by 1, and its name, and if the prompt name is still suffixed with ` (draft)` to remove the suffix, eg.

`002.00.00.prompt - monorepo restructing (draft).md`'s plan is stored as `002.00.01.plan - monorepo restructing.md`, and the original prompt is renamed: `002.00.00.prompt - monorepo restructing.md`

## Carry-forward

**The plan must include a step that writes this prompt's forward-looking work
into the prompts that will do it.** Anything deferred, discovered, or left
half-wired belongs in the prompt that picks it up — written into that file, not
only mentioned in this plan. A note nobody meets while reading the prompt they
are working on has not been recorded, it has been filed.

Where the note is about a test, a constraint or an assumption the later work
depends on, put it in that prompt's own Requirements or Testing section rather
than appending a loose paragraph.

## Goal

Phase 02 made ten architectural decisions and built an application. This prompt makes the record match reality, so the next person doesn't have to reconstruct it from the code.

## Requirements

- Documentation for the web application: what it does, how to run it in development, how it's deployed, and what it needs running.
- Every new doc registered in `docs/index.md`.
- **Each phase 02 ADR's status updated** to reflect what was actually built.
- **Where implementation diverged from a decision, an amendment records it** — not a silent edit to the original text.
- **[ADR-024](../../ADRs/ADR-024-browser-oidc-client-and-token-handling.md) carries amendments (a)–(l) across three prompts, and two of them are the kind that quietly get undone.** Carried forward from 004.03. Confirm (k) survived: `matchSignoutCallback`/`onSignoutCallback` were deliberately **not** wired, against a prompt that asked for them, and a later reader meeting that gap without the amendment will read it as an oversight and fill it. Confirm (l)'s two operator-facing limitations are still stated in `docs/authentication.md` and not only in the ADR — an open stream outliving revocation, and sign-out not propagating between browser tabs.
- Existing docs that this phase made stale are corrected.
- `docs/prompts/README.md` reflects phase 02's real state.
- **State plainly that the SSE payload summary types are outside the OpenAPI contract.** Carried forward from 005.01/005.02: `@Sse` routes carry no response schema, so `schema.d.ts` never carries `AssignmentChangeSummary`, `AgentChangeSummary` or `EnquiryChangeSummary`, and the generated-types drift check cannot police the event contract — those types come from `@tcp/shared/client` instead. Any close-out claim that "the API contract is covered" must say so explicitly, not gloss over the gap.
- **`?all=true` stays administrator-only, and the overview deliberately never sends it.** Carried forward from 006.01: a `403` from the overview is a refusal, surfaced as an error, never folded into the empty state. Confirm the documentation states that distinction rather than describing the overview as "showing no companies" for a non-administrator.
- **Recheck ADR-030's `Live` prefix against `STATIC_ENTITIES` in `src/api/query-keys.ts`.** Carried forward from 007.02: if `role`, `company-user` or `knowledge` gained an event, three hook names (`useCompanyRolesList`, `useCompanyKnowledgeList`, `useRoleState`) are now lying.
- **ADR-026 and ADR-027 both need an "as implemented" amendment covering the dialog and transcript surfaces, once 008.x is complete.**
- **Include the office view in the documentation sweep.** Carried forward from 000.01: `docs/web-client.md` gained a "The office view (company visualisation)" section, and ADR-027 gained a [000.01 amendment](../../ADRs/ADR-027-screen-reader-strategy.md#amendment-as-implemented-00001). Confirm both still match what shipped, the same as every other phase 02/03 decision this prompt checks.

## Implementation notes

- Follow the repo's ADR amendment convention: an appended amendment section with an explicit anchor, rather than rewriting the original decision. The original reasoning stays readable; the amendment says what changed and why.
- Status values come from `docs/index.md`'s own definitions — Proposed, Accepted, Partially Implemented, Implemented, Superseded. **Use them exactly.** (One ADR currently says "Approved", which isn't one of them; fix that while here.)
- Known divergences to check for and record:
  - anything the accessibility audit (001.02) changed, especially ADR-027's two open questions
  - `002.05` (authorization enforcement) **has landed**: ADR-011 carries an [002.05 amendment](../../ADRs/ADR-011-authentication-authorization.md#amendments-as-implemented-00205) and its status is "Partially Implemented (amended)". What remains open there is the **permission flags**, not membership — check that distinction is still stated accurately, since "authorization is deferred" is now wrong and "authorization is done" is also wrong. `route-audit.spec.ts` must still be green and still cover every controller
  - the `@guidepup/virtual-screen-reader` compatibility outcome from 002.02
  - whichever way 007.01 resolved its "assignment dialog" question
  - the minimised-chat streaming decision from 008.02
- Docs likely to need updating: development, testing, scripts, services, authentication, setup checklist, and the port table.
- Write for someone who wasn't here. The ADRs explain _why_; the docs should explain _what it is and how to run it_.
- Follow the documentation clarity conventions in `dev-environment/guidance/standards/documentation.md` — plain language up front, detail below, no unexplained jargon.

## Testing

- Verify every command, path and port named in the new documentation actually works — documentation that's wrong is worse than absent.
- Confirm every relative link resolves, in both directions between ADRs and docs.
- Confirm every new doc appears in `docs/index.md`, and every ADR row matches the ADR's own status line.
- Run the full suite via `./scripts/run-all-tests.sh` as the final check on the phase.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Markdown formatting is clean, and any mermaid diagram is parsed rather than eyeballed — a stray semicolon in a sequence diagram silently kills the whole thing.
- **No ADR left with a status that doesn't match reality.** That's the specific failure this prompt exists to prevent.
- Anything deferred out of phase 02 is recorded somewhere it will be found again.

## Unresolved notes

Before this prompt is done, record what it leaves open in
[unresolved-notes.md](../phase 02 - web ui/unresolved-notes.md):

- **Anything a later prompt will do** — write it into that prompt (see
  [Carry-forward](#carry-forward)) and add a row to that document's
  _Carried into a later prompt_ table, so it is visible from one place.
- **Anything unresolved with no owner** — a compromise taken knowingly, a
  constraint imposed from outside, a decision that can't be taken yet. State
  what would have to be true for it to be revisited.
- **Anything conditional or time-dependent** — an upstream project adding a
  feature, a library dropping a peer constraint, a threshold being crossed —
  needs the entry **and a memory**, because nothing in this repository will ever
  prompt anyone to re-check it. Write the condition so it can be tested, not as
  "revisit later".

If this prompt genuinely leaves nothing open, say so in the plan. Silence and
"checked, nothing to add" read identically afterwards, and only one of them is
true.
