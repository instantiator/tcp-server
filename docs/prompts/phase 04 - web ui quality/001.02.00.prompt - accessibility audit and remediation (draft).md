# 001.02 — Accessibility audit and remediation

Create a plan to audit the finished MVP against its accessibility commitments, and fix what's found.

> **Branch:** `p02/009_testing-and-a11y`, off `phase-02` — one branch per major index; see [the workflow](../phase 02 - web ui/README.md)
> **Follows:** [ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md) (standard, audit layers, screen reader matrix), [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md) (announcement policy, unresolved questions)
> **Needs first:** 001.01 (browser test suite), and every MVP feature prompt

## Standing instructions

**Sub-agents are allowed, without asking each time.** Delegating a step to a
sub-agent is the normal way to work here, not an escalation — see
[model allocation](../phase 02 - web ui/model-allocation.md). Prefer Sonnet or Haiku wherever one can
do the step correctly, and keep for Opus the work that document reserves for it.

**Write in simple, clear language.** This covers the plan, the code comments,
the documentation, any ADR amendment, and anything said back to the user. Short
sentences, plain words, and say the thing rather than framing it. Where a
concept is genuinely hard, explain it — do not compress it into jargon.

## Model allocation

**The plan must open with a section allocating work between models**, following
[model allocation](../phase 02 - web ui/model-allocation.md): default to the cheapest model that can do
each step correctly, spell out the detail a Sonnet or Haiku step needs, and let
Sonnet be the reviewer of record for the mechanical ones.

Good Sonnet candidates: running the automated audit and applying clear-cut fixes such as missing labels or contrast values. **Opus should own the manual screen reader pass and everything it turns up** — that's judgement work, and it's the part that can't be automated.

## Plan storage

NB. The plan's implementation phase should start with a directive to store the plan as `xxx.xx.xy.plan - ******** plan.md` reflecting the prompt's three-part index with the third number incremented by 1, and its name, and if the prompt name is still suffixed with ` (draft)` to remove the suffix, eg.

`002.00.00.prompt - monorepo restructing (draft).md`'s plan is stored as `002.00.01.plan - monorepo restructing.md`, and the original prompt is renamed: `002.00.00.prompt - monorepo restructing.md`

## Carry-forward

**The plan must include a step that writes this prompt's forward-looking work
into the prompts that will do it.** Anything deferred, discovered, or left
half-wired belongs in the prompt that picks it up — written into that file, not
only mentioned in this plan. A note nobody meets while reading the prompt they
are working on has not been recorded, it has been filed.

Where the note is about a test, a constraint or an assumption the later work
depends on, put it in that prompt's own Requirements or Testing section rather
than appending a loose paragraph.

## Goal

Accessibility is this MVP's quality bar, not a finishing touch — the UI ships deliberately unstyled, so this is what "finished" means.

Automated tooling catches somewhere between a third and a half of real barriers, and none of what [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md) is about. **This prompt is where a human actually listens to the application.**

## Requirements

- An automated audit across every MVP view and dialog, with findings recorded rather than just fixed in passing.
- **A manual screen reader pass** across the six MVP journeys, on the named matrix:
  - VoiceOver + Safari (macOS)
  - NVDA + Firefox (Windows)
  - VoiceOver on iOS Safari
- WCAG 2.2 AA met throughout, plus the three adopted AAA criteria: enhanced contrast in the high-contrast theme, location (the breadcrumb), and no content that conveys information and then disappears on its own.
- Findings fixed, with regression tests where a fix could quietly come undone.
- **The `/callback` route's two transient states are in the manual pass.** Carried forward from 004.02: it shows a `ProgressBar` while the exchange is in flight — briefly on a fast connection, for a while on a slow one — and an `ErrorState` on any of four failures. Both are states a user meets mid-journey with no page around them yet, and the loading one is easy to miss precisely because it usually flashes past. Force it by throttling the network rather than waiting to catch it.
- **The session expiry warning and the two recovery states are in the manual pass.** Carried forward from 004.03. `SessionExpiryWarning` announces **assertively** — it interrupts whatever is being read — and it is the only surface in the application that speaks without the user having done anything, thirty seconds before their session ends. Whether that interruption is proportionate is a judgement no automated scan makes, and getting it wrong in either direction is a real failure: too quiet and the session ends under someone mid-task, too loud and it cuts across their work every hour. The **Stay signed in** control is what makes the timed session meet WCAG 2.2.1, so confirm it is reachable and operable by keyboard and by screen reader, not merely present. `RequireSession`'s recovering and failed states belong in the same pass, and the recovering one usually flashes past — force it by throttling the network, as with `/callback`.
- **The two questions [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md) left open are answered**, using what the manual pass shows.
- **A `<ul>` styled with `list-style: none` loses its list semantics in Safari/VoiceOver.** Carried forward from 006.01: the overview's company list and 007.01's four lists are all built on bare `<ul>`s with a stylesheet that carries the class name and nothing else, per ADR-026's empty-rule-body convention — so nothing sets `list-style` yet, and nothing has been checked against the trap. Confirm it once the themes are written, and if a theme does turn list markers off, keep the list role with `role="list"` on the affected elements.
- **The overview's `403` branch is proven only in jsdom.** Carried forward from 006.01: `CompaniesPage`'s forbidden state (`?all=true` refused to a non-administrator) is reachable in the component tier by mocking the response, but nothing in the browser tier has driven it with a real administrator token. It deserves one browser-tier confirmation.
- **`base.css` gained `.react-aria-Tab*` rules in 006.01**, including a selected state carried by a border rather than by colour (WCAG 1.4.1), chosen because the high-contrast theme may have very little colour to spend. The contrast scan should cover the tab list in both themes and both modes.
- **The office view's canvas ignores the high-contrast theme.** Carried forward from 000.01: `scene/palette.ts` in the isometric office view (`src/visualisation/isometric/company/`) is a fixed set of colours that resolves through no `--tcp-*` token, so switching to the high-contrast theme changes nothing on the canvas. This was a deliberate 000.01 trade — placeholder shapes, not a themed design system — judge whether it is still acceptable once the rest of the application is themed.
- **The office view's details picker can change while it is open.** Carried forward from 000.01: the "Show details for…" picker lists roles, unfinished tasks and active agents live, and a task or agent arriving while it is open moves the list under the keyboard cursor — the case ADR-027's "live updates never reorder what's under the cursor" rule is about, applied here to a picker rather than a list.
- **The office stage's focus and description need a real screen reader.** Carried forward from 000.01: the stage is `role="group"` ("Office view"), described by a live-computed summary plus key help, with the details picker as the keyboard route to every clickable object. Confirm both actually read well, not just structurally.
- **The office view's tooltip needs checking against WCAG 1.4.13.** Carried forward from 000.01: `VisualisationTooltip` is dismissible with Escape and its content also appears in the tray, which is the automated proof. Only a manual pass confirms it reads as hoverable, dismissible and persistent the way the criterion asks.

## Implementation notes

- The open questions to resolve:
  - **Is a completed agent response announced in full, or only as "a response arrived"?** An answer can run to several paragraphs, and announcing all of it is disruptive in a different way from announcing none of it. This needs real listening.
  - **Are the throttle intervals right?** They were guesses, deliberately left configurable. Tune them.
- Record the answers by updating ADR-027, not only in the code — its Consequences section currently flags both as unresolved.
- The manual pass needs **macOS and Windows**. That's a real obligation and the honest reason many projects skip this step; plan for it rather than discovering it.
- Test both themes and both light and dark modes. The high-contrast theme exists to meet the enhanced-contrast criterion, so verify it actually does.
- Verify `prefers-reduced-motion` is honoured.
- Check keyboard-only operation of every journey, including the dialog and menu patterns, which are where it usually breaks.
- Where a fix reveals a pattern rather than a one-off, fix the shared component rather than each use.

## Testing

- Every fix that could regress gets a test — a fix without one will quietly come undone.
- Add announcement tests using `@guidepup/virtual-screen-reader` and `spokenPhraseLog()` for any behaviour the manual pass changes.
- **Tune the two announcer constants, and record the values you land on.** Carried forward from 003.03: `ANNOUNCE_THROTTLE_MS` (10s) and `ANNOUNCE_LOADING_MIN_MS` (1s) in `src/announce/announcer.ts` are guesses that have never been heard by a real screen reader. ADR-027 says so explicitly; this is the pass that settles them.
- **The live activity view's four channels (`agents`, `tasks`, `consultations`, `enquiry`) are 007.01's wordings for `useListChangeAnnouncement`, and the first real surface to tune `ANNOUNCE_THROTTLE_MS` against.** Carried forward from 007.01: the `announce.*` wordings in `strings.ts` and the ~10s throttle are unverified against a real screen reader — listen to them here.
- **Confirm an in-context error reads as well announced as alerted.** Carried forward from 003.03: `ErrorState` is deliberately `role="group"` plus an assertive announcement rather than `role="alert"`, because `role="alert"` is itself a live region and three failing lists would mount three. Listen for one specific thing the automated tier cannot judge: two _different_ assertive channels firing in the same tick truncate each other, because they are separate sentences by design. If that reads badly, the fix is a decision about assertive channels, not about reintroducing per-component alerts.
- **Scan `document.body`, not the render container, for anything announcement-related.** Carried forward from 003.03: the announcer's two live regions are created by `@react-aria/live-announcer` in `document.body`, outside the React root — the same trap React Aria's `Popover` already sets, for the same reason.
- **Only the route-change announcement has browser-tier coverage.** Carried forward from 003.03: `test/browser/app-shell.spec.ts` proves the announcer's two regions exist and are empty on load, and that a real navigation puts the page title into the polite one — which matters because jsdom skips the 100ms first-announcement delay react-aria applies in a real browser, so that path is otherwise never exercised. Nothing else that announces was reachable signed out. Extend it once the MVP journeys exist: coalescing, throttling and assertive politeness are all still jsdom-only.
- Confirm the automated audit runs clean across every view and dialog afterwards.
- **`/callback` is a page the contrast scan can reach without signing in**, alongside `/` — worth including for that reason, since its error state is the only red-adjacent surface in the application. Carried forward from 004.02.
- **Extend 003.01's four-combination contrast scan to every page.** Carried forward from 003.01: `test/browser/app-shell.spec.ts` seeds `tcp.theme` through `localStorage` and scans `/` in each theme × mode, using `color-contrast` for `default` and `color-contrast-enhanced` (AAA, 7:1, off by default in axe) for `high-contrast`, asserting `passes.length > 0` so a rule that silently failed to run cannot pass vacuously. The component tier **cannot** check contrast at all — `src/test-support/axe.ts` disables the rule because jsdom has no layout engine — so this is the only tier where ADR-026's 4.5:1 and 7:1 targets are ever verified.
- **Also assert what is drawn, not only the attribute that drives it.** Carried forward from 003.01: jsdom returns defaults for `getComputedStyle(el, '::before')` and never expands a shorthand, so a component test can confirm `data-selected`/`data-focus-visible` are present while the indicator and focus ring render as nothing at all. `app-shell.spec.ts` has one test that reads the computed pseudo-element and outline; anything new in `src/styles/base.css` needs the same treatment.
- Re-run the six browser journeys with accessibility scanning, and confirm they still pass.
- Run the full suite via `./scripts/run-all-tests.sh`.
- **A jsdom test can be green while the browser is wrong.** Carried forward from 003.02, which found this twice. React Aria's `Popover` portals out of the render container, so scanning `container` rather than `document.body` audits nothing. And `main.tsx` uses `StrictMode` while the test helper originally did not, so the application moved focus and announced on arrival — which ADR-027 forbids — with every component test passing. Where a behaviour depends on the real environment, the browser tier is the tier that proves it.
- **The shell's browser-tier coverage runs against an unknown address.** Carried forward from 003.02: no signed-in page is reachable in a real browser until 004.02, so `test/browser/app-shell.spec.ts` asserts the skip link, the not-found page and the shell's accessibility on `/no-such-page` — the only shell-bearing route reachable without a session. Once sign-in exists, move that coverage onto a real page and add the account menu, which has no browser-tier coverage at all today.
- **The completed-response announcement is arrival-only.** `ANNOUNCE_RESPONSE_BODY` in `src/components/Transcript/useTranscript.ts` is `false`. ADR-027 leaves the full-text alternative open pending this manual pass, and both wordings already exist in `strings.ts` — so settling it is a one-line change here. **The chat dialog is the surface this was deferred for, so judge it there** — with two conversations streaming at once, which is the case the arrival-only wording was chosen for. `describe('speech')` in `src/components/ChatDialog/ChatDialog.test.tsx` already proves two channels produce two separate sentences rather than one that names neither agent; listen to both wordings against that same scenario before deciding.
- **The transcript renders each entry's raw event label** (`tool_call:search`, `state_change:agent`, `llm_response:reasoning`) exactly as the shared renderers produce it. That is honest and matches the CLI, but it is machine wording in a user-facing surface. Judge it in the manual pass.
- **The task dialog puts several named regions inside one modal — judge whether that reads as navigable or as noise.** Carried forward from 008.03: it is a `<section>` per assignment, one per panel, each with its own heading naming a role and a status, all inside the dialog's own region. The automated tier only proves the structure is valid (`aria-labelledby` resolves, roles are correct); only a real screen reader can say whether stepping through several regions to find one panel's transcript is a reasonable way to read a task with many assignments.
- **The MVP's two forms are proven only in jsdom, and forms are where accessibility usually fails.** Carried forward from 008.04: the response dialog and the task creation dialog are the first surfaces in this application that take user input, and `src/components/Field/TextField.tsx` is the one field they share. Its error association comes from React Aria (`isInvalid` plus a `FieldError` child wiring `aria-invalid` and `aria-describedby`), and the component tier proves the association exists via `toHaveAccessibleDescription` — which is not the same as hearing it. Confirm with a real screen reader that (a) the error is announced when focus lands on the field it belongs to, not only when the message appears, and (b) after a failed submit the user is told _why_ focus moved, rather than being silently relocated.
- **Judge the native file input in the task creation dialog.** Carried forward from 008.04: the materials control is a plain `<input type="file" multiple>` rather than React Aria's `FileTrigger`, chosen because the native element is understood by every assistive technology without any of our code. The part with no automated proof is the selected-files list that follows it — adding and removing a file changes a list that nothing announces. Listen to whether a user who removes a file learns that it happened.
- **Assignment panels open collapsed by choice, not by default behaviour — judge whether that reads as tidy or as hidden.** Carried forward from 008.03: a task's work is one keypress away rather than shown on arrival, so a task with several assignments opens as a list of status lines with nothing expanded. Listen to how that reads with a real screen reader before treating it as settled — if it reads as hiding the very thing the dialog exists to show, the fix is a different default (008.03 also considered opening active assignments expanded), not a wording change.

## Quality gates

- `./dev-qual/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- **Findings are recorded, not just fixed** — including anything deliberately deferred, with a reason. A deferred item with no record becomes an invisible one.
- ADR-027 updated with the resolved open questions, and ADR-026's status updated to reflect what's now verified.

## Unresolved notes

Before this prompt is done, record what it leaves open in
[unresolved-notes.md](../phase 02 - web ui/unresolved-notes.md):

- **Anything a later prompt will do** — write it into that prompt (see
  [Carry-forward](#carry-forward)) and add a row to that document's
  _Carried into a later prompt_ table, so it is visible from one place.
- **Anything unresolved with no owner** — a compromise taken knowingly, a
  constraint imposed from outside, a decision that can't be taken yet. State
  what would have to be true for it to be revisited.
- **Anything conditional or time-dependent** — an upstream project adding a
  feature, a library dropping a peer constraint, a threshold being crossed —
  needs the entry **and a memory**, because nothing in this repository will ever
  prompt anyone to re-check it. Write the condition so it can be tested, not as
  "revisit later".

If this prompt genuinely leaves nothing open, say so in the plan. Silence and
"checked, nothing to add" read identically afterwards, and only one of them is
true.
