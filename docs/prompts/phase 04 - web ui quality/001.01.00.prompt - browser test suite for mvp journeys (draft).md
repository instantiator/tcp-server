## Goal

Component tests mock the network. These journeys don't: they drive a real browser against a real deployment, and they're the only thing that exercises the sign-in redirect, live event streams over a real connection, and HTTP/2 under real connection limits.

## Requirements

**The sign-in harness now exists** — [007.03](../phase 02 - web ui/007.03.01.plan - browser authentication harness.md) built `test/browser/auth.setup.ts`, which signs in once through a real Zitadel login and saves the provider's session cookie, and a spec opts in with `test.use({ storageState: ... })`. Journeys 1 and 2 of the six below are already covered — `companies.spec.ts` (sign in, reach the companies overview) and `company-activity.spec.ts` (open a company, see live activity, including a live task change moving a row with no reload). **This prompt's scope is the remaining four:**

1. ~~Sign in, and reach the companies overview~~ — covered by `007.03`
2. ~~Open a company and see live activity~~ — covered by `007.03`
3. Create a task and watch it progress
4. Chat with a role and receive a streamed reply
5. Answer a user enquiry
6. Sign out, and land back on the landing page

Plus:

- **Journey 3 should also cover cancelling a task, not only creating one.** Carried forward
  from 008.03: cancelling is the only destructive action in the MVP, and its confirmation
  step and the focus behaviour afterwards are proven only in jsdom (`TaskDialog.test.tsx`'s
  `describe('focus')` block), against a mocked stream and a mocked confirm/reject. Open a
  task from the activity view, press cancel, confirm, and see the task and its assignments
  reach `cancelled` for real. jsdom cannot prove where focus actually lands after a real
  browser removes the confirmation dialog — this journey is what closes that gap.

- **Journeys 3 and 5 are now reachable end to end, and both have a part jsdom cannot prove.** Carried forward from 008.04:
  - **Journey 3 needs a real file upload.** The creation dialog attaches files through a native `<input type="file" multiple>` and a real `multipart/form-data` request (`src/api/client.ts`'s `postFile`, the one request that does not go through the generated client). jsdom fakes both the `File` and the request, so the boundary, the `FileInterceptor` field name (`file`) and the server's rejection of a material once the task has left `ready` are all unexercised. Use Playwright's `setInputFiles`. Cover the ordering too — create, then upload, then start — because a start that lands before the uploads makes the server refuse them.
  - **Watch for a stale enquiry notification in journey 5.** `applyEvent` patches a closed enquiry's `status` in place and never removes its row from the cached `awaiting_user` list, so both readers of that list (`EnquiriesList` and `NewEnquiryNotifications`) re-filter client-side. That guard is proven only in jsdom against a synthesised event. In a real browser, answering an enquiry should make both the list row **and** any notification for it disappear without a reload — if the notification lingers, the filter is not doing what the jsdom test claims.
  - **Journey 5 should include the already-answered case.** Answer an enquiry from `tcp-cli` (or a second browser context) first, then submit from the UI and confirm the `409` reads as "already answered somewhere else" with the form gone, rather than as a generic failure. This is a real race between two clients, and the jsdom test asserts it against a mocked status code alone.
- Each journey scans its rendered pages for accessibility violations.
- The suite runs in CI and locally with one command.
- **The suite is reliable.** A flaky browser suite gets ignored, which is worse than not having one.
- **Journey 1 already has its first browser coverage, via `007.03`.** `companies.spec.ts` signs in through a real Zitadel login (`test/browser/auth.setup.ts`) and reaches the companies overview — the redirect, the PKCE round trip and Zitadel's own response are all exercised for real, closing the gap 004.02 left: the jsdom tier only intercepts `signinCallback()` on the real `UserManager`, proving the wiring above the exchange and nothing about the exchange itself. Extend that spec rather than building a second sign-in path from `test/browser/oidc-registration.spec.ts`.
- **Retire the `/no-such-page` workaround while you are here.** Carried forward from 003.02 and 004.02: `test/browser/app-shell.spec.ts` runs the shell's browser coverage on an unknown address, because until sign-in existed that was the only shell-bearing route a browser could reach. Journey 1 removes that constraint, and the comment saying so should go with it.

## Implementation notes

- This tier is **black-box** ([ADR-016](../../ADRs/ADR-016-test-infrastructure-orchestration.md)): it drives a deployment someone else started, provisions nothing itself, and takes its base URL as input. `scripts/run-api-tests.sh` is the model.
- **Carried forward from 002.03: the tier already drives the deployment, and there is no local-server fallback.** `tcp-web` serves the app, `playwright.config.ts` has no `webServer` block, and the base URL is **https** on `EXPOSE_PORT_WEB` — `tcp-web` is TLS-only because HTTP/2 is. `ignoreHTTPSErrors` is on because the container self-signs by default. Don't reintroduce a `vite preview` fallback for convenience: it serves HTTP/1.1, which would silently disable the connection-limit conditions several of these journeys depend on.
- **The browser tier runs inside CI's `api-test` job**, not a job of its own, because that job is the one with a deployment. New journeys needing more setup should extend that job rather than add a second stack.
- The deployment is started by `scripts/start-deployment.sh` with `tcp-stub-llm`, so agent responses are scripted and repeatable rather than depending on a real model.
- **Sign-in needs a real identity provider round trip.** Zitadel is part of the deployment; work out how a test user authenticates without hardcoding credentials, following how the api tier already resolves test credentials.
- **The bootstrapped test user's login is four pages, not two.** Verified by hand during 004.02 against a `.env.testing` deployment: `/ui/login/login` (fill `input[name="loginName"]`, press **Next** — not Enter, which reloads the form), then `/ui/login/password` (fill `input[name="password"]`, **Next**), then a **2-Factor Setup** page the org policy inserts, whose "skip" button is below the fold on a 1280×720 viewport. Skipping it completes the flow. Either drive that page or turn the policy off in `start-deployment.sh` — but decide which, because a journey that assumes two pages passes locally today and breaks the moment the policy changes.
- Journeys 3 and 4 depend on agents actually running and streaming. Script `tcp-stub-llm` so they complete predictably — this is where flake will come from if anywhere.
- **Wait on real conditions, not timeouts.** Wait for an element or a state, never a fixed sleep. Live-updating views make this especially important, and especially tempting to get wrong.
- Each journey should be independently runnable and not depend on another having run first.
- Consider what state each journey leaves behind, and whether the next one cares.
- Add the tier to `scripts/run-all-tests.sh` and to CI as its own job, with browser binaries cached.

## Testing

The deliverable is tests, so verification is about the suite's own trustworthiness:

- **The signed-in journey has to go through a real provider login, a reload and a sign-out.** Carried forward from 004.03, which built all three and could prove none of them in a browser: no tier in this repository completes a Zitadel login. What 004.03 left behind is one browser assertion that a guarded route _leaves_ for the provider — everything past that redirect, including the reload recovery that is the whole point of the work, is proven only in jsdom against a spied `UserManager`. Sign in for real, reload the page and confirm no login form appears, then sign out and confirm the back button does not reach the protected page.
- **A real end-user sign-in helper now exists, alongside the machine-credential path.** Carried forward from 005.02: `test/browser/event-streams.spec.ts` proves several concurrent streams work using a `client_credentials` grant. `007.03` added the other half — `test/browser/auth.setup.ts` signs in a real human through Zitadel and saves the session for any spec that opts in. Use it for the four remaining journeys rather than building a second helper.
- **Each journey must fail when the feature it covers is broken.** Verify by deliberately breaking something and confirming the right journey fails — a passing test that can't fail is worthless.
- Run the suite repeatedly to shake out flake before declaring it done. Intermittent failures must be fixed, not retried around.
- Confirm accessibility scanning actually runs on each page and reports violations.
- Confirm the suite works against a deployment on a non-default port, since it must not assume one.
- Confirm CI reports results the same way the existing tiers do.
- **`/company/:id` and a live list change under a real SSE connection are already covered.** `007.03` closed the gap 007.02 left open: `company-activity.spec.ts` signs in, opens a company, asserts exactly one event stream, and drives a task's status through the API to watch the row move with no reload. The component tier proves `applyEvent` patches the cache; `007.03` is what proves the browser receives the event over a real connection. Build on that spec rather than duplicating it.
- **The office view's agent avatars have no browser coverage.** Carried forward from 000.01: the browser-tier deployment has no LLM, so no journey can watch an agent avatar walk, work or leave — `company-visualisation.spec.ts` only proves roles and task rooms against real Phaser. Decide whether `tcp-stub-llm` joins the browser deployment; if it does, agent-avatar journeys join this suite the same way journeys 3 and 4 do for tasks and chat.
- **Once task creation publishes a live event, extend the live task journeys.** Carried forward from 000.01: `TaskService.create` publishes nothing, so `company-visualisation.spec.ts` and `company-activity.spec.ts` can each only prove a task's live _removal_ today — both create their fixture task before opening the page, because there is no event to watch it appear. When the backend gains a `ready` state_change (see phase 03's [unresolved notes](<../phase 03 - web visualisation/unresolved-notes.md>)), add the matching live-creation journeys to both specs.
