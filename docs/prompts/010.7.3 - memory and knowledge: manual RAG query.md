# Memory and knowledge 3/4: manual RAG query

Part 3 of the memory-and-knowledge work (see
`010.7.0 - memory and knowledge: overview.md` for the map — you do not need
to read it to implement this plan; everything required is below).

> **Recommended implementing model: Sonnet.** Small, well-specified addition:
> expose an existing internal service via one new endpoint + one CLI verb.

## Goal

Let a developer see the raw chunks that would accompany a prompt (the same
data RAG injection would provide) without invoking any LLM chat call.

## Current state (verified)

- `RagRetrievalService.retrieve(roleId, companyId, query, embeddingConfig, topK = 5, threshold = 0.7)`
  (`apps/lcp-server/src/rag/rag-retrieval.service.ts:53-89`) is already exactly
  this capability: it embeds the query (the **only** external call it makes —
  no chat/LLM call anywhere in this path) and runs a raw pgvector
  cosine-similarity query against `knowledge_chunk`, scoped to
  `("roleId" = $2) OR ("roleId" IS NULL AND "companyId" = $3)` — i.e. the
  role's own chunks **plus** the company's shared chunks, in one call. Returns
  `RagChunk[]` (`id, documentPath, chunkIndex, content, similarity`).
- This service (and its lcp-agent duplicate, `AgentRagService.retrieve`) is
  currently **only called from the prompt-assembly path** — no controller
  exposes it. Confirmed via grep: no `/knowledge/query` or `/knowledge/search`
  route exists anywhere in `apps/lcp-server/src/api/`.
- `KnowledgeController`/`KnowledgeService` is the existing pattern to extend —
  same JWT-guard/Swagger/role-or-company-scope conventions as every other
  route in `apps/lcp-server/src/api/knowledge.controller.ts`.
- CLI pattern to mirror: `apps/lcp-cli/src/commands/reindex-knowledge.ts` +
  `apps/lcp-cli/src/lib/docs/reindex-knowledge.action.ts` (command/action
  split, `apiRequest` for a plain JSON GET, JSON to stdout).
- A company's `embeddingConfig` is required for `retrieve` to return anything
  (`if (!embeddingConfig) return [];`) — the new endpoint needs the same
  company-embedding-config lookup `RagRetrievalService`'s callers already do
  (grep how `chat.service.ts`/`agent-loop.service.ts` fetch it before calling
  `retrieve`, and reuse that lookup rather than re-deriving it).

## Implementation

### 1. Server: endpoint

New route on `KnowledgeController` (or a thin new controller if that file is
getting large — your call, but prefer extending the existing one since it
already owns the `role`/`company` scope-resolution pattern this needs):

- `GET /api/role/:roleId/knowledge/query?q=<string>&topK=<n>&threshold=<n>`
  — JWT-guarded, resolves the role → company → `embeddingConfig` (reusing the
  existing lookup, see above), calls `RagRetrievalService.retrieve` directly,
  returns the `RagChunk[]` as-is (it's already a clean, minimal shape). 400 on
  a missing `q`; sensible defaults for `topK`/`threshold` matching
  `RagRetrievalService`'s own defaults (5 / 0.7) unless the caller overrides
  them.
- A company-shared-only equivalent is **not** needed as a separate route:
  `retrieve` already unions role + shared scopes in one query, so the
  role-scoped endpoint is sufficient for both "what would this role see" and,
  implicitly, "what's in the shared pool" (shared-only chunks still surface,
  just alongside the role's own). Note this reasoning inline in the
  controller's JSDoc so a future reader doesn't add a redundant route.

### 2. CLI verb

`apps/lcp-cli/src/commands/query-knowledge.ts` +
`apps/lcp-cli/src/lib/docs/query-knowledge.action.ts`:

`query-knowledge --role <slug-or-id> --query "<text>" [--top-k <n>] [--threshold <n>]`

Prints the ranked `{documentPath, chunkIndex, similarity, content}` array to
stdout as JSON, matching the CLI's existing JSON-output conventions. Register
in `apps/lcp-cli/src/main.ts` alongside the other `registerXxx` calls.

### 3. Tests

- Unit: the new controller method (mock `RagRetrievalService`/embedding-config
  lookup) — happy path, missing `q` → 400, unknown role → 404, no
  `embeddingConfig` → empty array (not an error).
- e2e: new describe-block in `test/e2e/lcp-server/knowledge.e2e-spec.ts`
  covering the endpoint end-to-end against real seeded chunks (reuse the
  file's existing fixture-setup conventions), plus the 401-unauthenticated
  case matching every other endpoint in that file.
- CLI: `query-knowledge.action.spec.ts` mocking `apiRequest`, matching
  `reindex-knowledge.action.spec.ts`'s style.

### 4. Documentation

Document the new endpoint/verb alongside the rest of the knowledge REST API
(grep `docs/` for where `knowledge.controller`'s routes are currently
documented) and cross-reference it from `docs/manual-testing/05-rag-documents.md`
as a lighter-weight alternative to that doc's existing "call
`RagRetrievalService.retrieve` manually" walkthrough.
