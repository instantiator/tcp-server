## Configurable third-party services

TCP uses a number of third-party services. Each should be configurable - ie. to use a pre-existing third party service, or to provide its own through a docker container.

We currently do this with the authentication service - either a third party OIDC service is specififed for user accounts, or a Zitadel container can be spun up alongside TCP.

A couple of improvements to make:

1. Simplify: rather than specifying the docker compose profile, if a particular piece of config isn't provided (or blank) in the `.env` being used for configuration, then provide the service internally.
2. Expand the provision to other services that TCP uses.

We use several other services...

- postgres
- redis

### Relational database

TCP uses a postgresql container for our core database, but we also use SQLite (in memory) when running tests.

NB. The postgresql instance is pgvector, because it also holds vectors for RAG knowledge storage services.

Ideally this would be fully configurable:

- Split core database usage and the vector database usage, allow them to be configured separately
- Permit configuration with a variety of database types (those supported by TypeORM)
  - Is there a common database connection string format we can use for that?
- In testing environments, use SQLite (in memory), as now
- If configuration is provided, use the third party service
- If configuration is not provided, use the postgres container
- Only spin up 1 container (if required), whether it's needed for core db, vector db, or both

Hopefully we've followed a pattern that makes this easy. Ideally there would be a clean adapter and interface for database access.

### Queue service

We use BullMQ for queue manangement, and this requires access to a Redis service.

We currently connect to BullMQ queue(s) from a number of locations. Let's consolidate all access to BullMQ and Redis with a shared interface for working with queues, which can then be implemented by a QueueService. Then we can build an adapter for it that implements the interface, and works with BullMQ/Redis.

We currently spin up a Redis container.

Ideally this would also be fully configurable:

- It has to be Redis for BullMQ, but allow configuration to be provided for a third party provider
- If configuration is not provided, use the Redis container, as now

Evaluate, but don't implement, alternatives for BullMQ. It might be worth considering alternative queueing systems that don't need Redis - eg. an alternative that can work with any of the databases supported by TypeORM might mean one fewer third party service / one fewer container. Make a recommendation (keep, or migrate). That migration can be a part of a future piece of work, and will be easier for having an interface + adapter for the queueing service.

### LLM provider

Unlike the database, the queue and storage, the LLM provider is already
configurable per company and per role — `LlmConfig` carries `provider`, `model`,
`baseUrl` and `apiKey`, resolved by `LlmConfigResolver` with a fallback to the
environment (`LLM_PROVIDER` / `LLM_MODEL`). So the work here is not to build the
configurability; it is to establish **which providers are actually known to
work**, and to say so in the documentation rather than leaving it implied.

Today every worked example in `docs/tcp-agent.md`, `docs/agent-services.md` and
`docs/context-management.md` points at `http://localhost:1234/v1` — LM Studio.
That is the only local provider anyone has exercised, and nothing records
whether the OpenAI-compatible surface TCP relies on is being used in a way other
implementations share.

**Test ollama specifically.** It is the most likely alternative a developer will
already have installed, it serves an OpenAI-compatible API on
`http://localhost:11434/v1`, and it is not currently known to work — nobody has
tried it. Worth confirming, for each of the places TCP depends on that surface:

- chat completions with tool calls, which is the agent loop's whole basis
- streaming responses (`streamEvents`), including how tool calls arrive in a
  stream — this is where OpenAI-compatible implementations most often diverge
- the embeddings endpoint, used by `embeddingConfig` for the RAG index; ollama
  serves embeddings on a different route shape to chat, so check it separately
- whether an `apiKey` is required, optional or rejected — ollama needs none by
  default, and `LlmConfig` stores the field regardless

Where a provider diverges, the question to answer is whether TCP should adapt or
whether the provider should simply be documented as unsupported. Both are fine
answers; an undocumented guess is not. The same treatment is worth extending to
whichever hosted providers are in scope (OpenAI, Anthropic, and any
OpenAI-compatible gateway), so the supported set is a stated list rather than
folklore.

### Storage service

We currently use minio for our storage service. Again, ideally this should be configurable.

We should aim to support storage services with an adapter and interface model, allowing us to use any S3 service, and some other common storage services.

Include recommendations for supportable services in the plan. Some candidates:

- third party s3 service configuration
  - minio
  - AWS S3
  - Google Compute equivalent?
  - Azure equivalent?
  - other services?
- candidate third party alternative storage configurations...
  - Google Drive
  - Dropbox
  - OneDrive / Microsoft office equivalent
  - Others?
- basic storage services
  - SFTP?
  - SCP?
  - local file storage (eg. docker volume, or local filesystem path)
- If configuration is not provided, use the minio container, as now

Is there a generalised storage service connection provider library we can use for this? Perhaps a small number of libraries that can help with these.

The storage service will need authentication. Some storage services will provide their own, others may be configurable to use the auth service defined for TCP (as we do with minio now?)

For example, Google Drive is probably best paired with Google's authentication service. This may mean that the choice of storage provider is linked to the choice of auth provider. (Equally, perhaps Google Drive _can_ share a third part OIDC service with TCP, in which case that doesn't matter so much.) Research each option.

We should clarify in documentation and configuration what the options are, clearly, to configure any of the supported services.

We'll need a plan for testing, too. Integrations tests against common services we support are important. If we can spin up services in docker to represent them, that's good. Services like Google Drive likely don't work that way, so we may need a test account we can exercise in integration tests.

Credentials like these should live in `.env` (where they can't be included in the repo), and GitHub actions secrets (for use in CI). You may need to walk me through creating an account and generating + storing credentials. We should document that process, too.

### Storage and authentication

Two pieces of work sit alongside the storage adapter. Both need to hold whichever storage service and whichever OIDC service is configured.

**Silo with any OIDC service**

Silo (the MinIO-compatible container) should authenticate users against the OIDC service TCP is configured with. That might be the bundled Zitadel, or any third-party OIDC provider.

- Silo's OIDC settings should be derived from TCP's existing OIDC configuration, not set a second time.
- Research whether Silo can federate with an arbitrary OIDC provider, and what claims or policy mapping it needs.
- Optional extra: synchronise access. When a user is granted access to a company, they get access to that company's bucket; revoke it when the membership ends. (This is carried over from `unplanned.md`.)
- Third-party storage services that bring their own authentication are out of scope here. Say so clearly in the documentation.

**System user for storage**

TCP's own services (tcp-server, tcp-agent, the MCP servers) need an identity that can read and write storage, without acting for a particular person.

- Configure one "system user" for storage, with credentials in `.env`.
- The configuration should have the same shape for every storage adapter (S3 access key and secret, an SFTP key, a service-account token and so on), so the services don't care which backend is behind it.
- Work out the least privilege it needs, for example per-company bucket or prefix access rather than all storage.
- When the bundled Silo is used, create the system user at deployment, the way the Zitadel client secrets are created now.
- Document how to create and store this user's credentials for each supported service.
