## lcp-cli

### Storing knowledge

At the moment, the `store-knowledge` verb is designed to accept an OKR document, store it in the role's knowledge store, and initiate a refresh of the RAG store for the specified role, or company.

Ideally, it would work as follows:

1. Accept a wider range of file types. examples include: markdown, pdf, html, csv, json, yaml, txt, docx
2. Generate OKF documentation from these files with a suitable header block (or retain the doc if it's already OKF)
3. Store in a suitable location
4. Add to an index file
5. Initiate update of RAG data

Possible supporting library: https://github.com/Nano-Collective/get-md

- this provides support for html, pdf, docx, and md

Is it a good option? Are there other libraries that could do this? We value:

- typescript / js
- does what we need, and generates a simple and easy to read markdown document that can be easily converted to OKF
- good reputation (either of the library or of the maintainers)
- mature (well tested, well adopted)
- well maintained and recently updated
- no serious known vulnerabilities
- high download count (or a competitive count for its age)

For csv, json, yaml: These are structured data and it ought to be reasonably simple to roll our own data -> OKF document converter if there isn't a simple library that does it. If we roll our own:

- I _suggest_ keeping that data largely as is, but surrounding in code block backticks for their data type (eg. "```json"), I'd expect a decent LLM to be able to read these formats aleady
- We'd still need to generate the OKF headings block
- There may be a better way - focus on what's easiest for an LLM to interpret

Do we need an LLM to generate some of the OKF headings, or to help index the document, or can we use other techniques to make it easily discoverable and prepare those OKF headings?

The processing should take place in lcp-server rather than lcp-cli - lcp-cli should be a reasonably thin client.

lcp-cli also offers a `reindex-knowledge` verb. It should also have a `get-knowledge-index-status` verb to pass back information about the index (ie. to show if indexing is in progress, how many documents are indexed (of how many), how large the indexed data is, and any other vital stats)

### Manual testing

Let's add a way to query the RAG index manually through lcp-cli. Can we do that without invoking an LLM? It'd be good to get a view of the chunks of RAG data that would accompany a prompt (eg. an assignment prompt, or a chat prompt, or when an agent interrogates the knowledge store itself using an MCP tool during the agent-loop)

### Automated testing

Let's develop some tests for this, if these aren't already implemented - in the test suite that best fits them (e2e tests? manual tests?)

- test that each type of knowledge can be added to the system
- test that a correct and useful OKF document can be generated from each type of knowledge
- test that the system uploads that OKF document to the right place (for role, and for company)
- test that the system initiates an update of RAG data
- test that the system can retrieve RAG data relevant to the document
