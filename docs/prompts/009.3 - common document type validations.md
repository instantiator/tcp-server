## minio adapter and storage service

Let's make the lcp-server storage service slightly more abstracted:

Instead of `MinioService`, implement a `StorageService` and create an adapter class that connects to minio (containing the code we've currently got that's specific to Minio, and implementing a general storage interface).

> That might seem like early optimisation, but it helps keep things readable, and sets us up to be more flexible about storage services in future (eg. in future perhaps adapters for Google Drive or other tools).

This storage interface, should reflect what's currently in the minio service. It'll be extended as we consolidate storage actions.

- `putRaw`
- `putKnowledgeFile`
- `listKnowledgeFiles`
- `getKnowlegeFile`
- `deleteKnowledgeFile`
- `getByKey`
- `putByKey`
- `ensureBucketExists`

While we're here, the `minio.service.ts` has `knowledgeKey` as a private function. Please shift that out of the new service, and provide it as a shared helper function, eg. exported from a file like `storage-keys.ts` - we may also want to provide other common key structures in future, and these should be grouped so they're easy for developers to find.

## Move all storage code to lcp-server

The `storage-tools.service.ts` in `lcp-mcp-storage` can currently perform its own work on files and buckets.

Many of the functions that it provides can be shifted to the new `StorageService` in lcp-server, and the `StorageToolsService` should be acting as a proxy, making calls to lcp-server endpoints to work with storage:

- `listFiles`
- `readFile`
- `writeFile`
- `deleteFile`
- `restoreFile`
- `searchFiles`
- `getFileProperties`
- `copyFile`
- `moveFile`
- `getFileSummary`

This will also require us to extend the lcp-server endpoints to accommodate the additional functionality.

Quite a few of the private functions should also be in lcp-server. Those that use the S3 service directly can stay with those above, others that evaluate or manipulate paths, strings, data can be shifted into a collection of helpers and exported from there.

eg.

- `validatePath`
- `checkMissingFiles`
- `objectExists`
- `isNotFound`
- `textResult`
- `globToRegex`
- `analyzeContent` (should be exported from its own helper and fan out to multiple functions based on the determined file type)
- `emitAudit` (if not already provided through another service in lcp-server)

Some things are specific to MCP, and can stay in the MCP app eg.

- `describeFolder`
- `register*`

This keeps storage work centralised, and allows us to keep auditing and validation DRY.

## Validation

When the user or agents write to or update files in the shared document store, the files should be validated to ensure they validate before they can be accepted.

Types of files to validate:

- JSON
- Markdown
- OKF
- YAML
- XML
- CSV

If files provide a location for their schema following common conventions for that file format, this should be used to validate the file.

There may be other formats in future, so let's plan a way that this can be developed into a modular solution in future (although it needn't be fully implemented now, shaping it so that it can and marking the intervention points in code comments would be helpful).

Suggested location for valodation code: `libs/lcp-shared/src/storage/validation/` (then called by the lcp-server storage service to validate before writing files).

Please plan some clean business logic that's called when writing to storage, and can reject a file. If rejected, the response from the service to an agent should contain a clear explanation that an LLM could use to resolve the issue.

Please review all places that currently access storage. All non lcp-server applications _should_ use the lcp-server API, to keep things DRY (and so centralisr the implementation).

## Additional verb

Because it's possible for users to access minio directly, the validate-before-write-through-lcp-server guard isn't sufficient to protect the store. We ought to add a way to validate a file independently of this. Please add a new shared document validation path for lcp-server, and a new `validate-shared-document` verb for lcp-cli.

It should accept a path or glob, with an optional recursive option (if the path/glob points to a directory). It should run validations against each file it finds, returning a results object describing any validation errors found across the documents checked, eg.

```ts
{
  query: {
    path: string, // a path or a glob
    recursive: boolean
  },
  validations: { path: string, found: boolean, size: number, valid: boolean, errors: string[] }[],
}
```

`lcp-cli` should return a 404 failure if a specifically named file cannot be found or if a directory in a path/glob doesn't exist (but a success code is fine if a valid glob didn't find any files), 500 codes for unexpected errors, and a success code if the validation was completed successfully (even if it shows validation errors).
