# Plan: Completing MCP Services, Human/Agent Interactions — 006.4

> Store at: `docs/prompts/006.4 - interaction service plan.md`

## Context

This plan fully implements the three MCP services (`lcp-mcp-storage`, `lcp-mcp-memory`, `lcp-mcp-interactions`) and the cross-cutting infrastructure they depend on: a centralised audit endpoint, a real user/conversation model, and agent-to-agent consultation. It also adds the CLI verbs needed for humans to participate.

**Current state:**

- `lcp-mcp-storage`: 6 tools with real MinIO S3 calls; no audit logging; no overwrite guard; hard delete; missing 4 tools (search_files, get_file_properties, copy_file, move_file); `summarise_file` deferred
- `lcp-mcp-memory`: 4 stub tools; no DB connection; infrastructure (RagRetrievalService, EmbeddingService) exists in lcp-server/lcp-agent but not accessible from this service
- `lcp-mcp-interactions`: 3 stub tools; no DB connection; no Conversation entity; no user model
- `AuditEvent` written by direct TypeORM calls in both `agent-loop.service.ts` and `chat.service.ts` — duplicated; no HTTP endpoint; MCP servers have no audit path
- No `User`, `CompanyUser`, `Conversation`, or `ConversationMessage` entities

## Conflicts, Risks, and Improvements

### Audit endpoint vs. DB connections in MCP servers

**ADR-008** describes audit events flowing from lcp-agent's LangGraph stream directly to PostgreSQL. This plan expands audit writing to three additional services. Options:

| Approach                             | Pros                                                                    | Cons                                                                                  |
| ------------------------------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| DB connection per MCP server         | No network hop; consistent with lcp-agent today                         | Gives stateless HTTP servers a DB dependency; credential sprawl                       |
| `POST /internal/audit` on lcp-server | Single write path; deduplicates saveAudit(); no DB creds in MCP servers | One extra network hop per audit event; audit events lost if lcp-server is unreachable |

**Recommendation: POST /internal/audit.** The MCP servers have no other reason for a DB connection (except lcp-mcp-memory and lcp-mcp-interactions which need one for their primary work). Fire-and-forget audit writes from all services; errors are logged but do not fail agent operations. lcp-agent drops its duplicate `saveAudit()` and uses the same endpoint. Internal endpoints are on `/internal/*` and protected by `X-Internal-Api-Key` header (matching `INTERNAL_API_KEY` env var) — consistent with ADR-011's network-level trust model.

Note: lcp-mcp-memory and lcp-mcp-interactions _will_ have DB connections for their primary work. They could write audit events directly. For consistency, they still use the HTTP endpoint — one pattern, one place to change.

**ADR-008 divergence:** ADR-008 mentions a `log_decision()` MCP tool and MinIO JSONL export. This plan replaces `log_decision()` with a better `complete_task()` tool (see Phase 7). MinIO export remains deferred.

### lcp-mcp-memory needs a DB connection

`recall`, `remember`, and `search_knowledge` all require pgvector queries. lcp-mcp-memory must have a `DATABASE_URL` and TypeORM connection. This changes it from fully stateless to DB-dependent — add the `postgres` health dependency to its Docker Compose service.

`EmbeddingService` currently lives in `apps/lcp-server/src/rag/`. lcp-mcp-memory needs it too. **Move it to `libs/lcp-shared/src/rag/`**. lcp-agent already has `AgentRagService` which wraps a similar pattern — consolidate both so they share the same `EmbeddingService` from libs.

### lcp-mcp-interactions needs a DB connection

It needs to write `Conversation` records, look up `CompanyUser` rows for routing, and trigger BullMQ jobs. It must have `DATABASE_URL` and `REDIS_URL`.

### User model vs ADR-011's CompanyMembership

ADR-011 proposes a `CompanyMembership` entity with five permission flags. The user's request is a simpler model: creator/owner/member with `roles[]` and `knowledgeDomains[]` for routing. **This plan implements the simpler model as `CompanyUser`** and defers the permission flag system from ADR-011 to a future auth hardening phase. ADR-011 should be updated to note this staged approach.

Intervention points: each API endpoint is annotated with a `// permission: <flag>` comment indicating which ADR-011 permission flag will guard it. A no-op `@RequirePermission()` decorator is added to `lcp-server` — enabling real enforcement later is a one-line change per endpoint, plus wiring the guard.

### Conversation entity vs ADR-012's task_id/step_id

ADR-012 links conversations to `task_id` and `step_id`. Neither Task nor TaskStep entities exist yet. This plan links conversations to `agentId` instead, which is the equivalent at the current stage. ADR-012 should be updated to reflect this.

### get_file_summary: structural analysis (no LLM)

`summarise_file` (renamed `get_file_summary`) is implemented as a structural analyser — no LLM access needed. It reads the file and extracts format-specific metadata:

| Format (detected by extension + magic bytes) | Extracted                                                                                                                                                   |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Markdown / OKF                               | Frontmatter fields; headings with start/end line spans                                                                                                      |
| JSON object                                  | First-level property names and value types                                                                                                                  |
| JSON array                                   | Object count; common first-level properties (sampled)                                                                                                       |
| JSONC                                        | Strip `//` and `/* */` comments, then parse as JSON object/array                                                                                            |
| YAML                                         | Top-level keys                                                                                                                                              |
| TypeScript / C#                              | Top-level class, interface, and function names + leading doc-comment (regex only — no AST)                                                                  |
| Open document / DOCX                         | Heading text if easily extractable via XML (docx = zip; iff straightforward)                                                                                |
| Everything else                              | Filename, size, best MIME type from `file-type` library (MIT, no transitive deps — check license before adding; fallback: extension-to-MIME map, ~10 lines) |

No new heavy deps. `gray-matter` is already in lcp-cli (check if also available in lcp-mcp-storage; if not, implement frontmatter parsing inline for YAML front-matter: read lines until second `---`, parse with Node's built-in `yaml` or manual split). `file-type` adds magic-byte detection — only add if license is MIT and downloads are high; otherwise use extension map.

### Unified pause/resume: agent-agent and agent-user use the same interrupt() mechanism

Both `request_user_input` and `request_agent_consultation` follow the same pattern:

1. MCP tool calls `POST /internal/pause-agent` on lcp-server, which:
   - Sets `LcpAgent.status = paused`
   - Records the pending interaction (Conversation for human; PendingConsultation for agent)
   - Returns a `pauseToken` to the tool
2. MCP tool returns a message to the calling agent: "Paused. [Request/Consultation] submitted."
3. lcp-agent's `streamAndAudit()` loop checks agent status after each tool result. On detecting `paused`, it calls `graph.updateState()` with a terminal marker and exits the stream — no more LLM calls. BullMQ job completes normally (agent is paused, not failed). Resources are freed.
4. **Human input resume:** user calls `POST /api/conversation/:slug/reply` → lcp-server sets conversation closed, re-enqueues `{ agentId, type: 'resume', replyContent }` on BullMQ → lcp-agent resumes from checkpoint with reply injected as HumanMessage
5. **Agent consultation resume:** consultation agent BullMQ job completes → lcp-agent (completion handler) calls `POST /internal/consultation-complete` on lcp-server → lcp-server re-enqueues calling agent with consultation result injected as HumanMessage

The mechanism is DRY: `PauseAndResumeService` in lcp-server handles both flows. lcp-agent's loop has a single "check for paused status" guard. The only differences are in what triggers the resume.

**Adding `output` to `LcpAgent`:** set on agent completion to the last AI message content; used by the consultation resume flow to pass the result to the calling agent.

### LangGraph interrupt() for human input

LangGraph `interrupt()` is the mechanism for agent-initiated pause (ADR-012). This plan implements it. The flow:

1. Agent calls `request_user_input`
2. lcp-mcp-interactions calls `POST /internal/conversation` on lcp-server
3. lcp-server creates a `Conversation` record (status: `awaiting_user`), sets agent status to `paused`, calls LangGraph `graph.updateState()` with an `interrupt` marker
4. BullMQ job is considered "complete" (agent is now paused, not failed)
5. When user calls `respond <slug> "message"`, lcp-server resumes the agent via `POST /api/agent/resume/:agentId` with the reply injected as the next message

**Risk:** This is the most complex piece. The LangGraph checkpoint must correctly restore state on resume. Verify with integration tests.

### RAG context replacement tool

The agent can replace its injected RAG context via `update_rag_context(agentId, newContent)` in lcp-mcp-memory. Implementation: lcp-mcp-memory calls `POST /internal/agent/:agentId/rag` on lcp-server, which uses `graph.updateState()` to replace the RAG message in the checkpoint (finding it by a known marker in the message metadata). This requires tagging RAG messages with `{ type: 'rag' }` metadata when they are injected. Size check via IncomingDataGuardService applies before injection.

### Phase 6 — lcp-mcp-interactions: real implementation (unified pause/resume)

**Goal:** Working user input pause + agent consultation — both using the same interrupt()/resume mechanism.

**Shared mechanism — `PauseAndResumeService` in lcp-server:**

- `pauseAgent(agentId, reason: 'user_input' | 'agent_consultation', metadata)`: sets `LcpAgent.status = paused`; creates the pending record (Conversation or PendingConsultation); returns the record
- `resumeAgent(agentId, replyContent)`: enqueues `{ agentId, type: 'resume', replyContent }` on BullMQ

**Pause detection in lcp-agent `streamAndAudit()`:**
After each tool result in the event stream, check `agent.status` from DB. On `paused`: call `graph.updateState(config, { messages: [] }, 'agent')` to commit the checkpoint cleanly, then exit the stream. BullMQ job completes normally. No CPU/memory consumed while paused.

- Migration: `AddAgentOutputAndPendingConsultation`
- `apps/lcp-agent/src/agent/agent-loop.service.ts`:
  - On normal completion: set `agent.output` to last AI message content
  - After each tool result event: reload agent status; if `paused`, exit stream gracefully
  - On consultation agent completion: call `PauseAndResumeService.resumeAgent(callingAgentId, consultationResult)`
- `apps/lcp-server/src/api/internal/PauseAndResumeService.ts` — extracted shared logic
- `InteractionsToolsService`:
  - `list_available_users(companyId)`: `GET /api/company/:companyId/users` → `{ identifier, name, roles, knowledgeDomains }[]`
  - `list_available_roles(companyId, excludeSelf?)`: `GET /api/roles?companyId=` → role list (excluding self if `excludeSelf: true`)
  - `request_user_input(agentId, companyId, question, context?)`:
    1. `POST /internal/pause` on lcp-server → `PauseAndResumeService.pauseAgent(agentId, 'user_input', { question, context })` → creates Conversation, routes to users
    2. Returns `"Paused. Query submitted as {slug}. Your task will resume when the user responds."`

    1. `POST /internal/pause` on lcp-server → `PauseAndResumeService.pauseAgent(agentId, 'agent_consultation', { roleName, question, context })` → creates PendingConsultation + enqueues consultation agent job with supplementary context: _"This is a consultation from {callingRoleName}.     2. Returns `"Paused. Consultation request dispatched to {roleName}. Your task will resume when the consulting agent responds."`
  - `complete_task(agentId, finalAnswer, outputFiles?)`:
    1. `POST /internal/agent/:agentId/complete` → sets status completed, `output`, writes StateChange audit event

- `POST /internal/agent/:agentId/complete` — mark agent completed with output
