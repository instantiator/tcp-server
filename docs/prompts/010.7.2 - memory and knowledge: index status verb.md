# Memory and knowledge 2/4: index status verb

Part 2 of the memory-and-knowledge work (see
`010.7.0 - memory and knowledge: overview.md` for the map — you do not need
to read it to implement this plan; everything required is below).

> **Recommended implementing model: Sonnet.** Small, well-specified addition:
> one read-only endpoint, one CLI verb, following existing patterns exactly.

## Goal

Add a `get-knowledge-index-status` CLI verb (does not exist today) reporting,
per knowledge scope (a role, or a company's shared scope): document count,
total stored size, indexed chunk count, and whether indexing is currently in
progress.

## Current state (verified)

- No such verb exists anywhere in `apps/lcp-cli` (grepped `status`/
  `index-status` — no matches). No REST endpoint exposes `KnowledgeIndexState`
  today (`apps/lcp-server/src/api/knowledge.controller.ts` has no `GET` for it).
- `KnowledgeIndexState` (`libs/lcp-shared/src/models/KnowledgeIndexState.model.ts:41-75`)
  has exactly: `id`, `companyId`, `roleId` (nullable — null = shared scope),
  `generation` (int), `fingerprint` (text, nullable — set only at the end of a
  successful rebuild), `updatedAt`. **No count/size columns exist or should be
  added** — derive them instead:
  - Document count + total bytes: `StorageService.listKnowledgeFiles(scope)`
    (`apps/lcp-server/src/storage/storage.service.ts:51`) already returns
    `StorageObject[]` with `size`/`lastModified` per object.
  - Chunk count: new query, e.g.
    `SELECT COUNT(*) FROM knowledge_chunk WHERE "roleId" = $1` (or
    `"roleId" IS NULL AND "companyId" = $1` for shared) — no schema change.
  - "Last successfully indexed at": `KnowledgeIndexState.updatedAt` **only
    when `fingerprint` is non-null** (a non-null fingerprint is written only
    on a completed rebuild — `apps/lcp-server/src/rag/knowledge-reindex.service.ts`'s
    `rebuild()`); report `null` if no successful rebuild has ever completed.
  - "Indexing in progress": `KnowledgeReindexService` builds its own BullMQ
    `Queue` internally (`this.queue = new Queue<RebuildJob>(QUEUE_NAME, ...)`,
    `knowledge-reindex.service.ts:88`) rather than going through NestJS's
    `BullModule`/`@InjectQueue` — add a method **on `KnowledgeReindexService`
    itself** (e.g. `isRebuilding(companyId, roleId): Promise<boolean>` using
    `this.queue.getJobs(['active', 'waiting', 'delayed'])` filtered by job
    data) rather than opening a second connection to the same queue elsewhere.
- `KnowledgeService` (`apps/lcp-server/src/api/knowledge.service.ts`) is the
  existing pattern to extend: it already resolves scopes
  (`resolveScope`/`KnowledgeScopeRef`) and is the natural home for a new
  `status(ref: KnowledgeScopeRef)` method, injecting `KnowledgeReindexService`
  (already a constructor dependency, line 51) and the `knowledge_chunk`
  repository/DataSource for the count query.
- CLI pattern to mirror exactly: `apps/lcp-cli/src/commands/reindex-knowledge.ts`
  (command registration) +
  `apps/lcp-cli/src/lib/docs/reindex-knowledge.action.ts` (thin action calling
  `apiRequest`) + its sibling `.spec.ts` (mocks `apiRequest`, asserts the exact
  URL/method and stdout JSON).

## Implementation

### 1. Server: stats query

Add `KnowledgeService.status(ref: KnowledgeScopeRef): Promise<KnowledgeStatus>`
returning something like:

```ts
interface KnowledgeStatus {
  documentCount: number;
  totalBytes: number;
  chunkCount: number;
  generation: number;
  lastIndexedAt: string | null; // ISO 8601, or null if never successfully rebuilt
  indexing: boolean;
}
```

For company scope, return one `KnowledgeStatus` per sub-scope (shared +
each role) as a keyed/array structure — decide the exact shape by mirroring
how `list`/other multi-scope responses are already shaped in this file, and
document your choice in this section's Deviations if it differs from this
sketch.

### 2. Server: endpoint

New route on `KnowledgeController`, JWT-guarded, Swagger-decorated like every
other route in the file:

- `GET /api/company/:companyId/knowledge/status` — status for shared + every
  role.
- Consider whether a role-scoped `GET /api/role/:roleId/knowledge/status` is
  also warranted (single-role status without listing every role) — recommend
  adding it, since it's a one-line extension of the same `status()` method
  and mirrors the existing role/company route pairing used throughout this
  controller.

### 3. CLI verb

`apps/lcp-cli/src/commands/get-knowledge-index-status.ts` +
`apps/lcp-cli/src/lib/docs/get-knowledge-index-status.action.ts`, following
`reindex-knowledge`'s exact command/action split:
`get-knowledge-index-status (--company X [--role Y] | --role Y)`, printing
the JSON response to stdout. Register it in `apps/lcp-cli/src/main.ts`
alongside the other `registerXxx` calls.

### 4. Tests

- Unit: `KnowledgeService.status` (unit-test the count/size/generation
  assembly with mocked `StorageService`/`KnowledgeReindexService`/repository);
  `KnowledgeReindexService.isRebuilding` (mock the BullMQ `Queue`).
- e2e: extend `test/e2e/lcp-server/knowledge.e2e-spec.ts`'s existing
  `reindex` describe-block style with a new `status` block covering the
  happy path, an unknown company, and the unauthenticated-401 case (matching
  every other endpoint in that file).
- CLI: `get-knowledge-index-status.action.spec.ts` mocking `apiRequest`,
  matching `reindex-knowledge.action.spec.ts`'s style exactly.

### 5. Documentation

Document the new endpoint/verb wherever `reindex-knowledge`/the knowledge
REST API is currently documented (grep `docs/` for `reindex-knowledge` and
`knowledge.controller`).

## Deviations

**2026-07-21 — company-scope response shape.** `KnowledgeService.status(ref)`
computes one `KnowledgeStatus` for a single scope (role, or a company's
_shared_ scope only — matching how `list`/`get`/`store` already treat a
`{kind: 'company'}` ref). A separate `statusForCompany(companyId)` resolves
the company, calls `status` for its shared scope and for each role, and
returns `{ shared: KnowledgeStatus, roles: { roleId, roleSlug, status }[] }`.
`GET /api/company/:companyId/knowledge/status` calls `statusForCompany`;
`GET /api/role/:roleId/knowledge/status` calls `status` directly. Both new
routes are registered _before_ their sibling `:filename` routes in
`KnowledgeController` (Express matches route patterns in registration
order — a `status` request would otherwise be swallowed by the earlier
`:filename` route).

**2026-07-21 — repository access.** `KnowledgeService` gained direct
`@InjectRepository` access to `KnowledgeChunk` (chunk count) and
`KnowledgeIndexState` (generation/fingerprint/updatedAt), registered
alongside its other entities in `ApiModule`'s `TypeOrmModule.forFeature`
(the same entities are also registered in `RagModule` for
`KnowledgeReindexService`'s own use — duplicate `forFeature` registration
across modules is normal in TypeORM/Nest and was the simplest option, since
`RagModule` doesn't export its repository providers).

Added `KnowledgeReindexService.isRebuilding(companyId, roleId)` exactly as
specified, checking the queue's `active`/`waiting`/`delayed` jobs.
