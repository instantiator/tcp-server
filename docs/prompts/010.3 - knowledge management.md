Embeddings should be kept in sync with the contents of the knowledge folders.

At the moment, the documentation describes the knowledge folders as:

```
knowledge/
  {role_name}/
```

Knowledge should be kept for each role, and for the whole company, and folders should be named by slug to make it easier for users to explore the data.

```
knowledge/
  {company_slug}/
  {role_slug_1}/
  {role_slug_2}/
```

## Embedding sync

Whenever documents stored in a `knowledge/{role_slug}` folder are changed, the RAG chunks/embeddings should be rebuilt so that the folder and embeddings database stay in sync.

This should happen regardless of the source - eg. if a user uploads into a `knowledge/*/` folder, or if an agent alters files in the knowledge folder, the embedding for that folder should be rebuilt.

## Embedding search rules

When a role attempts to retrieve knowledge from the RAG store, only the embeddings for that role, and the company embeddings, should be searched and made retrieved.

## Storage management (users)

A user may upload information (in the form of OKF documents) into any `knowledge/*` folder. At the moment, the `lcp-cli` allows upload into any path at all, through the `store-role-documents` verb. At the moment, this command accepts an unconstrained path.

Instead, let's introduce several new verbs to replace this:

- `list-knowledge (--role {role_slug-or-id} | --company {company_slug-or-id})`
- `delete-knowledge (--role {role_slug-or-id} | --company {company_slug-or-id}) --file {filename}`
- `get-knowledge (--role {role_slug-or-id} | --company {company_slug-or-id}) --file {filename}`
- `store-knowledge (--role {role_slug-or-id} | --company {company_slug-or-id}) --source {filename} [--target {filename}]`

When the knowledge stored in the system changes, the affected embeddings should be prepared again. This may take a while. If other changes come in that would alter the embeddings currently being prepared, the process should be halted and restarted for the new state of the files.

All other file based operations that users may wish to do (eg. exploring anything else) should be done by signing in to minio.

## Storage management (agents)

Most file storage operations that agents wish to do must also be constrained to prevent mistakes.

The `lcp-mcp-storage` service currently offers several tools:

- decribeServer
- describeFolder
- listFiles
- readFile
- writeFile
- deleteFile
- restoreFile
- searchFiles
- getFileProperties
- copyFile
- moveFile
- getFileSummary

These should all be further constrained.
