It's time to implement task orchestration.

Tasks are created by users, who specify a piece of work to be done (this can involve taking actions, researching answers, modifying shared storage, recalling information from RAG memory / creating new memories).

This is a big piece of work and the following prompts describe the work:

- @docs/prompts/010.1.1 - knowledge management.md
- @docs/prompts/010.1.2 - task orchestration planning.md

Please review both, and review related code:

- for consistency (I've revised the prompts several times, and may have missed a correction that needed to be applied everywhere)
- for opportunities to improve the approach
- for opportunities to simplify the approach (and to simplify the code that will eventually be written)
- for overlooked aspects that could lead to an incomplete or unsatisfactory implementation
- for incorrect assumptions (eg. that something exists or is implemented which isn't yet)
- for redundant features (ie. for code that isn't really needed and can be removed)

Because this is a significant piece of work, we are going to plan the creation of several documents that represent the plan.

Please create a new plan, synthesised from both prompts, in sufficient detail that it can be broken down into several pieces of work (sub-plans) to be delivered by Sonnet or Opus (ie. smaller / less capable models than Fable). It's expected that these sub-plans will be ordered. Aim to have them implement discrete and testable units of functionality (eg. an MCP service, or a capability, or migrations, etc.)

This plan should contain all the detail of the sub-plans, and be focussed on breaking up and storing the completed implementation plan as a series of sub-plans in separate files. Each sub-plan should be sufficiently contained and represent a part of the implementation. Each sub-plan should be complete: it should include implementation, tests, quality checks, and documentation updates. Their filenames should have prefix: `010.2.x - ` eg.

- `docs/prompts/010.2.1 - task orchestration: <part 1 focus>.md`
- `docs/prompts/010.2.2 - task orchestration: <part 2 focus>.md`
- `docs/prompts/010.2.3 - task orchestration: <part 3 focus>.md`
- etc.

Once these are created, we'll be able to implement each, one at a time - so that the implementing model is not overwhelmed by the size of the overall plan. Please be explicit about the quality checks to perform for each sub-plan. The prompt to the implementing model will be something like: `Please implement the plan laid out at: <path>` (ie. a simple instruction to read one of the sub-plans and implement it.)

Each sub-plan should have some additional instructions, stating:

- if the work becomes exceedingly complex or a problem is difficult to solve, to halt and inform the user - so that we can switch model (if necessary) or solve the problem together
- if the work reveals a beneficial alteration to the plan, to halt and inform the user - so that we can discuss any changes to the plan
- to document any changes to the plan by appending notes to the plan

Each sub-plan should incorporate knowledge of:

- our coding standards
- `npm run format` before any quality checks
- requirement to write unit / integration / e2e tests for all new code and code changes
- requirement to update related tests as code goes on
- basic quality checks at each stage of the process (`npm run typecheck`, `npm run lint`, `npm run build`, `npm run test`)
- requirement to run all test suites before completing the work (`scripts/run-all-tests.sh`)
- requirement to update documentation after each major piece of work
- requirement to update ADRs to track what's completed, and what remains (and to update any in the light of design changes)

Each sub-plan should also update and test the lcp-cli tool, if any changes would affect how it interacts with the system.
