# Internal Consistency Pass — LCP

## Context

`docs/prompts/009.1 - internal consistency.md` asks for a broad internal-consistency pass across the LCP monorepo: timestamps/UTC handling, quieter test output, data-quality warnings, prompt/MCP-list consistency between `LcpCompany`/`LcpRole`, automatic company-user creation, CLI deletion support, a context-window sizing tool, and slug-based lookups (plus a rewrite of the `setCompany`/`setRole` create-vs-update logic, which currently has a real atomicity gap).

Three research passes over the actual code confirmed the prompt's references are still accurate, and surfaced things worth fixing that weren't explicitly asked for but fall out of the same work:

- **Timestamp type history**: `lcp_agent.createdAt/updatedAt` and `audit_event.timestamp` were `TIMESTAMPTZ` in the original migration, then reset to plain `TIMESTAMPTZ`-less `TIMESTAMP` by a later migration. This is **not a bug to reverse blindly** — this repo has an established convention (see `[[feedback-typeorm-cross-db-dates]]` in project memory) that entity `Date` columns must stay **untyped** (no explicit `type:`) because the app runs against both SQLite (tests) and Postgres (deployment), and an explicit type string like `timestamptz`/`datetime` breaks one driver or the other. The most likely explanation: an auto-generated migration reconciled real drift back to what the (deliberately untyped) entity implies for Postgres — plain `timestamp`. The fix here is **Postgres-only, hand-written schema changes** (never touching entity decorators), with the reasoning documented so nobody "fixes" it back again.
- **`{{date}}` in prompts** is duplicated verbatim in two files and only ever supplies a bare calendar date (no time, no explicit UTC label), despite the prompt spec implying "time and date."
- **No automatic `CompanyUser` creation** happens today, despite `MemberType` already having a `'creator'` value implying it should.
- **No DELETE endpoints exist yet** for company/role, and five tables (`conversation`, `conversation_message`, `knowledge_chunk`, `episodic_memory`, `company_user`) have **no FK constraints at all** back to `lcp_company`/`lcp_role` — adding delete support requires fixing this first, or deletes will silently orphan data.
- **`ContextBudgetService`** (tiktoken-based token counting, already in `libs/lcp-shared`) is a ready-made engine for the context-window estimator — no new counting logic needed.
- **`resolveRunConfig`** (`libs/lcp-shared/src/config/resolve-run-config.ts`) is the existing precedence pattern (`role ?? company ?? env ?? default`) — the new resolvers build on a shared base rather than re-deriving the pattern ad hoc.

User decisions from clarification and plan review:
1. Plan all workstreams as phases, not just a subset.
2. Data-quality warnings surface at both the API and CLI layers.
3. Existing naive-`TIMESTAMP` columns get migrated to `TIMESTAMPTZ` in Postgres now (assuming Postgres session timezone is UTC — no `TZ` override anywhere in `docker-compose.yml`) — via hand-written migration only, **not** by adding explicit types to entities (see above).
4. The MCP server list is **additive**, not a precedence chain (system + company + role servers are all made available, unioned) — must not share the override-style resolver logic used for LLM config / prompt template.
5. The precedence-chain resolvers (LLM config, system prompt template) should share code via a common base class, both for DRY and to make the configuration-resolution system easier to extend consistently later.
6. CLI warnings print in yellow with a warning-emoji prefix.
7. The default system prompt template also tells the agent the company's region and the locally-adjusted time, not just UTC.
8. This plan document itself becomes `docs/prompts/009.2 - internal consistency plan.md` in the repo (first action once implementation starts).
9. Every phase must check and update related documentation; a final phase reconciles all ADRs' implementation-status fields against what's actually been built.

New shared code in `libs/lcp-shared`, replacing logic currently duplicated or hand-rolled per call site:

| Helper | Location | Shape | Replaces |
|---|---|---|---|
| `PrecedenceResolver<T>` (abstract base) | `libs/lcp-shared/src/config/precedence-resolver.ts` | template method: subclasses supply ordered sources + a default, base does the null-coalescing scan | — new, DRYs the two resolvers below |
| `LlmConfigResolver extends PrecedenceResolver<LlmConfig>` | `libs/lcp-shared/src/config/resolve-llm-config.ts` | `role.llmConfig → company.llmConfig → env fallback` | ad hoc chain in `agent-loop.service.ts:156-159` |
| `SystemPromptTemplateResolver extends PrecedenceResolver<string>` | `libs/lcp-shared/src/config/resolve-system-prompt-template.ts` | `role.systemPromptTemplate → company.systemPromptTemplate → baked-in default` | direct `role.systemPromptTemplate` reads in `agent-loop.service.ts` / `chat.service.ts` |
| `resolveMcpServerList(registryNames, company, role)` | `libs/lcp-shared/src/mcp/resolve-mcp-server-list.ts` | plain function — **additive union + dedup**, not precedence | inline union in `agent-loop.service.ts:233-240` that today ignores company |
| `buildPromptDateVars(company)` | `libs/lcp-shared/src/llm/prompt-vars.ts` | plain function returning `{ date, datetime, timezone, localDatetime }` | duplicated `new Date().toISOString().split('T')[0]` in `agent-loop.service.ts:616-622` and `chat.service.ts:244-250` |
| `findCompanyByIdOrSlug` / `findRoleByIdOrSlug(companyId, idOrSlug)` | methods on `DbService` | — | existing ad hoc `isUUID(...)` branch already in `DbService.getCompany` |

**Why the MCP list resolver doesn't extend `PrecedenceResolver`**: precedence means "first defined value wins" (a single winning value); the MCP list is a union of *all* sources at once (system + company + role), a fundamentally different shape with no shared scan logic to DRY. Forcing it into the same base class would just be a `resolve()` override that ignores the base's early-return logic entirely — so it stays a small standalone function instead.

**`PrecedenceResolver<T>` design**:
```ts
export abstract class PrecedenceResolver<T> {
  protected abstract getSources(): Array<T | null | undefined>;
  protected abstract getDefault(): T | undefined;

  resolve(): T | undefined {
    for (const source of this.getSources()) {
      if (source !== null && source !== undefined) return source;
    }
    return this.getDefault();
  }
}
```
`LlmConfigResolver`/`SystemPromptTemplateResolver` each just implement `getSources()`/`getDefault()` from their constructor args and call `.resolve()`. Note for later (not part of this pass, just flagged): `resolveRunConfig`'s per-field precedence over `AgentRunConfig` is a different shape again (it resolves one key inside a nested config object, not a whole value) — it could theoretically be rebuilt on top of the same base per-key, but that's a separate refactor outside this pass's scope; mention it as a follow-up opportunity in Phase Z's docs, don't do it now.

## Phase A — UTC timestamps (Postgres-only) + company timezone + localized prompt time

- **Entity decorators stay untyped** — do not add `type: 'timestamptz'` anywhere in `libs/lcp-shared/src/models/*.model.ts`. This is deliberate: TypeORM's `Date`-typed columns must remain driver-agnostic so the same entities work against SQLite (tests) and Postgres (deployment) — an explicit `timestamptz`/`datetime` string breaks one or the other. Add a short doc comment to this effect near the top of `libs/lcp-shared/src/models/LcpAgent.model.ts` (the file with the most affected columns) linking to the fuller explanation in `docs/database.md` (new section, see below).
- New **Postgres-only, hand-written migration** converts the 9 naive-`TIMESTAMP` columns to `TIMESTAMPTZ` directly in the schema (not via entity metadata):
  ```sql
  ALTER TABLE "<table>" ALTER COLUMN "<col>" TYPE timestamptz USING "<col>" AT TIME ZONE 'UTC';
  ```
  Columns: `audit_event.timestamp`, `company_user.createdAt`, `conversation.createdAt`, `conversation_message.timestamp`, `episodic_memory.createdAt`, `knowledge_chunk.createdAt`, `lcp_agent.createdAt`/`updatedAt`/`pausedAt`. Top-of-migration comment notes the UTC-session-timezone assumption and suggests `SHOW timezone;` as a pre-flight check. `down()` reverts to naive `TIMESTAMP`.
- **New `docs/database.md` section, "Timestamp storage convention"**: explains why entities are untyped, that Postgres columns are hand-migrated to `TIMESTAMPTZ` for correctness while SQLite test runs are unaffected, and that `npm run migration:generate` will continue to report "drift" on these columns forever as a result — this is expected and already covered by the project's existing drift-is-diagnostic-only convention (`scripts/check-migrations.sh`), not something to "fix" by adding explicit types back.
- `buildPromptDateVars(company)` (cross-cutting helper) replaces both duplicated date-injection call sites. Returns:
  ```ts
  { date: string; datetime: string; timezone: string; localDatetime: string }
  ```
  where `datetime` is an explicit, human-labeled UTC timestamp (e.g. `2026-07-06 14:32 UTC`), `timezone` is `company.timezone ?? 'UTC'`, and `localDatetime` is `datetime` re-rendered via `Intl.DateTimeFormat` with `timeZone: timezone` (falls back to being identical to `datetime` when no company timezone is set, so the template never renders an empty/broken sentence). Existing `{{date}}` templates keep working unchanged.
- Add `timezone?: string | null` to `LcpCompany` (`@Column({ type: 'varchar', nullable: true })`, IANA name e.g. `'Europe/London'`) — **display and prompt-localization only**: storage stays UTC always; the LLM is still always told the authoritative UTC time explicitly, with the local time given as additional context (never a replacement). Added to the same migration as Phase D's company-column changes.
- Thread the company timezone into CLI display formatting: `apps/lcp-cli/src/lib/queries/read-query.action.ts` (`toLocaleString()` at lines 32/48) — extend the conversation-read response to include `companyTimezone`, pass to `new Date(x).toLocaleString('en-US', tz ? { timeZone: tz } : undefined)`. Check `apps/lcp-cli/src/lib/chat/session.ts` and `apps/lcp-cli/src/lib/tui/tui-format.ts` for the same pattern at implementation time.
- MinIO: no code change needed — `LastModified` is already exposed as UTC ISO strings (S3 API guarantee, independent of container config); add a one-line confirmation note to `docs/database.md` or `docs/shared-storage.md`.
- Keycloak: no code change in this pass — `jwt.strategy.ts` has no `clockTolerance` (defaults to 0); note as an optional future follow-up only, in Phase Z's docs pass.
- **Docs**: `docs/glossary.md`, `docs/schema.md`, `docs/lcp-agent.md` — add `{{datetime}}`, `{{timezone}}`, `{{localDatetime}}`, document new `LcpCompany` fields (`timezone`, `systemPromptTemplate`, `mcpServerList`); `docs/database.md` gets the new timestamp-convention section described above.

## Phase H — Slug lookups + `setCompany`/`setRole` rewrite

- `LcpRole` gets a new `slug` column (per-company unique, unlike `LcpCompany.slug` which is already globally unique via `UQ_lcp_company_slug` since the initial migration). New migration: add nullable `slug`, backfill via `slugify(name)` + de-dup suffix per `companyId` (JS loop in the migration's `up()`), `SET NOT NULL`, then `CREATE UNIQUE INDEX ON lcp_role ("companyId", "slug")`.
- `DbService` gains `findCompanyByIdOrSlug` (refactor of existing `getCompany`) and `findRoleByIdOrSlug(companyId, identifier)` (role slugs are company-scoped, so always requires a company). A `WithSlug { id: string; slug: string }` type documents the shape — not a runtime service, just two focused methods.
- Routing: company's existing `/api/company/:id` already accepts id-or-slug via `isUUID` detection (`db.service.ts:92-97`) — keep that. For roles, add a company-scoped route (e.g. `/api/company/:companyId/roles/by-slug/:slug`) since a bare role slug is ambiguous without knowing the company; `/api/role/:id` stays UUID-only.
- **Rewrite `DbService.setCompany`** (`apps/lcp-server/src/db/db.service.ts:57-85`), replacing delete-by-slug-then-recreate:
  ```ts
  async setCompany(
    company: DeepPartial<LcpCompany>,
    { id, slug }: { id?: UUID; slug?: string } = {},
  ): Promise<LcpCompany> {
    const updateIndex = id ?? company.id ?? (slug ? (await this.companyRepo.findOneBy({ slug }))?.id : undefined);
    const isUpdate = !!updateIndex;
    const existing = isUpdate ? await this.companyRepo.findOneBy({ id: updateIndex }) : null;
    if (isUpdate && !existing) throw new NotFoundException(`Company ${updateIndex} not found`);
    const merged = existing
      ? { ...existing, ...company, llmConfig: /* same deep-merge as today, renamed */ }
      : company;
    return this.companyRepo.save(this.companyRepo.create(merged));
  }
  ```
  Drops the `replace: boolean` param (redundant with `isUpdate`). Looking up the entity **before** merging, and merging in place instead of delete+insert, is itself the atomicity fix for the race the user flagged — there's no longer a window where the row doesn't exist. A smaller residual race remains between concurrent writers reading `existing` before either saves — flag `@VersionColumn()` optimistic locking (already used elsewhere via the `AddVersionColumns` migration, but not on `lcp_company`/`lcp_role`) as future hardening, out of scope here.
- Apply the identical pattern to roles: unify `createRole`/`updateRole` into one `setRole(partial, { id, slug, companyId })`, same 404-before-merge-no-delete discipline. `POST /api/role` and `PUT /api/role/:id` both delegate to it.
- Update `ApiService.setCompany` (currently hardcodes `replace=false`) and the role-controller equivalent to pass `{ id, slug }` through instead.
- `lcp-cli`: add `--company-slug`/`--role-slug` alongside every existing `--company-id`/`--role-id` (confirmed call sites: `list-role-documents.ts`, `list-open-queries.ts`, `list-roles.ts`, `remove-role-documents.ts`, `store-role-documents.ts`, `set-role.ts`). Add a small shared resolver (e.g. `resolveCompanyIdentifier`/`resolveRoleIdentifier` in `apps/lcp-cli/src/lib/core/`) instead of duplicating the "prefer id, fall back to slug, error if both/neither" branch six times.
- `lcp-agent`: `apps/lcp-mcp-interactions/src/mcp/interactions-tools.service.ts`'s `request_agent_consultation` tool gains optional `companySlug`/`roleSlug` zod fields as alternates to the existing required `companyId`/`roleId` UUIDs. `buildInitialState`'s prompt vars add `companySlug`/`roleSlug` alongside (not replacing) the existing id vars.
- **Docs**: `docs/lcp-cli.md` (new flags on every affected verb), `docs/schema.md`/`docs/glossary.md` (new `LcpRole.slug` field, per-company uniqueness contrasted with company's global uniqueness).
