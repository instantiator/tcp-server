# 010.5.2 — Agent improvements

**Recommended implementation model: Sonnet** — five well-scoped, mostly mechanical changes with clear call sites. Keep the quality gate green after each change (`./dev-environment/scripts/check.sh`); run the full suite (`./scripts/run-all-tests.sh`) before declaring done; e2e via `./scripts/run-e2e-tests.sh`.

## Context

Feedback from recent task runs: an agent in finalisation mode ran out of iterations while reconciling a markdown file that should have been a csv. Three contributing factors: the iteration budget is small, the planner isn't hinted strongly enough to weave final output files into the plan, and the storage toolset makes whole-file replacement awkward. Separately, failed assignments carry no human-readable reason.

A second, related observation from live runs (see section 5): agents have been seen writing to/naming files by their full resolved storage key (e.g. `test-company/tasks/{taskId}/assignments/2/working/report.md`) instead of a bare filename — a prompt-assembly bug that both wastes iterations (self-inflicted completion-gate mismatches) and risks writing to the wrong place in shared storage. Likely a further contributing factor to the iteration-exhaustion pattern above, not just a separate polish item.

## 1. Double(d) the iteration default → 40

The real code default is **10** (`DEFAULT_AGENT_ITERATIONS`, `libs/lcp-shared/src/config/defaults.ts`), despite `.env` example comments implying 20. Decision made: adopt **40** (the value proven in live use) as the new default.

- `libs/lcp-shared/src/config/defaults.ts`: `DEFAULT_AGENT_ITERATIONS = 40`.
- `.env.example` and `.env.testing`: update the commented line to `# AGENT_ITERATIONS=40` (comments should show the true default).
- The live `.env` already sets `AGENT_ITERATIONS=40` — leave it.
- Resolution order (unchanged, for reference): role `runConfig.maxIterations` → company `runConfig` → `AGENT_ITERATIONS` env → default (`apps/lcp-agent/src/agent/agent-loop.service.ts`; enforced in `libs/lcp-shared/src/llm/run-supervised-graph.ts`).
- Update any docs stating the old default.

## 2. New storage tool: `create_working_file`

In `apps/lcp-mcp-storage` (tools defined in `src/mcp/storage-tools.service.ts`, descriptions in `src/storage-tool-descriptions.ts`, loaded from `src/tools.jsonc`):

- New tool `create_working_file` — `{ agentId: uuid, filename: string, content: string, overwrite?: boolean }`.
  - File does not exist → create it with `content`.
  - File exists and `overwrite: true` → replace the whole file.
  - File exists and no/false `overwrite` → **fail with a clear warning** naming the file and suggesting `overwrite: true` or `append_working_file`.
- This serves both the "file replacement" need (overwrite instead of delete-then-create or fragile string surgery) and simpler creation (less reasoning than using append-as-create).
- Gate it with the existing read-only mode check (`READ_ONLY_WORKING_TOOLS`) — refused in `plan`/`qa`/`chat`/`consultee` modes, like the other mutating tools.
- `append_working_file` keeps its create-if-missing behaviour, unchanged. `replace_in_working_file` already covers string find/replace — no new tool needed there.
- Tool description should be short and directive (these agents may have small context windows): when to create vs append vs replace-in.

Rationale note for the implementer: the toolset is deliberately small to support small-context agents. One added tool plus sharper hints (below) is the chosen balance — do not add further tools (e.g. write/patch/move variants) in this pass.

## 3. Planner hints: weave final outputs into the plan

`MODE_PROMPTS.plan` (`libs/lcp-shared/src/prompts/mode-prompts.ts`) already directs matching output types and making the final step produce the task's overall expected output. Strengthen it:

- Explicitly instruct the planner to **weave the task's final expected output files and their types into the plan steps**, so the files are created in the right format _during_ the plan by the assigned agents — not left to a separate finalisation/reconciliation pass at the end.
- Where a task expects specific file types (e.g. csv), each producing step's expected output should name the file with the correct extension/format.
- Review the finalise agent's prompt (built in `apps/lcp-server/src/api/task-orchestration.service.ts`, around the finalise-prompt construction) for consistency: finalisation should verify/assemble expected outputs, not convert formats that steps should have produced directly.

**Prerequisite work already done (as of this note):** a step referencing an earlier step's approved output via an `assignment-completed-path` material used to crash prompt assembly outright (`AgentLoopService.buildInitialState` never populated `ArtifactResolutionContext.planAssignments`) — fixed. `AssignmentService.planTask` now also rejects, at plan-creation time, any `assignment-completed-path` material whose value doesn't match an earlier step's declared `assignment-working-path` expected output in the same plan (`resolveArtifactKey`'s cross-reference guarantee, enforced structurally before any assignment is created). This strengthened prompt should lean on that existing guardrail rather than duplicate validation in prose — just make sure the planner's guidance stays consistent with it (name the exact same filename in both the producing step's `expected` and the consuming step's `materials`).

## 4. Assignment `failureReason`

Tasks already carry `failureReason` (`libs/lcp-shared/src/models/LcpTask.model.ts`); assignments do not. Add the mirror:

- `libs/lcp-shared/src/models/LcpAssignment.model.ts`: nullable string column `failureReason` (follow the task model's column style).
- New migration + **manual registration in `apps/*/src/app.module.ts`** (import + migrations array — the CLI data-source glob silently masks omissions; repo rule).
- Populate with simple human-readable reasons at every site that sets an assignment to `failed`:
  - `task-orchestration.service.ts` QA-exhaustion path → `did not pass QA`
  - `task-orchestration.service.ts` planner-completed-without-plan path → `created a plan with 0 assignments`
  - Agent-run failures must propagate to the owning assignment through the existing failure-notification/status-update flow (`agent-loop.service.ts` `failRun`/abort paths, `run-supervised-graph.ts` failure reasons, `pause-and-resume.service.ts` `failAgent`, `chat.service.ts` failure path), with reasons such as:
    - `timed out after ${secs} seconds`
    - `exceeded ${maxIterations} iterations`
    - `did not call required tools: ${csvOfRequiredToolCalls}`
    - `unexpected LLM failure`
- Residual case worth covering: `AssignmentService.resolveMaterials` (backing `GET /internal/agent/:id/storage-scope`, used by every `lcp-mcp-storage` tool call, not just material-reading ones) now throws on an unresolvable material instead of silently dropping it. Each MCP tool call already catches this and returns it as normal tool output, so the agent can react — but if it doesn't and instead loops to iteration/timeout exhaustion, the resulting `failureReason` (e.g. "exceeded N iterations") won't say why. `planTask`'s plan-time validation (see section 3) makes this rare for a normally-created plan, but it's not structurally impossible, so it's worth a failureReason case if it's not already covered by the generic iteration/timeout reasons above.
- Expose `failureReason` in the assignment API responses and in the CLI's assignment display (wherever status is shown).
- Regenerate generated artefacts (`schemas/schema.json`) via `npm run build` — never hand-edit.

## 5. Stop showing agents resolved storage keys — filenames only

### The problem, confirmed

An assignment's own presentation of its `materials`/`expected` list (`buildAssignmentMessage` → `renderArtifactList`, `libs/lcp-shared/src/prompts/prompt-assembly.ts`) prints **the fully resolved storage key** — `resolveArtifactKey(a, ctx) ?? a.value` — not the bare filename/name the scoped MCP tools actually take. So an implement-mode agent's "Expected outputs" line reads something like `test-company/tasks/{taskId}/assignments/2/working/cat-chicken-team-game.md` instead of `cat-chicken-team-game.md`. The agent reasonably echoes that same string back as the tool's `filename`/`prepared[].value`.

This is more than noise. `resolveScopedKey` (`apps/lcp-mcp-storage/src/mcp/storage-tools.service.ts`) only rejects an absolute path or a `..` segment — a relative-looking full key like the one above passes straight through and gets **concatenated onto the already-resolved working prefix**, silently writing to a doubly-nested, wrong location instead of erroring. The tool call "succeeds", the agent believes it's done, `complete_assignment`'s gate then can't find the file at the real expected location and rejects it — wasted iterations reconciling a self-inflicted mismatch.

`qa-prompts.ts::renderArtifacts` shows the resolved key too, but for a different (previously reasonable-looking) reason: it deliberately points QA at the _unscoped_ `read_file` tool with a full key. That's unnecessary — a `qa`-mode caller's `resolveStorageScope` already points `workingPrefix` at the _target_ assignment's working directory (read-only), so QA can use the _scoped_ `read_working_file(filename)` with the same bare filename the implementing agent used.

### Rule: what the framework should already resolve, by caller mode × tool

| Caller situation                                                                                | Tool(s)                                                                                                                                                                          | What the agent supplies                                                                                                                       |
| ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Any mode, any material (task upload / prior approved step / inline — the origin doesn't matter) | `list_material_files` / `read_material_file` / `get_material_file_properties`                                                                                                    | bare **name** (`ResolvedMaterial.name` is already just the artifact's declared value — already correct)                                       |
| `implement` / `consultee` / `plan`, own working dir                                             | `append_working_file` / `read_working_file` / `replace_in_working_file` / `delete_working_file` / `restore_working_file` / `rename_working_file` / `get_working_file_properties` | bare **filename**, scoped server-side via `resolveStorageScope` → `workingPrefix` (already correct)                                           |
| `qa`, target assignment's working dir (read-only)                                               | same scoped `*_working_file` tools, pointed at the target's `workingPrefix`                                                                                                      | bare **filename** — **should** use these instead of `read_file` + a resolved key (currently wrong)                                            |
| `finalise`, task's `completed/` dir                                                             | same scoped `*_working_file` tools, `taskCompletedPrefix`                                                                                                                        | bare **filename** — already correct (`dispatchFinalise` hand-builds its prompt from `task.expected`, doesn't go through `renderArtifactList`) |
| `complete_assignment`'s `prepared[]`, `create_plan`'s `expected[]`/`materials[]`                | —                                                                                                                                                                                | bare **filename/value** (the tool schema already says so — the bug is the agent's own assignment prompt contradicting it)                     |
| Anyone browsing _outside_ their own scope (shared knowledge, cross-task inspection)             | `list_files` / `read_file` / `search_files` / `get_file_properties` / `get_file_summary` / `describe_folder`                                                                     | full key — genuinely correct here, the one legitimate case for a full path                                                                    |

The underlying path-resolution logic already exists and is already correct (`resolveArtifactKey` server-side, `resolveScopedKey` in `lcp-mcp-storage`) — this isn't a "build it" item, it's "stop bypassing it in agent-facing text."

### Action items

- `prompt-assembly.ts::renderArtifactList` — show `a.value` (the bare name/filename) always; never `resolveArtifactKey(...)`. Adjust the surrounding text to point at the matching scoped tool (`read_material_file` for materials; `append_working_file`/`complete_assignment`'s `prepared` for expected) instead of implying a raw storage-key lookup.
- `qa-prompts.ts::renderArtifacts` — same: bare filename, point QA at `read_working_file` (its own resolved scope), drop the full-key text entirely.
- `resolveScopedKey` (`storage-tools.service.ts`) — harden against a full-path-shaped filename slipping through some future prompt regression: reject a filename containing more than one path segment (or, narrower, one containing `tasks/`, `assignments/`, `materials/`, `completed/`, or `working/` as a segment) instead of silently concatenating it onto the prefix. Defense in depth, independent of the prompt fix above — the tool should refuse a wrong-shaped filename loudly, not accept it and write to the wrong place.
- Once neither renderer needs the resolved key for _display_, check whether `resolutionContext`/`ArtifactResolutionContext` is still needed at each call site for anything else (likely yes — e.g. `planTask`'s cross-reference validation is separate) — don't strip the parameter, just stop rendering its resolved output.
- `MODE_PROMPTS.qa` (`mode-prompts.ts`) currently just says "read the file artifacts via the storage service" — tighten to name `read_working_file` explicitly, to match.
