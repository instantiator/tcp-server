## Context

The web UI can't create, edit or delete roles, manage knowledge, or show a company's users. The CLI can do the first two with raw JSON, and nothing shows the users. This plan adds an **Admin** tab (Roles, Users, Knowledge, Data protection) and renames **Tables** to **Data** (tables and document links), so a company can be configured from the browser.

### What exploration found

- **Tabs** (`pages/CompanyPage/CompanyTabs.tsx`): the hash picks the tab (`hash.slice(1).split('/')`, :92). `TABLES_TAB` and `DATA_PROTECTION_TAB` are not force-mounted. `TablesPanel.tsx` already has a left list/main layout (`TablesPanel.css:2-41`, ListBox with label and description slots).
- **Hooks** (`api/endpoints.ts:170-265`): reads exist for roles, users, role knowledge (list, status, search) and company knowledge (list, status). Most are unused. **There are no mutations** for roles, users or knowledge. `role`, `company-user` and `knowledge` are `STATIC_ENTITIES` (not live).
- **Uploads:** `postFileForJson` (`api/client.ts:139`) with field `file`. Native `<input type="file">` is the house choice (`CreateTaskDialog.tsx`, `RecordTableActions.tsx`).
- **UI parts to reuse:** `Dialog`, `ConfirmDialog`, `RoundIconButton` with tooltips, `ActivityList` states (`LoadingState`/`ErrorState`/`EmptyState`), `announce()`, `tCount`, and `api/warnings.ts` (decodes `X-Tcp-Warnings`). There is **no table component and no tabbed dialog** yet.
- **Roles API** (`api/api.role.controller.ts`): `POST /api/role`, `PUT|GET|DELETE /api/role/:id`. Create needs `companyId, slug, name, description, knowledgeDomains[], mcpServerList[]`. The optional fields are `rolePrompt`, `mcpServerToggles`, `llmConfig` and `systemPromptTemplate`. `shared` is a reserved slug.
  - Warnings come back in `X-Tcp-Warnings`.
  - `MaskSecretsInterceptor` returns `apiKey` as `***`, so the form must never send it back.
- **Deleting a role** cascades in the database: chunks, agents, conversations and memory go, and `company.plannerRoleId` is set to null. **The knowledge files in object storage and the `knowledge_index_state` row are left behind**, so a new role with the same slug inherits the files.
- **Planner:** if the company's planner role is deleted, starting a task returns 422 unless the task names its own planner.
- **Knowledge API** (`api/knowledge.controller.ts`):
  - Upload accepts `.md .txt .html .pdf .docx .csv .json .yaml` and converts to Markdown. **There is no size limit.**
  - Only company reindex exists, and it rebuilds every role. `KnowledgeReindexService.bump(companyId, roleId)` (:158) already rebuilds one scope.
  - The only query route is per role (role chunks plus shared ones), embeddings only. **There is no company-only query.**
  - Nothing streams indexing status.
- **MCP:** the catalogue is `MCP_REGISTRY` (`libs/tcp-shared/src/mcp/mcp-registry.ts`), and no route exposes it. Each server is enabled by `role.toggles[name] ?? company.toggles[name] ?? true`.
- **LLM fallback:** role, then company, then environment, whole-object (`resolve-llm-config.ts`).
- **Users:** `GET /api/company/:id/users` gives `identifier, name, memberType, roles[], knowledgeDomains[], createdAt`. No route checks `memberType`. There is no `/api/me`. `MembershipsDialog` lists `useCompanies({})`, and `ProfileDialog` shows the OIDC claims.
- **Documents:** there is no storage browse route. `storageLink.ts` `taskOutputsUrl` builds a URL into the Silo console, or `null` if it isn't configured. It is used in `TaskDetails.tsx`.

### Decisions agreed with you (2026-10-16)

- **The LLM setting is read-only in the role dialog.** It shows the effective setting and where it comes from (this role, the company, or the app default), plus "Use the company's setting" when the role has its own. Editing waits for 002.01.
- **Backend additions:**
  - deleting a role removes its files and index state;
  - a company-only knowledge query;
  - a per-role reindex;
  - a 50 MB upload limit;
  - an MCP catalogue route.
- **Data uses one merged menu:** a "Tables" section listing each table, then "Documents".
- **Memberships merge into Profile**, showing your member type per company. The separate Memberships menu entry goes.

### Design (object at approval if wrong)

**Tabs and hashes.** The order is Company view, the six activity tabs, **Data**, **Admin**.

| Hash                                                                         | Shows                                        |
| ---------------------------------------------------------------------------- | -------------------------------------------- |
| `#data`                                                                      | Data, with the first table selected (if any) |
| `#data/tables/<name>`                                                        | That table                                   |
| `#data/documents`                                                            | Document links                               |
| `#admin`                                                                     | Admin, on Roles                              |
| `#admin/roles`, `#admin/users`, `#admin/knowledge`, `#admin/data-protection` | That section                                 |

- **Old hashes are rewritten** with `replace`: `#tables/<x>` → `#data/tables/<x>`, and `#data-protection` → `#admin/data-protection`. Bookmarks and sign-in returns keep working.
- **Side menu:** the `TablesPanel.css` grid moves to `base.css` as `.tcp-side-menu`, `__menu` and `__main`, and stacks below 40rem. It's a shared class, not a component.
- Each menu is a single-select `ListBox` with an `aria-label`, as `TablesPanel` does now. Selecting an item moves no focus (`TablesPanel.tsx:25-35`).

**Tables.** We use React Aria `Table`, which is new to the app. It gives `sortDescriptor` (client-side sort), `selectionMode="multiple"` with checkbox cells, and a `SearchField` filter above it. Four tables use it: roles, users, knowledge documents and query results. **We won't build a shared wrapper.** There's one small `sortRows(rows, descriptor)` helper in `components/Table/sortRows.ts`, plus `.tcp-table` styles in `base.css`. A filter with no matches shows `EmptyState`.

**Admin → Roles** (`pages/CompanyPage/admin/RolesAdmin.tsx`):

- **Toolbar** of round icon buttons: Add role (`Plus`), and Delete selected (`Trash2`), which is disabled with no selection and named for the count.
- **Columns:** selection, Name, Slug, Description (truncated), Planner (a text "Default planner" marker, not just an icon), and an Open (`PanelRightOpen`) button per row, named "Open <role>". Pressing the name opens the dialog too. Name and Slug sort.
- **Delete** uses `ConfirmDialog`:
  - It says "Delete N roles? Their knowledge, agents and conversations are deleted too."
  - If the planner is among them, it adds: "<name> is the company's default planner. Tasks without their own planner won't start until another is chosen."
  - After deleting, focus goes to the table, or to Add role if the table is empty. The change is announced.

**Role dialog** (`pages/CompanyPage/admin/RoleDialog.tsx`) is a `Dialog` with React Aria `Tabs`: **Details | Knowledge**.

- **Details form**, modelled on `RetentionDialog`:
  - name;
  - slug (create only; filled from the name until edited; `shared` is refused);
  - description;
  - role prompt (TextArea);
  - knowledge domains (comma-separated);
  - **MCP servers**: one `Select` per catalogue server with _Company default (on/off)_ / _On_ / _Off_, mapping to `mcpServerToggles`;
  - **LLM**: read-only, as agreed.
- Saving is `POST` for a new role and `PUT` (partial) for an existing one. `systemPromptTemplate` is left untouched.
- Warnings appear inside the dialog. Field errors attach to their fields.
- **The Knowledge tab is disabled until the role is saved.** Its tooltip explains why. After creating, the dialog stays open on the new role.

**Knowledge panel** (`pages/CompanyPage/admin/KnowledgePanel.tsx`), scope `{ kind:'role', roleId } | { kind:'company', companyId }`, used by the role dialog and by Admin → Knowledge:

- **Document table:** name, size, modified, and a per-row delete (`ConfirmDialog`; focus goes to the next row, else the upload button).
- **Upload:**
  - A native file input behind a round `Upload` button.
  - The accepted types and the 50 MB limit are shown as text **before** picking.
  - A pending state, and a Cancel button that aborts the request with `AbortController` (no byte progress: `fetch` gives none).
  - Errors are shown and announced.
- **Status line:** documents, chunks, last indexed, "Indexing…" and the last error.
  - A round **Refresh** button refetches it.
  - **It also polls every 3 s while `indexing` is true**, and announces "Knowledge index ready" or "failed" when that changes.
- **Reindex** (`RefreshCcw`) is disabled while uploading or indexing. _Challenge:_ uploads already reindex automatically, so this is a manual retry. It reads "Rebuild index" so it isn't mistaken for a required step.
- **Query:** a `TextField` and a Search button below the table. The results table shows source file (the last path segment), similarity % and chunk text. Embeddings only, no LLM.

**Admin → Users** (`admin/UsersAdmin.tsx`): a read-only table (name, identifier, member type, roles), sortable, with a name filter. A note says: "For now, every member can do everything in this company." (ADR-011 flags are not built.)

**Admin → Knowledge** is the `KnowledgePanel` for company scope. **Admin → Data protection** is the existing `DataProtectionPanel`, unchanged.

**Data → Documents** (`pages/CompanyPage/DocumentsPanel.tsx`):

- A table of links into the Silo console: Company root (`<slug>/`), Company resources (`<slug>/resources/`), and one row per task's outputs (`useLiveTasks`, newest first).
- `storageLink.ts` gains `storageFolderUrl(config, prefix)`, and `taskOutputsUrl` uses it.
- Without console config, it shows the existing "not configured" text.
- Links open in a new tab with the existing visually-hidden suffix. A Refresh button refetches the tasks.

**Profile:**

- `ProfileDialog` gets a "Your companies" section (the `MembershipsDialog` list plus member type). `MembershipsDialog` and its Account menu item are removed.
- Backend: `GET /api/company` rows gain `memberType: 'creator'|'owner'|'member'|null` (`null` for an admin's `?all` rows they don't belong to).

### Security notes

- Uploads now have a size limit (closing a disk/memory DoS gap). Types are still checked on the server.
- The API key is never round-tripped: the dialog shows only provider, model and base URL.
- Deleting role files now runs before the DB delete, so a failure can't leave orphaned files for a future same-slug role to inherit.
- Any member can still delete roles. This is recorded, not fixed (permission flags are deferred).

### Changed while implementing stage 1 (2026-10-16)

- **The order is files, then the role row, then the index state**, not the state before the row. The state row is keyed by the role's UUID, so it can't leak to a new same-slug role; only the files can. Deleting the state last means a rebuild queued by the file deletes finds no role and stops, rather than writing a fresh state row for a role about to vanish.
- **The logic lives in `KnowledgeService.deleteRole`**, called by both delete routes (`/api/role/:id` and the company's by-slug route). `DbService.deleteRole` now says it leaves files behind.
- **A storage failure propagates as whatever error storage raised**, not a mapped 502. The role is still left intact.
- **`queryRag` takes a scope ref**, and `KnowledgeRetrievalService.retrieve` accepts a `null` role for shared-only.
- **Knowledge uploads use multer's `limits.fileSize`**, which stops reading at 50 MB and answers 413. The storage proxy keeps its own `ParseFilePipe` check, which only runs after the whole file is buffered. That was left alone as out of scope and is noted for wrap-up.
- The e2e tests are in `knowledge.e2e-spec.ts`. The storage-failure case is a unit test (`knowledge.service.spec.ts`).

### Changed while implementing stage 2 (2026-10-16)

- **Sonnet did the stage in one pass.** `memberType` is tested in `company-scoping.e2e-spec.ts`, which already had the sub/email/admin setup. `CompanyListItem` in `@tcp/shared` gained `memberType`.
- **`schema.d.ts` is regenerated at the start of stage 3**, not here, so one rebuild of the stack covers it.
- The "another company's role is 403" e2e case was dropped: `route-audit.spec.ts` checks that the route declares `@CompanyScope`, which is the same guarantee every other knowledge route relies on.

### Changed while implementing stage 4 (2026-10-16)

- **Done before stage 3**, because it needs none of the new routes, and stage 3 waits on the stack rebuild for `schema.d.ts`.
- **`TablesPanel` became `DataPanel`** (`git mv`). Its menu is one `ListBox`: a "Tables" `ListBoxSection` with a `Header`, then a "Documents" item. Item ids are the hash path (`tables/<name>`, `documents`), so a table called "documents" can't clash with the item.
- **`#data` with no table shows the "choose a table" hint**, not the first table. Opening a sheet nobody asked for would load it for nothing.
- **Admin's sections live in `admin-sections.ts`**: the fast-refresh lint rule forbids a component file exporting constants. Roles, Users and Knowledge show a "Not built yet" placeholder (`admin.placeholder`) until stages 5, 7 and 8 replace it.
- **An old hash is read as its new one on the first render**, then rewritten in the address by an effect. The right tab mounts straight away, rather than the office canvas mounting for one frame.
- **Documents uses a plain `<table class="tcp-table">`**, since its rows are static links. `.tcp-table` and `.tcp-side-menu` joined `base.css`.
- **The rebuild that regenerates `schema.d.ts` builds `tcp-web` from the working tree**, so it can only run while the frontend compiles.

### Changed while implementing stage 3 (2026-10-16)

- **Deletes use `expectAccepted`, not `unwrap`.** Role and knowledge deletes answer 204 with no body, and `unwrap` throws on an empty body by design. Stage 5's delete test caught it; the Sonnet brief hadn't said so (record for next time: name the helper for 204 routes).
- **`queryKeys.mcpServers()` is `['system', 'list']`**, because `query-keys.test.ts` allows only the fixed scope words.
- **`hooks.ts` wraps both scopes in one hook each** (`useKnowledgeList`, `useKnowledgeStatus`, `useKnowledgeSearch`), calling both reads with `enabled` so the hook order stays fixed. The raw role-knowledge reads are no longer re-exported; nothing used them.
- **Company status `select`s its `shared` part**, while `refetchInterval` still reads the raw shape.
- `schema.d.ts` was regenerated here, from the rebuilt testing stack (`--project tcp-testing`, port 3001).

### Changed while implementing stage 5 (2026-10-16)

- **After deleting the last roles, focus goes to the section heading** (`tabIndex={-1}`), not Add role: `RoundIconButton` takes no ref, and the heading is the pattern `DataProtectionPanel` already uses.
- **The planner warning is a second sentence of `ConfirmDialog`'s one `message`**, which takes a string.
- **Selection checkboxes are `CheckboxField slot="selection"` + `CheckboxButton`**, the non-deprecated pair in React Aria 1.20.
- **The announcement test mocks `announce`**, as `ShutdownDialog.test.tsx` does. The virtual screen reader throws (`root.getElementById is not a function`) computing names inside a React Aria `Table`.
- `RoleDialog.tsx` is a placeholder until stage 6.

### Changed while implementing stage 6 (2026-10-16)

- **Sonnet stopped rather than cast**, and was right: the generated types gave `llmConfig` as `Record<string, never>`, and `UpdateRoleDto` didn't allow `null`. Fixed at the source (commit "type llmConfig on role and company responses"): `RoleResponseDto` and `CompanyResponseDto` declare a nullable `LlmConfigDto`, and the update DTO accepts `null`. An e2e test covers clearing.
- **Warnings show as plain text in the dialog, with no live region.** ADR-027 allows one; the success announcement is the spoken part.
- **Tools are a `RadioGroup` per server** (Company default / On / Off), since the app has no styled `Select` yet.
- **A disabled React Aria tab sets `aria-disabled`, not `disabled`**, and the reason is visible text under the tab list rather than a tooltip.
