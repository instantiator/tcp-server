## Context

An admin can drain the system for shutdown only from the CLI, and nobody can see system health anywhere except by curling each service. The web UI has an account menu but no system menu. 000.04 also left four items that wait on this work: supporting services fail a task rather than pause it, an MCP server that's down when tools load is skipped quietly, an agent is stranded `running` when its failure write fails, and cancelling a drain has no surface.

### What the code does today (from exploration)

- **Health.**
  - Every service has a public `GET /health` (Terminus `{status, info, error, details}`, `service` entry first). tcp-server's checks the database, Redis, MinIO and OIDC (`apps/backend/apps/tcp-server/src/health/health.controller.ts`).
  - tcp-agent checks the database and Redis. tcp-mcp-memory checks the database. Storage, interactions and tasks always answer `ok` (`libs/tcp-shared/src/health/static-health.module.ts`), which deliberately avoids circular health checks.
  - nginx proxies only `/api/`, so the browser can't reach `/health`. tcp-agent and the MCP servers aren't published outside the compose network.
  - tcp-server already knows `MCP_*_URL` (the `x-internal-urls` anchor in `docker-compose.yml`, e.g. `http://tcp-mcp-tasks:3013`). It has no tcp-agent URL.
- **Shutdown.**
  - `POST`/`GET`/`DELETE /api/system/shutdown` exist in `api/system.controller.ts`, each with `@AdminOnly()`. The status shape is `ShutdownStatusResponseDto` `{ state: 'idle'|'draining'|'quiesced', forced, agentsRunning }`.
  - The state lives in memory and is pushed over no SSE channel. `GET` is cheap and safe to poll.
  - The API drains, and the host halts (ADR-019). `tcp-cli.sh` runs `docker compose stop` once the drain is quiesced. A web page can drain and cancel, but it can't stop containers.
  - `DELETE` (cancel) is used by nothing (it's on 006.05's unused-route list).
  - The CLI `shutdown` command is `tcp-cli/src/commands/shutdown.ts` with `lib/system/shutdown.action.ts`.
- **Admins.** `TCP_ADMIN_IDENTIFIERS` holds `sub` claims or emails, checked by `MembershipService.isAdmin` (`auth/membership.service.ts:53`). The web client has no admin flag, and ADR-023 chose no `/api/me`.
- **Web shell.**
  - The account menu is a RAC `MenuTrigger` in `src/shell/Header.tsx:104-139`. Dialogs open from `onAccountAction` into `openDialog` state.
  - `MembershipsDialog` is the pattern to copy for a dialog that fetches data (`useQuery` + `LoadingState`/`ErrorState`).
  - The `/health` path is already in `schema.d.ts`.
  - `endpoints.ts` deliberately sets no `refetchInterval` (L16-28).
- **Startup recovery.**
  - `TaskRecoveryService.onModuleInit` (`api/task-recovery.service.ts`) repairs tasks with `Completed`/`Failed` agents, and leaves `Running`/`Paused` agents alone.
  - Nothing reconciles a `running` or `queued` agent with no job.
  - Jobs carry no `jobId`. The pattern for finding an agent's job is `knowledge-reindex.service.ts:204-210` (`queue.getJobs([...])`, then filter on `job.data.agentId`).
  - The fail pair to reuse is `internal.controller.ts:186-205`: `pauseResume.failAgent(agentId, reason)` then `taskFailures.handleAgentFailed(agentId, reason)`.
  - Side finding: `reconcileFinalising` can never run on boot, because the query at L41 selects only `planning` and `in-progress` tasks.
- **Supporting-service pause (the revisit).** Most outages never classify as `service_unavailable`:
  - MCP and MinIO errors return to the model as tool results (LangGraph `ToolNode` `handleToolErrors`).
  - The checkpointer throws raw `pg` errors, which classify as `unexpected`.
  - A database outage can't write a pause at all.
  - Only the message, not the code, reaches tcp-server (`FailDto` has `reason` only).
- **MCP down at tool load.**
  - `McpClientService.loadTools` (`libs/tcp-shared/src/mcp/mcp-client.service.ts:55-81`) warns and skips. A missing URL is also skipped; that one is a deliberate "service disabled".
  - The caller is `tcp-agent/src/agent/run-environment.service.ts:118-126`, and it knows the intended `serverNames()` (L165-184).
  - When a missing server holds the completion tool, the run can't finish, and it ends as `no_output` or narration.

### Decisions agreed with the user (2026-10-09)

- **Health is one admin route.** `GET /api/system/health` (`@AdminOnly`). tcp-server fetches every service's `/health` on the internal network and returns one combined result. Compose healthchecks keep using each service's own `/health`. The web dialog and the CLI's `get-health` both read this route.
- **The client learns admin status from a small route.** `GET /api/system/access` → `{ admin: boolean }` (`@NoCompanyScope`). The System menu shows only for admins. ADR-023 is amended: still no general `/api/me`, but this one boolean is server-side knowledge that no token claim carries.
- **Supporting services still fail a task.** The pause is re-deferred, and the outstanding issue is rewritten with the findings above and a sharper condition.
- **Startup recovery for stranded agents is included.**

### Decisions made in this plan (object at approval if wrong)

- **The combined health result is always HTTP 200** when the route itself works. The body says which services are down. A 503 would make `unwrap` throw away the very body the dialog shows.
- **Each probe has a 5 s timeout** and the probes run in parallel. A service with no configured URL is reported `not_configured`, not `down`.
- **tcp-server's own entry runs its checks in process** (the same `HealthCheckService` checks as `GET /health`), not an HTTP call to itself.
- **New config:** `TCP_AGENT_URL` (Joi optional uri, `empty('')`), added to the `x-internal-urls` anchor as `http://tcp-agent:3001`. The `/health` URL is built from the URL's origin, for tcp-agent and for each `MCP_*_URL`.
- **The web shutdown dialog drains and cancels; it never halts.** Once quiesced, it says the services can now be stopped and names `./scripts/stop-dev.sh`. Force needs a second, explicit confirmation that says in-flight tokens are wasted.
- **Drain status is polled every 2 s, only while the shutdown dialog is open and the state is `draining`.** The interval lives in the `hooks.ts` wrapper (endpoints stay interval-free, as `endpoints.ts` documents). No SSE channel is added.
- **No drain banner for other users.** Non-admins already get the plain refusal "The system is shutting down…" on any new work. A banner goes to outstanding issues.
- **Health is shown as a list, with the raw JSON behind a disclosure.** Each service gets a row: name, then "Up", "Down" or "Not configured", in words, not colour alone. The full JSON (as `deferred-work.md` asked) sits in a `<details>`. A Refresh button re-fetches; nothing polls.
- **An MCP server the run needs that can't be reached at tool load fails the run** with `service_unavailable`, naming the server ("The tasks service (MCP) didn't respond…"). A server with no URL configured is still skipped, as now. The run fails rather than pausing, consistent with the re-deferral above.
- **Startup recovery covers `running` and `queued` agents with no job.** A `queued` agent with no job is stranded the same way, for example when the database was down before the run started. It is failed with a new run-failure code, `interrupted`. This is one entry and one message in `RUN_FAILURE_MESSAGES`, plus a test: "This step stopped unexpectedly, probably because the system restarted, and can't continue. Start the task again."
  - Boot only. A tcp-agent restart while tcp-server stays up is left to BullMQ's stall handling. That ceiling goes in outstanding issues.
- **`reconcileFinalising` stays as it is.** It's out of scope (rule 6), and is recorded in outstanding issues.
- **CLI gains `get-health [--app <name>]` and `cancel-shutdown`.** `--app` filters the combined result to one service by name.

## Design

### A. Backend routes (tcp-server)

- **`api/system-health.service.ts`** (new), `SystemHealthService.check(): Promise<SystemHealthResponse>`:
  - `SystemHealthResponse = { status: 'ok' | 'degraded'; services: ServiceHealth[] }`
  - `ServiceHealth = { name: string; status: 'up' | 'down' | 'not_configured'; detail?: unknown; error?: string }`
  - Services, in this order: `tcp-server`, `tcp-agent`, `tcp-mcp-storage`, `tcp-mcp-memory`, `tcp-mcp-interactions`, `tcp-mcp-tasks`.
  - **tcp-server:** move the check list out of `HealthController.check` into an exported function or provider that both use, so the two can't drift. A Terminus `HealthCheckError` / `ServiceUnavailableException` → `down`, with its response as `detail`.
  - **Others:** `fetch(origin + '/health', { signal: AbortSignal.timeout(5000) })`. A 2xx → `up`, any other status → `down`, and the JSON body (if any) → `detail`. A thrown error → `down` with `error: err.message`.
  - `status` is `ok` only when nothing is `down`.
- **`system.controller.ts`** gains:
  - `GET /api/system/health` (`@AdminOnly()`, 200, `SystemHealthResponseDto`).
  - `GET /api/system/access` (`@NoCompanyScope()`, 200, `{ admin: boolean }` from `MembershipService.isAdmin(getCurrentUserIdentifiers(req))`). Check the guard lets a `@NoCompanyScope` handler sit on an `@AdminOnly` controller; the decorators are per handler today, so this should hold.
- DTOs in `dto/system.dto.ts`, with class-validator/Swagger decorators so `api:generate` types them (memory: Swagger `*.model.ts` suffix; wire ≠ persistence).

### B. Startup recovery for stranded agents (tcp-server)

- In `TaskRecoveryService.onModuleInit`, **before** the task pass:
  1. Load agents with `status IN (running, queued)`.
  2. Collect `agentId`s from `queue.getJobs(['active', 'waiting', 'delayed', 'prioritized', 'waiting-children'])`.
  3. For each agent with no job, make a conditional update from its current status to `Failed`, with `failureReason` set to the `interrupted` message. If it affects 0 rows, skip it (something else moved it).
  4. Then reuse the internal fail pair: `pauseResume.failAgent` (it resolves pending consultations) and `taskFailures.handleAgentFailed`.
  - Log one `warn` per agent recovered.
  - Check `failAgent`'s own write is idempotent with step 3, or let `failAgent` do the write and use its result as the claim. Pick whichever keeps one writer, and say so in the as-built notes.
- Chat agents (no assignment): `handleAgentFailed` must no-op cleanly. Verify, and test it.
- `RunFailureCode` gains `interrupted` in `libs/tcp-shared/src/llm/run-failure.ts`.

### C. MCP server down at tool load (shared + tcp-agent)

- `McpClientService.loadTools` returns `{ tools: McpTool[]; unreachable: string[] }`. `unreachable` holds the servers whose fetch threw, not those with no URL. Update every caller (grep, including `test/integration` and `test/e2e`; memory: grep test dirs on refactor).
- `run-environment.service.ts` exposes `unreachable`. Before the first LLM call, `AgentLoopService.run()` fails the run with `{ code: 'service_unavailable', message: RUN_FAILURE_MESSAGES.service_unavailable({ service: '<Name> service (MCP)' }) }` when `unreachable` is non-empty.
  - Name map: `storage` → "The storage service (MCP)", `memory` → "The memory service (MCP)", `interactions` → "The interactions service (MCP)", `tasks` → "The tasks service (MCP)". It lives next to the message table.
- Chat runs use the same environment. A chat fails the same way, which is acceptable: it says which service is down.

### D. CLI

- `commands/get-health.ts` + `lib/system/health.action.ts`: `GET /api/system/health` → pretty JSON on stdout. `--app <name>` prints only that service's entry, and exits 1 with "No service named <name>. Known: …" if there's none. The exit code is 0 even when degraded (the command worked). The `status` field carries the state.
- `commands/cancel-shutdown.ts` + an action in `lib/system/shutdown.action.ts`: `DELETE /api/system/shutdown` → status JSON.
- Pattern: `commands/dismiss-cap.ts` + `lib/spend/spend.action.ts:19-41` (`resolveToken`, `apiOptions`, `apiRequest`, `runCommand`). Register in `main.ts` next to `registerShutdown`.
- Update the `shutdown` timeout message to name `cancel-shutdown`.

### E. Web: System menu and health dialog

- `Header.tsx`: a second `MenuTrigger` before the account menu, rendered only when `useSystemAccess().data?.admin === true`.
  - Icon button `aria-label={t('header.system.label')}` ("System"), with a `WithTooltip`.
  - Items: `health` ("System health") and `shutdown` ("Shut down…").
  - The `openDialog` union gains `'health' | 'shutdown'`.
  - The account menu and its keyboard test (L93) are unchanged.
- `hooks.ts`:
  - `useSystemAccess` (with `staleTime: Infinity`; the answer is fixed for a session);
  - `useSystemHealth` (no interval);
  - `useShutdownStatus(enabled)` (`refetchInterval: (q) => q.state.data?.state === 'draining' ? 2000 : false`);
  - `useBeginShutdown(force)` and `useCancelShutdown` (invalidate the status key).
  - Raw hooks go in `endpoints.ts`, copying `useSpendOverview` / `useCancelTaskMutation`.
- `components/SystemHealthDialog/` (copy `MembershipsDialog`):
  - a `<ul>` of services, each row "{name}: Up | Down | Not configured", with the error text under a down row;
  - the overall line, "All services are up" or "{n} services are down" (`tCount`);
  - a Refresh button;
  - a `<details><summary>Full report</summary><pre>` of the JSON;
  - `LoadingState`/`ErrorState` with `refusalKey`.
  - `RefusalAction` gains `'health' | 'shutdown'` where needed.

### F. Web: shutdown dialog

- `components/ShutdownDialog/`. The content depends on the state:
  - **idle:** text explaining a graceful shutdown (agents finish their current step and pause, then resume after restart). Buttons: **Shut down gracefully** and **Force shut down…**. The latter shows an inline confirmation: "This stops agents mid-call and wastes the tokens already spent. Force shut down?" with **Force shut down** and **Back**.
  - **draining:** "Shutting down: {n} agents still finishing their current step" (`tCount`), and **Cancel shutdown**.
  - **quiesced:** "Every agent is at rest. You can stop the services now, for example with `./scripts/stop-dev.sh`. Agents stay paused until resumed." and **Cancel shutdown** (it reopens intake).
- State changes are announced politely through the existing announcer, and focus moves to the dialog's status text when the buttons change (as `TaskDialog` does).
- No new notifications. The drain's existing `task_paused` notices stay.

## Verification

- Every stage gate passes, and `./scripts/run-all-tests.sh` finishes green (in `check.sh --comprehensive`).
- By hand on `tcp-dev`, signed in as an admin:
  1. The System menu shows; as a non-admin it doesn't.
  2. System health lists six services as up. `docker compose -p tcp-dev stop tcp-mcp-tasks`, press Refresh: the tasks row reads Down with its error. `./tcp-cli.sh get-health --app tcp-mcp-tasks` agrees.
  3. With tcp-mcp-tasks still stopped, start a task: it fails with "The tasks service (MCP) didn't respond…". Start the service again.
  4. Start a task, open Shut down…, and choose graceful. The dialog counts the agents down to "Every agent is at rest". Cancel shutdown, then resume the task, and it completes.
  5. Start a task, then kill tcp-server and tcp-agent hard (`docker compose kill`) and flush the agent's job (or kill mid-enqueue). Bring the stack up: the agent and task end `failed` with the "stopped unexpectedly" reason, not `running`.
