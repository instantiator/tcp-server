## Context

Agents work out sums, dates and unit conversions in their heads, and small models get them wrong. They also have nowhere structured to keep orders, customers or stock, so records end up as unchecked free text, and a retried run can create the same order twice. These two MCP servers fix both problems:

- `tcp-mcp-utilities`: stateless and deterministic. Decimal arithmetic, date maths and unit conversion.
- `tcp-mcp-records`: typed tables per company, stored as JSONB and checked by ajv. Unique keys make a repeated insert a no-op. Every read and write is audited.

### Decisions agreed with the user (2026-10-10)

- **Records may live in a fully separate database.** `RECORDS_DATABASE_URL`, falling back to `DATABASE_URL`.
- **Records logic is a shared service with direct DB access.** `RecordsService` lives in `libs/tcp-shared/src/records/`. `tcp-mcp-records` uses it now, and tcp-server reuses it in 001.03.
- **Agents create tables with a `create_table` tool.** Agents can't alter or drop tables. Schema changes wait for 001.03 (users) or templates (002.03).
- **`calculate` uses decimal.js 10.6.0** (MIT, no dependencies) and a small recursive-descent parser. It never calls `eval`.

### Decisions made in this plan (object at approval if wrong)

**Records: data model** (entities in `libs/tcp-shared/src/records/`, **not** `models/`, so tcp-server's `data-source.ts` glob doesn't pick them up and `migration:generate` doesn't try to create them in the main DB)

- `record_table`: `id`, `companyId`, `name` (`^[a-z][a-z0-9_]{0,62}$`, unique per company), `purpose`, `schema` jsonb, `primaryKey` jsonb (field names), `uniqueKeys` jsonb (a list of field-name lists), `createdByAgentId` (nullable, no FK), and timestamps.
- `record`: `id`, `tableId` (FK, cascade), `companyId`, `data` jsonb, `version` int, and timestamps.
- `record_key`: `(tableId, keyName, keyValue)` primary key, plus `recordId` (FK, cascade). `keyValue` is the canonical JSON of the key fields' values. **This is what enforces unique keys.** The rows are written in the same transaction as the record, and Postgres rejects a duplicate, even from two concurrent inserts. It needs no per-table DDL.
- **The records server owns its migrations.** It has its own `migrations/` list (registered by hand, like tcp-server's) and `migrationsTableName: 'records_migrations'`, and it runs `migrationsRun: true` on its own connection.
  - The company FK (`ON DELETE CASCADE`) is added **only when `tcp_company` exists in that database** (`to_regclass('public.tcp_company')`). That one migration covers both the shared and separate cases.
- **Company deletion when the DB is separate:** the records server exposes `DELETE /internal/companies/:id/records`, guarded by `InternalApiKeyGuard`. tcp-server calls it after deleting a company when `MCP_RECORDS_URL` is set. In a shared DB the FK has already cascaded, so the call is a harmless no-op. A failure is logged, not fatal (company UUIDs are never reused).
- **Limits:** 50 tables per company, 50 fields per table, 64 KB per record, `query` limit default 50 and max 200.

**Records: tools**

- `describe_server`, `list_tables` (name + purpose), `describe_table`, `create_table`, `insert`, `update`, `delete`, `query`, `aggregate`. `companyId` and `agentId` are injected on every tool, and **every SQL statement filters on `companyId`**. That is the access boundary.
- `create_table(name, purpose, schema, primary_key, unique_keys?)`:
  - The schema must be `type: object` with `properties`. Field names match `^[a-z][a-z0-9_]*$`. Top-level types are limited to string, number, integer and boolean, with `format: date` allowed. Key fields must be required scalars.
  - It must compile under `new Ajv({allErrors:true, strict:true})` + `addFormats`.
- `insert(table, record)` is **idempotent**. When a primary or unique key already exists, it returns `already_exists` with the existing record's id and whether the data matches. It never creates a duplicate and never throws.
- `update(table, id | key, changes)`: a shallow merge. `null` removes a field. The merged record is re-validated, and its key rows are rewritten. It runs in a transaction with `SELECT … FOR UPDATE` and bumps `version`.
- `delete(table, id | key)` is a hard delete. The old value survives in the audit payload.
- `query(table, filters?, sort?, limit?, offset?)`:
  - `filters` are ANDed `{field, op, value}` with `op ∈ eq ne lt lte gt gte contains in`. Fields are checked against the schema's properties, and every value is a bound parameter.
  - Numeric fields compare as `(data->>f)::numeric`, so `"10" > "9"` comes out right.
- `aggregate(table, op ∈ count sum avg min max, field?, group_by?, filters?)` is computed in Postgres `numeric`, so totals are exact, and returned as decimal strings. That is why the agent never adds up records itself.
- **Read-only in `plan` and `qa` modes.** `MODE_TOOLS` gains `records`, and a `RECORDS_WRITE_TOOLS` list (`create_table insert update delete`) is filtered out on the client side for those modes, the same way storage's are. Ponytail: there's no server-side check of the mode. Company scoping is the security boundary, and the mode limit only shapes behaviour. Add a server check if an agent is ever seen getting around it.

**Records: audit** (`AuditClientService.record`; tcp-server fills in task and assignment from `agentId`)

- Writes record `state_change`, `{source:'records', action: create_table|insert|update|delete, table, recordId, before, after}`.
- Reads record `tool_call`, `{source:'records', tool: query|aggregate, table, filters, recordIds}` for `query`, or the group keys for `aggregate`.
- `AuditClientService` is fire-and-forget, so a lost audit POST doesn't roll back the write. That is consistent with every other service. It is written up as an outstanding issue with a condition: act on it if an audit gap is ever found, or when 001.04 (data protection) needs a guaranteed history.

**Records: configuration and operations**

- `RECORDS_DATABASE_URL`: `Joi.string().uri().empty('').optional()`, read as `config.get('RECORDS_DATABASE_URL') || config.getOrThrow('DATABASE_URL')`. The empty-env-var trap is noted in memory.
- Compose: the records service gets `DATABASE_URL` (same as memory), plus `RECORDS_DATABASE_URL: ${RECORDS_DATABASE_URL:-}`. It depends on postgres. Its health check is a DB ping (copy memory's `HealthModule`).
- **A separate DB isn't backed up** by `scripts/backup.sh`, and backup/restore's "newer than checkout" check only reads tcp-server's migrations. Both are documented and logged as outstanding issues. Act on them when someone actually sets `RECORDS_DATABASE_URL`.
- **Every mode gets records**, read-only in plan and qa. Registry `usage`: "keeping and looking up structured business records — orders, customers, stock, income — and totalling them; use instead of free-text files for anything tabular."
- **Postgres only.** JSONB, `FOR UPDATE` and `numeric` casts don't exist on the SQLite unit-test path. Logic tests run in the integration tier against real Postgres, and the tools service gets mocked unit tests.

  - **The FK cascade when the company is deleted** in the shared DB.
