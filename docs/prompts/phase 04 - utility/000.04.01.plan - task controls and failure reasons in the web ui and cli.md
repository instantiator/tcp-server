## Context

Today a task can be started and cancelled, but not paused, edited or (from the web) started once it is ready. When a task can't move, it often says nothing. A provider error is stored as raw SDK text. A refusal shows as a bare status code. One task (LM Studio up, no model loaded) neither started nor failed. Separately, the ui-notes ask for a set of office-view and tray improvements: task numbers in tooltips, a reorganised assignment list, room lighting, a bookshelf count, and completed rooms that stay until closed.

### What the code does today (from exploration)

- **Pause machinery.**
  - `PauseReason` is `user_input | consultation | shutdown | spend_cap | rate_limited` (`libs/tcp-shared/src/models/TcpAgent.model.ts:56`).
  - `resumeAgent` (`tcp-server/src/api/agent-orchestration.service.ts:241`) is the single resume primitive, and it **never checks `pauseReason`**. A conversation reply (`conversation.controller.ts:134`) or a consultation result (`pause-and-resume.service.ts:351`) therefore lifts _any_ pause.
  - If a spend-capped agent is woken this way, the spend gate re-pauses it before `streamEvents`. By then the reply has already been marked delivered, so **the reply is lost**.
- **Safe points.**
  - `checkTerminalStatus` runs before every graph iteration except the first (`libs/tcp-shared/src/llm/run-supervised-graph.ts:154`). A DB status of `Paused` stops the loop cleanly. This is how the drain works, and manual pause reuses it.
  - Gaps: the worker's `admit` (`tcp-agent/src/worker/agent-worker.service.ts:230`) doesn't drop jobs for `Paused` agents, and `run()` sets `Running` unconditionally (`agent-loop.service.ts:156`).
- **Cancel.**
  - Cancel is DB-only, with no abort signal.
  - `failRun` (`tcp-agent/src/agent/run-status.service.ts:228`) doesn't guard `Cancelled`, so an error after a cancel overwrites it with `Failed`.
  - `failRun` has no try/catch. If its write fails, the agent is left in `running` forever.
- **Failures.**
  - `describeRunFailure` (`run-status.service.ts:53`) stores the raw `err.message`.
  - A failed planner already fails the task (`task-failure.service.ts`, "planner failed: …"), so hypothesis 4 is ruled out.
  - `recomputeTaskStatus` (`task-state.service.ts:93`) can fail a task **without** a `failureReason`.
  - `classifyProbeError` (`tcp-server/src/model-check/probe-error.ts:75`) already produces plain, actionable messages for unreachable, timeout, auth_rejected, forbidden, model_not_found and similar errors. Only model-check uses it.
- **LLM client.** `llm-factory.ts` sets no `maxRetries`, so LangChain retries a refused connection **6 times with backoff**. The timeout is 30 min. Hypotheses 1 and 2 are both live.
- **Refusals.**
  - There is no global exception filter, so errors use Nest's default `{ statusCode, message, error }`.
  - The web client maps status to text in each view. `TaskDialog` shows one generic "could not be cancelled" message.
  - The CLI prints `… failed with HTTP 409: <message>` (`tcp-cli/src/lib/core/api.ts:50`).
- **Web.**
  - `TaskDialog` (`apps/frontend/tcp-frontend/src/components/TaskDialog/TaskDialog.tsx`) has only Cancel. Start exists only inside `CreateTaskDialog`.
  - `agentStatusLabel` (`src/api/statuses.ts:105`) names only `rate_limited`. Every other pause reads "Paused".
  - The tray list in ui-notes is `visualisation/isometric/company/ui/TaskDetails.tsx`, not `TaskAssignmentPanel`.
  - Task rooms are client-side and are removed once empty after the task finishes (`rules/taskRoomRules.ts`, `rules/cleanupRules.ts`).
  - The Phaser palette has no notion of lighting (`scene/palette.ts`).
- **CLI.**
  - One file per command (`tcp-cli/src/commands/*.ts`), with actions in `lib/tasks/task.action.ts` and `lib/spend/spend.action.ts`.
  - `get-task` prints JSON. Its docs say `{ task, assignments }`, but the actual response is flat.
  - The TUI has `s` (start) and `c` (cancel) only.

### Decisions agreed with the user (2026-10-09)

- **Closed rooms are a server flag.** Add `TcpTask.visualisationClosedAt`, set by a "Close room" action. It is named for the view, not the room metaphor, because other views may come later. A finished task's room stays until then, survives a reload, and is the same for every viewer. The migration closes the rooms of tasks that are already finished.
- **Toasts are short-lived and click through** (from plan review). Every notification and every new-enquiry notice shows a small toast that can be dismissed.
  - It hides after about 8 s. The timer pauses while the toast is hovered or focused.
  - Clicking it opens that notification's (or enquiry's) own row.
  - The durable list row is what makes the timer acceptable under ADR-026's 2.2.3. ADR-026 is amended to say so.
- **Task failures and shutdown pauses raise notifications.** Notifications gain a nullable `companyId` and `taskId`, plus the kinds `task_failed` and `task_paused`.
- **Resume exempts only if a cap is reached.** `resumeTask` uses `exemptIfCapped`, as Start does, instead of always setting `spendCapExempt`.
- **A supporting service that's down fails the task**, with a plain reason. Revisit once 000.05's health signal exists (outstanding issue).
- **One commit per stage.**

### Decisions made in this plan (object at approval if wrong)

- **A manual pause is a soft stop.** No in-flight LLM call is killed. Running agents stop at their next `checkTerminalStatus` boundary, and the UI says so ("Pausing — agents stop after their current step").
- **The pause is recorded on the task**, as `pausedAt` and `pausedBy`, not only on its agents. This is the one place that blocks every automatic resume. It also covers agents created while the task is paused, and it records who paused it. No new task status is added.
- **Automatic resumes only lift waits they own.** Reply, consultation and QA resumes lift only `user_input`, `consultation` and QA hand-off (null reason) pauses, and do nothing while the task is manually paused. Their replies stay undelivered, and the explicit resume applies them. This also fixes the lost-reply bug for spend-capped agents.
- **A failed task has no "retry".** The message says what to fix. A retry endpoint is new scope, so it goes in outstanding issues.
- **The TUI gets no new keys.** 002.07 retires it.
- **Failure messages are server-side English text in the existing `failureReason` column**, shown as is, like today. No code column is added. The extendable set lives in one typed table, described below.

## Design

### A. Manual pause and resume (backend)

- **Migration** (one file, registered by hand in `migrations-list.ts`; memory: manual migration registration):
  - add `tcp_task.pausedAt` (`@Column({ nullable: true }) pausedAt?: Date`, with no explicit type; memory: cross-DB dates);
  - add `pausedBy` (varchar, nullable);
  - add `visualisationClosedAt` (a nullable date, used in section E);
  - backfill `visualisationClosedAt = now()` for tasks that are `succeeded`, `failed` or `cancelled`.
- **`PauseReason`** gains `'manual'`.
- **`POST /api/task/:id/pause`** (202, `@CompanyScope`, returns the task):
  - 404 if the task doesn't exist.
  - 409 `"This task isn't running, so it can't be paused."` unless the status is `planning`, `in-progress` or `finalising` and `pausedAt` is null.
  - It sets `pausedAt` and `pausedBy` in one conditional update, using the same actor label the audit `actor` field uses.
  - Then it sets every agent of the task in `idle`, `queued` or `running` to `paused` / `manual` / `pausedAt` (also conditional).
  - It publishes a task `state_change` and agent `state_change` events. `TaskChangeSummary` gains `pausedAt`, `pausedBy` and `visualisationClosedAt`.
- **Worker:**
  - `admit` drops a job whose agent is `Paused` (add it to the skip set alongside `FINISHED`).
  - `run()` moves to `Running` only from `idle` or `queued` (a conditional update). If that update fails, the run returns silently.
- **New agents while paused:** at the single enqueue point in `AgentOrchestrationService` (start dispatch), if the agent's task has `pausedAt`, write the agent `paused` / `manual` instead of enqueueing.
- **`resumeAgent(agentId, replyContent?, { explicit = false } = {})`:**
  - When the call is not explicit:
    - if the task has `pausedAt`, throw `ConflictException('This task is paused. Resume the task to continue.')`. Existing callers already log and swallow.
    - if `pauseReason` is not one of `user_input`, `consultation` or null, return without claiming the pause or marking replies delivered.
  - `POST /api/agent/resume/:id` maps the 409 through.
- **Sweeps:** the rate-limit and spend sweep queries add `assignment.task.pausedAt IS NULL`, so they don't spam the log.
- **`resumeTask`:**
  1. `assertAccepting`.
  2. 404 if the task doesn't exist.
  3. Clear `pausedAt` and `pausedBy`.
  4. `exemptIfCapped` (replaces the unconditional exemption).
  5. Resume agents with `pauseReason IN (EXPLICITLY_RESUMABLE ∪ manual, user_input, consultation)`, using `explicit: true`. `resumeAgent`'s outstanding-count check keeps agents that are still waiting on a reply paused.
  - It still returns `{ resumed }`.
  - `EXPLICITLY_RESUMABLE` gains `manual`.
  - `resumeCompany` keeps its behaviour but skips manually paused tasks.
- **`pauseResumePrompt()`** gains a `manual` branch with `MANUAL_RESUME_PROMPT` ("A user paused you and has now resumed you. Continue where you left off."). It applies only when an `llm_response` row exists, as for `spend_cap`. Otherwise the run restarts, which is correct for an agent that never started.
- **`failRun`** also no-ops when the agent is `Cancelled`, or `Paused` with `manual`.

### B. Failure reasons (backend)

- **Move `classifyProbeError` and `PROBE_ERROR_CODES`** to `libs/tcp-shared/src/llm/provider-error.ts`, and point model-check's imports at it. The messages stay the same.
- **`libs/tcp-shared/src/tasks/run-failure.ts` holds the extendable set:**
  - `RunFailureCode` = the provider codes plus `no_llm_config`, `timed_out`, `iteration_limit`, `context_too_long`, `tools_unsupported`, `required_tools_missing`, `no_output`, `no_plan`, `repeating_refused_call`, `service_unavailable` and `unexpected`.
  - `RUN_FAILURE_MESSAGES: Record<RunFailureCode, (ctx) => string>`. Each message says what went wrong and what to do.
  - `describeRunFailure(err, signal, config) → { code, message }`. It replaces the raw-message version and is the only classifier. Adding a reason means adding one code, one message and one test.
  - **`service_unavailable`**: recognise Redis/BullMQ connection errors, MCP client connect errors, S3/MinIO errors and embedding-call failures by error class or name. Stage 4 lists the exact classes found. The message names the service.
- **Callers:**
  - `failRun` records the message.
  - `task-failure.service.ts` prefixes it plainly: "The planner stopped: …", "Step 3 (Chicken assistant) stopped: …", "The review stopped: …", "Finishing stopped: …".
  - `recomputeTaskStatus` sets `failureReason` from the failed assignment's reason.
- **Database errors** (the prompt's question):
  - wrap `failRun` in a try/catch that logs at `error` with the agent id, task id and reason;
  - `internal.controller` fail has a try/catch that logs the same;
  - an API-initiated error reaches the caller as a 500, shown as "Something went wrong on the server…";
  - a stuck `running` agent after a failed write goes to outstanding issues, with its condition.
- **Stage 1's fixes for the stuck task** (see stage 1, as found):
  - **Stop a repeating refused call.** If an agent makes the same tool call, with identical input, and it is refused with the same message 3 times in a row, fail the run with a new code, `repeating_refused_call`. The message reads: "The {role} kept sending the same {tool} call, and it was refused each time: {first line of the refusal}. Try a more capable model for this role, or simplify the request." The check goes where the loop sees tool results (`agent-loop.service.ts` / `supervised-turn.service.ts`). A changed input resets the count.
  - **Readiness check, for `local` and `custom` providers only:** `GET {baseUrl}/models` with a 10 s timeout, before the run's first LLM call.
    - No answer → `unreachable`.
    - The model is missing from the list → `model_not_found`. LM Studio otherwise **answers with whichever model is loaded**, so a wrong model name runs silently on another model.
    - LM Studio lists downloaded models whether or not they are loaded, so JIT loading still works.
  - `maxRetries` stays at LangChain's default. A refused connection fails in about a minute (backoff of 1+2+…+32 s), and the readiness check catches it within 10 s anyway.
  - The 30 min generation timeout stays.
- **Planner validation errors that list nothing** (added 2026-10-09, from a real run). `create_plan` refused a `completed-file` material with "Valid values are: ." The list of earlier-step outputs (`plan-validation.service.ts` `danglingPriorOutputs`) was empty, because no earlier assignment promised a `file` in its `expected` list. The planner was never told that rule.
  - `InvalidEnumValue` gains an optional `hint`. `buildEnumValidationError` (`libs/tcp-shared/src/validation/enum-validation.ts`):
    - with an empty `validValues`, writes `There are no valid values yet.` instead of a blank list;
    - always appends the hint when one is given.
  - `danglingPriorOutputs` passes the hint: "A `completed-file` must name a file an earlier assignment promises. Add `{ type: 'file', value: '<filename>' }` to that earlier assignment's `expected` list, and use the same filename here."
  - The `create_plan` material `type` description in `tcp-mcp-tasks/src/mcp/tasks-tools.service.ts` says the same: `completed-file` is an earlier step's output, and the filename must appear as a `file` in that step's `expected`.

### C. Wait reasons and labels (shared, web, CLI)

- **`libs/tcp-shared/src/tasks/task-waiting.ts`** (runtime-free, exported from `client.ts`): `taskWaiting(task, agents) → { kind: 'manual' | PauseReason | 'queued'; pausedBy?; resumeAfter? } | null`.
  - Precedence: task `pausedAt` (→ `manual`), then `rate_limited` (earliest `resumeAfter`), `spend_cap`, `shutdown`, `user_input`, `consultation`, then `queued`.
  - `GET /api/task/:id` adds `waiting` (CLI `get-task` shows it).
  - The web client computes it from live data.
- **Text maps typed as `Record<…>`,** so a new reason fails typecheck until it has text:
  - web: `agent.pause.<reason>` and `task.waiting.<kind>` keys in `strings.ts`;
  - shared transcript: `PAUSE_REASON_TEXT: Record<PauseReason, string>`, used by `stateChangeText`.
  - Example text: spend cap → "Spend cap reached — resume to continue, or wait for the cap to reset"; shutdown → "Paused by a shutdown — resume to continue"; manual → "Paused by {name} — resume to continue"; user_input → "Waiting for your reply"; consultation → "Waiting for a colleague's answer"; queued → "Waiting for the model".

### D. Refusals in plain words

- **Web:** `refusalKey(err: ApiError, action: 'start' | 'pause' | 'resume' | 'cancel' | 'edit' | 'closeVisualisation')` in `src/api/errors.ts` maps:
  - 0 → offline;
  - 403 → "You're not a member of this company";
  - 404 → "This task no longer exists";
  - 409 → `refusal.<action>.wrongState`;
  - 422 → `refusal.start.noPlanner`;
  - 503 → shutting down;
  - ≥500 → server error.
  - 401 is already a sign-in redirect.
  - It is used by every `TaskDialog` action through `ErrorState`.
- **CLI:** `apiRequest` throws `Error: <message> (HTTP 409)`. Validation arrays are joined with "; ". A 401 adds a hint to sign in again, using the command named in `docs/tcp-cli.md`.

### E. Office view and tray (ui-notes)

- **Tooltips:**
  - Whiteboard: "Task {shortcode}: ({step}/{steps})", then the request.
  - Task room: add the shortened request as a third line.
  - Bookshelf title: "Bookshelf: {count}", where the count is the succeeded tasks (`ArchiveDetails`' set).
- **Tray assignment list (`TaskDetails.tsx`):**
  - Number assignments chronologically (`createdAt`, then `id`) as 001, 002 …, and keep each number in its section.
  - Sections: "In progress" (ready, in-progress, in-qa) and "Completed" (succeeded, failed, cancelled), each in chronological order.
  - Row: "{n}. {role} — {mode} ⓘ — {status}". The ⓘ is a focusable info trigger using the `Focusable` + `TooltipTrigger` pattern from `SpendBar.tsx`. Its tooltip reads "Task {shortcode}, Assignment {n}", followed by the assignment's `prompt`.
- **Completed rooms:**
  - `openTaskRooms` keeps a room for any task with `visualisationClosedAt == null`, finished or not.
  - `closeTaskRooms` closes on `visualisationClosedAt`, not on finishing. Avatars still leave when the task finishes, and a succeeded task's carrier still walks the outputs to the archive.
  - `POST /api/task/:id/close-visualisation` (202, `@CompanyScope`) returns 409 unless the task is finished.
  - The tray adds:
    - a **Close room** button when the task is finished;
    - an **Outputs** link (`taskOutputsUrl`) when it succeeded.
  - `DetailsPicker` lists tasks with open rooms, so a finished room stays keyboard-reachable.
  - A succeeded task draws a small tick above its whiteboard. Its hover zone gives the tooltip "Task completed".
- **Lighting:**
  - Pure `roomLighting(world, snapshot) → { litRooms: Set<roomId>; litBoards: Set<taskId> }` in `rules/`.
  - A room is lit when an avatar inside its bounds belongs to a `running` agent. The corridor is always lit.
  - A whiteboard is lit when its task is `planning`, `in-progress` or `finalising` and not paused.
  - The draw functions take a `lit` flag. Unlit rooms use `dim(colour)`, which mixes toward a dark tone, in `palette.ts`.
  - The scene redraws only when the lit sets change. The switch is instant, with no fade (reduced motion).

### G. Notifications and toasts

- **Backend:**
  - A migration adds nullable `notification.companyId` and `taskId` (uuid).
  - `NotificationKind` gains `task_failed` and `task_paused`.
  - `TaskStateService.failTask` (the only writer of `failureReason`) creates `task_failed`: severity `error`, message `"Task {shortcode} failed: {reason}"`, dedupeKey `task_failed:{taskId}`.
  - `SystemDrainService.pauseRunningAgents` creates one `task_paused` per affected task: severity `warning`, message `"Task {shortcode} was paused by a shutdown. Resume it to continue."`, dedupeKey `task_paused:shutdown:{taskId}:{pausedAt ISO}`.
  - No notification for spend-cap pauses, since `spend_reached` already covers them. None for manual pauses, since the user did it.
  - `GET` notifications takes an optional `companyId` and returns app-wide rows (null `companyId`) plus that company's rows. Dismissal stays global.
- **Web:**
  - **`components/Notification/Notification.tsx`:**
    - `durableHref` stays required, and now points at the item's own row.
    - The message becomes the link, so clicking the toast goes there. Dismiss stays as a button.
    - New `AUTO_HIDE_MS = 8000`. The timer pauses while the toast is hovered or has focus within, and restarts on leave. Calling `onDismiss` when it ends is the only timer. Rewrite the "nothing here dismisses itself" comment to give the new rule: a durable row is required, and that is what allows the timer.
    - Smaller styling in `Notification.css`, with no animation under `prefers-reduced-motion`.
  - **Row deep links:**
    - `NewNotificationToasts` → `/company/{id}?notification={nid}#notifications`.
    - `NewEnquiryNotifications` → `?enquiry={eid}#enquiries`.
    - `NotificationsList` and `EnquiriesList` read the query param once the data has loaded. They scroll the matching row into view, focus it (`tabIndex={-1}`) and mark it `aria-current="true"`. A hash change moves no focus by itself (ADR-027), so the lists do it.
  - **Task notification rows** carry an **Open task {shortcode}** link that opens the task dialog.
  - `useLiveNotifications` passes the company id.

### - [x] 1. Reproduce the stuck task — Opus

- **Brief:** with LM Studio up and no model loaded, start a task on `tcp-dev` and find out why it neither starts nor fails.
- **As found (2026-10-09):**
  - **No model loaded isn't a hang here.** JIT loading is on, so the first request loaded gemma (about 23 s) and ran. Hypothesis 1 is half right: the first call's wait includes the load. JIT-off couldn't be tested (it isn't scriptable); the readiness check covers it.
  - **A wrong model name runs silently on the loaded model.** A request for `no-such-model` got HTTP 200 from `google/gemma-4-e4b`.
  - **A closed port fails at once** (`ECONNREFUSED`). LangChain's backoff bounds it to about a minute, so hypothesis 2 is a delay, not a hang.
  - **Hypothesis 3** (queued behind a stuck call) wasn't seen.
  - **The real "neither started nor failed": a planner looping on a refused plan.** gemma 4B promised `cats_drink_info` as `text` in one step's `expected`, then used it as a `completed-file` in a later step. `create_plan` refused it with "Valid values are: ." (an empty list), and the planner resent the identical plan 5 times, about 2 minutes per call, before the user stopped it. The task sat in `planning` with nothing on screen to explain it. At the 40-iteration limit it would have run for over an hour.
  - Cancelling it showed the soft stop's lag: the in-flight call (about 2 minutes) finished before the loop noticed.
- **Fixed in stage 1a:** the validation message. **Designed for stage 3:** the repeating-call stop and the readiness check (Design B).
- **For stage 10:** stub-llm needs no "model not found" mode. That scenario becomes "a model the provider doesn't list fails with `model_not_found` before any call", using stub-llm's `/models`.
