## Context

`main.tsx` creates `new QueryClient()` with no options. TanStack's default is 3 retries with back-off, for any error, including 403, 404 and 409, which give the same answer every time they're asked. A 404 for a deleted table was retried for about 7 s, so "Delete table" seemed to hang. 002.00 patched that one case with `useDropAndForget` in `src/api/hooks.ts:1244`. This plan adds one policy that retries only the failures where trying again can help, and removes the patch.

### What exploration found

- **`ApiError`** (`src/api/errors.ts`) carries `status`, with `0` for a request that never landed. Every request path throws it: `unwrap`, `expectAccepted` and `send` in `src/api/client.ts`.
- **tcp-server never sends 429 or `Retry-After`.** Only `tcp-stub-llm` does. A grep of `apps` and `libs` found no throttler.
- **There are two app `QueryClient`s:**
  - `src/main.tsx:18`;
  - `src/test-support/render-app.tsx:33`.

  Unit tests that build their own clients (`retry: false`) are left alone.

- **Polling:**
  - `useShutdownStatus` already sets `retry: false` and drives itself with `refetchInterval` while the server is down. The new policy doesn't affect it.
  - `useKnowledgeStatus` uses the default. Under the new policy a poll that fails with a 5xx retries, and then the next interval tick polls again. That is fine.
- **Per-hook `retry: false` overrides stay as they are:**
  - `endpoints.ts:436`;
  - `memory-changes.ts:68`;
  - `record-changes.ts:90` and `:106`;
  - `hooks.ts:188`, `:208`.

  Each one is deliberate.

- **Announcements:** `ErrorState` (`src/components/ErrorState/ErrorState.tsx`) announces once per message. It mounts only when `isError` is true, which TanStack sets after the last retry. So a final failure is announced once, not once per attempt. While retrying, the query stays pending and `LoadingState` keeps showing. The policy shortens that wait for 4xx answers.

### Decisions

| Failure                 | Retry?                       | Why                                                                                |
| ----------------------- | ---------------------------- | ---------------------------------------------------------------------------------- |
| `0`, 502, 503, 504      | Up to 3 times, with back-off | Transient                                                                          |
| 429                     | Up to 3 times, with back-off | No `Retry-After` support yet: the server never sends 429                           |
| 500                     | Once                         | Usually a bug, sometimes a transient fault                                         |
| 401 and every other 4xx | No                           | 401 already redirects to sign-in; the other 4xx answers don't change               |
| Not an `ApiError`       | No                           | A bug in our own code (a thrown `TypeError` or a parse failure): retrying hides it |

- **Back-off:** TanStack's default `retryDelay` (1 s, 2 s, 4 s, capped at 30 s). There is no custom delay, so nothing sets `retryDelay`.
- **Mutations:** left at TanStack's default of 0. There is no opt-in hook: no mutation needs one yet.
- **The event stream** (`src/events/connect.ts`): left out. It has its own reconnect policy (ADR-025).

### - [ ] Stage 1 — The policy (Opus)

- **In `src/api/client.ts`, beside `unwrap`:**

  ```ts
  /** Which failed queries are worth asking again (002.09); TanStack's default back-off spaces them. */
  export const retryQuery = (failureCount: number, error: unknown): boolean => {
    if (!(error instanceof ApiError)) return false;
    if (TRANSIENT.has(error.status)) return failureCount < 3;
    return error.status === 500 && failureCount < 1;
  };
  ```

  `TRANSIENT` is the set `{0, 429, 502, 503, 504}`, with a `ponytail:` comment saying that 429 ignores `Retry-After` until the server sends one.

- **`main.tsx` and `render-app.tsx`:** `new QueryClient({ defaultOptions: { queries: { retry: retryQuery } } })`. Also fix `main.tsx`'s stale "Nothing queries yet" comment.
- **Tests:** `src/api/retry.test.ts`.
  - **The policy, case by case:**
    - 0, 429, 502, 503 and 504 retry while `failureCount` is 0–2 and stop at 3;
    - 500 retries at 0 and stops at 1;
    - 400, 401, 403, 404, 409, 410 and 422 never retry;
    - a plain `Error` never retries.
  - **Through a real `QueryClient` with the same defaults, using fake timers:**
    - a 404 query settles in error after one fetch;
    - a 503 query is fetched 4 times, then errors;
    - a 503 followed by a 200 resolves on the second fetch.
- **Then run the whole frontend unit suite.** `render-app` tests that relied on hidden retries would surface now. Fix them in the test, never in the policy.
- **Gate:** `check.sh --fast`, and `npm --prefix apps/frontend/tcp-frontend test`.
