> ## Secrets
>
> **Today:** LLM API keys are stored on `LlmConfig` in the DB and masked in API
> responses (`mask-secrets.interceptor.ts`). There is no general store, and no
> encryption at rest.
>
> **Recommend:** a per-company `Secret` entity, encrypted at rest with a key from
> the environment. MCP service configs refer to secrets by name. Values are
> injected into the outbound MCP connection and never appear in prompts, logs,
> audit events or API responses. Rotation and deletion should be possible from
> the web UI. Security work: Opus.

## Templates (from 002.03)

[002.03](002.03.01.plan%20-%20company%20template%20format%20v1%20with%20import%20and%20export.md) built company templates. They never carry secrets, and that rule stays.

- Today the import preview (`CompanyTemplatePreviewDto`) has `neededKeys`: the LLM providers in the template that need a key.
- Extend it into a "you'll need" list of named secrets, for services as well as providers. Each entry gives the secret's name and what it is for. Never a value.
- Show the list in the import dialog (it replaces the "You'll need a key for <provider>" notice) and in the CLI's `import-company --preview`. Mark which secrets the company already has.
- Exports must keep dropping every secret value. Check that a service's auth reference (the secret's name) survives export, and the value never does.
- Template services come with 004.00 and format v2 (see 005.04). Until then this list only covers LLM providers. The format is documented in `templates/blank/README.md`, which travels inside every blank download. Update it in the same change, so it never lags behind the code.
