## Context

Parity row 14: nobody can see what agents remember. The prompt asks for view, edit and delete of a role's episodic memories (web UI + CLI), memory for every agent, nudges so agents actually use `remember`, and a way for relevant memories to surface.

### What exploration found

- **Memories live in `episodic_memory`** (`libs/tcp-shared/src/models/EpisodicMemory.model.ts`): `id, companyId, roleId, agentId?, content, tags?, createdAt`, plus an unmapped `embedding vector` column. There's no `updatedAt` or `version`. Only the memory MCP server reads or writes the table, through raw SQL (`apps/backend/apps/tcp-mcp-memory/src/mcp/memory-tools.service.ts`).
- **Tools:** `remember` (episodic only), `recall` (episodic and knowledge together, one SQL UNION, fixed 0.5 cut-off), and `search_knowledge`. Descriptions are in `tools.jsonc`, and replies in `prompts.jsonc`.
- **Bug: the model has to supply `roleId`.** `McpToolContext` (`libs/tcp-shared/src/mcp/mcp-client.service.ts:27-30`) injects only `agentId` and `companyId`. The default system prompt never states the role id, so an agent can't know it, and nothing stops it passing another role's id. Episodic recall also filters by `roleId` only, with no `companyId` check (`memory-tools.service.ts:255`).
- **Bug: `remember` lies when there's no embedding config.** It returns "memory stored without embedding" and stores nothing (`memory-tools.service.ts:301-302`).
- **The knowledge gate** is in `run-environment.service.ts:190` (tcp-agent worker runs only). Chat turns (`chat-turn-environment.service.ts:55-62`) already get memory. ADR-006 says memory is "provided to all agents… not optional", so the gate contradicts the ADR.
- **No prompt asks for `remember`.** The mode prompts (`libs/tcp-shared/src/prompts/mode-prompts.ts`) mention memory only in chat (:87-90) and consultee (:110).
- **Part 6 of the initial prompt is reserved:** `initial-state.service.ts:96` reads "episodic memory — recalled … relevant to this task (not yet implemented)". `buildRagMessage` beside it is the pattern to copy. Chat has the same RAG step in `chat-turn-prompt.service.ts:73,120`.
- **The server can embed:** `EmbeddingService.embedTexts` from `@tcp/shared` (already used by tcp-server's `rag-index.service.ts`), with config from `resolveEmbeddingConfig(company, resolveEnvEmbeddingConfig(config))`.
- **The "changed, reload" pattern** is records' (001.05):
  - `OutOfDateNotice` (`src/components/RecordSheet/OutOfDateNotice.tsx`, CSS in `TableView.css:38-52`), driven by `record-changes.ts`, which debounces, fetches a `latest` copy, and compares it with `compareRows` (by `id` and `version`).
  - The event comes from `toRecordSignal` in `audit-event-publisher.service.ts:47-63`.
  - The memory server already has `AuditClientService`, so it can publish the same way the records server does (`records-tools.service.ts:539-551`).
- **Role dialog:** `RoleDialog.tsx` has Details and Knowledge tabs. `KnowledgePanel.tsx` (a `tcp-table`, a trash button per row, `ConfirmDialog`, focus to the next row after a delete) is the panel to copy.
- **CLI:** flat verbs, e.g. `commands/list-knowledge.ts` and `lib/docs/list-knowledge.action.ts`, with `resolveRoleId`, `apiRequest` and `confirmAction`.
- **Outstanding issues this resolves:** the tool-footprint "counts memory for a knowledge-less role" item (`outstanding-issues.md:629`; its first bullet is already stale, since `RoleDialog` edits the toggles). It also partly helps "data protection reaches record tables only": memories can now be deleted one by one.

### Decisions agreed with you (2026-10-20)

| Decision               | Choice                                                                                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| How memories surface   | Inject the best 3 above the role's RAG threshold: at the start of an assignment (prompt part 6), and on each chat turn. No count nudge. |
| Users can add memories | Yes: an Add button, a POST route and a CLI verb (ADR-006's "user teaching").                                                            |
| Duplicates             | `remember` refuses a near-duplicate (≥ `DUPLICATE_SIMILARITY = 0.92`, tunable), and quotes the existing memory and its id.              |

### Where this plan challenges the prompt

1. **The parity row says "read-only"; the prompt says view, edit and delete.** The prompt wins. Edit and delete also help data protection.
2. **"Memory for all agents" needs a qualifier.** Without an embedding model, `remember` and `recall` can't work at all. So memory is offered whenever the company resolves an embedding config (company or env), not only when it has knowledge. That's every real deployment. A role can still switch it off with `mcpServerToggles: { memory: false }`.
3. **The duplicate guard would block corrections.** "Made a mistake and learned the correction" produces a memory very close to the wrong one. So `remember` gains an optional `replaces: <id>` (same role only). The guard's refusal says: "If your new memory corrects this one, call `remember` again with `replaces` set to its id." This is the one way an agent edits a memory.
4. **Fix the `roleId` bug first.** Memory for all agents is pointless if agents can't name their own role, and unsafe if they can name someone else's. `roleId` becomes injected context, like `companyId`.
5. **Surfacing "when the agent has reasoned about something" mid-run is deferred.** That would cost an embedding call per iteration plus a heuristic for when to search. Injecting at the start and on each chat turn covers the request and the user's message, which is where most relevance is. Deferred with a condition.
6. **Not a count nudge.** It needs the same search as injection, plus an extra tool round-trip. That's the costliest thing for the slow local models this project runs.

### Prompt wording (decided here; stage 3 types it in)

Each section goes in `MODE_PROMPTS` with `needs: 'memory'`, so it disappears when memory is switched off.

- **implement, plan, qa, finalise** (the same section in each, as a shared const):

  > Before you finish, ask yourself: did you learn anything that would help your role do this kind of work better next time — a fact about the company, a user's preference, or a mistake and its fix? If so, store each one with the `remember` tool as a single short sentence that makes sense on its own. Don't store task progress or anything already in your instructions.

  Why this wording: "before you finish" puts the decision at the point where the agent knows what it learned. The three examples name the categories worth keeping. The last sentence stops progress notes from flooding the table.

- **chat** (replaces the current memory sentence):
  > Draw on your knowledge base and memories rather than guessing. When the user tells you something new that matters to your role — a fact, a preference, or a correction — store it straight away with the `remember` tool as a single short sentence that makes sense on its own.
- **consultee:** `Draw on your knowledge base and memories.` No remember nudge, because a consultation is a short answer.
- **Injected block** (`prompts.jsonc`, `memory_intro`), followed by one bullet per memory: `- {content} (memory {id})`:
  > Things your role remembered from earlier work that may be relevant. Prefer these over guessing; if one turns out to be wrong, store the correction with `remember` and `replaces`.
- **`remember` description** (`tools.jsonc`):
  > Store one short fact for future runs of your role: something learned, a user's preference, or a correction. Write a single sentence that makes sense on its own. Set `replaces` to a memory's id to correct it.

### Choices made in the design (say if you disagree)

1. **Memories get `version` (int, default 1) and `updatedAt`.** That reuses `compareRows` for the out-of-date notice (generalised to `{ id; version }`). One migration, registered by hand in `apps/tcp-server/src/app.module.ts` (the CLI's glob hides a missing entry).
2. **One write path per process.** The memory server (`remember`) and tcp-server (`MemoryService`) both embed, write, and audit `StateChange { source: 'memory', action, roleId, memoryId }`. A new `toMemorySignal` turns that into `{ entity: 'memory', action, roleId }` on the company channel. The signal carries no content.
3. **The list is capped:** the newest 500, with `truncated` (the same shape as 001.05's view cap). Newest first. No search or paging. Deferred.
4. **Content is capped at `MAX_MEMORY_LENGTH = 2000` characters**, in the tool schema, the DTO and the UI's text field. Tags: at most 10, each at most 40 characters.
5. **The table** has these columns: Memory (the content, `th scope="row"`), Tags, Source ("Agent" when `agentId` is set, "Person" otherwise), Updated, and actions (Edit and Delete icon buttons). The empty state is `EmptyState` "This role has no memories yet". Add and Edit open one `MemoryDialog` (a text area and a tags field). Delete uses `ConfirmDialog`.
6. **Without an embedding model**, the routes return 422 "This company has no embedding model, so memories can't be saved or searched." The tab shows that message instead of the Add button. Listing and deleting still work.
7. **Any member can add, edit and delete**, as with knowledge (002.00). Permissions come with 003.01.
8. **No office-tray link.** The role dialog has no deep link, and it isn't needed for parity.

### Security notes

- Every route sits under `api/role/:roleId/memory`, with `@CompanyScope({ from: 'param', key: 'roleId', via: 'role' })`, so `route-audit.spec.ts` covers it. Every query filters on both `roleId` and `id`, so a memory id from another role gives 404.
- `roleId` is removed from the model-visible schemas of `recall`, `remember` and `search_knowledge`, and injected server-side. Episodic SQL also filters on `companyId`. `replaces` must name a memory of the same role and company, or the tool refuses.
- **Memories are persistent prompt content.** Injected memories are agent- or member-written, so the trust level is the same as the role prompt, which members can already edit. The risk grows when agents read untrusted inbound content (email in 004.02): a poisoned message could plant a memory that's replayed on every run. Stage 8 adds this to the 003.04 prompt.
- No secrets are involved. Embedding API keys stay where they are.
