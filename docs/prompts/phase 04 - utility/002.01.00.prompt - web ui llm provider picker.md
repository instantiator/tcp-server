Please prepare a picker that allows the user to select from pre-existing LLM provider templates, and to enter their own details.

Challenge any parts of this plan to improve the user experience.

Transfer the detail of any parts of this plan into upcoming plans from phase 04 that cover their aspect of this. For instance, 002.02.00.prompt covers creating and editing a company.

This component can either exist in a dialog of its own, or be embedded in other component views.

This component should support modification of:

- Application level default LLM provider
- Company level default LLM provider
- Role level LLM provider

It should support all the templated LLM providers, as used by the setup wizard.

It should offer the known models at each LLM provider, and common / popular models that will work with the local system for local providers (eg. LM Studio, etc.)

It should permit modification of all details.

It should allow selection of a "(none)" option - so that the user can remove LLM configuration from a role/company/app default.

It should handle the error case if a role (or roles) are left without any LLM provision.

It should identify localhost / 127.0.0.1 in the settings, and offer to replace with the docker equivalent with a confirmation dialog, on submit.

It should also manage the configuration of application level embedding model.

It should offer information about recommended context window size, embedding size, and choice of a good local model (for both).

Wire this component in to the various parts of the UI:

- Role editing dialog (opened through the company admin tab)
- Company default LLM provider (a menu / main view in company admin)

For application-level defaults, _for now_ these are managed through config files - so it's ok to leave them as such. We'll need a way to override config with application level settings in future. Add this as a known unresolved piece of work to a future prompt or track it in the usual place.

## Notes from 002.00

002.00 built the role dialog and the Admin tab this picker plugs into. What the picker needs to know:

- **Where it goes.** The role dialog (`apps/frontend/tcp-frontend/src/pages/CompanyPage/admin/RoleDialog.tsx`) has a read-only "Language model" section on its Details tab. It says whether the role uses its own model, the company's, or the app default, and offers "Use the company's model". The picker replaces that section. The company default needs a new Admin menu section (`pages/CompanyPage/admin-sections.ts` lists the sections; `AdminPanel.tsx` renders them).
- **Never send the API key back.** Every response masks `apiKey` as `***` (`MaskSecretsInterceptor`). If a form sends that value back, it overwrites the real key. Send `apiKey` only when the user types a new one. The server keeps the existing key when the provider and base URL are unchanged, and drops it when either changes (`mergeLlmConfig` in `apps/backend/apps/tcp-server/src/db/llm-destination-policy.ts`). So switching provider without entering a key leaves the role with no key, and the picker should say so.
- **"(none)" already works for a role.** `PUT /api/role/:id` with `{ llmConfig: null }` clears the role's model, so it falls back to the company's. `RoleResponseDto` and `CompanyResponseDto` type `llmConfig` as `LlmConfigDto | null` since 002.00. The company side does not accept `null` yet: `UpdateCompanyDto.llmConfig` needs the same change 002.00 made to `UpdateRoleDto` (`@ApiProperty({ type: LlmConfigDto, nullable: true })` and `| null`), then regenerate `schema.d.ts`.
- **Partial patches fail validation.** `LlmConfigDto` requires `provider` and `model`, so `{ llmConfig: { model } }` is refused. Always send the whole config.
- **The tools setting is beside it.** The same Details tab has a Company default / On / Off choice per MCP server, from `GET /api/mcp-servers`. If the picker shows a context window recommendation, the tool footprint (`GET /api/company/:companyId/roles/by-slug/:slug/tool-footprint`) is the other half of that budget.
- **Tests** for the dialog are in `RoleDialog.test.tsx`. One asserts that `apiKey` never appears in a request body; keep it passing.
