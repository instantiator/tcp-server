Once a record table exists, nobody can change its columns. Agents can create tables, add rows and update them; people can edit cells, add and delete rows, and clear or delete a whole table. But no one can add, rename or delete a column.

An example from the dev server (task 007): asked to record that the chicken was fed at 08:00 and the cat at 09:00, the agent made a `feedings` table with `feeding_date` and `feeding_time` only, keyed on both. There is nowhere to say which animal was fed, and feeding both at the same time would be refused as a duplicate. Ordinarily I'd ask the agent to improve the table, but it can't.

Filling in missing data already works once a column exists: agents have `update`, and people can edit cells in the sheet. What's missing is changing the schema.

Please create a plan to let agents and people change a table's columns.

**Agents, with limited permissions at first:**

- **Add a column.** Existing records get a blank, or a default value the agent gives. A new column is optional unless a default fills every existing row.
- **Rename a column.** Every existing record is rewritten under the new name.
- **Delete a column** — a deliberate placebo. The tool deletes nothing. It returns advice: ask a user (with `request_user_input`) to delete the column, naming it and explaining why. Once 003.01 (action approval) lands, this should become an approval request carrying the exact action, which the platform runs when the user approves.

**People, in the web UI:** add, rename and delete columns from the sheet. Deleting asks first, and offers a download of the table (as clear and delete do now).

**Protected columns:**

- The record id, version and timestamps live outside a record's fields, so schema changes can't reach them. Keep it that way.
- Primary and unique key fields can't be renamed or deleted by agents. Renaming one rewrites every stored key, and deleting one breaks uniqueness. Decide whether people may, and how.
- Changing a key (such as adding `animal` to the `feedings` key above) is a question for the plan: in scope, or deferred?

Things the plan must respect:

- Every change is audited: by the agent through tcp-mcp-records, by a person through tcp-server (see ADR-008's 001.01 and 001.03 amendments).
- A change and the rewrite of existing records happen in one transaction, safe against concurrent inserts and updates.
- Tool schemas cost context on every turn (see `docs/context-management.md` and the tool footprint estimator). Consider one `alter_table` tool rather than three.
- A table's schema is stored as `jsonb`, which doesn't keep field order; the sheet and CSV use `fieldOrder`.
- An open sheet won't see a schema change until it reloads (001.05 covers live updates).

Challenge me on the design if there's a simpler or safer way to do this.
