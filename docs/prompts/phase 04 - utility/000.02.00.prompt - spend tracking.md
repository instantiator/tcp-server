> ## Spend tracking
>
> **Today:** no token usage is recorded. `AGENT_ITERATIONS` caps loop length,
> not cost.
>
> **Recommend:** record input/output tokens per run (LangChain reports them),
> show them per company and task, and allow an optional monthly budget per
> company that pauses non-urgent work when it runs out. A side income that pays
> its API bill first isn't a side income.

Notes on the optional input/output caps...

- It should be possible to set a cap at the application level, and then also at individual company levels
  - Both kinds of cap are optional
- Company level caps should be expressible as X tokens, or a percentage of the application cap
  - Company level % caps should only be observed if there's an application level cap
    - If not observed, this should generate a warning for the user
- Caps should contain any number of optional notifications, tiggered at given percentages of the way to the cap
- This will also need a mechanism to configure how to handle reaching the cap
  - eg. permit the immediate pause of running agents (with sufficient stored state to resume them - either from exactly where they were, or allow a resume of the task to restart the currently running agent(s))
  - eg. permit the graceful completion of currently running agents
  - eg. permit the graceful completion of currently running tasks (and then not start new tasks automatically)
    - this can be effected in the web UI by switching the default 'start now' to false for new tasks, when 'capped'
    - this will also require an easy way to start/resume a task that is currently paused
      - through the API, TUI, CLI, and web UI
      - starting/resuming a task should still work as it's an intentional action taken by the user
      - it should also be possible to do this at company level (ie. resume a whole company)
- it should also be possible to dismiss a company level / application cap
  - until the next reset
  - indefinitely
- it should also be possible restore a company level / application cap
- the company should track token usage per task, on the way to the cap
- the company should track token usage per 5 minute period (when active), so that it can be more easily observed
- the cap reset condition should be configurable, options include:
  - 00:00 on the first of the month (ie. the monthly spend cap)
  - X tokens, per 5-hour stint (ie. the pro-plan cap) and Y tokens, per week
    - What are the default pro-plan caps for common providers? (Anthropic, OpenAI, Gemini, ...?)
    - If these aren't known (or vary over time), can they be tracked through the provider API?
      - Do we need some special-case provider handling for this?
  - X tokens daily (ie. a daily spend cap)
- the CLI should be able to report on usage (and if caps are set, include detail of the caps and progress towards caps)
- the web UI and TUI should show notifications to the user
  - the API will need an endpoint to retrieve notifications
  - CLI should also be able to retrieve notifications
  - application and company views that use SSE will also need to be able to receive updates to the current notifications for the user
  - notifications should be dismissible
  - notifications should be able to have different levels of severity (info, warning, others?)
- the web UI should show an unobtrusive horizontal bar under the breadcrumbs
  - each breadcrumb part should have a bar, below its text, eg.

    ```text
    companies > company name
    [====---]   [======----]
    ```

  - bars should have a tooltip with the full details (eg. "X% of Y token cap, since [last reset]<br/>All tasks will be immediately paused<br/>Next reset: [whenever it is]", or "X% of the Y% share of the application cap, since [last reset]<br/>All tasks will finish gracefully<br/>Next reset: [whenever it is]")
  - if no cap is set, the bar should show as 'full', and the tooltip should read something like "X tokens used since [when tracking began]"

Ideally we'll re-use a lot of code for the configuration - as we're implementing configuration at app and company level. We've got that style of configuration elsewhere in the application.

The notifications are new, but this is a good opportunity to implement them, I think.

Aim for consistent, concise, clear code. Some previous work was done without dev-qual guidance in place, so where you _encounter_ code that isn't compliant with code quality guidelines, make improvements - but don't reach further than that.

Where there's a part of this prompt that's already featured in an upcoming prompt, it's ok to defer to that prompt (provided the rest of this work still makes sense in the light of it). Carry forward any additional guidance needed into that prompt to ensure it's done as planned here.

At the moment, the web ui offer application-level or company-level configuration. That's ok - we'll do it through company definition JSON and `.env` file configuration for now, and it can be incorporated into company creation / editing in a future prompt.

Is there a standard way to publish this kind of telemetry? We may consider that it's the beginning of API compatibility with an open telemetry standard if there's one that's appropriate for this.

## Addendum — agreed in planning (2026-10-04)

The plan is [000.02.01.plan - spend tracking](000.02.01.plan%20-%20spend%20tracking.md). Planning changed the scope of this prompt:

- **Caps are per LLM provider, at application level only**, configured in `.env` (`SPEND_CAPS`). Company caps, and company caps as a % of the application cap, are dropped for now and recorded in `docs/outstanding-issues.md`. The "% cap without an application cap" warning goes with them.
- **Threshold notifications stay.** Each cap's `notifyAt` percentages raise `warning` notifications; reaching the cap raises an `error`.
- **A cap limits total tokens.** Input and output tokens are still recorded separately.
- **An explicit start or resume exempts that task until it ends**, so it isn't paused again after its next LLM call. Resuming a company does the same for that company's paused tasks; it doesn't lift the cap.
- **Reset windows:** `month`, `week`, `day` (all UTC), or an `<N>h` stint that starts at first use. When a cap resets, the agents it paused resume automatically.
- **Actions on reaching a cap:** `pause` (at the next LLM-call boundary, from the agent's checkpoint), `finish-agents`, or `finish-tasks`.
- **Chats are counted but never gated.**
- **No TUI work** — 002.07 retires the TUI. The CLI and web UI cover everything.
- **No pro-plan special-casing.** Subscription plans aren't usable through API keys, and their limits aren't published as token counts. Users enter their own numbers, and should also set a hard limit in each provider's console.
- **Telemetry:** field names follow the OpenTelemetry GenAI conventions (`gen_ai.usage.input_tokens` / `output_tokens`). An OTLP exporter is deferred.
- **Deferred to other prompts:** the task dialog's Resume button (000.04), push delivery of notifications (003.03), honouring caps on automatic starts (004.01), and per-task usage on the dashboard (005.00).
