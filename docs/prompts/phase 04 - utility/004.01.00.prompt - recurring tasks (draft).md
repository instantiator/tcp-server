> ## Recurring tasks
>
> **Today:** none. BullMQ is already in the stack.
>
> **Recommend:**
>
> - A `TaskSchedule` entity: a task template (request, materials, expected
>   outputs), a cron expression or interval, a timezone, and enabled/paused.
> - Use BullMQ job schedulers to create the task. No new dependency.
> - **No overlap:** skip a run while the last one is still going.
> - **Catch-up rule:** home machines sleep. On wake, run a missed schedule once,
>   not once per missed slot.
> - Show schedules and their last and next runs in the web UI and the CLI.

**Carried from 000.02 (spend tracking):** an automatic (scheduled) task start
is **not** an explicit user action — it must not go through the
cap-exempting start path (`POST /api/task/:id/start`'s exemption on a
reached cap is for a user choosing to spend, not a schedule firing), and must
not start at all while any cap with action `finish-tasks` (or `pause`/
`finish-agents`) is reached. Once started, a scheduled run is gated by
tcp-agent's spend gate exactly like any other agent run.

## Templates (from 002.03)

- Add schedules to the template format (v2, planned in 005.04): the task template, the cron expression or interval, and the time zone. Whether a schedule starts enabled or paused on import is a plan decision. Paused is the safer default. A format change means bumping `formatVersion` (to 2 or higher). v1 refuses unknown keys, so an older server will refuse the new template with its "made by a newer version of TCP" message, which is the right result. The new code must still read version 1.
- `cottage-industry` candidates: check for new orders and enquiries daily, a weekly stock check, and a monthly bookkeeping summary.
- Export writes schedules back. The format is documented in `templates/blank/README.md`, which travels inside every blank download. Update it in the same change, so it never lags behind the code.
