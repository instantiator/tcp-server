> ## Customer data protection
>
> Orders mean storing names, addresses and emails of members of the public.
>
> **Recommend:** a retention period per record table (for example, delete
> customer addresses N months after delivery), a "find and delete everything
> about this person" action, and an export for subject access requests. The
> template should say that the user may have data protection duties (in the UK,
> possibly an ICO fee) and point to the official source, without giving advice.

We should also add UI for managing data protection by supporting:

- search through all tables to create a view of matching rows
  - allow modification of data through that view
- select a subset of entries or all entries of any table or view (including the search view) for...
  - export
  - deletion

ie. if multiple rows are selected then a download / deletion applies to those rows.

We should also make it possible to add strings to a "do not store" list (per company) - both in the UI and for agents. (The UI should also offer a searchable view of that list - reuse the table view component for this, and edit/remove features, so users can adjust or remove a string from the list if it's there in error, or the request changes).

There should be a tool for an agent to remove or modify a string in the "do not store" list, but it should advise the agent to make an enquiry to ask a user to do it, rather than directly make the change.

- when agents store records, only records that do not match entries on the do not store list should be stored - the others generate a warning
- agents are warned about entries that could not be stored, and advised to fail their assignment if they cannot process the record

NB. Do we have ways for an assignment to fail (effectively failing the task) right now? If not, or if any of the reasons outlined below are missing, please include that as a part of the plan. Possible reasons for an agent to fail an assignment:

- GDPR violation: the data to act on would involve storing PII found in the "do not store" list
- An agent has exhausted all variants of a tool call it can think of, and it's not working
- An agent makes the same call to a tool N times
- An agent cannot obtain the information it needs, and determines the task is not possible without specific information
- The reviewing agent determines that the agent output is insufficient after N attempts
- Unexpected system errors...
  - Unable to access a required MCP server after N attempts
  - Unable to access LLM provider after N attempts
  - Other (record what's possible - eg. exception name and message, and what the agent was doing at the time)

A failed task should store its failure reason and that should be visually presented to the user on inspection - ie. through the web ui, task description, and CLI.

If unable to take action on a failed task (eg. because of unexpected system errors) the system should halt, and attempt to log the issue by all means possible:

- Audit log
- Console error logs
