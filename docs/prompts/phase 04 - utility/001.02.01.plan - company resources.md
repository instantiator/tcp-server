## Context

Today every writable file belongs to a task (`tasks/{id}/…`). An invoice made by one task sits in that task's `completed/` folder, and the next task has to go looking for it. Nothing is company state except records.

This plan adds `{company}/resources/`, a place for long-lived company documents: invoices, price lists, policies, listing copy. Agents get tools to read, list and change them. Inside a task, a change is a **draft** that QA reviews. The draft is copied into `resources/` only when the task succeeds. Bucket versioning keeps old versions, so a bad change can be undone.

The plan also rewrites the mode prompts so that each sentence about a server appears only when the agent has that server, and it makes the records and resources guidance clear for small models.

### Decisions agreed with the user (2026-10-11)

- **Draft, then apply.**
  - In a task, `write_resource` writes a draft next to the working files.
  - A read looks in three places, in order: this agent's own draft, then the draft from the latest earlier step that QA approved, then the live resource.
  - Drafts are applied to `resources/` when the task succeeds. This happens on both finalise paths.
- **Chat writes directly.** The user in the conversation is the review, and versioning makes the change undoable. Resources are read-only in consultee, plan and qa modes.
- **One new artifact type, `resource`.** It's used for expected outputs and for materials. Its value is the path under `resources/`, for example `invoices/INV-0042.md`. A `resource` output can create a new resource or update an existing one.
- **Sensitive-change approval is deferred to 003.01.** The 003.01 prompt gains a section, so it gets done once the core of 003.01 has landed.
- **The tools live in the storage server.** They are switched on and off together with storage.
- **The cross-company read gap gets fixed, as its own stage.** The shared read tools can currently read any company's files.
- **Versioning covers the whole bucket.** Old (non-current) versions expire after `STORAGE_VERSION_RETENTION_DAYS`, which is 90 by default. A company can override this with `TcpCompany.versionRetentionDays`.
- **Undo goes through the MinIO console for now.** The steps are documented, and the 002.05 storage-browser prompt gains a "history and restore" note.

### Decisions made in this plan (object at approval if wrong)

**Key layout** (helpers in `libs/tcp-shared/src/storage/artifact-keys.ts`):

| What                      | Key                                                                                                                           |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Live resource             | `{slug}/resources/{path}`                                                                                                     |
| Draft (task step)         | `{assignmentWorkingPrefix}resources/{path}`                                                                                   |
| Approved draft (after QA) | `{assignmentCompletedPrefix}resources/{path}`. `promoteApproved` puts it there.                                               |
| Task's pending changes    | `{taskCompletedPrefix}resources/{path}`. `promoteToTaskCompleted` puts it there. This is also the finaliser's working folder. |

- The existing promotion pipeline carries drafts all the way through, so the only genuinely new step is **apply**. It copies `tasks/{id}/completed/resources/**` to `{slug}/resources/**`.
- The task's copy is kept afterwards, as the record of what the task changed.

**Tools** (storage server, 5 new). Write tools are hidden in plan, qa and consultee modes, and the server checks this too.

| Tool                  | Input                 | What it does                                                                                              |
| --------------------- | --------------------- | --------------------------------------------------------------------------------------------------------- |
| `list_resources`      | `path?`               | A folder tree, with each folder's purpose (the first line of its `README.md`) and drafts marked `(draft)` |
| `read_resource`       | `path`                | Reads through the layers above                                                                            |
| `write_resource`      | `path, content`       | Creates or replaces the file. It has no `overwrite` flag; the reply says whether it created or replaced.  |
| `append_resource`     | `path, content`       | Appends text. On the first change in a task, it copies the current version into the draft first.          |
| `replace_in_resource` | `path, find, replace` | Same copy-on-first-change as append, then a literal find-and-replace                                      |

- **Paths are forgiving.** The tools trim the path and turn `\` into `/`. They strip a leading `/`, `resources/` or `{slug}/resources/`. They reject `..`, `_deleted`, an empty path, and a trailing `/` on a file tool (that reply suggests `list_resources`).
- **Feedback when something is wrong.** Every one of these is plain `ok()` text, as the storage server's other tools do.
  - A file that doesn't exist: the reply names the folder and lists its files.
  - The same stem with a different extension, or the same filename in another folder: the reply says "Did you mean …?".
  - A folder that doesn't exist: the reply shows the tree from the deepest folder that does exist.
  - A binary extension (pdf, docx, images…): the reply says the file can't be read as text.
  - A write into a folder that has no `README.md`: the reply says the folder was created and suggests adding a one-line purpose note.
- **Folder purpose = `README.md` in that folder.** It's an ordinary resource that users and agents can both edit. No new metadata is needed.
- **Listing uses `listAll`, not `listFiles`.** `listFiles` stops after the first 1,000 keys.
- **Deleting a resource is out of scope.** It goes into outstanding issues, to act on when a task needs to remove one.

**Artifact type `resource`:**

- **Allowed in:** assignment `expected` and `prepared` (`WORKING_ARTIFACT_TYPES`), and in materials. The user-set task-level `expected` stays as it is.
- **Gate:** `checkAssignmentOutputs` checks that the draft exists.
- **Promotion:** QA accept promotes **every** file under `working/resources/`, whether or not it was listed in `prepared`. This is forgiving for small models.
- **QA presentation:** it lists the resource drafts, and tells QA to read them with `read_resource`.
- **Display:** `renderArtifactList` shows `- resource: {path}`, so the agent knows which tool to use.
- **Plan validation:**
  - The path must pass the path rules above.
  - A `resource` material must exist live, or be expected by an earlier step. This works the way `danglingPriorOutputs` does today.
- **When apply runs:** in `finaliseMechanical`, and in `assignmentFinalised`, before the task is marked `succeeded`.
  - It runs files in order. If one fails, the task fails, and the message lists the files already applied.
  - Running it twice is harmless (it just writes another version). So recovery after a restart can simply run it again.
- **The finaliser:** whether a finalise agent runs is unchanged (it runs only when the task has `expected` outputs). When it does run, its prompt lists the pending resource changes, and it can fix them with the resource tools.

**Versioning:**

- On boot, `StorageVersioningService` turns on bucket versioning and then syncs the lifecycle rules. It syncs again after a company is created, updated or deleted, and after a template import.
- Rules:
  - One rule per company prefix `{slug}/`, with that company's days, falling back to the app default.
  - One rule for `_deleted/` at the app default.
  - `ExpiredObjectDeleteMarker` is on in all of them.
- The whole configuration is replaced on each sync. A `ponytail:` comment names the ceiling: about 1,000 rules per bucket.

**Prompts that depend on servers:**

- `MODE_PROMPTS` becomes a list of sections per mode, each `string | { text, needs: McpServerName }`.
- `modePrompt(mode, serverNames)` drops any section whose server isn't loaded.
- `buildAssignmentMessage` takes `serverNames`. tcp-agent already has `loadedServerNames`, and the chat path has its own resolved list.
- Every sentence that names a server's tools gets a `needs`, including the existing ones about storage, interactions and memory.
