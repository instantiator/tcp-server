## Context

Record tables load once. If an agent or another person changes a row while someone has the sheet open, they see the old value until they reload, and only the version check (409 `stale`) stops them overwriting it. This plan makes the sheet say when it is out of date, lock the rows that changed elsewhere, and keep the list of tables current. It does all this without moving rows under the reader.

### What exploration found

- **Records changes are audited but never reach the company stream.** Both emitters write `state_change` with `{source:'records', action, table, …}` and no `entity`:
  - agents: `tcp-mcp-records/src/mcp/records-tools.service.ts:413` (`change()`);
  - people: `tcp-server/src/api/records-api.service.ts:487` (`changed()`);
  - retention: `records-retention.service.ts:55`.

  `AuditEventPublisher` (`tcp-server/src/events/audit-event-publisher.service.ts:32,71`) sends only five entities to the company channel.

- **The payloads hold customer data** (`before`/`after` rows). Bulk actions (`append_csv`, `clear_table`, `retention_sweep`) carry no row ids, and nothing carries a version.
- **A separate records database is unaffected.** Audits go over HTTP to `POST /internal/audit` (`libs/tcp-shared/src/audit/audit-client.service.ts:53`), then `AuditService.write` saves to the main database and publishes, all inside tcp-server.
- **Priming** (`tcp-server/src/api/company-priming.service.ts:50`) replays current state on every (re)subscribe, and has nothing for records.
- **Precedent:** `usage.service.ts:93` emits `{entity:'spend', reason:'change'}`, a summary-less "go refetch" signal.
- **Client:**
  - `applyEvent` (`frontend/src/events/cache.ts:93`) invalidates `[entity]` when an event has no summary. That would refetch and re-sort the open sheet, so `record` needs its own branch.
  - Query keys are in `src/api/query-keys.ts:34–54,162–176`.
  - The cache patch helpers are `useRecordCache` (`src/api/hooks.ts:710`).
- **Sheet:**
  - `RecordSheet.tsx`: `editable` is a static per-column flag (224, 347). `MarkedCell` (117) already draws icon plus hidden-text marks from grid context. The default sort compares positions in `rows` (209, 299).
  - `TableView.tsx`: the notices are `<p className="table-view__notice">` (335, 353).
  - Reload is `RecordTableActions` `onReload` (TableView 319).
- **Search view:** `DataProtectionPanel.tsx` (`SearchGroup` at 324) shows one editable `RecordSheet` per matching table, from `useRecordSearch` (`endpoints.ts:775`).
- **Announcer:**
  - `src/announce/announcer.ts` owns every live region and coalesces per channel.
  - `announceRecords` (`RecordSheet/announceRecords.ts`) announces immediately.
  - `SystemBanner.tsx:27-82` is the model for a labelled notice that announces once, with a StrictMode-safe guard.
- **Table summaries** are ordered by name (`records.service.ts:482`). A live refresh never re-sorts them.

### Decisions agreed with you (2026-10-15)

- **A "this table changed" signal plus a background compare**, not per-row events.
- **Announce once until Reload.** Later changes update the notice text silently.
- **The search view is included**, using the same mechanism.
- **One commit per stage.**

### Design (object at approval if wrong)

**Server**

- `AuditEventPublisher.publish`: a `state_change` whose `payload.source === 'records'` and which has a string `payload.table` also goes to the company channel. It goes as a **copy with a cut-down payload**, `{entity:'record', action, table}`, so no row data or user id reaches the browser. Persisted audit rows and the agent channel are unchanged. `do_not_store_*` actions have no `table`; they are sent as `{entity:'record', action}` so the do-not-store list refreshes too.
- `CompanyPrimingService.prime` appends one `{entity:'record', reason:'replay'}` event. After a reconnect, the client re-checks every open table and search, so changes missed while the stream was down are still caught. ADR-025 keeps its "the server primes, the client holds no state" rule.

**Client**

- `query-keys.ts`:
  - `'record'` moves from `STATIC_ENTITIES` to `EVENT_ENTITIES`.
  - New scope `'latest'`, with keys `recordTableLatest(companyId, table)` = `['record','latest',{companyId,table}]` and `recordSearchLatest(companyId, q)` = `['record','latest',{companyId,q}]`.
- `applyEvent` gets a `record` branch before the generic path. It **never touches `['record','detail']` or `['record','search']`**, which are what is on screen. It calls a small `recordChanged(queryClient, companyId, table?)` that, trailing-throttled at 1s per company (`// ponytail:` comment naming the ceiling):
  1. invalidates `['record','list']`, which covers the summaries and the do-not-store list;
  2. for each detail query of that table **with observers** (or every table when `table` is absent), `fetchQuery`s the table into its `latest` key;
  3. for each search query with observers, whose groups include that table (or any, when `table` is absent), `fetchQuery`s the search into its `latest` key.

  The 1s delay also means a person's own edit has patched the cache before the compare runs. The compare is derived, so a late patch still resolves.

- `compareRows(shown, fresh)` is a pure function in `src/components/RecordSheet/compareRows.ts`. It returns `{ changed: Set<id>, deleted: Set<id>, added: number }`:
  - **changed:** in both, with `fresh.version > shown.version`;
  - **deleted:** in shown, not in fresh;
  - **added:** in fresh, not in shown.
- Hooks, following ADR-030 (`Live` means push-updated):
  - `useRecordTables` becomes **`useLiveRecordTables`**.
  - New **`useLiveRecordTableChanges(companyId, table, shownRows)`** reads the `latest` key without fetching (cache subscription only; fetching happens only from `recordChanged`). It returns `{ changed, deleted, added, dropped, any }`; `dropped` is true when the latest fetch got a 404.
  - New **`useLiveRecordSearchChanges(companyId, q, groups)`** does the same per group.
  - `useRecordTable` and `useRecordSearch` stay un-prefixed: what they show is deliberately a snapshot.
- **Reload** (existing `reload` in `useRecordCache`, and the search's reload) also removes the matching `latest` queries, so the notice clears once the fresh rows are on screen.

**Sheet UI** (`TableView`, `SearchGroup`, `RecordSheet`)

- **Notice** above the grid, while `any`. It is a `role="group"` labelled "Out of date", modelled on `SystemBanner` (not `role="alert"`). The text is counted with `tCount`, for example "Changed elsewhere since you opened it: 2 rows changed, 1 deleted, 3 added." It is followed by a **Reload** button. A dropped table reads: "This table was deleted elsewhere. You can still read it here; it can't be changed."
- **Announcement:** one polite announcement on a new `records-remote` channel when `any` goes from false to true ("Orders table is out of date. Reload to see the changes."). It is guarded like `SystemBanner` so StrictMode doesn't double it. Further changes are not announced until after a Reload.
- **Read-only rows:**
  - `RecordSheet` takes `staleRows?: ReadonlyMap<string, 'changed' | 'deleted'>`, carried in the grid context like the existing marks.
  - Columns use `editable: ({ data }) => !readOnly && !staleRows.has(data.id)`.
  - `MarkedCell` on the first field shows an icon plus hidden text, "changed elsewhere" or "deleted elsewhere". The mark is never colour alone, and the cell's own accessible text says it.
  - When the table is dropped, every row is read-only, and Add, Delete and the More menu's write actions are disabled.
  - TableView's single-row Delete is disabled for stale rows. Bulk Delete of selected rows still works: deleting an already-deleted row is harmless.
- Rows never move: `rows` (the shown snapshot) is untouched until Reload, so the position sort is unaffected.
- `TablesPanel` keeps an open table mounted, with its dropped notice, when the table vanishes from the list, rather than closing it under the reader. Moving focus elsewhere would break ADR-027.

### Changed while implementing stage 2 (2026-10-15)

- **Files live in `src/api/`, not `src/events/` or `components/`.**
  - `record-changes.ts` (`recordChanged`, `forgetLatestRecords`) and `compareRows.ts` read `endpoints.ts`.
  - The eslint boundary keeps `endpoints.ts` internal to `src/api/`. `cache.ts` imports `recordChanged` from there.
- **An edit made here patches the fresher copy too.**
  - Without that, a row added here after the copy was read would show as "deleted elsewhere" until the next change.
  - `useRecordCache.edit` and `replaceInSearches` apply the same change to both copies.
- **Reading the screen again forgets the fresher copies it makes stale, cancelling any read in flight.**
  - Reload forgets its own table and every search.
  - Bulk actions forget them all.
  - Deleting selected rows forgets the searches.
- **A truncated copy calls nothing deleted.** A row missing from it may only have been pushed out by newer rows.
- **Known gap:** if a person's own save takes longer than the 1s window plus a read, that row shows "changed elsewhere" until the save's response arrives. The derived compare then clears it, but the one announcement may already have been made.
