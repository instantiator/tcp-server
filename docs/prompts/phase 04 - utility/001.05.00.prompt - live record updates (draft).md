Record tables are not live yet. A table loads when it opens; the list of tables refetches when the window regains focus; **Reload** in the sheet's More menu fetches a table again. If an agent changes a row while a person has the sheet open, the person sees the old value until they reload. The version check stops their edit overwriting the agent's (409 `stale`), and the table then reloads.

Please create a plan to make record tables live, so that people know when what they are looking at has changed.

When an agent (or another person) changes a record table that someone has open:

- **Say that the sheet is out of date.** Show that the sheet needs an update — a notice with **Reload**, and one polite announcement — rather than silently replacing what the person is reading.
- **Stop edits to rows that are out of date.** A row known to have changed elsewhere becomes read-only, and is marked as changed elsewhere (not by colour alone), until the sheet is reloaded. The version check stays as the backstop.
- Keep the list of tables (the tray and the Tables tab menu) current: counts, new tables, deleted tables.

Things the plan must respect:

- **Rows never move under the cursor** (ADR-027). The 001.03 sheet keeps edited rows in place by patching the cached table in place, and its default "Updated" sort compares positions in that cache. Don't apply incoming changes in a way that reorders the sheet.
- **One stream per company** (ADR-025, `MAX_STREAMS`): use the existing company stream, not a new one. Records changes would add volume to a channel that already carries five entity kinds — consider whether the sheet needs every change, or only a "this table changed" signal.
- **The `Live` prefix means push-updated** (ADR-030). `record` is in `STATIC_ENTITIES` today; if it moves out, the hook names should say so.
- **Records changes are already audited** (`state_change`, `source: 'records'`, from the agents' MCP server and from people's edits — see ADR-008's 001.01 and 001.03 amendments). Audit events are what the company stream already carries, so they may be enough.
- **A separate records database** (`RECORDS_DATABASE_URL`) must still work.

Challenge me on the design if there's a simpler way to give people the same confidence. Accessibility is very important.
