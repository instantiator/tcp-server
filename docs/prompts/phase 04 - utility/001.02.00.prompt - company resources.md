> ## Company resources
>
> **Today:** the storage tree (`libs/tcp-shared/src/storage/artifact-keys.ts`) is
> task-scoped: `tasks/{id}/materials`, `working`, `completed`. The shared-storage
> tools are read-only (`describe_folder`, `list_files`, `read_file`,
> `search_files`, …). An invoice made by a task ends up in that task's
> `completed/` folder, and the next task has to search for it.
>
> **Recommend:**
>
> - A `{company}/resources/` area for long-lived documents: invoices, price
>   lists, policies, listing copy. Each subfolder has a short purpose note the
>   agent can read.
> - Tasks declare expected outputs as **resource changes** ("create
>   `resources/invoices/INV-0042.pdf`", "update `resources/price-list.md`"). The
>   agent works on a draft in its working folder. Finalisation applies the change
>   once QA accepts it, or once the user approves it for anything listed as
>   sensitive.
> - Keep version history (MinIO object versioning) so a bad change can be undone.
> - Records and resources together are "company state". Tasks are how it changes.

Create a plan to implement company resources including:

- a way to read, write, and modify company resourcs
- a way to list subfolders or see parts of the directory tree for company resources
- expected task outputs currently only have a couple of types, this is effectively a new type
  - agree the names of types with the user during planning
  - types should be inutitive to help small models interpret them correctly
- new directions for the finaliser
- simple but clear descriptions for the tools that work with resources
  - again to help small models use them correctly
  - include advice about when to create/use company resources in the agent assignment prompts
  - include advice to the planner about mentioning them in assignment descriptions if company resources need to get made or used by agents
- the new tools should give clear feedback if anything isn't right, and make suggestions for the model to reason about
  - eg. incorrectly provided parameters (as with other tools, explain what's not right clearly)
  - eg. if the request is to read a file that doesn't exist, respond with a clear explanation and a list of files in the directory
  - eg. if a directory to read from doesn't exist, respond with the tree from parts of the path that _do_ exist
  - eg. if the file doesn't exist, but another does with the same name but a different type, return a suggestion ('did you mean...?')
  - eg. create directories as needed for write operations
- existing task file tools should spot requests that look like they're for company resources, and recommend resource tools

Please also revisit the records tools and ensure that the tool descriptions, and working prompts for planning, implementing, and finalising are clear - indicating what the various tools are for and when they should be used.

Remember that not all MCP tools are available to all roles - they're configurable, so be sure to compose these prompts using that knowledge (ie. so as not to waste context on instructions about tools that won't make sense to the agent and that they can't use).
