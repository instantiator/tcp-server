## Context

Agents will soon store orders: the names, addresses and emails of members of the public. Today nothing limits how long those rows live, nobody can find everything held about one person, and nothing stops an agent storing data about someone who asked not to be stored. Separately, an agent has no way to give up on its assignment: it can only complete, pause, or loop until a limit trips.

This plan has two parts, failure first because do-not-store needs it:

1. **Assignment failure** — an agent can fail its own assignment with a reason; failure codes are saved and shown; the missing system failure cases are detected; a failure that can't be recorded halts the system.
2. **Data protection** — per-table retention, cross-table search with editing, export and delete of selected rows in any sheet, a per-company do-not-store list (people and agents), and a non-advisory note about data protection duties.

### Decisions agreed with you (2026-10-12)

- **One plan, failure part first.** Data protection's refusals point agents at `fail_assignment`.
- **Do-not-store matching:** whole words, any case. Normalise both sides (lower case, collapse whitespace, trim); an entry matches a string field if it appears bounded by non-letter/non-digit characters (Unicode-aware). "Ann Lee" matches "Deliver to ann lee, 3 High St"; "Ann" doesn't match "Annual".
- **Agents can't read the list.** They only learn of a match when a write is refused; the refusal names the field, not the entry.
- **People's edits: warn and allow.** Add, edit and CSV append return 409 `do_not_store` with the matching fields; the UI asks to confirm and retries with `confirmDoNotStore: true`.
- **Search view:** one editable sheet per matching table; selection spans the sheets; export gives one CSV per table (a zip when more than one).
- **Retention:** per table, N days after a chosen date field, or after the row's last update if none is chosen. Rows with a blank or unparsable date never expire. Whole rows are deleted.
- **Erasure scope:** record tables only. The page says plainly what it doesn't reach (audit log and transcripts, knowledge, resources, files, memory, backups); `outstanding-issues.md` gets an entry for each.
- **ICO note** sits at the top of the data protection page, with a link to the ICO's own page; it moves into templates when they exist.
- **Repeated calls:** count identical tool + arguments across the whole run (results ignored), so A,B,A,B,A loops are caught. N stays 3, a const.
  - **Changed at F3 (2026-10-12):** the result stays part of the match. Without it, a healthy run that lists files three times while writing them would be stopped. Counting across the whole run still catches A,B,A,B,A loops, since a real loop gets the same answer each time.
- **Halt** = start the 000.05 drain, `Logger.error`, and try an audit row. tcp-agent, if it can't reach tcp-server after retries, pauses its own workers and logs.

### Decisions made in this plan (object at approval if wrong)

**Failure**

- **Failure codes are stored.** New nullable `failureCode varchar` on `tcp_assignment` and `tcp_task` (tcp-server migration, registered by hand in `app.module.ts`). `FailDto` gains `code`. The UI and CLI show `RUN_FAILURE_MESSAGES[code]` plus any detail; `failureReason` keeps the full text for old rows.
- **New `RunFailureCode`s:** `data_protection`, `tools_exhausted`, `information_unavailable` (agent-chosen), `review_exhausted` (QA, replacing the UUID wording). MCP mid-run reuses `service_unavailable`. `unexpected`'s detail becomes `"<ErrorName>: <message> (while <activity>)"`, where activity is the last tool call's name, "calling the model", or "setting up".
- **`fail_assignment` tool** in tcp-mcp-tasks: `{reason: 'data_protection' | 'tools_exhausted' | 'information_unavailable', explanation: string}`. It ends the run the same way `complete_assignment` does. Offered in plan, implement, qa and finalise; withheld in chat and consultee (`mode-tools.ts`). Its description says: try other approaches and `request_user_input` first.
- **MCP mid-run:** 3 consecutive connection failures to the same server abort the run with `service_unavailable` naming it. Tool errors that aren't connection errors still go to the model.
- **LLM:** unchanged; already covered. The rate-limit pause has no attempt cap; that's deliberate (000.03) and stays, noted in outstanding issues.
- **Unrecordable failure:** `notifyFailed` retries 3 times (1s, 5s, 25s). On final failure tcp-agent logs at `error` with code, reason and agent id, and pauses its BullMQ workers. In tcp-server, if `failAgent`/`failTask` throws: `Logger.error`, an `AuditService.record` attempt in its own try/catch, then `SystemDrainService.begin` with reason "a failure could not be recorded".

**Data protection** (records DB, so tcp-mcp-records and tcp-server both reach it without HTTP)

- **Records migration** (tcp-mcp-records, added to `migrations-list.ts`):
  - `record_table.retention jsonb null` — `{days: integer 1..36500, from: 'updated' | <date field name>}`.
  - `record_do_not_store (id uuid, companyId, value text, normalised text, note text null, addedByRole 'user'|'agent', addedById text, createdAt, updatedAt)`, unique `(companyId, normalised)`, FK to `tcp_company` only if present (same trick as the first migration). Cap 1,000 entries per company.
- **`RecordsService` additions:** `listDoNotStore`, `addDoNotStore`, `updateDoNotStore`, `removeDoNotStore`; `doNotStoreMatches(companyId, data) → field names[]` (pure matcher in `libs/tcp-shared/src/records/do-not-store.ts`); `search(companyId, q)` (ILIKE on `jsonb_each_text` values, all tables, ≤1,000 rows, grouped by table with `truncated`); `readRowsById`; `deleteRows(companyId, table, [{id, version}])` (one transaction, all or nothing on a stale version); `setRetention`; `sweepRetention(now) → [{companyId, table, deleted}]`.
  - Search is a plain substring match: finding should be broad, blocking should be precise.
  - The check happens before the insert, outside its transaction: an entry added mid-write can miss that write. Marked `ponytail:`.
- **Agent writes:** `insert` and `update` (and `insertMany` callers) refuse a matching record, returning `{stored: false, fields, note}` with: "Not stored: field(s) X match this company's do-not-store list. Don't try to store this another way. If the task can't be done without it, call `fail_assignment` with reason `data_protection`."
- **`do_not_store` agent tool** (records server, one tool): `{action: 'add' | 'remove' | 'change', value, newValue?, reason}`. `add` stores the entry (audited). `remove` and `change` do nothing and return advice: ask a user with `request_user_input`, naming the entry and why. Offered in every mode (a customer may ask in chat), not in `RECORDS_WRITE_TOOLS`.
- **REST** (all `@CompanyScope`, under `/api/company/:companyId/records`):

  | Route                                                      | Does                                                                         |
  | ---------------------------------------------------------- | ---------------------------------------------------------------------------- |
  | `POST search` `{q}`                                        | Grouped matches. POST so the person's name stays out of URLs and access logs |
  | `POST export` `{tables: {[name]: ids[] \| 'all'}}`         | CSV for one table, zip for several                                           |
  | `POST tables/:table/rows/delete` `{rows: [{id, version}]}` | Bulk delete; 409 `stale` if any version is stale                             |
  | `PUT tables/:table/retention` `{days, from} \| null`       | Set or clear; 400 if `from` isn't a date-format field                        |
  | `GET/POST do-not-store`, `PATCH/DELETE do-not-store/:id`   | The list                                                                     |
  | existing add, update, CSV append                           | Gain the 409 `do_not_store` / `confirmDoNotStore` behaviour                  |

- **Audit:** bulk deletes, retention changes and sweeps, and do-not-store changes are `state_change` with `source: 'records'`. Payloads carry ids, counts and table names, never row values or list entries (the audit log is out of erasure scope, so it mustn't collect more PII). Sweeps are audited with role `system`.
- **Retention sweep:** `RecordsRetentionService` in tcp-server, spend-resume pattern, hourly const; tests call `sweep()` directly. Date fields are guarded with a `^\d{4}-\d{2}-\d{2}` check before casting.
- **Web UI:**
  - `RecordSheet` gets AG Grid multi-row selection (checkbox column; the header box selects the filtered rows). `TableView`'s **Download** and **Delete** act on the selection when there is one (labels show the count), else the whole table / the focused row as now. Delete asks first and offers to download the rows.
  - **Retention…** in `RecordTableActions` opens a dialog (days; from: "last update" or a date field). The sheet header says "Rows deleted N days after …".
  - New **Data protection** tab on the company page (`CompanyTabs.tsx`): the ICO note and link; **Search records** (input + button; results as one `TableView` per table in a "rows subset" mode, with Export selected / Delete selected across them); **Do-not-store list** (a `RecordSheet` over a fixed definition `value, note, added by, added`, quick filter, add dialog, cell edit, delete selected). Adding an entry offers "Search records for this".
  - Warn-and-allow: a `ConfirmDialog` naming the matching fields, on add, edit and CSV append.
- **Out of scope:** an office entry for the page; CLI verbs for search and the list; retention set by agents; clearing single fields. Each goes in `outstanding-issues.md` with a condition.
