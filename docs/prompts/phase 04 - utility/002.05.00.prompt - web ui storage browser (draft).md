Create a plan to implement a storage browser. Challenge any part of this plan during planning - the goal is to create an intuitive, simple, accessible, user inteface to allow the user to see, browse, download, delete, and upload items in the document storage.

Mock screenshots for the plan, to illustrate the new UI, showing where it will appear, and how it will look. (Outline / sketch quality is fine - this doesn't need to be a hi-def prototype.) Mock screenshots for each proposed option (if more than one). There's a `docs/prompts/phase 04 - utility/illustrations` directory to hold these images. Items are numerically numbered there (`XX.`).

We may need additional libraries to support file tree, and previews. Follow the usual guidance to identify appropriate libraries.

We'll keep a way to visit the document storage server itself - ie. retain the direct links that allow the user to visit the S3 service web interface.

Features:

- Ability to show file tree or file tree + preview (if a single file is selected)
- Component can work inside a dialog, tab, or 'main' section of a 'menu/main' layout
- File tree (starting at specific directories, eg. task outputs, or company resources, or (in other parts of the UI) role/company knowledge directories)
- Preview
  - if there's a supporting library that covers common formats, images, markdown, CSV, PDF, etc.
  - Readonly preview - this isn't for editing files
- Navigate, select, limited to the file tree starting at the route specified (ie. no way to escape that tree)
  - File tree and files retrieved through the S3 interface to Silo (or any other S3 compatible storage service)
    - TBD: Should the backend implement routes to support this, and shield the frontend from the S3 interface, or should the frontend retrieve and use an S3 token from the backend, or should it hold sufficient credentials to do this itself and manage the entire S3 connection directly? Make a recommendation during planning.
- Select and download (individual items / groups of items / directories)
- Upload file / directory / multiple files
- Drag and drop to upload
- Ability to show some directories as read-only
  - There are things that need to happen when files are uploaded to certain directories (eg. if a user uploaded into a role knowledge directory, they might assume that the file would be converted to OKF and the role's knowledge would be automatically re-indexed)
  - ...so for this work we probably ought to mark knowledge directories as read only
    - in future uploads from a file browser in role editing (provided we can detect a successful upload and initiate conversion, followed by re-indexing) could be permitted
    - those uploads should come with a confirmation dialog, indicating that if the user proceeds, the file will be converted to open knowledge format, and that the original will not be stored

If there's a good future prompt to cover the management of uploads where actions are required, move the knowledge upload (and any other cases like this) to there. If not, perhaps we need to create an additional upcoming prompt for uploads / deletions that must trigger backend activity.
