The web client retries every failed query the same way, whatever went wrong. Please create a plan for one shared retry policy that retries only the failures where trying again can help.

## What happens today

- **Every request already goes through shared code.** Queries and mutations call `unwrap` (or `expectAccepted`) in `apps/frontend/tcp-frontend/src/api/client.ts`. Uploads and downloads use `send`, in the same file. A failure becomes an `ApiError` with the HTTP status, or status `0` when the request never landed (`networkError`).
- **But retries are decided somewhere else.** `main.tsx` creates `new QueryClient()` with no options, so TanStack's default applies to every query: 3 retries with back-off (about 1 s, 2 s, then 4 s), for any error. That includes 400, 401, 403, 404, 409 and 422, which give the same answer however often they're asked.
- **Mutations aren't retried** (TanStack's default for mutations is 0). Keep it that way for anything that isn't safe to repeat.
- **What it costs.**
  - A 404 for something just deleted is retried for about 7 seconds. In 002.00, that made "Delete table" seem to hang: the reload after a bulk change waited for the deleted table to be fetched again.
  - A 403 or a 404 page shows a loading state for seconds before it shows the error.
- **The workaround to remove.** 002.00 made `useDropRecordTable` (`src/api/hooks.ts`, `useDropAndForget`) forget the dropped table's queries before the reload. With this policy in place, decide whether that workaround is still needed, and remove it if not.

## What to build

One policy, written once, beside `unwrap` in `client.ts`, and used as the `QueryClient`'s `defaultOptions.queries.retry` (and `retryDelay`) in `main.tsx` and in `test-support/render-app.tsx`.

A starting point to challenge:

| Failure                                  | Retry?                   | Why                                                              |
| ---------------------------------------- | ------------------------ | ---------------------------------------------------------------- |
| Network error (status `0`)               | Yes, with back-off       | The server or the connection may come back                       |
| 502, 503, 504                            | Yes, with back-off       | A proxy or a restarting service; often brief                     |
| 500                                      | Once, perhaps            | Usually a bug that won't change, but sometimes a transient fault |
| 429                                      | Yes, after `Retry-After` | The server says when; respect it, and cap the wait               |
| 401                                      | No                       | `client.ts` already runs the sign-in redirect policy             |
| Other 4xx (400, 403, 404, 409, 410, 422) | No                       | The same request gets the same answer                            |

Things to decide in the plan:

- **Where `Retry-After` comes from.** `ApiError` doesn't keep the response headers today. Either carry the parsed value on the error, or don't support it yet and say so.
- **Mutations.** Leave them unretried. If one kind is safe to repeat (a `GET`-like read done as a `POST`, or an idempotent `PUT`/`DELETE`), make retrying opt-in per hook, never the default.
- **Polling queries.** `useKnowledgeStatus` and `useShutdownStatus` set their own `refetchInterval`. Check how the policy combines with them. `useShutdownStatus` keeps polling while the server is down on purpose, and must keep doing so.
- **The event stream is separate.** `src/events/connect.ts` reconnects the company stream itself (ADR-025). Leave it out of this policy unless there's a reason to join them.
- **What the person sees.** When a query is retrying, the view should not look stuck. Check that `LoadingState` and `ErrorState` still read correctly, and that a final failure is announced once (ADR-027), not once per attempt.

## Testing

- **Unit tests for the policy itself:** each status in the table above, the attempt limit, and the back-off delays, including a `Retry-After` header if it's supported.
- **One integration-style test through a real `QueryClient` with the default options.** Most component tests turn retries off (`retry: false`), so they can't catch this. Assert that a 404 settles straight away and a 503 is retried.
- **The browser tier is the real check.** `records.spec.ts`' "a table is cleared, then deleted" found the original problem. It must still pass with the 002.00 workaround removed, if the plan removes it.
