**Build this after 002.05.** 002.05 built the storage browser, and made `resources/` the only folder it can change. Knowledge was left read-only there on purpose: knowledge has its own upload door, which converts the file and reindexes. This prompt lets people upload knowledge from the browser, through that same door.

## What 002.05 left

- **Knowledge is read-only in the browser.** Data → Documents shows `knowledge/` locked. The only way to add knowledge in the web client is the Admin tab's knowledge panels (`KnowledgePanel.tsx`).
- **The server refuses writes outside `resources/`.** `isWritable` in `apps/backend/apps/tcp-server/src/api/company-storage-paths.ts` decides. The web client mirrors it as `isWritablePath` in `src/components/StorageBrowser/paths.ts`, which only decides what to show locked. Do not widen `isWritable`: a direct write into `knowledge/` would skip the conversion.
- **Knowledge uploads convert.** `POST /api/role/:roleId/knowledge` and `POST /api/company/:companyId/knowledge` run `knowledge-conversion.ts`: a `.docx` or `.pdf` becomes OKF Markdown and **the original is not kept**. Writing the file triggers a reindex of the scope, so nothing extra is needed to keep the index current.

## What to build

Please create a plan to let people upload into `knowledge/` from the storage browser.

- **In Data → Documents,** an Upload into `knowledge/shared/` and `knowledge/{role_slug}/` goes to the knowledge routes above, not to the storage upload route. The target folder decides which route and which scope.
- **In the role dialog's Knowledge tab,** a storage browser rooted at the role's knowledge folder (`knowledge/{role_slug}/`), beside or in place of the current list.
- **Behind a confirmation.** Before the upload, a `ConfirmDialog` says the file will be converted to OKF Markdown and the original won't be kept. Say it once per upload, not once per file.
- **Reindexing happens by itself.** Don't add a rebuild call. Check that the browser and the knowledge status both show the new document once indexing has run.

Pieces to reuse:

- `StorageBrowser` and `useUploads` (`src/components/StorageBrowser/`). `useUploads` takes the target folder and posts each file. The plan should decide whether it gains an "upload through" option or whether knowledge gets its own small variant.
- `isWritablePath` in `src/components/StorageBrowser/paths.ts`. Knowledge needs a third state: not writable like the rest, but uploadable through a different route. Keep the rule in one place on each side, and keep the server as the authority.
- The knowledge hooks in `src/api/hooks.ts`, which already handle the conversion errors and the 50 MB limit.

## Other folders whose writes need backend work

Knowledge is the first, but check every folder the browser could write to for the same trap: a file dropped in the folder does nothing unless something else is told.

- **Task materials.** Agents read a task's materials from the task row's list, not from the `materials/` folder. A file dropped into `tasks/{id}/materials/` is ignored today. `POST /api/task/:id/materials` is the real door.
- Decide for each folder you open up: which existing route is the door, what it does besides storing the file, and what the confirmation says.

## Notes for the plan

- **Which role slug?** A browser at the company root shows several role folders. The plan should say what happens when a file is dropped on `knowledge/` itself, rather than a scope.
- **Names.** Converted files get a new name (`.md`). Say what the browser shows after a `.docx` upload, and what the "Replace?" question means when the converted name already exists.
- **Permissions.** Any member can upload knowledge today, as in the Admin tab (see "Any member can delete roles and knowledge" in [outstanding-issues.md](../../outstanding-issues.md)). Don't widen that.

Accessibility is very important: the confirmation must be an `alertdialog` with focus handled as in ADR-027, and the upload result must be announced on the `storage` channel.
