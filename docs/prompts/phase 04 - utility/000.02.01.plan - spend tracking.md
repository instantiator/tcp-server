## Context

Nothing records token usage today. A remote API bill could eat a company's profit, and `AGENT_ITERATIONS` only caps loop length. This prompt records tokens for every LLM call and adds optional **per-provider caps at application level**. Each cap can raise notifications at thresholds and take an action when it is reached. The prompt's notifications are built here as a small in-app system, which 003.03 later extends to push delivery.

### Scope changes agreed with the user (they challenge the prompt)

- **Caps are per provider, at application level only.** There are no company caps and no "% of app cap" shares, so the prompt's "a % cap is ignored without an app cap" warning goes away. Threshold notifications are unchanged: each cap's `notifyAt` percentages still raise `warning` notifications, and reaching the cap raises an `error`. A home install that only uses LM Studio sets no cap and never trips one. Company caps go to `outstanding-issues.md`.
- **Unit:** total tokens. Input and output are still recorded separately.
- **An explicit start or resume exempts that task until it ends.** Otherwise the gate would pause it again after its next LLM call.
- **The TUI is skipped.** 002.07 retires it; the CLI and web cover everything.

### Answers to the prompt's questions

- **Pro-plan defaults.** Consumer plans (Claude Pro/Max, ChatGPT Plus, Gemini subscriptions) can't be used through API keys. API keys are pay-as-you-go. Plan limits aren't published as token counts, and they change. Provider APIs expose per-minute rate-limit headers, and with an _admin_ key, usage and cost reports (Anthropic Admin API, OpenAI Usage/Costs API); Gemini has nothing equivalent. So there is **no provider special-casing**: the user enters numbers, and the `"5h"` window imitates a stint. **Security advice:** our cap can overshoot by however many calls are in flight. Also set a hard spend limit in each provider's console as the real backstop. The docs will say this.
- **A telemetry standard.** The OpenTelemetry GenAI semantic conventions define `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens` and the `gen_ai.client.token.usage` metric (with attribute `gen_ai.token.type`). Those conventions are still at "Development" status. We name our fields to map 1:1 (`inputTokens`, `outputTokens`, `provider`, `model`) and add **no OTel dependency now**. An OTLP exporter goes to outstanding-issues, with the condition "when an operator wants usage in an external dashboard".
- **Conflicts resolved:**
  - _"Non-urgent work"_ (in usage.gaps): there is no urgency concept, so the rule becomes "explicit user actions always run; automatic dispatch is gated".
  - _"Finish running tasks, then don't start new ones automatically"_: today every task start is explicit, so this action blocks nothing yet. It switches the web's "start now" default off, and 004.01 must honour it (guidance carried forward).
  - _"Resume a company"_ resumes that company's cap-paused agents and exempts their tasks. It does **not** lift the cap for other companies.
  - _Chats_ are always explicit: their tokens are counted, but chats are never gated.

## Design

### Recording — one hook, one table

- tcp-agent puts `usage: { inputTokens, outputTokens }` into the `llm_response` audit payload. It reads this from `on_chat_model_end` `event.data.output.usage_metadata` in `stream-event-mapper.ts:93`. Context compaction (`context-compactor.service.ts:97,125`) adds the same `usage` to its `compaction` audit payload. Chat already goes through the same mapper in tcp-server.
- In tcp-server, `AuditService.write` (`audit/audit.service.ts`) calls `UsageService.record(event)` for any event whose payload has `usage`. That inserts one **insert-only** `token_usage` row with columns `id, companyId, taskId?, agentId?, provider, model, inputTokens, outputTokens, createdAt`, indexed on `(provider, createdAt)` and `(companyId, createdAt)`.
- Insert-only avoids cross-DB upserts with nullable keys. Per-task totals are `GROUP BY taskId`. The "per 5-minute period" series is computed when reading, in the query (`floor(epoch/300)`). Only active buckets exist.
  - `// ponytail:` cap checks `SUM` over a window. That's fine to around 1M rows; add a rollup table if it gets slow.
- **No usage reported:** a provider that sends no `usage_metadata` records nothing. The first time this happens, it raises one `warning` notification: "<provider> reports no token usage; caps can't be enforced". Stage 2 checks whether stub-llm and LM Studio need `stream_options.include_usage` (`ChatOpenAI` `streamUsage`, `llm-factory.ts:28`).
- **Not counted** (goes to outstanding-issues): embeddings, because LangChain's `OpenAIEmbeddings` exposes no usage, and the model-check probes.

### Configuration — `.env` only

`SPEND_CAPS` (tcp-server only) is a JSON object keyed by catalogue provider id (`PROVIDER_CATALOGUE`, `libs/tcp-shared/src/llm/provider-catalogue.ts`):

```json
{
  "anthropic": {
    "limits": [
      { "tokens": 2000000, "per": "5h" },
      { "tokens": 20000000, "per": "week" }
    ],
    "notifyAt": [50, 80],
    "action": "pause"
  }
}
```

- `per`: `month` (00:00 UTC on the 1st), `week` (Monday 00:00 UTC), `day` (00:00 UTC), or `"<N>h"`. An `<N>h` stint starts at the first use after the previous stint ended.
  - `// ponytail:` UTC only. Add a timezone setting when someone asks.
- `notifyAt`: percentages below 100. The default is `[80]`. Reaching 100% always notifies.
- `action`: `pause` (the default), `finish-agents` or `finish-tasks`.
- Validated with Joi in `apps/backend/apps/tcp-server/src/config/config.schema.ts`: parse the JSON, then use `Joi.object().pattern(<catalogue ids>, …)`. An unknown provider or bad shape fails boot.
- Several `openai-compatible` endpoints share one key. That limitation is documented.

### Cap state and evaluation

- The `spend_cap_state` table: `provider` PK, `windowStarts` jsonb (stint anchors), `reachedUntil` (Date or null: the end of the reached window), `dismissal` (`none`, `until-reset` or `indefinite`), `action` (the reached cap's action, so the agent's gate can apply its scope; _added during stage 1_), `updatedAt`. This table is the single source of truth, read by both apps.
- Pure maths lives in `apps/backend/apps/tcp-server/src/spend/` (`windowFor(per, now, stintStart?)` and `evaluateLimit(limit, used, notifyAt)`). _Changed in stage 2: only tcp-server uses it, so it isn't in the shared library. Thresholds are deduplicated by the notification `dedupeKey`, not by the maths._
- `SpendCapService` (tcp-server) runs after each recorded row for that provider. It is serialised per provider with an in-process promise chain, and the ceiling is noted in a `ponytail:` comment (single tcp-server instance). It does three things:
  1. Sums usage per limit window.
  2. Creates threshold notifications. Duplicates are prevented by a unique `dedupeKey` (`cap:<provider>:<per>:<windowStart>:<pct>`), and an insert that collides is ignored.
  3. When a limit is reached and not dismissed, sets `reachedUntil` and sends an `error` notification.
- Reset sweep: a `setInterval(...).unref()` every 60 seconds, the same pattern as `knowledge-reindex.service.ts:129`. It clears `reachedUntil` once it has passed and clears `until-reset` dismissals. It then **auto-resumes the agents it paused**, the ones with `pauseReason: 'spend_cap'`, and sends an `info` notification. _Decision to confirm:_ auto-resume on reset. A 5-hour stint cap is useless without it. Unlike a shutdown drain, the user configured this cap.

### Enforcement — one gate, in tcp-agent

- Add `'spend_cap'` to `PauseReason` (`TcpAgent.model.ts:45`). Add `spendCapExempt boolean default false` to `TcpTask`.
- **The gate:** before each LLM call, at the iteration check in `run-supervised-graph.ts:187` via a hook, the agent loop reads `spend_cap_state` for its resolved provider. One PK lookup is negligible. The gate trips when **all** of these hold:
  - `reachedUntil > now`
  - `dismissal = none`
  - the task is not `spendCapExempt`
  - the mode is not `chat`
  - the action's scope applies:
    - `pause`: every iteration.
    - `finish-agents`: only the first iteration of a `start` job.
    - `finish-tasks`: never in the agent; it only changes the UI default and 004.01.
- **When it trips:** the agent pauses itself with reason `spend_cap`, using the same exit path as the terminal-status check, with the checkpoint intact. It spends no tokens, and it resumes exactly from that checkpoint. In-flight calls finish, which is the overshoot already noted.
- **Explicit actions set `spendCapExempt = true`:**
  - `POST /api/task/:id/start`, if any cap is reached.
  - New `POST /api/task/:id/resume`: resumes the task's agents paused with reason `spend_cap` or `shutdown`, via `AgentOrchestrationService.resumeAgent`.
  - New `POST /api/company/:slug/resume`: does the same for every task in the company.
- **Admin-only endpoints** (`@AdminOnly`), because they lift spend protection for every company:
  - `POST /api/spend/caps/:provider/dismiss {until: 'reset' | 'indefinite'}` — clears the gate and resumes the agents with reason `spend_cap`.
  - `POST /api/spend/caps/:provider/restore`.

### Notifications

- The `notification` table: `id`, `severity` (`info`, `warning` or `error`), `kind` (`spend_threshold`, `spend_reached`, `spend_reset`, `spend_untracked`), `message`, `params` jsonb, `dedupeKey` unique nullable, `createdAt`, `dismissedAt`. It is application-wide and dismissed for everyone. It has no `companyId` column; 003.03 adds one if it needs it.
- `GET /api/notifications?includeDismissed=` and `POST /api/notifications/:id/dismiss` are `@NoCompanyScope`, open to any signed-in user.
- **SSE:** each create or dismiss writes a `state_change` audit row with entity `notification`. `AuditEventPublisher` fans it out to **every company channel**, so there is no new stream (MAX_STREAMS and the stream budget are unchanged). Add `notification` to `COMPANY_CHANNEL_ENTITIES` (`events/audit-event-publisher.service.ts:32`), `EVENT_ENTITIES` (frontend `src/api/query-keys.ts:34`) and `CompanyPrimingService.prime`. A spend-state change publishes entity `spend` the same way, so the bars update live.

### Reporting

- `GET /api/spend` (`@NoCompanyScope`) returns, per provider: limits, used, percent, window start, next reset, action, dismissal and reached. It also returns overall totals since tracking began.
- `GET /api/company/:slug/spend` (`@CompanyScope`) returns the company's totals per provider, per-task totals, and the 5-minute series for the last 24 hours.

### CLI (`apps/backend/apps/tcp-cli`, using the `commands/` + `lib/<area>/*.action.ts` pattern)

| Command                                   | What it does                                                                                 |
| ----------------------------------------- | -------------------------------------------------------------------------------------------- |
| `usage [--company <slug>]`                | Prints the caps and progress. With `--company`, adds per-task usage and the 5-minute series. |
| `notifications [--all]`                   | Lists notifications.                                                                         |
| `dismiss-notification <id>`               | Dismisses one notification.                                                                  |
| `dismiss-cap <provider> [--indefinitely]` | Lifts a cap until its reset, or indefinitely.                                                |
| `restore-cap <provider>`                  | Restores a dismissed cap.                                                                    |
| `resume-task <id>`                        | Resumes a paused task.                                                                       |
| `resume-company <slug>`                   | Resumes every paused task in a company.                                                      |

### Web UI (`apps/frontend/tcp-frontend`)

- **Breadcrumbs** (`components/Breadcrumbs/Breadcrumbs.tsx`): each crumb gets a thin RAC `Meter` under its text.
  - The "companies" crumb shows the provider with the highest percentage. Its tooltip lists every provider: "X% of Y tokens per <per>, since <start> · <action text> · Next reset: <date>". With no caps, the bar is full and reads "X tokens used since <tracking began>".
  - The company crumb has no cap, so it shows a full bar: "X tokens used by this company since <start>".
  - The tooltip trigger must be focusable and announce through `aria-valuetext`. ADR-026/027 are checked first.
- **Notifications:**
  - New arrivals use the existing `components/Notification/Notification.tsx` toast. Its `durableHref` points to a new **Notifications** tab among the company page's force-mounted activity tabs, which lists them with a Dismiss button.
  - A `spend_reached` row also offers **Resume this company** (company resume) and, for admins, **Lift cap until reset**.
- **"Start now":** in `CreateTaskDialog.tsx:105`, it defaults to `false` while any cap is reached.
- **Deferred to 000.04** (carried forward): a Resume button in the task dialog that calls `POST /api/task/:id/resume`.

### - [x] 4. Cap evaluation and enforcement — Opus

- **Brief:** as in Design → Cap state and Design → Enforcement. Add `SpendCapService`, the reset sweep, the gate hook in `run-supervised-graph.ts`, `PauseReason 'spend_cap'`, task exemption on start/resume, and the task, company, dismiss and restore endpoints. Reuse `AgentOrchestrationService.resumeAgent` and the `SystemShutdownService.assertAccepting` guard ordering.
- **Tests:**
  - Unit: each action's gate scope; an exempt task passes; chat passes; a dismissed cap passes.
  - Two concurrent records crossing 100% produce one `spend_reached` notification.
  - The sweep resumes only agents paused with reason `spend_cap`.
  - e2e: a non-admin gets 403 on dismiss/restore.
- **Gate:** `check.sh --fast`; unit, e2e and integration tiers.

- **As built:**
  - **The gate also runs before compaction.** `holdSpending` is checked at the top of every runner iteration, before `checkBudget`, so a held run spends nothing at all. It lives in `apps/backend/apps/tcp-agent/src/agent/spend-gate.service.ts`; tcp-agent now registers `SpendCapState` and `TcpTask`.
  - **Resume trap found and handled.** A resume with no message is treated as a fresh start, which rebuilds the initial state. `resumeAgent` now sends a spend-cap continuation prompt, but only when the agent has an `llm_response` audit row. An agent held before its first call has no checkpoint, so it restarts instead.
  - **Threshold notifications are attempted only when a threshold is newly crossed** by the latest row. The `dedupeKey` still guards races. This avoids a duplicate-key error in Postgres on every later call.
  - **Untracked providers.** When an `llm_response` has a known provider but no usage, the payload carries `untrackedProvider`. `UsageService` warns once per provider per process, and the notification is deduplicated forever.
  - **Module layout.** `UsageService` moved into a new `SpendModule` with `SpendCapService`; `AuditModule` imports it. `SpendResumeService` (reset sweep, dismissal and explicit resumes) and `SpendController` sit in the API layer, because resuming needs the agent queue.
  - **Responses.** Task and company resume return `{ resumed }`, the number of agents a resume was requested for. Dismiss and restore return the `SpendCapState` row.
  - **Auto-resume on reset is implemented as planned.** It resumes every `spend_cap`-paused agent. Any whose provider is still capped re-pause at their first check, spending nothing.
