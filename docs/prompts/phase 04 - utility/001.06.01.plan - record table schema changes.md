## Context

Once a record table exists, nobody can change its columns. On the dev server an agent made `feedings` keyed on `(feeding_date, feeding_time)` with no `animal` column. Nothing can say which animal was fed, and feeding two animals at once is refused as a duplicate. This plan lets agents and people add, rename and delete columns, and change the primary key, safely.

### What exploration found

- **Storage** (`libs/tcp-shared/src/records/`; migrations in `tcp-mcp-records/src/migrations/`):
  - `record_table.schema` is a closed JSON Schema (`TableSchema`, `records.types.ts:37`), alongside `primaryKey` and `uniqueKeys` (jsonb) and `retention` (`{days, from}`, where `from` is `'updated'` or a date field name).
  - Rows keep fields in `record.data` (jsonb). `id`, `version` and the timestamps are real columns, out of reach of a schema change.
  - Keys are enforced by `record_key (tableId, keyName, keyValue)`. `keyName = fields.join(',')` and `keyValue = JSON.stringify(values)` (`table-schema.ts:193-200`). **Renaming a key field is one `UPDATE record_key SET "keyName"`. The values don't change.**
  - `fieldOrder` (`field-order.ts:7`) is the key first, then alphabetical. It isn't stored, so new and renamed columns sort themselves.
- **Concurrency gap:** every write reads the table definition **outside** its transaction, with no lock on `record_table` (`records.service.ts` `insert`:278, `update`:314, `insertMany`:578). A rename committed between that read and the write would store a record under the old field name.
- **Things that hold a field name:**
  - `primaryKey` and `uniqueKeys`;
  - `record_key.keyName`;
  - `retention.from` (the sweep reads `data ->> from`, so a stale name silently deletes nothing);
  - the client undo stack (`useUndoStack.ts`, `rowId:field`).

  The do-not-store list and search aren't keyed by field.

- **Agent tools:**
  - `records-tools.service.ts` uses `registerTool` with zod shapes. Descriptions are in `tools.jsonc` and `records-tool-descriptions.ts`; prompts are in `prompts.jsonc` and `records-prompts.ts`.
  - `do_not_store` is the precedent for the placebo: it returns `recordsPrompts.do_not_store_ask_user`.
  - Write tools are listed in `RECORDS_WRITE_TOOLS` (`libs/tcp-shared/src/prompts/mode-tools.ts:28`). The audit helper is `change()` (:413).
- **People's API:**
  - `records.controller.ts` with `records-api.service.ts`, whose `changed()` audit is at :487.
  - DTOs are in `dto/records.dto.ts`. `PUT tables/:table/retention`, which returns the definition, is the closest model.
  - Do-not-store confirmation uses the `?confirmDoNotStore` query parameter (:68).
- **Live:**
  - Any `source:'records'` `state_change` already reaches the company stream (`toRecordSignal`).
  - The sheet compares rows only (`useLiveRecordTableChanges`, `hooks.ts:989`). It has no idea of a schema change.
- **Web UI:**
  - The More menu is `RecordTableActions.tsx`, and clear/drop use an inline confirmation `Dialog` with "Download a copy first".
  - `RetentionDialog.tsx` is the form-dialog template, and `AddRowDialog.tsx` with `parseFieldInput` handles typed values.
  - Bulk mutations go through `useBulkRecordMutation` (`hooks.ts:862`).
  - Strings live in `src/strings.ts` as `records.<feature>.<part>`.
- **CLI:** the records commands follow `commands/export-table.ts` with `lib/records/export-table.action.ts` (`runCommand`, `resolveCompanyId`, `apiOptions`).

### Decisions agreed with you (2026-10-16)

- **Key changes are in scope** for agents and people, with strong but short agent guidance and specific feedback on bad values.
- **Agents may only widen a key** (add fields), which can never clash or merge. Narrowing returns advice to ask a user. People can do both.
- **Key fields can be renamed by agents and people.** That is one cheap `keyName` update.
- **A key field can't be deleted by anyone.** It has to be taken out of the key first.
- **People use a "Columns…" dialog** from the More menu, not header menus.
- **The CLI gets the same operations.**
- **One commit per stage.**

### Design (object at approval if wrong)

**Operations**, in `RecordsService.alterTable(companyId, table, change)`. `change` is a discriminated union in `records.types.ts`:

| `op`              | Input                                                                              | Effect                                                                                                                                                       |
| ----------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `add_column`      | `column`, `type`, `format?` (`date` only), `description?`, `default?`, `required?` | Adds it to `properties`. Given `default`, every row gets the default; otherwise rows are left without it (blank).                                            |
| `rename_column`   | `column`, `newName`                                                                | Renames it in `properties`, `required`, `primaryKey`, `uniqueKeys`, `retention.from`, every row's `data`, and the `record_key.keyName` of each key it is in. |
| `delete_column`   | `column`                                                                           | Removes it from `properties`, `required` and every row's `data`.                                                                                             |
| `set_primary_key` | `fields`                                                                           | Replaces `primaryKey`, makes those fields `required`, deletes the old key's `record_key` rows and writes new ones from every record.                         |

**Rules.** Each is a `RecordsError` that says what to do instead:

- **Add:**
  - The name is valid and not taken.
  - The table stays at 50 fields or fewer.
  - `type` is one of the four.
  - `default` must fit the new field's schema (checked with the strict Ajv).
  - `required: true` only with a `default`, or when the table is empty.
  - A string default is checked against the do-not-store list. Agents are refused; people confirm with `?confirmDoNotStore`, as with rows.
  - With a default, refuse if the largest row plus the default would exceed 64 KB.
- **Rename:** the column exists; the new name is valid, not taken, and not equal to the old name.
- **Delete:**
  - Refused for a primary or unique key field ("take it out of the key first").
  - Refused for the `retention.from` field ("change retention first").
- **Set key:**
  - Every field exists, is `string` or `integer`, and is not repeated.
  - The key differs from the current one and from every unique key.
  - Every record must have a value for every key field. If not: "N records have no `animal` — fill it in with `update`, then try again."
  - No two records may share the new key. Before writing, list up to 3 clashing value sets and the clash count.
  - For agents (`allowNarrow: false`), the new key must contain every current key field. Otherwise: "Narrowing a key can make different records count as the same one. Ask a user with `request_user_input` to change the key in the sheet; say which fields and why."
- Changing unique keys and retyping a column stay out of scope. Both go to `outstanding-issues.md` with conditions.

**Rewriting rows.**

- Every rewritten row gets `version + 1`, so open sheets lock it and stale saves get 409.
- `updatedAt` is **not** touched: a column change isn't a data edit, and it must not reset retention clocks or the "Updated" column.
- Rows are rewritten in SQL: `data || jsonb_build_object(...)` for an add, `data - $old || jsonb_build_object($new, data -> $old) WHERE data ? $old` for a rename, `data - $col` for a delete.
- Set key reads every row in the transaction and computes `keyValue` in JS, because Postgres jsonb text formatting differs from `JSON.stringify`. Add a `// ponytail:` comment: fine to the 10k-row scale, batch-insert if it gets slow.

**Concurrency.**

- `alterTable` opens a transaction, then `SELECT … FROM record_table … FOR UPDATE`, and re-reads the definition under the lock.
- Every write path reads its definition **inside** its transaction with `FOR SHARE`, before any row lock. That covers `insert`, `update`, `insertMany`, `delete` and `deleteRows`.
- So writes don't block each other, but an alter waits for in-flight writes, and writes wait for an alter. Lock order is always table then rows, so there are no deadlocks.
- The private `table(manager, companyId, name, lock?: 'share' | 'update')` gains the lock parameter.
- `insert`'s pre-transaction `findByKeys` fast path stays, re-checked inside the transaction.

**Audit.** A `state_change` with `action: 'alter_table'`, `op`, `table`, `before` and `after` definitions, and `rewritten` (the row count).

- **No row values, and no `default` value.** This follows the 001.04 rule: the audit log outlives an erasure.
- The audit is written from tcp-mcp-records (role `agent`) and tcp-server (role `user`, `userId`).
- The existing `toRecordSignal` carries it to the company stream unchanged.

**Agent tool: one `alter_table`** (not four, to save context).

- Arguments: `table`, `action` (enum of the four ops), and the optional `column`, `new_name`, `type`, `format`, `description`, `default`, `required`, `fields`. zod checks per action happen in the handler, and give correctable errors.
- `action: 'delete_column'` changes nothing and writes no `state_change`. It returns `recordsPrompts.delete_column_ask_user` naming the column. It tells the agent to use `request_user_input` to ask a person to delete it in the sheet, and to say why. A future 003.01 note becomes an approval request.
- A successful call returns the new definition (the `describe_table` shape) plus `rewritten`.
- The description text (Opus drafts it in stage 2, kept to about 120 words) covers:
  - add a column rather than make a new table;
  - existing rows are blank unless you give a `default`;
  - to add a field to the key: add it, fill it in on every record with `update`, then `set_primary_key`;
  - the key is the smallest set of fields that differs for every real thing the table records;
  - never key on a free-text name, an amount, or a time something was recorded;
  - delete and narrowing a key go to a person.
- `alter_table` joins `RECORDS_WRITE_TOOLS`, and the `describe_server` text lists it.
- Measure the footprint before and after with the estimator spec. Report the delta.

**People's API** (`records.controller.ts`). Each returns `RecordTableDefinitionDto` and audits through `changed()`:

- `POST tables/:table/columns` takes `AddColumnDto`, plus `?confirmDoNotStore`.
- `PATCH tables/:table/columns/:column` takes `{ newName }`.
- `DELETE tables/:table/columns/:column`.
- `PUT tables/:table/primary-key` takes `{ fields }`, with `allowNarrow: true`.

DTOs need class-validator decorators (the whitelist strips anything without them). Regenerate `schema.d.ts` with `start-deployment.sh --rebuild` before `api:generate`.

**Web UI.**

- **The Columns dialog** (`components/RecordSheet/ColumnsDialog.tsx`, modelled on `RetentionDialog`) opens from a new "Columns…" item in `RecordTableActions`. It is only offered when `definition` is passed.
- **Column list:**
  - The list is in `fieldOrder`. Each row shows the name, a type in words, and "key" / "required" as text.
  - Each row has **Rename** and **Delete** buttons.
  - A key field's Delete is disabled, and the row says why in visible text ("In the key — change the key first"), not just a disabled state.
- **Rename** is an inline `TextField` form.
- **Delete** uses the clear/drop confirmation pattern: an `alertdialog` with the count of records holding a value, "Download a copy first", and "No" focused first.
- **Add column form:**
  - name;
  - type as a `RadioGroup` (Text, Number, Whole number, Yes/no, Date);
  - optional default, parsed with `parseFieldInput`;
  - a Required checkbox, enabled only with a default or an empty table, with a description saying why;
  - a do-not-store confirm on 409, copying `AddRowDialog`'s flow.
- **Key section:** "Key: feeding_date, feeding_time" and a "Change key…" `CheckboxGroup` of the eligible fields. Server errors, such as missing values or clashes, go in `tcp-field__error`.
- Mutations go through `useBulkRecordMutation`, so they forget `latest` and invalidate `['record']`. On success the sheet also clears its undo stack. Each change has an announcement: `records.announce.columnAdded` / `columnRenamed` / `columnDeleted` / `keyChanged`.
- **Live:**
  - `useLiveRecordTableChanges` gains `columnsChanged`. It is true when the latest copy's `schema`, `primaryKey` or `uniqueKeys` differ from what's shown (compared with `JSON.stringify` after sorting the keys of `properties`).
  - `OutOfDateNotice` shows "This table's columns were changed elsewhere. Reload to see them."
  - The sheet is made fully read-only, as for `dropped`, because an edit under an old column name would be refused anyway.
  - The search view gets the same per group (`useLiveRecordSearchChanges`).

**CLI.** `tcp-cli alter-table --table <t> <op>`, with `op` one of `add-column`, `rename-column`, `delete-column` or `set-key`. The flags are `--column`, `--new-name`, `--type`, `--format`, `--default`, `--required`, `--fields a,b` and `--confirm-do-not-store`. `delete-column` needs `--yes`. It calls the API routes above and prints the new definition as JSON. It follows `export-table`, and goes in the CLI docs.

### Changed while implementing stage 1 (2026-10-16)

- **No `narrow_key_ask_user` prompt.** The shared service's narrowing refusal carries the advice itself, naming `request_user_input`, as its other messages name `update` and `list_tables`. Stage 2 just passes it through.
- **`deleteRows` and `clearTable` take no table lock.** They act on ids and never read the schema, so a column change can't make them write a wrong field.
- **`insert` has no fast path outside its transaction.** It reads the definition, checks the record and looks for an existing key all under the share lock.
- **Set key writes its key rows with one `unnest` insert**, not a row at a time. It still reads every record into memory (`// ponytail:` in `rekey`).
- **`AlterResult` carries `before` too**, so callers can audit both definitions without reading the table twice.

### Changed while implementing stage 2 (2026-10-16)

- **Opus wrote the whole stage.** The handler was about 60 lines, so a Sonnet brief would have been as long as the code.
- **`alter_table` costs about 460 tokens a turn.** Its schema is 1,832 characters; the records server goes from about 10,700 to 12,500 characters. About 800 of those characters are the identity arguments every tool carries. The guidance text is about 620.
- **The delete placebo checks the column first** (`checkDelete`, now exported). Asking to delete a key column gets the same "take it out of the key first" error a person would, not advice to ask a user.

### Changed while implementing stages 4 and 5 (2026-10-16)

- **A column change closes the dialog.** It announces the change, and focus goes back to the More menu. That is the one stable place, rather than a list that has just changed under the reader. It also reuses the sheet's Reload (`onChanged`), so the undo stack, which names old columns, is cleared too.
- **Columns changed elsewhere lock the whole sheet.** `columnsChanged` compares schema, primary key and unique keys, ignoring jsonb key order. Retention and purpose don't count. The search view locks only the affected table's group.
- **The key form doesn't use `isInvalid`.** React Aria's native validation would then block the next submit until the ticks changed, though the fix (filling in rows) may be elsewhere. The server's reason is linked to the group with `aria-describedby` instead.

### Changed while implementing stage 6 (2026-10-16)

- **The browser tests ran against the rebuilt dev stack** (port 5173, `--username test`), not the testing stack: 15 passed, 0 skipped in `records.spec.ts`.
- **The real-app agent check and the VoiceOver pass are left to the user.** Driving an agent needs a signed-in CLI and the company's LM Studio token, and the agent path is covered end to end by the MCP e2e round trip. Logged in the summary rather than skipped silently.
