## Context

Agents now keep orders, customers and stock in record tables (001.01). Users can't see them yet. The tables are only reachable through the MCP server, so nobody can check or correct what an agent wrote.

This plan adds:

- a REST API in tcp-server;
- a spreadsheet view that users can edit, in two places: a filing cabinet in the office's archive (tray, then a dialog), and a new **Tables** tab on the company page;
- CSV download (one table, or all tables as a zip) and CSV append;
- clear and delete for whole tables, and add and delete for single rows;
- CLI verbs to list tables, export one as CSV, and print database connection strings, so users can edit in their own DB tool.

### What exploration found

- **`RecordsService`** (`libs/tcp-shared/src/records/records.service.ts`) uses raw SQL on the default DataSource. Every method takes `companyId` first.
  - It has `listTables` (no counts), `describeTable`, `insert` (idempotent), `update` (locks the row, re-validates, bumps `version`), `delete`, `query` and `deleteCompany`.
  - It has no clear and no drop.
  - `query` caps the offset at 10,000, and `StoredRecord` doesn't include timestamps. `record."updatedAt"` exists in the table and `update` sets it.
  - Dropping a `record_table` row cascades to `record` and `record_key`. Deleting `record` rows cascades to their keys. So clear and drop are one `DELETE` each.
- **tcp-server has no records DB connection.** Its only link to records is the HTTP cleanup call in `api/records-cleanup.service.ts`. `RECORDS_DATABASE_URL` is global (it falls back to `DATABASE_URL`), and compose passes it only to `tcp-mcp-records`. **There is no per-company records DB.** The "connection for a company's tables" is the records DB plus that company's `companyId` filter.
- **REST conventions:** `knowledge.controller.ts` is the model: `@UseGuards(JwtAuthGuard, CompanyMembershipGuard)` plus `@CompanyScope({from:'param', key:'companyId', via:'company'})` on each route. `route-audit.spec.ts` checks new routes automatically. Downloads set `Content-Disposition` (`storage-proxy.controller.ts:83`). No controller audits as a user yet; `getCurrentUserId(req)` (`auth/current-user.ts:9`) gives the JWT `sub`.
- **Dependencies:** the backend has `csv-parse`, but nothing to write CSV and no zip library. The frontend has no grid or table library and no download helper.
- **CLI:** `commands/<verb>.ts` plus `lib/<area>/<verb>.action.ts`. Reuse `apiRequest`, `apiDownload`, `addCompanyOptions`/`resolveCompanyId` and `runCommand`. `open-swagger.action.ts` is the model for a verb that reads env vars and needs no auth. `tcp-cli.sh` sources the env file but not `scripts/lib/derive-urls.sh`, whose `derive_host_urls` builds the host-facing `DATABASE_URL`.
- **Office:** add `FurnitureKind` (`world/types.ts:52`). The archive is furnished in `world/furnishing.ts:86-94` (bookshelf at `roomTile(room,4,1)`).
  - Click: `SelectionTarget` (`TcpPhaserEventBus.ts:13`), and `buildArchiveZone` (`scene/TcpCompanyScene.ts:419`) as the model.
  - Tray: the `selection.kind` switch in `ui/VisualisationTray.tsx:38-114`, `ui/TrayPanel.tsx` and `RoundIconButton`.
  - Keyboard route: `ui/DetailsPicker.tsx`.
  - Text: `ui/officeDescriptions.ts` and `src/strings.ts`.

- **Company tabs:** `pages/CompanyPage/CompanyTabs.tsx` (`ACTIVITY_TABS`, the `lists` record, force-mounted panels, the URL hash). The menu+main layout to copy is `ChatDialog` (`ChatDialog.css:14-32` grid, and `ChatList.tsx` `ListBox` with focus handed over by refs).

### Decisions made in this plan (object at approval if wrong)

**API** (tcp-server, new `api/records.controller.ts` + `records-api.service.ts`; each route is `@CompanyScope(... via:'company')`)

| Route under `/api/company/:companyId/records`       | Does                                                                                                                  |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `GET tables`                                        | `[{name, purpose, records, updatedAt}]`                                                                               |
| `GET tables/:table`                                 | `{definition, rows:[{id, data, version, createdAt, updatedAt}], total, truncated}`. Newest first, at most 10,000 rows |
| `POST tables/:table/rows` `{data}`                  | Add a row. 201, or 409 `already_exists` with the existing id                                                          |
| `PATCH tables/:table/rows/:id` `{changes, version}` | Edit a row. 409 `conflict` (with the current row) when `version` is stale; 400 with the validation messages           |
| `DELETE tables/:table/rows/:id?version=`            | Delete a row, checking the version                                                                                    |
| `POST tables/:table/csv` (multipart)                | Append CSV rows. All or nothing                                                                                       |
| `DELETE tables/:table/rows`                         | Clear the table                                                                                                       |
| `DELETE tables/:table`                              | Delete the table                                                                                                      |
| `GET tables/:table/csv`, `GET export`               | One table as `text/csv`; all tables as `application/zip`                                                              |

- **The records connection:** tcp-server opens a second TypeORM connection, named `records`, with `url: RECORDS_DATABASE_URL || DATABASE_URL`, no entities, no migrations and a small pool (`extra: {max: 5}`). It provides `RecordsService` with a factory on that DataSource (as `records.integration-spec.ts:80` does). The records server keeps owning the migrations. Compose passes `RECORDS_DATABASE_URL` to tcp-server; the Joi entry is `.empty('').optional()`.
- **New `RecordsService` methods:**
  - `listTableSummaries` (counts and latest `updatedAt`);
  - `readRows(companyId, table, cap)` (with timestamps, newest first);
  - `forEachRowBatch` (keyset by id, 1,000 rows a batch, for export with no cap);
  - `insertMany` (one transaction; it checks every row first and reports `{row, messages}[]`; an existing key counts as `already_exists`, not as an error);
  - `clearTable` and `dropTable` (each returns the count removed);
  - `update` and `delete` gain an optional `expectedVersion`.
  - `RecordsError` gains a `code` (`not_found | conflict | invalid`), so the controller can map it to 404, 409 or 400.
  - The MCP tool outputs don't change, so agents pay no extra tokens.
- **CSV:** `csv-stringify` (MIT, no dependencies, the sibling of the `csv-parse` we already use).
  - Columns are the schema's fields in order, and only those (no `id` or timestamps). So an exported file can be appended back in.
  - `csv-parse` reads uploads with `{columns: true, bom: true, skip_empty_lines: true}`. An unknown header is an error. A missing optional column is fine.
  - Cells are converted to the field's type. An empty cell means the field is absent.
  - Limits: 5 MB and 10,000 rows per upload.
- **Formula injection (security advice):** agents write records from untrusted content, and a cell starting with `= + - @`, a tab or a CR runs as a formula in Excel. On export, those string cells get a leading `'`. On import, one leading `'` before those characters is removed for string fields, so a file still round-trips.
- **Zip:** `fflate` `zipSync` (MIT, no dependencies, ~98M downloads/week), built in memory. A `ponytail:` comment names the ceiling (50 tables × the rows they hold) and the upgrade (stream it with `fflate`'s `Zip` class).
- **Audit:** every user write records `state_change` with role `'user'` and agent `null`. The payload is `{source:'records', action: add_row|update|delete_row|append_csv|clear_table|drop_table, table, recordId?, before?, after?, removed?, definition?, userId}`. Drop records the definition; clear and drop record counts, not row data. User reads aren't audited, in line with the storage proxy.
- **Who may change things:** any company member can edit, clear and delete. There are no role flags yet. Logged in outstanding issues: limit clear and delete to owners once membership flags exist.

**Web UI**

- **One shared `TableView`** (`src/components/RecordSheet/`) is used in both the dialog and the Tables tab main area. Its header bar has: a fixed title, **Download**, **Add row**, **Delete row**, **Undo**, and the **More actions** menu.
- **The sheet** (`RecordSheet.tsx`, loaded with `React.lazy` so AG Grid stays out of the main chunk):
  - **Columns:** one per schema field, with a typed editor: text, number (`integer` uses step 1), a true/false/empty select for boolean, and a `format: date` text field checked as `YYYY-MM-DD`. Then a read-only **Updated** column, sorted newest first by default, so the order can be seen.
  - Key fields are marked in their header.
  - The header row is styled through the theme, and every column gets a sort and a text, number or date filter.
  - **Keyboard** (AG Grid's own model, which follows the ARIA grid pattern): arrows move; Enter, F2 or typing starts an edit; Enter saves; Esc cancels; Tab moves on. `stopEditingWhenCellsLoseFocus` saves when you click away.
  - For screen readers: pagination of 100 rows, `ensureDomOrder`, and row and column virtualisation off (AG Grid's own advice). There are visually hidden usage notes linked with `aria-describedby`.
  - **Saving:** `PATCH` with the row's `version`. On 400 the cell reverts and the error is announced. On 409 the row reloads, and the announcement says it was changed elsewhere.
  - **Theme:** `themeQuartz.withParams` reads our CSS custom properties, so light, dark and high contrast all follow. `popupParent` is the `portalContainer`, so filter menus stay inside full screen.
- **Track changes and undo:** a session stack of inverse operations: edit (field, from, to), add (id) and delete (data).
  - Each saved change marks its cell or row. The mark is not colour alone: there's an icon, plus visually hidden "changed" text.
  - **Undo** (a button, or Ctrl/Cmd+Z when the focus isn't in an editor) applies the inverse through the API and announces it, e.g. "Undid: qty in row 3".
  - AG Grid's own undo is off, because it can't undo adding or deleting a row.
  - The stack clears when you switch table or reload.
- **Add row:** a small form `Dialog` built from the schema with React Aria fields. Required fields and key clashes show inline errors.
- **Delete row:** it acts on the row of the focused cell. The button is labelled with that row (e.g. "Delete row 3: order 1001"), and a `ConfirmDialog` asks first.
- **More actions menu:**
  - Append CSV (a native file input, the `CreateTaskDialog` pattern; the result is announced, and each error names its row).
  - Clear and Delete, each behind a `ConfirmDialog` that says how many records will go, and offers **Download a copy first**.
- **Tray** (`ui/RecordsDetails.tsx`):
  - a `TrayPanel` whose actions hold a round **Download all** `RoundIconButton`;
  - the body is a native `<table>` with a caption and the columns Table, Records, Actions;
  - clicking a table name opens `RecordTableDialog` (a wide `Dialog`, passed the `portalContainer`).
- **Tables tab:** add `{id: 'tables'}` to `ACTIVITY_TABS`. The panel is a menu+main grid like `ChatDialog`'s:
  - the left side is a single-select `ListBox` of tables, with names and counts, and a **Download all** button at the top;
  - the right side is the `TableView`;
  - the table you pick goes in the URL (`#tables/orders`) so a reload keeps it;
  - below 40rem the two parts stack.
- **Office:** `FurnitureKind 'filingCabinet'` at `roomTile(room, 5, 1)`, next to the bookshelf. It gets a size, a colour, a description, `SelectionTarget {kind: 'records'}`, its own hit zone, and a `DetailsPicker` entry (the keyboard route).
- **Data layer:** add `record` to `STATIC_ENTITIES`. Add the hooks `useRecordTables`, `useRecordTable`, `useAddRecord`, `useUpdateRecord`, `useDeleteRecord`, `useAppendRecordsCsv`, `useClearRecordTable` and `useDropRecordTable`, plus `downloadRecordTableCsv` and `downloadAllRecordTables`.
  - Downloads go through a new `client.ts` `getBlob` (it carries the token and the 401 policy). The file is saved with an object URL and an anchor `download`, and its name comes from one `downloadName(slug, label, ext, now)` helper.
- **Not live:** record tables aren't on the SSE stream. The views refetch when they open and when the window regains focus, and the version check stops edits from overwriting each other. Logged in outstanding issues.

**CLI**

- `list-tables` (company options) prints `[{name, purpose, records}]` as JSON.
- `export-table --table <name> [--target <file>]` writes CSV to the file, or to stdout. The target defaults to the `downloadName` pattern when you pass a folder.
- `db-url` (no auth) prints the tcp-server DB URL. `db-url --records [--company …]` prints the records DB URL; with a company it signs in to look up the id, and adds `{companyId, tables: ['record_table', 'record', 'record_key'], filter: "\"companyId\" = '…'"}`.
- The host URL comes from `derive-urls.sh`, never worked out in TypeScript: `tcp-cli.sh` exports `TCP_HOST_DATABASE_URL="$(derive_host_urls; echo "$DATABASE_URL")"` from a subshell, so it changes nothing else. `RECORDS_DATABASE_URL` is used as it is when set.
- **Security:** connection strings are never sent through the API. The CLI reads them from the local env file, so `db-url` only works where the CLI shares the deployment's env. The docs warn that the output contains the password.
