## Context

A home install has one GPU. Agents running at once queue inside the local model server, and a wait looks like a hang. Remote providers can take more parallel work, but unlimited parallel work also means unlimited spend rate. Separately, a provider's 429 currently fails the run. LangChain retries a short-hinted 429 itself, but a longer or hint-less one goes straight to `failRun` (_corrected after stage 1_). Spend caps already pause and auto-resume (ADR-031). Rate limits should behave the same way.

### What the code already does

- **Long timeouts are mostly done.** `DEFAULT_LLM_TIMEOUT_MS` and `DEFAULT_AGENT_LOOP_TIMEOUT_MS` are both 30 minutes (`libs/tcp-shared/src/config/defaults.ts:139,156`). The model-check probe uses the same value (`model-check/probe-error.ts:85`). The run timer starts in `AgentLoopService.run`, so time spent queued doesn't count. Stage 2 confirms this and documents it. No new timeout work is planned.
- **Global concurrency** is BullMQ worker `concurrency` from `AGENT_WORKER_CONCURRENCY`, which defaults to 1 (`apps/tcp-agent/src/worker/agent-worker.service.ts:96`, `defaults.ts:127`).
- **Every provider goes through one `ChatOpenAI`** (`libs/tcp-shared/src/llm/llm-factory.ts`), so one error parser covers all of them.
- **The pause and resume plumbing exists:** the spend gate's pause (`tcp-agent/src/agent/spend-gate.service.ts:83`), `pauseResumePrompt()` (`tcp-server/src/api/agent-orchestration.service.ts:199`), the 60-second sweep and explicit resumes (`tcp-server/src/api/spend-resume.service.ts`, `EXPLICITLY_RESUMABLE` at :28).
- `TcpAgent.status` and `pauseReason` are `varchar`, so new values need no migration.

### Decisions agreed with the user

- **Two global pools replace the single global limit.** One pool counts every local agent run and the other every remote one. This gives a simple setup: one number protects home performance and another limits spend rate, with no per-model config needed.
- **Pool defaults: local 1, remote 4.** They ship set, and an operator can raise them or clear them (`null` means unlimited).
- **Per-endpoint limits are optional overrides, with no default.** They are for finer control, for example two local servers or a provider with a lower rate limit.
- **Both apply.** An agent starts only when its pool and its endpoint limit (if one is set) both allow it. An unset limit doesn't constrain anything.
- **`AGENT_WORKER_CONCURRENCY` is retired.** If it is still set, tcp-agent logs a warning at boot that names `MODEL_CONCURRENCY`, then ignores it. BullMQ's worker concurrency becomes a large constant, and all limiting happens in the slot service.
- **Config is environment JSON**, validated at boot like `SPEND_CAPS`. Changes need a restart.
- **Limits are enforced per run, not per LLM call** ("can this agent start"). A run makes one LLM call at a time. A paused agent's job ends, so it frees its slot.

## Design

### Configuration (tcp-agent)

`MODEL_CONCURRENCY` (optional JSON):

```json
{
  "local": 1,
  "remote": 4,
  "endpoints": { "anthropic": 2, "http://gpu-box:1234/v1": 3 }
}
```

- **Endpoint key** (used only for `endpoints` overrides):
  - Remote providers: the catalogue provider id. Rate limits and spend are per account.
  - `local` and `custom` providers: the normalised `baseUrl`. One server is one GPU, whatever model it serves.
- **`local` and `remote` are pool totals** across every endpoint of that kind, picked by catalogue `kind` (`custom` counts as local). When they're missing, the built-in defaults apply: `DEFAULT_LOCAL_MODEL_CONCURRENCY = 1` and `DEFAULT_REMOTE_MODEL_CONCURRENCY = 4`.
- **`endpoints[key]`** is an optional extra limit for that one endpoint. When it's missing, the endpoint has no limit of its own.
- `null` means unlimited. Positive integers only. A bad shape fails boot.
- **BullMQ worker concurrency** becomes a large constant, marked `// ponytail:` (BullMQ needs a number).

### Per-endpoint slots (tcp-agent worker)

- `EndpointSlotService` holds in-memory counts for the two pools (`pool:local`, `pool:remote`) and for each endpoint key, plus a FIFO of waiting job ids per pool. `tryAcquire` checks the pool and the endpoint and takes both, or neither, with no `await` in between. tcp-agent is single-instance, which is already noted in the worker's header. Mark the ceiling with `// ponytail:`.
- **In the processor, after the registry guard:** resolve the agent's LLM config. Reuse `resolveRunLimits` / `resolveLlmConfig` rather than a second resolver. Then `tryAcquire(key)`:
  - **If the slot is acquired:** run as today and release in `finally`.
  - **If the endpoint is full:**
    1. Deregister from the registry.
    2. Set the agent's status to `queued`.
    3. Call `job.moveToDelayed(Date.now() + 30_000, token)` and throw BullMQ's `DelayedError`. This is BullMQ's documented manual-delay pattern, and the job keeps no global slot while it waits.
- **Recheck when conditions change:** on release, promote the oldest waiting job in that pool that can now start (`Job.fromId(queue, id)` then `.promote()`, using a `Queue('agent-jobs')` with an `.on('error')` handler). The 30-second delay is the fallback if a promote is missed.
- **`queued` is a new `AgentStatus`** ("waiting for a model"). tcp-server also sets it when it dispatches a start or resume job (`AgentOrchestrationService`). That way, waiting for a global slot shows too. `AgentLoopService.run` already sets `running`.
- **Drain interaction:** a drain stops the worker. Delayed jobs stay in Redis and run after restart. Queued agents aren't running, so the drain doesn't pause them. Stage 3 checks this against `system-drain.service.ts` and `shutdown-listener.service.ts`.

### Rate limits: pause and auto-resume

- **Classify the error** with a small `classifyRateLimit(err, provider): { kind: 'rate' | 'quota'; retryAt?: Date } | undefined` in `libs/tcp-shared/src/llm/rate-limit.ts`. It builds on LangChain rather than duplicating it (_changed after stage 1_):
  - `@langchain/core`'s `classifyRateLimitError` (exported from `@langchain/core/utils/async_caller`) already reads `Retry-After` (seconds or HTTP date), "try again in N s" message text and quota patterns. Its `stop` result means `quota`, and `wait`/`capacity` mean `rate`.
  - On top of it: status 402 (OpenRouter) means `quota`; `retry-after-ms` (Azure); and, when there's no `Retry-After`, the provider's own reset header, read by provider id (never by header name alone): OpenAI and Groq's Go-duration `x-ratelimit-reset-*`, Azure's integer seconds, Anthropic's RFC 3339 `anthropic-ratelimit-*-reset`, OpenRouter's epoch-ms `X-RateLimit-Reset`.
  - A 429 with no hint is `rate`, so it gets the doubling backoff (see `docs/llm-rate-limits.md` § Parser rules).
- **LangChain's retries stay as they are** (_changed after stage 1: the plan's premise was wrong_). `AsyncCaller` already retries only 429s with a hint of 60 s or less, honouring the hint. It throws at once on a hint-less 429, a longer hint or a quota. So no `maxRetries` change.
- **Where to catch it:** the error reaches `AgentLoopService`'s catch (`agent-loop.service.ts:300`) unwrapped. Classify it there, before `describeRunFailure` turns it into a string.
- **The pause, in `AgentLoopService`'s catch:** a classified error pauses the agent instead of failing it.
  - It sets `status = paused`, `pauseReason = 'rate_limited'`, `resumeAfter` and `rateLimitRetries + 1`, using the spend gate's pause-and-audit shape.
  - The audit payload carries `reason` and `resumeAfter`, so live UI rows can show them.
  - `rateLimitRetries` resets on the next successful LLM response, written only when it's above 0.
- **`resumeAfter`, computed in tcp-agent from its config:**
  1. The provider's hint, if there is one.
  2. Otherwise, for `rate`: `RATE_LIMIT_RETRY_MS` (default 60 s), doubling with each retry, up to `RATE_LIMIT_RETRY_MAX_MS` (default 30 min).
  3. Otherwise, for `quota`: `RATE_LIMIT_QUOTA_RETRY_MS` (default 1 h). A used-up quota is never retried every few seconds.
  4. With `RATE_LIMIT_AUTO_RESUME=false`, `resumeAfter` is `null`, and only an explicit resume lifts the pause.
- **Resume:**
  - `SpendResumeService`'s existing 60-second sweep also resumes agents with `paused` / `rate_limited` and `resumeAfter <= now`. The interval becomes injectable so tests don't wait 60 s.
  - `EXPLICITLY_RESUMABLE` gains `rate_limited`.
  - `pauseResumePrompt()` gets a `rate_limited` branch with a continuation prompt, but only if the agent has an `llm_response` row (the same rule as `spend_cap`).
- **Migration:** add `tcp_agent.resumeAfter` (`@Column({ nullable: true })`, no explicit type) and `rateLimitRetries` (int, default 0). Register it by hand in each `apps/*/src/app.module.ts`.
- **Stub-llm** gains a 429 mode that sends a `Retry-After` header, for tests.

### UI and CLI

- `statuses.ts`:
  - Add `queued` to `ACTIVE_AGENT_STATUSES` and `STATUS_KEYS` ("Waiting for model").
  - A `rate_limited` pause reads "Rate limited — next try HH:MM" (or "— resume by hand" when `resumeAfter` is null).
  - These show in `AgentsList`, `TaskAssignmentPanel` and `AgentDetails`.
- **Live rows:** `synthesiseAgentPatch` in `src/events/cache.ts` carries `pauseReason` and `resumeAfter` from the event. Otherwise a live row shows "paused" with no reason (see memory: live agent rows carry no summary).
- **Office view:** `companySnapshot.ts` treats `queued` as waiting, not working.
- **CLI:** agent status output shows `queued`, and shows the rate-limit reason and next try. `resume-task` / `resume-company` already work once `EXPLICITLY_RESUMABLE` includes `rate_limited`.
