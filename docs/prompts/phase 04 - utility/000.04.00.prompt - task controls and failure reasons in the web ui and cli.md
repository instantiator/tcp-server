## Manual pause

A user can pause a running task, and resume it later, from the web UI and the
CLI.

- Add a `manual` pause reason (`PauseReason` in `TcpAgent.model.ts`). Every
  agent working on the task pauses at its next safe point. Don't kill an LLM
  call mid-flight unless the plan finds that's the only way.
- A manual pause stays paused until a user resumes it. It must not be lifted
  by the spend-cap sweep, the rate-limit auto-resume, or a consultation reply.
  Decide what happens when a reply or consultation result arrives for a
  paused task. It should probably be recorded and applied on resume.
- Resume uses the existing `POST /api/task/:id/resume`. Add `manual` to the
  reasons an explicit resume lifts (`EXPLICITLY_RESUMABLE` in
  `spend-resume.service.ts`). Check whether resume should still exempt the
  task from spend caps when the pause wasn't a cap.
- Every new `PauseReason` needs a branch in `pauseResumePrompt()` (see
  memory: resume without a message restarts).
- Web UI: a **Pause** button in the task dialog while the task is running, and
  a **Resume** button while it is paused for any explicitly resumable reason.
  The paused state and its reason are visible.

## Say why a task can't start, resume or continue

When a task can't start, resume or move forward, the web UI and the CLI show
the reason, in plain words.

- If the cause is something the user must fix (the provider is unreachable,
  the model isn't loaded, the API key is rejected, the model doesn't exist),
  the task goes to `failed` with a `failureReason` that says what went wrong
  and what to do. `TcpTask.failureReason` already exists.
- If the cause is temporary and already handled (queued for a model slot,
  rate limited, spend cap reached), the task stays paused or queued, and the
  UI shows why and, where known, until when.
- Requests that are refused outright (not signed in, not allowed, wrong task
  state) don't change the task. The web UI and CLI show the refusal in plain
  words rather than a bare status code.
- The task dialog and the CLI's task views (`get-task`, task lists, the
  transcript) show the reason. A task must never sit apparently idle with no
  explanation.
- New reasons will appear (new providers, MCP services, action approval in
  003.01). Make the reason a small, extendable set, so adding one is one
  entry and a message, not a new code path. Every reason has a test.

### Known reasons

The plan confirms this list against the code, adds anything missing, and
decides for each one: refuse, fail, pause or wait, and the message shown.
Starting points are noted where they exist.

**The request is refused (the task is unchanged)**

| Reason                                                  | Where today                                              |
| ------------------------------------------------------- | -------------------------------------------------------- |
| Not authenticated: no token, or an expired or bad token | JWT guard; the web client redirects to sign in on 401    |
| Not authorised: the user isn't a member of the company  | `@CompanyScope` membership checks (403)                  |
| Task or company not found                               | `task.service.ts` (404)                                  |
| Task in the wrong state to start, edit or resume        | `task.service.ts` (409, "not ready", "already terminal") |
| Shutting down: the system isn't accepting new work      | `SystemShutdownService.assertAccepting` (503)            |
| Invalid configuration: provider base URL not allowed    | LLM baseUrl policy (`LLM_ALLOWED_HOSTS`, catalogue URL)  |

**The task fails (the user must fix something, then retry)**

| Reason                                                                                       | Where today                                                 |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| LLM provider unreachable: connection refused, DNS failure, connect timeout                   | Unknown: see "A task that neither started nor failed"       |
| Model not loaded or not found (for example LM Studio with no model loaded)                   | Unknown: as above                                           |
| API key missing or rejected (401/403 from the provider)                                      | Probably `failRun`; message needs checking                  |
| Provider quota or credit used up (not a temporary rate limit)                                | 000.03 tells quota from rate limit; check what it shows     |
| Model can't do what's needed: no tool calls, context too long                                | Check                                                       |
| Agent gave up: required tool calls never made, iteration limit reached                       | `agent-loop.service.ts`, `supervised-turn.service.ts`       |
| Planner failed, so no plan exists                                                            | Check: see hypothesis 4 below                               |
| Role, planner or LLM config missing or invalid for the company                               | Check                                                       |
| Database error: the task, assignment or agent state couldn't be read or saved                | Check: a failed write may also stop the failure being saved |
| Supporting service down: Redis/BullMQ, MCP servers, storage (Silo/MinIO), embeddings for RAG | Check                                                       |

**The task waits or pauses (it continues by itself, or on resume)**

| Reason                                   | Shows                                    | Where today                               |
| ---------------------------------------- | ---------------------------------------- | ----------------------------------------- |
| Queued for a model slot                  | Position or "waiting for model"          | `AgentStatus.Queued`, `MODEL_CONCURRENCY` |
| Rate limited by the provider             | When it will retry (`resumeAfter`)       | `rate_limited` pause                      |
| Spend cap reached                        | Which cap, and when it resets            | `spend_cap` pause                         |
| Paused by a shutdown                     | Resume needed                            | `shutdown` pause                          |
| Paused by a user                         | Who paused it, and that resume is needed | `manual` pause (new, above)               |

Two questions for the plan:

- **Database errors:** when the write that records the failure itself fails,
  where does the reason go, and who sees it? At minimum, the logs and the
  caller's response.
- **Supporting services:** should a service that's down fail the task, or
  pause it so it can be resumed once the service is back?

### A task that neither started nor failed

Seen during 000.03: a task was started while LM Studio was running but no
model was loaded. The task didn't start, and it didn't fail either. Find the
cause before designing the fix. Hypotheses, most likely first:

1. **The LLM call is still waiting.** `DEFAULT_LLM_TIMEOUT_MS` is 30 minutes
   (raised for slow local models in 000.03). If LM Studio holds the request
   open, or is loading the model on demand (JIT), the agent sits in `running`
   for up to 30 minutes. A long timeout for generation is right; a long wait
   to _connect_ or to find the model is not. Consider a short readiness check
   (for example, `GET /v1/models` lists the model) before the first call.
2. **LangChain is retrying.** A refused connection or a 5xx may be retried
   with backoff, quietly, before any error reaches the agent loop.
3. **The agent is queued.** It's waiting in the model pool (`queued`) behind
   another call that is itself stuck, so it never reaches the provider.
4. **The failure didn't reach the task.** The planner agent failed, but
   `deriveTaskStatus` only fails a task through its plan assignments, so a
   failed planner may leave the task in `planning`.

Reproduce it (LM Studio up, no model loaded), confirm the cause with the
agent's status and logs, and add a test that a task in this state ends as
`failed` with a clear reason, within a bounded time.

## Addendum — agreed in planning (2026-10-09)

Plan: [000.04.01.plan - task controls and failure reasons in the web ui and cli.md](<000.04.01.plan - task controls and failure reasons in the web ui and cli.md>).

- **The phase 06 `ui-notes.md` items are folded in.** These are task numbers in the office tooltips, the reorganised tray assignment list, room lighting, the bookshelf count, and finished task rooms that stay until a user closes them. The notes file is retired.
- **A manual pause is a soft stop, recorded on the task** (`pausedAt`, `pausedBy`). Running agents stop at their next safe point, and no in-flight LLM call is killed. While the task is paused, replies, consultation results and the automatic sweeps don't resume it. Replies are kept and applied when it resumes.
- **Automatic resumes lift only the waits they own.** A reply can no longer wake an agent paused for a spend cap and lose the reply.
- **Resume exempts a task from spend caps only if a cap is reached at that moment**, the same rule as Start.
- **Failures get plain, actionable reasons from one typed table.** Adding a reason means adding one entry, one message and one test. A supporting service that's down fails the task. Revisit this when 000.05's health signal exists.
- **A finished task's room stays until "Close room"**, which sets a server flag, `TcpTask.visualisationClosedAt`. It is named for the view, not the room, because other views may come later.
- **Toasts are short-lived and click through to their own row.** This covers every notification and new enquiry. A toast hides after about 8 s, and the timer pauses while it is hovered or focused. The durable row is what keeps this within ADR-026's "no timing" rule, and ADR-026 is amended to say so.
- **Task failures and shutdown pauses raise company-scoped notifications.**
- **Commits:** one per stage.
