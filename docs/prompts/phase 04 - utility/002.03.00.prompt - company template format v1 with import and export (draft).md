> ## Company templates
>
> > 📝 **In a draft, not implemented:** [deferred-work.md](../deferred-work.md#company-definitions-as-zip-files) ("Company definitions as zip files") covers company, roles and knowledge, loaded by `tcp-cli`. This gap extends it with MCP services, records, schedules, reports and hooks.
>
> **Today:** `scripts/test-data/companies/*.json` describe the company row only
> (slug, name, description, context, LLM config). Roles and knowledge are added
> one CLI call at a time.
>
> **Recommend:** a template package: company, roles (prompts, skills, model
> minimums), knowledge packs, MCP service attachments (without secrets, which
> are listed as "you'll need"), record table schemas, schedules, reports, hooks.
>
> - Import and export through the API, CLI and web UI.
> - A gallery in the web UI. "Create company" starts here.
> - Version the format from day one.
> - First template: **cottage industry**.

Templates should be importable as a zipped collection of files.

The structure of a template should be fully documented, and a template directory with blank template files and a README.md with instructions for modifying it, adding roles, knowledge, etc. should be downloadable through the UI, too.

Templates distributed in the github repo should be served from the backend, and shown in the gallery.

The gallery should support multiple sources and should support public git repository urls containing templates. Github repository sources, and a local source directory, containing template zips, should be configurable through application config, but also tracked in application config held in the database (so allowing the user to add / remove sources through the UI).

Although the first template is mentioned above as cottage industry, other templates should be avaialble for testing. For now, that's:

- Blank (very simple, no roles)

The cottage industry template will need some researching. Recommend several roles, draft basic role prompts, and source some open documents that can serve as their knowledge. (Where possible, seek documents with clear, permissive, licensing - eg. creative commons licenses. Ensure that any licensing requirements for these documents are followed correctly.)

During import, the company configuration options should be shown to the user for modification (eg. to provide a default LLM service).

The getting started documentation (README, your first company, any others) will also need to be updated to reflect this new (and preferred) method of setting up and working with a company.

## Also: choosing a model on import (from 002.01)

"Provide a default LLM service" during import means [002.01](002.01.01.plan%20-%20web%20ui%20llm%20provider%20picker.md)'s `LlmConfigPicker`. A template must never carry an API key: export with `apiKey` removed, and say "you'll need a key for <provider>" on import. A model named in a template may not exist on the importer's local server. The picker's live list (`POST /api/company/:companyId/llm/models`) lets them choose one that does.

## Also: an existing slug is a 409 (from 002.02)

Since [002.02](002.02.01.plan%20-%20web%20ui%20create%20and%20edit%20a%20company.md), `POST /api/company` refuses a slug that is already taken (409) unless `?replace=true` is given, and replacing needs membership of the existing company or administrator access. An import must not replace a company silently: on a clash, ask whether to replace it or import under a new slug, and send `replace=true` only on an explicit "replace". The web create dialog (`CreateCompanyDialog`) is where an import entry point would sit.
