## Context

The storage browser (002.05) can only change `resources/`. Knowledge and task materials stay read-only there, because putting a file in those folders does nothing by itself:

- **Knowledge** has to go through `POST /api/role/:roleId/knowledge` or `POST /api/company/:companyId/knowledge`. These convert the file to OKF Markdown (the original is not kept) and reindex the scope.
- **Task materials** have to go through `POST /api/task/:id/materials`. It adds the file to the task row's materials list, which is what agents read, and only works while the task is `ready`.

This plan lets the browser upload into those folders **through their own routes**. It doesn't widen `isWritable`. It also puts the browser into the knowledge panels.

### What exploration found

**The browser (`src/components/StorageBrowser/`):**

- `StorageBrowser.tsx` works out the upload target from the selection.
- `isWritablePath` (`paths.ts`) decides which controls show. A browser rooted outside `resources/` shows no write controls at all (`writableSomewhere`).
- `useUploads.ts` posts each file to the storage route. It gathers 409s for a single "Replace?" `ConfirmDialog` (an `alertdialog`), and announces on `STORAGE_CHANNEL`.

**Knowledge routes (`knowledge.controller.ts` `storeConverted`):**

- Knowledge is flat: a filename in a scope, with no subfolders.
- The stored name is the file's own name for `.md`, and `{base}.md` for anything else (`toOkfDocument`, `knowledge-conversion.ts:203`).
- A clash returns 409 **only for converted files**. A same-named `.md` overwrites without asking. Sending `filename` overwrites on purpose.
- Size limit `MAX_UPLOAD_BYTES`; an unsupported extension returns 400.
- Scope folders: `knowledge/shared/` for the company, `knowledge/{role_slug}/` for a role.

**Materials route (`task.service.ts:168` `addMaterial`):**

- Stores the file at `tasks/{taskId}/materials/{name}` and **appends** it to `task.materials`. Uploading the same name twice overwrites the file but lists it twice.
- Returns 409 when the task isn't `ready`.

**Client hooks:**

- `useUploadKnowledgeMutation` (`api/endpoints.ts:624`) posts the file alone, with `postFile`.
- The materials mutation is at `endpoints.ts:613`.
- `useUploadKnowledge` and `useDeleteKnowledge` (`api/hooks.ts:388`) invalidate `['knowledge']` only.
- `postFormForJson` (`client.ts`) already sends extra fields, so it can carry `filename`.

**Where the browser and `KnowledgePanel` appear:**

- `StorageBrowser` hosts:
  - `DocumentsPanel.tsx` (root `''`);
  - `TaskDialog.tsx:239` (root `tasks/{id}/`);
  - the office trays.
- `KnowledgePanel.tsx` (status, Rebuild, list with Delete, upload, test search) is used by:
  - `RoleDialog.tsx:458`;
  - `AdminPanel.tsx:63` (Admin → Knowledge).

### Decisions (yours, 2026-11-22, plus mine)

1. **"Doors", with one rule on each side.**
   - In `paths.ts`, `isWritablePath` becomes `doorFor(path, roleIdBySlug)`. It returns one of:
     - `{ kind: 'storage' }` under `resources/`;
     - `{ kind: 'knowledge', scope }` for exactly `knowledge/shared/` or `knowledge/{slug}/` of a known role;
     - `{ kind: 'materials', taskId }` for exactly `tasks/{id}/materials/`;
     - `null` for everything else.
   - On the server, the rule is the routes themselves, and they stay the authority. `isWritable` is not changed.
2. **Upload targets:**
   - Dropping on `knowledge/` itself, or on any folder that isn't a scope, uploads nothing. The target line reads "Choose shared or a role's folder to upload knowledge into."
   - A folder under `knowledge/` with no matching role is read-only.
   - Folder uploads aren't allowed through a door, because knowledge and materials are flat. **Upload folder** is disabled there, and dropped files inside subfolders are listed as failures ("Folders can't be uploaded here").
3. **One confirmation per upload** (an `alertdialog`, `ConfirmDialog`), shown before anything is sent. The wording depends on the door:
   - knowledge: "These files will be converted to OKF Markdown and the originals won't be kept. The index rebuilds by itself." It then lists any renames, e.g. `report.docx → report.md`;
   - materials: "These files become the task's materials, which its agents read. Materials can only be added before the task starts."

   A `resources/` upload doesn't ask, as today.

4. **"Replace?" checks names first.**
   - Before sending, the browser compares each file's stored name (`storedName`, copied from the server's rule and kept beside `doorFor`) with the target folder's listing.
   - Clashes get the existing "Replace?" dialog, once.
   - **Replace** sends `filename` for knowledge. For materials, the backend now replaces the list entry instead of adding a second one.
   - A 409 from a door is shown as a failure, with the server's reason ("not ready"). It is never treated as a clash.
5. **Knowledge panels use the browser.** `KnowledgePanel` keeps status, Refresh, Rebuild and the test search. Its list and upload control are replaced by a `StorageBrowser` rooted at the scope's folder. That applies to the role dialog and to Admin → Knowledge, since one component serves both.
   - In a knowledge scope the browser's **Delete** goes through the knowledge delete route, so RAG chunks go too.
   - Version history stays for `resources/` only.
6. **Materials are opened too.**
   - Uploads into `tasks/{id}/materials/` work from Data → Documents and from the task dialog's Files browser.
   - There is no delete, since there is no route for it.
   - Afterwards the task query is refetched along with storage.
7. **What you see after an upload:**
   - the storage listing (`['storage']`) refetches, so a `.docx` appears as its `.md` name, which the confirmation already showed;
   - the knowledge status polls through its rebuild, as it does today;
   - the result is announced once on the `storage` channel (`storage.uploaded`). Failures interrupt (`storage.uploadFailed`) and are listed under the toolbar.
8. **Permissions are unchanged:** any member can still upload, as in the Admin tab today. `@CompanyScope` on every route stays as it is.

### - [x] Stage 2 — Doors and routed uploads (Opus)

- **`paths.ts`:**
  - `doorFor(path, roleIdBySlug: ReadonlyMap<string,string>)` and the `Door` type, as in decision 1. `isWritablePath` stays for version history and deletes outside knowledge.
  - `storedName(name, door)`: for knowledge, the name itself for `.md` and `{base}.md` otherwise; for other doors, the name unchanged. Its comment names `toOkfDocument` as the rule it mirrors.

- **`api/hooks.ts`:**
  - knowledge upload and delete also invalidate `['storage']`;
  - a materials upload invalidates `['storage']` and the task's query key;
  - export one routed upload hook, `useDoorUpload(companyId)`, which returns `(door, item, overwrite) => Promise`. It dispatches to the storage, knowledge or materials mutation.
- **`useUploads.ts`:**
  - `start(items, folder, door)`;
  - for a door other than storage: refuse items in subfolders (they become failures); work out clashes from the target folder's listing (`queryClient.fetchQuery` on the storage folder key); send through `useDoorUpload`; treat any 409 as a failure;
  - storage keeps its 409-means-clash path;
  - `replace` sends `overwrite`, which becomes `filename` for knowledge.
- **Tests:**
  - `paths.test.ts`, covering every door case: `knowledge/` → null; `knowledge/shared/`; a known slug; an unknown slug → null; `knowledge/x/y/` → null; `tasks/id/materials/`; `tasks/id/` → null; `resources/a/`. Also `storedName` for `.md`, `.docx` and `.PDF`.
  - `useUploads` (through a test component and the fetch mock), covering:
    - a knowledge upload posts to the role's knowledge route;
    - a clash with an existing `.md` waits for "Replace?", then sends `filename`;
    - a materials 409 is listed as a failure, not as a clash;
    - a nested item is refused;
    - one announcement is made per batch.
- **Gate:** `check.sh --fast`, plus the frontend unit suite.

### - [x] Stage 3 — The browser shows the doors (Opus)
