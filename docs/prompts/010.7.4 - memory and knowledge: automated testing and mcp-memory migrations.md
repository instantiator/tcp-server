## Goal (a): fix the e2e migrations gap

Today, `recall`/`remember`/`search_knowledge` **cannot** be tested against a
real Postgres+pgvector backend end-to-end — fix this first; everything else
in this plan depends on it.

### Current state (verified)

- `apps/lcp-mcp-memory/src/app.module.ts:17-28` configures TypeORM with
  `synchronize: false` and no migrations array. This is **deliberate, not a
  bug** — `apps/lcp-agent/src/app.module.ts` has the identical pattern with an
  explicit comment: "migrations are lcp-server's responsibility" (single
  migration owner; in real deployments lcp-server runs its migrations first,
  other apps connect to the already-migrated shared schema). **Do not add a
  migrations array to lcp-mcp-memory's (or any other app's) own `AppModule`
  — that would duplicate migration-running responsibility across apps and
  contradicts this documented design.**
- The actual gap is test-infrastructure-only:
  `test/e2e/global-setup.ts` starts one Postgres container for the **whole**
  e2e tier (shared across every `*.e2e-spec.ts` file in the run) but never
  runs any migrations against it. Individual lcp-server e2e specs get a
  migrated schema only as an incidental side effect of booting lcp-server's
  own `AppModule` in their own `beforeAll` (which passes
  `migrationsRun: !!migrations?.length` to TypeORM via `makeTypeOrmConfig`,
  `libs/lcp-shared/src/db/typeorm-config.factory.ts:39`) — but
  `test/e2e/lcp-mcp-memory/*.e2e-spec.ts` only ever boots lcp-mcp-memory's
  own `AppModule`, so the shared Postgres container never receives lcp-server's
  migrations in that context, and `knowledge_chunk`/`episodic_memory` don't
  exist. This is why today's `mcp.e2e-spec.ts` only tests transport
  (initialize returns 200/202, GET/DELETE return 405) and never calls a real
  tool — doing so would 500 on missing tables.
- lcp-server's migrations array is currently **inlined** in
  `apps/lcp-server/src/app.module.ts:70-118` (28 individual imports) — there
  is no standalone exported list to reuse from a test file without either
  duplicating all 28 imports or importing `AppModule` itself (which would
  also boot the whole lcp-server app unnecessarily just to get its migration
  list).

### Implementation

1. Extract the inline migrations array in `apps/lcp-server/src/app.module.ts`
   into a new exported constant, e.g.
   `apps/lcp-server/src/migrations/index.ts` exporting
   `export const MIGRATIONS: (new () => MigrationInterface)[] = [...]` (same
   28 classes, same order). Update `app.module.ts` to import `MIGRATIONS` from
   there instead of listing them inline — behaviourally identical, just a
   single source of truth (this also reduces the surface of the existing
   "migrations must be registered by hand in every app.module.ts" footgun —
   there's now exactly one array to keep in sync as new migrations are added,
   not a copy embedded in a giant import list).
2. In `test/e2e/global-setup.ts`, after `rememberComposeEnv(environment)`,
   run these migrations once against the tier's shared Postgres: create a
   plain `DataSource({ type: 'postgres', url: env.DATABASE_URL, migrations: MIGRATIONS })`,
   `await dataSource.initialize()`, `await dataSource.runMigrations()`,
   `await dataSource.destroy()`. Add a doc comment explaining why (every
   e2e spec in the tier — including lcp-mcp-memory's, which never boots
   lcp-server's own `AppModule` — now gets a real, migrated schema without
   relying on spec-file ordering).
3. Do **not** touch the integration tier — `rag-retrieval-isolation.integration-spec.ts`'s
   existing `synchronize: true` + manual pgvector-column pattern is a
   different, already-working approach for that tier and is out of scope here.
4. Sanity-check: run the existing `mcp.e2e-spec.ts`/`health.e2e-spec.ts` after
   this change — they should still pass unmodified (migrations running
   earlier shouldn't affect transport-only assertions).

## Goal (b): round-trip tests

Once (a) lands, lcp-mcp-memory's e2e specs get a real, migrated schema. Add:

### 1. Knowledge round trip (e2e)

New test in `test/e2e/lcp-server/knowledge.e2e-spec.ts` (or a new
`knowledge-rag-roundtrip.e2e-spec.ts` alongside it if that file is getting
long): store a document via `POST /api/role/:roleId/knowledge` (using the
format-aware endpoint from 010.7.1, if landed — else a plain `.md` OKF doc) →
wait for the write-hook's async reindex to complete (poll
`GET .../knowledge/status` from 010.7.2 if landed, else poll
`knowledge_chunk` directly via the test's own repo access until a row for the
new `documentPath` appears, with a sane timeout) → confirm retrieval finds it,
either via the manual-query endpoint (010.7.3, if landed) or by seeding a
`companyId`/`embeddingConfig` and calling `RagRetrievalService.retrieve`
directly the way `rag-retrieval-isolation.integration-spec.ts` already does.

### 2. Memory round trip (e2e, real `/mcp` transport)

Extend `test/e2e/lcp-mcp-memory/mcp.e2e-spec.ts` with real tool calls now that
schema exists:

- `remember`: POST a JSON-RPC `tools/call` request
  (`{ jsonrpc: '2.0', id, method: 'tools/call', params: { name: 'remember', arguments: {...} } }`)
  to `/mcp` and assert the response contains a memory UUID.
- `recall`: POST a `tools/call` for `recall` with a query matching the
  `remember` call's content, assert the stored memory comes back.
- `search_knowledge` exclusion: `remember` something, then `search_knowledge`
  with a matching query, and assert the episodic-memory content is **not**
  present in the results (only `knowledge_chunk` rows should ever appear —
  this is the behaviour `memory-tools.service.spec.ts`'s unit tests already
  assert against a mocked DB; this test proves it against the real UNION/
  filter SQL).
- **Note on the transport**: `BaseMcpController`
  (`libs/lcp-shared/src/mcp/base-mcp.controller.ts:22-24`) constructs its
  `StreamableHTTPServerTransport` with `sessionIdGenerator: undefined` — a
  fresh `McpServer` is created per POST, so there is no session to establish
  across requests. Verify at implementation time whether the installed MCP
  SDK version accepts a standalone `tools/call` POST without a preceding
  `initialize` on the same connection (likely yes, given the stateless
  design) — if it does not, adjust accordingly; this plan does not assume a
  specific SDK behaviour it hasn't verified.
- These will need real embedding calls — reuse the `STUB_LLM_URL` fixture
  pattern from `rag-retrieval-isolation.integration-spec.ts` (a plain
  `{ provider: 'openai', model: 'stub-embed', baseUrl: STUB_LLM_URL, apiKey: 'test' }`
  object) rather than a real OpenAI/LM Studio endpoint, and seed the
  `LcpCompany` row with it via the same repo-access pattern
  `cross-service.e2e-spec.ts` uses (`moduleFixture.get(getRepositoryToken(...))`).

### 2. Tests to avoid duplicating

Cross-reference 010.7.2's and 010.7.3's own test sections — those sub-plans
already add unit/e2e coverage for their new endpoints in isolation. This
file's job is round-trip coverage (multiple steps chained together proving
the whole pipeline), not re-testing each endpoint standalone again.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/
  methods/functions describing intent (not implementation), `//` inside
  bodies, `{@link}` for type references. Match the surrounding code's style.
- No new dependencies needed for this plan. No unrequested changes outside
  this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`) — run
   this repeatedly while iterating on the global-setup change, since a
   mistake there affects every e2e spec in the tier, not just the new ones.
4. Before declaring done: `./scripts/run-all-tests.sh` (full suite) and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Git hooks run the quality gate; never use `--no-verify`.

Standing instructions:

- If the work becomes exceedingly complex or a problem resists solution,
  HALT and inform the user.
- If you discover a beneficial alteration to this plan, HALT and inform the
  user before proceeding — do not silently change the design.
- Document any agreed deviations by appending dated notes to this file.
