# Memory and knowledge 1/4: wider ingestion and OKF generation

Part 1 of the memory-and-knowledge work (see
`010.7.0 - memory and knowledge: overview.md` for the map — you do not need
to read it to implement this plan; everything required is below).

> **Recommended implementing model: Sonnet.** Well-specified, pattern-following
> work — extend an existing controller/service, add narrow converter functions.

## Goal

Let `store-knowledge` (CLI + server) accept `.md, .txt, .html, .pdf, .docx,
.csv, .json, .yaml`, converting each into an OKF Markdown document (YAML
front-matter with a `title` field + a Markdown/fenced-code body), generated
**server-side** so `lcp-cli` stays a thin client per the source prompt's
explicit instruction.

## Implementation

### 1. Add conversion dependencies

Add exactly these (latest versions; each independently checked during
planning — MIT, 6-27M weekly downloads, actively maintained):

- `turndown` + `turndown-plugin-gfm` + `cheerio` — HTML → Markdown.
- `pdf-parse` — PDF → plain text.
- `mammoth` — DOCX → Markdown (`mammoth.convertToMarkdown`, if supported by
  the installed version, else convert to HTML and pipe through the same
  turndown step used for HTML — check the actual API of the version you add).

Do **not** add a dependency for `.txt`/`.csv`/`.json`/`.yaml` — see step 2.
Do not add `@nanocollective/get-md` (rejected during planning — see
`010.7.0`'s shared context).

### 2. Converter module

New file, e.g. `apps/lcp-server/src/api/knowledge-conversion.ts`, exporting
one pure function per format plus a dispatcher:

- `convertToMarkdown(filename: string, buffer: Buffer): { title: string | null; body: string }`
  — dispatches on extension.
- `.md` — pass through as today (front-matter parsed via the existing
  `parseFrontMatter`; if present, its `title` wins).
- `.txt` — body is the raw text, `title` is `null` (falls through to the
  filename-stem fallback in step 3).
- `.html` — `cheerio.load(buffer)`, then `turndown` (with the GFM plugin) on
  the body; `title` from the HTML `<title>` tag if present, else `null`.
- `.pdf` — `pdf-parse(buffer).text`; `title` is `null` (PDFs rarely have a
  clean single heading; fall through to filename).
- `.docx` — mammoth conversion; `title` from the first Markdown heading in
  the result if present, else `null`.
- `.csv` / `.json` / `.yaml` — wrap the raw text in a fenced code block of the
  matching language (` ```csv`/` ```json`/` ```yaml`), per
  the source prompt's own suggestion. Use the already-installed `js-yaml`
  (`.yaml`) / `csv-parse` (`.csv`) purely as a well-formedness check before
  wrapping — reject with a clear error on a parse failure rather than storing
  malformed data silently. `.json` well-formedness is `JSON.parse`.

### 3. OKF front-matter generation (heuristic — no LLM)

New function `ensureOkfFrontMatter(filename: string, converted: { title: string | null; body: string })`:

- If `converted.title` is set, use it.
- Else, scan `converted.body` for the first `# ` or `## ` heading line and use
  its text.
- Else, use the filename stem (`path.basename(filename, path.extname(filename))`).
- Prepend `---\ntitle: <escaped-title>\n---\n\n` to the body (reuse `js-yaml`'s
  `dump` for correct YAML escaping of the title rather than hand-rolling
  string interpolation).
- If the source was already `.md` **with** valid front-matter, skip this step
  entirely — do not double-wrap.

### 4. Wire into `KnowledgeService`/`KnowledgeController`

- `KnowledgeController.storeRoleKnowledgeFile`/`storeCompanyKnowledgeFile`:
  detect the format from the uploaded filename's extension (reuse
  `path.extname`), run it through `convertToMarkdown` + `ensureOkfFrontMatter`
  before calling `KnowledgeService.store`. Store the result **as a `.md` file**
  regardless of source extension (e.g. `report.pdf` → stored as `report.md`) —
  decide and document the exact rename rule (recommend: same basename, `.md`
  extension, erroring clearly on a name collision with an existing differently-
  sourced file).
  Run the existing `validateOkf` on the generated content as a final
  authoritative check before storing (defense in depth — the heuristic in
  step 3 should always satisfy it, but don't silently trust that).
- Reject unsupported extensions with a 400 and a clear message listing
  supported formats.
- `lcp-cli`'s `store-knowledge.action.ts`: drop the `.md`-only /
  `validateOkfDocument` client-side pre-check (or narrow it to "is this
  extension one of the supported list", not "is this valid OKF" — the server
  now does the real conversion+validation). Update its JSDoc accordingly.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/
  methods/functions describing intent (not implementation), `//` inside
  bodies, `{@link}` for type references. Match the surrounding code's style.
- Only add the dependencies listed in step 1, at their latest versions;
  check each one's license/health before adding (already pre-checked during
  planning — re-verify current versions at implementation time). Do not
  update unrelated existing dependencies. No unrequested changes outside
  this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` (full suite) and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Git hooks run the quality gate; never use `--no-verify`.

Write unit/e2e/API tests alongside each unit of code — main cases, edge
cases, and failure cases; verify HTTP response codes explicitly.
