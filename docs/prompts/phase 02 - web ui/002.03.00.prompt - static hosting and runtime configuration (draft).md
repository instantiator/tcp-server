## Goal

The application is built once and has to run in several environments. It needs the identity provider's address and client ID at runtime, and it needs the API to look like it lives at the same address so the browser doesn't treat API calls as cross-origin.

## Requirements

- One nginx image that serves the built assets **and** forwards `/api` to tcp-server. To the browser, the app and the API share one address.
- Environment-specific settings reach the running app without rebuilding it. Only two values need this — the identity provider address and the client ID — because the API address is always `/api`.
- **HTTP/2 must be available in development as well as in the deployed image.** This is a requirement, not a nicety: the live views open five or more simultaneous event streams, and HTTP/1.1 caps a browser at six per address. The failure mode is requests hanging with no error, which looks exactly like a backend fault.
- Deep links survive a page refresh — loading a company URL directly must work, not 404.
- The web app's port follows the existing `EXPOSE_PORT_*` convention and is wired into the same places as every other service.

## Implementation notes

- The runtime settings arrive as a small `config.js`, generated by an entrypoint script when the container starts, and loaded before the bundle.
- `config.js` must be served with `Cache-Control: no-store`, while the hashed bundle assets are served as immutable. A cached `config.js` pointing at a previous environment's identity provider is a confusing failure.
- nginx falls back to `index.html` for any path that isn't a file and isn't `/api`.
- For development, either enable HTTP/2 on the Vite dev server or run the same nginx image in front of it. The second is more faithful and gives development the same `/api` path as deployment. **Verify this early** rather than assuming it works.
- `EXPOSE_PORT_WEB` is added in three places: `docker-compose.yml`, `derive_host_urls` in `scripts/lib/derive-urls.sh`, and `scripts/lib/check-ports.sh`. The last one currently only pre-flight-checks API, DB, MinIO and Zitadel, so a new service isn't covered unless it's added.
- Host ports 3000, 3001, 3002, 3010–3013, 5432, 8080, 9000 and 9001 are taken. 5173 and 4173 are free.
- The frontend's image is the simplest in the stack: static assets on `nginx:alpine`, no `node_modules`, no Node runtime.
- Because the proxy makes everything same-origin, CORS is not needed. `enableCors()` stays documented as the fallback for a split-origin deployment (see 002.04) but is not wired on by default.

## Testing

- A smoke check that the served app loads, and that an API call through `/api` reaches tcp-server.
- **Verify HTTP/2 is actually in use**, in development and in the image — assert on the negotiated protocol, don't assume it from configuration.
- A test that opening more than six simultaneous event streams works. This is the specific failure this requirement exists to prevent, and it won't show up any other way.
- A test that a deep link loads correctly on a fresh page load, not just via in-app navigation.
- Confirm cache headers differ correctly between `config.js` and the hashed assets.
- Confirm the port pre-flight check catches a collision on the new port.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- `shellcheck` passes on the entrypoint and any modified scripts.
- The full suite passes via `./scripts/run-all-tests.sh`, including with the new service in the compose stack.
- Document the new service, its port, and the runtime configuration mechanism in `docs/`, and update `docs/index.md`.
