# 004.02 — Sign in

## Context

The web client can render a sign-in button and can construct an OIDC client, but
the two have never been connected. `startSignIn()` logs a placeholder,
`RequireSession` saves a destination nobody reads, and there is no callback route
at all — so `/callback`, which `start-deployment.sh` has registered with Zitadel
since 004.01, resolves to the not-found page.

This prompt closes the loop: press the control, go to the provider, come back,
and land on a page that needs a session. It is the first point where the
application does something real for a user, and the first point where an
attacker-influenced value (`state.from`) is followed — so open-redirect
validation is the security work of the prompt, not a footnote.

Two decisions, confirmed with the user, differ from the prompt's literal wording:

1. **`AuthProvider` performs the code exchange**, not the callback route.
   `react-oidc-context`'s init effect already calls `userManager.signinCallback()`
   whenever `hasAuthParams()` is true, behind a `didInitialize` ref that survives
   StrictMode. Calling `signinRedirectCallback()` in the route as well would
   exchange the same code twice, and the second call throws "No matching state
   found in storage" — rendering an error on a _successful_ sign-in. The route
   becomes presentational, reading `useAuth()`.
2. **The session is derived here, not in 004.03.** Without it the callback
   navigates to `/companies`, `RequireSession` sees `null` and bounces to `/` —
   the exact redirect loop this prompt must make impossible. 004.03's prompt is
   amended to own reload recovery, expiry and sign-out only.

## Step 2 — the redirect-target validator (Opus)

**New file:** `apps/frontend/tcp-frontend/src/auth/redirect-target.ts`.

```ts
import { matchPath } from 'react-router';

/** Where a signed-in user lands with no usable saved destination. */
export const DEFAULT_SIGNED_IN_PATH = '/companies';

/**
 * The routes a returning user may be sent to: exactly the ones behind
 * `RequireSession` in `App.tsx`. `/` and `/callback` are deliberately absent —
 * returning to either is the redirect loop this prompt exists to prevent — and
 * so is the catch-all, which matches everything and would make the allow-list
 * decorative.
 *
 * ponytail: hand-maintained beside the route table rather than derived from it.
 * A guarded route added later and not listed here loses the return-to-page
 * behaviour, which is an inconvenience and not a hole. Derive it from a shared
 * route array if the table outgrows a screenful.
 */
const RETURNABLE_ROUTES = ['/companies', '/company/:companyId'];

/**
 * The path to send a user to after signing in, given whatever came back in the
 * OIDC `state`.
 *
 * The input is attacker-influenced twice over: `RequireSession` and
 * `handleUnauthorized()` both take it from the address bar, and it then makes a
 * round trip through the identity provider. Following it unchecked is an open
 * redirect, so this returns nothing but a path this application's own route
 * table declares.
 *
 * Parsed with `URL` rather than matched as a string, because the WHATWG parser
 * folds `\` into `/` for HTTP origins: `/\evil.example` becomes
 * `//evil.example` and fails the origin check, where `startsWith('/')` would
 * have waved it through. `javascript:` parses to a null origin and fails the
 * same check.
 */
export const safeRedirectTarget = (state: unknown): string => {
  const from =
    typeof state === 'object' && state !== null && 'from' in state
      ? state.from
      : undefined;

  if (typeof from !== 'string') return DEFAULT_SIGNED_IN_PATH;

  let url: URL;
  try {
    url = new URL(from, window.location.origin);
  } catch {
    return DEFAULT_SIGNED_IN_PATH;
  }
  if (url.origin !== window.location.origin) return DEFAULT_SIGNED_IN_PATH;

  // The query string is kept: `handleUnauthorized()` saves `pathname + search`,
  // so a validator matching bare paths would silently discard it.
  return RETURNABLE_ROUTES.some((route) => matchPath(route, url.pathname))
    ? url.pathname + url.search
    : DEFAULT_SIGNED_IN_PATH;
};
```

## Step 3 — mount the provider and derive the session (Opus)

**New file:** `apps/frontend/tcp-frontend/src/auth/AuthSession.tsx` — exports one
component only (`react-refresh/only-export-components` is an error here).

```tsx
/**
 * Turns the OIDC user into the {@link Session} the shell reads.
 *
 * The OIDC user always wins; `fallback` is what stands in when there is none.
 * That ordering is the point: `main.tsx` passes `?devSession=`'s stand-in and
 * the test tier passes a literal, and neither may displace a real signed-in
 * user — nor, once 004.03 puts a token behind the session, imply one.
 */
export const AuthSession = ({
  fallback = null,
  children,
}: {
  readonly fallback?: Session | null;
  readonly children: ReactNode;
}) => {
  const { isAuthenticated, user } = useAuth();
  const sub = isAuthenticated ? user?.profile.sub : undefined;

  return (
    <SessionProvider session={sub === undefined ? fallback : { userId: sub }}>
      {children}
    </SessionProvider>
  );
};
```

**`src/main.tsx`:** wrap with `<AuthProvider userManager={getUserManager()}>` —
the existing singleton, never a fresh settings object — and replace the
`SessionProvider` call with `<AuthSession fallback={readDevSession(window.location.search)}>`.
Resulting stack: `StrictMode > QueryClientProvider > AuthProvider > ThemeProvider

> BrowserRouter > AuthSession > App`.

**`src/test-support/render-app.tsx`:** mirror that stack (this is the
carried-forward requirement from 004.01), factoring the shared part into a
non-exported `Providers` component, and add a second export for tests that need
the real `window.location`:

```tsx
export const renderAppAt = (path: string, session: Session | null = null) => …
  // Providers > MemoryRouter initialEntries={[path]} > AuthSession fallback={session} > App

/**
 * Renders at a real browser URL rather than a memory entry. The callback route
 * needs it: `AuthProvider` decides whether to exchange a code by reading
 * `window.location`, which `MemoryRouter` does not touch — so a memory-only
 * render would have the router on `/callback?code=…` and the library seeing `/`.
 */
export const renderAppAtUrl = (url: string) => {
  window.history.replaceState({}, '', url);
  return render(…); // Providers > BrowserRouter > AuthSession > App
};
```

**`src/test-setup.ts`:** every component test now mounts `AuthProvider`, which
constructs the manager, which reads the runtime config. Supply one:

## Step 5 — the callback route (Sonnet)

**New file:** `apps/frontend/tcp-frontend/src/pages/CallbackPage/CallbackPage.tsx`.
No CSS file — `NotFoundPage` has none either.

```tsx
/**
 * Where the identity provider returns the user.
 *
 * It exchanges nothing itself. `AuthProvider` has already called
 * `signinCallback()` by the time this renders — behind a ref that survives
 * StrictMode's double mount — so a second exchange here would fail on the same
 * code and report an error for a sign-in that worked.
 *
 * **Nothing on this page redirects to the provider on its own.** Every route
 * back out is a control the user pressed. That is what makes a redirect loop
 * impossible rather than unlikely: a failing callback that re-attempted
 * sign-in would bounce between here and the provider with nothing to stop it.
 */
export const CallbackPage = () => {
  useDocumentTitle(t('page.callback.title'));
  const auth = useAuth();

  if (auth.isLoading) {
    /* <main><h1/><LoadingState label={t('callback.loading')} /></main> */
  }
  if (auth.isAuthenticated) {
    return <Navigate to={safeRedirectTarget(auth.user?.state)} replace />;
  }
  // …error branch
};
```

Error classification — a helper in the same file:

```ts
const errorKey = (error: AuthContextProps['error']): StringKey =>
  error === undefined
    ? // No error and no user means the page was opened on its own:
      // `AuthProvider` only exchanges when the URL carries auth parameters.
      'callback.error.direct'
    : error.innerError instanceof ErrorResponse &&
        error.innerError.error === 'access_denied'
      ? 'callback.error.cancelled'
      : 'callback.error.failed';
```

`ErrorResponse` is exported by `oidc-client-ts`; `instanceof` keeps this free of
`any`. `callback.error.failed` deliberately covers both a provider error and a
replayed callback ("No matching state found in storage") — the user's action is
the same in each, and naming the second would be describing our storage to them.

The error branch renders, inside `<main>` with the same `<h1>`:

- `<ErrorState message={t(key)} channel="auth" onRetry={…} />` — `onRetry` is
  `undefined` for `callback.error.direct` (there is nothing to retry) and
  otherwise `() => { void startSignIn(); }`.
- `<Link to="/">{t('page.notFound.home')}</Link>` in every error case, so there
  is always a way out that does not involve the provider.
