# 002.01 — Application infrastructure

Create a plan to scaffold the web application: a React + Vite project in the frontend workspace, with the conventions every later prompt depends on already in place.

> **Follows:** [ADR-021](../../ADRs/ADR-021-web-ui-framework-and-architecture.md) (framework and architecture), [ADR-022](../../ADRs/ADR-022-monorepo-workspace-structure.md) (workspace structure), [ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md) (component library, theming)
> **Needs first:** 002.00 (monorepo restructuring)

## Model allocation

**The plan must open with a short section allocating work between models.**

- **Opus drives the implementation** and reviews everything before it lands.
- Opus may delegate parts of the work to sub-agents, choosing the most appropriate model for each part.
- Name the parts where **Sonnet** is a good fit — mechanical, well-specified, repetitive or high-volume work — to keep costs down.
- Keep judgement-heavy work with Opus: architecture, security, accessibility behaviour, and anything where an ADR leaves a choice open.

Good Sonnet candidates here: the Vite/eslint/prettier/TypeScript configuration files, and the boilerplate of the theme and strings modules once their shape is agreed. Opus should own the shape of those two seams, and the pre-paint theme script.

## Goal

Stand up an application that builds, runs, lints and type-checks — and that already has the seams later work relies on, because they are expensive to retrofit once components exist.

Nothing user-facing ships here. The landing page is 003.01.

## Requirements

- A React + Vite application in `apps/frontend/tcp-frontend/`, producing a static build.
- React Router for navigation, with URLs that can be deep-linked and refreshed.
- TanStack Query v5 available as the only server-state cache. No separate client-state store.
- Every user-facing string resolves through a single lookup — a `strings.ts` module, or a trivial `t('key')` function. **No strings inlined in JSX.** No translation library and no locale files yet; this exists so the phase 03 translation work replaces one module instead of rewriting every component.
- Theme values (colour, spacing, borders) resolve through CSS custom properties. **No literal values in component stylesheets.** Component CSS files carry meaningful class names with empty rule bodies, to be filled per theme later.
- Two themes exist as structure, even if mostly empty: `default` and `high-contrast`, each with light and dark modes.
- Theme selection is a user choice, seeded from the browser's `prefers-color-scheme` and `prefers-contrast` and then remembered. The system settings set the starting point; they don't override the user.
- `prefers-reduced-motion` is honoured from the start.
- The app runs in development on a port that follows the repo's existing `EXPOSE_PORT_*` convention — not a hardcoded one.

## Implementation notes

- React Aria Components provides component behaviour ([ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md)). It ships no styling at all, so a minimal base stylesheet is needed from day one — otherwise focus rings and borders are invisible and early screens can't be reviewed by sighted testers.
- The chosen theme must be readable before the page first paints, or it flashes the wrong theme. That means a small inline script in the document head, ahead of the bundle.
- `eslint-plugin-jsx-a11y` is wired in as a lint error, not a warning — it's part of the existing zero-warnings rule.
- The frontend gets its own eslint, prettier and TypeScript configuration. It cannot share the root Node-targeted setup.
- Keep this prompt's output boring: no speculative abstractions, no component library wrappers "for later". The seams above are the exception, and they exist because retrofitting them is disproportionately expensive.

## Testing

- Vitest and Testing Library are configured and running in this workspace — the testing tier itself is 002.02, but this prompt must leave a working `npm test` behind.
- At least one real test proving the setup works end to end: render something, query it by role, assert on it.
- A test covering the theme seam: switching theme changes the applied custom properties, and the user's choice survives a reload.
- A test covering the strings seam: a component renders text via the lookup, not a literal.
- Verify the production build produces a static bundle that can be served from a plain file server.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y` rules. No `any` casts.
- The frontend's lint, typecheck and test commands run in CI, not just locally.
- Document the new application in `docs/` and register it in `docs/index.md`.
