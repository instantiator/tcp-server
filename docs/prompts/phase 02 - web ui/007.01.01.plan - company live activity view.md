# 007.01 — Company live activity view

## Context

This is the capability the web client exists to provide, and the thing `tcp-cli`
cannot match: several live views at once, on one screen, updating while the user
reads. 006.01 left `<TabPanel id="activity">` deliberately empty for it.

Four lists — active agents, tasks, agent-to-agent consultations, user enquiries
— each with its own loading, error and empty states, its own announcer channel,
and a stable sort. One list failing must not blank the others.

### Three decisions taken before planning

**1. Data path: query-first, per ADR-025.** The prompt says to "render from the
stream's priming, without a separate fetch". 005.02 shipped the opposite and
ADR-025 ratifies it: `useEventStream` does not expose audit events to callers at
all — it folds every event into the TanStack Query cache via `applyEvent`, which
patches rows carrying a summary and invalidates otherwise. Priming's role in
that design is **reconnect recovery**, not initial render.

Stream-first would need `useEventStream` widened, a second source of truth beside
the cache that 008.x's dialogs will read, and — decisively — the collection lifted
into `CompanyPage`, because the activity view mounts inside the `!isPending &&
company !== undefined` branch, _after_ the subscription opened, and would
therefore miss its own priming.

So: the four existing hooks fetch, and the stream patches. The prompt's "no
separate fetch" note and its matching test are dropped, recorded as a deviation.
One targeted fix to `cache.ts` closes the gap that made the note attractive.

**2. Agent and consultation rows are non-interactive.** The originating design
said they open an "assignment dialog"; ADR-020 does not contain one. Tasks and
enquiries stay interactive because they have real dialogs (008.03, 008.04).
ADR-020 is titled _a window on a running company, not a control panel_ — this is
that. Recorded in ADR-020 and written into 008.01 and 008.03.

**3. Notifications are deferred to 008.04.** `Notification` requires a
`durableHref`, and an enquiry has no URL until 008.04 decides whether dialogs are
routes or state. A new enquiry is still announced individually (ADR-027) and
still appears in the enquiries list, which is the durable record — so nothing a
user can perceive is lost by waiting.

### Two things the prompt gets wrong, corrected here

- **"defaulting to active and paused"** — `paused` is an _agent_ status, not a
  task one. `TcpTaskStatus` is `ready | planning | in-progress | finalising |
succeeded | failed | cancelled`. The filter defaults to the four non-terminal
  statuses, which is exactly `ACTIVE_TASK_STATUSES` from 006.01.
- **The 'add new' control is deferred to 008.07**, which the prompt itself says
  covers it in full. Both actions it offers open dialogs that do not exist yet
  (008.05, 008.02), so building it here ships a menu whose every item is inert.

## Step 1 — `cache.ts` patches agent rows by `agentId` (Opus)

`apps/frontend/tcp-frontend/src/events/cache.ts`.

A live `agent` row carries **no summary** — 002.04 widened the routing predicate
but not the ~8 places that write agent state, several in `tcp-agent` across a
process boundary. Today that falls to `invalidateQueries({ queryKey: ['agent'] })`,
so every agent status change refetches the whole agents list. Agent status is the
highest-frequency event on the company stream; the activity view is the first
thing that would feel it.

The row does carry what a patch needs: `event.agentId` at the envelope's top
level, and `payload.newStatus`. Synthesise the summary and fall through to the
existing patch path — nothing below changes:

```ts
// Live `agent` rows carry no summary (002.04 widened the routing predicate,
// not the writers), but they do carry the two fields a list row needs. Without
// this, the most frequent event on the company stream refetches the whole
// agents list; with it, the row it names is patched in place.
const patch = hasStringId(summary)
  ? summary
  : entity === 'agent' &&
      typeof event.event.agentId === 'string' &&
      typeof newStatus === 'string'
    ? { id: event.event.agentId, status: newStatus }
    : undefined;
```

An agent whose row is not cached still falls to the trailing
`invalidateQueries([entity, 'list'])`, which is how a newly created agent
appears. That stays.

**Tests** in `cache.test.ts`: a summary-less agent event patches the matching
cached row's `status` and does **not** invalidate; one naming an uncached agent
still invalidates `['agent','list']`; a summary-less event for any other entity
still invalidates as before.

**Boundary:** no change to the summary path, the delta path, or the entity guard.

## Step 2 — `useListChangeAnnouncement` (Opus)

New: `apps/frontend/tcp-frontend/src/announce/useListChangeAnnouncement.ts`.

ADR-027 wants each list's changes combined and throttled into one phrase
describing _what changed_. `announcer.ts` already does the combining, the
throttling and the `{count}`; the missing piece is noticing what changed.

```ts
export const useListChangeAnnouncement = (
  ids: readonly string[] | undefined,
  options: {
    readonly channel: string;
    readonly added: StringKey;
    readonly removed?: StringKey;
    readonly throttleMs?: number;
    /** Reseeds silently when it changes — a filter change is not a change. */
    readonly resetKey?: string;
  },
): void => { … };
```

Behaviour:

- Holds the previous `ids` in a ref. The **first** non-`undefined` value seeds it
  and announces nothing — the initial load is `useLoadingAnnouncement`'s job.
- Then: one `announce({ channel, change: added })` per id that is new, and one
  per id that has gone if `removed` is given. The announcer counts the repeats
  into `{count}`, which is what turns four added tasks into "Tasks: 4 added".
- When `resetKey` changes, reseed the ref and announce nothing.
- **Guard on the value that changed, never on whether the effect has run** —
  `StrictMode` invokes it twice on mount and spends a run-count flag on the
  first. `ErrorState.tsx` is the pattern to copy.

Because every list is filtered client-side to its open/active rows, "left the
list" _is_ "finished", so `removed` needs no status knowledge.

**Tests** (`useListChangeAnnouncement.test.tsx`, `virtual.spokenPhraseLog()`):
first render silent; a burst of adds produces **one** phrase with the right
count; an id leaving produces the removed phrase; a `resetKey` change is silent;
rendering under `StrictMode` announces once, not twice.

## Step 5 — `ActivityList`, the shared frame (Sonnet)

New: `src/pages/CompanyPage/activity/ActivityList.tsx` and `activity.css`.

One component, four uses. It owns the whole accessibility contract so the four
lists cannot drift apart:

```tsx
export interface ActivityListProps {
  readonly heading: string;
  readonly headingLevel?: 2 | 3;
  readonly isPending: boolean;
  readonly error: Error | null;
  readonly onRetry: () => void;
  readonly channel: string; // the announcer channel, also the error's
  readonly count: number;
  readonly emptyBody: ReactNode;
  readonly children: ReactNode; // the <ul>, when there is one
  readonly note?: string; // the consultations approximation
}
```

Renders `<section className="activity-list" aria-labelledby={headingId}>` with an
`h3`, the item count, an optional `note`, and one `aria-busy` region holding the
four mutually-exclusive branches in `CompaniesPage.tsx`'s exact shape:
`isPending` → `LoadingState`; `error !== null` → `ErrorState` with `onRetry`;
`count === 0` → `EmptyState` with an explicit `headingLevel`; otherwise
`children`. Each condition spelled out in full, not short-circuited.

`h3` because the page's `h1` is the company name and the tab panel sits under it
— `EmptyState` inside therefore takes `headingLevel={4}`.

The stylesheet follows ADR-026: meaningful class names, **empty rule bodies**, no
literal colour, spacing or border value.

## Step 6 — the four lists and the filter (Sonnet)

New: `src/pages/CompanyPage/activity/lists.tsx` — four thin components plus the
filter, all consumed only by `CompanyActivity`. Each takes `companyId`, calls its
hook, filters, announces, and hands rows to `ActivityList`.

| List          | Hook                                                               | Client-side filter             | Row shows                          | Channel         |
| ------------- | ------------------------------------------------------------------ | ------------------------------ | ---------------------------------- | --------------- |
| Agents        | `useAgents({ companyId })`                                         | `ACTIVE_AGENT_STATUSES`        | role name, status, `initialPrompt` | `agents`        |
| Tasks         | `useTasks({ companyId })`                                          | the filter's selected statuses | `shortcode`, `request`, status     | `tasks`         |
| Consultations | `useAssignments({ companyId, taskId: 'null', mode: 'consultee' })` | `ACTIVE_ASSIGNMENT_STATUSES`   | role name, status                  | `consultations` |
| Enquiries     | `useConversations({ companyId, status: 'awaiting_user' })`         | `status === 'awaiting_user'`   | `roleName`, `question`             | `enquiry`       |

Four points that are not obvious:

- **`taskId: 'null'` is the literal string.** `AssignmentController` tests
  `taskId === 'null'` and maps it to `IsNull()`; an omitted parameter means "any
  task". This is the consultations query from ADR-023, and it is an
  approximation — hence `note={t('activity.consultations.partial')}`.
- **Filter client-side as well as in the query.** An event patches a row's status
  in place, so a task that succeeds stays in a list fetched with the old filter
  and a closed enquiry stays in the `awaiting_user` list. The rendered filter is
  what makes rows leave.
- **Role names need `useCompanyRoles(companyId)`.** Agent and assignment rows
  carry `roleId` only; `AgentResponseDto` omits the `role` relation and nothing
  eager-loads it. Build a `Map` once in `CompanyActivity` and pass it down.
  Enquiries already carry `roleName`.
- **Do not render `completedSteps`/`totalSteps`.** They are on
  `TaskChangeSummary` but not on `TcpTask`, so they are absent on first paint and
  appear after the first stream patch. A field that materialises out of nothing is
  worse than one that was never shown.

**Order is stable**: render in the order the API returned, filtered. New items
land where the server puts them and status changes update in place. Do not sort
by recency — it moves content out from under someone mid-read.

Announcements, one channel each, via `useListChangeAnnouncement`:

- agents → `announce.agentsStarted` / `announce.agentsFinished`
- tasks → `announce.tasksAdded` / `announce.tasksCompleted`, `resetKey` = the
  serialised filter selection, so changing the filter announces nothing
- consultations → `announce.consultationsOpened` / `announce.consultationsClosed`
- enquiries → `announce.enquiryNew`, `throttleMs: ANNOUNCE_IMMEDIATE_MS`, **no
  `removed`**. Its own channel, not a throttle override on a shared one: a
  channel's interval is fixed by the announcement that opens its window, so an
  immediate announcement joining an open list window would wait behind it.

**The filter** is a React Aria `CheckboxGroup` labelled `t('activity.filter.label')`,
one `Checkbox` per `TcpTaskStatus`, defaulting to `ACTIVE_TASK_STATUSES`. State
lives in the tasks list. Every `className` must repeat React Aria's own default
(`react-aria-CheckboxGroup`, `react-aria-Checkbox`) — passing `className`
**replaces** the default rather than composing with it.

## Verification, end to end

Beyond the gates, against a running deployment:

1. Open a company with work in flight. All four lists populate on arrival.
2. Start a task from `tcp-cli` and watch it appear without a reload; watch an
   agent's status change in place while the list order holds.
3. Trigger a user enquiry and confirm it appears in the enquiries list.
4. Stop tcp-server. The stream error appears **above** the lists and the lists
   stay readable — they are stale, not blank.
5. Restart it. The stream reconnects, the server re-primes, and the lists
   correct themselves without a reload.
6. Deselect every task status: the tasks list shows its empty state, and the
   other three are untouched.
7. With VoiceOver or NVDA: confirm a burst of task changes produces one phrase,
   a new enquiry interrupts on its own, and changing the filter says nothing.
