# 003.02.01 — Application shell, routing and header plan

## Context

`apps/frontend/tcp-frontend` currently has exactly one route. `App.tsx` renders
`<Route path="/" element={<LandingPage />} />` and nothing else, and its own doc
comment says "the route table, the catch-all and the shell are 003.02". Every
path other than `/` loads the app document — nginx already falls back to
`index.html` (002.03) — and then renders **nothing at all**. `hosting.spec.ts`
asserts the 200 and deliberately stops there, because the rendering half is this
prompt's.

So this prompt builds the frame every later view sits in: the route table, the
public/protected split, the header, and the accessibility behaviour that
surrounds navigation. Getting it right once means 006, 007 and 008 inherit it.

Confirmed against the code before planning:

- `App.tsx` carries `<span hidden>{channelForAgent('boundary-control')}</span>` —
  the reachable value import keeping the `@tcp/shared/client` bundling control
  alive. It must survive the rewrite.
- `LandingPage.tsx` owns the page's only `main`, and `LandingPage.test.tsx`
  asserts the full heading outline `[[1, app.title], [2, …], [2, …]]`.
- `ThemeControl` (`src/theme/ThemeControl.tsx`) exists, is written for reuse and
  has its own tests. The theme precedent for context is two files:
  `useTheme.ts` (context + hook + types) and `ThemeProvider.tsx` (the component),
  split because `react-refresh/only-export-components` is an **error** here.
- `startSignIn()` in `src/auth/sign-in.ts` is the established seam shape: one
  exported function, a `console.info` body, a doc comment naming the prompt that
  replaces it. Sign-out gets the same treatment.
- `react-aria-components` 1.20 exports `MenuTrigger`, `Menu`, `MenuItem`,
  `Popover` and the `Key` type, with default class names `react-aria-Menu`,
  `react-aria-MenuItem`, `react-aria-Popover`. No deprecations on that path
  (unlike `Radio`, which bit 003.01 mid-implementation).
- `react-router` 8.3 exports `Outlet`, `Navigate`, `useLocation`, `useNavigate`,
  `matchRoutes` — everything a nested-layout route table needs, with no data
  router.
- All nine `--tcp-color-*` tokens needed already exist in both theme files
  (`surface`, `border`, `text`, `accent`, `focus`, …). **This prompt adds no new
  token**; if a step thinks it needs one, that is a stop-and-report.
- `expectNoA11yViolations(container)` accepts `document.body`, which is what a
  portalled popover needs.

### Decisions taken with the user before planning

1. **Branch:** `git checkout p02/003_landing-page-and-shell && git reset --hard
phase-02`. The branch is fully merged (PR #71) and `phase-02` has moved on
   since (the TS 6 upgrade), so nothing is lost and the README's
   one-branch-per-major-index rule holds — 003.02 and 003.03 land on it, then
   one more PR into `phase-02`.
2. **The not-found page renders inside the shell**, and the header shows its
   account menu only when there is a session. This is the decision that makes
   the shell reachable at all: no protected route can be reached in a real
   browser until 004.02 exists, so without it the skip link, the header and the
   route-change behaviour would have no browser-tier coverage whatsoever. The
   conditional is also simply correct — a signed-out visitor must not be offered
   "Sign out".
3. **The skip link is native** — `<a href="#main-content">` with
   `<main id="main-content" tabIndex={-1}>`. jsdom does not move focus on
   fragment navigation, so the component tier asserts it is the first tab stop
   and targets `main`'s id, and the **browser tier** asserts focus actually
   lands. Same split 003.01 used for contrast and pseudo-elements.

### Two findings that shape the work

**The company view's title is loaded data, not a route-table constant.** That
rules out holding page titles alongside paths in a route table: `/company/:id`
is titled by the company's name, which 006.01 fetches. So each page owns its
title through a `useDocumentTitle(title)` hook, and the route-change effect in
`App` reads `document.title` after it has been set. This is correct by React's
commit ordering — child effects flush before parent effects — and that ordering
is the one subtle thing in this plan, so it is commented at both ends.

**React Aria's `Breadcrumb` only supplies `aria-current="page"` to a React Aria
`Link`.** Verified in `dist/private/Breadcrumbs.mjs`: it computes
`isCurrent = node.nextKey == null` and passes `aria-current` down through
`LinkContext`, which a `react-router` `Link` never reads. Adopting RAC's
breadcrumb properly would therefore mean adopting RAC's `RouterProvider` too, to
keep its links client-side. A breadcrumb has no keyboard behaviour to inherit —
it is a `nav`, an `ol` and some links — so this one is built from native
elements with an explicit `aria-current` on the last crumb, and the
`RouterProvider` question is carried into 006.01 where RAC links may actually
proliferate. The account menu still uses React Aria, as the prompt requires:
that one is all behaviour.

### Out of scope

The application announcer with its coalescing and throttling is 003.03 — this
prompt ships one polite live region carrying the page title, which 003.03
replaces. Real sign-in is 004.02; the callback route arrives with it, not here.
Sign-out is 004.03. The profile and memberships dialogs are 008.06. The
companies overview and company view are 006.01; this prompt ships placeholder
pages behind their routes.

### 4. The session abstraction and route guard (Opus)

Two files, mirroring the `useTheme.ts` / `ThemeProvider.tsx` split — that split
exists because `react-refresh/only-export-components` is an error in this
workspace, and a module exporting both a component and a hook fails it.

`src/auth/useSession.ts`:

```ts
import { createContext, use } from 'react';

/**
 * Who is signed in. Deliberately the smallest thing the shell needs — the
 * header greets nobody, and 008.06's profile dialog reads the ID token's claims
 * directly rather than through this (ADR-023, there is no `/api/me`).
 */
export interface Session {
  /** The OIDC `sub` claim: the stable identifier for this user. */
  userId: string;
}

/**
 * `null` means signed out, which is every session in the application until
 * 004.03 fills the provider in.
 */
export const SessionContext = createContext<Session | null>(null);

/** The current session, or `null` when signed out. */
export const useSession = (): Session | null => use(SessionContext);
```

`src/auth/session.tsx` — both components, since neither is a hook:

```tsx
import type { ReactNode } from 'react';
import { Navigate, Outlet, useLocation } from 'react-router';
import { SessionContext, useSession, type Session } from './useSession';

/**
 * Supplies the session to the tree.
 *
 * The `session` prop is the seam, in two directions at once. 004.03 replaces
 * this body with one that derives the session from the token client (ADR-024)
 * and drops the prop; until then the application mounts it with no session, so
 * every protected route redirects — which is correct, because there is no way
 * to sign in yet. And every component test from here on renders inside this
 * shell, so passing a literal session object is all mocking a signed-in user
 * ever needs to be. No `vi.mock`, no fake token, no auth library in the tests.
 */
export const SessionProvider = ({
  session = null,
  children,
}: {
  session?: Session | null;
  children: ReactNode;
}) => <SessionContext value={session}>{children}</SessionContext>;

/**
 * The application's only access gate: a layout route that renders its children
 * when there is a session and sends the visitor to the landing page when there
 * is not.
 *
 * `replace`, so the protected URL does not stay in the history — otherwise the
 * back button walks straight back into the redirect. The attempted path is
 * carried in location state for 004.02, which returns the user there after
 * signing in; **that prompt must validate it before navigating**, because a
 * destination read back out of history is attacker-influenced (an open
 * redirect). Nothing here dereferences it.
 */
export const RequireSession = () => {
  const session = useSession();
  const location = useLocation();

  return session === null ? (
    <Navigate to="/" replace state={{ from: location.pathname }} />
  ) : (
    <Outlet />
  );
};
```

### 5. Route-change focus and announcement (Opus)

`src/shell/useDocumentTitle.ts`:

```ts
import { useLayoutEffect } from 'react';

/**
 * Sets the document title for the page currently rendered.
 *
 * The title lives with the page rather than in the route table because
 * `/company/:companyId` is titled by the company's name — loaded data, which no
 * table can hold (006.01). A layout effect, not an effect, so the title is set
 * within the same commit as the render that requested it.
 *
 * This is half of the route announcement: `App`'s route effect reads
 * `document.title` back, and React flushes child effects before parent ones, so
 * it is guaranteed to read the new page's title rather than the previous one.
 * A page that forgets to call this announces the page before it — which is what
 * the per-page title assertions in §9 are there to catch.
 */
export const useDocumentTitle = (title: string): void => {
  useLayoutEffect(() => {
    document.title = title;
  }, [title]);
};
```

`src/shell/useRouteChange.ts`:

```ts
import { useEffect, useRef, useState } from 'react';
import { useLocation } from 'react-router';

/**
 * Moves focus to the page's main heading on every route change and returns the
 * text to announce — the page title, politely, once focus has moved (ADR-027).
 *
 * Route change is one of exactly four points at which this application moves
 * focus. Don't add a fifth here.
 *
 * Three deliberate choices:
 *
 * - **Not on first render.** Arriving at a URL is not a route change, and
 *   yanking focus out of the document on load is a worse experience than the
 *   browser's own starting position.
 * - **`tabIndex` is set here rather than declared on each page's `h1`.** A page
 *   that forgets the attribute would fail silently — `focus()` on a
 *   non-focusable element does nothing and throws nothing — so the one place
 *   that needs it is the one place that sets it. `-1` makes the heading
 *   programmatically focusable without adding a tab stop.
 * - **The heading is found in the DOM, not through a ref.** A ref would have to
 *   be threaded through every page and every layout to reach here, and the
 *   thing being focused is defined by the rendered document, not by the tree.
 */
export const useRouteChange = (): string => {
  const { pathname } = useLocation();
  const [announcement, setAnnouncement] = useState('');
  const isFirstRender = useRef(true);

  useEffect(() => {
    if (isFirstRender.current) {
      isFirstRender.current = false;
      return;
    }

    const heading = document.querySelector('h1');
    if (heading !== null) {
      heading.tabIndex = -1;
      heading.focus();
    }

    setAnnouncement(document.title);
  }, [pathname]);

  return announcement;
};
```

Two consecutive routes sharing a title announce once, because the live region's
text does not change. Note it in the doc comment; it cannot happen with the
MVP's titles and 003.03 owns the general case.

```tsx
import {
  Button,
  Menu,
  MenuItem,
  MenuTrigger,
  Popover,
  type Key,
} from 'react-aria-components';
import { startSignOut } from '../auth/sign-out';
import { useSession } from '../auth/useSession';
import { t } from '../strings';
import './Header.css';

/**
 * Handles a choice from the account menu.
 *

/**
 * The header on every page except the landing page (ADR-020).
 *
 * The account menu renders only for a signed-in user. An unknown address is
 * reachable signed out, and offering a signed-out visitor "My profile" and
 * "Sign out" would be a lie about their state — and one that becomes actively

 * exactly those defaults.
 */
export const Header = () => {
  const session = useSession();

  return (

          link: this prompt invents no navigation the MVP has not asked for. */}
      <span className="app-header__logo">{t('app.title')}</span>

        <MenuTrigger>
          <Button className="react-aria-Button app-header__account">
            {t('header.account.label')}
          </Button>
          <Popover>
            <Menu onAction={onAccountAction}>
              <MenuItem id="profile">{t('header.account.profile')}</MenuItem>
              <MenuItem id="memberships">
                {t('header.account.memberships')}
              </MenuItem>
              <MenuItem id="signOut">{t('header.account.signOut')}</MenuItem>
            </Menu>
          </Popover>
        </MenuTrigger>
      )}
    </header>
  );
};
```

```tsx
import { Link } from 'react-router';
import { t } from '../../strings';
import './Breadcrumbs.css';

/** One step in the trail. The last crumb has no destination — it is here. */
export interface Crumb {
  label: string;
  to?: string;
}

/**
 * Where the user is, and the way back up (WCAG 2.4.8, adopted by ADR-026).
 *
 * Built from `nav`/`ol`/`li` rather than React Aria's `Breadcrumbs`, which is
 * the one place in this application where the library earns nothing: it has no
 * keyboard behaviour to inherit, and it supplies `aria-current="page"` only
 * through its own `Link` component — adopting it would mean adopting React
 * Aria's `RouterProvider` too, to stop those links doing full page loads. Four
 * lines of native markup against a router-wide integration.
 *
 * First used by the company view (006.01); nothing renders it yet.
 */
export const Breadcrumbs = ({ items }: { items: readonly Crumb[] }) => (
  <nav className="breadcrumbs" aria-label={t('breadcrumbs.label')}>
    <ol className="breadcrumbs__list">
      {items.map((item) => (
        <li className="breadcrumbs__item" key={item.label}>
          {item.to === undefined ? (
            <span aria-current="page">{item.label}</span>
          ) : (
            <Link to={item.to}>{item.label}</Link>
          )}
        </li>
      ))}
    </ol>
  </nav>
);
```

```tsx
 * content announces nothing at all (ADR-027).
 *

 * boundary's positive control reachable from the entry point. 005.02's SSE
 * client is the first screen that will import from the shared package for real,

          <Route path="*" element={<NotFoundPage />} />
        </Route>
      </Routes>

      <span hidden>{channelForAgent('boundary-control')}</span>
    </>

};
```

## As implemented

Everything the prompt asked for landed. Three things the plan got wrong or did
not foresee — one of them a real defect that every automated gate missed.

### The route-change guard was wrong in the browser, and green in jsdom

The plan's `useRouteChange` guarded "not on first render" with a boolean ref.
`main.tsx` wraps the application in `StrictMode`, which invokes every effect
**twice on mount**: the first invocation spent the flag, and the second one
focused the `h1` and announced the page title **on arrival** — precisely what
ADR-027 forbids and what the hook's own doc comment claimed it prevented.

The component test asserting exactly this ("neither announces nor moves focus on
first render") passed throughout, because `render-app.tsx` did not wrap in
`StrictMode` while `main.tsx` did. The test was asserting a configuration the
application never runs.

Two changes, and neither is worth having without the other:

- The guard now remembers the **last path it acted on** rather than whether it
  has run. Keying on the value that actually changed is immune to being invoked
  again for the same navigation.
- `renderAppAt` wraps in `StrictMode`, so the provider stack genuinely matches
  `main.tsx` — which its doc comment already claimed.

Confirmed both ways: with the old guard restored under the new helper, two tests
fail — the first-render one, and the skip link's tab-order test, because focus
had already jumped to the heading and the first Tab overshot it. That second
failure is the more interesting one: the bug was reachable from a test that was
not looking for it.

This was only ever going to be found by running the application. It is the
clearest argument in this phase for §12 existing at all.

### Deferring the skip link's proof to the browser tier was right, and nearly cost a false finding

The first review pass reported that activating the skip link left focus on
`body`. It does not: read after the fragment navigation settles, the URL carries
`#main-content` and focus is on `main`. The first measurement was polluted by
the StrictMode defect above — focus was already on the `h1` at load, so the tab
sequence was one step off.

Worth recording because the failure and the artefact looked identical, and the
tempting response to the first reading would have been to add a JavaScript
`onClick` fallback to a native behaviour that works.

### The focus ring on the heading is correct, and looks like a bug

After navigating by **mouse**, the focused `h1` computes `outline-style: none`;
after navigating by **keyboard**, a 2px solid ring. That is `:focus-visible`
doing its job — a mouse user who just clicked a link does not need a ring on the
destination heading, and a keyboard user does. Verified with
`el.matches(':focus-visible')` in both directions rather than inferred.

### `toBeVisible()` on the skip link asserted nothing

Verification step 4 — delete `.skip-link:focus` and watch the browser test fail
— did not fail. Playwright calls an element visible when it has a non-empty
bounding box, and the skip link is clipped to 1x1 rather than hidden, so
`toBeVisible()` holds whether or not the rule that reveals it exists.

This is the same shape as 003.01's `data-focus-visible` assertion, which its
plan described as "the assertion that would have caught S3 being absent" and
which also passed with the rule deleted. Twice now, an assertion written to
guard a CSS rule has been satisfied by something the rule does not control.

The test now reads the computed `clip-path` and the rendered width, and was
confirmed both ways: it passes with the rule and fails with it suppressed. The
suppression was done by injecting an overriding stylesheet from the browser
rather than by editing the source, which is the safer way to run this check.

### §12 — the accessibility review

Run against a real Chromium instance driving the dev server, with the session
provider temporarily given a literal session so protected routes were reachable.

- **Tab order on a signed-in page**: Skip to content → Account → document. Both
  stops report a 2px outline, and the skip link is unclipped once focused.

- **Account menu**: `aria-haspopup="true"`, `aria-expanded` flips false→true,

- **Popover paint**: surface background, bordered, positioned — the thing §3

- **Landmarks per route**: exactly one `main` and one `h1` on `/`, `/companies`,
  `/company/:id` and an unknown address. `header` present on three, absent on
