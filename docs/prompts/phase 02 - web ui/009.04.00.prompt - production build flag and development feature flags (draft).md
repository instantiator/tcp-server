# 009.04 — Production build flag and development feature flags

Create a plan to give every build an explicit statement of whether it is a production build, use that to remove development-only capabilities from the artefact rather than merely switch them off, and put the remaining runtime-adjustable behaviour behind a small, deliberate flag mechanism.

## Goal

Development conveniences accumulate, and each one is a small hole in the shipped
product. This prompt establishes the rule that decides their fate — **a
development-only capability is absent from a production build, not disabled in
one** — and gives the codebase the single flag that makes the rule enforceable.

The same flag then does the ordinary, unglamorous work of setting sensible
production defaults, starting with the log level.

## Requirements

**A build knows what it is**

- Every artefact carries an explicit, build-time statement of whether it is a production build. Set by the build pipeline, not inferred at runtime from a hostname, a port or the absence of a development server.
- One answer per artefact, reachable from anywhere in that codebase, named the same way in each.
- **Audit what already exists before adding anything.** The web client has `import.meta.env.PROD`/`DEV`, which Vite substitutes at build time and which the development session hatch already relies on. The backend services have their own conventions, and `NODE_ENV` may already be doing part of this job inconsistently. The deliverable may be "adopt and document what is there", and that is a better outcome than a second mechanism beside the first.

**Development-only capabilities are removed, not disabled**

- **`?devSession=<id>` is the first and most urgent case.** Carried forward from 003.02: `src/dev/dev-session.ts` lets a query string stand in for a signed-in user, so the shell could be tested before sign-in existed. It is guarded by `import.meta.env.DEV` and is genuinely absent from a production bundle today — `test/browser/app-shell.spec.ts` proves it twice, behaviourally and by searching the served JavaScript. **That guarantee must survive this prompt, and every later one.**
- **Nothing else stands behind that guarantee any more.** Carried forward from 004.03. The reason `?devSession=` has been tolerable is not the build flag alone — it is that a `Session` is a user id and nothing else, so a session built from a query string carries no credential to misuse and every API call it leads to is still refused. 004.03 added reload recovery, expiry handling and sign-out **without** putting a token in the `Session`, deliberately, so that property still holds. But the work that would have broken it has now been done and did not, which means the next change to that type will not feel like the dangerous one. From here the build flag is the whole of the defence. Treat it as load-bearing rather than as belt-and-braces, and say so in `src/dev/dev-session.ts`.
- The rule to establish: a capability that must not exist in production is compiled out, and its absence is asserted against the built artefact. A runtime `if` around it ships the code and leaves only a condition between an attacker and the capability.
- Produce the list of what qualifies. It is short today; the point is that it stays enumerated rather than discovered later.

**Feature flags, with the two kinds kept apart**

- **Development affordances** — compiled out of production, as above. `?devSession=` is one.
- **Unreleased features** — shipped in the artefact, off by default, switchable so an unfinished feature can be exercised in a real deployment. These are present in production by definition, which is exactly why they must not be confused with the first kind.
- A flag is settable from the query string. Decide, and state, whether it persists beyond the page that set it — a flag that survives silently is one that gets left on.
- **Do not build a flag framework for one flag.** Two concrete uses exist (the session stand-in, the log level) and a third is anticipated. Build for those; the shape can grow.

**Log level**

- The default follows the production flag.
- Overridable by a query-string flag, so a live problem can be diagnosed without a rebuild.
- The web client has no logging abstraction at all today — components call `console` directly, and the slop gate already objects to some of that. Introducing one is in scope here; making every existing call site use it may not be.

## Implementation notes

- **The distinction this prompt exists to enforce.** `import.meta.env.DEV` is replaced by a literal at build time, so `if (import.meta.env.DEV)` leaves unreachable code the minifier deletes. A value read from configuration at runtime does not do this, however carefully it is checked. The two look almost identical in the source and are not remotely equivalent in the artefact.
- A flag mechanism is the natural place to accidentally undo that: routing a development-only capability through a general runtime flag lookup ships it. Whatever is built must make the compiled-out path the easy one to take.
- Query-string flags are visible to anyone who can put a URL in front of a user. Nothing that grants access, elevates permission or exposes data may be reachable that way, in any build.
- The log level override is the case to think hardest about: a verbose level can put tokens, ids and payloads into a place the user can read and paste into a bug report.
- Consider what a flag should do when it is not recognised — silently ignoring a typo means a developer believes a feature is on when it is not.
- Backend services share `libs/tcp-shared`; if a flag concept belongs anywhere shared, it belongs there rather than duplicated per app.

## Testing

- **Assert absence against the built artefact, not the source.** The pattern already exists in `test/browser/app-shell.spec.ts`: navigate to `/companies?devSession=someone` against a real deployment and confirm the route guard still redirects, and separately fetch the served bundle and confirm the parameter name does not appear in it. The component tier runs with `DEV` true by construction and reports the opposite of production, so it cannot answer this question at all.
- Every development-only capability on the list gets that pair of tests. A capability with no absence test is one nobody will notice returning.
- A test that an unrecognised flag behaves as decided, rather than as an accident.
- A test that the log level default differs between a production and a development build, and that the override changes it.
- **A test that a flag cannot grant access.** Whatever the mechanism ends up being, assert that a query string cannot produce a session, a token or a permission in a production build.
- **Assert against the production bundle that no token reaches browser storage.** Carried forward from 004.01: `src/auth/user-manager.test.ts` proves the _configuration_ — an `InMemoryWebStorage` user store, with only the PKCE verifier and `state` in `sessionStorage` — but it proves it in jsdom, against settings the test constructed itself. The shipped artefact is a different question, and it is the one the security property is actually about. Sign in against a real deployment, then enumerate every key and value of `localStorage` and `sessionStorage` and assert no access, ID or refresh token appears. Match on the token strings, not on expected key names, so a renamed or additional key is still caught.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings. No `any` casts.
- No development-only capability relies on a runtime check alone — each one's absence from a production build is asserted by a test.
- Confirm no flag, in any build, can be used to reach data or elevate permission.
