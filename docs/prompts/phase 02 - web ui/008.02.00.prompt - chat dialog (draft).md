## Goal

The main way a user talks to an agent. Several conversations can be open at once, so the dialog behaves more like a chat client than a modal form.

## Requirements

- A chat view holding every currently open conversation.
- Each conversation shows a small amount of context: the role, and the assignment reference if there is one.
- Each conversation renders its agent's event stream as a conversation, using the transcript from 008.01.
- **Interactive**: when the agent is waiting on the user, they can type and send.
- **Each conversation's token-level streaming deltas (`StreamDelta`) belong in that conversation's own local state.** Carried forward from 005.02: they arrive through `useEventStream`'s `onDelta` callback and must never be written to the query cache — with several conversations open at once, that also means keeping each one's deltas separate, not pooled.
- A control to close one conversation.
- A close control for the dialog itself:
  - with no conversations open, the dialog disappears
  - with conversations still open, it **minimises to a bar at the bottom** rather than closing
- Starting a new chat with a role, entered from the live activity view's 'add new' control (008.07).

## Decision to make during planning

**Do minimised chats keep streaming?**

Four minimised chats, plus a task dialog, plus the live activity view, is six connections — the browser's limit under HTTP/1.1, and the reason HTTP/2 is required ([ADR-025](../../ADRs/ADR-025-browser-event-stream-consumption.md)).

Decide, and record, whether a minimised chat holds its connection or releases it and re-primes when restored. **This is exactly the kind of thing that otherwise gets decided by accident.** If they release, work out how a restored chat catches up — the agent stream synthesises a terminal event for late subscribers, which helps but doesn't cover everything.

## Implementation notes

- Sending a message returns immediately; the reply arrives on the event stream, not in the response. The UI must reflect "sent, waiting" rather than appearing to hang.
- Get connections through the subscription manager (005.02) so the connection limit is enforced.
- Starting a chat creates a chat-mode agent, then messages go to that agent.
- **Never announce a partial response** ([ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md)) — this dialog is where that rule matters most, since it's the main streaming surface.
- The minimise-to-bar behaviour is unusual for a modal. Make sure a minimised chat is still reachable by keyboard and describable by a screen reader — it isn't just visually parked.
- Several conversations open at once means several transcripts; keep each one's state separate.

## Testing

- Component tests for the dialog, queried by role and accessible name.
- Tests for both close behaviours: last conversation closes the dialog; remaining conversations minimise it instead.
- A test that a minimised chat can be restored by keyboard and is announced properly.
- A test of sending a message, including the waiting state before a reply arrives.
- Tests with several conversations open, confirming their state stays separate.
- **An announcement test using `@guidepup/virtual-screen-reader` and `spokenPhraseLog()`**, confirming a streaming reply produces no per-token announcements and one announcement on completion.
- A test covering whichever minimised-streaming decision is made — including the catch-up path if connections are released.
- Accessibility assertions on the dialog in both states, with no violations.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- No hardcoded user-facing strings, and no literal values in stylesheets.
- The minimised-stream decision is recorded in the code or the docs, not left implicit.
