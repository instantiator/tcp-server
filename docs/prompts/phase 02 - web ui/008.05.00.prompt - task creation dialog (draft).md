## Goal

The one place in the MVP where a user creates something. It's the entry point to everything the live activity view then shows.

## Requirements

- Fields matching what `tcp-cli` asks for when creating a task — check the CLI's task creation command for the current set rather than assuming.
- Create and cancel controls.
- Validation feedback before submitting, shown clearly and accessibly.
- Server-side rejections are shown clearly too — including any soft warnings the API returns alongside a successful response.
- Opened from the live activity view's 'add new' control (008.07).
- After creating, the user can see the new task without hunting for it.

## Implementation notes

- Look at `apps/tcp-cli/src/commands/create-task.ts` and its supporting code for the real field set. Don't guess it.
- Decide whether creating also **starts** the task, or only creates it. The API separates the two, and `tcp-cli` exposes both. Whichever is chosen, make it obvious to the user which happened.
- Material or attachment upload is part of the CLI's flow. Decide whether it's in scope here, and say so — if it isn't, don't leave a half-built control behind.
- The API returns soft data-quality warnings in a response header on some create routes. These don't fail the request, and they're useful — surface them rather than dropping them.
- Validation errors must be **associated with their fields**, not just listed at the top, or a screen reader user can't tell which field is wrong.
- Focus moves to the first invalid field on a failed submit.
- The task list updates when a task is created — the live stream should cover this, so avoid a manual refetch if the event already does the job.

## Testing

- Component tests queried by role and accessible name, with every field reachable and labelled.
- Tests of validation: each rule, and that errors are associated with their fields.
- A test that focus lands on the first invalid field after a failed submit.
- A test of a successful creation, and that the new task appears in the list.
- Tests of server-side rejection and of soft warnings being shown.
- A test that the whole form is completable by keyboard alone.
- Accessibility assertions on the dialog, including the error state — **not just the empty form**, since that's where problems usually are.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- No hardcoded user-facing strings, and no literal values in stylesheets.
- If the field set diverges from `tcp-cli`'s, that's a deliberate decision and should be recorded.
