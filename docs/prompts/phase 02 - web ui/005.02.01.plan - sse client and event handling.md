# 005.02 — Event stream client and event handling

## Context

The web UI's whole point is live views, and nothing in the browser can read the
server's event streams yet. The browser's built-in `EventSource` can't be used,
because it only accepts a URL and these streams need an `Authorization` header
(ADR-025). `tcp-cli` already reads exactly these endpoints with `fetch` +
`ReadableStream`, in two small tested files — so this prompt moves that reader
into `@tcp/shared/client`, adds the one thing it lacks (reconnection), and wraps
it in a connection manager plus a rule for turning events into cache updates.

Three server routes emit the same wire union: `GET /api/{company,task,agent}/:id/events`.
All three are guarded by `CompanyMembershipGuard`, so a non-member gets `403` at
connect — a permanent refusal the backoff must not chew on forever.

**Verified payload shape** (this is what the cache mapping keys off):

```ts
payload: { entity: 'company'|'task'|'agent'|'assignment'|'enquiry',
           newStatus?, reason?, summary?: TaskChangeSummary | ... }
```

The summary is nested under `payload.summary`, not spread. Plenty of real events
carry an `entity` and **no** summary — `{ entity: 'company', reason: 'replay' }`
(`company-priming.service.ts:73`), `{ entity: 'agent', newStatus: Running }`
(`chat.service.ts:120`). Those are the invalidate case.

## Step 2 — `readWireStream` reports how the stream ended (Sonnet)

Currently it swallows everything and returns `void` — best-effort, which is
right for the CLI and useless for a reconnect loop. Add a return value and an
open callback rather than throwing, so **zero CLI call sites change** (they
ignore the return) and there is no unhandled-rejection hazard on the CLI's
`void readWireStream(...)` calls.

```ts
export type StreamEnd =
  | { reason: 'done' } // server closed it
  | { reason: 'aborted' } // our signal fired
  | { reason: 'failed'; status: number; cause?: unknown }; // status 0 = never landed

export async function readWireStream(
  url: string,
  token: string,
  signal: AbortSignal,
  onEvent: (event: WireEvent) => void,
  onOpen?: () => void, // called once the response is ok; resets the caller's backoff
): Promise<StreamEnd>;
```

Mapping: `!res.ok` → `{ reason: 'failed', status: res.status }`; no `res.body` →
`{ reason: 'failed', status: 0 }`; a thrown error with `signal.aborted` →
`{ reason: 'aborted' }`, otherwise `{ reason: 'failed', status: 0, cause }`;
reader `done` → `{ reason: 'done' }`. Status `0` deliberately matches
`ApiError`'s "never landed" convention in `src/api/errors.ts`.

Add spec cases for each of the five outcomes and for `onOpen` firing once.

**Done:** CLI specs still green with no call-site edits.

## Step 3 — `apps/frontend/tcp-frontend/src/events/connect.ts` (Opus)

One reconnecting connection. No React, no cache, no manager.

```ts
export interface Connection { close(): void }
export const connect = (
  url: string,
  onEvent: (event: WireEvent) => void,
  onError: (error: ApiError) => void,
): Connection
```

Constants: `RETRY_BASE_MS = 1000`, `RETRY_CAP_MS = 30_000`.

The loop, per attempt:

1. `await whenResumable(signal)` — resolves at once when `navigator.onLine &&
!document.hidden`; otherwise waits on `online` / `visibilitychange`.
2. `const token = await getAccessToken()` from `src/auth/access-token.ts` —
   **inside the loop, every attempt**. If `null`, `void handleUnauthorized()`
   and stop. Never hoist this out of the loop; a captured token works for hours
   and then fails permanently at the first blip after expiry.
3. `await readWireStream(url, token, signal, onEvent, () => { attempt = 0 })`.
4. On the result:
   - `aborted` → return.
   - `done` → backoff, retry (a server-closed stream is a drop).
   - `failed`, `status === 401` → `void handleUnauthorized()` un-awaited, call
     `onError(new ApiError(401, …))`, **return**. Not a transient failure.
   - `failed`, `400 <= status < 500` → `onError(new ApiError(status, …))`,
     **return**. This is the `403` membership refusal (and `404`): permanent,
     surfaced, never retried.
   - anything else (`0`, 5xx) → transient; backoff and retry without surfacing.
5. Backoff: `Math.min(RETRY_CAP_MS, RETRY_BASE_MS * 2 ** attempt)` scaled by
   `0.5 + Math.random() * 0.5` (jitter), slept with an abortable timer that also
   resolves early on `online` / `visibilitychange`. `attempt++`.

`close()` aborts the controller and stops the loop; it must be safe to call
twice. Remove every listener on close.

**Tests** (`connect.test.ts`, vitest fake timers, `vi.stubGlobal('fetch', …)` —
the same hand-rolled pattern as `src/api/client.test.ts`; there is no MSW here):

- backoff grows, is capped at 30s, resets after `onOpen`
- retries pause while `navigator.onLine` is false, and resume immediately when it flips
- same for `document.hidden`
- **fresh token on reconnect** — mock `getAccessToken` to return `'token-a'`,
  let the stream drop, change it to `'token-b'`, and assert the `Authorization`
  header on the _second_ `fetch` call is `Bearer token-b`. Asserting only that
  `getAccessToken` was called again passes against a reader that then sends a
  captured value. Name the real failure in the test: a capturing reader does not
  fail at expiry, it fails at the first network blip _after_ expiry and then
  never recovers.
- 401 calls `handleUnauthorized()` and does not retry
- 403 calls `onError` with `ApiError(403)` and does not retry

## Step 4 — `src/events/subscriptions.ts` (Opus)

```ts
export const MAX_STREAMS = 12;   // ponytail: constant, not config. Double the
                                 // HTTP/1.1 ceiling; raise it when a real view needs more.
export const streamUrls = {
  company: (id: string) => `/api/company/${id}/events`,
  task:    (id: string) => `/api/task/${id}/events`,
  agent:   (id: string) => `/api/agent/${id}/events`,
};
export const subscribe = (
  url: string,
  onEvent: (event: WireEvent) => void,
  onError: (error: ApiError) => void,
): () => void;   // returns unsubscribe
```

A module-level `Map<string, { connection, listeners: Set, errors: Set }>` keyed
by URL. First subscriber to a key opens a connection; the last to unsubscribe
closes it and deletes the entry. Unsubscribe must be idempotent — React
StrictMode double-invokes effects, and a refcount that goes negative or an
unsubscribe that runs twice will silently tear down a live connection.

Before opening a **new** key, if `map.size >= MAX_STREAMS`: `console.error` with
the cap and the refused URL, then **throw** an `Error` naming both. Visible
refusal, not silent queuing.

**Tests** (`subscriptions.test.ts`, with `connect` mocked):

- two subscribers to one URL cause exactly one `connect` call, and both receive events
- the connection closes only after the last unsubscribe
- unsubscribing twice does not close a connection a later subscriber reopened
- the 13th distinct URL throws, and the message names the cap

## Step 5 — `src/events/cache.ts` (Sonnet)

```ts
export const applyEvent = (queryClient: QueryClient, event: WireEvent): void
```

Rules, in order:

1. `event.type === 'stream'` (a `StreamDelta`) → **return immediately**. Token
   deltas never touch the cache; they are high-frequency, append-only, and
   belong to one open transcript.
2. `const { entity, summary } = event.event.payload`. If `entity` is not one of
   `EVENT_ENTITIES` from `src/api/query-keys.ts` → return. (Most audit events —
   `llm_request`, `tool_call` and friends — carry no `entity`.)
3. If `summary` is an object with a string `id`, **patch**:
   `queryClient.setQueriesData({ queryKey: [entity] }, patch)` where `patch`
   handles two shapes and nothing else —
   - an array: map rows, replacing any whose `id` matches with
     `{ ...row, ...summary }`; record whether a row matched
   - a single object whose `id` matches: `{ ...old, ...summary }`
   - anything else: return `old` untouched

   Matching on the **cached value's** `id`, not on the key, is deliberate: it
   needs no knowledge of key shapes, so it handles `['enquiry','detail',slug]`
   (keyed by slug, not id) with no special case.

   If no cached array matched, the entity is new to every cached list — then
   `invalidateQueries({ queryKey: [entity, 'list'] })`, or a created task never
   appears. Nothing matched and nothing cached is a no-op, which is correct.

4. Otherwise → `queryClient.invalidateQueries({ queryKey: [entity] })`.

`entity` is the event's own `payload.entity`, which is exactly why
`query-keys.ts` keys conversations on `'enquiry'` rather than `'conversation'`.

**Tests** (`cache.test.ts`, real `QueryClient`, `retry: false`):
a summary-carrying event patches a cached list row and a cached detail with no
refetch; an entity event with no summary invalidates its key; a `StreamDelta`
touches nothing (assert both `setQueryData` and `invalidateQueries` unspied-and-
unchanged via cache contents); an unknown entity is ignored; a summary matching
no cached row invalidates the list key.

## Step 7 — The >6-simultaneous-streams browser test (Sonnet writes, Opus reviews)

Carried from 002.03, which proved the transport (`h2` negotiated, 8 concurrent
requests open zero new connections) but could not prove the streams, because
long-lived authenticated SSE didn't exist. Eight instant requests prove nothing
about concurrency; the failure guarded against is the _seventh stream hanging
with no error_.

The Playwright tier cannot sign in today — the `?devSession=` hatch is
dead-code-eliminated from the production build it drives, and no test completes
a Zitadel login. So give it the same machine token the api tier uses.

**`scripts/run-browser-tests.sh`** — copy the env-file resolution block from
`scripts/run-api-tests.sh` (which reads `TEST_CLIENT_ID` / `TEST_CLIENT_SECRET`
from `--env-file`, else `.env.dev`, else `.env.testing`, checking the gitignored
`<env-file>.local` override written by the Zitadel bootstrap). Export those plus
`OIDC_DISCOVERY_URL`. Add `--env-file`, `--client-id`, `--client-secret` and
`--oidc-discovery-url` flags with the same precedence, and document them in the
usage block.

**`apps/frontend/tcp-frontend/test/browser/event-streams.spec.ts`** — new:

1. In Node, using Playwright's `request` fixture (it already has
   `ignoreHTTPSErrors`, so the self-signed cert is fine): fetch the discovery
   doc, then a `client_credentials` token — the same flow as
   `ApiHelper.getMachineToken`.
2. `POST /api/company` through `TCP_WEB_URL` to create a company; delete it in
   `afterAll`.
3. `page.evaluate` with the token and company id: open **seven** concurrent
   `fetch` streams to `/api/company/{id}/events`, read the first chunk from each
   with a per-stream timeout of ~15s, then abort all seven.

   Seven connections to the _same_ URL is the right test, not seven different
   entities: the browser's HTTP/1.1 cap is six per **origin**, path-independent.
   And the company stream primes with current state on subscribe, so every one
   of the seven delivers immediately if the transport allows it.

4. Assert all seven produced a chunk. Under HTTP/1.1 the seventh would hang and
   the assertion fails on timeout — which is the point.

Add a second, smaller case in the same file: assert `nextHopProtocol === 'h2'`
for one of the streams, so a regression to HTTP/1.1 fails with a clear reason
rather than a timeout.

## What this deliberately does not build

- No `EventSource` polyfill and no new SSE dependency — `fetch` +
  `ReadableStream` is already proven against these endpoints.
- No client-side event log or replay buffer. Recovery comes from the server's
  priming, which is the coupling Step 10 records.
- No per-entity hooks (`useCompanyStream` etc.). One `useEventStream(url)` plus
  three URL builders; add named wrappers when a view actually wants one.
