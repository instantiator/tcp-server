## Goal

Give the application a working identity client. This prompt sets up the machinery; the visible sign-in journey is 004.02.

## Requirements

- The app registers with Zitadel as a **public client** using Authorization Code with PKCE. It holds no secret, because a browser cannot keep one.
- **Access tokens are held in memory only.** Nothing durable is written to browser storage.
- The user is re-authenticated by a **full-page redirect**, not a hidden iframe.
- Both the API client and the event stream reader can obtain the current token.
- A single, shared policy for what happens when the API rejects a token.
- The local development stack sets the web application up automatically, the way it already does for the CLI.
- Redirect addresses are derived from the app's configured address — never hardcoded.

## Implementation notes

- Use `react-oidc-context` (over `oidc-client-ts`). Don't hand-roll PKCE.
- **The full-page redirect matters and is not interchangeable with an iframe.** An iframe depends on the identity provider's cookie being readable in a cross-origin frame — a third-party cookie, which browsers are increasingly blocking. A full-page redirect is a first-party navigation, so it keeps working. With an active provider session the user is redirected straight back, usually without seeing a login form.
- The cost is a brief redirect on page load. That's accepted: it means a cross-site scripting attack gets at most a short-lived access token, never a long-lived one.
- **The token is fetched at the moment it's needed, never captured.** A component that grabbed a token when it mounted would keep presenting an expired one after renewal — and for a long-lived event stream, would do so for hours.
- The shared 401 policy: one renewal attempt, then redirect to sign-in if that fails. Both the API client and the stream reader call the same policy, so a genuinely-gone token doesn't produce a redirect from one path and a silent failure from another.
- The app must request the `profile` and `email` scopes, or the profile dialog (008.06) shows an ID and nothing else.
- `scripts/start-deployment.sh` gains a second application registration alongside the CLI's device-flow client. Both live in one Zitadel project. The CLI's flow is untouched.
- The generated client ID and the provider address reach the app through the runtime settings from 002.03, not the build.
- **Carried forward from 002.03: `tcp-web` is currently handed the _confidential_ client.** Its `OIDC_CLIENT_ID` in `docker-compose.yml` is the same `OIDC_CLIENT_ID` tcp-server uses, as a stopgap so `config.js` had a non-empty value to serve. Repointing it at this prompt's new public PKCE registration is part of the work, not a follow-up — the container refuses to start on an empty value, so it cannot be left unset.
- **Redirect and post-logout URLs are `https://localhost:${EXPOSE_PORT_WEB}`, not http.** `tcp-web` is TLS-only because HTTP/2 requires it (ADR-025), so a redirect URI registered against `http://` will be rejected by Zitadel as a mismatch at the end of an otherwise-working sign-in. `derive-urls.sh` already exports `TCP_WEB_URL` in exactly this form — use it rather than composing the URL again.
- If the reload redirect proves too intrusive in practice, moving to `sessionStorage` is a small configuration change — but it's a **recorded decision with a stated trade-off**, not a quiet default. Don't make it here.

## Testing

- Tests that the token is requested fresh per call rather than captured — the failure mode is subtle and only appears after expiry.
- A test of the shared 401 policy: one renewal attempt, then redirect on failure, from both the API client and the stream reader.
- A test that no token is written to `localStorage` or `sessionStorage`. This is a security property and deserves an explicit assertion.
- Verify `start-deployment.sh` creates a working registration, with derived rather than hardcoded redirect addresses — including on a non-default port.
- Confirm the CLI's device flow still works after the change.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- `shellcheck` passes on the modified deployment script.
- Zero lint errors and zero warnings. No `any` casts.
- **No secrets in the codebase.** The client is public and holds none; verify nothing was added.
- Update `docs/authentication.md` to describe the browser client alongside the CLI's device flow.
