# 007.03 — Browser authentication harness

## Context

The browser tier can reach three pages: the landing page, the not-found page
and the sign-in callback. Everything else in the application is behind a
sign-in gate the tier cannot pass, so the companies overview, the company view
and the four activity lists have no browser coverage at all — only component
tests that mock the network.

007.02 tried to close that gap and could not. The backlog behind the gate grows
with every prompt: five dialogs in 008.x, a configuration view in 010.01. This
closes it now, at four views rather than ten.

### Why `?devSession=` cannot be the answer

It looks like the obvious route and is a dead end. `src/auth/user-manager.ts`
holds tokens in `InMemoryWebStorage`, and `user-manager.test.ts` asserts that
nothing reaches `localStorage` or `sessionStorage`. `?devSession=` fakes a
signed-in _shell_ and mints no token, deliberately. A test using it would sign
in and then get a 401 from every API call — a page of error states.

Serving a development bundle to CI would also stop the tier testing the
artefact that ships, and `app-shell.spec.ts` has two tests asserting the dev
hatch is _absent_ from the production build.

### What already exists, so this is smaller than it looks

- `start-deployment.sh` creates a human Zitadel user: `TEST_USERNAME` /
  `TEST_PASSWORD`, both in the committed `.env.dev` (`test` /
  `ChangeMe123!`), with a verified email.
- That user is added to `TCP_ADMIN_IDENTIFIERS`, so it sees every company with
  no membership seeding.
- `run-browser-tests.sh` already resolves `TEST_CLIENT_ID`/`TEST_CLIENT_SECRET`
  from `<env-file>.local` then `<env-file>`, and exports them only when found.
- `event-streams.spec.ts` already gets a machine token by `client_credentials`
  and calls the API directly, and already skips cleanly when credentials are
  absent.

So the missing piece is a login, and a place to keep its result.

### The mechanism, and the one thing that makes it work

The app keeps no token anywhere Playwright's `storageState` can capture. That
sounds fatal and is not: `storageState` captures **Zitadel's own session
cookie**, on Zitadel's origin. With that cookie present, a test that lands on a
guarded route is redirected to the provider, recognised without a prompt, and
sent back — and the application mints a fresh in-memory token from the code in
that callback.

So the harness stores an _identity-provider session_, not an application
session, and every test signs in for real, silently, in a few hundred
milliseconds. One file touches the login form.

## Step 2 — the setup project (Opus)

**New file:** `apps/frontend/tcp-frontend/test/browser/auth.setup.ts`.

- Navigate to a guarded route so the application starts its own redirect. Do
  not construct an authorize URL by hand: the point is to exercise the path the
  app really takes, and a hand-built URL would keep passing after the app's own
  redirect broke.
- Fill the form found in Step 1 and submit.
- Wait for the browser to arrive back on the application, signed in — assert on
  something only a signed-in page renders, never on a URL alone and never on a
  timer.
- Save `storageState` to a gitignored path under the repo-root `test-results/`,
  which CI already collects and `.gitignore` already covers.

**`playwright.config.ts`:**

- A `setup` project matching `auth.setup.ts`.
- The existing `chromium` project gains `dependencies: ['setup']` and
  `storageState`.
- Keep one project, not two. Every spec that does not want a session can clear
  it per test; splitting the tier into signed-in and signed-out projects
  doubles the matrix to serve four existing tests.

**Skipping:** if the username or password is absent, the setup project must
skip with a stated reason, and the specs that need a session must skip too
rather than fail. Follow `event-streams.spec.ts`. A contributor with no
deployment must still be able to run the tier.

**Boundary:** do not weaken `app-shell.spec.ts`'s two `?devSession=` tests.
They assert the hatch is compiled out of the production build, and that is
still true and still worth proving.

## Step 5 — journey 2: live activity (Sonnet writes, Opus reviews)

**New file:** `apps/frontend/tcp-frontend/test/browser/company-activity.spec.ts`.

Fixtures: get a machine token and create a company and a task through the API,
the way `event-streams.spec.ts` already creates a company. Do not depend on
seeded data — a test that needs a particular row to already exist fails on a
fresh deployment for a reason that has nothing to do with the code.

Assert, on the company page:

1. All four activity lists render, each found by role `region` and its
   accessible name — the same query the component tests use.
2. axe finds no violations.
3. **Exactly one event stream is open.** ADR-030 makes that a rule and the
   browser is the only place it is observable.
4. A real change moves a row: drive a task's status through the API and watch
   the page update **without a reload**. Use Playwright's own waiting on the
   expected end state. Never `waitForTimeout`.

Point (4) is the reason this tier exists. The component tier already proves
`applyEvent` patches the cache; only this proves the browser receives the event
over a real connection.

**If a journey proves flaky, delete it and record why.** Do not add a retry, do
not add a sleep, and do not lower an assertion to something that always passes.

## Notes, recorded as built

**Step 1, the login form as found** (Zitadel v4.16.1, 2026-08-09). The instance
serves the **classic** login UI at `/ui/login/…`, not the v2 Next.js one. It
takes two screens:

| Screen                            | Field        | Submit           |
| --------------------------------- | ------------ | ---------------- |
| `/ui/login/login` "Welcome Back!" | `#loginName` | `#submit-button` |
| `/ui/login/loginname` "Password"  | `#password`  | `#submit-button` |

Both submits use the same id, which is a real trap: clicking `#submit-button`
twice without waiting for the second screen would resubmit the first.

**No password-change screen.** The user is created with
`password: {password: …}` and Zitadel defaults `changeRequired` to false, so
nothing needed changing there.

**An MFA interstitial does appear, and the first reading of this was wrong.**
Probing the long-lived dev deployment showed the two screens landing straight
on `/companies`, and that was recorded here as "no MFA interstitial". It only
held because that user had signed in before. On a **freshly bootstrapped org** —
which is what CI and `run-all-tests.sh` always have — Zitadel shows a
"2-Factor Setup" screen between the password and the application. It is only an
offer, with a Skip button, but it stops the harness.

Fixed in provisioning, as this plan requires, not in the harness:
`start-deployment.sh` now removes both second factors from the login policy.
Two details cost a cycle each and are worth writing down:

- It must be the **admin** API (`/admin/v1/policies/login/second_factors/…`).
  The org carries no policy of its own (`isDefault: true`), so the
  management-API delete has nothing to act on and changes nothing, silently.
- The type is the full enum name. `OTP` is rejected with
  "type mismatch, parameter: type" — it has to be `SECOND_FACTOR_TYPE_OTP`.

A conditional "click Skip if it appears" in the setup project was rejected: a
conditional step in a test is a step nobody can tell has stopped running, and
it would have left dev and CI disagreeing about what signing in looks like.

With that, the two screens land back on
`https://localhost:5173/companies` with `<h1>Companies</h1>` rendered, which
confirms the whole round trip: the app's own redirect, the provider's session,
the callback, and a token minted into memory.

If this breaks after a Zitadel upgrade, the likely cause is the v2 login being
switched on — the selectors and the screen count both change.
