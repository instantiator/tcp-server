## Context

Four dialogs are left in the MVP, and they share one skeleton, so they are built
together.

The **response dialog** is why the MVP is interactive rather than read-only
(ADR-020). An agent that asks a question stops until someone answers it. Today
`EnquiriesList.tsx` shows blocked agents with deliberately non-interactive rows
— you can see the agent is stuck and you cannot unstick it, so `tcp-cli` stays
mandatory for the one workflow that is time-sensitive.

The **creation dialog** is the one place in the MVP where a user makes
something. Nothing in the web UI can currently create a task; `POST /api/task`
has no client hook at all.

**Profile** and **memberships** are the two smallest dialogs, reached from the
account menu. Both are read-only — editing either would need user-management
endpoints that do not exist. Their menu items are already in `Header.tsx` and
currently do nothing.

Almost everything they need exists: `Dialog` (008.01), `LoadingState` /
`ErrorState` / `EmptyState` (003.03), `Notification` (003.03, still rendered
nowhere), the announcer (003.03), the two-layer API hooks (005.01, 007.02), and
`TaskDialog.tsx` (008.03) as the worked example for stacked dialogs and focus
rehoming.

Two things genuinely do not exist and are built here, once, first:

1. **A labelled text field with an associated error message.** There is no form
   field abstraction anywhere in `src/components`. `FieldError`, `aria-invalid`
   and `aria-describedby` appear zero times in the whole codebase. Both input
   dialogs need it.
2. **Client hooks for `POST /api/task`, `POST /api/task/{id}/start`,
   `POST /api/task/{id}/materials` and `POST /api/conversation/{slug}/reply`.**
   All four routes exist on the server and none has a hook.

Intended outcome: from the activity view, answer a blocked agent's question and
watch it resume; create a task with files attached and start it; and from the
account menu, see who you are signed in as and which companies you can reach.

## Departures from the prompt, and why

Each is a departure from a stated implementation note. Nothing here licenses
further improvisation.

1. **Task create returns no soft warnings today.** The prompt says the API
   returns them "on some create routes" — `X-Tcp-Warnings` is set only by
   `api.company.controller.ts`, `api.role.controller.ts` and
   `knowledge.controller.ts`. `task.controller.ts` never sets it. The dialog
   still reads the header generically (Step 3), so it is correct if the server
   starts sending one, and the test drives it with a mocked header. No backend
   change is made to start sending task warnings — that is a data-quality
   decision, not this prompt's.

2. **The materials upload route needs a one-line backend fix before the client
   can call it.** `TaskController_uploadMaterial` generates as
   `requestBody?: never`, because the controller declares `@ApiConsumes` but no
   `@ApiBody`. openapi-fetch will refuse a `body` against that type, and the
   only ways round it are a cast (banned) or a second HTTP client that
   duplicates the 401 policy (worse). So Step 2 adds `@ApiBody` and regenerates
   the schema. This also fixes a real bug in the published OpenAPI document.

3. **`EnquiriesList` stops announcing, and `Notification` announces instead.**
   `Notification` always announces, immediately, on the channel it is given. If
   it renders on channel `enquiry` while `EnquiriesList` still calls
   `useListChangeAnnouncement` on the same channel, one arriving enquiry
   produces two announcements coalesced into one confusing phrase. One writer
   per channel is the convention, so the notification becomes that writer. The
   cost: the `removed` announcement is lost — a user is no longer told when an
   enquiry leaves the awaiting list. That is background noise (it means someone
   answered), and the list's count and `aria-busy` still change. **Flagged for
   Opus review in Step 8.**

4. **The response dialog opens no event stream.** The enquiry detail cache entry
   has the enquiry's own `id` at the top level, and the company stream that
   `CompanyPage` already holds patches it by that id. Opening a second stream
   would spend a connection from the budget of 12 for nothing.

## Step 1 — The shared form field (Sonnet)

Everything in this step is new. There is no existing pattern to follow beyond
`src/components/ChatDialog/MessageInput.tsx`, which is a single unlabelled-error
input and is **not** the pattern to copy for errors.

### Create `src/components/Field/TextField.tsx`

```ts
export interface TextFieldProps {
  /** The visible label. Already resolved through `t`. */
  readonly label: string;
  readonly value: string;
  readonly onChange: (value: string) => void;
  /** Shown, and associated with the field, when set. Already through `t`. */
  readonly errorMessage?: string;
  /** Standing help text, not an error. Already through `t`. */
  readonly description?: string;
  readonly isRequired?: boolean;
  readonly isDisabled?: boolean;
  /** Renders a `TextArea` instead of an `Input`. */
  readonly multiline?: boolean;
  /** So a failed submit can move focus here. */
  readonly inputRef?: RefObject<HTMLInputElement | HTMLTextAreaElement | null>;
}
```

Implementation, using `react-aria-components`:

- `<TextField className="react-aria-TextField tcp-field" value onChange isDisabled isRequired isInvalid={errorMessage !== undefined}>`
- `<Label className="react-aria-Label">{label}</Label>`
- `{multiline ? <TextArea ref={inputRef} className="react-aria-TextArea" /> : <Input ref={inputRef} className="react-aria-Input" />}`
- `{description !== undefined && <Text slot="description" className="react-aria-Text">{description}</Text>}`
- `{errorMessage !== undefined && <FieldError className="react-aria-FieldError">{errorMessage}</FieldError>}`

React Aria wires `aria-describedby` and `aria-invalid` from `isInvalid` +
`FieldError`. Do not add either attribute by hand. Pass `FieldError` explicit
children (not a render function) so it shows our message rather than a browser
validation string.

**Class-name trap (see `styles/base.css`):** passing `className` to a React Aria
component _replaces_ its default class. Always write
`"react-aria-X my-block__element"`, never just the custom one.

Also export from the same file:

```ts
/** Moves focus to the first field the caller has marked invalid. */
export const focusFirstInvalid = (
  fields: readonly {
    readonly error?: string;
    readonly ref: RefObject<HTMLElement | null>;
  }[],
): void => {
  fields.find((field) => field.error !== undefined)?.ref.current?.focus();
};
```

Three lines, two callers. Do not build a form library.

## Step 3 — The API layer (Sonnet)

The two-layer split is the law here and eslint enforces the import boundary:
`endpoints.ts` describes a request and nothing else; `hooks.ts` names the facade
and owns cache invalidation; components import only `hooks.ts`. Copy
`useCancelTaskMutation` (`endpoints.ts:281`) / `useCancelTask` (`hooks.ts:187`)
exactly.

### Create `src/api/warnings.ts`

```ts
/** The header tcp-server puts soft data-quality warnings in. */
const WARNINGS_HEADER = 'X-Tcp-Warnings';

/**
 * Soft warnings from a successful response, or an empty list.
 *
 * They do not fail the request. The value is a JSON array of
 * percent-encoded strings — the same shape `tcp-cli` decodes.
 */
export const readWarnings = (response: Response): readonly string[] => { … };
```

Parse defensively: a missing header, a body that is not JSON, or an entry that
is not a string each yield `[]` or are skipped. A malformed warnings header must
never turn a successful create into a failure. Mirror
`apps/backend/apps/tcp-cli/src/lib/core/api.ts:75` (`reportWarnings`) for the
decode, and `apps/backend/apps/tcp-server/src/api/validation-warnings.ts` for
the encode.

### Add to `src/api/endpoints.ts`

```ts
/** Creates a task in the `ready` state. Starting it is a separate call. */
export const useCreateTaskMutation = () =>
  useMutation({
    mutationFn: async (body: components['schemas']['CreateTaskDto']) => {
      const result = await api.POST('/api/task', { body });
      // The warnings header only survives if it is read here — `unwrap`
      // returns the body alone.
      …
      return { task, warnings };
    },
  });

/** Starts a task. 202: the work has been accepted, not finished. */
export const useStartTaskMutation = () =>
  useMutation({
    mutationFn: (id: string) =>
      unwrap(api.POST('/api/task/{id}/start', { params: { path: { id } } })),
  });

/** Uploads one task material. Rejected once the task has left `ready`. */
export const useUploadMaterialMutation = () =>
  useMutation({
    mutationFn: ({ id, file }: { id: string; file: File }) =>
      unwrap(
        api.POST('/api/task/{id}/materials', {
          params: { path: { id } },
          body: { file },
          // openapi-fetch JSON-encodes by default; multipart needs the raw
          // FormData, and the browser sets the boundary itself.
          bodySerializer: (body) => {
            const form = new FormData();
            form.append('file', body.file);
            return form;
          },
        }),
      ),
  });

/** Answers an enquiry. Closes it, and resumes the agent as a side effect. */
export const useReplyToEnquiryMutation = (slug: string) =>
  useMutation({
    mutationFn: (content: string) =>
      unwrap(
        api.POST('/api/conversation/{slug}/reply', {
          params: { path: { slug } },
          body: { content },
        }),
      ),
  });
```

Notes the implementer needs:

- `unwrap` and `api` are already imported in `endpoints.ts`. `unwrap` throws
  `ApiError` (`src/api/errors.ts`), which carries `status`.
- `create` cannot use `unwrap` as-is, because it must reach `response.headers`.
  Call `api.POST` directly, then throw `apiError(response, error)` when
  `!response.ok` or `data === undefined`, exactly as `unwrap` does — do not
  invent a different error shape.
- `start` returns 202 with the task as its body, so `unwrap` is right;
  `expectAccepted` is for 202-with-no-body and is the wrong helper here.
- `authorIdentifier` is optional on `ConversationReplyDto` and is **not** sent.
  The server already knows who the caller is from the token; sending a
  client-supplied identifier alongside a bearer token invites the two to
  disagree.

### Add to `src/api/hooks.ts`

```ts
/**
 * Creates a task, optionally uploading materials and starting it.
 *
 * One facade rather than three, because the three calls are ordered and a
 * later one is meaningless without the earlier: materials are rejected once
 * a task leaves `ready`, so they must land before the start.
 */
export const useCreateTask = () => { … };

/** Answers an enquiry and closes it. */
export const useReplyToEnquiry = (slug: string) => { … };
```

`useCreateTask` takes
`{ companyId, request, plannerRoleId?, expected?, files, start }` and returns a
mutation whose `mutationFn`:

1. creates the task;
2. uploads each file **sequentially** (a `for…of` with `await`, not
   `Promise.all` — a parallel burst of multipart uploads against one task is
   avoidable load and makes partial-failure reporting unreadable), collecting
   the names that failed;
3. starts the task **only if every upload succeeded**;
4. resolves with `{ task, warnings, failedUploads, started }`.

A failed upload does not throw and does not undo the task — the task exists and
the user must be told exactly that. A failed _create_ throws normally.

`onSuccess` invalidates `['task']` and `['assignment']`, matching
`useCancelTask` (the server cascades a task change to its assignments).

`useReplyToEnquiry` wraps `useReplyToEnquiryMutation` and invalidates
`['enquiry']` on success. Not `['agent']` — the agent resuming arrives on the
company stream, and an invalidation would be a second, slower source of the same
truth.

Query-key reminder: conversations key on `'enquiry'`, not `'conversation'`
(`src/api/query-keys.ts`).

  ```ts
   * the company has none, and when the zone string is one `Intl` refuses —
   * a bad zone must not blank the whole conversation.
   */
  const formatTime = (iso: string, timeZone: string | null): string => { … };
  ```

  `new Intl.DateTimeFormat(undefined, { timeZone, dateStyle: 'medium', timeStyle: 'short' })`

  `timeZone`.

- The reply form: a `<form onSubmit>` with `event.preventDefault()`, one
  `<TextField multiline isRequired label={t('enquiry.reply.label')} …>` from

  `t('enquiry.reply.sent')` — wording that claims only that the answer was
  sent, not that the agent has resumed, because the request returns before it

- **The already-answered case.** `useReplyToEnquiry`'s error is an `ApiError`.
  Map by status, never by the server's message text:

  ```ts

      ? 'enquiry.reply.alreadyAnswered'
      : error instanceof ApiError && error.status === 404
  ```

  removed — retrying cannot succeed, and leaving a live Send button there is
  the confusing failure the prompt warns about.
