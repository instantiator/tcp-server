## Goal

This is the capability the web client exists to provide, and the thing `tcp-cli` cannot match: several live views at once, on one screen, updating while the user reads.

## Requirements

Four lists, all live:

- **Active agents** — each showing its role and what it's working on.
- **Tasks** — with status, filterable by one or more statuses, defaulting to active and paused.
- **Agent-to-agent consultations.**
- **User enquiries** — questions from agents waiting on a person.

Plus:

- An 'add new' control offering two actions: create a task (008.05), and start a chat with a role (008.02, with a submenu of roles).
- Loading, error and empty states **per list** — one list failing must not blank the whole view. Use 003.03's `LoadingState`, `ErrorState` and `EmptyState`; don't build more.
- The view renders immediately on arrival, then keeps up as things change.
- **This prompt owns the announcement wording for all four lists.** Carried forward from 003.03: `strings.ts` currently holds only `announce.tasksAdded` and `announce.tasksCompleted`, which exist so the ADR-027 gate can assert a real phrase rather than a synthetic one. Treat both as placeholders to finalise, and add the keys the other three lists need. Because `t` has **no plural rules**, phrase every wording count-agnostically — `'Tasks: {count} added'`, never `'{count} tasks added'`, which reads wrong at one.
- **Decide where a `Notification` renders.** Carried forward from 003.03: the component exists (`src/components/Notification/`) with a required `durableHref`/`durableLabel` pair, but there is deliberately no queue, no provider and no container — where notifications sit on the page is a layout decision, and this is the first view with somewhere to put them. Whatever you build, a notification must never be the only record of an event (WCAG 2.2.3): the list below it reflects the same thing.
- **This is the first view that could plausibly hit `MAX_STREAMS = 12`.** Carried forward from 005.02: the subscription manager throws visibly rather than queuing a connection silently past that cap. If this view genuinely needs more than it allows, raise the constant deliberately — don't work around the manager by opening a raw connection outside it.

## Open question to resolve during planning

The originating prompt says selecting an agent or a consultation opens an "assignment dialog" — but **no such dialog exists** in the MVP scope ([ADR-020](../../ADRs/ADR-020-web-ui-mvp-scope.md) lists chat, task, user response, task creation, profile and memberships).

Decide and record what these two actions do. Options worth weighing:

- Open the **task dialog** (008.03) focused on that assignment. Works for an agent on a task; **doesn't work for a consultation**, which is an assignment with no task.
- Add a small assignment-scoped view reusing the shared transcript component from 008.01.
- Make consultations non-interactive for the MVP, and say so.

This affects 008.01 and 008.03, so resolve it before those are planned.

## Implementation notes

- **The company stream carries five `payload.entity` values** after 002.04: `company`, `task`, `agent`, `assignment` and `enquiry`. Priming arrives first, in this order: the company signal (no summary), one row per task, one per active agent, one per open consultation, one per open enquiry — all `reason: 'replay'`, all sharing one timestamp, none with an `id`.
- **Summary shapes** (from `@tcp/shared/client`): `TaskChangeSummary`, `AgentChangeSummary` (`id`, `status`, `roleId`, `assignmentId`), `AssignmentChangeSummary` (`id`, `status`, `mode`, `orderIndex`, `roleId`), `EnquiryChangeSummary` (`id`, `slug`, `status`, `roleName`, `question`, `createdAt`).
- **Primed rows carry a summary; live `agent` rows do not.** 002.04 widened the routing predicate but did not change the ~8 places that write agent `state_change` rows (several of them in tcp-agent, across a process boundary). A live agent row gives you `event.agentId` and `payload.newStatus` and nothing more, so render the agent list from the primed summary and apply live rows as status patches keyed on `agentId`. Keying an agent row's render on `payload.summary` will work on subscribe and then silently stop.
- **The consultations list is exactly** `GET /api/assignment?companyId=X&taskId=null&mode=consultee`. It is an approximation: a consultation requested but not yet picked up has no assignment and does not appear. Do not present it as complete.

- Subscribe to the company event stream through the subscription manager from 005.02 — don't open connections directly.
- **All four lists can only be live after 002.04.** Before that change, the company stream carries only company and task events; agents, consultations and enquiries never arrive.
- The stream primes with current state on subscribe, so the view should render from the stream rather than fetching separately and then subscribing.
- **The consultations list is an approximation** ([ADR-023](../../ADRs/ADR-023-backend-api-surface-for-the-web-ui.md)): it shows consultee assignments, so a consultation requested but not yet picked up doesn't appear. **Don't present the list as complete** — the wording matters.
- Announcements follow [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md): each list's changes are combined and throttled into one announcement, describing what changed ("Tasks: 2 added, 1 completed") rather than re-reading the list. A new user enquiry is announced individually — it's a request for the user to act.
- Use the single announcer from 003.03. **Do not add live regions per list.** The call is `announce({ channel, change, params })` from `src/announce/announcer.ts`, **one channel per list** — changes sharing a channel coalesce into one phrase, so two lists sharing one would produce a sentence describing neither.
- **The announcer counts repeats rather than de-duplicating them**, because two identical changes usually mean two things happened. Guard every announcing effect on the value that changed, never on whether the effect has run — `StrictMode` invokes it twice on mount and spends a run-count flag on the first. `ErrorState.tsx` is the pattern to copy.
- **A new enquiry announced individually needs its own channel**, not a `throttleMs` override on the shared one: a channel's interval is fixed by the announcement that opens its window, so an immediate announcement joining an open list window would wait behind it.
- **Lists keep a stable order.** New items append; status changes update in place. Re-sorting moves content out from under someone mid-read. "Most recently active first" is the obvious visual design and is rejected for this reason.
- Each list is a labelled region with a heading and an item count, fully browsable.
- The 'add new' control and its role submenu use the standard menu-button pattern; 008.07 covers it in full.

## Testing

- **Enquiries stream open and close only.** 002.04 writes one `entity: 'enquiry'` row when a conversation opens (`newStatus: 'awaiting_user'`, `reason: 'created'`) and one when it closes (`newStatus: 'closed'`, `reason: 'replied'`) — there is no per-message event, so a reply in progress is invisible until it closes. Test that the enquiries list is correct across both, and decide deliberately whether the gap between them needs any indication in the UI.

- Component tests for each list, queried by role and accessible name.
- **Tests that each list updates from a stream event**, using a mocked stream that feeds events directly.
- A test of the status filter, including its default.
- Tests that one list's failure leaves the others working.
- **Announcement tests using `@guidepup/virtual-screen-reader` and `spokenPhraseLog()`**: a burst of changes to one list produces one combined announcement, not several; a new enquiry is announced on its own.
- **A test that list order stays stable** when an item's status changes.
- A test that the view renders from the stream's priming, without a separate fetch.
- Accessibility assertions on the whole view, with no violations.
