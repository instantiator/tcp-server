# 008.03 — Task dialog

## Context

A user watching the live activity view can see tasks in flight but cannot open
one. Task rows in `TasksList.tsx` are deliberately non-interactive, with a
comment saying 008.03 adds the dialog. This prompt adds it: a task's details,
one panel per assignment showing that agent's work as a conversation, live
updates as both progress, and a confirmed control to cancel.

Everything it needs already exists. The dialog framework and `<Transcript/>`
landed in 008.01, the chat dialog in 008.02 proved the multi-panel shape, and
008.02 also recorded the connection budget this dialog has to live inside. The
one genuinely missing piece on the client is a cancel mutation — the route
`POST /api/task/{id}/cancel` has existed on the server all along and no hook
calls it.

The intended outcome: from the activity view, open a task, read what each role
has done, watch it change, and stop it.

---

## Decisions taken before planning

These were settled with the user before this plan was written. Do not reopen
them during implementation.

1. **The task dialog does not minimise.** It is a plain modal: one task at a
   time, opened from a row, closed by its Close button or Escape, with React
   Aria returning focus to the row. There is no `TaskProvider` in `AppShell`,
   no dock entry, no restore callback. The chat dialog needed all of that
   because a chat holds a half-typed message and must survive being parked; a
   task dialog holds nothing the user has authored.
2. **Assignment panels open collapsed.** Each panel header carries the role and
   the assignment's status, which is the summary; the user expands the ones
   they want to read. One rule, no seeding logic, and the connection-budget
   rule ("a collapsed panel is a parked surface") becomes the normal path
   rather than an edge case.
3. **The task's own audit history is not rendered.** The per-assignment
   transcripts are the work. `useTaskHistory` is named in the prompt's first
   Requirements bullet, but that bullet is about the `hooks.ts` import
   boundary, and no Requirement asks for a task-level event list.

## Four places this plan departs from the prompt

Each is a departure from a stated implementation note, with its reason. Nothing
below is a licence to improvise further.

1. **"The initial render needs one request" is not achievable and is not
   followed.** `GET /api/task/{id}` does return `assignments` nested, but
   `applyEvent` (`src/events/cache.ts`) patches a cached value by matching its
   **top-level** `id`. An `assignment` event carries the assignment's id, and
   the cached task detail's top-level id is the task's — so the nested array is
   never patched, and it never gains a row when the planner fans a task out
   into new assignments. The dialog therefore reads assignments from
   `useLiveAssignmentsList({ taskId })`, whose cache entry is a top-level array
   of assignment rows: `applyEvent` patches a status in place, and invalidates
   `['assignment','list']` when an id it has never seen arrives. Two requests
   on open, both live. `useLiveTaskState(taskId)` still supplies the task's own
   fields and is patched correctly by the same mechanism.
2. **The dock extensions 008.02 added are not used here**, following decision 1.
   `DockEntry.label` as a `ReactNode`, `dock.remove` and `dock.focusEntry`
   remain used only by the chat dialog. Recorded as an unresolved note with a
   testable condition, so this does not read as an oversight.
3. **The collapsible panel is hand-rolled, not React Aria's `Disclosure`.**
   `Disclosure`/`DisclosurePanel` do exist in `react-aria-components@1.20.0`,
   but `DisclosurePanel` always renders its children and hides them with the
   `hidden` attribute — a collapsed panel would keep its `<Transcript/>`
   mounted and its stream open, which is exactly what the budget rule forbids.
   Adopting it would also mean adding `.react-aria-Disclosure*` defaults to
   `styles/base.css`. The existing hand-rolled precedent, `AgentPrompt` in
   `src/pages/CompanyPage/activity/AgentsList.tsx`, already does the right
   thing: `aria-expanded` + `aria-controls`, and the collapsed content out of
   the DOM rather than clipped by CSS.
4. **The task's `materials`, `expected` and `completed` fields are not shown.**
   The generated client types all three as `Record<string, never>[]` — the
   Swagger plugin never described the artifact union — so nothing can be read
   out of them without an `any` cast. Details are the request, the status and
   the failure reason.

## Step 1 — cancel mutation hooks (Sonnet)

Two edits, following `useCompleteChatMutation` / `useCompleteChat` exactly.

**`src/api/endpoints.ts`** — add at the end of the write half, after
`useCompleteChatMutation`:

```ts
/**
 * Cancels a task: it moves to `cancelled`, and the server cascades that to its
 * still-running assignments and their agents.
 *
 * `unwrap`, not `expectAccepted` — the route answers `202` but with the
 * cancelled task as its body, and `unwrap` accepts any `ok` response that
 * carries one.
 */
export const useCancelTaskMutation = (id: string) =>
  useMutation({
    mutationFn: () =>
      unwrap(api.POST('/api/task/{id}/cancel', { params: { path: { id } } })),
  });
```

**`src/api/hooks.ts`** — add beside `useCompleteChat`:

```ts
/**
 * Cancels a task, and makes every list holding it agree.
 *
 * Both keys are invalidated because the server cascades: the task moves to
 * `cancelled` and so does every assignment still working it. The task's own
 * change arrives on its event stream, but the assignments' do not all carry a
 * summary, so a refetch is what keeps the panels honest.
 *
 * The server refuses a task that is already terminal with a `409`. The control
 * is hidden for those statuses, so this is a race rather than an ordinary
 * path — it still surfaces through `isError`.
 */
export const useCancelTask = (taskId: string) => {
  const queryClient = useQueryClient();
  const cancelTask = useCancelTaskMutation(taskId);
  return useMutation({
    mutationFn: () => cancelTask.mutateAsync(),
    onSuccess: () => {
      void queryClient.invalidateQueries({ queryKey: ['task'] });
      void queryClient.invalidateQueries({ queryKey: ['assignment'] });
    },
  });
};
```

Import `useCancelTaskMutation` alongside the other endpoint imports at the top
of `hooks.ts`. Wrap `mutateAsync` in an arrow — passing it by reference is not
a valid `MutationFunction` and only the full `npm run typecheck` catches it.

**Done:** `cd apps/frontend/tcp-frontend && npx tsc --noEmit` clean, and
`npm run typecheck` from the repo root clean.

  `t('task.assignment.label', { role: roleName, status: statusLabel(status) })`.

  own `<Heading slot="title">` is the `h2`.
- A React Aria `<Button className="react-aria-Button task-assignment__toggle"
aria-expanded={isExpanded} aria-controls={bodyId} onPress={onToggle}>` whose
  label is `t('task.assignment.collapse', { role })` when expanded and
  `t('task.assignment.expand', { role })` when not. The role is in the name
  because every panel has one of these buttons and identically-named controls
  on one screen fail WCAG 2.4.6.
- `<div id={bodyId} className="task-assignment__body">` holding, **only when
  `isExpanded`**:
  - `agentId === null` → `<EmptyState heading={t('task.assignment.noAgent.heading')} headingLevel={4}>{t('task.assignment.noAgent.body')}</EmptyState>`
    (an assignment nobody has picked up yet has no agent, so no transcript).
  - otherwise `<Transcript agentId={agentId} roleName={roleName} />`.

The conditional render is the load-bearing line, and it needs a comment saying
so: a collapsed panel must **unmount** its transcript, because that is what
releases its event stream (rule 2 of the budget, in the `MAX_STREAMS` docblock
in `src/events/subscriptions.ts`). Hiding it with CSS or with `hidden` would
hold a connection open for a surface the user cannot see.

Do not add `tabIndex={-1}` or a ref: nothing moves focus into a panel, and
collapsing leaves focus on the toggle button, which stays put.

`<Transcript/>` already renders `at-capacity` as its own message. Do not wrap
it, do not add a retry, do not treat that status as a failure.

**Role names.** Assignment rows carry only `roleId`. Look the name up inline:

```ts
const roleName = (roleId: string): string =>
  roles?.find((role) => role.id === roleId)?.name ?? t('activity.role.unknown');
```

Deliberately not `roleLabel` from
`src/pages/CompanyPage/activity/activity-list-utils.ts` — a shared component
must not import from a page's own directory. That is the same layering rule
that moved `statusLabel` into `src/api/statuses.ts` in 008.02. Do not move
`roleLabel`; one expression is smaller than the move.

**Stable order.** Sort on immutable fields only, so nothing reshuffles when a
status changes:

```ts
const ordered = useMemo(
  () =>
    [...(assignments.data ?? [])].sort((a, b) =>
      a.createdAt === b.createdAt
        ? a.id.localeCompare(b.id)
        : a.createdAt.localeCompare(b.createdAt),
    ),
  [assignments.data],
);
```

`createdAt` is an ISO-8601 string, so a lexicographic compare is a chronological
one. `id` breaks a tie only so the order is total.

**Expanded panels:**

```ts
const [expanded, setExpanded] = useState<ReadonlySet<string>>(new Set());
```

Keyed by assignment id, so a live patch cannot snap a panel shut. Toggle by
building a new `Set` from the previous one.

**Announcements** — one channel for this dialog, `` `task:${taskId}` ``. Two
effects, each seeded silently on its first run so opening the dialog announces
nothing:

```ts
// Seeded silently: the first pass records what is already on screen, so
// opening the dialog is not read out as N status changes. StrictMode's second
// invocation sees the same values and announces nothing, which is why this
// keys on the status itself rather than on a "have I run?" boolean.
const seenStatuses = useRef(new Map<string, string>());
```

- Assignment statuses: for each row, compare against `seenStatuses`, write the
  new value, and when it changed from a value that was already recorded call
  `announce({ channel: `task:${taskId}`, change: 'task.announce.assignment', params: { role, status: statusLabel(next) } })`.
  A row seen for the first time is recorded and not announced.
- The task's own status: the same shape with a single `useRef<string | null>`,
  calling `announce({ …, change: 'task.announce.status', params: { status: statusLabel(task.data.status) } })`.

Distinct `params` stay distinct clauses in the announcer and identical ones
coalesce into a count, so several changes inside one window read as
"Task: cancelled, Sales: cancelled, Legal: cancelled". Never render a live
region — ADR-027 allows exactly one in the application and the announcer owns it.

Plus the completed-wait announcement:

```ts
useLoadingAnnouncement(
  task.isPending,
  task.data === undefined
    ? null
    : {
        channel: `task:${taskId}`,
        change: 'task.announce.loaded',
        params: { shortcode: task.data.shortcode },
      },
);
```

`null` while it has not succeeded, so a failure is not also announced as a load.
It stays silent under `ANNOUNCE_LOADING_MIN_MS`, so a fast response needs no
check of its own.

**Cancel.** The control is only rendered while cancelling is legal:

```ts
const canCancel =
  task.data !== undefined &&
  (ACTIVE_TASK_STATUSES as readonly string[]).includes(task.data.status);
```

`ACTIVE_TASK_STATUSES` from `src/api/statuses.ts` is exactly the complement of
the server's terminal set in `TaskService.cancel`, so the control's visibility
and the server's `409` agree.

Confirmation is a **second `<Dialog>`**, opened from the first.
`Dialog.test.tsx` already proves stacked dialogs work. State:
`const [confirming, setConfirming] = useState(false);`

```tsx
{
  canCancel && (
    <Button
      className="react-aria-Button task-dialog__cancel"
      isDisabled={cancel.isPending}
      onPress={() => {
        setConfirming(true);
      }}
    >
      {t('task.cancel')}
    </Button>
  );
}
<Dialog
  isOpen={confirming}
  onOpenChange={(open) => {
    if (!open) setConfirming(false);
  }}
  heading={t('task.cancel.confirm.heading')}
>
  <p>{t('task.cancel.confirm.body')}</p>
  <Button
    className="react-aria-Button"
    onPress={() => {
      setConfirming(false);
      cancel.mutate();
    }}
  >
    {t('task.cancel.confirm.accept')}
  </Button>
  <Button
    className="react-aria-Button"
    onPress={() => {
      setConfirming(false);
    }}
  >
    {t('task.cancel.confirm.reject')}
  </Button>
</Dialog>;
```

The confirmation body has to say what will happen, not just ask: cancelling
stops the task and every agent working on it, and it cannot be restarted.
Neither button says a bare "Cancel" — in a dialog about cancelling a task, that
word means two opposite things.

**Focus after cancelling.** React Aria returns focus to whatever opened the
confirmation dialog, and that button is about to disappear. Copy
`ChatConversation`'s recovery exactly:

```ts
useEffect(() => {
  if (canCancel) return;
  // The cancel button has just been removed, and a focused element that
  // disappears drops focus onto the page body — which ADR-027 forbids
  // leaving it on. Only the body, deliberately: React Aria's focus scope
  // often catches this itself, and when it has, focus is already somewhere
  // deliberate and must not be moved again.
  if (document.activeElement !== document.body) return;
  details.current?.focus();
}, [canCancel]);
```

`details` is a ref on the details `<section>`, which carries `tabIndex={-1}` and
`aria-labelledby` pointing at its own heading — so focusing it says which task
this is.

**Render tree:**

```tsx
<Dialog
  isOpen
  onOpenChange={(open) => { if (!open) onClose(); }}
  heading={
    task.data === undefined
      ? t('task.dialog.heading.pending')
      : t('task.dialog.heading', { shortcode: task.data.shortcode })
  }
>
```

Inside, in order:

1. `task.isPending` → `<LoadingState label={t('task.loading')} />` and nothing
   else.
2. `task.isError` → `<ErrorState message={t('task.error')} channel={`task:${taskId}`} />`
   and nothing else.
3. Otherwise: the details `<section>` (request, status via `statusLabel`, and
   the failure reason when `failureReason !== null`), the cancel control, the
   confirmation dialog, then the assignments.
4. Assignments: `<h3>{t('task.assignments.heading')}</h3>`, then either
   `<EmptyState heading={t('task.assignments.empty.heading')} headingLevel={3}>{t('task.assignments.empty.body')}</EmptyState>`
   when `ordered.length === 0`, or one `<TaskAssignmentPanel/>` per row keyed by
   assignment id.
5. `cancel.isError` → `<ErrorState message={t('task.cancel.failed')} channel={`task-cancel:${taskId}`} />`.
   Its own channel, following `chat-complete:` in `ChatConversation`: a failed
   cancel and a failed load are different things to be told about, and one
   channel would coalesce them into a sentence describing neither.

`isOpen` is a literal `true` — the opener mounts this component only while a
task is open, and unmounting is what closes it. `hideClose` is **not** set:
unlike the chat dialog, Close here is a real, distinct outcome.

## Step 4 — behaviour tests (Sonnet)

One new file, `src/components/TaskDialog/TaskDialog.test.tsx`. **Copy the

Fixtures: task `task-1` (`shortcode: 'TASK-1'`, `status: 'in-progress'`,

Routes for `respondByRoute`, specific before general, anchored the way
`AGENT_A_ROUTE` is:

| Pattern                                         | Answers                             |
| ----------------------------------------------- | ----------------------------------- |
| `/\/api\/task\/task-1\/cancel/`                 | the task with `status: 'cancelled'` |
| `/\/api\/task\/task-1(\?\|$)/`                  | the task detail                     |
| `/\/api\/assignment\?/`                         | both assignment rows                |
| `/\/api\/company\/company-1\/roles/`            | both roles                          |
| `/\/api\/agent\/agent-a\/history/`, `…agent-b…` | one audit row each                  |
| `/\/api\/agent\/agent-a(\?\|$)/`, `…agent-b…`   | an agent fixture each               |

Harness: a `StrictMode > QueryClientProvider` tree containing a real
keyboard-reachable `<Button>Open task</Button>` that sets local state and
renders `<TaskDialog taskId="task-1" companyId="company-1" onClose={…} />`.
`DockProvider` is **not** needed — this dialog does not dock. No `ChatProvider`.
StrictMode is mandatory: it is what catches an effect guard that fires on mount.

Tests in this step:

1. The dialog renders the task's shortcode as its accessible name, and its
   request and status as text.
2. One panel per assignment, each named by its role and status, queried by
   `role: 'region'` with the name built from `t('task.assignment.label', …)`.
3. Panels are collapsed on open: no transcript `<ol>` is present, and each
   toggle has `aria-expanded="false"`.
4. Expanding one panel shows that agent's transcript; the other stays collapsed.
5. Two expanded panels keep separate state: a `stream` delta emitted on
   `agent-a` appears in Sales' transcript and nowhere in Legal's.
6. A live `assignment` `state_change` on the **task** stream updates a panel's
   status heading without a refetch.
7. A live `task` `state_change` updates the status shown in the details.
8. Stable order: emit status changes that would reorder a naive sort (make
   `assign-b` succeed while `assign-a` still runs) and assert the two region
   names are still in creation order.
