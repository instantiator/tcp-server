# 003.03 — Shared UI states, notifications and accessibility primitives

Create a plan to build the shared pieces every later view depends on: loading, error and empty states, the notification pattern, and the single announcer that speaks to screen readers.

> **Follows:** [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md) (announcement policy — this prompt implements it), [ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md) (standard, component library, "no timing" criterion)
> **Needs first:** 003.02 (application shell)

## Model allocation

**The plan must open with a short section allocating work between models.**

- **Opus drives the implementation** and reviews everything before it lands.
- Opus may delegate parts of the work to sub-agents, choosing the most appropriate model for each part.
- Name the parts where **Sonnet** is a good fit — mechanical, well-specified, repetitive or high-volume work — to keep costs down.
- Keep judgement-heavy work with Opus: architecture, security, accessibility behaviour, and anything where an ADR leaves a choice open.

Good Sonnet candidates here: the loading, error and empty state components and their tests. **Opus should own the announcer entirely** — coalescing, throttling and politeness are the hardest behaviour in the application and the thing ADR-027 exists to protect.

## Goal

This prompt turns [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md) from a policy into working infrastructure. It must land **before** any live-updating view, because retrofitting it means unpicking every component that grew its own live region.

## Requirements

- Loading, error and empty state components, usable by every data-driven view and dialog.
- A notification pattern for events that reach a user who isn't looking at the relevant view — for example, a task failing while its dialog is closed.
- **A single application-level announcer** that owns the screen reader announcements for the whole app. Components ask it to announce; they never mount their own live regions.
- Announcements are **combined and throttled**: several changes in one region become one announcement, sent at most once per interval.
- Announcements say **what changed**, not the whole new state.
- Notifications never disappear on their own as the only record of an event — the underlying view must also reflect it.

## Implementation notes

- React Aria Components provides the live announcer primitive ([ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md)); build on it rather than hand-rolling live regions.
- Scattered live regions are the standard way this goes wrong. A region mounted at the same time as its content announces all of it on mount, and several regions updating together produce interleaved, unreadable output. One announcer avoids both.
- Politeness levels: most announcements wait their turn; only failures needing action interrupt. [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md)'s per-surface table is the reference.
- The throttle interval starts around 10 seconds and is a **configurable constant**, not a hardcoded number — the manual screen reader pass will tune it.
- Loading states announce completion, not the start, and only when the wait was long enough to be worth mentioning.
- Errors appear next to whatever failed, and interrupt.
- Empty states are ordinary content with a heading, reached by browsing — they announce nothing.
- The "no timing" criterion from [ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md) means a notification that vanishes on its own can't be the only notice of something.

## Testing

This is the prompt where announcement testing gets established for real. Later prompts follow the pattern set here.

- **Announcer tests using `@guidepup/virtual-screen-reader`**, asserting on `spokenPhraseLog()`:
  - several changes within one interval produce **one** announcement, not several
  - the announcement describes what changed
  - politeness is correct per surface
  - **a burst of rapid updates does not produce a flood of announcements** — this is the specific failure ADR-027 exists to prevent
- Use fake timers to advance past the throttle interval; don't rely on real waiting.
- Component tests for loading, error and empty states, queried by role and accessible name.
- A test that a notification's information is also available somewhere durable.
- Accessibility assertions on every component here, with no violations.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- No hardcoded user-facing strings, and no literal values in stylesheets.
- The announcer's behaviour is covered by automated tests, not left to the manual pass — that's what makes [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md) enforceable.
