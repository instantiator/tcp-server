# 004.01.01 — OIDC client plan

## Context

[ADR-024](docs/ADRs/ADR-024-browser-oidc-client-and-token-handling.md) chose `react-oidc-context`, a public PKCE client, and tokens held in memory only. None of it exists. The web app has a `Session` shaped like an OIDC `sub` and a `SessionProvider` seam, and nothing that could ever produce one — `startSignIn()` logs a message, and `tcp-web` is currently handed **tcp-server's confidential client ID** as a stopgap so `config.js` had a non-empty value to serve.

This prompt builds the machinery and repoints the registration. It does not build a sign-in journey: 004.02 owns the callback route and the button, 004.03 owns deriving the session from a token, 005.01 and 005.02 own the two callers of the token accessor and the 401 policy. Everything here is therefore a module with tests and no in-app caller — deliberately, because the alternative is 005.01 discovering it needs an auth context and retrofitting one around a mounted tree.

The security property this prompt is actually responsible for is narrow and testable: **no token reaches browser storage, and no caller can hold a stale one.** Both failure modes are silent. A token in `localStorage` looks identical to a token in memory until an XSS lands, and a captured token works perfectly until it expires.

### Confirmed against the code before planning

- `react-oidc-context@3.3.1` (MIT, published 2026-03-13), peers `oidc-client-ts@^3.1.0` and `react>=16.14.0` — React 19.2.8 satisfies it. `oidc-client-ts@3.5.0` (Apache-2.0, same publication date). Both checked with `npm view`.
- [runtime-config.ts](apps/frontend/tcp-frontend/src/runtime-config.ts) exports `getRuntimeConfig()` returning `{ oidcIssuerUrl, oidcClientId }` and **throws** when `window.__TCP_CONFIG__` is absent. Nothing in `src/` calls it today; this prompt is its first consumer, which is why the manager is built lazily rather than at module load — an import-time throw would white-screen a bare `vite dev`.
- [docker/nginx/10-tcp-init.sh:44-71](docker/nginx/10-tcp-init.sh#L44-L71) hard-fails on an empty `OIDC_CLIENT_ID`, rejects quotes, backslashes and angle brackets in it, and interpolates both values into **single-quoted JavaScript string literals**. The container's variable name stays `OIDC_CLIENT_ID`; only what Compose maps into it changes. The repointing alone touches no TypeScript — `oidcLoadUserInfo` (Decision 5) is what brings `runtime-config.ts` and its tests into this prompt.
- [start-deployment.sh:363-386](scripts/start-deployment.sh#L363-L386) fetches `APP_LIST` once via `apps/_search` with an empty body — it returns every app in the project, so the second registration reuses that same response and matches on a different name. The block runs before `$DC up -d`, and `$DC` is invoked with `--env-file $LOCAL_ENV_FILE` last, so anything `set_env_var` writes reaches Compose interpolation.
- [derive-urls.sh:18](scripts/lib/derive-urls.sh#L18) already exports `TCP_WEB_URL="https://localhost:${EXPOSE_PORT_WEB:-5173}"`, and `derive_host_urls` is called at line 128, well before the Zitadel block.
- `.env.testing` sets `EXPOSE_PORT_WEB=5174`, which is what makes a hardcoded redirect URI break the browser tier rather than fail visibly in development.
- [local-env-keys.ts](libs/tcp-shared/src/config/local-env-keys.ts) is the declared single source of truth for which keys live in the gitignored `.local` file.
- `vite.config.ts` sets `NODE_OPTIONS=--no-webstorage` so jsdom owns `localStorage`/`sessionStorage` — the storage assertion runs against real storage objects, not a stub.
- `react-refresh/only-export-components` is an **error** in this workspace, which is why `session.tsx` and `useSession.ts` are split. Nothing in this prompt exports a component, so every new file is a plain `.ts`.
- `src/tsconfig.json` has `"types": []` and no Node types. Both libraries are browser-clean.

**This prompt adds no route, no component, no user-facing string and no `--tcp-*` token.** A step that thinks it needs one is a stop-and-report.

### Decisions taken with the user before planning

1. **No refresh token. The redirect _is_ the renewal.** Scopes stay `openid profile email`; `offline_access` is not requested. ADR-024's threat table says an in-memory client exposes "a short-lived access token" to an XSS, and that is only true if no refresh token exists. The consequence is that the prompt's "one renewal attempt, then redirect to sign-in if that fails" collapses into a single `signinRedirect()`: with a live Zitadel session the user bounces straight back with a fresh token and never sees a form (the renewal), and without one they see the login page (the sign-in). Zitadel decides which. Recorded as an ADR-024 amendment in §9 and as an unresolved note in §10, because it is a real divergence from the prompt's wording and must not read afterwards as an oversight.
2. **The `UserManager` singleton only; `AuthProvider` is not mounted.** Nothing in the tree consumes an auth context in this prompt, and the two real consumers of a token — a fetch wrapper and a stream reader — are not components. A module singleton is what they need and it is what makes "fetched at the moment it's needed" expressible outside React. `main.tsx` and `render-app.tsx` are untouched; 004.02 mounts `AuthProvider` **around this same instance** when there is a sign-in to drive.
3. **The browser tier verifies the registration, not a sign-in.** There is no callback route until 004.02, so a journey cannot complete. What can be proved without one is that Zitadel accepts an authorize request for the served client ID with the derived `https` redirect URI and PKCE — which fails loudly if `config.js` is still serving the confidential client, whose only registered redirect URI is tcp-server's.
4. **The client is standards-only; Zitadel appears in the bootstrap and nowhere else.** `authority` plus OIDC discovery, `response_type: 'code'` with PKCE, `openid profile email`, and a bearer token read off the user object — no vendor parameter in any of the three modules. Repointing `OIDC_ISSUER_URL` and `OIDC_WEB_CLIENT_ID` at Auth0, Okta or Entra needs no code change, which is the promise `docs/authentication.md`'s existing "Using an external OIDC provider" section already makes for the API. The Zitadel-shaped things — `accessTokenType: OIDC_TOKEN_TYPE_JWT`, `appType: USER_AGENT`, `devMode` — are all in `start-deployment.sh`, which already only targets the bundled localhost instance. Two settings carried a provider-dependent assumption; Decision 5 makes one of them configurable, and the other — the post-logout URI's reliance on an `end_session_endpoint` — is carried into 004.03 in §10.
5. **`loadUserInfo` becomes a runtime setting, `OIDC_LOAD_USER_INFO`, defaulting to `false`.** It is exactly what ADR-029's `config.js` exists for: a value that varies by deployment and cannot be baked into the build. `false` because Zitadel puts `profile` and `email` in the ID token and a userinfo round trip on every load would buy nothing; `true` for a provider that returns a minimal one. This is the difference between "edit a source file and rebuild the image" and "set a variable", and it removes the only unresolved note the client would otherwise have carried.

### Out of scope

The callback route, `startSignIn()`'s body and `{ from }` validation (004.02). Deriving `Session` from the ID token, `startSignOut()`, and closing the `?devSession=` hole (004.03). The fetch wrapper (005.01) and the stream reader (005.02) — this prompt gives them `getAccessToken()` and `handleUnauthorized()` and requires them, by carry-forward, to use both. The CLI's device flow is not touched.

### 1. The `UserManager` settings and singleton (Opus)

New file `apps/frontend/tcp-frontend/src/auth/user-manager.ts`.

```ts
import {
  InMemoryWebStorage,
  UserManager,
  WebStorageStateStore,
  type UserManagerSettings,
} from 'oidc-client-ts';
import { getRuntimeConfig } from '../runtime-config';

/**
 * The settings that make this a public PKCE client whose tokens never touch
 * durable storage (ADR-024). Exported separately from the manager so the
 * security-critical values can be asserted without standing one up.
 *
 * `redirect_uri` is derived from the origin the app was actually loaded from,
 * which is the address `start-deployment.sh` registered — deriving it here
 * rather than configuring it means a non-default `EXPOSE_PORT_WEB` cannot
 * disagree with the registration.
 */
export const createUserManagerSettings = (): UserManagerSettings => {
  const { oidcIssuerUrl, oidcClientId, oidcLoadUserInfo } = getRuntimeConfig();

  return {
    authority: oidcIssuerUrl,
    client_id: oidcClientId,
    redirect_uri: `${window.location.origin}/callback`,
    post_logout_redirect_uri: `${window.location.origin}/`,
    // Authorization Code. oidc-client-ts applies PKCE to it unconditionally;
    // there is no hand-rolled challenge anywhere in this codebase.
    response_type: 'code',
    // `profile` and `email` are not decoration: without them 008.06's profile
    // dialog has an opaque subject identifier and nothing else to show.
    scope: 'openid profile email',
    // No `offline_access`. The client never receives a refresh token, so an
    // XSS gets at most the short-lived access token that happens to be in
    // memory when it runs — which is the entire basis of ADR-024's decision.

    // The tokens. An in-memory store is emptied by a page reload, and
    // re-authentication is a full-page redirect that costs a few hundred
    // milliseconds against a live provider session.
    userStore: new WebStorageStateStore({ store: new InMemoryWebStorage() }),
    // The PKCE verifier and the `state` nonce, which must survive the
    // navigation to the provider and back and therefore cannot live in
    // memory. Neither is a token: single-use, scoped to one sign-in, and
    // worthless to an attacker who cannot also receive the callback.
    stateStore: new WebStorageStateStore({ store: window.sessionStorage }),

    // Both of these renew through a hidden iframe, which depends on the
    // provider's cookie being readable cross-origin — a third-party cookie,
    // and one browsers are removing. ADR-024 rejected the mechanism, so the
    // library must not be left to reach for it on a default.
    automaticSilentRenew: false,
    monitorSession: false,

    // The one setting here that depends on the provider rather than the
    // protocol, and therefore the one that is configured rather than decided.
    // Zitadel puts `profile` and `email` in the ID token, so the default is a
    // userinfo round trip nobody makes; a provider returning a minimal ID
    // token sets OIDC_LOAD_USER_INFO=true instead of editing this file.
    //
    // `=== true` rather than a truthiness check: a hand-written config.js
    // carrying the *string* 'false' is truthy, and the resulting behaviour is
    // the exact opposite of what was asked for.
    loadUserInfo: oidcLoadUserInfo === true,
  };
};

let manager: UserManager | undefined;

/**
 * The application's single OIDC client.
 *
 * Constructed on first use rather than at module load, because
 * {@link getRuntimeConfig} throws when `/config.js` is absent — as it is under
 * a bare `vite dev` — and an import-time throw would take the whole bundle
 * down instead of the one call that needed configuring.
 *
 * A singleton because the fetch wrapper (005.01) and the stream reader
 * (005.02) are not components and cannot read a React context, and because
 * two managers would hold two different in-memory users.
 */
export const getUserManager = (): UserManager =>
  (manager ??= new UserManager(createUserManagerSettings()));
```

### 2. `getAccessToken()` (Opus)

New file `apps/frontend/tcp-frontend/src/auth/access-token.ts`.

```ts
import { getUserManager } from './user-manager';

/**
 * The access token to present on the next request, or `null` when there is
 * none to present.
 *
 * **Call this at the moment the token is needed and do not keep the result.**
 * A caller that reads it once and holds it keeps presenting the same string
 * after the user has signed in again — for a request that is a puzzling 401,
 * and for an event stream that reconnects every few minutes it is hours of
 * them (ADR-024).
 *
 * An expired user yields `null` rather than the dead token it still holds:
 * sending one produces a 401 the caller has to interpret, where `null` is a
 * fact it can act on directly.
 */
export const getAccessToken = async (): Promise<string | null> => {
  const user = await getUserManager().getUser();
  return user !== null && !user.expired ? user.access_token : null;
};
```

Done-condition: typecheck passes; no caller anywhere yet.

### 3. `handleUnauthorized()` — the shared 401 policy (Opus)

New file `apps/frontend/tcp-frontend/src/auth/unauthorized.ts`.

```ts
import { getUserManager } from './user-manager';

/**
 * The one in-flight redirect, if any. Not cleared on success: the page is
 * navigating away, and the promise never settles from the caller's point of
 * view.
 */
let redirecting: Promise<void> | null = null;

/**
 * What happens when the API rejects the token — the single policy the fetch
 * wrapper (005.01) and the stream reader (005.02) both call (ADR-024).
 *
 * One full-page redirect to the provider. It is both halves of "renew, then
 * sign in": this client holds no refresh token, so there is nothing to renew
 * with, and the redirect is what a renewal would have been. Against a live
 * Zitadel session the user returns with a fresh token and never sees a form;
 * against an expired one they see the login page. The provider decides, and
 * the client does not have to guess which case it is in.
 *
 * Deduplicated, because a 401 rarely arrives alone: a token that has gone
 * fails the stream and every queued request at once, and each unguarded
 * caller would start its own navigation. The first one wins and the rest wait
 * on it.
 *
 * The attempted location travels in `state` for 004.02 to return the user to.
 * **That prompt must validate it against the route table before navigating**
 * — it is round-tripped through the provider and comes back
 * attacker-influenced, and following one unchecked is an open redirect.
 */
export const handleUnauthorized = (): Promise<void> =>
  (redirecting ??= getUserManager()
    .signinRedirect({
      state: { from: window.location.pathname + window.location.search },
    })
    .catch((error: unknown) => {
      // The navigation never started — a misconfigured authority, or an
      // unreachable discovery document. Clear the latch so a later 401 can
      // try again rather than resolving instantly against a dead promise.
      redirecting = null;
      throw error;
    }));
```

Done-condition: typecheck passes.

### 5. The Zitadel public client registration (Sonnet)

Edit `scripts/start-deployment.sh` only. Insert the block below immediately after line 386 (`export OIDC_CLIENT_SECRET="$APP_CLIENT_SECRET"`) and before the `# Human test user` comment. Change nothing above it.

```bash
  # Browser application — a public client using Authorization Code with PKCE
  # (ADR-024). No secret: a browser cannot keep one, so there is none to
  # regenerate and nothing to drift. accessTokenType is JWT for the same
  # reason as the CLI's client above.
  #
  # Redirect URIs come from TCP_WEB_URL (scripts/lib/derive-urls.sh), which is
  # https because tcp-web is TLS-only (ADR-029). A hardcoded port would work
  # in development and fail sign-in on .env.testing's 5174, with a
  # provider-side error that never names the port.
  #
  # devMode relaxes Zitadel's redirect-URI validation for localhost. This
  # bootstrap only ever targets the bundled localhost Zitadel; a real
  # deployment registers its client by hand.
  WEB_APP_NAME="tcp-web"
  WEB_APP_ID=$(echo "$APP_LIST" | jq -r --arg n "$WEB_APP_NAME" '.result[]? | select(.name == $n) | .id // empty')
  WEB_APP_CONFIG=$(jq -n --arg cb "${TCP_WEB_URL}/callback" --arg home "${TCP_WEB_URL}/" '{
    redirectUris: [$cb],
    postLogoutRedirectUris: [$home],
    responseTypes: ["OIDC_RESPONSE_TYPE_CODE"],
    grantTypes: ["OIDC_GRANT_TYPE_AUTHORIZATION_CODE"],
    appType: "OIDC_APP_TYPE_USER_AGENT",
    authMethodType: "OIDC_AUTH_METHOD_TYPE_NONE",
    accessTokenType: "OIDC_TOKEN_TYPE_JWT",
    devMode: true
  }')
  if [[ -z "$WEB_APP_ID" ]]; then
    OIDC_WEB_CLIENT_ID=$(zit POST "/management/v1/projects/$PROJECT_ID/apps/oidc" \
      "$(echo "$WEB_APP_CONFIG" | jq --arg name "$WEB_APP_NAME" '. + {name: $name}')" \
      | jq -r '.clientId')
    echo "  Created application: $WEB_APP_NAME (public PKCE client, no secret)"
  else
    # The redirect URI moves with EXPOSE_PORT_WEB, and a reused Zitadel volume
    # would otherwise keep the previous port's — which fails at the end of an
    # otherwise-working sign-in. Rewrite it every run, as the CLI's client
    # rewrites its secret, so Zitadel and the environment cannot disagree.
    zit PUT "/management/v1/projects/$PROJECT_ID/apps/$WEB_APP_ID/oidc_config" "$WEB_APP_CONFIG" > /dev/null
    OIDC_WEB_CLIENT_ID=$(echo "$APP_LIST" | jq -r --arg n "$WEB_APP_NAME" '.result[]? | select(.name == $n) | .oidcConfig.clientId // empty')
    echo "  Application $WEB_APP_NAME: already exists (redirect URIs rewritten to $TCP_WEB_URL)"
  fi
  set_env_var "$LOCAL_ENV_FILE" OIDC_WEB_CLIENT_ID "$OIDC_WEB_CLIENT_ID"
  export OIDC_WEB_CLIENT_ID
```

Also add `tcp-web` to the summary block's list of what was created, matching the existing wording style there.

Then the registration spec itself:

New file `apps/frontend/tcp-frontend/test/browser/oidc-registration.spec.ts`. No new script, no new env plumbing — it reads the issuer and client ID out of the served page and asks Zitadel directly.

The test issues an authorize request with a syntactically valid PKCE challenge and `maxRedirects: 0`. Zitadel answers a correctly registered public client with a redirect to its login UI; it answers an unregistered redirect URI, or a client that does not exist, with an error. That single request proves the client exists, is public, accepts PKCE, and has this deployment's derived `https` redirect URI — including the case this prompt exists to fix, since the confidential client's only registered URI is tcp-server's `http://localhost:3000/auth/callback`.

```ts
test('Zitadel accepts a PKCE authorize request for the client config.js serves', async ({
  page,
  request,
  baseURL,
}) => {
  await page.goto('/');
  const config = await page.evaluate(
    () =>
      (
        window as unknown as {
          __TCP_CONFIG__: { oidcIssuerUrl: string; oidcClientId: string };
        }
      ).__TCP_CONFIG__,
  );

  const params = new URLSearchParams({
    client_id: config.oidcClientId,
    redirect_uri: `${baseURL ?? ''}/callback`,
    response_type: 'code',
    scope: 'openid profile email',
    state: 'registration-probe',
    // 43 characters of unreserved ASCII — a well-formed S256 challenge. Only
    // its shape matters; nothing here completes the exchange.
    code_challenge: 'E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM',
    code_challenge_method: 'S256',
  });

  const response = await request.get(
    `${config.oidcIssuerUrl}/oauth/v2/authorize?${params.toString()}`,
    { maxRedirects: 0 },
  );

  // A 302 to Zitadel's own login UI. An unregistered redirect URI or an
  // unknown client is a 4xx, or a 302 carrying `error=` — both of which are
  // what a still-confidential client ID produces here.
  expect(response.status()).toBe(302);
  const location = response.headers()['location'] ?? '';
  expect(location).not.toContain('error=');
  expect(location.startsWith('/')).toBe(true);
});
```

If Zitadel's success response turns out to be a 200 rather than a 302 on this version, **assert the actual shape and say so in the report** — do not delete the assertion. The discriminating property is the absence of an error, not the status code.

## Risks

- **The dedup latch in `handleUnauthorized()` is module state, and module state is where test pollution lives.** If the unauthorized tests do not reset the module registry they will pass individually and fail in suite order, or worse, pass in suite order and hide a real latch bug. The `vi.resetModules()` in `beforeEach` is load-bearing, not hygiene.
- **`jq`'s `PUT` to `oidc_config` replaces the whole configuration.** Any field omitted from `WEB_APP_CONFIG` on the update path reverts to a Zitadel default on the second run — which would present as sign-in working on a fresh stack and failing on a restarted one. The config object is built once and used by both paths precisely to make that impossible.
- **`getRuntimeConfig()` throwing is now reachable.** Nothing in the app tree imports the auth modules yet, so bare `vite dev` still renders; the moment 004.02 mounts `AuthProvider` it will not. The lazy singleton keeps that a 004.02 problem rather than one this prompt introduces silently.
- **Nothing type-checks `10-tcp-init.sh`'s heredoc against `RuntimeConfig`.** They are a shell script and a TypeScript interface that agree by convention, and adding a third value widens the gap. A quoted `'false'` satisfies the interface, is truthy, and inverts the default — which is why the shell normalises, the client compares `=== true`, and the browser tier asserts the strict boolean. Three guards for one value because none of them is checked by a compiler.
- **The authorize probe in §7 depends on Zitadel's response shape.** If it changes across a Zitadel upgrade the test fails as a mystery rather than a regression. The `error=` assertion is the durable half; the status code is the fragile half, and the step says to report a mismatch rather than weaken it.

## As implemented

Everything the prompt asked for landed. Five things differed from the plan, one of them a real defect the plan itself introduced.

### An unconditional `oidc_config` update aborts the second run

The plan told §5 to rewrite the browser client's redirect URIs on **every** run, mirroring how the CLI client regenerates its secret every run. That is wrong, and the deployment proved it within a minute: Zitadel answers an update that changes nothing with **HTTP 400 `No changes (COMMAND-1m88i)`**, and `zit()` uses `curl -sf`, so under `set -e` the whole script died silently between "Application tcp-server: already exists" and the app services ever starting. The stack came up with only infrastructure containers and no error that named the cause.

The fix compares first: read the existing `redirectUris` out of the `APP_LIST` response already in hand, and call the API only when they differ. That removes the 400 by construction rather than by tolerating an error string, which would have been the brittle alternative across Zitadel versions.

Both branches are proven, not assumed. The unchanged path prints "already exists" and makes no API call. For the changed path I moved the registration to `https://localhost:9999/callback` by hand, re-ran, and watched it print "redirect URIs rewritten to https://localhost:5173" and restore the URI. This was the plan's own second Risk bullet, and it fired.
