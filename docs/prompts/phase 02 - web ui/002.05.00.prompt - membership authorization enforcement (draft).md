## Goal

tcp-server authenticates but does not authorize. `JwtAuthGuard` proves _who_ the caller is; nothing checks what they may do. Any valid token can read and write any company — its tasks, its knowledge, its agents.

Until now the only client was `tcp-cli`, run by an operator who already had the credentials and the intent to administer the system. A browser client with a **public** OIDC application changes that: any account the identity provider will issue a token to can reach everything.

## Requirements

- **Not blocking local MVP development**, where the operator is the only user.
- **Blocking any deployment reachable beyond localhost.** Treat this as a release gate, not a backlog item.
- Every user-facing route that names a company — directly or through a task, assignment, agent or conversation — checks that the caller belongs to that company.
- A caller who doesn't belong gets a clear rejection, not a silently filtered result.
- `?all=true` on the company list becomes restricted, rather than available to everyone.
- The permission flags already described in ADR-011 are enforced, rather than merely recorded.

## Implementation notes

- The check resolves the caller's `CompanyUser` for whichever company the action targets, and rejects when there is none.
- **Match on `sub` or email.** `CompanyUser.identifier` holds either. Matching on `sub` alone silently denies users whose membership rows were created with an email — a failure that looks like a permissions bug but is a data-shape problem.
- Most routes don't take a company ID directly. Work out how the company is resolved for task, assignment, agent and conversation routes, and make that resolution consistent rather than per-controller.
- A wrong request should **fail loudly**: a non-member asking for a company gets a rejection, not an empty list. Quietly degrading one request into a different one hides bugs and confuses users.
- `?all=true` becomes restricted to system administrators once permission groups exist. If groups don't exist yet, decide and document what it is restricted to in the meantime — don't leave it open by accident.
- Internal service-to-service routes (`/internal/*`, guarded by the API key) are **out of scope**. They are a different trust boundary.
- Consider what happens to `tcp-cli`: an operator who administers the system but was never added as a `CompanyUser` will start being refused. Decide whether that's correct, or whether the CLI's identity needs different treatment.

## Testing

- Coverage for **both** outcomes on every guarded route family: a member succeeds, a non-member is rejected. A test that only proves the happy path proves nothing about authorization.
- A test with an email-keyed `CompanyUser` row, since that path fails silently.
- Tests that the indirect routes are covered — reaching a company's task, assignment, agent or conversation as a non-member must fail, not just the direct company route.
- A test that `?all=true` is refused to an unauthorised caller.
- Confirm `/internal/*` routes are unaffected.
- Run the full suite via `./scripts/run-all-tests.sh`. Existing tests likely assume unrestricted access and will need updating — that churn is expected, and each change should be checked rather than made to pass mechanically.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings. No `any` casts.
- **A security review of the finished change**, including a deliberate check for routes that were missed. Enumerate every user-facing route and state its status; don't rely on spot checks.
- Update ADR-011's implementation status, and update `docs/authentication.md` to describe what is now enforced.
