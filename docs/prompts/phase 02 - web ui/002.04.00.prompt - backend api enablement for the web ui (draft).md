# 002.04 — Backend API enablement for the web UI

Create a plan to make the tcp-server changes the browser client needs. Without these, four MVP surfaces cannot be built.

> **Follows:** [ADR-023](../../ADRs/ADR-023-backend-api-surface-for-the-web-ui.md) (backend API surface), [ADR-029](../../ADRs/ADR-029-spa-hosting-and-runtime-configuration.md) (whether CORS is needed)
> **Needs first:** 002.03 (static hosting) — its proxy decision determines whether CORS is needed at all

## Model allocation

**The plan must open with a short section allocating work between models.**

- **Opus drives the implementation** and reviews everything before it lands.
- Opus may delegate parts of the work to sub-agents, choosing the most appropriate model for each part.
- Name the parts where **Sonnet** is a good fit — mechanical, well-specified, repetitive or high-volume work — to keep costs down.
- Keep judgement-heavy work with Opus: architecture, security, accessibility behaviour, and anything where an ADR leaves a choice open.

Good Sonnet candidates here: the stat-set query, updating existing callers and tests to pass `?all=true`, and the Swagger annotations. Opus should own the membership matching logic and the event-channel widening, since both have silent failure modes.

## Goal

The API was built for `tcp-cli` — a trusted client, run by an operator who already knows which company they mean. A browser is a different consumer: it has to discover what the signed-in user may see, and it renders four live lists on one screen.

This prompt closes that gap. It is backend-only; no frontend work here.

## Requirements

- **`GET /api/company` returns only the caller's own companies by default.** An explicit `?all=true` asks for every company.
- The company list includes a small, fixed set of per-company statistics, so the overview doesn't have to make one request per company.
- **The live activity view's four lists can all update live.** Today only tasks can — agents, consultations and enquiries never reach the company event stream.
- A user's profile can be shown without a new endpoint.
- Consultations can be listed without a new endpoint.
- CORS is available as a documented fallback for a deployment where the app and API are on different addresses, but is not switched on by default.

## Implementation notes

- **Membership matching must accept both identifier forms.** `CompanyUser.identifier` holds an OIDC `sub` **or** an email address. Matching on `sub` alone silently misses email-keyed rows — the user sees an empty list and no error, which looks identical to "you're not a member of anything". Match `identifier IN (sub, email)`.
- **`?all=true` carries no permission check in this prompt.** Any authenticated caller can still use it, exactly as today. What changes is that it becomes an explicit, named request instead of the silent default — which is the seam that 002.05 will gate. Do not imply the gap is closed.
- **Existing callers must be updated.** `tcp-cli list-companies` becomes `?all=true` so operators keep their current view, and any API test asserting "every seeded company" needs updating. A flipped default won't be caught by the compiler.
- **Widening the company event channel** is a change to `AuditEventPublisher.publish`'s predicate, which currently only forwards rows whose `payload.entity` is `company` or `task`. Adding `agent` and `assignment` reuses the existing event bus, Redis channel and SSE endpoint.
- The larger half of that work is **priming**: the live view must render immediately on subscribe, so the company stream's priming needs current agent, consultation and enquiry summaries alongside the task summaries it already sends.
- Profile data comes from the ID token's claims, read in the browser. No `/api/me` — deliberately.
- Consultations reuse `GET /api/assignment?companyId=X&taskId=null` filtered to `mode: 'consultee'`. **This is an approximation:** it returns consultee assignments, not pending consultations, so a consultation requested but not yet picked up won't appear. Note this so the UI doesn't imply the list is complete.
- The fixed stat set is: active agent count, task counts by status, and open enquiry count.
- No database migration is needed — these are query, routing and configuration changes.

## Testing

- Unit and e2e coverage for the membership filter, including **a case with an email-keyed `CompanyUser` row** — the failure here is silent, so it needs an explicit test.
- A test that `?all=true` returns every company, and that the default does not.
- Tests proving agent, assignment and enquiry events now reach the company stream, and that priming includes them on subscribe.
- Verify existing `tcp-cli` behaviour is unchanged after its update to `?all=true`.
- Confirm the stat set is computed in the same query rather than per company.
- Run the full suite via `./scripts/run-all-tests.sh` — this touches shared publish paths used by other tiers.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings. No `any` casts.
- Swagger annotations updated for changed endpoints, so the generated client (005.01) picks the changes up.
- Update `docs/` for the changed endpoint behaviour, and note the consultations approximation where the API is documented.
