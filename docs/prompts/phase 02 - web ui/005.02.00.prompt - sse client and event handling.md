## Goal

The live views are the reason this application exists. This prompt builds the plumbing they all sit on.

**The browser's built-in `EventSource` cannot be used here.** It only accepts a URL, and the streams need an `Authorization` header. The planning prompt's original recommendation predates that discovery — [ADR-025](../../ADRs/ADR-025-browser-event-stream-consumption.md) supersedes it.

## Requirements

- Read all three event streams — agent, company and task — with authentication.
- **One shared implementation of stream parsing**, used by both the browser and `tcp-cli`, so the two clients can't drift on what an event means.
- Connections are shared: several components watching the same thing use one connection, not one each.
- A hard limit on how many connections can be open, so an unexpected fan-out fails visibly instead of silently queuing.
- Dropped connections recover on their own, without losing state.
- Events update the existing view data rather than maintaining a second copy of it.

## Implementation notes

- **The query-key convention is settled: `[entity, scope, ...discriminators]`.** Carried forward from 005.01: `src/api/query-keys.ts` builds every read hook's key this way, where `entity` is the event's `payload.entity` value — not the route name. **`GET /api/conversation` keys on `'enquiry'`, not `'conversation'`**, because the event's name wins over the route's; get this wrong and `invalidateQueries({ queryKey: ['conversation'] })` silently misses every enquiry query. `EVENT_ENTITIES` in that file is the authoritative list of the five kinds an event can carry.
- **There is one error shape: `ApiError`.** Carried forward from 005.01: `src/api/errors.ts` exports `ApiError` (`status`, `message`, `body`), where status `0` means the request never landed (a network failure, not a server response). The stream reader must throw the same shape on a stream failure, not a second one a caller has to distinguish.
- Use `fetch` with a readable stream. `apps/tcp-cli/src/lib/core/sse.ts` (30 lines) and `sse-reader.ts` (43 lines) already do exactly this against these endpoints and are unit-tested. **Extend that, don't start over.**
- Move `parseWireEvents` and `wire-parse.ts` into `@tcp/shared`'s client export and have the CLI import them from there. `parseWireEvents` imports only a _type_, so it moves unchanged.
- What the existing reader lacks is **reconnection** — roughly 40–60 lines. That's the actual work here.
- Reconnect with exponential backoff and jitter, capped, resetting after a successful read. Pause retries while the browser is offline or the page is hidden, and retry immediately when either changes.
- **Recovery comes from the server, not from client bookkeeping.** The company and task streams already prime with current state on subscribe, and the agent endpoint synthesises a terminal event for late subscribers. A reconnected stream re-renders correctly on its own. This coupling is now load-bearing — note it.
- Every connection attempt fetches a **fresh** token. Reusing an expired one turns a network blip into a permanent failure loop. Carried forward from 004.01: call `getAccessToken()` from `src/auth/access-token.ts` inside the connect function, on **every** attempt including each reconnect — not once when the subscription is created. It returns `null` for an expired user as well as a signed-out one, so there is no dead token to accidentally present. A reader that captured the token at subscribe time works perfectly for hours and then fails permanently, which is why this is stated twice.
- **A 401 at connect goes through `handleUnauthorized()`** in `src/auth/unauthorized.ts`, the same policy the fetch wrapper (005.01) uses. Carried forward from 004.01: it is one deduplicated full-page redirect, so a token that has genuinely gone produces one navigation whether it was the stream or a request that noticed first — rather than a redirect from one path and a silent reconnect loop from the other. Do not treat a 401 as a transient failure for the backoff to retry; that is the distinction this shares with the 403 case below.
- **`handleUnauthorized()` now has its first caller: `onResponse` in `src/api/client.ts` (005.01).** Call it from the stream reader exactly the same way — un-awaited, and with nothing retried afterwards. It self-deduplicates, so calling it a second time from a second source is the point, not a hazard.
- The subscription manager is keyed by stream, holds one connection per key with a subscriber count, and opens on the first subscriber and closes after the last.
- Events carrying an entity summary **patch** the matching cached data directly — the payload is the same shape a list row renders from, so no refetch is needed. Events without a usable summary invalidate their key instead.
- Token-level streaming deltas **never touch the cache**. They're high-frequency, append-only, and belong to one open transcript, so they go to local component state.
- All three streams carry the same event shape, discriminated at runtime. There aren't three event types to model.
- **`App.tsx`'s hidden `<span>{channelForAgent('boundary-control')}</span>` is still there.** 005.01 added no value import from `@tcp/shared/client`, so removing it — replacing it with a real consumer — is still this prompt's job.
- **The SSE payload summary types are absent from the OpenAPI description.** `@Sse` routes carry no response schema, so `schema.d.ts` (005.01) will never carry `AssignmentChangeSummary`, `AgentChangeSummary` or `EnquiryChangeSummary`, and the generated-types drift check will never police the event contract. They come from `@tcp/shared/client`, which is why moving `parseWireEvents` there (above) is load-bearing for types as well as code.
- HTTP/2 is in place from 002.03 and needs no work here: `tcp-web` serves the app over HTTPS with `http2 on`, and `/api` is proxied on the same origin with `proxy_buffering off` — which is what keeps SSE events flowing rather than sitting in an nginx buffer until it fills. **Don't develop against `vite dev` directly for this prompt.** Bare Vite is HTTP/1.1, so the six-connection ceiling is fully present there and the symptom is a hang, not an error. Use `start-deployment.sh --dev-web`, which puts the same nginx in front of the dev server.

## Testing

- Unit tests for the moved parser, and confirmation the CLI still passes using it from its new home.
- Tests for the subscription manager: two subscribers to one stream share a connection; the connection closes after the last unsubscribes; the connection cap refuses extra connections **visibly**.
- Reconnection tests using fake timers: backoff grows and is capped, resets after success, pauses while offline or hidden, and resumes when that changes.
- **A test that reconnection fetches a fresh token** rather than reusing the previous one — change the stored token between the drop and the retry, and assert the _new_ value went out on the wire. Asserting only that `getAccessToken()` was called again passes for a reader that then sends a captured value. **Carried forward from 004.03**, which was asked for this test and had no stream to write it against: name the failure in the test, because it is not the one the shape suggests. A reader that captures its token does not fail at expiry — it fails at the first network blip _after_ expiry, and then never recovers, because every retry presents the same dead credential. Provoke expiry deliberately; a short test that reconnects inside the token's lifetime passes against the broken reader.
- **A test that a 401 at connect calls the shared policy once**, not once per stream, when several streams fail together. Carried forward from 004.01: `handleUnauthorized()` deduplicates internally, so this asserts the reader routes through it rather than starting its own navigation.
- Tests for the event-to-cache mapping: summary-carrying events patch without refetching; others invalidate; streaming deltas don't touch the cache at all.
- **A test that more than six simultaneous event streams work**, which is what HTTP/2 is there for. **This is carried forward from 002.03 and is this prompt's to finish.** That prompt proved the transport — the browser reports `h2`, and eight concurrent requests open zero new connections (`test/browser/hosting.spec.ts`) — but it could not prove the thing the requirement is actually about, because long-lived authenticated SSE connections did not exist yet. Open more than six real streams against a running deployment, hold them open at once, and assert every one of them delivers. Eight requests that return instantly prove nothing about concurrency; the failure this guards against is the seventh stream hanging with no error.
- **A test that a fetch 401 and a stream 401 arriving together still produce one redirect, not two.** 005.01 proved the fetch wrapper reaches `handleUnauthorized()` on its own; this prompt proves the stream reader does too — but nothing yet proves the two together dedupe rather than each firing its own navigation. Trigger both in the same test and assert one redirect.
- **A test that a `403` on a stream is surfaced, not retried.** Since 002.05 every SSE route (company, task, agent) enforces membership at connect: a caller who is not a member of the company gets `403` rather than a stream. That is a permanent refusal — reconnecting with backoff against it produces an infinite loop of failures and no error the user ever sees. Distinguish it from the transient failures the backoff exists for.
- Run the CLI's existing tests too — this changes shared code it depends on.
