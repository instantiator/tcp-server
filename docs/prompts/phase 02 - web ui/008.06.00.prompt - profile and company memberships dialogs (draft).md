## Goal

Two small dialogs, built together because they share an entry point, a data source and a shape.

Both are **read-only in the MVP**. Editing either would need user-management endpoints that don't exist, and read-only keeps them in scope at almost no cost.

## Requirements

**Profile dialog**

- Shows who the user is signed in as.
- Read-only. No editing controls — not even disabled ones, which just raise questions.

**Company memberships dialog**

- Lists the companies the user belongs to.
- Selecting one goes to that company's view.
- Read-only.

**Both**

- Opened from the account menu in the header (003.02).
- A close control, with focus returning to the account menu.
- Loading, error and empty states.

## Implementation notes

- **Profile data comes from the ID token's claims, read in the browser** — there's deliberately no `/api/me` ([ADR-023](../../ADRs/ADR-023-backend-api-surface-for-the-web-ui.md)). Zitadel supplies subject, name and email, and the app requests the `profile` and `email` scopes (004.01).
- **Handle missing claims.** If a claim isn't present, show something sensible rather than an empty row or a raw subject ID. A different identity provider might not supply everything Zitadel does.
- Memberships come from the same membership-scoped company query the overview uses (006.01). Don't add a second way of fetching the same thing.
- Because both read data that's already loaded elsewhere, they should be fast — avoid making them re-fetch what the app already has.
- Note in the code that read-only is a **scope decision**, not an oversight, so a later reader doesn't assume the editing was forgotten.
- Selecting a company from the memberships dialog navigates and closes the dialog. Make sure focus lands correctly on the destination rather than being lost.

## Testing

- Component tests for both, queried by role and accessible name.
- A test that profile details render from token claims, and **a test of the missing-claim case**.
- A test that memberships list the user's companies, and that selecting one navigates correctly.
- A test that focus returns to the account menu on close, and lands correctly after navigating.
- Tests for loading, error and empty states — including a user with no memberships.
- Accessibility assertions on both dialogs, with no violations.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- No hardcoded user-facing strings, and no literal values in stylesheets.
- Confirm no token or claim data is written anywhere durable as a side effect of showing it.
