We're planning a web ui application to cover the same functionality as tcp-cli (initially), with a live view of the activity going on in a company, and the ability to create tasks, initiate conversations with roles, upload or download documents and knowledge, etc.

This task is to break down the work across logical implementation boundaries, and plan the construction of:

- Draft prompts for implementation of each stage and feature of the MVP
  - Prompts should describe the intent, the key technology choices, the broad shape of what's to be implemented, but needn't go into fine detail: Plans will be created from prompts one at a time as they are being prepared for implementation
  - Starting suggestions:
    - `002.00.00.prompt - monorepo restructuring (draft).md`
    - `002.01.00.prompt - application infrastructure (draft).md`
    - `002.02.00.prompt - testing infrastructure (draft).md`
    - `003.01.00.prompt - landing page (draft).md`
    - `004.01.00.prompt - oidc client (draft).md`
    - `004.02.00.prompt - sign in (draft).md`

- ADRs for the key technical decisions
  - Webapp framework
  - Monorepo package/workspace structure
    - Today the six NestJS apps + `tcp-cli` share one root `package.json`, `nest-cli.json`, `tsconfig.json`, and a single multi-stage `Dockerfile` (deliberately consolidated to run `npm ci` once - see the comment at the top of the root `Dockerfile`)
    - We want each application to own its own `package.json`, living close to the application itself, rather than one shared root manifest. Target shape:
      - `apps/backend/` - `package.json`, `nest-cli.json`, and the six NestJS apps + `tcp-cli`
      - `apps/frontend/tcp-frontend/` - `package.json`, the new web app
      - `libs/tcp-shared/` - `package.json`, becomes a real (workspace) package rather than raw TS consumed via a path alias
    - Use npm workspaces to keep a single lockfile/install/CI run across the split
    - **Constraint, not an open question: the Dockerfile must keep its single-install/single-build-pass shape.** `npm ci` at the workspace root remains one install for the whole workspace graph (npm resolves/hoists all three workspaces' dependencies in one pass) - it must not regress to a separate `npm ci` per app. The `builder`/`prod-deps` stages stay shared; only the `COPY package*.json` layer needs to widen to include every workspace's manifest (backend, frontend, tcp-shared) ahead of that one `npm ci`, so the cache-friendliness is preserved. The new frontend's final image is static assets served by nginx - it doesn't need `node_modules` or a Node runtime at all, so it's simpler than the six existing Node-runtime targets, not a second install/build path
    - Work out in the ADR: where `nest-cli.json` and the root `tsconfig.json` end up (they don't have to stay at the repo root - Nest CLI resolves `nest-cli.json` relative to cwd); whether `tcp-shared` needs a build step or stays symlinked source; what changes in `.github/workflows/ci.yml`
      - `tcp-shared` becoming a real package is also the mechanism for the barrel-export split below - it can declare separate `exports` entries (eg. `.` for the full server-side surface, `./client` for a DTO/event-type-only surface) so the frontend can only ever resolve the slim one
    - This is a real structural migration (not just adding a new app) - scope and sequence it as its own plan, before or alongside the application infrastructure plan, since the frontend's own file layout depends on where it lands
  - Testing framework
    - Evaluate Jest vs. Vitest for unit/component tests (Vitest is the natural pairing with Vite's transform pipeline; Jest is what the rest of the repo uses - decide explicitly rather than defaulting to either)
    - Evaluate browser testing tools (eg. Playwright) for the browser test tier - none exist in this repo today
  - Event streaming (client side)
    - The server-side transport is already decided (ADR-015: SSE, not WebSockets/long-poll) - this ADR is scoped to how the browser client consumes it, not re-opening that choice
    - Note: browsers cap concurrent connections per origin under HTTP/1.1 (typically 6). The live activity view opens a company event stream, and each open chat/task dialog opens its own agent event stream - a handful of open dialogs plus the live view can hit that ceiling. HTTP/2 (which multiplexes streams over one connection) on the serving origin is a requirement to avoid this, not an optional nicety - the ADR should say so explicitly
  - Accessibility standards, choices, and auditing tools
  - OIDC client (browser client)
    - The provider (ADR-017: Zitadel) and grant type (Auth Code + PKCE, not device-code or ROPC) are already decided - this ADR is scoped to the browser client library and token handling
    - Assess and recommend a client library (eg. `oidc-client-ts`, `react-oidc-context`)
    - Discuss token storage strategy: benefits and risks of localStorage vs. in-memory storage for access/refresh tokens, and how that interacts with silent renewal
  - Static hosting & runtime configuration
    - The SPA is built once but needs environment-specific config (API base URL, OIDC issuer URL) - evaluate how that config reaches the running app without a rebuild per environment
    - Prioritise simplicity. An nginx-entrypoint-generated config script (substituting env vars into a small `config.js` served alongside the built assets) is a reasonable starting option - evaluate it against any other genuinely simple alternatives (eg. same-origin reverse proxy removing the need for runtime config entirely) and recommend one
  - MVP scope

Where a plan relies on an ADR's decision:

- add a note to the ADR indicating which plans should be updated when a decision is made
- add a note in the prompt indicating which ADRs it relies on, and which decisions

At implementation time, store this plan as `docs/prompts/phase 02 - web ui/001.01.01.plan - mvp prompt generation plan.md`

## Requirements

- Compiles to a SPA that can be hosted statically
- Uses the existing tcp-server backend
- Uses the configured OIDC service
- Keeps the user signed in with refresh token
- Fully accessible: for the MVP, we'll build an unstyled version
- Follows the existing `EXPOSE_PORT_*` / `derive-urls.sh` port scheme - the web app (and its dev/preview server) needs its own `EXPOSE_PORT_WEB`-style entry wired into `docker-compose.yml` and `derive-urls.sh`, not a hardcoded port

### Framework

- React / Vite
- React Router for client-side routing
- Build an API client against the Swagger/OpenAPI endpoint for tcp-server (but not the other services - the new application will only interact with tcp-server)
- Build an SSE client against the SSE endpoint(s) available
- Use a common OIDC client library

### Recommendations

Recommendations from previous planning conversations:

- Enable CORS (currently not enabled by tcp-server)
- API and SSE already implemented - we can use those
  - Generate an API clienty from the Swagger doc (`openapi-typescript` + a thin fetch wrapper)
- OIDC/Bearer auth is already expected (but we should use Auth code + PKCE, not device-code flow)
  - Create a public OIDC client for the web app
- **Hard requirement, not a nice-to-have:** the browser app must never import the full `@tcp/shared` barrel export. It re-exports server-only code (BullMQ, Redis, MinIO, TypeORM-adjacent modules) - a browser bundler will either fail to resolve it or bundle it uselessly into the app. This is a build-breaker, not just an exposure/tidiness concern, so carry that reasoning through into the monorepo/infrastructure plan rather than treating it as optional polish
  - The monorepo restructuring above (`tcp-shared` becoming a real package with a separate `./client` export of DTOs/event-types only) is the mechanism that enforces this - the frontend should have no way to even resolve the full export
- Use a native `EventSource` against the existing SSE endpoints
- Use React Query for server-side state
  - This is now TanStack Query v5
  - See: https://www.npmjs.com/package/@tanstack/react-query
  - We don't have much client-side state to manage yet
- Use the verbs available to `tcp-cli` (under `apps/tcp-cli/src/commands/`) to ensure that the initial feature list is appropriate, there are API calls for the various features to be implemented at MVP, and that the prompt below doesn't miss anything important

### Testing

- Every component must have comprehensive tests (mock dependencies)
- Every pure function must have comprehensive tests (success and failure paths)
- Test runner (Jest vs. Vitest) and browser test tool (eg. Playwright) are decided in the testing framework ADR - see the ADR list above
- Testing hierarcy:
  1. Unit tests
     - Test code in isolation
  2. Component tests
     - Mock dependencies, test each React component
  3. Browser tests
     - Run a test system with docker compose and tcp-stub-llm
     - Perform actions through the browser to test common end-to-end flows

### Accessibility

Render a simple UI for MVP and prioritise accessibility. Offer some basic styles for accessibility (light/dark/high contrast). We'll implement a wider selection of styles in future phases. Ensure we use a UI library that has full support for accessibility at AA or AAA.

Recommendations welcome for possible UI frameworks...

- MUI?
- Bootstrap?
- Tailwind?
- Other?

As a part of planning, review the options in an ADR and make a recommendation.

#### Minially styled UI

- Use a hierarchy of headings to structure content in views and the page as a whole
- Apply alt, roles, and other a11y properties to elements as needed
- Apply meaningful CSS classes to elements that can be styled later
  - Create CSS files for those corresponding classes, leave each class empty to be filled in later
  - Structure the application for theme selection, allowing the selection between multiple themes
  - Each theme should offer light / dark modes through CSS
  - Build some simple themes for MVP:
    - default (simple, soft colours, accessible contrast, light and dark modes)
    - high-contrast (much clearer use of fewer colours to indicate functional things like edges, boxes, buttons, the current focus, light and dark modes)
- Route every user-facing string through a single lookup (eg. a `strings.ts` module or a trivial `t('key')` passthrough) instead of inlining text in JSX - no translation library or locale files needed for MVP, this just leaves the seam for phase 03's i18n work to fill in later without a repo-wide rewrite

#### Screen readers

There are some decisions to make about views that show live events, or that update when things change. As a part of planning: prepare an ADR, evaluate the options, list out the pros and cons, and make a recommendation.

Some options for data-rich views:

- Display all the components, make all components accessible to the screen reader, allow the screen reader to read out the entire view in the order / way it sees fit
- Suppress normal screen reading, create a summary of the view, give that to the screen reader

Some options, for live changes:

- Update the view and allow new/updated components to be read by screen readers as they see fit
- Suppress normal screen reading, update the view, create a summary of the change, and make that acessible to the screen reader

- Loading, error, and empty states for every data-driven view and dialog (eg. a companies overview with zero companies, a task list that fails to load)
- A notification pattern (eg. a toast) for background events reaching the user when they're not looking at the relevant view (eg. a task fails while its dialog is closed)

### Companies overview (MVP)

- Redirect here after sign in
- Shows all companies currently in the system that the user is linked to by `CompanyUser`, a few live stats about each

### Company view (MVP)

A small breadcrumb component with `Companies > ${company}`

- Companies is clickable to return to the companies overview

2 tabs:

1. live activity (MVP)
2. configuration

NB. the configuration view is _not_ a part of the MVP. This may seem counter-intuitive, as the basics of company configuration would ordinarily come first, but as the company and roles can be managed through the tcp-cli, this can be integrated into the web application later.

NB. Although this means "only show 1 tab", still implement a tabbed component here: tabs now, deliberately, rather than retrofitting a single-view layout into a tabbed one when the configuration tab is added later.

### Company live activity view (MVP)

Displays a real-time view of the current activity in a given company

- List of all active agents
  - Shows each agent, its role, and the assignment it's working on
  - Click the agent to open the **assignment dialog** for that agent
- List of all tasks
  - Shows the task and status
  - Click a task to open the **task dialog** for that task
  - Filterable by one or more task statuses
    - Default: Shows active and paused tasks
- List of all agent-to-agent consultations
  - Click a consultation to open the **assignment dialog** for the originating agent (which should also show the interaction between the two agents)
- List of all user enquries
  - Click an enquiry to open the **user response dialog** (showing the selected enquiry)
- 'Add new' FAB expands to a small menu:
  1. Create new task
     - Click to open a **task creation dialog**
  2. New chat
     - Has a submenu of all roles
     - Pick a role and opens the **chat dialog** to a new conversation with the chosen role

### Company configuration view

- List of all roles
  - Click a role to open a **role dialog**
  - Filterable by name (eg. start typing a name to reduce the list)
- List of company knowledge files, with controls to:
  - Download file
  - Delete file
  - Upload file
- Current indexing status of the company knowledge
- List of all `CompanyUser`s
  - Click to open an **edit company user dialog**

### Dialogs

### Profile edit dialog (MVP)

- A simple dialog, for the MVP just read-only

### Company memberships dialog (MVP)

- Read-only again in MVP

### Chat dialog (MVP)

- A chat view with conversations representing each currently open chat
- Small amount of context shown (eg. the role and assignment shortcode (if any))
- Each chat shows the event stream for the chat assignment as chat entries
- Each chat is interactive - ie. when waiting for user input, the system allows the user to type and send a message
- An additional control to close a given chat
- Dialog has a close button
  - If there are 0 chats, the dialog disappears when closed
  - If any open chats, the dialog 'minimises' to a bar anchored to the bottom of the view

### Task dialog (MVP)

- Some details of the task
- A chat view with conversations representing the different assignments (and their states)
- For each assignment
  - the role, the assignment status
  - a chat view showing the assigned agent's event stream as chat entries
- Additional controls: cancel the task

### User response dialog (MVP)

- A chat view with a conversation for each user enquiry
- Interactive - the user can type and submit a response
- Dialog has a close button

### Task creation dialog (MVP)

- Fields matching the tcp-cli task creation pane
- Dialog has create and cancel buttons

### Role dialog

  - Download file

### Edit company user dialog
