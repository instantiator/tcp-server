# 008.03 — Task dialog

Create a plan to build the task dialog: a task's details, the work happening under it, and the ability to cancel it.

> **Follows:** [ADR-020](../../ADRs/ADR-020-web-ui-mvp-scope.md) (MVP scope), [ADR-025](../../ADRs/ADR-025-browser-event-stream-consumption.md) (streams, connection budget), [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md) (announcements)
> **Needs first:** 008.01 (dialog framework and transcript)

## Model allocation

**The plan must open with a short section allocating work between models.**

- **Opus drives the implementation** and reviews everything before it lands.
- Opus may delegate parts of the work to sub-agents, choosing the most appropriate model for each part.
- Name the parts where **Sonnet** is a good fit — mechanical, well-specified, repetitive or high-volume work — to keep costs down.
- Keep judgement-heavy work with Opus: architecture, security, accessibility behaviour, and anything where an ADR leaves a choice open.

Good Sonnet candidates here: the details panel and the per-assignment layout. Opus should own the multi-stream connection handling, since a task with several assignments is where the connection budget gets tested.

## Plan storage

NB. The plan's implementation phase should start with a directive to store the plan as `xxx.xx.xy.plan - ******** plan.md` reflecting the prompt's three-part index with the third number incremented by 1, and its name, and if the prompt name is still suffixed with ` (draft)` to remove the suffix, eg.

`002.00.00.prompt - monorepo restructing (draft).md`'s plan is stored as `002.00.01.plan - monorepo restructing.md`, and the original prompt is renamed: `002.00.00.prompt - monorepo restructing.md`

## Goal

Where a user follows a task: what it is, which roles are working on it, what each has done, and how to stop it.

## Requirements

- The task's details and current status.
- **One panel per assignment**, each showing the role, the assignment's status, and that agent's work as a conversation.
- Live updates as the task and its assignments progress.
- A control to cancel the task.
- Loading, error and empty states.

## Implementation notes

- A task's assignments come back with the task itself, so the initial render needs one request.
- The task event stream carries task and assignment changes. Individual agents' transcripts come from **agent** streams — one per assignment panel.
- **This is the view most likely to hit the connection limit.** A task with several assignments opens several streams at once, before counting the live activity view behind it. Get every connection through the subscription manager (005.02), and check behaviour when the limit is reached.
- Consider whether every assignment panel needs its stream open at once, or only expanded ones. A task with many assignments is the realistic case; decide deliberately rather than opening everything by default.
- Cancelling is destructive and not obviously reversible. Confirm before doing it, and make what will happen clear.
- After cancelling, focus must land somewhere sensible — a stable neighbouring element, never the page body ([ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md)).
- Assignment panels keep a **stable order** — they shouldn't reshuffle as statuses change.
- 007.01 may resolve its "assignment dialog" open question by routing here, focused on one assignment. Check that outcome before planning, since it could add a requirement.

## Testing

- Component tests queried by role and accessible name.
- Tests that task and assignment changes arrive live, using a mocked stream.
- Tests with several assignments, confirming each panel's transcript stays separate.
- **A test of behaviour when the connection limit is reached** — it must fail visibly, not hang.
- A test of the cancel flow, including confirmation and where focus lands afterwards.
- A test that assignment order stays stable as statuses change.
- **An announcement test using `spokenPhraseLog()`**, confirming assignment status changes are announced sensibly and streaming responses aren't announced per token.
- Accessibility assertions on the dialog, with no violations.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- No hardcoded user-facing strings, and no literal values in stylesheets.
