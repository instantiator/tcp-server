# 003.01.01 — Landing page plan

## Context

`apps/frontend/tcp-frontend` currently renders one route, `/`, showing an inline `Placeholder` whose own comment says "Deliberately a placeholder — the landing page is 003.01". Everything the landing page needs was built by 002.01 and 002.02 and has never been used by a real screen: the string lookup holds exactly one key, the theme seam is exercised only by a test-only `Harness`, and `react-aria-components` is installed but imported nowhere in `src/`.

So this prompt is the first end-to-end exercise of the conventions, not just the first page. It has to produce a page and prove the foundations under it work.

Confirmed against the code before planning:

- `src/strings.ts` holds one key (`'app.title': 'TCP'`), with `StringKey = keyof typeof strings` making a typo a type error. Call sites use `t(…)` and never import `strings`.
- `src/theme/useTheme.ts` exposes `{ theme, mode, setTheme, setMode }`; `src/theme/storage.ts` owns `THEME_STORAGE_KEY = 'tcp.theme'`, seeding, persistence and `applyThemeChoice` (which sets `data-theme`/`data-mode` on `<html>`). `index.html` duplicates resolve+apply in a pre-paint script.
- `src/styles/base.css` declares every non-colour token; the two theme files each declare the same nine `--tcp-color-*` tokens under `:root[data-theme=…][data-mode=…]`.
- `src/test-support/axe.ts` exports `expectNoA11yViolations(container)` with `color-contrast` **disabled** — jsdom has no layout engine, so contrast is only ever checked in the Playwright tier.
- `src/App.tsx`'s `Placeholder` carries `<p hidden>{channelForAgent('boundary-control')}</p>` — the reachable value import that keeps the `@tcp/shared/client` bundling control alive. Deleting `Placeholder` without rehoming this silently stops the control testing anything.
- `src/App.test.tsx` and `test/browser/app-shell.spec.ts` both assert a level-1 heading at `/`.

### Decisions taken with the user before planning

1. **The theme control is two React Aria `RadioGroup`s** — palette (Default / High contrast) and colour mode (Light / Dark). No popup to open, natively keyboard-operable, and queryable by role and accessible name. Built as a reusable `ThemeControl` in `src/theme/` so 003.02's header reuses it rather than building a second one.
2. **Route-level pages live in `src/pages/<PageName>/`**, holding the component, its stylesheet and its test. This sets the precedent for 006/007/008, where pages will certainly grow sub-components.
3. **Sign-in goes through a named seam**, `src/auth/sign-in.ts` exporting `startSignIn()`. 004.02 replaces one function body; the page and its tests never move. The component test mocks that module, so it asserts the control _invokes sign-in_ rather than merely existing.
4. **The browser tier scans `/` for real contrast in all four theme × mode combinations.** This is slightly beyond the prompt's literal testing list, and it is the only place ADR-026's 4.5:1 and 7:1 targets are verified rather than asserted in a comment.

### A finding that changes the shape of the work

React Aria's `Radio` renders a **visually hidden `<input type="radio">` inside a `<label class="react-aria-Radio">`**, exposing state as `data-selected` / `data-focus-visible` on the label. Verified in `node_modules/react-aria-components/dist/private/RadioGroup.mjs`.

With no CSS at all that means two real accessibility failures, not cosmetic ones:

- **No visible selected state** — the option text renders, but nothing distinguishes the chosen option (WCAG 1.4.1).
- **No visible focus** — `base.css`'s `:focus-visible` rule lands on an input clipped to 1×1 (WCAG 2.4.7).

ADR-026's "empty rule bodies" convention is about **component** stylesheets. `base.css` is explicitly the exception — its own header says it exists because "React Aria Components ships no styling at all, so without this there is no focus ring and no border". So the fix belongs there: a minimal, entirely token-valued RAC layer in `base.css`, while `LandingPage.css` and `ThemeControl.css` ship meaningful class names with empty bodies exactly as the ADR requires.

### Out of scope

The header, route table, catch-all route, skip link and route-change focus management are all 003.02. The real sign-in flow is 004.02. The application announcer is 003.03. This page has no live region and needs none.

### 4. `ThemeControl` (Sonnet)

`src/theme/ThemeControl.tsx`:

```tsx
import { Label, Radio, RadioGroup } from 'react-aria-components';
import { t } from '../strings';
import type { Mode, Theme } from './storage';
import { useTheme } from './useTheme';
import './ThemeControl.css';

/** Narrows RAC's `string` back to the stored union without a cast. */
const asTheme = (value: string): Theme =>
  value === 'high-contrast' ? 'high-contrast' : 'default';

const asMode = (value: string): Mode => (value === 'dark' ? 'dark' : 'light');

/**
 * The user's explicit theme choice, as the two independent axes ADR-026
 * defines: the palette, and its light or dark variant.
 *
 * Radio groups rather than a menu or a pair of toggles — the choice is one of
 * a small, fully visible set, which is what a radio group states to a screen
 * reader. A toggle would assert a boolean where the model has two named
 * values, and a menu would hide the alternatives behind a popup.
 *
 * 003.02's header reuses this component; it is not landing-page-specific.
 */
export const ThemeControl = () => {
  const { theme, mode, setTheme, setMode } = useTheme();

  return (
    <div className="theme-control">
      <RadioGroup
        className="theme-control__group react-aria-RadioGroup"
        value={theme}
        onChange={(value) => {
          setTheme(asTheme(value));
        }}
      >
        <Label>{t('theme.palette.label')}</Label>
        <Radio value="default">{t('theme.palette.default')}</Radio>
        <Radio value="high-contrast">{t('theme.palette.highContrast')}</Radio>
      </RadioGroup>

      <RadioGroup
        className="theme-control__group react-aria-RadioGroup"
        value={mode}
        onChange={(value) => {
          setMode(asMode(value));
        }}
      >
        <Label>{t('theme.mode.label')}</Label>
        <Radio value="light">{t('theme.mode.light')}</Radio>
        <Radio value="dark">{t('theme.mode.dark')}</Radio>
      </RadioGroup>
    </div>
  );
};
```

Passing `className` to a RAC component **replaces** its default class, which is why `react-aria-RadioGroup` is repeated explicitly alongside the component class. `Radio` and `Label` are left to their defaults. If RAC turns out to compose rather than replace, drop the duplicate and say so in the step report — do not leave both if it produces a duplicated class attribute.

## Verification

Each check has a distinct failure mode; run them in order.

1. **`npm test --workspace apps/frontend/tcp-frontend`** — the component tier. Fails if the heading outline is wrong, the sign-in seam isn't invoked, keyboard operation is broken, the theme choice doesn't persist, or axe finds a violation.
2. **Break the focus rule deliberately**: comment out `.react-aria-Radio[data-focus-visible]` in `base.css` and confirm `ThemeControl.test.tsx`'s focus-indicator test fails. A gate that has never failed is unproven. Restore it.
3. **Break a string**: inline `'Sign in'` in `LandingPage.tsx` instead of `t('landing.signIn')` and confirm the test still passes — then confirm it fails once the key's value is changed in `strings.ts`. This is what the assert-against-`t(...)` convention actually buys; if it buys nothing, say so rather than claiming coverage.
4. **`npm run typecheck --workspace apps/frontend/tcp-frontend`** — all three tsconfig projects. Catches a missing `type` on an import (`verbatimModuleSyntax`) and an unnarrowed `string` reaching `setTheme`.
5. **`npm run lint:check`** — `jsx-a11y` runs as errors here, and `react-refresh/only-export-components` will reject `ThemeControl.tsx` if it ever exports anything but the component.
6. **`./scripts/run-browser-tests.sh`** — real contrast, all four combinations, plus the theme control driven for real and surviving a reload. This is the only tier that can fail on a token that misses 4.5:1 or 7:1.
7. **`./dev-environment/scripts/check.sh`** then **`./scripts/run-all-tests.sh`** — the full gate, including the backend tiers, since `base.css` and `App.tsx` are shared surfaces.
8. **§11's manual pass** (Opus), recorded in `## As implemented`.
9. Commit to `p02/003_landing-page-and-shell`. The user opens the PR into `phase-02`; do not open it, and do not merge to `main`.

## Risks

- **The `className` replacement question in §4.** If RAC replaces rather than composes the default class, omitting `react-aria-RadioGroup` silently drops every rule in §3 — and the jsdom tests would still pass, because they assert data attributes rather than computed styles. §11's manual pass is the real check; the plan names the fallback explicitly so the implementer doesn't guess.
- **`color-contrast-enhanced` is an axe AAA rule that is off by default.** If `.withRules()` doesn't enable it, the high-contrast scan passes vacuously. Confirm it reports _passes_, not zero results, before trusting a green run.
- **Nine colour tokens, four theme blocks.** If the landing page needs a token that doesn't exist, it must be added to all four blocks in both theme files or it resolves to nothing under the other theme. Nothing in this plan needs a new token; if a step thinks it does, that's a stop-and-report.

## As implemented

Everything the prompt asked for landed. Four things the plan got wrong or did not foresee, all found by gates rather than by review.

### `Radio` is deprecated in React Aria 1.20

The plan specified `<Radio>` verbatim. `@typescript-eslint/no-deprecated` failed the lint gate on all four uses: 1.20 deprecates `Radio` in favour of `RadioField` + `RadioButton`. The delegated step stopped and reported rather than adding a disable comment, which is what the boundary asked of it.

The replacement renders the same shape — `RadioField` is a `div.react-aria-RadioField` carrying `value`, `RadioButton` a `label.react-aria-RadioButton` wrapping the visually hidden input and carrying `data-selected` / `data-focus-visible`. So the `base.css` rules transferred with a selector rename, `.react-aria-Radio` → `.react-aria-RadioButton`. This is the "surface is moving" risk arriving during implementation rather than at some later upgrade, which is why the unresolved note about it is written as an observed fact.

### The `className` risk was resolved before the work, not after

The plan left "does React Aria compose or replace `className`?" to §11's manual pass. It is answerable in ten seconds from the bundle: `useRenderProps` returns `computedClassName ?? defaultClassName`, so a string `className` **replaces** the default. Repeating `react-aria-RadioGroup` alongside `theme-control__group` is therefore required, and `ThemeControl`'s doc comment says so. Deferring a checkable fact to a manual pass was the wrong call in the plan.

### The focus-indicator assertion the plan designed did not test anything

§7 test 4 was specified as "assert the focused label carries `data-focus-visible`", described in the plan as "the assertion that would have caught §3 being absent". Verification step 2 — deleting the rule and re-running — showed the test **still passed**. React Aria emits that attribute whether or not any stylesheet acts on it.

The fix uses a jsdom behaviour worth recording: jsdom **does** apply the cascade, but neither expands shorthands nor resolves `var()`. So `getComputedStyle(label).outline` returns the declared shorthand string when the rule matched, and `''` when it did not. Asserting it is non-empty now fails when the rule is deleted, verified both ways. The test comment states what each half proves, because the original comment claimed coverage the assertion did not have.

`getComputedStyle(el, '::before')` returns defaults in jsdom, so the selected-state indicator is genuinely untestable in the component tier. It moved to a browser-tier test that reads the pseudo-element's computed background and size, and the focused label's computed outline width.

### The `t(...)` convention catches drift, not inlining

Verification step 3 asked whether asserting against `t('key')` buys anything. Inlining `'Sign in'` in JSX while the lookup still says `'Sign in'` passes every test. Changing the key's value then fails two tests at once. So it is a **drift detector**, not a guard against inlining — nothing in the repository prevents a string being hardcoded, it only becomes visible once the lookup and the markup disagree, which is exactly when translation would break. The comment in `ThemeControl.test.tsx` says this; the older, stronger claim in `App.test.tsx` ("this fails if a component ever inlines the string in JSX") predates this work and is an overclaim.

### The browser tier caught a pointer path jsdom cannot see

`page.getByRole('radio').click()` failed against the real deployment: React Aria's input is visually hidden beneath its label, so Playwright's hit-testing reports the label intercepting the click. Testing Library's `userEvent` does no hit-testing, so the component tier never sees it. The test now clicks the label, which is what a user clicks, and asserts the radio became checked. Not a defect in the component — a reminder that the two tiers verify genuinely different things.

### §11 — the accessibility review

Run against a real Chromium instance rather than by eye, driving the dev server.

- **Heading outline**: `h1 "TCP"` → `h2 "Get started"` → `h2 "Appearance"`, exactly one `main`, two `section`s. No level skipped.
- **Tab order**: Sign in → Theme group → Colour mode group → document. One tab stop per radio group, which is the correct pattern; every stop reported a 2px outline.
- **Selected indicator, as drawn**: selected `16px` circle filled `rgb(7, 87, 186)`; unselected the same circle, transparent with a `rgb(208, 215, 222)` border. Distinguishable by fill and by shape, not by hue alone.
- **Contrast, for real, in all four combinations**: zero violations, with `color-contrast` (AA) reporting 11 passing checks under `default` and `color-contrast-enhanced` (AAA, 7:1) reporting 11 under `high-contrast`. The rule genuinely ran — which is what the `passes.length > 0` assertion in the browser spec exists to guarantee.
- **Full axe scan**: zero violations in every combination.
- **Theme switching**: applies immediately, survives a reload, no flash of the wrong theme.

One observation, recorded in the unresolved notes rather than fixed: the two radio groups sit flush against each other, because `ThemeControl.css` ships empty rule bodies and has nowhere to put spacing. Unambiguous to a screen reader, cramped to a sighted reader. That is ADR-026's trade working as designed, and ADR-020 defers visual design entirely.
