# 008.01 — Dialog framework and event transcript components

## Context

Five dialogs follow this prompt (008.02–008.06), and 008.07 builds the menu that
opens two of them. All of them need the same two things: a modal dialog that
handles focus and escape correctly, and — for the chat and task dialogs — a
component that turns an agent's event stream into a readable conversation.
Building those once means the five inherit the behaviour instead of each
reinventing it, which is also the only way the accessibility bar in
[ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md) and
[ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md) survives contact with
five separate implementations.

Everything the transcript needs on the browser side already exists:
`useEventStream(url, onDelta)` and the `subscribe` connection budget from 005.02,
`useAgentHistory` through the one data door in `src/api/hooks.ts`, and the
application announcer from 003.03.

### Decisions taken before planning

**1. The CLI's transcript logic moves into `@tcp/shared/client`. It is not ported
and not reimplemented.**

The prompt says to decide explicitly, and warns that a reimplementation will be
worse and will drift. Reading the code settles it: `audit-renderers.ts`,
`line-format.ts`, `entries.ts`, `event-log.ts`, `heading.ts` and the two
`core/` helpers are already pure functions and pure state over `AuditWireEvent`
and `StreamDelta`. The only terminal coupling in the whole set is the ANSI and
terminal-kit colour backends in `style.ts`, which sit behind a `StyleBackend`
interface the browser never uses.

So there is nothing to port. The files move, `tcp-cli` imports them from their
new home, and the browser gets the same implementation. That means the two
clients cannot disagree about what an event means — the risk the prompt raises —
and it makes the prompt's requirement of "tests proving the same event produces
equivalent output in both clients" unnecessary rather than something to build.
The CLI's existing specs move with the code and are the safety net for the move.

**2. Announcing a completed response: arrival only, behind one constant.**

ADR-027 flags this as unresolved. An agent answer can run to several paragraphs,
and reading all of it aloud monopolises the audio channel for a long time with no
useful way to interrupt. The text is on screen and browsable either way. So the
transcript announces `"Response from {role} received"` and nothing more, with the
choice expressed as one exported constant so the manual screen reader pass can
change it without touching the transcript.

**3. Minimising a dialog unmounts it.**

A modal that stays mounted keeps its focus trap and keeps the rest of the page
inert, which is exactly wrong for a dialog the user has parked. Minimise
therefore unmounts the modal and leaves a button in the dock; the dialog's owner
keeps whatever state it needs. This also means the transcript inside a minimised
dialog unmounts and releases its stream — so 008.02's open question ("do
minimised chats keep streaming?") stays 008.02's to answer, by choosing whether
to hold state above the dialog, not something this prompt decides by accident.

### Two places this plan departs from the prompt

- **"If the CLI's renderers are ported: tests proving the same event produces
  equivalent output in both clients."** Not built. With one shared
  implementation there is no second output to compare against. The CLI's existing
  specs move to the shared library and cover the logic for both.

- **"A dock: a bar anchored to the bottom of the view."** Built, because the
  prompt asks for it, but kept deliberately small (a provider, a list of
  entries, a bar of restore buttons). Its only consumer is 008.02, which has not
  been designed yet, so anything more would be guessing at requirements. Marked
  with a `ponytail:` comment saying so.

   `isBlankText`, `parseClockTime` and `ASSIGNMENT_COMPLETE_LABEL` moved to
   `transcript/format.ts`; the rest stayed. `heading.ts` and `text-wrap.ts`
   moved whole, and `style.ts` split so only the ANSI and terminal-kit backends
   stayed behind.

2. **`shortId`, `agentHeading`, `LogHeadingTracker` and `JsonDeltaFormatter` in
   the CLI's `core/agent-log-format.ts` are dead.** Nothing but their own spec
   imports them. Left in place — deleting them is not this prompt's work — but
   worth a sweep.

3. **`useEventStream`'s `onDelta` widened to `onEvent`.** A transcript needs the
   audit events as well as the token deltas, and the old callback only carried
   deltas. One callback for the whole stream is a smaller surface than two for
   its halves, and nothing was using `onDelta` yet.

4. **The transcript primes from history first, then subscribes.** Not stated in
   the plan, and it is a real decision: the two sources cannot be interleaved
   correctly without buffering one of them. The cost is a short window in which
   a live event is missed, recorded as an Open note.

   an error here, so the context and its hook live in `useDock.ts` and the
   component in `DockProvider.tsx` — the same split `theme/useTheme.ts` and
   `ThemeProvider.tsx` already use.

6. **`ANNOUNCE_RESPONSE_BODY` selects between two real strings.** A constant
   nothing reads is a lie, so both wordings exist in `strings.ts` and the
   constant is typed `boolean` so the compiler checks both branches.

7. **`verbatimModuleSyntax` is set in the frontend and not the backend.** Code
   moving into `libs/tcp-shared` needs `import type` for every type-only import
   or it compiles in one workspace and fails in the other. The pre-commit hook
   caught it; the CLI's own typecheck did not.

## Step 5 — the transcript hook (Opus)

**New file:** `apps/frontend/tcp-frontend/src/components/Transcript/useTranscript.ts`.

```ts
export interface TranscriptState {
  entries: readonly LogEntry[];
  status: 'loading' | 'ready' | 'refused' | 'at-capacity' | 'failed';
}
export const useTranscript: (
  agentId: string,
  roleName: string,
) => TranscriptState;
```

What it does, in order:

1. **Primes from history.** `useAgentHistory(agentId)` from `src/api/hooks.ts` —
   the one data door. The prompt notes reopening a transcript is a real request;
   this is it. Each returned `AuditEventResponseDto` is fed to the buffer as an
   `AuditWireEvent`.

2. **Holds one `EventLogBuffer`** in a ref, constructed with
   `new EventLogBuffer(() => ({}), false, false)` — the third argument turns
   headings off, which is what that flag already exists for ("single-scope
   surfaces that render their own richer heading").

3. **Mirrors the buffer into React state.** The buffer mutates the trailing entry
   in place when a delta extends it, which React cannot see, so `onAppend`
   translates each `AppendEvent` into an immutable update:
   - `entry` → append a copy
   - `delta` → replace the last entry with `{ ...last, text: last.text + delta }`
   - `heading` → ignored (headings are off)

   This is the only place deltas live. They are component state and never reach
   the query cache — `applyEvent` in `src/events/cache.ts` already ignores
   `type: 'stream'` for the same reason (ADR-021).

4. **Opens one stream** with `useEventStream(streamUrls.agent(agentId), onDelta)`.
   Going through `useEventStream` means going through the subscription manager,
   which enforces `MAX_STREAMS`.

5. **Maps the error to a status.** `useEventStream` returns one `error` covering
   two different situations, told apart by type:
   - `error instanceof ApiError` (from `src/api/errors.ts`) — a permanent refusal.
     `status === 403` → `'refused'`, other 4xx → `'failed'`. Never retried, and
     never rendered as a spinner: the reconnecting reader has already given up.
   - a plain `Error` — thrown synchronously by `subscribe` when opening would
     exceed `MAX_STREAMS` → `'at-capacity'`.

6. **Announces once, on completion.** When an audit event of type `llm_response`
   or `agent_loop_completion` arrives, call
   `announce({ channel: \`transcript:${agentId}\`, change: 'transcript.announce.response', params: { role: roleName }, politeness: 'polite' })`.

   Three rules this must hold to, all of them things ADR-027 exists to prevent:
   - **Deltas never call `announce`.** Suppression is this hook's job, not the
     throttle's — a token that never announces costs nothing, whereas streaming
     tokens into the announcer and relying on coalescing would still speak every
     ten seconds mid-response.
   - **The channel is per transcript**, so two dialogs streaming at once produce
     two sentences rather than one describing neither.
   - **The effect is guarded on the event's identity, not on a boolean.** Keep
     `lastAnnouncedRef` holding the last announced `event.id ?? event.timestamp`.
     A "have I run?" guard is spent by StrictMode's double invocation and the
     announcer counts repeats rather than de-duplicating them, so the same
     response would be announced twice.

   The wording choice lives in one exported constant so the manual screen reader
   pass can change it without touching this file:

   ```ts
   /** ADR-027 leaves this open until the manual screen reader pass. `false`
    * announces only that a response arrived; the text is on screen to browse. */
   export const ANNOUNCE_RESPONSE_BODY = false;
   ```

**Boundary:** this hook must not render a live region. The announcer owns the
only two, in `document.body`.

**Tests** (`useTranscript.test.tsx`), with `subscribe` mocked as
`src/events/useEventStream.test.tsx` already does, capturing `onEvent`/`onError`
and firing them inside `act()`, and history served by
`src/test-support/fetch-mock.ts`:

- **No per-token announcements.** Stream a dozen deltas, advance fake timers past
  `ANNOUNCE_THROTTLE_MS`, assert `await virtual.spokenPhraseLog()` is empty. This
  is the specific failure ADR-027 exists to prevent.
- **One announcement on completion**, run through `renderAppAt`, which wraps in
  `StrictMode` — the only helper that catches the double-announce.
- A 403 `ApiError` produces `'refused'` and no retry.
- A `MAX_STREAMS` throw produces `'at-capacity'`.
- History primes the buffer before any stream event arrives.

Use `vi.useFakeTimers({ shouldAdvanceTime: true })`, per ADR-027's amendment: the
throttle needs driving deterministically, but the screen reader simulator has its
own awaits that never settle under a frozen clock.

## Step 6 — transcript rendering (Sonnet)

**New files:** `Transcript.tsx`, `Transcript.css`, `Transcript.test.tsx` in the
same directory.

`Transcript` takes `agentId` and `roleName`, calls `useTranscript`, and renders
the entries. Each `LogEntry` already carries everything needed:
`style` (`user` | `llm` | `reasoning` | `response` | `json` | `state`), `time`,
`label` and `text`, with `json: true` marking text that is already pretty-printed
and must not be re-wrapped.

- The list is an `<ol>`; each entry is an `<li>` carrying its author and time, so
  a screen reader can browse entry by entry.
- `style` maps to a CSS class. Wrapping is CSS, not `wrapText` — the shared
  `text-wrap.ts` exists for fixed-width terminals and the browser does not need
  it.
- `json` entries render in a `<pre>`.
- `response` entries whose text is blank render the same placeholder the CLI
  shows — reuse `isBlankText` from `@tcp/shared/client` rather than re-deriving
  the rule, and take the placeholder text from `strings.ts`.
- The four non-ready statuses render the existing shared components:
  `LoadingState` for `loading`, `ErrorState` for `refused`, `at-capacity` and
  `failed`, each with its own message. `refused` must not render a spinner.

**Tests:** one per event kind the streams carry — `input`, `llm_request`,
`llm_response` (reasoning and response), `tool_call`, `tool_result`, `decision`,
`state_change`, `compaction`, `agent_loop_completion` — plus a test that a
streamed response renders progressively (assert the text grows across successive
deltas), and `expectNoA11yViolations`.
