# 008.02 — Chat dialog

## Context

The chat dialog is the main way a user talks to an agent. It has to behave like
a chat client rather than a modal form: several conversations open at once,
each rendering its own agent's event stream, each able to be typed into, and the
whole thing parkable in the dock instead of closed.

008.01 built the parts: `Dialog` (React Aria modal, minimise unmounts),
`DockProvider`/`useDock` (a deliberately minimal list of `{id, label, restore}`),
and `Transcript`/`useTranscript` (one agent's stream as a conversation, with the
never-announce-a-partial-response rule already enforced). Nothing mounts any of
them yet. 008.02 is the first consumer of all three.

It is also the first surface to open more than one event stream at once, so it
owns the stream budget for the whole 008 series. 008.03 reads that answer rather
than deciding again.

Two other firsts land here: the web client has **no mutation hooks at all**
today (every hook is a `useQuery`), and `useLiveChatState` /
`useLiveCompanyChatsList` exist with no consumer, so their shape is unproven.

### Decisions taken before planning

Four were put to the user and confirmed.

1. **A parked stream releases its connection.** Minimising unmounts the dialog,
   which unmounts every transcript in it, which releases every stream. This is
   the framework's existing behaviour and costs nothing to keep. Catch-up on
   restore is automatic: `useAgentHistory` has no `staleTime`, so a remount
   refetches the full server-side history and rebuilds the buffer from it, and
   only then subscribes — and the server synthesises a terminal state event for
   a late subscriber.

2. **No per-surface stream quota.** `MAX_STREAMS = 12` stands and stays the only
   cap. An over-opened transcript already renders `at-capacity` as its own
   visible message rather than hanging, so the failure is loud and local.

3. **The dock button for a parked chat shows the agent's status** ("Sales —
   thinking", "Sales — reply ready"). Zero extra connections: the agent's status
   is already patched into the query cache by whatever stream is open. Needs
   `DockEntry.label` widened from `string` to `ReactNode`.

4. **The open-conversations state lives in `AppShell`, beside `DockProvider`.**
   A dock entry's `restore()` closure must not outlive the component that made
   it. `AppShell`'s own docstring already says a minimised dialog belongs to the
   session, not to whichever route is showing.

Two more taken here, following from the requirements:

5. **One dock entry per conversation, not one for the whole dialog.** The
   prompt's own arithmetic counts "four minimised chats". Restoring any entry
   re-opens the dialog with every conversation, and moves focus into the
   conversation whose button was pressed.

6. **`Conversation` carries `{ agentId, roleName, reference }` and no more.**
   The chats-list row already has all three (`assignment.agentId`,
   `roleNames.get(roleId)`, `assignment.shortcode`), so opening a chat costs no
   extra request and `useLiveChatState` does not need changing. The panel calls
   `useLiveAgentState({ agentId })` for one thing only — the status that decides
   whether the input is enabled — and that value is live because the panel's own
   transcript stream patches the agent cache.

### Three places this plan departs from the prompt

- **The prompt says deltas arrive through `useEventStream`'s `onDelta`
  callback.** It was renamed to `onEvent` in 008.01 and widened to carry the
  whole stream. The requirement behind it still holds exactly: deltas stay in
  `useTranscript`'s component state, one buffer per `<Transcript/>`, never the
  query cache. Nothing to build — it is already true.

- **The prompt lists "starting a new chat with a role" as entered from 008.07's
  control.** 008.02 ships the capability (`startChat`) and 008.07 ships the
  menu. To give the dialog a real entry point now, this plan adds a fifth list
  to the live activity view whose rows open an existing chat — which also
  proves `useLiveCompanyChatsList`, the hook the prompt flags as unproven.

- **The prompt asks whether `MAX_STREAMS = 12` still stands.** It does, and the
  recheck is recorded rather than the number changed. See Step 1.

### Discovered during implementation

1. **`MessageInput` calling `useTranscript` a second time would have announced
   every completed response twice.** The step 6 brief reasoned carefully about
   the second call being safe — the stream is shared by url and the query by
   key, both true — and missed that the hook also announces, with a
   `lastAnnounced` ref per instance. Two instances, two announcements, and the
   single rule ADR-027 exists to enforce broken by a hook that was only being
   read for one boolean. Fixed by removing the second call and taking the
   waiting signal from the agent's status instead, which deleted step 3's field
   as well.
2. **`statusLabel` had to move before the dock label could use it.** It lived in
   `src/pages/CompanyPage/activity/activity-list-utils.ts`, and a shared
   component reaching into a page's own directory for it would have been a
   layering rot. Moved to `src/api/statuses.ts`, with the three activity lists
   re-pointed.
3. **A `<button>` may only hold phrasing content**, so the two-paragraph row
   shape the other four activity lists use cannot go inside one. The chats list
   makes its row title the button and drops the `aria-label`, which also makes
   its accessible name and its visible text the same string.
4. **The frontend's bare `tsc --noEmit` does not typecheck what the gate
   typechecks.** `useStartChat` passed `mutateAsync` by reference, which is not
   a valid `MutationFunction`; only `npm run typecheck` — which runs three
   separate projects — caught it. A sub-agent's done-condition must be the
   gate's command, not a shorter one that looks equivalent.
5. **A second chat cannot be opened while the dialog is showing.** React Aria's
   `Modal` correctly makes the page behind it inert, so the chats-list row that
   would open another conversation is unreachable. The working route is
   minimise, then open the next. This is what "modal" means rather than a bug,
   but it lands squarely on 008.07 and is written into that prompt's
   Requirements as something it has to solve.
6. **One pre-existing flake was fixed on the way through.**

   after a fake-timer advance and failed once under the full suite's load. Three
   call sites now wait for the warning instead. Outside this prompt's scope, but
   it was the gate that was red.

## Step 1 — the stream budget policy (Opus)

The policy, in full. It answers all four questions the prompt asks.

- **One stream per mounted transcript, and nothing else opens a stream.** A page
  owns at most one (`CompanyPage`'s company stream). A dialog owns one per
  visible conversation or panel. No hook opens a stream (ADR-030). There is no
  per-surface numeric quota — a quota would be a second cap to keep in sync with
  the real one for no benefit.
- **A parked stream releases its connection.** Parked means unmounted:
  minimising the chat dialog, or collapsing an assignment panel in 008.03.
  Nothing holds a connection for a surface the user cannot see.
- **A restored one catches up by re-priming, not by replay.** Remount refetches
  `GET /api/agent/{id}/history` (no `staleTime` anywhere in `endpoints.ts`, so a
  mount refetches), rebuilds the buffer from the full history, and only then
  subscribes. The server synthesises a terminal state event for a late
  subscriber. Token deltas from while it was parked are lost and that is
  correct — they were never persisted, and the completed response is in history.
- **`MAX_STREAMS = 12` stands.** Rechecked here, as 005.02 asked. With parked
  streams released the realistic worst case is 1 company stream + N open chat
  panels + M expanded assignment panels; reaching 12 needs a fan-out bug, which
  is what the cap is for. HTTP/2 is mandatory (ADR-029), so the browser's
  six-per-origin HTTP/1.1 ceiling does not bind.

**Where it is recorded — both places, because 008.03 may meet either:**

1. Rewrite the docblock above `MAX_STREAMS` in
   [subscriptions.ts](apps/frontend/tcp-frontend/src/events/subscriptions.ts#L7-L15)
   to state the four rules above and name 008.02 as where they were decided.
   Keep the existing `ponytail:` note that it is a constant, not configuration.
2. Draft the ADR-025 amendment text here; Step 12 writes it into the file.

## Step 2 — mutation hooks (Sonnet)

The first mutations in the web client. Everything today is `useQuery`.

**`src/api/client.ts`** — add beside `unwrap`:

```ts
/**
 * Runs a call whose success carries no body, throwing an `ApiError` if it
 * failed.
 *
 * `POST /api/agent/{id}/message` answers `202` with no content, so `unwrap`
 * would see `data === undefined` and throw on success. The check is on the
 * response, not the body.
 */
export const expectAccepted = async (
  call: Promise<{ error?: unknown; response: Response }>,
): Promise<void> => { … };
```

Mirror `unwrap`'s `try`/`catch` → `networkError(cause)` for a request that never
landed, then `if (!response.ok) throw apiError(response, error);`.

**`src/api/endpoints.ts`** — two `useMutation` hooks. Match the file's existing
three-line shape:

```ts
export const useStartChatMutation = () =>
  useMutation({
    mutationFn: (body: { companyId: string; roleId: string }) =>
      unwrap(api.POST('/api/agent/chat/start', { body })),
  });

export const useSendMessageMutation = (id: string) =>
  useMutation({
    mutationFn: (message: string) =>
      expectAccepted(
        api.POST('/api/agent/{id}/message', {
          params: { path: { id } },
          body: { message },
        }),
      ),
  });
```

**`src/api/hooks.ts`** — re-export both under the names components use:

```ts
export { useSendMessageMutation as useSendMessage } from './endpoints';
```

`useStartChat` needs one extra thing, so it gets a facade rather than a
re-export: chat-mode assignments are **not** primed on the company stream (only
`consultee` ones are — see `CompanyPrimingService.prime`), so a new chat will
not appear in the chats list on its own. On success, invalidate the assignments
key:

```ts
export const useStartChat = () => {
  const queryClient = useQueryClient();
  const mutation = useStartChatMutation();
  // Chat assignments are not primed on the company stream, so the list will
  // not learn about a new one by itself. One invalidation, at the one place a
  // chat is created.
  …onSuccess: () => queryClient.invalidateQueries({ queryKey: ['assignment'] })
};
```

Add a note to the docblock at the top of `hooks.ts`: the "one door" rule now
covers writes as well as reads.

**Done-condition:** `npx tsc --noEmit` in `apps/frontend/tcp-frontend` passes;
`npm run test:import-boundary` passes.

**Boundary:** do not add `staleTime`, `retry` or `refetchInterval` to anything.
Do not touch any existing hook.

## Step 5 — `ChatProvider` and `useChat` (Opus)

New directory `src/components/ChatDialog/`.

**`useChat.ts`** — context, mirroring `useDock.ts`'s split (the provider file
must export only its component, for `react-refresh/only-export-components`).

```ts
/** One open conversation in the chat dialog. */
export interface Conversation {
  /** The agent holding the chat. The transcript, its stream and its dock entry all key on this. */
  readonly agentId: string;
  /** The agent's role, for the panel heading, the dock label and the completion announcement. */
  readonly roleName: string;
  /** The chat assignment's shortcode, or `null` for a chat that has none. */
  readonly reference: string | null;
}

export interface ChatContextValue {
  readonly conversations: readonly Conversation[];
  /** Opens a conversation, or brings an already-open one to the fore. Restores the dialog if it is parked. */
  readonly openChat: (conversation: Conversation) => void;
  /** Creates a chat-mode agent for a role, then opens it. 008.07's menu calls this. */
  readonly startChat: (input: { companyId: string; roleId: string; roleName: string }) => void;
  /** Closes one conversation. Closing the last one closes the dialog. */
  readonly closeChat: (agentId: string) => void;
}

export const ChatContext = createContext<ChatContextValue | null>(null);
export const useChat = (): ChatContextValue; // throws outside a ChatProvider
```

**`ChatProvider.tsx`** — holds `conversations`, an `isOpen` flag and
`focusAgentId` (which conversation to focus when the dialog next opens). Renders
`{children}` and `<ChatDialog/>`.

Lifecycle, written out because it is the whole of this step:

- `openChat(c)` — replace any existing entry with the same `agentId`, append,
  set `isOpen`, set `focusAgentId = c.agentId`, and clear that agent's dock
  entry via `dock.restore` semantics (see below).
- `startChat(input)` — call `useStartChat()`, and on success
  `openChat({ agentId: agent.id, roleName: input.roleName, reference: null })`.
  A failure renders `t('chat.start.failed')` through the existing `ErrorState`
  inside the dialog; if the dialog is closed, it opens to show it.
- `closeChat(agentId)` — drop it. If none remain, `isOpen = false`.
- **Minimise** — for every conversation, `dock.minimise({ id: agentId, label:
<ChatDockLabel …/>, restore: () => openChat(c) })`; then `isOpen = false`;
  then `dock.focusEntry(conversations[0].agentId)`.
- **Dialog close control** — if `conversations.length === 0`, `isOpen = false`
  and nothing else. Otherwise it minimises. (This is the requirement's two close
  behaviours; the dialog itself only reports the press.)
- **Restore** — a dock button's `restore()` runs `openChat(c)`, which reopens
  the dialog for _all_ conversations and focuses the one pressed. Clear every
  dock entry as part of that: the dialog is showing again, so no conversation is
  parked. Do this by tracking the docked ids in the provider and calling
  `dock.restore(id)` for the rest — or, if that double-fires their `restore`
  callbacks, add a `dock.clear(ids)`. **Decide once it is running; if the dock
  needs a third method, add it in Step 4's file with a comment saying why.**

**`ChatDockLabel.tsx`** — the live dock label. `({ agentId, roleName })`, calls
`useLiveAgentState({ agentId })`, renders
`t('chat.dock.label', { role: roleName, status: statusLabel(agent.status) })`.
Reuse `statusLabel` from
[activity-list-utils.ts](apps/frontend/tcp-frontend/src/pages/CompanyPage/activity/activity-list-utils.ts#L39).
It opens no stream; the value is whatever the query cache holds.

**`AppShell.tsx`** — wrap `ChatProvider` immediately inside `DockProvider`, and
extend the docstring's existing paragraph about why the dock sits there to cover
the chat state for the same reason.

**Boundary:** `ChatProvider` opens no event stream. Every stream in this feature
belongs to a mounted `<Transcript/>`.

## Step 6 — the dialog, the conversation panel and the input (Sonnet)

Three components in `src/components/ChatDialog/`, plus one stylesheet.

**`ChatDialog.tsx`** — reads `useChat()`, renders nothing when there are no
conversations. Otherwise:

```tsx
<Dialog
  isOpen={isOpen}
  onOpenChange={(open) => { if (!open) onClose(); }}
  heading={t('chat.dialog.heading')}
  onMinimise={onMinimise}
>
  {conversations.map((c) => <ChatConversation key={c.agentId} conversation={c} … />)}
</Dialog>
```

A plain vertical stack, not tabs. Tabs would unmount the hidden conversations,
which contradicts the requirement that each conversation has its own transcript
and its own stream, and would make the stream-budget question meaningless.

**`ChatConversation.tsx`** — one panel:

- `<section aria-labelledby={headingId} tabIndex={-1} ref={…}>` — focusable so
  the provider can move focus into a restored conversation. Focusing the section
  announces its heading, and works whether or not the input is enabled.
- `<h3 id={headingId}>` — `t('chat.conversation.label', { role })`, or
  `t('chat.conversation.labelWithReference', { role, reference })` when
  `reference !== null`. **`h3`, explicit**: the dialog's `Heading slot="title"`
  is the `h2`. This is the same rule `ActivityList` follows.
- A close-this-conversation `Button`, accessible name
  `t('chat.close', { role })` — one per panel, so "Close" alone would be four
  identically-named buttons.
- `<Transcript agentId={c.agentId} roleName={c.roleName} />` — its own
  component, so its own `EventLogBuffer`, its own `transcript:<agentId>`
  announcer channel and its own stream. Never shared.
- `<MessageInput …/>`.

**Focus when a conversation is closed** (ADR-027 names closing a chat as the
destructive completion that must not drop focus to the body): move focus to the
next panel's `section`, or the previous one if it was last. If it was the only
one the dialog closes and React Aria restores focus to the opener. Write this in
`ChatConversation`'s parent (`ChatDialog`), which knows the neighbours.

**`MessageInput.tsx`** — `({ agentId, roleName, disabled })`.

- A `<form>` around React Aria `TextField` + `Label` + `Input` + a submit
  `Button`. Single-line `Input` and native form submission, so Enter sends with
  no key handling code at all.
  `// ponytail: single-line input, so Enter-to-send is the browser's. A
multi-line composer needs its own key handling — add it when someone asks.`
- `useSendMessage(agentId)`; on submit, send and clear the field. Do not echo
  the message locally — the backend records an `input` audit event and it
  arrives on the stream (`ChatService.sendMessage`).
- **Waiting state**: `const waiting = send.isPending || awaitingReply;` from
  Step 3, rendered as plain text `t('chat.waiting', { role })`. **Not a live
  region** — ADR-027 announces a completed response and nothing before it, and
  `useTranscript` already makes that announcement.
  `// ponytail: a sub-second gap between the 202 and the input event arriving
can show neither. Add a local "just sent" flag if it reads as a flicker.`
- `disabled` when the agent's status is `running`. The panel reads it from
  `useLiveAgentState({ agentId })`, which is live because this panel's own
  transcript stream patches the agent cache. A disabled input needs a visible
  reason: render `t('chat.busy', { role })` in place of the waiting line.
- A failed send renders `ErrorState` with `message={t('chat.send.failed')}` and
  `channel={'chat:' + agentId}`, and does not clear the field.

**`ChatDialog.css`** — follow the house rule stated at the top of every
stylesheet in `src/components/`: meaningful BEM-ish class names, empty rule
bodies for anything a theme will fill, and **no literal colour, spacing or
border values — only `--tcp-*` tokens**. Layout rules only.
