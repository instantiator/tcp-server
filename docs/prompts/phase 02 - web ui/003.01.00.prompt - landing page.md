# 003.01 — Landing page

Create a plan to build the landing page: the first thing a signed-out visitor sees, and where they return after signing out.

> **Branch:** `p02/003_landing-page-and-shell`, off `phase-02` — one branch per major index; see [the workflow](README.md)
> **Follows:** [ADR-020](../../ADRs/ADR-020-web-ui-mvp-scope.md) (MVP scope), [ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md) (accessibility standard, theming), [ADR-021](../../ADRs/ADR-021-web-ui-framework-and-architecture.md) (framework)
> **Needs first:** 002.01 (application infrastructure)

## Model allocation

**The plan must open with a section allocating work between models**, following
[model allocation](model-allocation.md): default to the cheapest model that can do
each step correctly, spell out the detail a Sonnet or Haiku step needs, and let
Sonnet be the reviewer of record for the mechanical ones.

This is a small, well-specified page — a good candidate for Sonnet throughout, with Opus reviewing the accessibility result and confirming the heading structure and theme switching are right.

## Carry-forward

**The plan must include a step that writes this prompt's forward-looking work
into the prompts that will do it.** Anything deferred, discovered, or left
half-wired belongs in the prompt that picks it up — written into that file, not
only mentioned in this plan. A note nobody meets while reading the prompt they
are working on has not been recorded, it has been filed.

Where the note is about a test, a constraint or an assumption the later work
depends on, put it in that prompt's own Requirements or Testing section rather
than appending a loose paragraph.

## Goal

A simple public page that explains what this is and offers a way in. It's deliberately small, and it's the first place the accessibility conventions get exercised end to end.

## Requirements

- A short piece of explanatory text about the system.
- A sign-in control. Wiring it to the real sign-in flow is 004.02 — here it can call a placeholder, but it must be the real control, in the right place, correctly labelled.
- This is the page users land on after signing out.
- Reachable and usable while signed out.
- A theme control, so the theme work from 002.01 is visible and testable somewhere real.

## Implementation notes

- Use a proper heading hierarchy — this page sets the pattern the rest of the app follows.
- All text goes through the string lookup, not inline in JSX.
- All styling goes through theme custom properties. Component stylesheets carry meaningful class names with empty rule bodies, per [ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md).
- Remember React Aria Components ships no styling: without the minimal base stylesheet from 002.01, controls here will be invisible rather than merely plain.
- Keep it genuinely simple. This page's job is to be correct and accessible, not impressive.

## Testing

- Component tests querying by role and accessible name — not by test ID or class.
- An accessibility assertion on the rendered page, with no violations.
- A test that the sign-in control is reachable and operable by keyboard alone.
- A test covering theme switching from this page, including that the choice persists.
- Verify the heading structure forms a sensible outline.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- No hardcoded user-facing strings, and no literal colour or spacing values in stylesheets.

## Unresolved notes

Before this prompt is done, record what it leaves open in
[unresolved-notes.md](unresolved-notes.md):

- **Anything a later prompt will do** — write it into that prompt (see
  [Carry-forward](#carry-forward)) and add a row to that document's
  _Carried into a later prompt_ table, so it is visible from one place.
- **Anything unresolved with no owner** — a compromise taken knowingly, a
  constraint imposed from outside, a decision that can't be taken yet. State
  what would have to be true for it to be revisited.
- **Anything conditional or time-dependent** — an upstream project adding a
  feature, a library dropping a peer constraint, a threshold being crossed —
  needs the entry **and a memory**, because nothing in this repository will ever
  prompt anyone to re-check it. Write the condition so it can be tested, not as
  "revisit later".

If this prompt genuinely leaves nothing open, say so in the plan. Silence and
"checked, nothing to add" read identically afterwards, and only one of them is
true.
