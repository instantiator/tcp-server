# 007.03 — Browser authentication harness

Create a plan to let the browser test tier sign in, and use it to cover the live activity view.

> **Branch:** `p02/007_live-activity`, off `phase-02` — one branch per major index; see [the workflow](README.md)
> **Follows:** [ADR-028](../../ADRs/ADR-028-frontend-testing-strategy.md) (the black-box browser tier), [ADR-024](../../ADRs/ADR-024-browser-oidc-client-and-token-handling.md) (the OIDC client), [ADR-030](../../ADRs/ADR-030-component-hooks-for-live-data.md) (the hooks under test)
> **Needs first:** 007.02

## Context

No browser test has ever reached a signed-in page. The tier can only see the
landing page, the not-found page and the sign-in callback, because it has no way
to become a signed-in user. Everything behind the sign-in gate — the companies
overview, the company view, the four activity lists — is covered only by
component tests that mock the network.

That gap is growing. 008.x adds five dialogs and 002.01 adds a configuration
view, all of them behind the same gate. This prompt closes the gap now, while
the backlog is four views rather than ten.

### Why the development escape hatch cannot do this

`?devSession=` looks like the answer and is not. Tokens are held in
`InMemoryWebStorage` (`src/auth/user-manager.ts`), deliberately, with a test
asserting nothing reaches `localStorage` or `sessionStorage`. The dev session
fakes a signed-in _shell_ and mints no token, so every API call behind it
returns 401. A test using it would render a page of error states.

Building a development bundle for CI would also stop the tier testing the
artefact that ships, and two existing tests assert the dev hatch is _absent_
from the production build.

### What is already in place

`start-deployment.sh` provisions a human user in Zitadel — username `test`, a
known password, a verified email — and adds it to `TCP_ADMIN_IDENTIFIERS`, so
it can see every company without any membership seeding. The browser tier
already reads test credentials from the env file and already skips specs
cleanly when they are absent (`event-streams.spec.ts`).

So the missing piece is only the login itself.

## Goal

- The browser tier can sign in, against the production bundle it already tests
- One place touches the identity provider's login form, so an upgrade to it
  breaks one file
- The live activity view has browser coverage: it renders, it updates from a
  real event stream, and it is free of accessibility violations while signed in
- 001.01 inherits a working harness and spends its effort on journeys

## Requirements

### The harness

- A Playwright **setup project** that signs in once through the real login
  form and saves `storageState`. Every other project depends on it.
- Saved state carries the identity provider's own session cookie, not an
  application token — the app holds tokens in memory only. A test then reaches
  a guarded route, is redirected to the provider, is recognised, and comes back
  signed in with a fresh token. That silent round trip is the mechanism; a test
  should not have to know about it.
- Credentials come from the same env-file resolution `run-browser-tests.sh`
  already uses for `TEST_CLIENT_ID`/`TEST_CLIENT_SECRET`. Add the username and
  password to that resolution rather than inventing a second scheme.
- **A missing credential skips, with a reason.** It must never fail the rest of
  the suite, and it must never fail silently — follow the pattern in
  `event-streams.spec.ts`.
- Confirm whether Zitadel requires a password change on first login. If it
  does, `start-deployment.sh` sets `changeRequired: false` when creating the
  user; the harness must not click through a password-change screen.

### The journeys this prompt covers

Only the two that prove the harness and cover 007.01/007.02. **The remaining
MVP journeys stay with `001.01`** — do not absorb them.

1. Signing in reaches the companies overview
2. Opening a company shows the four activity lists, and a live event moves a
   row without a reload

For (2), drive a real state change through the API rather than faking one in
the page. The component tier already proves `applyEvent` patches the cache;
this tier exists to prove the browser receives the event at all.

### Testing

- Accessibility: run axe on every signed-in page reached, as the existing
  browser specs do for the pages they can reach. ADR-026 wants the scan in both
  tiers, and until now the browser tier could only scan three pages.
- Assert exactly one stream is open on the company page. ADR-030 makes that a
  rule, and the browser is the only place it is observable.
- Do not weaken the two tests that prove `?devSession=` is compiled out of the
  production build. They keep their meaning once a real sign-in exists.

### Flake

Adding an authenticated tier to CI makes it depend on the identity provider
being up and on a third-party login form. This repository has already lost
weeks to one browser-tier flake, so:

- The login runs **once**, in the setup project, not per test.
- Wait on application state, never on a timer.
- If a journey proves flaky, the plan's own instruction is to delete it and
  record why, not to retry it.

### Documentation

- `docs/testing.md` — how the browser tier signs in, and how to run it locally
- `docs/web-client.md` — `?devSession=` signs you into the shell but mints no
  token, so API-backed views will error. That limitation is why the browser
  tier does not use it, and it is the kind of thing that costs someone an
  afternoon.
- Amend `001.01`'s prompt: the harness exists, journeys 1 and 2 are done, and
  its scope is the remaining four.
