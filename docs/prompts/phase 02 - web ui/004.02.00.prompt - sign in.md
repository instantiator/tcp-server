## Goal

Make sign-in work end to end, using the client from 004.01. This is the first point where the application does something real for a user.

## Requirements

- **The landing page's sign-in control starts the real flow.** Carried forward from 003.01: the seam is `startSignIn()` in `src/auth/sign-in.ts`. Replace that function's body and delete its `console.info` placeholder — do not move the call site. `LandingPage.test.tsx` mocks that module and asserts the control invokes it, by click and by keyboard, so the wiring stays proven while the implementation changes underneath it.
- A callback route handles the return from the identity provider.
- After signing in, the user arrives at the companies overview.
- If the user was trying to reach a specific page before signing in, they arrive there instead.
- Sign-in failures are shown clearly — the user must not be left on a blank screen or in a redirect loop.
- The whole journey is usable by keyboard and with a screen reader.
- **`RequireSession` already records where the user was going.** Carried forward from 003.02: `src/auth/session.tsx` redirects to `/` with `state={{ from: location.pathname }}`. Nothing reads it yet — this prompt is what makes the saved destination work. **Validate it before navigating**: a path read back out of history is attacker-influenced, and following one unchecked is the open redirect this prompt's own testing section already requires a test for. Allow only paths this application's route table declares.
- **The OIDC callback route is deliberately absent.** Carried forward from 003.02: the route table in `src/App.tsx` has `/`, `/companies`, `/company/:companyId` and a catch-all. Add the callback as a **public** route, alongside `/` and outside `RequireSession` — putting it behind the guard is a redirect loop, because the user has no session at the moment they arrive on it.
- **The client already exists; this prompt drives it.** Carried forward from 004.01: `getUserManager()` in `src/auth/user-manager.ts` is a configured `UserManager` singleton, and the callback route completes the flow by calling `signinRedirectCallback()` on it. The path Zitadel is registered against is `/callback` — `start-deployment.sh` registers `${TCP_WEB_URL}/callback`, and `createUserManagerSettings()` derives the same value from `window.location.origin`. Choosing a different route name means changing all three.
- **`state.from` reaches the callback from two places, not one.** Carried forward from 004.01: as well as `RequireSession`, `handleUnauthorized()` in `src/auth/unauthorized.ts` puts `{ from: pathname + search }` into the sign-in state when the API rejects a token. Both arrive at the same validation, and that one carries a query string where `RequireSession`'s does not — so a validator that only matches bare route paths will silently discard the destination.

## Implementation notes

- The callback route is transient. Show a clear loading state; the user may see it briefly, or for a while on a slow connection.
- **Validate the redirect target before using it.** An unvalidated return address is an open redirect. Only allow destinations inside this application.
- Failure cases to handle explicitly: the user cancels at the provider, the provider returns an error, the callback arrives with missing or malformed parameters, and the callback is replayed or arrives twice.
- A redirect loop is the characteristic failure of this journey — sign-in bouncing back to sign-in. Make it impossible rather than unlikely, and test for it.
- The companies overview doesn't exist until 006.01. Land somewhere sensible in the meantime and wire the real destination when it does.
- **Mount `react-oidc-context`'s `AuthProvider` around the existing singleton, not around a fresh set of settings.** Carried forward from 004.01: the library is installed and unused, deliberately, because nothing consumed an auth context yet. Give the provider `getUserManager()`'s instance. Two managers would hold two different in-memory users, so React would show a signed-in header while the fetch wrapper (005.01) still presented the old token — a divergence with no error message anywhere.
- **A bare `vite dev` stops rendering the moment `AuthProvider` mounts.** Carried forward from 004.01: `getRuntimeConfig()` throws when `/config.js` is absent, which it is without nginx in front. Today nothing in the mounted tree calls it. Use `scripts/start-deployment.sh --dev-web` and load the nginx port; the thrown error already says so, but it will arrive as a white screen rather than a message.

## Testing

- A test of the full journey with a mocked provider: control → redirect → callback → landing on the right page.
- A test that a saved destination is honoured, and **a test that an external or malformed destination is rejected**.
- Tests for each failure case above, asserting the user sees a clear message.
- **A test that no redirect loop is possible** when the callback fails.
- An accessibility assertion on the callback route's loading and error states.
- A test that the journey works by keyboard alone.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- No hardcoded user-facing strings.
- The open-redirect protection is covered by an explicit test, not assumed from the implementation.
