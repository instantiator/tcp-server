# 004.03 — Session persistence and sign out

## Context

004.01 built the OIDC client and 004.02 built sign-in, but tokens live in
`InMemoryWebStorage` — so a page reload loses them. Today a reload of
`/companies` finds no user, `RequireSession` bounces to `/`, and the user has to
press **Sign in** again. That is the gap this prompt closes.

Three things are missing, and one thing is quietly wrong:

- **Reload recovery.** Per [ADR-024], recovery is a full-page redirect to the
  provider, not a hidden iframe. With a live provider session it costs a few
  hundred milliseconds and shows no form.
- **Expiry while the app is open.** `automaticSilentRenew: false` means nothing
  subscribes to `accessTokenExpired`, and `react-oidc-context` computes
  `isAuthenticated` only at dispatch time — so after expiry the account menu
  keeps rendering against a token that is gone. This is exactly the
  "looks signed in but nothing works" state the prompt forbids.
- **Sign-out.** `src/auth/sign-out.ts` is still an empty placeholder.
- **The redirect loop.** Auto-recovery on a guarded route is the same hazard
  `/callback` was built to avoid, one level up.

### Confirmed against the code and the libraries before planning

- `UserManager._signoutStart()` **already calls `removeUser()`** before
  navigating, and it does so _before_ `createSignoutRequest()` — which is where
  a missing `end_session_endpoint` throws. So the local user is gone either way;
  the fallback only has to navigate.
- `removeUser()` raises `userUnloaded` → `react-oidc-context` dispatches
  `USER_UNLOADED` → `isAuthenticated: false` → `AuthSession` yields `null` →
  the header's account menu disappears. **No change to `AuthSession` is needed.**
- `AccessTokenEvents` arms both timers from `_events.load(user)`, which
  `getUser()` calls — so the expiring/expired events fire for a restored user.
  `accessTokenExpiringNotificationTimeInSeconds` defaults to 60.
- `handleUnauthorized()` already saves `pathname + search` as
  `state.from`, which is what `safeRedirectTarget()` reads back. Reusing it for
  reload recovery unifies the two paths onto one latch and one state shape.
- **There is no fetch wrapper and no SSE client yet** (005.01 / 005.02). Two of
  the prompt's required tests have nothing to exercise; see
  [What this prompt cannot test](#what-this-prompt-cannot-test).
- `Session` stays `{ userId }`. Nothing in this prompt puts a token in it, so
  003.02's `?devSession=` hazard does **not** trigger here.

### Decisions taken with the user before planning

1. **Auto-recover from guarded routes** using the existing
   `handleUnauthorized()`, replacing `RequireSession`'s bounce to `/`.
2. **`removeUser()` on expiry**, plus a visible warning **30 seconds before**
   with a control that extends the session (WCAG 2.2.1 "Timing Adjustable").
3. **Do not wire `matchSignoutCallback` / `onSignoutCallback`**, contrary to the
   prompt's implementation note — `signoutRedirect()` removes the user itself
   and the post-logout URI `/` is unguarded, so those hooks would only sweep a
   stale `sessionStorage` entry, behind a predicate that has to guess whether a
   `state` param on `/` is a logout return. `clearStaleState()` does the sweep
   without the guess. Recorded as an ADR-024 amendment and in the plan's Risks.

### Out of scope

Multi-tab sign-out propagation (no `BroadcastChannel`, `monitorSession: false`),
a cross-page-load loop counter, and moving tokens to `sessionStorage`. All three
are recorded in `unresolved-notes.md` with the condition that would trigger them.

### 3. Reload recovery in `RequireSession` (Opus)

**File:** `src/auth/session.tsx`. Replace the `Navigate` branch. `useLocation`
and the `state={{ from: … }}` hand-off both go — `handleUnauthorized()` builds

```tsx
export const RequireSession = () => {
  const session = useSession();
  const { isLoading } = useAuth();
  const [failed, setFailed] = useState(false);

  const recover = useCallback(() => {
    setFailed(false);
    handleUnauthorized().catch(() => setFailed(true));
  }, []);

  useEffect(() => {
    // `isLoading` is the provider still restoring: deciding now would send a
    // signed-in user round the provider for nothing.
    if (session !== null || isLoading || failed) return;
    recover();
  }, [session, isLoading, failed, recover]);

  if (session !== null) return <Outlet />;

  if (failed) {
    return (
      <ErrorState
        message={t('session.recovery.failed')}
        channel="auth"
        onRetry={recover}
      />
    );
  }

  return <LoadingState label={t('session.recovering')} />;
};
```

Rewrite the component's doc comment: it is no longer "sends the visitor to the
landing page". State the new contract and the loop reasoning:

```
// ponytail: one attempt per page load. `handleUnauthorized()`'s module latch
// absorbs StrictMode's double mount and any second guarded component; the
// `failed` guard stops the effect re-firing after a rejection, and the
// provider's return leg always lands on /callback, which never redirects on
// its own. A cross-page-load counter goes in only if a real loop is observed
// — see unresolved-notes.md.
```

### 4. Sign out (Sonnet)

**File:** `src/auth/sign-out.ts`. Replace the whole body; keep the module's one

```ts
/**
 * Ends the session here and at the provider, and returns the user to the
 * landing page.
 *
 * `signoutRedirect()` removes the local user itself, before it builds the
 * request — so by the time a provider without an `end_session_endpoint` throws,
 * the local side is already clean and only the navigation is missing. RP-
 * initiated logout is optional in OIDC; Zitadel publishes one, so this bites
 * only an external provider, and it bites as an exception thrown out of a menu

export const startSignOut = async (): Promise<void> => {
  const userManager = getUserManager();

  try {
    await userManager.signoutRedirect();
  } catch {
    await userManager.removeUser();
    window.location.assign('/');
  }
};
```

## As implemented

### `storeUser()` does not arm the expiry timers; `getUser()` does

The expiry subscription looked untestable at first, because storing a `User`
with a near-future `expires_at` raised nothing. `AccessTokenEvents.load()` is
what arms both timers, and `UserManager.storeUser()` never calls it — `getUser()`
does, which is why the events fire in production at all: `AuthProvider`'s init
effect calls `getUser()` on every mount. The test helper therefore stores **and**
gets, which is not a workaround but a faithful copy of the production path. A
test that only stored would have passed against a client with no subscription.

### `oidc-client-ts` publishes no way to raise `accessTokenExpiring`

There is no public raise method, so `SessionExpiryWarning`'s tests cross into the
30-second window for real, with `vi.useFakeTimers({ shouldAdvanceTime: true })`
and a user whose `expires_at` is inside it. Slower to write than a faked event
emitter and worth it: it exercises the same timer arithmetic the warning depends
on, which a hand-raised event would have skipped entirely.

### `window.location.assign` cannot be spied in this jsdom

`vi.spyOn(window.location, 'assign')` throws `Cannot redefine property`.
`sign-out.test.ts` swaps the whole `location` object with `Object.defineProperty`
in a `beforeEach`/`afterEach` pair instead. Worth knowing before the next test
that needs to observe a navigation.

### The `?devSession=` browser test asserted a destination this prompt changed

`app-shell.spec.ts`'s "cannot sign anyone in against a production build" asserted
that a guarded route lands on the landing page. It now lands on the provider. The
property the test exists to protect is untouched — a query string still cannot
sign anyone in — and leaving for the provider is itself the proof, since
`RequireSession` only does that having found no session. The `Account` assertion
was kept but is now nearly vacuous on a provider-hosted page, and its comment
says so rather than claiming more than it does.

### A guarded route stopped being usable as an inert probe, and one nginx test was using it as one

`hosting.spec.ts`'s "serves the app shell for a deep link on a fresh page load"
probed `/company/deep-link-probe`. Its subject is nginx's SPA fallback — status,
content type, `#root` attached, `config.js` having run — and the path was
incidental to that. Since this prompt it is not incidental: the app boots,
`RequireSession` finds no session and leaves for the identity provider, taking
the document being asserted on out of the browser mid-assertion. The probe moved
to `/deep-link-probe/nested`, which the catch-all route renders and no guard
touches. nginx has no location block below `/` other than `/api/`, `/assets/`
and `/config.js`, so the fallback is exercised identically.

This is the failure mode worth remembering from this prompt: **a guarded route is
no longer a neutral address.** Any test, script or manual check that used one as
a convenient deep link now navigates away on its own. `check.sh` cannot see it —
the browser tier is the only place it shows, and only against a running
deployment.

### The landing page's `location.state` hand-off is now unreachable

`RequireSession` no longer navigates to `/` with `{ from }`, so `LandingPage`'s
`useLocation().state` → `startSignIn(state)` path has no producer. It was left in
place: it still works if anything later navigates to `/` with state, removing it
churns two files, and `handleUnauthorized()` now carries the same information by
a better route. Worth deleting the day something else touches that page.

### Two required tests had no subject, and that was known before writing any code

Recorded in [What this prompt cannot test](#what-this-prompt-cannot-test) rather
than discovered late. Both are carried into 005.01 and 005.02 with the failure
mode named, because "reconnection uses a fresh token" is a test that passes
against the broken implementation unless expiry is provoked deliberately.

### Model allocation in hindsight

The allocation held, with one process failure that was not the allocation's
fault: a session limit terminated two Sonnet steps mid-flight. Step 5 had written
its component but not its CSS or the `AppShell` wiring; Step 7 had written the
two prose documents but not the ADR amendment. Both were finished by Opus. The
lesson is about batching rather than about model choice — a step that ends with a
component importing a stylesheet that does not exist leaves the tree in a state
that neither typechecks nor reads as unfinished.

Steps 2 and 3 were correctly Opus: the expiry subscription is the fix for a bug
nobody had reported (a UI that lies after expiry) and needed the library sources
read to find, and the recovery guard is where the loop hazard lives. Step 6 was
correctly Sonnet with Opus reviewing — the tests came back sound, and the review
caught one comment that overstated what a security assertion proved, which is
exactly the class of thing the review exists for.
