## Goal

Tokens are held in memory, so a page reload loses them. This prompt makes that invisible in normal use, and makes expiry-while-open behave predictably rather than silently breaking.

## Requirements

- Reloading the page keeps the user signed in, without them seeing a login form — as long as their provider session is still active.
- When the provider session has genuinely expired, the user sees a login form. That's correct behaviour, not a bug.
- A token expiring while the app is open doesn't break it: in-flight and subsequent requests recover.
- Sign-out ends the session properly and returns the user to the landing page.
- The user is never left in a state where the app looks signed in but nothing works.
- **`startSignOut()` in `src/auth/sign-out.ts` is the seam.** Carried forward from 003.02, and the same shape as `startSignIn`: replace the function's body, delete its `console.info` placeholder, and do not move the call site. `src/shell/Header.test.tsx` mocks that module and asserts the account menu item invokes it **by keyboard**, so the wiring stays proven while the implementation changes underneath it.
- **Sign-out must clear the session, not only the tokens.** Carried forward from 003.02: the header renders its account menu only when `useSession()` returns non-null (`src/shell/Header.tsx`). If sign-out drops the tokens but leaves the session object in place, the menu stays on screen offering "Sign out" to a user who already has.
- **The session derivation already landed — do not build a second one.** Carried forward from 004.02, which had to bring it forward from this prompt: without it the callback route navigated to a guarded page, `RequireSession` found no session and bounced the user to `/`, and signing in returned them to the sign-in control. `src/auth/AuthSession.tsx` maps the OIDC user's `sub` onto the `Session`; `SessionProvider`'s `session` prop survives as its **fallback**, which is what `?devSession=` and `src/test-support/render-app.tsx` supply. **The OIDC user always wins over the fallback**, and that ordering is the thing to preserve. What is left for this prompt is reload recovery, expiry while the app is open, and sign-out.

- **`AuthProvider` is already mounted, in `main.tsx`, around `getUserManager()`'s instance.** Carried forward from 004.02. Two of its props are the hooks for sign-out's return leg — `matchSignoutCallback` and `onSignoutCallback` — so the provider handles the post-logout arrival at `/` without a second route. Do not add one, and do not mount a second provider.

- **`?devSession=<id>` builds a `Session` from a URL, and this prompt is where that becomes dangerous.** Carried forward from 003.02: `src/dev/dev-session.ts` supplies a stand-in session for local testing. It is harmless today because a `Session` is a user id and nothing else — it decides whether `RequireSession` renders or redirects, carries no token, and every API call it leads to is still refused with a 401. **The moment the session is the thing that holds a bearer token, a session constructed from a query string must not be able to mint, imply or stand in for one.** The `import.meta.env.DEV` guard protects the production bundle; it does not protect a developer's own browser, and `?devSession=admin` must never become a local privilege escalation. If the shape of `Session` changes here, re-read that module and decide deliberately what it may set — 001.04 owns the build-flag rule, not this decision.

## Implementation notes

- Reload recovery is a **full-page redirect** to the provider, not a hidden iframe ([ADR-024](../../ADRs/ADR-024-browser-oidc-client-and-token-handling.md)). With an active provider session this is usually a few hundred milliseconds and no visible form.
- Sign-out clears the in-memory session **and** ends the session at the provider, then returns to the landing page. Clearing only the local side leaves the user able to sign straight back in without credentials, which isn't what they asked for.
- **An open event stream outlives its token.** The connection was authorised when it opened and the server doesn't re-check, so events keep arriving after expiry. This is accepted for the MVP and should be documented where a reader would look for it — but it means **revocation doesn't take effect until the stream drops**.
- Reconnection must fetch a fresh token rather than reusing the expired one. Without this, a brief network blip after expiry turns into a permanent failure loop.
- Use the shared 401 policy from 004.01 rather than adding a second path. It is `handleUnauthorized()` in `src/auth/unauthorized.ts`: one deduplicated `signinRedirect()`, which is both the renewal and the sign-in because this client holds no refresh token. Do not add a renewal step in front of it.
- **Sign-out is `signoutRedirect()` on `getUserManager()` plus clearing the in-memory user.** Carried forward from 004.01: the post-logout URI registered with Zitadel is `${TCP_WEB_URL}/`, derived in `createUserManagerSettings()` from `window.location.origin`, so the landing page is where the provider returns the user.
- **`signoutRedirect()` throws when the provider publishes no `end_session_endpoint`.** RP-initiated logout is optional in OIDC. Zitadel has one, so this only bites an external provider — but it bites as an exception thrown out of a menu item, leaving the user apparently signed in. Fall back to clearing the local user and navigating to `/` rather than letting sign-out throw.
- **The session must derive from the same singleton everything else reads.** Carried forward from 004.01: `getUserManager()` in `src/auth/user-manager.ts` is the one client, and `getAccessToken()` and `handleUnauthorized()` already go through it. Building a second manager here would give the header a user the fetch wrapper cannot see.
- Consider what happens with several tabs open, and don't leave one tab in a broken state after another signs out.

## Testing

- A test that reload recovers the session without a visible login form, and one that an expired provider session correctly shows a form.
- A test that a request made after token expiry recovers via renewal.
- **A test that reconnecting an event stream after expiry uses a fresh token**, not the expired one — the failure here is a permanent loop, and it won't appear in a short test unless deliberately provoked.
- A test that sign-out clears the local session, ends the provider session, and lands on the landing page.
- A test that a signed-out user cannot reach a protected route by going back in the browser.
- An accessibility assertion on any state shown during recovery or sign-out.
- **A test that `?devSession=` still cannot displace a real signed-in user.** Carried forward from 004.02: it is only `AuthSession`'s fallback today, so an OIDC user always wins. That is the property that stops `?devSession=admin` becoming a local privilege escalation once the session carries a token, and it is one refactor away from silently inverting.
- **A test that reload recovery does not become a redirect loop.** Carried forward from 004.02: a session that recovers by redirecting to the provider on mount is the same failure `/callback` was built to make impossible, one level up — an unreachable provider would bounce the user forever. `CallbackPage.test.tsx`'s "never redirects to the provider on its own" is the shape to copy.
- **The "no token in browser storage" assertion must still hold once the session carries one.** Carried forward from 004.01: `src/auth/user-manager.test.ts` stores a user with known token strings and greps every key and value of `localStorage` and `sessionStorage` for them. Deriving the session from the token client is exactly the change that could start persisting one — re-run that test rather than assuming it still covers the new path, and extend it if the session is stored anywhere of its own.
