# 008.04 — Response, creation, profile and membership dialogs

Create a plan to build the four dialogs in the MVP that open no event streams: the user
response dialog, the task creation dialog, the profile dialog and the company memberships
dialog.

**This prompt absorbs what were 008.05 and 008.06.** They are the sections of the same
name below, and references elsewhere to `008.05` or `008.06` mean those sections. They
were merged because 008.01 already built the dialog framework, and what was left in each
was the same skeleton three times over: a `Dialog`, its loading/error/empty states, a
labelled input or a read-only list, a close control that returns focus, and one
accessibility pass. Building them together does that work once.

> **Branch:** `p02/008_dialogs`, off `phase-02` — one branch per major index; see [the workflow](README.md)
> **Follows:** [ADR-020](../../ADRs/ADR-020-web-ui-mvp-scope.md) (MVP scope; profile and memberships are read-only), [ADR-012](../../ADRs/ADR-012-human-in-the-loop.md) (human-in-the-loop model), [ADR-023](../../ADRs/ADR-023-backend-api-surface-for-the-web-ui.md) (profile from token claims, membership scoping), [ADR-024](../../ADRs/ADR-024-browser-oidc-client-and-token-handling.md) (which claims are available), [ADR-026](../../ADRs/ADR-026-web-ui-accessibility-and-component-library.md) (component library, accessibility standard), [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md) (announcements), [ADR-030](../../ADRs/ADR-030-component-hooks-for-live-data.md) (component hooks for live data)
> **Needs first:** 008.01 (dialog framework), 006.01 (companies overview), 002.04 (membership-scoped `GET /api/company`), 003.02 (account menu)

## Goal

Four dialogs, built together because they share a skeleton.

The response dialog is why the MVP is interactive rather than read-only
([ADR-020](../../ADRs/ADR-020-web-ui-mvp-scope.md)): an agent that asks a question stops
until someone answers, and a UI that shows you a blocked agent but cannot unblock it
leaves the CLI mandatory for the one workflow that is time-sensitive.

The creation dialog is the one place in the MVP where a user makes something. It is the
entry point to everything the live activity view then shows.

Profile and memberships are the two smallest dialogs in the MVP, reached from the account
menu. Both are **read-only**. Editing either would need user-management endpoints that do
not exist, and read-only keeps them in scope at almost no cost.

## Shared requirements

These apply to all four dialogs. Each dialog's own section below adds to them and does not
repeat them.

- Use `Dialog` from `src/components/Dialog/Dialog.tsx` (008.01). **None of these four pass
  `onMinimise`** — minimising is the chat dialog's alone (008.02), and a dock entry for a
  form or a read-only panel would be a feature nobody asked for.
- Loading, error and empty states, using `LoadingState`, `ErrorState` and `EmptyState` in
  `src/components/` (003.03). Do not hand-roll a second set.
- A close control, with focus returning to whatever opened the dialog. React Aria already
  does this — do not hand-roll it, and do not move or replace a trigger that already
  works.
- **Read data only through `src/api/hooks.ts`.** Do not import `src/api/endpoints.ts`
  directly; eslint will stop you ([ADR-030](../../ADRs/ADR-030-component-hooks-for-live-data.md)).
- No hardcoded user-facing strings — use `t()` from `src/strings`. Note that `t` fills
  `{placeholder}` slots and has **no plural rules**, so phrase any counted string so it
  reads correctly at one.
- For the two dialogs that take input (response, creation):
  - validation errors are **associated with their fields**, not just listed at the top, or
    a screen reader user cannot tell which field is wrong;
  - focus moves to the first invalid field on a failed submit;
  - the pending state is honest. A request that returns before the work it triggered has
    finished should say "sent", not imply more than it knows.

## 008.04 — User response dialog

The dialog where a user answers an agent's question and unblocks it.

### Requirements

- **`useLiveEnquiryState(slug)` gives you a readable conversation.** `ConversationController.get`
  returns the conversation's own fields at the top level, plus `messages` and
  `companyTimezone`, flattened rather than wrapped so a live event can patch the cache by
  `id` ([ADR-030](../../ADRs/ADR-030-component-hooks-for-live-data.md)). The hook takes a
  slug, not an id, because there is no by-id route; `EnquiryChangeSummary.id` is real, so
  the cache still patches it correctly regardless.
- One conversation per open enquiry, showing the question and the context around it.
- The user can type and submit a response.
- Submitting a response closes the enquiry and lets the agent continue.
- Opened from the live activity view's enquiries list, showing the selected enquiry.
- **The `Notification` container is this section's to build.** Carried forward from
  007.01: it deferred rendering `Notification` for a new enquiry, because `Notification`
  requires a `durableHref`/`durableLabel` pair and an enquiry has no URL until this prompt
  decides whether dialogs are routes or component state. A new enquiry is announced
  individually and still appears in the activity view's enquiries list in the meantime, so
  nothing a user can perceive was lost by the wait — but this is where the container
  finally gets built.

### Implementation notes

- The relevant endpoints are the conversation ones: listing open enquiries, reading one
  with its messages, and replying.
- Replying resumes the agent as a side effect. The reply request may return before the
  agent has actually resumed — the UI should reflect "sent" honestly rather than implying
  more than it knows.
- **Handle the already-answered case.** Someone else — or the same user in another tab, or
  via `tcp-cli` — may have answered between the list loading and the reply being sent.
  Failing clearly is fine; failing confusingly is not.
- A new enquiry is announced individually rather than folded into a summary
  ([ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md)) — it is a request for the user
  to act, not background noise.
- **"Individually" means its own announcer channel**, not a `throttleMs` override. Carried
  forward from 003.03: changes coalesce per channel, and a channel's interval is fixed by
  the announcement that opens its window, so an immediate announcement sharing a list's
  channel would wait behind that list's open window instead.
- The response field should be properly labelled and usable by keyboard, with a clear path
  from reading the question to answering it.
- Company timezone context comes back with the conversation; use it when showing times
  rather than assuming the browser's.

## 008.05 — Task creation dialog

The dialog for creating a new task in a company.

### Requirements

- Fields matching what `tcp-cli` asks for when creating a task — check the CLI's task
  creation command for the current set rather than assuming.
- Create and cancel controls.
- Validation feedback before submitting, shown clearly and accessibly.
- Server-side rejections are shown clearly too — including any soft warnings the API
  returns alongside a successful response.
- Opened from the live activity view's 'add new' control (008.07).
- After creating, the user can see the new task without hunting for it.
- **Any further task mutation follows the two-layer shape 008.03 established.**
  `useCancelTaskMutation` in `endpoints.ts` describes the request once; `useCancelTask(taskId)`
  in `hooks.ts` wraps it and owns cache invalidation, calling `invalidateQueries` on both
  `['task']` and `['assignment']` because the server cascades a task change to its
  assignments. A create mutation follows the same split.

### Implementation notes

- **The confirmation pattern for a destructive control already exists — reuse it.**
  Carried forward from 008.03: cancelling a task opens a second `<Dialog>` from inside the
  first (stacked dialogs are supported and tested), its body says what will happen rather
  than only asking, neither button says a bare "Cancel", and an effect rehomes focus onto a
  stable element when the control that opened it disappears. `src/components/TaskDialog/TaskDialog.tsx`
  is the worked example — copy its shape rather than inventing a second one.
- **The task dialog has no provider of its own.** Carried forward from 008.03:
  `TasksList` holds `openTaskId` in local state and mounts `<TaskDialog/>` while it is set,
  rather than going through a context like the chat dialog's `ChatProvider`. If this dialog
  wants to open the task it just created, that is the first caller reaching in from
  somewhere else — and the point at which a `TaskProvider` beside `ChatProvider` in
  `AppShell` earns its place, not before.
- Look at `apps/tcp-cli/src/commands/create-task.ts` and its supporting code for the real
  field set. Don't guess it.
- Decide whether creating also **starts** the task, or only creates it. The API separates
  the two, and `tcp-cli` exposes both. Whichever is chosen, make it obvious to the user
  which happened.
- Material or attachment upload is part of the CLI's flow. Decide whether it's in scope
  here, and say so — if it isn't, don't leave a half-built control behind.
- The API returns soft data-quality warnings in a response header on some create routes.
  These don't fail the request, and they're useful — surface them rather than dropping
  them.
- The task list updates when a task is created — the live stream should cover this, so
  avoid a manual refetch if the event already does the job.

## 008.06 — Profile and company memberships dialogs

The two read-only dialogs reached from the account menu.

### Requirements

**Profile dialog**

- Shows who the user is signed in as.
- Read-only. No editing controls — not even disabled ones, which just raise questions.

**Company memberships dialog**

- Lists the companies the user belongs to.
- Selecting one goes to that company's view.
- Read-only.
- **Since 002.05 this list is authoritative, not informational.** Membership _is_ the
  access control: what it shows is exactly what the user can reach, and a company absent
  from it will refuse them with a `403`. Word it so it reads as "the companies you have
  access to", not "companies you happen to be listed in".

**Both**

- Opened from the account menu in the header (003.02).
- **The account menu is already wired — `onAccountAction` in `src/shell/Header.tsx` is the
  entry point.** Carried forward from 003.02: the three menu items are `profile`,
  `memberships` and `signOut`; the first two currently `console.info` a placeholder.
  Replace those two branches. React Aria's `MenuTrigger` already returns focus to the
  account button when the menu closes, which is the behaviour the shared "focus returns to
  the opener" requirement depends on — don't move the trigger or replace the pattern.

### Implementation notes

- Memberships come from the membership-scoped `GET /api/company` built in 002.04 — the
  same call the overview makes (006.01), with no `?all=true`. Don't add a second way of
  fetching the same thing.
- **Profile data comes from the ID token's claims, read in the browser** — there's
  deliberately no `/api/me` ([ADR-023](../../ADRs/ADR-023-backend-api-surface-for-the-web-ui.md)).
  Zitadel supplies subject, name and email, and the app requests the `profile` and `email`
  scopes (004.01).
- **Handle missing claims.** If a claim isn't present, show something sensible rather than
  an empty row or a raw subject ID. A different identity provider might not supply
  everything Zitadel does.
- **A dialog showing nothing but a subject identifier has a configuration cause, and a
  fix.** Carried forward from 004.01: the claims are read from the ID token, and whether
  the client also calls the provider's userinfo endpoint is the runtime setting
  `OIDC_LOAD_USER_INFO` (`false` by default, because Zitadel puts `profile` and `email` in
  the ID token). A provider that returns a minimal ID token needs it set to `true` — no
  rebuild. Say so wherever the missing-claim fallback is implemented, or the empty dialog
  reads as a bug in this prompt rather than a variable nobody set.
- **Read the claims through the same client everything else uses.** Carried forward from
  004.01: `getUserManager()` in `src/auth/user-manager.ts` is the single `UserManager`; its
  stored user carries `profile`, already merged with userinfo when that is enabled. Do not
  decode the ID token by hand.
- Because both read data that's already loaded elsewhere, they should be fast — avoid
  making them re-fetch what the app already has.
- Note in the code that read-only is a **scope decision**, not an oversight, so a later
  reader doesn't assume the editing was forgotten.
- Selecting a company from the memberships dialog navigates and closes the dialog. Make
  sure focus lands correctly on the destination rather than being lost.

## Testing

### Shared

These apply to all four dialogs, and should be written once against the shared skeleton
rather than four times.

- Component tests queried by role and accessible name.
- Tests for loading, error and empty states.
- A test that focus returns to the opener on close.
- Accessibility assertions on each dialog, with no violations. For the two that take
  input, assert the **error state too — not just the empty form**, since that's where
  problems usually are.
- **Scan `document.body`, not the render container.** Carried forward from 003.02: React
  Aria's `Popover` portals out of the container Testing Library returns, so an
  accessibility scan of `container` with a menu or dialog open examines a tree with
  nothing in it and passes vacuously. `src/shell/Header.test.tsx` shows the pattern.

### 008.04 — User response dialog

- A test of the full path: open an enquiry, type a response, submit, see the result.
- **A test of the already-answered case**, confirming a clear message rather than a silent
  failure.
- A test that the dialog is fully operable by keyboard, from reading to submitting.
- **An announcement test using `spokenPhraseLog()`** confirming a new enquiry is announced
  on its own.

### 008.05 — Task creation dialog

- Every field reachable and labelled.
- Tests of validation: each rule, and that errors are associated with their fields.
- A test that focus lands on the first invalid field after a failed submit.
- A test of a successful creation, and that the new task appears in the list.
- Tests of server-side rejection and of soft warnings being shown.
- A test that the whole form is completable by keyboard alone.

### 008.06 — Profile and company memberships dialogs

- A test that profile details render from token claims, and **a test of the missing-claim
  case**.
- A test that memberships list the user's companies, and that selecting one navigates
  correctly.
- A test that focus lands correctly after navigating.
- A test of a user with no memberships.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- No hardcoded user-facing strings, and no literal values in stylesheets.
- If the creation dialog's field set diverges from `tcp-cli`'s, that's a deliberate
  decision and should be recorded.
- Confirm no token or claim data is written anywhere durable as a side effect of showing
  it.
