# 007.02 — Live activity hooks

## Context

007.01 built the company live activity view: four lists in one file
(`activity/lists.tsx`), each calling a hook named after a REST route
(`useAgents`, `useAssignments`) and relying on the page above to open the one
SSE stream that keeps them fresh.

Two problems for the next developer:

1. **The hooks are named after routes, not after what you see.** Nothing in
   `useAssignments` says "consultations", and the trick that makes it one —
   `taskId: 'null', mode: 'consultee'` — is a comment in a component, not part
   of any interface. A chat is the same endpoint with `mode: 'chat'`, which
   nobody would guess.
2. **There is no signal about which hooks are live.** Some entities are pushed
   to the browser over SSE; roles and knowledge never are. `queries.ts` looks
   uniform, so it reads as if everything updates itself.

This prompt adds one set of hooks that a component author can read as a menu,
splits `lists.tsx` into a file per list, and writes the naming rule down in an
ADR so it survives the next three views.

Three visualisation styles are planned (plain HTML, an arranged layout, an
illustrated office). They will all consume the same data. These hooks are the
shared surface they consume it through.

### Decisions taken before planning

**`Live` means push-updated, and nothing else.** `role`, `company-user` and
`knowledge` are `STATIC_ENTITIES` in `query-keys.ts`; no event ever touches
them. So `useCompanyRolesList`, `useCompanyKnowledgeList` and `useRoleState`
carry no prefix. `useCompanies()` keeps its existing plain name too: a genuinely
live company _list_ needs a list-level stream this app does not have.

**No new hook opens its own stream.** Every hook here reads the shared query
cache. The page owns the one `useEventStream` subscription. An illustrated
office could plausibly call `useLiveAgentState` once per avatar; if each opened
a connection, that is the `MAX_STREAMS = 12` cap, not a facade.

**One door, enforced.** `src/api/queries.ts` becomes `src/api/endpoints.ts` —
one hook per route, internal to `src/api/`. The new `src/api/hooks.ts` is the
only thing components import. An eslint rule enforces it, the same way the
`@tcp/shared` boundary is already enforced.

**List hooks return the full DTO.** No mapping layer. The list routes already
return lighter rows than the detail routes, and live events spread wire-summary
fields onto cached rows — so a hand-written "summary" type would be a promise
the cache does not keep.

### Three places this plan departs from the prompt

1. **`useLiveAssignmentsList` takes an object, not three optional positional
   arguments.** `useLiveAssignmentsList(undefined, undefined, roleId)` is not a
   readable call, and every other params-taking hook in this codebase already
   uses an object.
2. **`useLiveAgentState` takes an object too**, for the same reason, and it is
   the one hook here with real logic rather than a rename — see Step 2.
3. **Browser coverage of live list changes cannot be added.** The browser tier
   cannot sign in: `?devSession=` is compiled out of the production build and no
   test completes a Zitadel login, so no browser test can reach `/company/:id`.
   That work belongs to `009.01`, which owns the MVP journeys. Step 9 writes it
   into that prompt rather than leaving it as a silent gap here.

### Discovered during implementation

**Two detail routes declare no response body, so two of these hooks ship
unreadable.** Found by the tests in Step 5, confirmed against the controllers:

| Route                          | Handler returns                               | `@ApiOkResponse` |
| ------------------------------ | --------------------------------------------- | ---------------- |
| `GET /api/task/{id}`           | `{ task, assignments }`                       | absent           |
| `GET /api/conversation/{slug}` | `{ conversation, messages, companyTimezone }` | absent           |

With no declared body the generated operation has `content?: never`, so
`useLiveTaskState` and `useLiveEnquiryState` are keyed and live-patched
correctly but every property access on `data` fails to compile.

Not fixed here. The fix is a backend change plus `npm run api:generate` against
a running server, which is `002.04`'s territory rather than a web-client hooks
prompt. Recorded in four places instead: the two hooks' doc comments, ADR-030's
Detail section, `web-client.md`, and as blockers in `008.03` and `008.04`.

The same scan found `content?: never` on five other operations. All are
`/internal/*` or storage routes, which no browser calls.

Three changes to the renamed file:

1. Update the header comment's first line to say this file is one hook per
   route and is internal to `src/api/` — components import `hooks.ts`.
2. Add an optional `enabled` parameter to `useAgent` only. `hooks.ts` needs to
   call two lookups and disable one:

   ```ts
   export const useAgent = (id: string, enabled = true) =>
     useQuery({
       queryKey: queryKeys.agent(id),
       queryFn: () =>
         unwrap(api.GET('/api/agent/{id}', { params: { path: { id } } })),
       enabled,
     });
   ```

3. Add a new hook. There is no `GET /api/agent/by-assignment/{id}` route, so
   this is the list route narrowed to one row:

   ```ts
   /**
    * The one agent holding an assignment. Agent and assignment are 1:1, so the
    * list route filtered by `assignmentId` returns at most one row.
    *
    * Resolves to `null`, not `undefined`, when there is no such agent —
    * TanStack Query treats an `undefined` result as a bug and throws.
    */
   export const useAgentByAssignment = (assignmentId: string, enabled = true) =>
     useQuery({
       queryKey: queryKeys.agentByAssignment(assignmentId),
       queryFn: async () => {
         const rows = await unwrap(
           api.GET('/api/agent', { params: { query: { assignmentId } } }),
         );
         return rows[0] ?? null;
       },
       enabled,
     });
   ```

In `query-keys.ts`, add the factory beside `agent`:

```ts
/**
 * Keyed under `detail`, not `list`: this holds one agent, and reusing
 * `agents({ assignmentId })` would put a scalar and an array under the same
 * key. Still prefixed `agent`, so live events patch it like any other row.
 */
agentByAssignment: (assignmentId: string) =>
  ['agent', 'detail', { assignmentId }] as const,
```

Add a case for it to `query-keys.test.ts`, matching the existing cases.

**Boundary:** do not change any other hook body, and do not add `enabled` to
hooks that do not need it.

### The header comment, verbatim

```ts
/**
 * The hooks a component uses to read company data (ADR-030).
 *
 * This is the only data door for a view. `endpoints.ts` sits behind it, one

 *

 * (`CompanyPage` calls `useEventStream`); these hooks only read what it
 * patches. An illustrated view could call `useLiveAgentState` once per avatar,
 * and if each opened a connection that is the `MAX_STREAMS` cap in
 * `subscriptions.ts`, not a facade.
 */
```

### The hooks

Companies:

```ts
export { useCompanies } from './endpoints';

export const useLiveCompanyState = (companyId: string) => useCompany(companyId);
```

`useLiveCompanyState` is a plain alias. It deliberately does **not** fold the
200-with-JSON-`null` case that `CompanyPage.tsx:38-44` handles: rewrapping the
result would cost the discriminated-union narrowing TanStack gives
(`isSuccess` implying `data` is present) to save one well-commented line.

A company's lists:

```ts
export const useLiveCompanyAgentsList = (companyId: string) =>
  useAgents({ companyId });

export const useLiveCompanyTasksList = (companyId: string) =>
  useTasks({ companyId });

/** Chats are assignments in `chat` mode. There is no chat route. */
export const useLiveCompanyChatsList = (companyId: string) =>
  useAssignments({ companyId, mode: 'chat' });

/**
 * Open consultations: assignments in `consultee` mode with no task (ADR-023).
 *
 * `taskId` is the literal four-character string `'null'`, not JS `null` — the
 * server's `AssignmentController` tests for it and maps it to `IsNull()`.
 * Omitting it would mean "any task" instead of "no task".
 *
 * Incomplete by design: a consultation that has been requested but not yet
 * picked up has no assignment row, so it cannot appear here. Any view using
 * this must say so — `t('activity.consultations.partial')` is the wording.
 */
export const useLiveCompanyConsultationsList = (companyId: string) =>
  useAssignments({ companyId, taskId: 'null', mode: 'consultee' });

export const useLiveCompanyEnquiriesList = (
  companyId: string,
  status?: string,
) => useConversations({ companyId, status });

/** Not live: nothing streams a role. */
export const useCompanyRolesList = (companyId: string) =>
  useCompanyRoles(companyId);

/** Not live: nothing streams a knowledge index. */
export const useCompanyKnowledgeList = (companyId: string) =>
  useCompanyKnowledge(companyId);
```

Assignments, which belong to a role and sometimes to a task:

```ts
export interface AssignmentFilter {
  readonly companyId?: string;
  readonly taskId?: string;
  readonly roleId?: string;
}

/** Assignments matching any combination of the three ids. */
export const useLiveAssignmentsList = (filter: AssignmentFilter) =>
  useAssignments(filter);
```

One entity at a time:

```ts
export const useLiveTaskState = (taskId: string) => useTask(taskId);

/**
 * A chat, which is an assignment in `chat` mode.
 *
 * The value is the assignment, not the conversation: the messages are not on
 * it. Read the transcript with `useAgentHistory` for the agent holding this
 * assignment, which `useLiveAgentState({ assignmentId })` will find.
 */
export const useLiveChatState = (assignmentId: string) =>
  useAssignment(assignmentId);

/**
 * A consultation, which is an assignment in `consultee` mode.
 *
 * Only resolves once the consultation has been picked up — before that there
 * is no assignment row and so no id to pass here (ADR-023).
 */
export const useLiveConsultationState = (assignmentId: string) =>
  useAssignment(assignmentId);

/**
 * One enquiry, by slug.
 *
 * A slug rather than an id, unlike its siblings: `GET /api/conversation` has
 * no by-id route, only `/{slug}`. The event summary does carry an id, so the
 * cache patches this row like any other.
 */
export const useLiveEnquiryState = (slug: string) => useConversation(slug);

/** Not live: nothing streams a role. */
export const useRoleState = (roleId: string) => useRole(roleId);
```

The one hook with real logic:

```ts
export interface AgentLookup {
  readonly agentId?: string;
  readonly assignmentId?: string;
}

/**
 * One agent, found by either id it can be reached through. Agent and
 * assignment are 1:1, so both answers are the same agent.
 *
 * `agentId` wins if both are given. With neither, the hook stays disabled and
 * never fetches. Looked up by `assignmentId`, `data` is `null` rather than
 * `undefined` when no agent holds it.
 *
 * Both lookups are called every render, because hooks cannot be called
 * conditionally; the unused one is disabled, so only one request is made.
 */
export const useLiveAgentState = ({ agentId, assignmentId }: AgentLookup) => {
  const byAgentId = useAgent(agentId ?? '', agentId !== undefined);
  const byAssignmentId = useAgentByAssignment(
    assignmentId ?? '',
    agentId === undefined && assignmentId !== undefined,
  );
  return agentId === undefined ? byAssignmentId : byAgentId;
};
```

Finally, re-export the endpoint hooks that have no facade, so `hooks.ts` is a
complete door and nothing has a reason to reach past it:

```ts
export {
  useAgentHistory,
  useCompanyUsers,
  useRoleBySlug,
  useRoleKnowledge,
  useRoleKnowledgeSearch,
  useRoleKnowledgeStatus,
  useTaskHistory,
  useCompanyKnowledgeStatus,
} from './endpoints';
```

**Boundary:** no hook in this file calls `api.GET` directly, sets `staleTime`,
`refetchInterval` or `retry`, or opens a stream. No `any`.

### The eslint rule

The existing `no-restricted-imports` block (around line 85) applies to every
file. **A second block declaring the same rule replaces it rather than merging
with it**, so writing a naive override would silently delete the `@tcp/shared`
boundary. Lift the shared config into a const at the top of the file and use it
in both places:

```js
const sharedPackageBoundary = {
  paths: [/* the existing @tcp/shared entry, unchanged */],
  patterns: [/* the existing @tcp/shared/* entry, unchanged */],
};

const endpointsBoundary = {
  group: ['**/api/endpoints', './endpoints'],
  message:
    "Import from 'api/hooks' instead. `endpoints.ts` is one hook per REST route and is internal to src/api/ — ADR-030.",
};
```

Then the general block uses
`{ paths: sharedPackageBoundary.paths, patterns: [...sharedPackageBoundary.patterns, endpointsBoundary] }`,
and a new block after it, `{ files: ['src/api/**'] }`, uses
`sharedPackageBoundary` alone.

No fixture test for this rule. The `@tcp/shared` one has
`test/fixtures/server-import-must-fail.ts` only because that file belongs to no
tsconfig; this rule fires under a plain `npm run lint`, which every gate runs.

## Step 5 — tests for `hooks.ts` (Sonnet)

**New file:** `apps/frontend/tcp-frontend/src/api/hooks.test.tsx`.

Pattern to copy: `src/pages/CompanyPage/activity/CompanyActivity.test.tsx` —
a real `QueryClient`, `installFetchMock` + `respondByRoute` at the network
boundary, `applyEvent(queryClient, event)` for live changes, no TanStack
mocking. Use `renderHook` from `@testing-library/react` with a
`QueryClientProvider` wrapper that also returns the client, the way
`renderActivity` does.

Two groups.

**Group 1 — each hook asks for the right thing.** One test per hook, asserting
the request `requestedUrls()` recorded. The ones that matter, because they
encode a decision rather than a rename:

- `useLiveCompanyChatsList` → `mode=chat`
- `useLiveCompanyConsultationsList` → `taskId=null&mode=consultee`
- `useLiveCompanyEnquiriesList(id, 'awaiting_user')` → `status=awaiting_user`
- `useLiveAgentState({ agentId })` → one request, to `/api/agent/{id}`
- `useLiveAgentState({ assignmentId })` → one request, to
  `/api/agent?assignmentId=…`, and `data` is the single row
- `useLiveAgentState({ assignmentId })` where the list comes back empty →
  `data` is `null`, and the hook does not throw
- `useLiveAgentState({})` → no request at all

The one-line aliases do not each need their own request test. Cover them with a
single table-driven test that renders each and asserts it hit its route.

**Group 2 — each class of live change reaches the hook.** For each of the five
`EVENT_ENTITIES`, seed the cache through the hook, call `applyEvent` with a
summary of that entity, and assert the hook's `data` reflects it:

- `task` summary patches `useLiveTaskState` and a row in
  `useLiveCompanyTasksList`
- `agent` summary patches `useLiveAgentState` (both lookups) and
  `useLiveCompanyAgentsList`
- an `agent` `state_change` with **no summary** still patches, via
  `synthesiseAgentPatch` — the case `cache.test.ts:151` covers at unit level
- `assignment` summary patches `useLiveConsultationState`,
  `useLiveChatState` and `useLiveAssignmentsList`
- `enquiry` summary patches `useLiveEnquiryState(slug)` even though the key
  holds a slug — `applyEvent` matches on the cached value's `id`, not the key.
  This is worth its own test; it is the least obvious behaviour in the file.
- a `company` event has no summary shape at all, so it invalidates rather than
  patches — assert `useLiveCompanyState` refetches

And one test for the static side: an event of any entity does **not** cause
`useCompanyRolesList` or `useCompanyKnowledgeList` to refetch. That is the
assertion that makes the `Live` prefix mean something.

## Step 7 — ADR-030 (Opus) and the index row (Haiku)

**New file:** `docs/ADRs/ADR-030-component-hooks-for-live-data.md`. ADR-029 is
the current highest.

Follow the house structure of ADR-020 to ADR-029: `**Status:** Accepted
(2026-08-09)`, then `## Context`, `## What needs deciding`, `## Options
considered`, `## Decision`, `## Consequences`, `## Alternatives considered`,
`## Detail`. Plain language in the summary sections, mechanics in `## Detail`.

The decision has three parts and the ADR exists to state them:

1. Components read data through one module, `src/api/hooks.ts`, named after
   what is on screen. `endpoints.ts` is one hook per route and is internal.
2. `Live` in a hook name means the value is pushed and updates itself. Its
   absence means the opposite, and is a fact about the system, not an
   oversight: `STATIC_ENTITIES` in `query-keys.ts` names the three entities no
   event ever touches, and `useCompanies` has no company-list stream behind it.
3. No hook opens a stream. The page owns the subscription; the hooks read the
   cache it patches. `MAX_STREAMS` is why.

`## Consequences` must include what gets harder: a hook that becomes live later
has to be renamed, and every caller with it; and around half these hooks are
one-line aliases, whose only value is the naming scheme being complete rather
than partial.

Cross-reference, do not amend: ADR-025 (the stream and the cache), ADR-023 (the
consultation gap), ADR-021 (TanStack Query).

**Then (Haiku):** add one row to `docs/index.md`'s
`## Architecture Decision Records` table, in ADR order, matching the columns of
the rows above it: `| [ADR-030](ADRs/ADR-030-component-hooks-for-live-data.md) |
Component Hooks for Live Data | Accepted | … | … |`. Status `Accepted`. The
Outstanding cell ends `Implemented by \`007.02\`.`
