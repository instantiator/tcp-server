# 008.01 — Dialog framework and event transcript components

Create a plan to build the two pieces every dialog depends on: the dialog itself, and the component that turns an agent's event stream into a readable conversation.

## Goal

Five dialogs follow this prompt. Building the shared pieces once — correctly, and accessibly — means they inherit it rather than each reinventing it.

## Requirements

**Dialog framework**

- Modal dialogs that trap focus, close on escape, and are labelled by their heading.
- Focus moves in on open, and returns to whatever opened it on close.
- A dock: a bar anchored to the bottom of the view, holding dialogs that have been minimised rather than closed (the chat dialog needs this — 008.02).
- Stacked dialogs behave sensibly, since a dialog can open another.

**Event transcript**

- Renders an agent's event stream as a readable conversation.
- Handles the event kinds the streams actually carry: messages, reasoning, tool activity, status changes, and terminal completion or failure.
- Shows a response arriving progressively, as it streams.
- Each entry is identifiable — author and time — and browsable by a screen reader.
- **Token-level streaming deltas (`StreamDelta`) reach the transcript through `useEventStream`'s `onDelta` callback.** Carried forward from 005.02: they belong in local component state and must never be written to the query cache — high-frequency, append-only, and belonging to one open transcript.
- **A `403` on a stream arrives as an `ApiError` with status 403 and is never retried.** Carried forward from 005.02: the reconnecting reader treats any `4xx` refusal as permanent. The transcript must render that as a permanent refusal, not a spinner that never resolves.
- **Agent and consultation rows in the live activity view are non-interactive, so no assignment-scoped transcript surface is needed.** Carried forward from 007.01: it decided against adding an "assignment dialog" — ADR-020 lists no such dialog, and 007.01 chose not to add one — so agent and consultation rows in `AgentsList`/`ConsultationsList` render as plain text with nothing to open. This transcript component is consumed by the task dialog (008.03) and the chat dialog (008.02) only; it does not need a mode that shows one bare assignment's history.

## Implementation notes

- **Decide explicitly whether to port or reimplement the CLI's rendering.** `apps/tcp-cli/src/lib/render/audit-renderers.ts`, `line-format.ts` and `apps/tcp-cli/src/lib/chat/wire-parse.ts` encode real earned knowledge: legacy payload fallbacks, the rule for de-duplicating streamed deltas against the audit row that follows them, and placeholder handling for blank responses. **Read them before writing anything.** If this is reimplemented without reference to them, the browser will rebuild it worse and the two clients will disagree about what the same event means.
- Their logic is portable; their shape is not — they're built around terminal output types. The realistic outcome is porting the logic and replacing the presentation layer.
- Use React Aria Components' dialog rather than hand-rolling. Focus trapping, scroll locking and stacked-dialog semantics are exactly where hand-written implementations fail.
- **Streaming deltas never touch the query cache** — they're local component state ([ADR-021](../../ADRs/ADR-021-web-ui-framework-and-architecture.md)).
- **Never announce a partial response.** Words appear on screen as they arrive; the announcement happens once, when the response is complete. This is the single most important rule in [ADR-027](../../ADRs/ADR-027-screen-reader-strategy.md) — announcing per token makes the application unusable.
- Whether a completed response is announced in full or just as "a response arrived" is **unresolved** in ADR-027, pending the manual screen reader pass. An agent's answer can run to several paragraphs. Make it easy to change.
- **The announcer is `announce({ channel, change, params })` from `src/announce/announcer.ts`, and a transcript must not render a live region.** Carried forward from 003.03: it owns the only two, in `document.body`. Give each open transcript its own channel, so two dialogs streaming at once are two sentences rather than one describing neither.
- **Suppressing per-token announcements is your job, not the throttle's.** Carried forward from 003.03: coalescing combines changes that were _asked to be announced_; a token that never calls `announce` costs nothing. Announce on completion only — do not stream deltas into the announcer and rely on the interval to thin them, which would still say something every ten seconds mid-response.
- Each open transcript needs its own stream connection. Get them through the subscription manager (005.02), which enforces the connection limit.
- A transcript that unmounts loses its local state; reopening re-primes from the agent's history endpoint. That's a real request — account for it.

## Testing

- Dialog tests: focus moves in on open and back on close, escape closes, the dialog is labelled, focus is trapped while open.
- A test for stacked dialogs, and one for the minimise-to-dock behaviour.
- Transcript tests fed by a mocked stream, covering **each event kind the streams carry** — not just messages.
- A test that a streamed response renders progressively.
- **A test that a streaming response produces no per-token announcements**, using `@guidepup/virtual-screen-reader` and `spokenPhraseLog()`. This is the specific failure ADR-027 exists to prevent, and it must be covered here.
- A test that a completed response announces once. **Test it under `StrictMode`** — carried forward from 003.03: the announcer counts repeats rather than de-duplicating them, so an effect guarded on "have I run?" rather than on the value that changed announces the same response twice, and `src/test-support/render-app.tsx` is the only helper that would currently catch it.
- If the CLI's renderers are ported: tests proving the same event produces equivalent output in both clients, so they can't drift.
- Accessibility assertions on the dialog and the transcript, with no violations.

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- If shared code moves or changes, run the full suite via `./scripts/run-all-tests.sh` — `tcp-cli` depends on it.
- No hardcoded user-facing strings, and no literal values in stylesheets.
