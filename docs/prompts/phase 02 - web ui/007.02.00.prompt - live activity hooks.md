# 007.02 - Live activity hooks

Create a plan to make the supporting code for live activity components more accessible to new developers.

> **Branch:** `p02/007_live-activity`, off `phase-02` — one branch per major index; see [the workflow](README.md)
> **Follows:** (Not yet documented in ADRs)
> **Needs first:** 007.01

## Context

I have a preference for a simple way for components to consume live company data. There's a future where the user can choose between different visualisations:

- simple html (the view we have now, very simple, optimal for accessibility)
- an arranged, styled, html view (better use of space as a standard backend)
- an illustrated office (avatars of agents work in cubicles (on a floor per task), move to meeting rooms for consultations)

Each of these components and sub-components would benefit from being able to consume live company / agent data through a common and intuitive interface. In discussion with you, we've reached agreement that set of hooks would offer that:

- current state of the company, tasks, agents, etc. (everything we had in our live lists so far) - updated as events change data

And similarly, hooks for:

- All companies (eg. `useCompanies()` — this already exists, from 006.01; no rename needed)
- Each company's current state (eg. `useLiveCompanyState(id)`)

Company lists with summary data, not the full entity:

- `useLiveCompanyAgentsList(id)`
- `useLiveCompanyTasksList(id)`
- `useLiveCompanyChatsList(id)`
- `useCompanyRolesList(id)`
- `useCompanyKnowledgeList(id)`
- `useLiveCompanyConsultationsList(id)`
- `useLiveCompanyEnquiriesList(id)`

Assignments are an interesting case - they might be associated with a task, but are always associated with a role. It should be possible to look them up by providing one or more ids:

- `useLiveAssignmentsList(companyId?, taskId?, roleId?)`

Individual entity states for entities with unique ids, that can track the full detail of the entity's state:

- `useLiveTaskState(id)`
- `useLiveChatState(id)`
- `useLiveConsultationState(id)` — `id` is the assignment id, and this only resolves once the consultation has been picked up (see below)
- `useRoleState(id)`
- `useLiveEnquiryState(slug)` — takes a slug, not an id (see below)

Agent and assignment are 1:1 - and it should be possible to look up the same data by either id:

- `useLiveAgentState(agentId?, assignmentId?)`

### Naming: `Live` means push-updated, nothing else

Dropped from `useCompanyRolesList`, `useCompanyKnowledgeList` and `useRoleState`, and from the knowledge-list/indexing-status fields that were bundled into `useLiveCompanyState`. `role`, `knowledge` and `company-user` are `STATIC_ENTITIES` in `query-keys.ts` — the code's own comment says why: _"Nothing streams a role, a member list or a knowledge index, so these refetch only when their own hook asks."_ A hook named `useLiveRoleState` would promise something the system has already decided not to build. A consumer wanting both a company's live state and its knowledge list calls `useLiveCompanyState(id)` alongside the plain `useCompanyKnowledgeList(id)`.

`useCompanies()` keeps its existing, un-prefixed name for the same reason: a genuinely live company _list_ — one that patches for any company, not just whichever one the current page happens to be individually subscribed to — needs a list-level stream this app doesn't have; only per-company channels exist. Not building that here (see Deferred for later).

**No new hook opens its own stream.** Every hook above reads the shared query cache exactly as 007.01's four lists do — the page or container component owns the one relevant `useEventStream` subscription (reusing `CompanyPage`'s where it already exists), and every hook here is a facade over the cache that subscription patches. This matters more here than it did in 007.01: an illustrated-office view could plausibly want one `useLiveAgentState` call per avatar, and if each independently opened a stream, that's the `MAX_STREAMS` cap 005.02 warned about, not a facade.

### What's still not possible

Only one genuine gap remains:

- A consultation that's been requested but not yet picked up. It has no assignment row — ADR-023's gap — so there's nothing to key on yet.

Once picked up, a consultation _is_ an assignment like any other, addressable the same way a chat is (`useLiveConsultationState(id)` above, `id` = assignment id).

> **Correction to an earlier round of this doc:** enquiries do have a clean id — `EnquiryChangeSummary.id` is a real field (`libs/tcp-shared/src/events/wire-events.ts`). What's actually missing is a fetch-_by-id_ route: `ConversationController`'s only detail route is `GET /api/conversation/:slug`. So a per-item enquiry hook is buildable now, it just takes a slug — matching the existing `useConversation(slug)` — rather than an id like its siblings.

### Considered

We discussed also capturing the most recent event (ie. the event that caused the most recent change to a data source), but this is currently complex to extract (it's discarded earlier up the chain) and not necessary for now.

> **Most recent event** is the one genuinely new piece
>
> This part isn't a hook-signature exercise — `applyEvent()` currently discards the raw event once it's extracted `summary` for the patch. To expose "most recent event" per entity you'd need a design decision: a new cache entry per entity (`[entity, 'lastEvent', id]`), a small separate map, or something else — and whether it's the raw `AuditWireEvent` or something normalized. Worth calling out explicitly as its own step, because it's where the actual engineering is, not the facade.

One goal of capturing the most recent event was to enable activation of animations or transitions between states, but it's likely sufficient for future components to achieve that by diffing their current state with previous state, and activating any transitions that aren't currently underway.

This decision should be reviewed at a later date.

## Goal

- Simplicity for new developers, and easily identified hooks across the UI code
- Updated documentation

When creating a component that can visualise (and eventually, interact with) entities in the system, simple hooks (backed by more complex sources like TanStack Query) make it easier to develop.

## Requirements

Break up the development into units of work that can be tested by quality gates as the plan is implemented.

### Clarity

Implementing the new hooks and refactoring existing components can be completed as separate units of work, to permit new tests and a quality gate check between them.

- New hooks for each of the classes of live data that a component might subscribe to
- Refactor the existing components `AgentsList`, `TasksList`, etc. in `lists.tsx` to use the new hooks

### Simplicity

- Break out each list type from `lists.tsx` and place into a separate component file in `apps/frontend/tcp-frontend/src/pages/CompanyPage/activity/` - eg.
  - `activity-list-utils.ts` (shared interfaces, consts, utility functions)
  - `AgentsList.tsx` (contains `AgentsList`)
  - `TasksList.tsx` (contains `TasksList`, `TaskStatusFilter`)
  - `ConsultationsList.tsx` (contains `ConsultationsList`)
  - `EnquiriesList.tsx` (contains `EnquiriesList`)

### Testing

- New tests establish that each class of change from TanStack Query results in an update by the appropriate hook
  - Where necessary, mock - follow the established pattern for this eg. `CompanyActivity.test.tsx` already calls `applyEvent(queryClient, event)` directly against a real `QueryClient` (ie. no TanStack mocking, which is the production path)
- New component tests for each component (if not already implemented)
- Check if browser tests cover live state changes amongst all 4 implemented lists, and implement if missing
- Accessibility properties of the UI are unaffected by component changes
- Screenreader content unaffected

### Documentation

- A new ADR representing the decision to implement hooks
  - Clear
  - Simple language
  - Covers the high level decision only
- Updated (or new) developer documentation for writing components that show live data (ie. how to use the hooks)

### Deferred for later

For deferred work, modify upcoming prompts in phase 02 (as described in 'Carry-forward'), or add to `docs/prompts/deferred-phases.md`

- Design and implement a way to clearly arrange and represent the components to group by theme/style of UI in the code base (eg. for the simple, arranged, illustrated styles)
- Add an assignment row the moment a consultation is requested, not just once picked up — the one entity that still has no id to track live, now that enquiries and picked-up consultations are resolved above
- A list-level stream for companies, so `useCompanies()` can genuinely patch for any company rather than only the one the current page happens to already be subscribed to
- Capture and provide the most recent event through hooks, to simplify detection of the most recent change (ie. to simplify activation transitions / animations)

## Quality gates

- `./dev-environment/scripts/check.sh` passes; fix what it reports.
- Zero lint errors and zero warnings, including `jsx-a11y`. No `any` casts.
- No hardcoded user-facing strings, and no literal values in stylesheets.
- Use `scripts/run-all-tests.sh` as a final pass to ensure the system works as intended.
