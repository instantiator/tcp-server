## Times and timestamps

Please review all timestamps and times and dates held in the system. They should all be stored as UTC (or unix time, or another common and unambiguous timestamp format), and converted to local time by any clients that present data to the user. The LLM should be given the UTC time and date in its initial prompt.

Please also confirm how minio stores timestamps and manages time. Ideally it would also present local time to users, and store time internally the same way the rest of the system does.

Please modify `LcpCompany` to hold timezone information for time and date presentation to users.

## Error logs during tests

Some tests are for error cases, and the lcp-server (and maybe other services) will log errors as they run. Please capture and hide this logging, so that it doesn't appear while the tests run. Please add some `expect()` statements to confirm that the errors are recorded. (Be reasonably flexible and search for keywords in the logged messages.)

## Warnings about data

Some data is technically acceptable when missing (eg. an empty set of knowledge domains on a role), however it's inadvisable - and the system should warn when this occurs. eg. using lcp-cli to set-role, if the role has empty knowledge domains, the user should be shown a warning (but the action should proceed).

Cases to warn about:

- empty knowledge domains
- company context is blank or null
- role prompt is blank or null

## Provision of `systemPromptTemplate` and `mcpServerList`

- `systemPromptTemplate` is currently on `LcpRole` - there should also be a field on `LcpCompany` and a baked default value that can be provided if either of these are blank (keep this in `prompts.jsonc`). Precedence: role overrides company overrides default value.
- `LcpCompany` should also have an `mcpServerList` - these are additive (ie. they don't have an order of precedence) - the MCP servers made available to agents should be a combination of the default servers provided by the system, those provided in `LcpCompany` and those provided in `LcpRole`

The default system prompt template should say something _like:_

> You are an agent operating within a company. Your role is {{name}} ({{description}}). There are users and other roles available in this company. Agents can be created from any role. Each role has different specialisms, knowledge, and capabilities. To complete the tasks given to you, you may need to consult other roles, consult a user, explore your own memory, or interact with files in shared storage. The time and date is: {{date}}.

## Initial prompt size estimator

Please review ways to reflect on and estimate the size of an initial prompt (using the 8 part prompt structure) for a given company and role based on some default assumptions. The goal is to support the user to review and set a sensible context window size ahead of starting.

Ideally this shouldn't require a _running_ service.

Things to consider:

- an estimated size of a (fairly simple) initial query from the user
- an estimated size of retrieved RAG information (is there an upper limit for this? there ought to be and, if so, use that)
- calculated size of the initial MCP self-descriptions (these should be known)
- calculated size of the other parts of the initial prompt (should be known: system prompt, role prompt, etc.)
- calculated size of the final instruction (should be known)
- an estimated size of a conversation entry (query or response)
- estimated size of an additional N conversation entries

Add an initial prompt size estimator to `lcp-cli`, eg. with verb `estimate-context-window` - the user should be able to override (optionally):

- company
- role
- all estimated sizes (initial query, retrieved RAG, conversatino entry, ...) (in bytes/words/tokens)
- all calculated sizes (initial MCP self-descriptions, other parts of the initial prompt)
- N (ie. estimated length of the conversation before compaction)
- preferred output (final estimated context window recommendation / full JSON details)

Defaults:

- If not provided, select the company with the largest company prompt + role prompt
- If not provided, select the role with the largest prompt (found in the selected company)
- If not provided, provide a sensible N, so that the conversation is usable and doesn't have to compact too frequently
- If not provided, provide a sensible estimate for all estimated parts
- If not provided, use known information for the calculated parts
- Default to providing the full JSON details in the output

It should prepare:

- the size of the initial user query
- the value of N used
- the estimated / calculated size of each part of the prompt (in both bytes and tokens)
- the recommended total context window (allows for N entries) in tokens

Outputs:

- `stderr` = progress and values used
- `stdout` = either the recommended context window (numeric) OR the full calculation (json)

## `lcp-cli` reference-by-slug

At the moment, `LcpCompany` has a unique property called `slug` - this should be a secondary index, as we'll be using it for looking up companies in future.

We should also add a `slug` property to `LcpRole`, too - also a unique secondary index.

The goal is that calls through `lcp-cli` (ie. user initiated calls) should be able to specify `--company-id` or `--role-id` as they do now, but the user should have the option of providing `--company-slug` or `--role-slug` everywhere they do that, to address the entity by something more human-readable (but still unique).

In addition, when using `--set-role` or `--set-company` with a partial role or company, they should also be able to provide `--role-id` / `--role-slug` / `--company-id` / `--company-slug` (as appropriate) to overwrite an exisiting company or role, so that they genuinely only need provide the properties that they're overwriting in the json they provide. (They should still be able to not do that, and just provide the object with its id, to overwrite the object. Providing the slug in the json would overwrite the slug, not use it as an index.) I hope that's clear! Clarify with me if not.

Please ensure that `slug` property on both company and role is set up as a secondary index to facilitate fast lookup when needed.

### `setCompany` example

`setCompany` currently assumes that if there's an `id` on the `DeepPartial<LcpCompany>` provided, then it's updating rather than creating. However, it should also accept optional `id` and `slug` parameters that would also indicate that it should update rather than create - and determine what which entity to update using these indices, eg.

```ts
const updateIndex = id ?? company.id ?? this.getCompanyIdBySlug(slug);
const isUpdate = !!updateIndex;
```

In this example code, `getCompanyIdBySlug` would return undefined if `!slug`.

There's also an oddity in `setCompany` - it does a replacement by deleting the current company _by slug_ - that doesn't seem right to me. I think it ought to do it using `updateIndex`.

I also think it ought to look up the indices (if provided) before it does anything to ensure it can find the company. It should fail with a `404` if it can't find the company it needs to update.

I also think `replace` doesn't need to be provided - it's equal to `isUpdate`.

Once we settle on a pattern for this, it should be replicated for `setRole`.
