## How BullMQ concurrency works

BullMQ does **not** use OS threads. Node.js is single-threaded; all concurrency is cooperative via the event loop.

When `new Worker(queueName, processor, { concurrency: N })` is used, BullMQ maintains up to `N` in-flight calls to the `processor` async function at once. Because `processor` is async and `AgentLoopService.run()` is full of `await` points (DB calls, LLM streaming), the event loop is free to process other jobs while any one agent is waiting for I/O.

So the queue does **not** block — it just controls the maximum number of concurrent coroutines, not threads. The default without the `concurrency` option is `1`, which means jobs queue up and wait for the previous one to finish (effectively serial).

**Practical limit:** Each concurrent agent opens its own `PostgresSaver` connection pool. Running very high concurrency (e.g. 50) would exhaust PostgreSQL connections. `concurrency: 5` is a safe MVP default; move to config when per-role resource limits are needed.
