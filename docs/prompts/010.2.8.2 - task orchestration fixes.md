# Task orchestration fixes (010.2.8.2)

Follow-on to `010.2.8.1 - task orchestration improvement.md`. Manual testing of
the orchestration flow (cat-assistant / chicken-assistant fixtures) surfaced two
related problems; this part fixes both.

## Problems observed

1. **Agents make poor tool decisions.** Asked (via consultation) whether it
   wanted a worm, the chicken-assistant wasted iterations and tokens: it typo'd
   a tool name, narrated a tool call instead of invoking it, and wrote a full
   working file when a plain-text answer would have done. Root cause:
   consultation replies run in **`implement` mode**, whose prompt pushed
   "produce your outputs as working files", and no mode prompt told the agent to
   _invoke_ tools rather than narrate them, to use exact tool names, or to
   match the output's weight to the request.

2. **A task wedged in `planning`.** A planner (`plan` mode) had the consultation
   tool available, so instead of calling `create_plan` it short-circuited and
   consulted chicken-assistant, which produced the report in an **orphan
   assignment** working directory (`lcp/<company>/assignments/<uuid>/working/…`).
   The planner never produced a plan and the task stayed in `planning`. The
   orchestrator only repairs a plan-less planner at **restart**
   (`reconcileTask`), not at runtime, and a planner paused mid-consultation that
   never cleanly resumes is a wedge recovery can't see.

## Resolutions

### 1. Reword every mode prompt + the consultation suffix

`libs/lcp-shared/src/prompts/mode-prompts.ts` (`MODE_PROMPTS`). Three
cross-cutting principles added where relevant:

- **Invoke, don't narrate** — writing out or describing a tool call does not
  count; actually call it.
- **Exact names** — use each tool's exact name; call `describe_server` for the
  exact names and signatures (directly targets the typo/narration failures).
- **Right-size the output** (implement + consultation) — a short answer goes in
  the `complete_assignment` `summary` (optionally one `inline-text` artifact);
  create working files only when the deliverable is itself a document or dataset.

Per mode: `implement` fronts the right-size guidance so files are the exception;
`plan` drops "consult other roles / put questions to the user" and states it is
plan-only with no consult/user-query/file-write; `qa` and `chat` gain the
invoke/exact-name lines. The `CONSULTATION_PROMPT_SUFFIX` in
`apps/lcp-server/src/api/pause-and-resume.service.ts` is reframed: a consultation
is usually a question, not a document — answer concisely in the `summary`, only
create files if genuinely needed, and actually invoke `tasks__complete_assignment`.

Kept in place per the existing per-service prompt convention (each app owns a
co-located `prompts.jsonc`; lcp-server holds static prompts as TS consts) — no
new central prompt location. `lcp-mcp-tasks`'s `describe_server` output already
interpolates `MODE_PROMPTS`, so it stays consistent automatically.

### 2. Per-mode tool restriction — strip `plan` mode

New `libs/lcp-shared/src/prompts/mode-tools.ts`: `MODE_DENIED_SERVERS` /
`MODE_DENIED_TOOLS` (only `plan` populated) plus `serverNamesForMode` and
`filterToolsForMode`. A `plan` agent is denied the `interactions` server
entirely (no agent consultation, no user queries) and the mutating storage tools
(`append`/`replace`/`delete`/`restore`\_working_file); it keeps storage reads,
memory, and the tasks server (`create_plan`).

Applied in `apps/lcp-agent/src/agent/agent-loop.service.ts` `runLoop`:
`serverNamesForMode(...)` before `loadTools` (a denied server is never
contacted), then `filterToolsForMode(...)` after (drops the mutating tools on
otherwise-kept servers). Other modes are unrestricted (the filter short-circuits).

Effect: a planner physically cannot consult, message the user, or write files —
so the short-circuit is impossible, and with **no pause vector** the existing
`create_plan` required-tool enforcement always drives the run to completion or a
clean `failRun` → `handleAgentFailed('plan')` → task `failed`. Planning can no
longer stall.

### 3. Guarantee planning terminates (belt-and-braces)

- `resolveRequiredTools` (`agent-loop.service.ts`) now logs at `error` (not
  `warn`) when a **mode completion tool** is the one missing from the loaded
  toolset — that is a wiring bug, not a benign optional skip.
- `TaskOrchestrationService.handleAgentCompleted` (new), called from the
  internal `POST /internal/agent/:id/complete` endpoint: if a `plan`-mode agent
  reaches `Completed` while the task is still `planning` with an empty plan, fail
  the task at runtime (reusing `reconcileTask`'s `plannerDead` predicate) instead
  of waiting for restart. A no-op for every other completion.

`// ponytail:` the broader "a lost fail/complete HTTP callback strands any task
until restart" case is out of scope — restart `reconcileTask` already covers it;
a periodic reconcile sweep is the upgrade path if it proves necessary.

### 4. Validation feedback for enumerable values (added after live testing)

Live testing (small local model) showed the planner _did_ stop consulting and
_did_ invoke `create_plan` — but with an **invented role** ("Food Researcher")
instead of a real one, so the call was rejected with a dead-end error that named
neither the valid roles nor batched the other problems. Two changes give the
model every chance to pick valid values and fix them in one retry:

- **Proactive**: a plan-mode agent's initial prompt now includes the company's
  **role roster** (`buildAvailableRolesMessage` in `@lcp/shared`, injected in
  `AgentLoopService.buildInitialState`; `AgentLoopService` gains an `LcpRole`
  repo). The planner sees the exact slugs before it plans.
- **Reactive**: a shared `buildEnumValidationError(purposeOfTool, invalid[])`
  (`@lcp/shared`) reports **every** invalid enumerable value at once, names the
  **valid values** for each in plain English, and closes with
  _"If you still intend to `${purposeOfTool}`, try again with corrected values for
  `${csvOfInvalidProperties}`."_ Applied wherever a tool validates a known
  enumerable set:
  - `create_plan` — assignment **roles** (valid = company role slugs) and
    **artifact types** (`expected`/`materials`), all collected and reported
    together (`AssignmentService.planTask`).
  - `complete_assignment` — **prepared artifact types** (`AssignmentService`).
  - `request_agent_consultation` — target **role** (valid = company role slugs),
    at the internal pause endpoint; the interactions MCP tool now **relays** 4xx
    corrective messages (new `relay4xxOrError`, mirroring tasks' `relayOrError`)
    instead of swallowing them into a generic failure.

Other MCP tools take no enumerable-set params (storage paths/filenames are
free-form; `assure_assignment`'s accept/reject is already a zod enum), so there
was nothing to change there.

### 5. Local-model support (added after a second live run)

A clean live run then showed the planner **succeed** (real roles first try, one
retry to fix an artifact type from the enum error), but the whole task still
crawled and the implement step failed. Audit review found three throughput
problems, all fixed:

- **The planner never stopped after `create_plan`.** Unlike `complete_assignment`
  (which pauses the implementer for QA), `create_plan` didn't end the planner's
  run — it kept looping to `max_iterations`, hogging the model for 15+ minutes
  after its job was done. Now `AssignmentService.planTask` marks the plan
  assignment `succeeded` and completes the planner agent, so the supervised loop
  detects the terminal status and exits promptly (`create_plan` is the planner's
  completion, mirroring `complete_assignment`).
- **Worker concurrency was hard-coded to 5**, so up to five agents thrashed one
  local model. Now configurable via `AGENT_WORKER_CONCURRENCY`
  (`DEFAULT_AGENT_WORKER_CONCURRENCY = 5`, resolving the existing `ponytail:`
  marker on the worker); the local `.env` sets it to `1` so a single shared
  model isn't starved.
- **Iteration budget** raised for the slow local model (`.env`
  `AGENT_ITERATIONS` 20 → 40), which burns turns narrating before it acts.

### 6. Input forgiveness + clearer QA prompt

- **Artifact-type aliases.** `canonicalArtifactType` / `canonicaliseArtifacts`
  (`@lcp/shared`) normalise common LLM near-misses before validation and storage:
  case-folding, `_`/spaces → `-` (`inline_text` → `inline-text`), and word
  aliases (`text`/`inline`/`string` → `inline-text`). Applied to `create_plan`
  (expected/materials) and `complete_assignment` (prepared); an unrecognised
  value still fails, now with the valid-values list. Complements §4's enum
  errors — accept the obvious, explain the rest.
- **QA mode prompt** reworded: it wrongly implied every prepared artifact is a
  storage path. It now states each artifact is either inline text (given
  directly) or a file path (read via storage), so a QA agent knows what to expect.

### 7. Tool-call reliability + fewer wasted turns (round 3)

Root of the repeated failures: the weak local model **narrates** tool calls
instead of invoking them, and burns turns on setup. Four changes, all wired
through the shared graph so chat and worker paths stay consistent:

- **Forced tool calls.** `buildAgentGraph` gains a `toolChoice` forwarded to
  `bindTools`. The worker sets it **mode-aware**: `'required'` for
  `plan`/`implement`/`qa` (they must end in a tool call — the model can't narrate
  one instead), `'auto'` for `chat` (needs to reply in prose). Hands the tool-call
  requirement and parameter validation to the established OpenAI/LangChain path.
- **Tools enabled from turn 1.** The describe-then-reveal gating
  (`ToolVisibilityTracker`, `ttl = 3`) is **removed** — it cost round-trips and
  let the model "forget" a tool after a few iterations. All mode-filtered tools
  are bound from the start; their schemas are compact (~1k tokens/mode). The
  tracker and its spec are deleted; both operation paths (`AgentLoopService`,
  `ChatService`) bind the full mode-filtered set. Mode prompts no longer tell the
  agent to call `describe_server` first (it's now optional, for fuller detail).
- **No knowledge service for empty-KB roles.** `AgentRagService.hasKnowledge`
  (a cheap `EXISTS` query, no embedding) gates two things: the `memory` server is
  dropped from the loaded set when the role has no indexed chunks, and RAG
  retrieval (including the embedding call) is skipped. Empty RAG prompt parts were
  already omitted. A server that contributes no tools (mode-filtered or dropped)
  never appears in the services list, since that list derives from loaded tools.

### 8. Output-gate contract (round 4)

A live run reached execution but the implementer got stuck: the planner set an
assignment's expected output as `inline-text` with a descriptive `value`, the
implementer produced a **file**, and the gate — which treated that `value` as a
**regex** the submitted inline text must match — rejected every attempt with a
message the agent couldn't act on. Three changes:

1. **Planner guidance.** The plan prompt now tells the planner to match each
   expected output's _type_ to what the step produces (`assignment-working-path`
   for a file/document, `inline-text` for a short text answer) and to make the
   final step produce the task's overall expected output.
2. **Actionable gate messages.** `checkOutputGate` failures now name the exact
   `prepared` entry to add (`{ type, value }`) and state that a file does not
   satisfy an `inline-text` output (and vice-versa), so the agent can correct the
   _form_, not just edit content.
3. **Gate checks shape, not content (3b).** An `inline-text` expectation is now
   satisfied by any non-empty `inline-text` artifact in `prepared`; the expected
   `value` is a description for the agent/QA, **not** an enforced regex. Judging
   whether the content is actually right is the **QA agent's** job — the gate no
   longer blocks a reasonable submission before QA sees it. (`inlineMatches`
   removed.)

## Tests

- Unit: `mode-tools.spec.ts` (denials for `plan`, untouched for other modes,
  prefixed/unprefixed names); `mode-prompts.spec.ts` (new invoke/exact-name/
  right-size/plan-restriction phrases); `task-orchestration.service.spec.ts`
  (`handleAgentCompleted`: fails a plan-less planning task, no-op when a plan
  exists, no-op for non-planner); `internal.controller.spec.ts` (complete
  delegates to `handleAgentCompleted`).
- Existing `agent-loop.service.spec.ts` stays green (implement/plan-mode runs
  unaffected by the identity/short-circuit filter).
- Validation feedback: `enum-validation.spec.ts` (all-at-once message, valid
  values, suffix); `mode-prompts.spec.ts` (`buildAvailableRolesMessage`);
  `assignment.service.spec.ts` (`create_plan` reports every invalid role/type at
  once, naming valid roles); `interactions-tools.service.spec.ts` (consultation
  relays a 4xx corrective message instead of a generic failure).
- Local-model support: `assignment.service.spec.ts` (`create_plan` completes the
  planner agent and marks its plan assignment `succeeded`);
  `agent-worker.service.spec.ts` (worker concurrency falls back to
  `DEFAULT_AGENT_WORKER_CONCURRENCY`).

## Working practices (mandatory)

Strict TypeScript, no `any`. `/** */` intent comments on
classes/methods/functions, `//` inside bodies, `{@link}` for type refs. No new
deps; no unrequested changes. Quality gates at each stage: `npm run format` →
`typecheck && lint && build && test` → `./scripts/run-e2e-tests.sh` →
`./scripts/run-all-tests.sh` + `./dev-environment/scripts/check.sh`. Never
`--no-verify`.
