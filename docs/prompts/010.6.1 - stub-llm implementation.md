# 010.6.1 — lcp-stub-llm implementation

## Context

`docker/stub-llm/server.js` is a 170-line, dependency-free Node script that fakes an OpenAI-compatible `/v1/chat/completions` + `/v1/embeddings` endpoint for one integration test (`chat-llm.integration-spec.ts`). It has no prompt matching, no tool-call simulation, and one canned response set via `/stub/config`.

`docs/prompts/010.6 - stub-llm.md` asks for this to grow into `lcp-stub-llm`: a config-driven fake LLM (prompt→response matching with `loop`/`random`/`sequence` modes, tool-call responses, per-token delay simulation, optional API-key auth) that can drive whole agent/task flows through pre-scripted conversations — and that is architecturally independent enough to be split into its own repo later. This plan designs that app, its tests, and the changes needed elsewhere in this repo to adopt it.

Three scope decisions were confirmed with the user before designing:

- **Tool calls**: `lcp-stub-llm` only emits OpenAI-shaped `tool_calls` in its response, exactly like a real LLM. It does **not** hold its own MCP client or call MCP servers itself — the existing LangGraph `ToolNode` in `lcp-agent`/`lcp-server` already dispatches tool calls to real MCP servers, so simulating that here would duplicate working machinery for no benefit.
- **App shape**: `apps/lcp-stub-llm` is a plain Node/TS app with its own `package.json`, `tsconfig.json`, lint config, and test config — not a NestJS app, not registered in `nest-cli.json` or root `build:apps`/`typecheck`, and importing nothing from `@lcp/shared` or other apps. This matches the "no shared code, exportable later" requirement and continues the current zero/minimal-dependency style of `server.js`.
- **Multi-format future-proofing**: this suite only ever needs an OpenAI-compatible wire format today (`@langchain/openai`'s `ChatOpenAI` is the only client), but since `lcp-stub-llm` is explicitly meant to become a standalone tool for testing _other_ LLM/agentic systems later, the request/response handling is built behind a small per-format adapter seam now, with only the OpenAI adapter implemented. See "API format abstraction" below.

### Config schema (`config.ts`)

```ts
interface StubTool {
  tool: string;
  data: unknown;
}
interface StubResponse {
  text: string;
  tools?: StubTool[];
}
type ResponseMode = 'loop' | 'random' | 'sequence'; // default 'sequence'

interface PromptRule {
  match: string; // compiled as a RegExp — plain substrings are valid regexes,
  // so one code path covers both "contains" and regex matching
  responses: StubResponse[];
  mode?: ResponseMode;
}

interface StubLlmConfig {
  apiFormat?: 'openai'; // which wire format to speak — default/only value 'openai' for now
  key?: string; // if set, required as `Authorization: Bearer <key>`
  minDelay?: number; // ms, per "generated" word — default 0 (instant)
  maxDelay?: number;
  prompts?: PromptRule[];
  defaults?: { responses: StubResponse[]; mode?: ResponseMode };
}
```

Loaded from a JSON file at startup (`--config <path>` / `STUB_LLM_CONFIG_FILE` env var — comments in the example are JSONC, so parse leniently or document plain JSON as the actual input format) and replaceable at runtime via `PUT /stub/config`, which also resets per-rule state (see below). `GET /stub/config` returns the active config with `key` masked, following the existing masked-secret convention used for `LlmConfig.apiKey` elsewhere in this repo.

### API format abstraction (`formats/`)

Everything above `matcher.ts` — the `StubResponse`/`StubTool` shape, the mode logic, the delay simulation, the auth check — is wire-format-agnostic: it just decides _which_ response to send. Only request parsing (pull the prompt text and stream flag out of an inbound request) and response serialisation (build the reply body/SSE chunks/error in the calling convention a given client expects) are format-specific. That boundary is captured as one small interface:

```ts
interface ApiFormat {
  name: string; // 'openai', future: 'anthropic', 'ollama', ...
  routes(): { method: string; path: string }[]; // e.g. POST /v1/chat/completions, POST /v1/embeddings
  parsePrompt(req): { promptText: string; wantsStream: boolean };
  buildResponse(res: StubResponse): unknown; // non-streaming body
  buildStreamChunks(res: StubResponse): unknown[]; // SSE/NDJSON chunk sequence
  buildError(kind: 'auth' | 'no-match' | 'exhausted'): {
    status: number;
    body: unknown;
  };
}
```

`server.ts` mounts whichever adapter `config.apiFormat` selects (default, and only implemented today, `'openai'` — `formats/openai.ts`, covering `/v1/chat/completions` incl. streaming and `/v1/embeddings`). Adding a future format is then "write one `formats/<name>.ts` implementing this interface, register it" — no changes to matching, modes, delay, or auth. Known other LLM API shapes worth targeting later, for reference: **Anthropic Messages API** (`/v1/messages`, `content` blocks + `tool_use` blocks), **Ollama** (`/api/chat`, NDJSON streaming), **Google Gemini** (`generateContent`/`streamGenerateContent`, `parts`/`functionCall`). None are implemented now — this is scope for a future prompt, not this one.

### Matching and response selection (`matcher.ts`)

- Prompt text = the concatenated `content` of all `messages[]` in the request body (matches how `chat-llm.integration-spec.ts` already asserts against `lastChatRequest()`). This parsing is the OpenAI adapter's job (`formats/openai.ts`'s `parsePrompt`) — `matcher.ts` itself only ever sees the extracted `promptText` string, keeping it reusable across future formats.
- Rules are tested in array order; first `match` regex that tests true wins. No match → fall back to `defaults`. No `defaults` either → the adapter's `buildError('no-match')` (for `openai`: 400, `{error:{message,type:'invalid_request_error'}}`) — this is our own convention since real OpenAI has no equivalent case.
- Per-rule cursor state (for `loop`/`sequence`) is kept in memory, keyed by the rule's index in the config array (`defaults` gets its own cursor). Reset whenever `PUT /stub/config` loads a new config.
- `sequence` (default): advances the cursor each call; once exhausted, returns the adapter's `buildError('exhausted')` rather than repeating — the prompt is explicit that this is the difference from `loop`.
- `loop`: advances the cursor, wraps to 0 when exhausted.
- `random`: picks uniformly at random each call, no cursor.

### Auth

If `config.key` is set, every request to a format's routes must carry the credential that format's real API expects (for `openai`: `Authorization: Bearer <key>`); a missing/mismatched key returns the adapter's `buildError('auth')` — for `openai`, 401 with an OpenAI-shaped body (`{error:{message:'Incorrect API key provided...',type:'invalid_request_error',code:'invalid_api_key'}}`). If `key` is unset, no check is performed. This check lives in `server.ts` (format-agnostic: "does this request carry a valid credential"), only the error body shape is delegated to the adapter.

### Endpoints (`server.ts`)

Format-specific routes come from the active adapter (`formats/openai.ts` today):

- `POST /v1/chat/completions` — non-streaming and `stream: true` (SSE). Streaming reuses the same match/mode-selected response (content + `tool_calls`) rather than a placeholder — `chat-llm.integration-spec.ts` and the agent loop rely on `streamEvents`-driven streaming today (see memory: "streamEvents forces model streaming"), so the stream must carry the real configured content to stay useful. We only skip simulating fine-grained reasoning/thinking-token deltas, since nothing in this repo consumes them — noted as a `ponytail:`-style scope note in the code, not a re-litigated design question.
- `POST /v1/embeddings` — same deterministic hash-based embedding as today's `server.js` (`EMBEDDING_DIM = 1536`), copied standalone into `embeddings.ts` (no shared import) so `knowledge-reindex.integration-spec.ts` / `rag-retrieval-isolation.integration-spec.ts` keep working unchanged. Not part of the `ApiFormat` interface (no other target API shares OpenAI's embeddings contract) — `server.ts` mounts it directly alongside the active adapter's routes.

Format-agnostic, always present regardless of `apiFormat`:

- `GET /health`
- `GET /stub/last-request` — unchanged from today, still useful for prompt assertions.
- `GET /stub/config` / `PUT /stub/config` — read/replace the live config (key masked on read).

### Tool-call shape

A `StubResponse.tools` entry `{tool, data}` becomes, on the OpenAI response:

```jsonc
choices[0].message.tool_calls: [{
  id: "call_<random>",
  type: "function",
  function: { name: tool, arguments: JSON.stringify(data) }
}]
```

matching what `libs/lcp-shared/src/llm/build-agent-graph.ts`'s `bindTools`/`ToolNode` expects (confirmed by reading that file and `stream-event-mapper.ts`). Real tool names are `{mcpServerName}__{toolName}`, e.g. `lcp-mcp-tasks__complete_assignment` (see `apps/lcp-mcp-tasks/src/tools.jsonc`), so example/test configs should use that naming.

### Per-token delay

`minDelay`/`maxDelay` are read as ms-per-word: split the chosen response text on whitespace, draw one random delay per word from `[minDelay, maxDelay]`, sum them for the non-streaming path (sleep once before responding) and apply them between successive SSE chunks for the streaming path. `0`/unset on both means no delay.

### Wrapper script

`scripts/run-stub-llm.sh` at the repo root (alongside the other `scripts/*.sh`) — thin, forwards `--config`/`PORT`, runs `apps/lcp-stub-llm` via its own `npm start` (or `ts-node`), for manual testing convenience. Lives in the main repo (not inside the exportable app) since it's about this repo's workflow.

### Tests for `lcp-stub-llm` itself

- Unit: `matcher.ts` mode behaviour (loop wraps, sequence exhausts, random distribution sanity), `config.ts` validation, `embeddings.ts` determinism, auth pass/fail.
- E2E (self-contained, no testcontainers needed — it's just an HTTP server): boot `server.ts` on an ephemeral port in-process, drive real HTTP requests — chat completions (matched/default/no-match/exhausted), streaming SSE parsing, tool-call shape, `/stub/config` round-trip, auth 401.
- Own `check.sh --project apps/lcp-stub-llm` must pass (format/lint/typecheck/build/test) — note in the root pre-push hook or CI docs that this second project root now needs checking too (flag as a follow-up if not already wired into `dev-environment/scripts/check.sh`'s multi-project handling).

## Repo integration

1. **Delete** `docker/stub-llm/` (server.js + Dockerfile) once the new app is in place.
2. **`docker-compose.yml`**: `stub-llm` service's `build.context` → `./apps/lcp-stub-llm`; keep the same service name, port 3002, and `/health` healthcheck so `test/support/testcontainers-env.ts` (`SERVICE_PORTS['stub-llm']`) needs no change. Decide whether to bake a default config into the image or mount one — simplest: no config file needed for the container's default boot, since every consuming test drives behaviour through `PUT /stub/config` at test start (as `chat-llm.integration-spec.ts` already does via `POST /stub/config` today).
3. **`test/integration/lcp-server/chat-llm.integration-spec.ts`**: update `setStubResponse()` to `PUT` the new config shape, e.g. `{ defaults: { responses: [{ text: response, tools: [] }], mode: 'loop' } }` (loop mode keeps both existing tests — which each call `setStubResponse` once and expect the same text — working without needing sequence-exhaustion handling).
4. **New integration tests** exercising a full task/assignment flow driven by pre-scripted LLM responses and tool calls (the prompt's main ask): add `test/integration/lcp-agent/task-flow.integration-spec.ts` (or similar), following the existing pattern in `chat-llm.integration-spec.ts` — real Postgres + stub-llm containers, the real agent-loop provider wired up in-process via `Test.createTestingModule`, with `McpClientService.loadTools` mocked to return `DynamicStructuredTool` stubs whose `func` records the call and returns a canned result. This still exercises the real `bindTools`/`ToolNode` dispatch mechanics and the real state machine, while avoiding standing up live MCP-server containers wired to a network-reachable `lcp-server` (a materially bigger lift, since the e2e tier boots `AppModule` in-process rather than as a container the MCP servers' `LCP_SERVER_URL` could reach). Script at least:
   - a **success** case: sequence of stub responses that claim a task, submit a deliverable, and call `complete_assignment`, asserting the assignment/task reach their terminal "completed" status.
   - a **failure** case: a response sequence that leads to QA rejection/retry exhaustion or an unrecoverable error, asserting the terminal "failed" status and matching audit events.
     Flag to the user during implementation if a genuinely live-MCP-container e2e turns out to be wanted later — out of scope here.
5. **Docs**: write `docs/stub-llm.md` (config reference, endpoints, modes, auth, examples — reusing content from the app's own `README.md`), and add it to `docs/index.md`. Update `docs/testing.md`, `docs/scripts.md`, and `docs/development.md` wherever they currently mention the old stub-llm.
