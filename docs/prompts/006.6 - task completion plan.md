# Plan: 006.6 — Agent Loop Completion

## Context

The agent loop currently accepts any non-empty string as a `complete_task` finalAnswer with no structural validation. There is no check that referenced files actually exist in shared storage, no in-loop tracking of what changed, and no structured completion record beyond the raw output string. This work adds three things:

1. **File existence validation** — `complete_task` rejects completion if named output files are not in MinIO, returning a canned error with context so the agent can self-correct.
2. **In-loop file and action tracking** — the agent loop accumulates storage changes and an action log from LangGraph events during the run.
3. **Agent loop completion summary** — after a successful completion, one direct LLM call generates a short prose summary; the structured summary (`AgentLoopCompletionSummary`) is audit-logged as a new `agent_loop_completion` event.

---

## Phase 1 — In-loop file and action tracking

### 1a. In-memory tracker in `AgentLoopService`

**File:** `apps/lcp-agent/src/agent/agent-loop.service.ts`

Add a local `tracker` object inside `streamAndAudit()`:

```ts
const tracker = {
  actions: [] as string[],
  storage: {
    created: [] as string[],
    modified: [] as string[],
    deleted: [] as string[],
    moved: [] as { from: string; to: string }[],
  },
};
```

**Action log** — on every `on_tool_start` event, append a human-readable string:

| Tool                         | Template                                         |
| ---------------------------- | ------------------------------------------------ |
| `write_file`                 | `"Wrote file: {path}"`                           |
| `delete_file`                | `"Deleted file: {path}"`                         |
| `move_file`                  | `"Moved file: {from} → {to}"`                    |
| `copy_file`                  | `"Copied file: {source} → {destination}"`        |
| `restore_file`               | `"Restored file: {path}"`                        |
| `read_file`                  | `"Read file: {path}"`                            |
| `recall` / `remember`        | `"Recalled memory: {query}"` / `"Stored memory"` |
| `request_user_input`         | `"Requested user input: {question}"`             |
| `request_agent_consultation` | `"Consulted role '{roleName}': {question}"`      |
| `complete_task`              | `"Submitted task completion"`                    |
| _(other)_                    | `"Called tool: {toolName}"`                      |

The args are available in `event.data.input` at `on_tool_start`.

`// ponytail: actions include failed tool calls; on_tool_start used for simplicity`

**Storage changes** — on `on_tool_end` events for storage mutation tools, parse the result text to confirm success (result starts with `"Written:"`, `"Deleted:"`, `"Restored:"`, `"Copied:"`, `"Moved:"`) and accumulate:

- `write_file` success: `overwrite === true` → `modified`, else → `created`
- `delete_file` success → `deleted`
- `move_file` success → `moved` (push `{ from, to }`)
- `copy_file` success → `created` (destination path)
- `restore_file` success → `created`

Track the `on_tool_start` input args keyed by `event.run_id` so they're available at `on_tool_end`.

### 1b. Persist storage changes to lcp-server

**Why**: the interactions MCP needs to include tracked files in the completion-failure error message; cross-service, so in-memory is not enough.

**New endpoint on lcp-server internal controller** (`apps/lcp-server/src/api/internal.controller.ts`):

```
PATCH /internal/agent/:agentId/storage
Body: { created?: string[], modified?: string[], deleted?: string[], moved?: { from: string, to: string }[] }
```

Merges (appends, no dedup) into `LcpAgent.storageChanges` JSONB column.

**New column on `LcpAgent`** (`libs/lcp-shared/src/models/LcpAgent.model.ts`):

```ts
@Column({ type: 'simple-json', nullable: true })
storageChanges?: {
  created: string[];
  modified: string[];
  deleted: string[];
  moved: { from: string; to: string }[];
} | null;
```

Use `simple-json` (not explicit `jsonb`) for cross-DB compatibility (SQLite for unit tests, PostgreSQL for prod).

Generate a TypeORM migration for this column.

**Fire-and-forget from agent loop**: after each storage `on_tool_end` update to the tracker, post `PATCH /internal/agent/{agentId}/storage` via a new `StorageTrackingClientService` in lcp-agent (same pattern as `AuditClientService` — fire-and-forget, never throws).

The tracker state is also kept in-memory for the end-of-loop summary step (Phase 3).

## Phase 2 — File existence validation in `complete_task`

### 2a. File existence HTTP endpoint on lcp-mcp-storage

**File:** `apps/lcp-mcp-storage/src/` (new controller or new endpoint on health controller)

Add a new endpoint:

```
GET /files/exists?path=a&path=b&path=c
Response: { missing: string[] }
```

Uses the existing `StorageToolsService.objectExists()` (HeadObject) helper, already implemented. Accepts multiple `path` query params. Returns an array of paths that were not found. Protected by `X-Internal-Api-Key` (same pattern as lcp-server internal endpoints).

New `StorageCheckController` + module update, or inline on existing `McpController` — whichever is smaller.

### 2b. Enhance `complete_task` tool schema

**File:** `apps/lcp-mcp-interactions/src/mcp/interactions-tools.service.ts`

Add optional `outputFiles` to the Zod schema:

```ts
outputFiles: z
  .array(z.string().min(1))
  .optional()
  .describe(
    'Paths in shared storage that this task produced or references as output. ' +
    'Each path will be verified to exist before the task is marked complete.',
  ),
```

Update the tool description to mention that `outputFiles` are validated.

### 2c. Validation logic in the handler

New env var on lcp-mcp-interactions: `LCP_STORAGE_URL` (same pattern as `LCP_SERVER_URL`).

In the `complete_task` handler, before posting to lcp-server:

1. If `outputFiles` is non-empty: `GET ${LCP_STORAGE_URL}/files/exists?path=...` for each path.
2. If any are missing:
   - `GET /internal/agent/{agentId}` on lcp-server to retrieve `storageChanges`.
   - Return a canned error (do **not** call the complete endpoint):

```
Some output files could not be found in shared storage.

Missing files:
- {missing.join('\n- ')}

Files you created or modified during this task:
- created: {storageChanges.created.join(', ') || '(none)'}
- modified: {storageChanges.modified.join(', ') || '(none)'}

If you intended to reference one of those files, please correct the path and call
complete_task again. If the output is incomplete, continue working and submit
a new complete_task when ready. If the task does not produce file output,
omit the outputFiles parameter.
```

3. If all present (or `outputFiles` omitted): proceed with completion as now.

The interaction prompts file (`interactions-prompts.jsonc`) gets the new template key.

## Phase 3 — Post-completion summary generation

### 3a. New audit event type

**File:** `libs/lcp-shared/src/models/AuditEvent.model.ts`

```ts
AgentLoopCompletion: 'agent_loop_completion',
```

### 3b. `AgentLoopCompletionSummary` type

Add in `libs/lcp-shared/src/models/AuditEvent.model.ts`:

```ts
export interface AgentLoopCompletionSummary {
  summary: string;
  actions: string[];
  storage: {
    created: string[];
    modified: string[];
    deleted: string[];
    moved: { from: string; to: string }[];
  };
}
```

### 3c. Summary generation in the agent loop

**File:** `apps/lcp-agent/src/agent/agent-loop.service.ts`

In `runLoop()`, after detecting `AgentStatus.Completed` set by a tool call, call a new private method `generateAndRecordCompletionSummary(agent, role, model, tracker)`:

```ts
private async generateAndRecordCompletionSummary(
  agent: LcpAgent,
  role: LcpRole,
  model: ReturnType<typeof buildChatModel>,
  tracker: AgentLoopTracker,
): Promise<void>
```

This method:

1. Builds the summary prompt (see below).
2. Calls `model.invoke([new HumanMessage(prompt)])` directly (no graph, no tools).
3. Strips markdown code fences from the response, then parses JSON for `summary`.
4. Assembles `AgentLoopCompletionSummary`.
5. Records via `auditClient.record(companyId, role.name, agent.id, AuditEventType.AgentLoopCompletion, summary)`.

**Summary prompt:**

```
Your task is now complete.

Original task: {agent.initialPrompt}

Actions taken (in order):
{actions.map((a, i) => `${i + 1}. ${a}`).join('\n') || '(none recorded)'}

Storage changes:
- Created: {storage.created.join(', ') || '(none)'}
- Modified: {storage.modified.join(', ') || '(none)'}
- Deleted: {storage.deleted.join(', ') || '(none)'}
- Moved: {storage.moved.map(m => `${m.from} → ${m.to}`).join(', ') || '(none)'}

Respond with ONLY a JSON object — no markdown, no extra text:
{"summary": "One or two sentences describing what was accomplished at a high level."}

The summary should be concise and factual, suitable for an audit log.
```

Summary generation errors are caught, logged, and swallowed — the task is already Completed; a missing summary must not cause a failure.

## Tests

**Unit (per phase)**

- Tracker accumulation logic: given mock LangGraph event sequences, assert correct `created`/`modified`/`deleted`/`moved`/`actions` arrays (26 tests in `loop-tracker.spec.ts`).
- `complete_task` handler: mock storage check returning missing files → assert error text; all present → assert completion posted; fail-open when storage unreachable; skip check when `outputFiles` omitted (4 tests in `interactions-tools.service.spec.ts`).
- Summary generation: `AgentLoopCompletion` audit event written after Completed status detected; LLM errors swallowed without failing the run; markdown fences stripped from response (3 tests in `agent-loop.service.spec.ts`).

**Integration**

- `StorageTrackingClientService` posts to lcp-server and data persists in `LcpAgent.storageChanges`.
- `agent_loop_completion` audit event written to DB after agent loop completes.

**E2E / API**

- Full agent loop: `complete_task` with a missing `outputFiles` path → error message injected → agent resubmits with correct path → completes.
- Audit log contains `agent_loop_completion` event with `AgentLoopCompletionSummary` payload after completion.
