# Task orchestration 1/8: knowledge folders and knowledge API

Part 1 of the task-orchestration work (see `010.2.0 - task orchestration: overview.md`
for the map — you do not need to read it to implement this plan; everything
required is below).

> **Recommended implementing model: Sonnet.** The work is broad but
> well-specified and pattern-following (rename/generalise existing services,
> mirror existing CLI/API conventions).

## Goal

Restructure knowledge storage from name-based, role-only folders to slug-based
folders with a company-wide `shared/` scope, and replace the role-document REST
API and CLI verbs with scope-aware knowledge equivalents.

Target layout in shared storage (MinIO):

```
{company_slug}/
  knowledge/
    {role_slug}/     ← OKF Markdown docs for a role (was {role_name})
    shared/          ← OKF Markdown docs for the whole company (new)
```

No embedding-sync changes in this plan (that is the next piece of work) —
the existing synchronous ingest/remove calls are simply extended to cover the
shared scope.

## Current state (verified)

- `apps/lcp-server/src/storage/storage-keys.ts` — `knowledgeKey(companySlug, roleName, filename)` builds `{companySlug}/knowledge/{roleName}/{filename}`.
- `apps/lcp-server/src/storage/storage.service.ts` — abstract `StorageService` with `listKnowledgeFiles` / `putKnowledgeFile` / `deleteKnowledgeFile` (role-name-based), implemented by `MinioStorageAdapter`.
- `apps/lcp-server/src/api/role-document.service.ts` + `role-document.controller.ts` — REST CRUD under `/api/role/:roleId/documents`, keeps RAG chunks in sync via `RagIndexService` (`apps/lcp-server/src/rag/rag-index.service.ts`).
- `libs/lcp-shared/src/models/KnowledgeChunk.model.ts` — `roleId` is **non-nullable**; indexes `(companyId, roleId)` and `(roleId, documentPath)`. There is no way to represent company-shared knowledge today.
- `LcpRole.slug` exists (unique within a company) — see `libs/lcp-shared/src/models/LcpRole.model.ts`.
- CLI verbs `store-role-documents`, `list-role-documents`, `remove-role-documents` in `apps/lcp-cli/src/commands/` (+ actions in `apps/lcp-cli/src/lib/docs/`) call the role-document endpoints.
- `upload-shared-document` / `download-shared-document` / `validate-shared-document` are unrelated to this plan and must NOT be removed or changed.

## Implementation

Work in the order below. Follow existing file/naming/test patterns in each area.

### 1. Reserve the `shared` role slug

Roles must never claim the slug `shared` (it is the company-knowledge folder).
Find every place a role is created or its slug set/updated (grep `slug` across
`apps/lcp-server/src/api/` and `apps/lcp-server/src/db/`), and reject `shared`
with a 400 (`BadRequestException`) at the API layer. Unit-test both create and
update paths.

### 2. Storage keys and StorageService

In `storage-keys.ts`:

- Change `knowledgeKey(companySlug, roleSlug, filename)` to be slug-based
  (parameter rename + JSDoc; the shape is unchanged).
- Add `sharedKnowledgeKey(companySlug, filename)` → `{companySlug}/knowledge/shared/{filename}`.
- Add prefix helpers used for listing: `knowledgePrefix(companySlug, roleSlug)` and
  `sharedKnowledgePrefix(companySlug)`.

In `StorageService` (and `MinioStorageAdapter` + its tests): generalise the
knowledge-file methods to take a **scope** instead of a role name, e.g.
`type KnowledgeScope = { companySlug: string; roleSlug: string | null }` (null =
shared). Update all call sites (grep `listKnowledgeFiles|putKnowledgeFile|deleteKnowledgeFile`
across `apps/` AND `test/`).

### 3. KnowledgeChunk migration (destructive)

- Model: make `roleId` nullable (`null` = company-shared knowledge). Keep the
  column definition style consistent with the existing model (note the project
  rule: entity `Date`/column types must stay cross-DB compatible — mirror how
  the file already declares columns).
- New migration in `apps/lcp-server/src/migrations/` that:
  - `TRUNCATE knowledge_chunk` (existing chunks reference name-based paths and
    are invalidated by this restructure — destruction is explicitly authorised),
  - alters `roleId` to nullable,
  - keeps/recreates indexes so both lookups stay indexed: `(companyId, roleId)`
    and `(roleId, documentPath)`; add `(companyId, documentPath)` for
    shared-scope document lookups.
- **Register the migration by hand** in the migrations array in
  `apps/lcp-server/src/app.module.ts` (and any other `apps/*/src/app.module.ts`
  that lists migrations — grep for an existing migration class name to find
  them all). The data-source glob will NOT catch a missing registration.
- Do not trust `npm run migration:generate` drift output — it reports phantom
  drift (uuid↔varchar, timezone, pgvector). Write the migration by hand.
- Document (in `docs/shared-storage.md`) that existing knowledge files must be
  re-uploaded after this migration.

### 4. RagIndexService: shared scope

Extend `RagIndexService.ingestDocument` / `removeDocument`
(`apps/lcp-server/src/rag/rag-index.service.ts`) to accept `roleId: UUID | null`
(null = shared chunk rows). Update its spec.

### 5. KnowledgeService + controller (replaces RoleDocumentService)

Rename/generalise `RoleDocumentService` → `KnowledgeService`
(`apps/lcp-server/src/api/knowledge.service.ts`), handling both scopes:

- `list(scope)` — list files for a role or the company-shared folder.
- `get(scope, filename)` — return file content (404 if missing).
- `store(scope, filename, content, originators)` — validate + write via
  `StorageService`, then (re)index via `RagIndexService` (roleId null for
  shared). Same overwrite semantics as today.
- `delete(scope, filename)` — soft-delete the file + remove its chunks.
  Idempotent (unknown filename is not an error → still 204).

Scope resolution: role scope resolves roleId→(role, company) exactly as
`RoleDocumentService.resolveRoleAndCompany` does today; company scope resolves
companyId→company (404 if unknown).

New controller `knowledge.controller.ts` replacing `role-document.controller.ts`
(JWT-guarded, Swagger-decorated like the rest of `apps/lcp-server/src/api/`):

| Method & path                                        | Purpose                                                             | Success                 | Failures                               |
| ---------------------------------------------------- | ------------------------------------------------------------------- | ----------------------- | -------------------------------------- |
| `GET /api/role/:roleId/knowledge`                    | list role knowledge                                                 | 200 `DocumentSummary[]` | 404 unknown role                       |
| `GET /api/role/:roleId/knowledge/:filename`          | get file content                                                    | 200 (text)              | 404 unknown role/file                  |
| `POST /api/role/:roleId/knowledge`                   | multipart upload (field `file`, optional `filename` override field) | 201 `DocumentSummary`   | 400 invalid document, 404 unknown role |
| `DELETE /api/role/:roleId/knowledge/:filename`       | delete file                                                         | 204                     | 404 unknown role                       |
| `GET /api/company/:companyId/knowledge`              | list shared knowledge                                               | 200                     | 404 unknown company                    |
| `GET /api/company/:companyId/knowledge/:filename`    | get file content                                                    | 200 (text)              | 404 unknown company/file               |
| `POST /api/company/:companyId/knowledge`             | multipart upload                                                    | 201                     | 400, 404                               |
| `DELETE /api/company/:companyId/knowledge/:filename` | delete file                                                         | 204                     | 404 unknown company                    |

Remove the old `/api/role/:roleId/documents` controller and service (they are
fully superseded). Grep `role-document|RoleDocument|documents` across `apps/`,
`test/integration/`, `test/e2e/`, and API test suites — update every consumer
and test.

### 6. CLI verbs

In `apps/lcp-cli/src/commands/` + `apps/lcp-cli/src/lib/` (follow the existing
command/action split and output conventions — JSON to stdout):

New verbs (per 010.1.1), each taking exactly one of `--role <slug-or-id>` /
`--company <slug-or-id>`:

- `list-knowledge (--role X | --company Y)`
- `get-knowledge (--role X | --company Y) --file <filename>` (prints content;
  optional `--out <path>` to save)
- `store-knowledge (--role X | --company Y) --source <path> [--target <filename>]`
- `delete-knowledge (--role X | --company Y) --file <filename>`

Resolution rules: a value matching the UUID format is treated as an id;
otherwise as a slug. A role slug needs a company to resolve against — use the
`--company` option or the CLI's saved company context (see how existing
commands use `set-company` state); error clearly if neither is available.
Company slugs are globally unique and resolve via the companies list endpoint.

Remove `store-role-documents`, `list-role-documents`, `remove-role-documents`
(commands, actions, registrations in `main.ts`, and their tests — grep the CLI
test suites too). Leave `upload-shared-document`, `download-shared-document`,
`validate-shared-document`, `open-document-store` untouched.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.
- Do not add dependencies unless truly needed (prefer stdlib/existing deps); if
  one is unavoidable, use the latest version and check its license/health.
  Do not update existing dependencies. No unrequested changes outside this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` (full suite) and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Git hooks run the quality gate; never use `--no-verify`.

Write unit/integration/e2e/API tests alongside each unit of code — main cases,
edge cases, and failure cases; verify HTTP response codes explicitly. Update
existing tests as code changes (grep `test/` directories by class name when
changing constructors or behaviour).

Standing instructions:

- If the work becomes exceedingly complex or a problem resists solution, HALT
  and inform the user (model switch or joint problem-solving may be needed).
- If you discover a beneficial alteration to this plan, HALT and inform the
  user before proceeding — do not silently change the design.
- Document any agreed deviations by appending dated notes to this file.
