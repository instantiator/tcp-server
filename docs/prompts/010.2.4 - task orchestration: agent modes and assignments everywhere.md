# Task orchestration 4/8: agent modes and assignments everywhere

Part 4 of the task-orchestration work (map: `010.2.0 - task orchestration: overview.md`;
parts 1–3 are in place — in particular `LcpAssignment` exists, with `mode`
(`plan | implement | qa`), nullable `taskId` (null = orphan), and artifact
arrays).

> **Recommended implementing model: Opus.** This part touches the core agent
> loop and every agent-creation path, with a destructive migration and a
> behaviour-preservation requirement across chat/consultation flows.

## Goal

Every `LcpAgent` is created with an assignment, always. Plain conversations,
API-started agents, and consultations get an automatically created **orphan**
implement-mode assignment. The agent's mode is its assignment's mode (there is
no mode column on `LcpAgent`). Prompt assembly gains a mode-specific part, and
the N-part prompt construction is broken out into clean, testable business
logic.

This part changes plumbing and prompts only — the `plan`/`qa` modes exist but
nothing dispatches them until parts 5/7. Behaviour of existing flows
(chat, consultation, `/api/agent/start`) must be preserved exactly, except for
the added prompt part.

## Implementation

### 1. `LcpAgent.assignmentId` (destructive migration)

- Add `assignment` / `assignmentId` (uuid FK → LcpAssignment, **non-nullable**,
  ON DELETE CASCADE) to `libs/lcp-shared/src/models/LcpAgent.model.ts`.
- Keep `initialPrompt` and `requiredToolCalls` on the agent (010.1.2 allows
  copy-or-derive; we copy) — they are _populated from_ the assignment at
  creation time.
- Migration `AddAgentAssignment`: **deletes all existing `lcp_agent` rows**
  (authorised — a non-nullable FK cannot be backfilled; note in the migration
  comment that this cascades to conversations/consultations referencing those
  agents), then adds the column non-nullable. Hand-written; registered by hand
  in every `apps/*/src/app.module.ts` that lists migrations.

### 2. Orphan assignment creation

`apps/lcp-server/src/db/db.service.ts` `createAgent` +
`apps/lcp-server/src/templates/LcpAgentTemplate.ts`:

- Extend `LcpAgentTemplate` with optional `assignmentId` and optional `mode`.
- In `createAgent`, when no `assignmentId` is supplied, create an orphan
  `LcpAssignment` first: `{ taskId: null, companyId, mode: template.mode ?? 'implement',
prompt: template.initialPrompt, roleId, status: 'in-progress', agentId: <set after> ,
materials: [], expected: [] }` — then the agent (copying `initialPrompt`,
  `requiredToolCalls`), then update `assignment.agentId`. Wrap in a transaction.
- Callers that must keep working unchanged (verify each, and grep
  `test/integration/` and `test/e2e/` for `createAgent`/`LcpAgentTemplate`):
  - `POST /api/agent/start` (`api.agent.controller.ts` → `AgentOrchestrationService.startAgent`)
  - `POST /api/agent/chat/start` (creates an idle agent with empty prompt — its
    orphan assignment simply has an empty prompt)
  - consultations (`apps/lcp-server/src/api/pause-and-resume.service.ts` —
    `orchestration.createAgent` at ~line 157)

### 3. Mode prompts in `@lcp/shared`

New `libs/lcp-shared/src/prompts/mode-prompts.ts` exporting
`MODE_PROMPTS: Record<'plan' | 'implement' | 'qa', string>` (+ export from the
lib index). Base them on 010.1.2's drafts, strengthened for LLM clarity — each
must name the tasks service, the required tool, and the describe_server
discovery step:

- `implement`: follow the assignment prompt; highlighted materials are listed
  but shared storage may be explored (read-only) for other relevant material;
  the assignment MUST be completed by performing the work and then calling the
  `complete_assignment` tool on the tasks service, providing the artifacts to
  list as complete, which must meet or exceed the assignment's expectations;
  call `describe_server` on the tasks service for details.
- `plan`: design a plan achieving the task prompt using the `create_plan` tool —
  a plan is an ordered list of assignments, each `{ prompt, role, expected outputs }`;
  each assignment automatically receives the outputs of all prior assignments
  plus any materials specified; consultation with other roles and user queries
  are available while planning; `create_plan` MUST be called before ending.
- `qa`: review the assignment prompt and the list of prepared artifacts; read
  each artifact (via the storage service) and verify it meets the assignment's
  needs; then submit assurance via `assure_assignment` — accept, or reject with
  actionable feedback.

Until part 5 exists these tools aren't live — that's fine; nothing dispatches
`plan`/`qa` agents yet, and the implement prompt must keep naming the
**current** completion tool (`complete_task`) in this part, switching to
`complete_assignment` in part 5. Put a `TODO(010.2.5)` comment beside it.

### 4. Prompt assembly refactor (lcp-agent)

`apps/lcp-agent/src/agent/agent-loop.service.ts` currently builds the whole
initial message list inline in `buildInitialState`. Extract prompt-part
construction into a new dedicated module, e.g.
`apps/lcp-agent/src/agent/prompt-assembly.ts`, with a pure, unit-testable
function per concern (system prompt rendering; services part; RAG part —
keep the existing helpers `buildServicesMessage`/`buildRagMessage` by moving
them; NEW assignment part). `buildInitialState` becomes a thin composition.

New prompt part — **assignment presentation** — replaces the bare
`new HumanMessage(initialPrompt)` (prompt part 4) with a message containing:

1. The mode prompt (`MODE_PROMPTS[assignment.mode]`).
2. The assignment prompt (for orphans this is exactly the old `initialPrompt`,
   so content is preserved; when the prompt is empty — chat-start — omit the
   prompt block, keep the mode prompt).
3. If the assignment has materials: a "Materials" list — each artifact's
   resolved storage key (via `resolveArtifactKey` from part 3) or the inline
   text.
4. If the assignment has expectations: an "Expected outputs" list (filenames /
   inline-text criteria).

Template strings live in `apps/lcp-agent/src/prompts.jsonc` alongside the
existing prompt strings (extend `agent-prompts.ts` typing accordingly).

The agent must load its assignment: extend the `agentRepo.findOne` relations in
`AgentLoopService.run` to include `assignment` (and `assignment.task`). The
resume path (`replyContent` set) is unchanged.

### 5. `requiredToolCalls` per mode

Central helper (in `@lcp/shared` next to the mode prompts):
`requiredToolForMode(mode)` → plan: `create_plan`, implement:
`complete_assignment`, qa: `assure_assignment`. **Transition note:** in this
part, implement mode must still return `complete_task` (the rename lands in
part 5 — leave a `TODO(010.2.5)` comment). Use it when creating agents
(`DbService.createAgent` default when the template doesn't specify) so the
existing default-`['complete_task']` behaviour in
`agent-loop.service.ts` `resolveRequiredTools` is preserved for implement mode
and correct for the new modes later.
