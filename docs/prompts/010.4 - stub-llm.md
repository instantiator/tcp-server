## Stub-LLM

Please develop an additional application that can be launched independently. It should simulate a standard LLM API, responding in a standard way with responses to prompts.

It should accept an input file _on launch_ specifying prompt and response list pairs, and a list of default responses, eg.

```jsonc
{
  "key": "some-api-key-goes-here",
  "minDelay": 2000,
  "maxDelay": 3000,
  "prompts": [
    {
      "match": "What is the capitol of", // any prompt containing this string or regex
      "responses": [
        {
          "text": "London",
          "tools": [
            {
              "tool": "some-tool-name",
              "data": {
                /* some object */
              },
            },
          ],
        },
        { "text": "Paris", "tools": [] },
      ], // could contain regex groups
      "mode": "loop", // could be 'loop' | 'random' | 'sequence' (default)
    },
  ],
  "defaults": {
    "responses": [
      {
        "text": "Hi there, I am a deterministic testing tool. I didn't recognise your prompt, so I've returned this.",
        "tools": [],
      },
      {
        "text": "I still didn't recognise your prompt, so I've returned this.",
        "tools": [],
      },
      {
        "text": "I guess we're finished",
        "tools": [
          {
            "tool": "the-assignment-completion-call",
            "data": {
              /* some object */
            },
          },
        ],
      },
    ],
    "mode": "sequence", // could be 'loop' | 'random' | 'sequence' (default)
  },
}
```

If the key is not provided in the config, it shouldn't be required. Otherwise, it's essential and the API should respond with an accurate simluation of authentication failure from the API it's simulating.

If the prompt doesn't match any of the matches, then the responses fall back to the defaults, and if the defaults don't match anything then the API responds with an error code.

Responses can contain text and tool calls - and in the case of a tool call, the service will make a call to an MCP tool. This may involve some additional configuration, passed in through parameters during startup of the app or in the configuration json, to provide service names and their endpoints to ensure they can be called.

In `loop` mode, responses are issued in sequence, and restart from the beginning after the responses are exhausted.

In `sequence` mode (the default - needn't be specified), responses are issued in sequence and the API will respond with an error code if the list is exhausted.

In `random` mode the response is selected at random from those available.

The response returned is delayed by a random number of ms between `minDelay` and `maxDelay` to simulate an LLM service's generation time.

## Testing

As with other applications in this suite, ensure that there are unit tests, and e2e tests, and API tests.

Separate these reasonably cleanly so that the application and its tests can be exported to a separate repository in future.

Add a thin wrapper script to launch the new application to make it easier to incorporate into manual testing.
