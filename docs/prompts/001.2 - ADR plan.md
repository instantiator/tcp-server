# Plan: LCP Design ADRs

## Context

LCP is growing beyond company management (the current lcp-server) to include multi-agent orchestration, LLM loops, memory, shared storage, and audit logging. Before writing code, we capture key architectural decisions as ADRs in `docs/ADRs/` so that future contributors (and future sessions) understand _why_ things are the way they are.

The output of this task is **12 ADR files** — not implementation code. Each ADR follows a lightweight format:

```
# ADR-NNN: Title
Status: Proposed
## Context
## Options (table where ≥2 options exist)
## Decision / Recommendation
## Consequences
## Open Questions / Assumptions
```

**Confirmed answers** (from design session):

- Agent runner = separate deployable microservice from lcp-server
- Agent framework = compare options; recommend LangGraph.js over DeepAgentsJS
- Agent identity = **ephemeral roles** (not persistent named employees); memory is role-scoped
- Audit log retention = configurable per company; indefinite by default
- Agent memory retention = indefinite by default; scrubbing required (by date, topic, task); future periodic consolidation job extracts key memories into role knowledge base
- Audit logging = dual-path: software records all LLM/tool activity automatically; agents can also MCP-log their _decisions with justification_
- MCP servers = memory and storage are MCP; each agent type and company has a configurable list of additional MCP servers
- Task planning = LLM-generated by a "planner role" agent (e.g., "product owner"); each company config specifies the planner role; initial task submitted via API with supporting materials (stored in company storage)
- User-agent conversations = bidirectional: agents can request conversations with users; users can initiate conversations with any role; teaching a role goes into memory or knowledge base
- Knowledge base format = Open Knowledge Format (OKF): https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md
- Auth = company has a user list with per-user permissions (create tasks, initiate conversations, access storage, define roles, etc.); standard auth service with access tokens

## ADRs to Write

### ADR-001: Service Architecture

**Decision question**: How are LCP's concerns split across deployable services?

**Options to compare**:
| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| Monolith | Agent loops run as background workers in lcp-server | Simple; one repo; shared DB | Hung agent blocks API; can't scale independently |
| Two services | `lcp-server` (API + orchestration) + `lcp-agent` (agent runner) | Independent scaling/restarts; clear boundary | Inter-service comms needed |
| Many microservices | Per-concern services | Max isolation | Premature for current scale |

**Recommendation**: Two services. lcp-server owns API, orchestration state, DB access, task queue dispatch. lcp-agent owns the LLM loop and reports back via queue/HTTP. Docker Compose wires them.

**Key content**:

- Responsibility table for each service
- lcp-agent must be runnable standalone (for testing agents in isolation)
- Company data structure includes: user list, per-user permissions, planner role config, MCP server list
- Communication channel between services (see ADR-010)

---

### ADR-002: Agent Loop Framework

**Decision question**: What framework powers the LLM agent loop in lcp-agent?

**Options to compare**:
| Option | Resumability | Parallel agents | TS support | Notes |
|--------|-------------|-----------------|-----------|-------|
| DeepAgentsJS | ✗ custom | ✗ custom | ✓ | Deep-research loop (plan→search→write); not a general orchestrator |
| LangGraph.js | ✓ built-in checkpoints | ✓ subgraphs | ✓ | State-machine agent loops; interrupt/resume; LangChain ecosystem |
| Anthropic SDK directly | ✗ custom | ✗ custom | ✓ | Maximum control; minimal magic; ~20-line agent loop; most work for resumability |

**Recommendation**: LangGraph.js. Built-in checkpoint stores cover resumability (ADR-005); parallel subgraph execution covers parallel agents; interrupt/resume covers user-in-the-loop (ADR-011). DeepAgentsJS is research-loop oriented and would need significant custom work for these requirements.

**Key content**: DeepAgentsJS concern stated explicitly; LangGraph state-machine model explained; `checkpointer` maps to spec's "state captured in DB so agent can be resumed/cancelled" requirement.

### ADR-003: LLM Provider Abstraction

**Decision question**: How does lcp-agent support pluggable LLM providers (Anthropic API, OpenAI, LM Studio, etc.)?

**Options**:
| Option | Notes |
|--------|-------|
| LangGraph/LangChain model interface | Built-in if using LangGraph — `ChatAnthropic`, `ChatOpenAI`, etc. LM Studio works via its OpenAI-compatible endpoint with a custom `baseURL` |
| Vercel AI SDK | Provider-agnostic, TS-first; avoids LangChain lock-in if framework changes |
| Custom thin wrapper | Full control; more code |

**Recommendation**: LangChain model interface (zero extra work when using LangGraph). LM Studio: configured as `ChatOpenAI` with custom `baseURL` pointing to the local network machine. Per-agent LLM config (model, provider, base URL, API key) stored in DB, loaded at agent start.

### ADR-004: Database Strategy

**Decision question**: What database backs the system in production? (Currently: in-memory SQLite — dev only.)

**Options**:
| Option | Pros | Cons |
|--------|------|------|
| SQLite file-based | No extra service; simple backup | Not multi-writer; no vector search |
| PostgreSQL + pgvector | Production-grade; covers relational + vector in one service | Extra Docker service |

**Recommendation**: PostgreSQL + pgvector. Covers: company/agent/task state (relational), role memories and RAG (vector), LangGraph checkpoint store (key-value), audit events. `better-sqlite3` stays for unit tests.

**Key content**: Migration path from current `app.module.ts` TypeORM config; env-var config for connection string; note that `better-sqlite3` stays in `devDependencies` for fast in-process Jest tests.

---

### ADR-005: Agent State Persistence and Resumability

**Decision question**: What agent state is persisted, when, and how is resume/cancel implemented?

**Content to capture**:

- State: conversation history, tool results, current task step, role config, MCP server list
- Checkpointing: after each LLM response via LangGraph PostgreSQL `checkpointer`
- Cancellation: `status` column on task step record; agent loop polls before each iteration; LangGraph interrupt on flag
- Resume: re-hydrate from last checkpoint; orchestrator re-queues the task step
- Stuck-loop detection: per-step timeout + max-iterations guard; timeout threshold configurable

**Recommendation**: LangGraph PostgreSQL checkpoint store. The spec's "cancelled with a database change" maps directly to a status column + LangGraph interrupt.

### ADR-006: Agent Memory Architecture

**Decision question**: How do agents store and retrieve memories (working context, episodic memory) and specialist knowledge (role-scoped RAG)?

**Two distinct systems** (both role-scoped, not agent-instance-scoped — agents are ephemeral):

1. **Episodic memory**: what this role has done, conclusions, lessons — grows over time; scrubable
2. **Knowledge base**: specialist domain documents ("how to be a software architect") — OKF format; pre-seeded and taught via user conversations; occasional consolidation from episodic memory

**Options**:
| Option | Episodic | Knowledge | Notes |
|--------|----------|-----------|-------|
| pgvector (custom) | ✓ | ✓ | No extra service; integrates with ADR-004 DB |
| LanceDB | ✓ | ✓ | Embedded, TS-native; extra dep but no separate service |
| Qdrant | ✓ | ✓ | Dedicated vector DB; extra Docker service |

**Recommendation**: pgvector. Already in ADR-004 DB. Custom thin RAG wrapper. Knowledge base seeded from OKF-formatted documents.

**Key content**:

- Memory access via dedicated MCP server (keeps agent loop clean; makes memory swappable)
- Knowledge base format: Open Knowledge Format (OKF) — https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md
- Embedding model: Anthropic embeddings or local model via LM Studio (configurable)
- Memory retention: indefinite by default; scrubbing API (by date, topic, task id)
- Memory consolidation: future periodic job extracts key episodic memories into role KB; note as a planned extension in ADR
- User-to-agent teaching: when a user teaches a role during a conversation, the content is written directly to episodic memory and/or KB (via MCP memory server)

### ADR-007: Shared Company Storage

**Decision question**: What backs the per-company shared file storage accessible to all agents and users of a company?

**Options**:
| Option | Versioning | Access control | Notes |
|--------|-----------|----------------|-------|
| Filesystem + MCP filesystem server | ✗ (unless git) | ✗ | Simplest; no per-company isolation |
| MinIO (S3-compatible, Docker) | ✓ (bucket versioning) | ✓ (bucket policies) | Per-company bucket; S3-compatible MCP; portable |
| PostgreSQL large objects | ✓ (via DB history) | ✓ | No extra service; not suited to large files |
| Cloud storage (S3, GCS) | ✓ | ✓ | Best for prod scale; not self-hostable |

**Recommendation**: MinIO in Docker Compose. Per-company S3 bucket = natural isolation. Versioning covers overwrite/delete safety. Accessible via S3-compatible MCP server. Audit log exports stored here as timestamped JSON Lines alongside agent-created files.

**Key content**:

- Supporting materials for tasks submitted via API are stored here (referenced by task record)
- Agent access: for now, agents have access to the full company bucket; orchestrator prompts agent to confirm intent before overwrite/delete of existing files (not a hard ACL — a soft check in the orchestration layer)
- Audit log exports: per-session JSON Lines files in a dedicated `audit/` prefix

### ADR-008: Audit Logging

**Decision question**: How is the full audit trail captured and stored?

**Dual-path model** (confirmed):

1. **Automatic**: software captures every LLM message, tool call, result, state change via LangGraph event stream hooks — no agent action required
2. **Agent-initiated**: agents can MCP-log their _decisions with justification_ (e.g., "chose architecture pattern X because Y") — richer semantic audit trail

**Storage options**:
| Option | Queryable | Human-readable | Notes |
|--------|-----------|----------------|-------|
| DB table only | ✓ | partial | Fast inserts; easy queries |
| Files in shared storage only | ✗ indexed | ✓ | Easy to inspect; no real-time query |
| Hybrid | ✓ | ✓ | Best of both |

**Recommendation**: Hybrid. Automatic events written to PostgreSQL `audit_events` table. Session export to MinIO as JSON Lines for archival.

**Key content**:

- Event schema: `(id, timestamp, company_id, role, task_id, step_id, event_type, payload)`
- Retention: configurable per company; indefinite by default
- Agent MCP audit server: exposes a `log_decision(justification, context)` tool; writes a `decision` event type to the same table
- Index strategy: `(company_id, task_id, timestamp)` covers the common access pattern

### ADR-009: Containerization Strategy

**Decision question**: What is the containerization boundary?

**Options**:
| Strategy | Isolation | Overhead | Complexity | Notes |
|----------|-----------|----------|------------|-------|
| Per-agent container | Highest | High (startup per run) | High (dynamic provisioning) | Overkill for dev; useful if agents need different runtimes |
| Per-company stack (Compose) | Company-level | Medium | Medium | Good isolation; complex to template dynamically |
| Single Compose stack, logical isolation | Low (DB + bucket scoping) | Low | Low | Good starting point |

**Recommendation**: Single Docker Compose stack with logical per-company isolation (company ID in all DB queries + per-company MinIO buckets). MCP servers spawned on-demand per task step by lcp-agent, not as permanent containers. Revisit per-company stacks when multi-tenancy or stronger isolation is needed.

**Key content**:

- Docker Compose service list: `lcp-server`, `lcp-agent`, `postgres` (pgvector), `minio`, `redis` (BullMQ queue — see ADR-010)
- MCP server lifecycle: spawned at task step start, torn down on completion; or optionally long-lived per company for high-use servers
- One of the key benefits: the whole system can run on any server via `docker compose up`

### ADR-010: Orchestration Design

**Decision question**: How does the orchestration service manage task plans, agent lifecycle, agent-to-agent communication, and user-agent conversations?

**Task lifecycle states**: `created → planning → in_progress → reviewing → completed | failed | cancelled`

**Task queue options**:
| Option | Notes |
|--------|-------|
| BullMQ + Redis | Retry logic, priority queues, job persistence; adds Redis service |
| PostgreSQL LISTEN/NOTIFY | No extra service; simpler; less feature-rich |
| In-process event emitter | Simplest; state lost on crash |

**Recommendation**: BullMQ + Redis. Retry and priority matter for orchestration; Redis is lightweight and Docker-native.

**Key content**:

- Task plan: ordered list of steps; each step has: role, required knowledge domains, MCP servers, input/output contract
- Planner role: each company config specifies a "planner agent role" (e.g., "product owner"); this role generates the task plan from the initial user prompt; supporting materials for the task are stored in company storage and referenced by the plan
- Supporting task materials: submitted via API, stored in MinIO, referenced in task record
- Orchestrator loop: watches `planning` tasks → dispatches to planner role → receives plan → assigns first step → monitors completion → advances plan
- Agent-to-agent consultation: agent emits `consult` event → orchestrator pauses step, spins up consultant role, feeds output back as context, resumes
- Plan revision: agent emits `revise_plan` event → orchestrator validates and patches plan
- User-agent conversations:
  - Agent-initiated: agent emits `request_user_input` event → orchestrator suspends step (LangGraph interrupt) and surfaces a conversation thread to the user via API
  - User-initiated: user calls API to open a conversation with a specific role → orchestrator spins up a short-lived agent loop for the conversation; content can be written to role memory/KB
  - User teaching: content written directly to role episodic memory and/or KB via MCP memory server during conversation
- Restore on startup: scan DB for incomplete tasks; resume from LangGraph checkpoint
- Sequence diagram to include: standard task flow (architect → developer → reviewer) from the spec

### ADR-011: Authentication and Authorization

**Decision question**: How are users authenticated and what controls their access to a company and its resources?

**Content to capture**:

- Company has a user list with per-user permission flags: `create_tasks`, `initiate_conversations`, `access_storage`, `modify_company`, `define_agent_roles`
- Auth mechanism options:
  | Option | Notes |
  |--------|-------|
  | JWT (self-issued) | Simple; no external service; standard NestJS Guards |
  | OAuth2 / OIDC (external IdP) | Delegates identity to an existing provider (Google, GitHub, etc.); more setup |
  | API keys | Simplest for machine-to-machine; less suitable for user-facing |
- Standard NestJS Guards + JWT is the natural fit for this stack
- Agents themselves are not auth subjects — they inherit the company context and are trusted internal processes; the orchestrator (not the agents) enforces the soft overwrite/delete check on company storage

**Recommendation**: JWT with NestJS Guards. Company membership and permissions stored in DB. Per-request auth middleware. Note that agent-to-agent and orchestrator-to-agent calls are internal (no auth between services — network-level trust within Docker Compose).

**Key content**: User entity and permission flags; JWT payload (user id, company id, permissions); company membership CRUD endpoints; note that full IdP integration is a future extension.

### ADR-012: Human-in-the-Loop and User-Agent Conversations

**Decision question**: How do users interact with running agents in real-time, and how do agents surface requests to users?

**Content to capture**:

- Three conversation modes:
  1. **Agent-initiated pause**: agent requests input during a task step → step suspends; user responds via API; step resumes with response in context
  2. **User-initiated conversation**: user opens a thread with a role (not tied to a task) → short-lived agent loop; teaches the role or gets direct output
  3. **User observation**: user can view any in-progress task's audit log in real-time (SSE or polling)
- Transport options:
  | Option | Notes |
  |--------|-------|
  | REST + polling | Simplest; latency-limited |
  | Server-Sent Events (SSE) | Good for one-way streaming (audit log observation, agent output); built into NestJS |
  | WebSockets | Full duplex; more complex; worthwhile for real-time conversation UX |
- Teaching flow: user message in a conversation → orchestrator identifies if content should go to episodic memory or KB → calls MCP memory server to write

**Recommendation**: SSE for streaming agent output and audit log observation (fits NestJS naturally). REST POST/GET for conversation turns (simple enough; no need for WebSocket initially). LangGraph `interrupt` is the mechanism for agent-initiated pause.

**Key content**: API endpoints for conversation management; how agent-initiated pauses surface to the API consumer; teaching flow through the MCP memory server; note WebSocket upgrade as a future extension when real-time conversation UX matters.

## Verification

ADRs are documentation — verification is a reading pass:

1. Each ADR answers its decision question clearly
2. Recommendations are consistent across ADRs (e.g., LangGraph in ADR-002 is coherent with checkpointing in ADR-005; pgvector in ADR-004 is coherent with memory in ADR-006)
3. Open questions are called out explicitly, not left implicit
4. No ADR contradicts existing codebase conventions or coding standards — unless a good case is made for it
5. ADRs reference each other where decisions are interdependent

- **Memory scrubbing**: all three granularities (date range, task id, topic) to be supported; document the interface in ADR-006 but mark implementation as deferred
