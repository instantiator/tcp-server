## Unit 2 — Code-level fixes (4 aislop findings, plus one build papercut)

2. **`apps/tcp-server/src/api/claim-status.ts:25`** — double type assertion
   (`as unknown as X`) bypasses type checking. This is an ORM query return.
   Introduce a typed wrapper or a proper result interface so the assertion is
   unnecessary. **Do not** swap it for a single `as` cast, and never for `any` —
   the standards forbid type escapes, especially here where the value flows into
   an optimistic-concurrency check.

3. **`libs/tcp-shared/src/context/context-compactor.service.ts:80`** — unresolved
   `TODO`. The standards require every `TODO`/`LATER` to state a **WHEN or under
   what CONDITION** it should be actioned. Either resolve it, or rewrite it to name
   the trigger condition. Do not simply delete a TODO that describes real
   outstanding work.

4. **`scripts/setup-wizard/utils/prompt-with-help.ts:175`** — parameter `answers`
   declared but never used. Prefix with `_` if the signature is required by the
   inquirer callback contract, otherwise remove the parameter.

5. **`npm run build` always leaves `docs/licenses.md` dirty** (not an aislop
   finding; noticed during 011.1.1). `licenses:generate` pipes `license-report`
   straight to the file, and its output ends `|\n\n` — a trailing blank line
   after the table. Prettier's markdown parser trims that to a single newline, so
   the generator and the formatter each "correct" the other forever:
   `npm run build` dirties the file, the next `npm run format` reverts it.

   It is invisible in normal use only because `scripts/hooks/pre-commit`
   regenerates, then formats, then stages — so what gets committed is always the
   prettier-trimmed version. The cost is that the working tree is never clean
   straight after a build, which trains everyone to ignore a dirty
   `docs/licenses.md`, including when it is dirty for a real reason.

   **Fix:** add `docs/licenses.md` to `.prettierignore`. It is a generated
   artefact that nothing hand-edits, so the generator's output should simply be
   authoritative — this is the smallest change and it removes the conflict rather
   than papering over it. Do **not** "fix" it by post-processing the generator's
   output in the npm script; that adds a step to every build to satisfy a
   formatter that has no business touching the file.

   `schemas/schema.json` does **not** have this problem — the `format` script's
   globs cover `.ts`, `.md` and `.jsonc` only, so no `.json` artefact is
   formatted. Leave it alone.

**Tests:** add or update unit tests covering the `claim-status.ts` change — it is
the only one with behavioural surface. Confirm the typed wrapper returns the same
shape for both the found and not-found paths.

For item 5 there is nothing to unit-test; verify by hand instead. From a clean
tree run `npm run build`, then `git status` — `docs/licenses.md` must be
unmodified. Then run `npm run format` and confirm it stays unmodified.
**Gate:** `./dev-environment/scripts/check.sh`.

## Unit 3 — Migration correctness (carried over from 011.1.1)

Both defects were found while squashing the migrations in 011.1.1 and verified
against a real pgvector container.

### 1. `DynamicEmbeddingDimension` never detects a matching dimension

`apps/tcp-server/src/migrations/1784800000000-DynamicEmbeddingDimension.ts`

`readActualDimension()` reads `atttypmod` from `pg_attribute` and returns
`atttypmod - 8`. pgvector stores the dimension in `atttypmod` **directly** — for
a `vector(768)` column, `atttypmod` is exactly `768`, not `776`. So the method
reports `760`, never equals the target, and `up()` unconditionally drops and
recreates the `embedding` column and its IVFFlat index on both
`knowledge_chunk` and `episodic_memory`.

The class docstring claims the opposite: _"this migration is idempotent:
re-running it after the dimension already matches is a no-op."_ That is the
behaviour to restore.

Harmless today, because a migration runs once per database and this one runs
immediately after the baseline, before any embeddings exist. It stops being
harmless the moment anything re-runs it against a populated database — it would
silently discard every embedding and require a full re-index.

**Fix:** drop the `- 8`. Do not "fix" it by widening the comparison or adding a
tolerance — the arithmetic is simply wrong.

**Tests:** extend
`test/integration/tcp-server/baseline-schema.integration-spec.ts`, which already
applies both migrations into a throwaway schema. After they have run, record the
`pg_class.oid` of `IDX_knowledge_chunk_embedding`, run
`DynamicEmbeddingDimension.up()` a second time with `EMBEDDING_DIMENSION`
unchanged, and assert the oid is identical — a recreated index gets a new oid, so
this proves a genuine no-op rather than merely proving the end state is right.
Add a companion assertion that a _changed_ `EMBEDDING_DIMENSION` still resizes
both columns, so the fix cannot turn the migration into a permanent no-op.

### 2. The app and the TypeORM CLI track migrations in different tables

`apps/tcp-server/src/data-source.ts` sets
`migrationsTableName: 'typeorm_migrations'`. `makeTypeOrmConfig(...)`
(`libs/tcp-shared/src/db/typeorm-config.factory.ts`), which is what `AppModule`
actually boots with, does not set it — so the running app uses TypeORM's default
`migrations` table. Confirmed on a freshly deployed stack: it had a `migrations`
table holding both rows, and no `typeorm_migrations` table at all.

Consequences, both silent:

- `npm run migration:run` against a database the **app** has already migrated
  sees an empty history and tries to apply everything from scratch. Since
  011.1.1 that means the baseline runs against tables that already exist and
  fails on the first `CREATE TABLE`.
- `npm run migration:revert` against the same database reverts nothing, because
  the CLI's history table is empty.

`docs/db-migrations.md` § "Running migrations manually" documents exactly these
two commands, so the documented recovery path does not work on a real
deployment.

**Fix:** make the two agree. Prefer **deleting the `migrationsTableName` line
from `data-source.ts`** so both use TypeORM's default `migrations` — it is the
smaller change, and it leaves the table the running app already writes to
untouched. Setting the name in `makeTypeOrmConfig` instead would rename the
table the app depends on, orphaning the history on any database that has already
been migrated.

**Tests:** no unit test can see this — it is configuration agreement between two
entry points. Verify by hand instead, and record it in your report: bring up a
stack, confirm the app populated `migrations`, then run
`DATABASE_URL=... npm run migration:run` and confirm it reports no pending
migrations rather than trying to re-apply the baseline. Re-read
`docs/db-migrations.md` § "Running migrations manually" afterwards and correct it
if the verified behaviour differs from what it describes.

**Gate:** `./dev-environment/scripts/check.sh` plus
`./scripts/run-integration-tests.sh`.

## Unit 5 — IANA timezone validation

`TcpCompany.timezone` is `@Column({ type: 'varchar', nullable: true })` with no
validation at all. `CreateCompanyDto.timezone`
(`apps/tcp-server/src/api/dto/company.dto.ts:51`) and `UpdateCompanyDto.timezone`
(`:94`) carry only `@IsOptional() @IsString()`, so any string is accepted.

Both runtime consumers already defend themselves — `prompt-vars.ts` wraps
`Intl.DateTimeFormat` in try/catch and falls back to the UTC anchor, and
`read-query.action.ts` formats CLI timestamps — so this is a **fail-fast-at-write
improvement**, not a bug fix. A bad value currently fails silently at render time,
which is exactly the sort of thing that is hard to notice.

**Implementation:**

1. Use the built-in **`Intl.supportedValuesOf('timeZone')`**. Add no dependency —
   the codebase already relies solely on `Intl` for timezone handling, and neither
   `luxon` nor `moment-timezone` is installed. Build the valid-name set **once at
   module scope**, not per validation call.
2. Create `apps/tcp-server/src/api/dto/is-valid-timezone.validator.ts`, following
   the existing custom-validator idiom in the sibling
   `apps/tcp-server/src/api/dto/is-not-uuid.validator.ts` (`registerDecorator` /
   `ValidationArguments`). Match its structure and comment style.
3. Apply `@IsIanaTimeZone()` to both DTO fields, keeping `@IsOptional()`.
4. Make the failure message name the offending value and point at the IANA format
   (e.g. `Europe/London`) — an agent or user correcting this needs to know the shape.
5. Add `"engines": { "node": ">=18" }` to the root `package.json`.
   `Intl.supportedValuesOf` needs Node 18+, and **no `package.json` in the repo
   currently has an `engines` field**, so nothing pins the minimum today.

**Tests** (new spec beside the validator):

- Valid: `Europe/London`, `America/New_York`, `UTC`.
- Invalid: `Not/AZone`, `GMT+1`, empty string, arbitrary text.
- Absent (`undefined`) passes, because the field is optional.
- Case sensitivity: confirm and lock in the behaviour you implement — IANA names
  are case-sensitive, and `europe/london` should be rejected unless you decide to
  normalise, in which case test the normalisation.
- Add an e2e assertion that `POST /api/company` rejects a bad timezone with 400.

**Gate:** `./dev-environment/scripts/check.sh` plus `./scripts/run-e2e-tests.sh`.

## Code quality requirements

Route via `AGENTS.md` → `dev-environment/guidance/index.md`; read
`process/before-coding.md` first and `process/after-coding.md` when done. State the
filename of each guidance doc you read.

- **After every unit**, run `./dev-environment/scripts/check.sh` and fix what it
  reports before starting the next. Never bypass a hook with `--no-verify`.
- Zero compiler and linter **errors and warnings** — formatting counts as a warning.
- Never cast to `any`, especially in test mocks — type the mock instead.
- Comments state **intent**, not mechanics; TSDoc on classes/functions/consts;
  `{@link}` for type references; no decorative separator comments.
- No unrequested abstractions; only change what this sub-plan asks for.
- Tests cover intent and edge cases, not line coverage.
- No secrets in the codebase.
- Full suite via `./scripts/run-all-tests.sh`; e2e via `./scripts/run-e2e-tests.sh`,
  never bare `npm run test:e2e`.
