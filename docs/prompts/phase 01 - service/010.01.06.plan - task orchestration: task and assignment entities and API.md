Part 3 of the task-orchestration work (map: `010.01.03.plan - task orchestration: overview.md`;
parts 1–2 — knowledge folders and embedding sync — are already in place).

> **Recommended implementing model: Sonnet.** The entities, state rules, and

## Goal

The data layer for tasks: `LcpTask` and `LcpAssignment` entities, artifact
types, storage-key helpers for the task directory tree, migrations, a task REST
API (create / upload materials / start / list / get) and CLI verbs
(`create-task`, `list-tasks`, `get-task`). **No orchestration behaviour yet** —
starting a task only marks it `planning` and calls a dispatch hook that is a
logged no-op until part 7 wires it.

## Domain model (agreed — implement exactly this)

A _task_ is a piece of work requested by a user. A planner agent will (part 7)
turn it into a _plan_: an ordered list of implement-mode _assignments_, each
given to an agent of a specific role. There is **no plan entity** — the plan is
the task's implement-mode assignments ordered by `orderIndex`. Assignments also
exist outside tasks ("orphan" assignments — plain conversations/consultations,
wired in part 4) and in `plan`/`qa` modes (the planner's own assignment and QA
review assignments, wired in parts 5/7).

### Artifact types (new file `libs/lcp-shared/src/models/LcpArtifact.ts`)

```ts
/** Where an artifact lives; path types are relative filenames resolved against the task tree. */
export type LcpArtifactType =
  | 'task-materials-path' // {companySlug}/tasks/{taskId}/materials/{value}
  | 'task-completed-path' // {companySlug}/tasks/{taskId}/completed/{value}
  | 'assignment-working-path' // {companySlug}/tasks/{taskId}/assignments/{orderIndex}/working/{value}
  //   (orphan assignments: {companySlug}/assignments/{assignmentId}/working/{value})
  | 'assignment-completed-path' // {companySlug}/tasks/{taskId}/assignments/{orderIndex}/completed/{value};
  //   orderIndex = the MOST RECENT prior assignment whose approved list contains value
  | 'inline-text'; // literal text. As an EXPECTATION: value '' = any text, otherwise a regex the text must match.

export interface LcpArtifact {
  type: LcpArtifactType;
  value: string;
}

export type LcpMaterialArtifact = LcpArtifact & {
  type: 'task-materials-path' | 'assignment-completed-path' | 'inline-text';
};
export type LcpAssignmentWorkingArtifact = LcpArtifact & {
  type: 'assignment-working-path' | 'inline-text';
};
export type LcpAssignmentCompletedArtifact = LcpArtifact & {
  type: 'assignment-completed-path' | 'inline-text';
};
export type LcpTaskCompletedArtifact = LcpArtifact & {
  type: 'task-completed-path' | 'inline-text';
};
```

### Task status derivation (pure function, unit-tested)

New `libs/lcp-shared/src/models/task-status.ts` (or similar):

```ts
deriveTaskStatus(current: LcpTaskStatus, planAssignments: Pick<LcpAssignment, 'status'>[]): LcpTaskStatus
```

`planAssignments` = the task's implement-mode assignments only. Rules, in order:

1. `cancelled` and terminal statuses stick: if `current` is `succeeded | failed | cancelled`, return it.
2. If any assignment is `failed` → `failed`; if any is `cancelled` → `cancelled`.
3. Else if any is `in-progress` or `in-qa` → `in-progress`.
4. Else if there is at least one assignment and all are `succeeded` → `succeeded`.
5. Else if `current === 'planning'` and there are no assignments yet → `planning`
   (the planner is still working).
6. Else → `ready`.

`planning` itself is set explicitly when the planner is dispatched (part 7);
this function never invents it.

### Storage-key helpers (extend `apps/lcp-server/src/storage/storage-keys.ts`)

```
taskMaterialsKey(companySlug, taskId, filename)            → {companySlug}/tasks/{taskId}/materials/{filename}
taskCompletedKey(companySlug, taskId, filename)            → {companySlug}/tasks/{taskId}/completed/{filename}
assignmentWorkingKey(companySlug, taskId, orderIndex, filename)   → .../assignments/{orderIndex}/working/{filename}
assignmentCompletedKey(companySlug, taskId, orderIndex, filename) → .../assignments/{orderIndex}/completed/{filename}
orphanWorkingKey(companySlug, assignmentId, filename)      → {companySlug}/assignments/{assignmentId}/working/{filename}
```

plus the matching `...Prefix` helpers for listing. Also add a resolver used by
later parts:

```ts
/** Resolves an artifact to a full storage key (null for inline-text). For
 * 'assignment-completed-path', scans the given plan assignments (highest
 * orderIndex < currentOrderIndex wins) for the most recent approved entry
 * matching the value. */
resolveArtifactKey(artifact, ctx: { companySlug; task?; planAssignments?; assignment }): string | null
```

Unit-test the most-recent-version rule explicitly: if `report.md` appears in
the approved lists of assignments 0 and 2, an assignment-3 material
`{ type: 'assignment-completed-path', value: 'report.md' }` resolves to
`.../assignments/2/completed/report.md`.

## REST API (`apps/lcp-server/src/api/task.controller.ts` + `task.service.ts`)

JWT-guarded, Swagger-decorated, DTOs in `apps/lcp-server/src/api/dto/` with
validation (follow the existing DTO patterns):

| Method & path                  | Purpose                                                                                                                                                                                                                                                                            | Success     | Failures                                                     |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------------ |
| `POST /api/task`               | create (body: `companyId`, `request`, optional `plannerRoleId`, optional `expected`, optional inline-text materials)                                                                                                                                                               | 201 task    | 400 invalid body, 404 unknown company/role                   |
| `POST /api/task/:id/materials` | multipart upload (field `file`) into `tasks/{id}/materials/` via `StorageService` (validated like other writes); appends a `task-materials-path` artifact to `task.materials`                                                                                                      | 201 summary | 400 invalid document, 404 unknown task, 409 task not `ready` |
| `POST /api/task/:id/start`     | validates a planner role is resolvable (task's or company's — 422 if neither); sets status `ready → planning` via an **atomic conditional UPDATE** (409 if not `ready`); calls `TaskDispatcher.dispatchPlanner(task)` — in this part a logged no-op injectable, replaced in part 7 | 202 task    | 404, 409, 422                                                |
| `GET /api/task?companyId=`     | list company tasks                                                                                                                                                                                                                                                                 | 200         | 400 missing companyId, 404 unknown company                   |
| `GET /api/task/:id`            | task with its assignments (ordered: plan assignments by orderIndex, then others by createdAt)                                                                                                                                                                                      | 200         | 404                                                          |

The atomic-update pattern to copy: the `pausedAt` claim in
`apps/lcp-server/src/api/agent-orchestration.service.ts` (`resumeAgent`).

## CLI verbs

Following the part-1 CLI conventions (`--company <slug-or-id>` resolution,
command/action split, JSON to stdout):

- `create-task --company <slug-or-id> --request <text> [--planner-role <slug-or-id>] [--materials <paths...>] [--expected <filenames...>] [--start]`
  — creates the task, uploads each materials file, optionally starts it.
- `list-tasks --company <slug-or-id>`
- `get-task --task-id <uuid>` — prints the task including assignment statuses
  and QA outcomes.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.
- Do not add dependencies unless truly needed; if unavoidable, latest version,
  license/health checked. Do not update existing dependencies. No unrequested
  changes outside this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Never `--no-verify`.

Write unit/integration/e2e/API tests alongside each unit of code — main, edge,
and failure cases; verify HTTP response codes explicitly. Update existing tests
as code changes (grep `test/` directories by class name when changing
constructors or behaviour).

## Implementation notes (2026-07-11)

- **Materials upload failure code**: implemented as `422 Unprocessable
Entity`, not the `400` listed above. `POST /api/task/:id/materials` writes
  via `StorageService.putByKey`, which validates content through the same
  `DocumentValidationException` (a `422`, not `400`) every other validated
  write in the codebase uses (`writeFile`, `putKnowledgeFile`) — see
  `docs/shared-storage.md#write-validation`. Kept consistent with that
  existing convention rather than introducing a one-off `400` for this
  endpoint.
- **API test location**: endpoint/failure-code tests live in
  `test/e2e/lcp-server/task.e2e-spec.ts` (supertest + `AppModule`, run via
  `./scripts/run-e2e-tests.sh`), not `test/api/`. `test/api/api.spec.ts` is a
  separate, manually-run system-test tier requiring a live Keycloak
  (`docker compose --profile auth up`); every other REST controller's
  endpoint/failure-code coverage (company, role, knowledge, conversation,
  storage-validation, …) already lives under `test/e2e/lcp-server/`, so this
  follows that established precedent instead of the plan's literal path.
