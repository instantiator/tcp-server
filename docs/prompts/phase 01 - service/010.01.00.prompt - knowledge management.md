# Knowledge management changes

Embeddings should be kept in sync with the contents of the knowledge folders.

First we ought to rearrange the folder structure a little to support the planned implementation of tasks.

## Folder structure

At the moment, the documentation describes the knowledge folders as:

```text
{company_slug}/
  knowledge/
    {role_name}/
```

Knowledge should be kept for each role, and for the whole company, and folders should be named by slug to make it easier for users and agents to locate information.

```text
{company_slug}/
  tasks/
    {task_id}/
      materials/         ← user-submitted inputs; read-only for agents
      completed/         ← documents that represent the final output of the task (a selection of docs promoted from completed assignments)
      assignments/
        {index}/         - index of the assignment in the task's assignment plan
          working/       ← private working area for agents working on assignments
          completed/     ← documents promoted from `working/` when the assignment completes and passes QA
  knowledge/
    {role_slug}/         ← OKF Markdown documents used for RAG indexing (knowledge for the role)
    shared/              ← OKF Markdown documents used for RAG indexing (shared knowledge for the whole company)
```

- The `tasks/` directory and sub-directories contain data created for and about the task, and assignments that are a part of the task plan.
- The `knowledge/` directory contains OKF docs used for RAG indexing

## Embedding sync

Whenever documents stored in a `knowledge/{role_slug}/` directory are changed (or the `knowledge/shared/` directory), the RAG chunks/embeddings should be rebuilt so that the folder and embeddings database stay in sync.

This should happen regardless of the source - eg. if a user uploads into a `knowledge/*/` folder, or if an agent alters files in the knowledge folder (a future potential feature), the embedding for that folder should be rebuilt.

This could be managed by:

- Monitoring these folders with a MinIO feature (if available) to trigger the process
- Polling the folders periodically for an indication that their contents have changed
- Adding a trigger to reindex whenever the storage service is invoked through lcp-server

## Embedding search rules

When a role attempts to retrieve knowledge from the RAG store (and when retrieving knowledge for the initial prompt), only the data for the agent's role and the shared embeddings should be searched.

## Storage management (users)

A user may upload information (in the form of OKF documents) into any `knowledge/*` folder. At the moment, the `lcp-cli` allows upload into any path at all, through the `store-role-documents` verb. At the moment, this command accepts an unconstrained path.

Instead, let's introduce several new verbs to replace this:

- `list-knowledge (--role {role_slug-or-id} | --company {company_slug-or-id})` - lists knowledge files for the given role or company
- `delete-knowledge (--role {role_slug-or-id} | --company {company_slug-or-id}) --file {filename}` - deletes a specific knowledge file if found for the role or company
- `get-knowledge (--role {role_slug-or-id} | --company {company_slug-or-id}) --file {filename}` - retrieves a knowledge file if found for the role or company
- `store-knowledge (--role {role_slug-or-id} | --company {company_slug-or-id}) --source {filename} [--target {filename}]` - creates or updates a specific file for the role or company

When the knowledge stored in the system changes, the knowledge stored in the vector database should be regenerated.

This may take a while. If other changes come in that would alter the embeddings currently being prepared, the process should be halted and restarted for the new state of the files.

All other file based operations that users may wish to do (eg. exploring anything else) should be done by signing in to minio.

## Storage management (agents)

Most file storage operations that agents wish to do must also be constrained to prevent mistakes.

The `lcp-mcp-storage` service currently offers several tools:

- `decribeServer`
- `describeFolder`
- `listFiles`
- `readFile`
- `writeFile`
- `deleteFile`
- `restoreFile`
- `searchFiles`
- `getFileProperties`
- `copyFile`
- `moveFile`
- `getFileSummary`

At the moment, these are all pretty permissive. They should be better constrained, ie. a different set of tools:

- `describeServer` (keep)

- `listWorkingFiles` - lists all files in the `working/` directory for the agent's current assignment
- `getWorkingFileProperties` - like `getFileProperties` but constrained to the `working/` directory
- `readWorkingFile` - reads a specific working file
- `appendWorkingFile` - appends data to a working file (creates it if it doesn't exist)
- `replaceInWorkingFile` - replaces a string in a working file with another
- `deleteWorkingFile` - deletes a specific working file (this is moved to a special 'deleted' directory rather than fully removed)
- `retoreWorkingFile` - retores a specific working file

- `listMaterialFiles` - lists all material files provided to the agent for their current assignment
- `getMaterialFileProperties` - like `getFileProperties` but constrained to the material files available on the assignment
- `readMaterialFile` - reads a specific material file from the available material files

This simplfies the request that an LLM must make to use the tools, as some of the parameters can be filled in automatically by the agent loop code or MCP service itself. It also helps to avoid some (but not all) mistakes where the LLM furnishes the wrong information for some fields.
