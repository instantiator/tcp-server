# Assignment Completion & QA Improvements (010.08.01)

## Context

The user has watched agents (particularly weaker local LLMs) burn a retry on `complete_assignment`'s artifact `type` (guessing `file`/`text` instead of the real `assignment-working-path`/`inline-text`) and on `assure_assignment`'s `qa` verdict (submitting `Accept` instead of `accept`). The prompt asks: (1) do we already state acceptable values up front, (2) rename the artifact types to the intuitive `file`/`text` with synonyms accepted, (3) whether this should generalise into a shared description-generation utility for every MCP tool's enumerated properties, and (4) for QA specifically, whether to tell the model tool calls are case-sensitive or just accept case variants.

Research below (reading `tasks-tools.service.ts`, `assignment.service.ts`, `LcpArtifact.ts`, `mode-prompts.ts`, `enum-validation.ts`, and — the actual root cause — `libs/lcp-shared/src/mcp/mcp-client.service.ts`, the code that turns an MCP server's JSON Schema into the Zod schema LangChain actually binds to the model) confirms the current state and traces both complaints to one shared bug.

## Confirmed current state

1. **`type` is not an enum today.** `tasks-tools.service.ts`'s shared `artifactSchema` declares `type: z.string().describe("Artifact type, e.g. 'assignment-working-path' ... or 'inline-text'.")` — free text with two examples in prose, not an exhaustive constraint. It's shared across three call sites with three different valid sets (`create_plan.expected`: `assignment-working-path | inline-text`; `create_plan.materials`: `task-materials-path | assignment-completed-path | inline-text`; `complete_assignment.prepared`: `assignment-working-path | inline-text`, enforced server-side in `assignment.service.ts` via `WORKING_ARTIFACT_TYPES`/`MATERIAL_ARTIFACT_TYPES`) — which is exactly why it was never tightened into a real per-field enum.
2. **A near-miss alias mechanism already exists**, just not for path types. `libs/lcp-shared/src/models/LcpArtifact.ts`'s `canonicalArtifactType`/`ARTIFACT_TYPE_ALIASES` already maps `text`/`inline`/`string` → `inline-text`, applied in `assignment.service.ts` at both `create_plan` and `complete_assignment` before validation. So `text` already works today; `file` (and any path-type synonym) does not — there's no alias entry for it.
3. **Bad values already get a well-written corrective message — for HTTP-layer failures.** `enum-validation.ts`'s `buildEnumValidationError` reports every invalid value in one message, naming the field, what was supplied, and the full valid list, then invites a retry. This fires for role slugs, artifact types, and cross-referenced material filenames. This is the right pattern — it's just not applied everywhere (see #5).
4. **`qa` genuinely is a strict enum server-side**: `z.enum(['accept', 'reject'])` in `tasks-tools.service.ts`. So the QA case-mismatch isn't a validation-strictness gap — the constraint exists.
5. **The root cause of both complaints: the model never sees any of this.** `libs/lcp-shared/src/mcp/mcp-client.service.ts`'s `McpClientService` is what the agent actually uses — it fetches each MCP server's tools via `listTools()` (whose `inputSchema` is the JSON Schema `zod-to-json-schema` generated from the _real_ Zod schema, enums and `.describe()` text included), then **rebuilds a fresh Zod schema from that JSON Schema** for LangChain's `bindTools`/`DynamicStructuredTool`, via `buildZodSchema`/`jsonSchemaFieldToZod`. That rebuild only reads `field['type']` (`string`/`number`/`boolean`/`array`/`object`) — it **drops `enum` and `description` unconditionally, for every field, on every tool, across all four MCP servers**. Concretely: the model's actual function-calling schema for `assure_assignment` has `qa: z.string()` with no description at all, not `z.enum(['accept','reject'])` — the only place the model ever sees "accept"/"reject" is the prose in `tools.jsonc`'s tool-level description ("accept it, or reject it"). Same for `type` and every other `.describe()`'d property on every tool. This is a single, previously untested, unexported pair of functions (`git grep` finds zero references or specs beyond this one file) — a genuine gap, not a documented tradeoff.
6. **The two mistake-recovery paths are inconsistent.** A 4xx from lcp-server's internal endpoint (role/artifact-type/case-*) is relayed verbatim by `relayOrError` as the polished `buildEnumValidationError` text. A Zod schema-validation failure at the MCP layer (e.g. `qa: 'Accept'` failing `z.enum(...)`) is caught by the SDK's `validateToolInput`, which throws an `McpError` carrying the raw Zod message (`Invalid enum value. Expected 'accept' | 'reject', received 'Accept'`). LangGraph's `ToolNode` (used in `build-agent-graph.ts`) catches that and turns it into a `ToolMessage` the model does see — so it isn't a dead end — but it's a second, uncurated error format living alongside the first, for what is conceptually the same class of mistake.

## Recommendation

Fix the root cause once, in the one function both complaints funnel through, rather than patching each tool's prose. Concretely:

- **No new "shared description-generation utility" is needed.** One already exists, implicitly: every tool schema is already authored with Zod's own `z.enum()`/`.describe()` at the point of definition (`tasks-tools.service.ts`, `storage-tools.service.ts`, etc.) — that _is_ the single source of truth the user is asking for. The gap was never at generation; it's that `McpClientService.buildZodSchema` — the one function every tool's schema already passes through — silently discards it before the model ever binds to it. Completing that one function benefits `assure_assignment`'s `qa`, `list_available_contacts`' `kind`, every future enum, and every existing `.describe()` on every current tool, immediately.
- Then, and only for the `type` field specifically (its problem is vocabulary, not visibility — `assignment-working-path` is just an unintuitive name), rename the LLM-facing values to `file`/`text` and extend the existing alias map rather than inventing a second one.
- For `qa`, accept case variants (option 2 from the prompt) over a prose case-sensitivity warning (option 1) — a warning is exactly the kind of extra instruction the user already observed smaller local models skipping, whereas accepting variants is a one-time, zero-attention-cost fix. Apply it everywhere the same shape of problem exists, per the user's own generalisation.

## Implementation plan

### 0. Save this plan

Write this plan verbatim to `docs/prompts/010.07.01 - assignment completion and QA improvements.plan.md` (already done as part of producing it).

### 1. Fix `McpClientService`'s JSON Schema → Zod conversion (the root fix)

In `libs/lcp-shared/src/mcp/mcp-client.service.ts`:

- `jsonSchemaFieldToZod(field)`: after building the base type, call `.describe(field.description)` when `field['description']` is a string — for every branch, not just leaves at the top level (so array-item and nested-object properties keep their descriptions too).
- When `field['type'] === 'string'` and `field['enum']` is a non-empty string array, build `z.enum(field.enum as [string, ...string[]])` instead of `z.string()`, still chaining `.describe(...)`.
- `buildZodSchema`: no change needed beyond what the per-field fix already propagates through its existing recursion.
- Add a unit test (new `libs/lcp-shared/src/mcp/mcp-client.service.spec.ts`, since none exists) asserting: a JSON Schema property with `enum` produces a Zod schema that rejects an out-of-enum value and whose `.description` is preserved; a plain string property's `.description` survives the round trip.

This one change is what makes every subsequent step in this plan actually reach the model — do it first.

### 2. Extend the artifact-type alias map, then rename to `file`/`text`

In `libs/lcp-shared/src/models/LcpArtifact.ts`:

Do **not** default bare `file` to `task-materials-path` or `assignment-completed-path` — those two remain distinct concepts in `create_plan.materials` (an uploaded task input vs. a prior step's promoted output) and collapsing them would silently pick the wrong storage location; call sites needing that distinction keep using the fuller names (or plan-mode-specific short names, see below), and get a `buildEnumValidationError` listing the real options if they guess wrong.
- Rename the LLM-facing literal for the two-option contexts (`expected`/`prepared`, i.e. `WORKING_ARTIFACT_TYPES`) from `assignment-working-path`/`inline-text` to `file`/`text` at the MCP boundary only: change `tasks-tools.service.ts`'s artifact schema for `complete_assignment.prepared` and `create_plan.expected` to `z.enum(['file', 'text'])` (now that step 1 makes this reach the model), translate `file` → `assignment-working-path` before the axios POST to lcp-server, and translate back if ever echoed. Internal DB/domain types (`LcpArtifactType`, migrations, stored rows) are unchanged — this is purely a presentation-layer rename, minimal blast radius.
- `create_plan.materials` keeps three real options; give it its own `z.enum(['material-file', 'completed-file', 'text'])` (translated to `task-materials-path`/`assignment-completed-path`/`inline-text` at the same boundary) so it's still a real, visible enum rather than free text — just not collapsed into an ambiguous shared `file`.
- Update `canonicaliseArtifacts` call sites in `assignment.service.ts` — they keep working unchanged since they operate on the _internal_ type strings; the new MCP-boundary translation happens before those calls, so `canonicalArtifactType`'s existing aliasing remains a defence-in-depth layer for any direct API caller that isn't the LLM-facing MCP tool.

### 3. `assure_assignment`: accept case variants, consolidate the error path

- Change `qa` in `tasks-tools.service.ts` from `z.enum(['accept', 'reject'])` to a case/whitespace-normalising equivalent — either `z.string().trim().toLowerCase().pipe(z.enum(['accept', 'reject']))` if that survives the zod-to-json-schema round trip with `enum` intact (verify empirically once step 1 lands; a `.pipe()` may need `zod-to-json-schema`'s `pipeStrategy` handling), or, if not, fall back to the same manual pattern already used for `type`: accept `z.string()`, normalise (`.trim().toLowerCase()`), and validate against `['accept', 'reject']` with `buildEnumValidationError` on mismatch — one consistent mechanism instead of two. Prefer whichever keeps the real enum visible in the tool's JSON Schema per step 1's payoff.
- Update `assure_assignment`'s description in `tools.jsonc` to state the literal values explicitly: ``Verdict must be exactly `accept` or `reject`.`` (case no longer matters functionally once normalised, but the literal words should still be unambiguous).

## Implementation outcome

Steps 1, 3, 4 and 5 landed as planned. Step 2's alias/rename work landed; its
`z.enum(...)` conversion did not, for the reason below.

### Step 2's `z.enum` conversion for `type`: rejected

The plan called for `z.enum(['file', 'text'])` (and
`z.enum(['material-file', 'completed-file', 'text'])`) on the artifact `type`
field, reasoning that step 1 finally makes an enum visible to the model. Tracing
that through the real path shows it would **reintroduce the class of failure this
plan set out to remove**:

1. The MCP server declares `z.enum([...])`, so its JSON Schema carries `enum`.
2. `McpClientService.buildZodSchema` — post-step-1 — faithfully rebuilds that as
   a Zod enum, which is **strict and case-sensitive**.
3. `DynamicStructuredTool` validates the model's arguments against that rebuilt
   schema, client-side.
4. So `File`, `WORKING_FILE` or `path` would now be rejected _before_ reaching
   lcp-server — where `canonicalArtifactType` already normalises case,
   whitespace and underscores and resolves aliases, and accepts all of them
   today.

That directly contradicts step 3's own rationale — that a weaker local model
skipping a case instruction is exactly the observed problem, and "accepting
variants is a one-time, zero-attention-cost fix". Step 2 and step 3 are in
tension for this field, and step 3 reflects the reported pain.

Two further points settled it:

- **`qa` already made the same call.** It shipped as `z.string()` plus
  `qa.trim().toLowerCase()`, not `z.enum` (step 3's fallback branch). `type`
  staying `z.string()` is therefore consistent with the codebase, not an
  oversight. `kind` in `interactions-tools.service.ts` follows the same pattern.
- **Error quality is better without the enum.** A bad value today reaches the
  server and returns a `buildEnumValidationError` naming the field, the supplied
  value and the full valid list. Under a strict enum it fails client-side with a
  raw Zod message relayed by LangGraph's `ToolNode` — the "second, uncurated
  error format" this plan's own analysis criticised.

Step 2's actual goal — making the allowed values visible to the model — is met
regardless: step 1 guarantees `.describe()` survives the schema round trip, and
both artifact schemas name `file`/`text` (and
`material-file`/`completed-file`) explicitly in their descriptions. The enum
would only have added the strictness that hurts.

`ARTIFACT_TYPE_DISPLAY_NAMES` (in `LcpArtifact.ts`) was added beyond the plan, so
corrective messages report the short agent-facing names rather than internal
storage-path names — step 5's last bullet.

### Test coverage

The spec step 1 asked for exists as
`apps/lcp-agent/src/mcp/mcp-client.service.spec.ts` (that app re-exports the
shared service), driving the real `loadTools` path rather than the unexported
helpers. Top-level enum-and-description preservation was already covered;
coverage for the **recursive** branches — array items and nested-object
properties, which step 1 explicitly required — was added afterwards, since a
dropped nested description still yields a structurally valid schema and would
otherwise regress silently.
