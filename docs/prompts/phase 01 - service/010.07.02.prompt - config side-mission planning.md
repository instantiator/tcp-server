## Thoughts

There are configuration variables for the applications to see (ie. internal variables delivered through docker compose as environment variables for the application), and there are configuration variables for external applications (ie. lcp-cli, and tests).

For instance, as you pointed out, these variables:

- `DATABASE_URL`
- `REDIS_URL`
- `MINIO_ENDPOINT`

... in the `.env` file, these describe how to access these services on the local machine but external to the docker compose network. Whereas, `docker-compose.yml` provides its own values for these to the applications it launches, and uses docker compose network machine names (eg. `postgres://user:passwd@postgres`, `redis://redis`, `http://minio`)

We should improve how the config is actually specified and used, and _then_ return to correcting the wizard.

## Principles, preferences, knowns

1. Inside the docker compose network, the machine names are known (eg. postgres, redis, minio, etc.)

2. _Some_ port numbers should be exposed (eg. currently, lcp-server's API is at port 3000, minio is at port 9000, oidc is at 8080). These should be configurable. Not all applications should be exposed.

3. Exposed port numbers should be configurable to support concurrent environments running without competing for ports - ie. whatever the internal ports are inside docker compose, they must also be exposed as specific ports on localhost, offset from a base port number, eg. 3000 (dev), 4000 (testing), etc.

4. Some services may be delivered by third party providers.
   - Currently that's the OIDC auth service
   - The configuration indicates whether auth should be provided (in which case Zitadel is included by docker compose), or not (in which case, an external OIDC endpoint is provided, including sufficient credentials to create a machine token)

5. The `.env` order of precedence that we've been implementing is not ideal. I've changed my position on it. Default values for the system should really only live in one place, and using `.env.defaults` creates a second set of default values, which isn't ideal. Instead, we should set config in one place, in code - where it can be typed, checked, and generate appropriate warnings / errors if not correct. This removes the need for an order of precedence of `.env` files. We should ensure that all config defaults are in: `libs/lcp-shared/src/config/defaults.ts` and drawn from there. We'll keep environemnt-based config, eg. `.env.dev`, `.env.testing`, but we won't need `env.defaults`

6. `start-deployment.sh` and the test runner scripts shouldn't export environment variables to the shell. Values should be read from the `.env` files.

7. The applications running in docker _do_ expect to receive configuration by environment variables, and `docker-compose.yml` passes through these essential variables, using the environment files specified.

8. The setup wizard work we've done so far is good - and valuable. We should ensure that it remains compatible with the updates we're making to the configuration.

## Configuration approach

This means a bit of a redesign of the configuration in the `.env` files. We'll still use `.env.*` for specific environments. We'll remove `.env.defaults`.

## Defaults and precedence

If a value isn't provided in a `.env.*` file, we should fall back to hard coded values in `defaults.ts`.

The internal URLs between components inside the docker network can be generated inside docker compose.

Exposed ports should be relative to the API port (by default), but can be overridden in `.env.*` files. The API port will be 3000 for dev instance, and varies by environment.

## Environment variables

I suggest:

| variable              | value                    | notes                                                | eg. dev | eg. tesing |
| --------------------- | ------------------------ | ---------------------------------------------------- | ------- | ---------- |
| `EXPOSE_PORT_API`     | eg. 3000                 | use 3000 for `lcp-dev`, 3001 for `lcp-all` (testing) | 3000    | 3001       |
| `EXPOSE_PORT_MINIO`   | `EXPOSE_PORT_API` + 6000 |                                                      | 9000    | 9001       |
| `EXPOSE_PORT_DB`      | `EXPOSE_PORT_API` + 2432 |                                                      | 5432    | 5433       |
| `EXPOSE_PORT_ZITADEL` | `EXPOSE_PORT_API` + 5080 |                                                      | 8080    | 8081       |

Ideally the other services, ie. lcp-agent, lcp-mcp-*, are not exposed.

The db should only _really_ be exposed in dev and testing environments. We can modify the deployment to not expose it for production environments in future.
