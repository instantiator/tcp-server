# lcp-cli 010.02.03: SSE endpoints & TUI company task lists

Part 2 of the 010.02.00 lcp-cli improvements (map: `010.02.00 - lcp-cli improvements for
tasks and assignments.md`). Depends on `010.02.01` (the cancel path and
`AgentStatus.Cancelled` are referenced by the SSE emit points and the TUI). Part
3 (`010.02.05`) adds the task and assignment panels that consume the task-level SSE
introduced here.

> **2026-07-16 — scope added from `010.02.01` implementation feedback**
> (`docs/prompts/10.3.1.1 feedback.md`): the feedback identified gaps that
> block hands-on testing of the task/SSE work in this part (no way to set a
> planner, edit, or start a task from the CLI) and a data-model gap that
> affects the SSE emit points and task-history reconstruction this part builds
> (consultation assignments have no link back to their task). Both are added
> below as §1 and §5. Not TUI work, but they're prerequisites for exercising
> and correctly scoping the SSE/TUI work, so they land here rather than a new
> doc.

> **Recommended implementing model: Opus.** The SSE buses are cross-process
> (Redis) and must not leak subscriptions; the TUI multi-list generalisation and
> the terminal-resize fixes are fiddly terminal-kit work with real-widget tests.

## Goal

1. **CLI task-lifecycle verbs** — `set-planner`, `set-task`, `start-task`, and a
   fix to `create-task`'s expected-outputs flag, so a task can be configured,
   edited, and started entirely from the CLI.
2. **Company & task SSE endpoints** — the backend event buses the TUI needs:
   `GET /api/company/:id/events` (company + its tasks change) and
   `GET /api/task/:id/events` (task + its assignments change).
3. **TUI multi-list company panel** — generalise a panel to hold several
   selectable, titled, groupable lists with the `>` indicator moving across all
   of them; add the company's tasks as a grouped list, live-updating from the
   company SSE.
4. **Terminal resize resilience** — fix the crash on resizing to a small
   terminal.
5. **Assignment parent tracing** — a nullable `parentAssignmentId` so
   consultation (and other sub-agent) assignments link back to the task they
   were spawned for, fixing task-history/SSE gaps for consultations.

## 1. CLI task-lifecycle verbs

Today `create-task --start` is the only way to set a task running, and it fails
outright if neither the task nor its company has a `plannerRoleId` configured
(`UnprocessableEntityException` in `TaskService.start`,
`apps/lcp-server/src/api/task.service.ts:135-139`). There's also no way to edit
an unstarted task, or to start one after the fact without recreating it.

### `set-planner`

New CLI verb: `set-planner (--company <slug-or-id> | --task-id <uuid>) --role
<slug-or-id>` (role trio via `addRoleOptions`, `apps/lcp-cli/src/lib/core/
entity-ref.ts`). Exactly one of `--company`/`--company-id`/`--company-slug` or
`--task-id` must be given — validate and error otherwise.

- **Company target**: resolve the role (needs `resolveRoleId` with the given
  company as context), then `PUT /api/company/:id` with `{ plannerRoleId }`
  (the existing company update endpoint, `api.company.controller.ts` —
  reuse it, don't add a new one).
- **Task target**: `GET /api/task/:id` first to get the task's `companyId` (role
  slugs are company-scoped, so a `--role-slug` needs that context even though
  the user only named a task), resolve the role, then use the new
  `PUT /api/task/:id` endpoint from `set-task` below with
  `{ plannerRoleId }`. Same "unstarted only" guard applies (409 otherwise) —
  `set-planner` doesn't need its own guard, it inherits the one on
  `PUT /api/task/:id`.
- Implementation note: this verb is a thin convenience wrapper — no new
  resolution logic beyond what `set-task`/company-update already provide.

### `set-task`

New backend endpoint `PUT /api/task/:id` + `TaskService.update(id, dto)`
(`task.controller.ts`/`task.service.ts`), mirroring the existing `PUT
/api/role/:id` / `PUT /api/company/:id` deep-partial-update pattern
(`api.role.controller.ts:64-73`, `api.company.controller.ts:93`).

- **Editable fields** (all optional in `UpdateTaskDto`): `request`,
  `plannerRoleId`, `materials`, `expected`. Not editable: `id`, `companyId`,
  `status`, `completed`, `failureReason`, timestamps.
- **Guard**: only when `task.status === 'ready'` (the sole pre-start status,
  confirmed via `TaskService.start`'s own claim guard) — otherwise **409**.
  Unknown id → **404**. If `plannerRoleId` is provided, validate it the same
  way task creation already validates a given `plannerRoleId` (role exists and
  belongs to the task's company) — reuse that check, don't duplicate it.
- **CLI**: `set-task --task-id <uuid> (--input <json> | stdin)` — mirror the
  `--input`/stdin JSON-body pattern in `apps/lcp-cli/src/lib/crud/
role.action.ts` (`setRoleAction`) and the company equivalent. If a shared
  "read JSON body from `--input` or stdin" helper doesn't already exist,
  extract one (e.g. `core/read-json-body.ts`) rather than adding a third copy.

### `start-task`

New `src/commands/start-task.ts` + action: `start-task --task-id <uuid>` →
`POST /api/task/:id/start` (already exists server-side, per `010.02.01` —
there's just no standalone CLI verb for it yet, only the `create-task --start`
path). Print the updated task as JSON, same shape as `cancel-task`.

### `-e` for expected outputs

`create-task`'s `--expected <filenames...>` (`apps/lcp-cli/src/commands/
create-task.ts:24-28`) is a Commander **variadic** option (one occurrence
collects space-separated values); it has no short flag, and `-e` is free on
this command (confirmed: `-c` is company, `-r` is `--request`, `-m` is
materials). Change to a **repeatable** flag matching the feedback's expected
usage (`-e 'a.txt' -e 'b.txt'`):

```ts
.option(
  '-e, --expected <filename>',
  'expected output filename (repeatable)',
  (value: string, previous: string[]) => [...previous, value],
  [] as string[],
)
```

This is a deliberate behaviour change (space-separated `--expected a b c` in
one occurrence stops working; repeat the flag instead) — grep `test/` and
`docs/lcp-cli.md` for the old variadic usage and update both.

### Tests

- e2e: `PUT /api/task/:id` — 200 editing an unstarted task (each editable
  field), 409 editing a started/terminal task, 404 unknown id, 400 invalid
  `plannerRoleId` (unknown role / role from a different company).
- CLI tests: `set-planner` (company target, task target, missing-target error),
  `set-task`, `start-task`, and the `-e` repeatable-flag behaviour on
  `create-task`.

### Docs

- `docs/lcp-cli.md`: the four verbs, and the `-e` flag change (call out the
  behaviour change explicitly).
- `docs/tasks.md` / ADR-010 amendment: the new `PUT /api/task/:id` endpoint and
  its "unstarted only" guard.

## 2. Company & task SSE endpoints

### Model to follow

Copy the shape of the existing per-agent bus:
`apps/lcp-server/src/events/agent-event.service.ts` (`AgentEventService`) +
`@Sse(':id/events')` in `api.agent.controller.ts`, and the Redis relay in
`libs/lcp-shared/src/events/agent-events.ts`:

- A per-key `Map<string, Subject<Event>>`, ref-counted `observe(key)` returning
  an `Observable`, `emit(key, event)` for in-process producers.
- Optional cross-process delivery over a per-key Redis channel, reference-counted
  retain/release, **disabled when `REDIS_URL` is unset** (pure in-memory for
  tests).
- The SSE endpoint maps each event to `{ data: event }` and may prime the stream
  with a current-state snapshot (the agent bus does `replayTerminal`; here, prime
  with the current company/task state so a late subscriber renders immediately).

### New event types

Define in `libs/lcp-shared/src/events/` (new files, e.g. `company-events.ts`,
`task-events.ts`), following `agent-events.ts` conventions:

- `CompanyEvent` — kinds: `company_changed` (company entity updated) and
  `task_changed` (a task in the company changed state; payload carries the task's
  id + new status + minimal summary so the list can update without a refetch).
- `TaskEvent` — kinds: `task_changed` (task status) and `assignment_changed`
  (assignment id + new status + minimal summary).
- Channel-name helpers `companyEventsChannel(id)` / `taskEventsChannel(id)`
  (`company:events:${id}` / `task:events:${id}`), matching `agentEventsChannel`.

### Services & endpoints

- `CompanyEventService` + `TaskEventService` in `apps/lcp-server/src/events/`
  (register in the module that provides `AgentEventService`).
- `@Sse('company/:id/events')` — add to the company controller (or a small events
  controller); `@Sse('task/:id/events')` — add to `task.controller.ts`. Both
  JWT-guarded like the existing SSE route. Each merges a primed snapshot with
  `service.observe(id)`.

### Emit points

Task/assignment status changes already funnel through
`apps/lcp-server/src/api/task-orchestration.service.ts`
`recordTaskState` / `recordAssignmentState` / `recomputeTaskStatus`. Emit there:

- On task state change → `taskEvents.emit(taskId, {task_changed})` **and**
  `companyEvents.emit(companyId, {task_changed})`.
- On assignment state change → `taskEvents.emit(taskId, {assignment_changed})`
  (and the company `task_changed` if the task's derived status moved).
- On company entity update (the company update path in the company service) →
  `companyEvents.emit(companyId, {company_changed})`.

For cross-process (the lcp-agent worker mutates status too), publish to the Redis
channels from the same points that already publish agent events, or from the
orchestration service — mirror how `agent-event-publisher.service.ts` publishes.
Keep a single emit helper per service; don't scatter `redis.publish` calls.

> Implement §5 (`parentAssignmentId` / `taskId` inheritance) **before or
> alongside** this section: once a consultation assignment carries the parent's
> `taskId` directly, these emit points cover it automatically (a consultation's
> `recordAssignmentState` call already fires `taskEvents.emit(taskId, …)` — it
> just needs a non-null `taskId` to fire with). No special-casing needed here if
> §5 lands first.

### Tests

- e2e: subscribe to `GET /api/task/:id/events` and `GET /api/company/:id/events`,
  drive a task through a state change (e.g. start, or cancel from `010.02.01`), and
  assert both streams observe it. Cover the in-memory (no-Redis) path — that's the
  default in tests.
- Guard against the BullMQ/Subject leak class of bug (see the project memory on
  `.on('error')` handlers and subscription ref-counting): assert `observe`
  retain/release cleans up the Subject/Redis subscription when the last
  subscriber unsubscribes.

### Docs

- The events/SSE doc + ADR-008 amendment (dated): the two new streams, their
  event kinds, and the Redis channels.

## 3. TUI: multi-list company panel + company task list

All paths under `apps/lcp-cli/src/lib/tui/`.

### Generalise a panel to multiple selectable lists

Today the company panel (`RosterPane` in `panes.ts`) shows a single flat roles
list; selection is a `selectedIndex` into `roles[]` and `moveSelection` wraps
modulo that one list (`renderRoleList`/`renderRosterPane` in `tui-format.ts`).

Introduce a small, reusable grouped-list model (pure, in `tui-format.ts` /
`tui-state.ts`, no terminal-kit dependency):

```ts
interface ListGroup {
  title?: string;
  entries: ListEntry[];
}
interface SelectableList {
  title: string;
  groups: ListGroup[];
}
interface ListEntry {
  id: string;
  render(width, selected): string[];
  selectable?: boolean;
}
```

- A panel holds `SelectableList[]`. Maintain a **flat selection index** over all
  _selectable_ rows across all lists (skip non-selectable rows — e.g. group
  headings, and later the not-yet-begun assignments in `010.02.05`). Track, for the
  current flat index, which `(list, entry)` it maps to (so Enter knows what was
  chosen and `afterRedraw` can scroll it into view — keep the existing
  `listStartIndex`/`scrollLineIntoView` approach, generalised).
- `moveSelection(±1)` moves across list boundaries and **cycles top↔bottom** over
  the whole concatenated set.
- A **jump-between-lists** shortcut (e.g. `[` / `]` or `Tab`-like — pick a key not
  already bound in `Tui.handleKey`; document the choice) moves the selection to
  the first selectable entry of the previous/next list. Show it in the bottom
  hint bar via `fitHints` **when it fits**, and always in `HELP_TEXT`.
- Rendering: each list renders its `title`, then per group an optional group
  title, then entries (selected entry drawn with the inverse-video `>` marker as
  `renderRoleList` does today). Blank-line spacing between lists/groups.

Refactor the current roles list to be the first `SelectableList` in this model
(so there's one code path, not roster-special-cased + tasks-special-cased). Keep
`tui-state.ts` `PaneManager` responsibilities intact.

### Company task list

Add a **Tasks** `SelectableList` to the company panel, below Roles. Data comes
from `GET /api/task?companyId=` (existing) at panel open, then live updates.

Groups, in order:

1. **Active** tasks (`ready | planning | in-progress | finalising`), most-recent
   first (`createdAt`/`updatedAt` desc).
2. **Completed / failed** (`succeeded | failed | cancelled`), most-recent first.

Each entry, one line when not highlighted (truncate with ellipsis to fit width):

```
yyyy-MM-dd HH:mm:ss (in progress: 2/3) "Write a short story about a cat."
```

- Date/time `yyyy-MM-dd HH:mm:ss` (add a formatter next to the existing
  `clockTime()` in `tui-format.ts`).
- State + completion indicator, e.g. `(in progress: 3/5)`, `(succeeded)`,
  `(failed)`, `(cancelled)` — derive done/total from the task's implement-mode
  assignment statuses (the task summary the list holds should carry these counts;
  include them in the `task_changed` SSE payload / the list fetch).
- The initial prompt (task `request`), filling the rest of the line.

When **highlighted**, the prompt expands and word-wraps up to
`TASK_LIST_ENTRY_MAX_LINES` lines, with a blank line of spacing before/after the
entry (reuse the wrap in `tui-format.ts`).

### `TASK_LIST_ENTRY_MAX_LINES` config

- Default `const TASK_LIST_ENTRY_MAX_LINES` alongside the layout constants at the
  top of `tui.ts`.
- Overridable, resolved in this precedence: CLI param → env var → default.
  Thread it like `hideReasoning`: a Commander option on `commands/chat.ts`
  (`--task-list-max-lines <n>`, coerced with `Number`), into `ChatCmdOpts`, into
  `new Tui({ …, taskListEntryMaxLines })`. Env fallback
  `process.env['LCP_TASK_LIST_ENTRY_MAX_LINES']` read where the option default is
  applied (match the `process.env['NAME'] ?? default` pattern used by the
  links commands). Validate it's a positive integer; fall back to the default on
  garbage.

### Live updates

Open a company SSE stream (`GET /api/company/:id/events`) when the company panel
is shown, using the same `fetch`+reader+`parseSseBuffer` approach as
`session.ts` `streamAgent` (extract a tiny shared SSE-reader helper if it reduces
duplication — one `// ponytail:`-noted helper, not a framework). On
`task_changed`/`company_changed`, update the in-memory list and redraw the pane
if it's active. Close the stream when the panel/TUI closes (avoid the leak).

### Tests

- `tui-format.spec`: grouped-list rendering — list titles, group titles,
  truncation, highlight expansion to `TASK_LIST_ENTRY_MAX_LINES`, the date/state
  formatter.
- `tui.spec` (real widgets → `ScreenBuffer`, assert via `dumpChars()`/`get()`):
  `>` navigation crossing from the roles list into the tasks list and cycling
  top↔bottom; the jump-between-lists shortcut; non-selectable rows skipped.
- Config: `--task-list-max-lines` and the env var resolve/validate correctly
  (unit).

## 4. Terminal resize resilience

### Root cause

On resize, `Tui`'s handler does `dropInput(); refresh()`. `refresh()` →
`updateInput()` recreates the `InlineInput` at
`y = this.term.height - HINT_ROWS - INPUT_ROWS` (`tui.ts` ~L658) with **no lower
clamp**. Resizing a talkable pane's terminal to `height ≤ 3` makes `y ≤ 0` — the
input box is created at an invalid/off-screen row. `layout()` clamps `logHeight`
to ≥ 1 but the InlineInput's own `y` is not clamped. Combined with terminal-kit's
1×1 default sizing when a resize momentarily reports a degenerate size, this is
the most likely crash on the reported small-terminal resize.

(The other bars are safe: `hintBar` y = `height - 1` ≥ 0 for height ≥ 1; tabBar
fixed at y = 0. Width is mostly defended via `Math.max(width, 1)` in
`wrapText`/`redraw`, but height/positions are not.)

### Fixes

- Clamp **every** resize-derived coordinate and size to a valid range:
  `y ≥ 0`, `width ≥ 1`, `height ≥ 1`, in `layout()`, `updateInput()`,
  `createContentTextBox()`, `renderChrome()`.
- When the terminal is **too short to hold the input row** (i.e. computed input
  `y` would be `≤ CONTENT_TOP` or the content area would be < 1 row), **skip
  creating the input** (leave the pane in view-only layout) rather than place it
  at an invalid row. Recreate it when the terminal grows back. Keep the existing
  drop-and-rebuild-on-resize approach for InlineInput (it can't be repositioned).
- Guard against a resize reporting width/height `0` or `1` (terminal-kit 1×1
  default): treat as "too small", render nothing that would throw, and recover on
  the next resize with a real size.
- Do **not** nest widgets in Containers (the documented `Container.resize` trap) —
  keep sizing each TextBox directly via `setSizeAndPosition`.

### Tests

Extend `tui.spec` (currently only tests a 16→12 shrink):

- Resize to a **degenerate** terminal (`height ≤ 4`, and `width ≤ 2`) on both a
  talkable and a non-talkable pane — asserts no throw and a sane render.
- A **shrink-then-grow** cycle (large → tiny → large) — asserts the input box is
  dropped when too small and restored, and the panes re-lay-out correctly.

## 5. Assignment parent tracing (`parentAssignmentId`)

### The gap

`eavesdrop --task-id` (`010.02.01`) can't trace consultations spawned mid-task:
consultation assignments are created with `taskId: null`
(`apps/lcp-server/src/db/db.service.ts:359`, inside `createAgent`'s
orphan-assignment branch), so they never show up in a task's assignment list or
its audit history. This is also why the task-history/SSE work in this doc needs
a real fix, not a workaround — the underlying data model doesn't record "this
assignment exists because of that one."

QA and finalise assignments are **not** affected — they already set `taskId`
directly (`task-orchestration.service.ts:166` and `:525`), copied from their
source assignment/task at creation. Only the `createAgent` orphan-assignment
branch (consultations, and any other flow that omits `assignmentId`) is missing
the link.

### The fix

Add to `LcpAssignment` (`libs/lcp-shared/src/models/LcpAssignment.model.ts`,
alongside the existing `targetAssignment`/`targetAssignmentId` self-FK used for
QA):

```ts
/** The assignment whose agent spawned this one (e.g. a consultation). Distinct
 *  from `targetAssignment` (what a QA assignment reviews) — this is "who
 *  created me", not "what am I evaluating". */
@ManyToOne(() => LcpAssignment, { nullable: true, onDelete: 'SET NULL' })
parentAssignment?: LcpAssignment | null;

/** @format uuid */
@Column({ nullable: true })
@Index()
parentAssignmentId?: UUID | null;
```

New migration (register in every `apps/*/src/app.module.ts` migration list by
hand — the CLI's `data-source.ts` glob will silently mask a missed
registration, per project convention).

Thread it through the one call site that needs it:

- `LcpAgentTemplate` (`apps/lcp-server/src/templates/LcpAgentTemplate.ts`)
  gains an optional `parentAssignmentId?: UUID`.
- `DbService.createAgent` (`db.service.ts:345-388`): when
  `template.assignmentId === undefined` **and** `template.parentAssignmentId`
  is given, look up that parent assignment (one query) and set the new
  assignment's `taskId: parent.taskId` and `parentAssignmentId:
template.parentAssignmentId` instead of today's hardcoded `taskId: null`.
  When `parentAssignmentId` is absent, behaviour is unchanged (top-level
  agents — planner dispatch, the standalone `chat` command — stay parentless
  and taskless).
- `PauseAndResumeService.pauseForConsultation` (`pause-and-resume.service.ts:
106-192`): pass `parentAssignmentId: callingAgent.assignmentId` in its
  `orchestration.createAgent({...})` call (`:152-161`). `callingAgent` (an
  `LcpAgent`) already has `.assignmentId` — no extra lookup needed there; the
  lookup for `.taskId` happens once, inside `createAgent`, from the assignment
  row.
- Audit any other `createAgent` caller that omits `assignmentId` (grep
  `orchestration.createAgent(` and `dbService.createAgent(`) — apply
  `parentAssignmentId` wherever the new agent is spawned on behalf of an
  existing assignment (the pause-for-user-input follow-up path is the other
  candidate flagged during research; confirm at implementation time whether it
  creates a new assignment at all, or resumes the existing one). Flag any
  ambiguous case rather than guessing.

### `AuditEvent` denormalization

The feedback asked for advice on adding `task`/`taskId`/`assignment`/
`assignmentId` to `AuditEvent` directly, versus reaching them via
`event.agent.assignment.task`.

**Recommendation: add a denormalized `assignmentId` (nullable, indexed) — not
`taskId`, not object references.** This matches a precedent already in the
model: `AuditEvent.role` (`libs/lcp-shared/src/models/AuditEvent.model.ts`) is
already a denormalized copy of the role at write time, for exactly this reason
(fast, join-free filtering on an immutable log; the row reflects state _as of
the event_, which matters if an assignment's role/agent could be reassigned
later even though that's not the case today). `assignmentId` fits the same
pattern:

- Add `@Column({ nullable: true }) @Index() assignmentId?: UUID | null;`
  (`SET NULL`-style — no relation object, matching how `agentId` is handled).
  Composite index `[companyId, assignmentId, timestamp]` alongside the existing
  `[companyId, agentId, timestamp]`.
- Populate it in `AuditService.write` — the caller already knows the agent's
  current assignment at every write site that matters (the agent loop always
  runs within one assignment), so thread it the same way `role` already is.
- **Don't** add `taskId` to `AuditEvent`: with `assignmentId` denormalized and
  `taskId` now inherited directly onto every assignment (this section), "audit
  rows for task X" is one indexed join
  (`assignment.taskId = X → assignmentId IN (…)`) away — not a chain walk.
  Storing `taskId` too would be a second copy of data derivable from the first
  in a single hop; not worth the write-path complexity or drift risk.
- **Don't** add navigation properties (`task`/`assignment` relations) to
  `AuditEvent` — it's a write-heavy log table; every other FK on it
  (`companyId`, `agentId`) is a plain column, not a `@ManyToOne`, for the same
  reason (avoid accidental N+1 joins on the hot write path).

This also fixes the eavesdrop task-history reconstruction from `010.02.01`
without changing its query shape: once assignments carry `taskId` directly (see
above), the existing "gather the agent ids of a task's assignments" approach in
the history endpoint already includes consultations for free — no recursive
parent-chain walk needed, because the inheritance happens once, at creation
time, not per-query.

### Tests

- Unit: `LcpAssignment` migration round-trip (nullable, defaults to null); the
  `createAgent` inheritance logic (parent given → `taskId`/`parentAssignmentId`
  set; parent absent → unchanged `taskId: null`).
- e2e: trigger a consultation mid-task (existing consultation e2e fixture, if
  one exists — else a minimal repro), assert the resulting assignment has
  `taskId` equal to the parent's and `parentAssignmentId` set; assert it now
  appears in `GET /api/task/:id/history` (`010.02.01`) and on the task's SSE
  stream (§2 above).
- Unit: `AuditService.write` populates `assignmentId`; a query filtered by
  `[companyId, assignmentId]` uses the new index (or at minimum, is covered by
  a test asserting correct rows returned).

### Docs

- ADR-008 (audit logging) amendment: the new `assignmentId` column and its
  rationale (denormalization precedent).
- ADR-010 (orchestration) amendment: `parentAssignmentId`, the inheritance
  rule, and which flows set it.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.
- Do not add dependencies unless truly needed; if unavoidable, latest version,
  license/health checked. Do not update existing dependencies. No unrequested
  changes outside this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Never `--no-verify`.

Write unit/integration/e2e/API tests alongside each unit of code — main, edge,
and failure cases; verify HTTP response codes explicitly. TUI tests drive **real**
terminal-kit widgets into a `ScreenBuffer` and assert via `dumpChars()`/`get()` —
never fake the widget API (see the project's terminal-kit testing note). Update
existing tests as code changes.

Standing instructions:

- If the work becomes exceedingly complex or a problem resists solution, HALT
  and inform the user.
- If you discover a beneficial alteration to this plan, HALT and inform the
  user before proceeding.

rationale:

- **§2 emit mechanics**: `CompanyEventService`/`TaskEventService` share one
  new `KeyedEventBus<E>` (not two separate copies of `AgentEventService`'s
  shape). Since every producer of these events lives in-process in
  lcp-server (unlike the agent bus, which relays lcp-agent's own Redis
  publishes), `emit()` publishes to Redis and lets the channel subscription
  deliver the event back to local observers, rather than pushing to the
  local `Subject` directly — this avoids double-delivery on an instance that
  both emits and observes the same key. Falls back to a direct local push
  when `REDIS_URL` is unset. See the ADR-015 amendment.
- **§2 `AuditEvent.assignmentId`**: derived server-side in `AuditService.write`
  from the writing agent's current `assignmentId` (one repo lookup by
  `agentId`), rather than threading a new parameter through every
  `AuditClientService.record()` call site across lcp-agent and the three MCP
  servers. Can never drift from `lcp_agent` (the source of truth); avoids
  touching ~8 external call sites for a field only used for indexed
  filtering. See the ADR-008 amendment.
- **§2 bug found & fixed**: `TaskOrchestrationService.acceptAssignment`/
  `rejectAssignment` claimed the new status atomically in the DB via
  `claimStatus`/a raw `UPDATE`, but never updated the in-memory assignment
  object before calling `recordAssignmentState` — so the audit payload (and,
  now, the new SSE payload) reported the stale prior status (`in-qa`)
  instead of the real new one. Fixed alongside the SSE emit points (same
  method), since the new `assignment_changed` events would otherwise have
  shipped this bug visibly.
- **§2 `ready → planning` was unaudited**: `TaskService.start`'s atomic claim
  never went through `recordTaskState`, so there was no audit/SSE event for a
  task actually starting. Fixed by recording/emitting it once, idempotently,
  from `TaskOrchestrationService.dispatchPlanner` (guarded by the same
  existing-plan-assignment check that already makes that method idempotent).
- **§3 Tasks list data source**: the initial fetch does use
  `GET /api/task?companyId=` as specified, but that endpoint has no
  `completedSteps`/`totalSteps` (only the DB layer can compute those from
  plan-assignment statuses) — so the CLI populates placeholders (`0/0`) from
  it, corrected within the same startup sequence by the company SSE stream's
  priming `task_changed` events (which already carry the full summary). No
  second REST endpoint was added for this.
- **§4 root cause was one layer deeper than the unclamped `InlineInput.y`**:
  that fix (and clamping every other resize-derived coordinate) was
  necessary but not sufficient. terminal-kit's own `Document#onEventSourceResize`
  (registered on the terminal by the `Document` constructor, so it fires
  _before_ `Tui`'s own resize handler) resizes the Document's internal
  compositing buffer to the raw, unclamped size and redraws immediately,
  using whatever positions/sizes our widgets were last set to — which is
  what actually threw. Fixed by un-registering that listener and re-driving
  it ourselves, last, after our own resize handling has already
  reshaped/hidden every widget for the new (possibly degenerate) size — and
  by not forwarding the resize to Document at all when there isn't room for
  content (`hasRoomForContent()`: enough height for one content row, and
  width ≥ `MIN_CONTENT_WIDTH`), since passing a too-small size through
  Document's own resize, even transiently, was observed to corrupt it such
  that a _later_ resize back to a normal size then threw the same error.
