## Context

The parent prompt asks four questions of every document:

1. Are they up to date with the state of the application?
2. Are they simple and readable?
3. Do they overlap in content, or duplicate information?
4. Are they easy to navigate?

Plus diagrams: _"Some diagrams are deliberately simplified — check that they're not
wrong, and recommend changes to improve them — but you needn't aim for 100%
accuracy if that means adding much more detail."_

# Units of development

Each unit ends with a gate. Leave the work uncommitted — and stop after Unit 1 so
the user can review the audit before any edits land.

## Unit 1 — Audit, and agree the plan

**Read everything first; change nothing yet.** Produce a written audit covering:

- **Accuracy** — every doc against the current code. The system has changed a great
  deal recently (assignments, task orchestration, mode-gated tools, Zitadel, the
  config wizard, and now shutdown). Flag anything describing behaviour that no
  longer exists.
- **Overlap** — confirm or dismiss each hypothesis above, and note any others. For
  each real overlap, recommend which document is canonical and what the other
  should become (a cross-reference, a shorter summary, or deleted).
- **Readability** — flag documents that are too long to navigate. `tcp-cli.md` at
  1,202 lines is the obvious candidate; consider whether it should split per
  command group, or gain a table of contents.
- **Navigability** — is `docs/index.md` still a reliable entry point? Are the
  Operations / ADR / Features / Reference groupings still right? Can a newcomer get
  from `index.md` to what they need in two hops?
- **Diagrams** — list all 12 files' diagrams with a verdict each: _correct_,
  _simplified but not wrong_ (leave alone), or _wrong_ (fix).
- **Links** — Unit 2 already lists nine known-broken links from 011.1.1. Don't
  re-audit those; do decide the one judgement call among them (the missing
  ADR-008 amendment section) and re-run the sweep to catch anything
  011.01.02–011.01.07 added.

**Present the audit to the user and agree what to act on before editing.** Some
findings will be judgement calls about structure, and `AGENTS.md` requires planning
to be collaborative.

**Gate:** audit delivered and agreed. No file changes.

A link-and-anchor sweep during 011.01.01 confirmed the rename introduced no new

so this unit fixes them rather than rediscovering them. **Re-run the sweep first**

`## Amendments as implemented (010.01.04) — knowledge folders and knowledge API`,
which slugs to
`#amendments-as-implemented-01021-knowledge-folders-and-knowledge-api`. The short
form is a prefix of the real anchor, so every one of these silently fails:

- `docs/ADRs/ADR-007-shared-company-storage.md` → `#amendments-as-implemented-01026` (self-link)
- `docs/ADRs/ADR-013-prompt-assembly-context-management.md` → `ADR-007…#amendments-as-implemented-0094`
- `docs/index.md` → `ADR-006…#amendments-as-implemented-01022`
- `docs/index.md` → `ADR-007…#amendments-as-implemented-0094`
- `docs/index.md` → `ADR-007…#amendments-as-implemented-01021`
- `docs/index.md` → `ADR-007…#amendments-as-implemented-01026`

> [!IMPORTANT]
> Prefer adding an explicit `<a id="amendments-as-implemented-<nnn>"></a>` above
> each amendment heading over lengthening the links. The short form is what every
> author has reached for, `docs/index.md` uses it heavily, and an explicit id
> survives future edits to the heading's title text. Lengthening the links instead
> makes every one of them fragile against a title reword.
>
> Whichever you choose, apply it consistently across **all** ADR amendment
> headings, not just the six that happen to be linked today.

## Unit 3 — Overlap and duplication

Act on the agreed overlap findings. Principles:

- **One canonical home per topic.** Everywhere else cross-references it.
- Prefer **deleting duplicated prose and linking** over maintaining two versions —
  a duplicated explanation is a future contradiction.
- Keep a short orienting summary where the reader lands, then link for detail. Do
  not replace a helpful paragraph with a bare link.
- When merging, keep the better text, not just the longer one.

**Gate:** `./dev-environment/scripts/check.sh --fast`; no broken links.

## Unit 4 — Readability and navigation

- Split or restructure the documents the audit flagged (`tcp-cli.md` most likely).
  If splitting, update `index.md` and every inbound link.
- Ensure long documents have a usable heading structure.
- Verify `docs/index.md` describes each document accurately — the descriptions are
  the main navigation aid and several are doing real work.
- Check `README.md` and `CLAUDE.md` still point at the right entry points.

**Gate:** `./dev-environment/scripts/check.sh --fast`; a newcomer path check —
from `README.md`, can you reach setup, architecture and the CLI reference easily?

## Unit 5 — Diagrams

For each of the 12 files:

- **Wrong** — fix it. A diagram showing a flow that no longer exists is worse than
  no diagram.
- **Simplified but not wrong** — **leave it alone.** The prompt is explicit that
  100% accuracy is not the goal if it means much more detail. Note the
  simplification in your report rather than "improving" it into unreadability.
- **Missing** — only propose a new diagram where it would genuinely help. The
  shutdown drain sequence (011.01.06) is a plausible candidate, since it spans CLI,
  API, worker and Docker.

Pay particular attention to `docs/queue.md` (4 diagrams of BullMQ job flows, an
area heavily reworked) and `ADR-012`'s 2 diagrams (pause/resume, which shutdown now
also touches). ADR diagrams are historical records — if one no longer matches the
implementation, that belongs in an amendment section, not a silent edit.

Verify every mermaid block still parses.

**Gate:** `./dev-environment/scripts/check.sh --fast`; all diagrams render.

## Code quality requirements

Route via `AGENTS.md` → `dev-environment/guidance/index.md`; read
`process/before-coding.md` first and `process/after-coding.md` when done, and
follow `dev-environment/skills/docs-review/SKILL.md`. State the filename of each
guidance doc you read.

- **After every unit**, run `./dev-environment/scripts/check.sh` (at least
  `--fast`) and fix what it reports. Never bypass a hook with `--no-verify`.
- **Never hand-edit generated artefacts** — `docs/licenses.md` and
  `schemas/schema.json` come from `npm run build`.
- **Do not touch `docs/prompts/**`** beyond this 011.1.x family.
- ADRs record decisions as they were made. Corrections and reality-updates go in
  amendment sections using the existing anchor convention — do not rewrite history.
- Preserve intra-document anchor links when changing headings; ADRs cross-reference
  each other's amendment anchors heavily and these break silently — six of them
  are broken today for exactly this reason (Unit 2).
- Documentation should state **intent** and be simple and readable — the same
  standard the code is held to.
- Remove documentation for removed code; add it for new code.
- Do not change code in this sub-plan. If a doc is wrong because the _code_ is
  wrong, report it rather than fixing it here.
- aislop is opinionated and can disagree with these standards. Where they conflict,
  **the documented standards win**.
