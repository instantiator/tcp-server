# Task orchestration 5/8: the lcp-mcp-tasks service

Part 5 of the task-orchestration work (map: `010.2.0 - task orchestration: overview.md`;
parts 1–4 are in place — entities, task API with a no-op `TaskDispatcher` hook,
agents always have an assignment with a `mode`, mode prompts exist in
`@lcp/shared`).

> **Recommended implementing model: Opus.** The service scaffold is
> mechanical, but the state-transition endpoints must be race-safe and the
> `complete_task` retirement ripples through consultation/conversation
> behaviour that must not regress.

## Goal

A new MCP service, `lcp-mcp-tasks`, exposing three mode-gated tools —
`create_plan` (plan mode), `complete_assignment` (implement mode),
`assure_assignment` (qa mode) — plus `describe_server`; the lcp-server internal
endpoints that back them; and the retirement of `complete_task` in
lcp-mcp-interactions (implement-mode completion becomes `complete_assignment`).

Orchestration _reactions_ (dispatching QA agents, resuming after rejection,
copying approved files, advancing the plan) are **part 7** — in this part the
endpoints perform the validated state transitions and call the injectable
`TaskDispatcher` hook (still a logged no-op).

## Key design points (agreed — do not re-derive)

- **No assignment/task IDs in LLM-visible tool schemas.** `agentId`/`companyId`
  are auto-injected server-side by `McpClientService` (existing mechanism —
  the model cannot spoof identity). Each tool resolves the caller's assignment
  from `agentId`, so the model never supplies one.
- **Mode gating happens in the tool handler** (MCP servers are built per
  request, without agent context): each handler fetches the caller's assignment
  (`GET /internal/agent/:id/assignment`) and returns a clear error if the
  agent's mode doesn't permit the tool.
- **State transitions live in lcp-server** (which owns the DB and
  `StorageService`); the MCP service is a thin proxy + prompt/presentation
  layer, exactly like `lcp-mcp-storage` (see `storage-tools.service.ts`'s
  header comment) and `lcp-mcp-interactions`.
- Transitions use **atomic conditional UPDATEs** (the `pausedAt` claim pattern
  in `agent-orchestration.service.ts`) so double calls / races resolve to one
  winner; the loser gets a descriptive error.

### 2. lcp-server internal endpoints

In `apps/lcp-server/src/api/internal.controller.ts` (or a sibling
`internal-task.controller.ts` if that file is getting long), guarded by the
existing `InternalApiKeyGuard`:

**`GET /internal/agent/:agentId/assignment`** → 200
`{ assignment, task | null }` (assignment with mode, status, materials,
expected, prepared, orderIndex, targetAssignmentId; task when present).
404 if the agent doesn't exist. (Also used by part 6 for storage scoping.)

**`POST /internal/task/:taskId/plan`** — body
`{ agentId, assignments: { prompt: string; role: string; expected: { type: 'assignment-working-path' | 'inline-text'; value: string }[]; materials?: { type: 'task-materials-path' | 'assignment-completed-path' | 'inline-text'; value: string }[] }[] }`.
Validation (each failure → 4xx with a message the MCP layer relays verbatim,
written to guide the LLM to correct its call):

- caller agent exists, is in `plan` mode, and its assignment's task is `:taskId`;
- task status is `planning` (atomic `planning → in-progress` claim);
- ≥ 1 assignment; every `role` resolves (id or slug) within the company;
- artifact types within the allowed unions.
  Creates the implement-mode `LcpAssignment` rows (orderIndex 0…n−1, status
  `ready`, hint materials stored as given), then calls
  `TaskDispatcher.taskPlanned(task)` (no-op until part 7). 201.

**`POST /internal/assignment/:id/complete`** — body
`{ agentId, summary: string, prepared: { type: 'assignment-working-path' | 'inline-text'; value: string }[] }`.
Validation: caller is the assignment's agent, mode `implement`, assignment
`in-progress`. Then the **mechanical gate**:

- every `expected` entry of type `assignment-working-path` must appear in
  `prepared` AND the resolved storage key must exist (check via
  `StorageService`);
- every `expected` `inline-text` entry must be matched by some prepared
  `inline-text` (expected value `''` → any; otherwise treat expected value as a
  regex the prepared text must match);
- every prepared `assignment-working-path` must exist in storage.
  Gate failure → 422 with a corrective message listing exactly what is missing
  (model it on the `missing_output_files` prompt flow in
  `apps/lcp-mcp-interactions/src/mcp/interactions-tools.service.ts`).
  Gate pass, then **branch**:
- _Orphan assignment_ (`taskId === null`): assignment → `succeeded`
  (prepared ≡ approved), and the agent is completed via the same code path as
  today's `/internal/agent/:agentId/complete` with `summary` as the output —
  consultations and conversations must keep resolving exactly as with
  `complete_task`.
- _Task assignment_: set `prepared` and `summary` (the summary is held on the
  assignment and becomes the agent's `output` when QA accepts, in part 7),
  assignment `in-progress → in-qa` (atomic), agent → `Paused` (with
  `pausedAt`, so part 7 can resume it with QA feedback through the normal
  machinery), then
  `TaskDispatcher.assignmentReadyForQa(assignment)` (no-op until part 7).
  Recompute + persist the task status via `deriveTaskStatus` after the
  transition. 200.

**`POST /internal/assignment/:id/assure`** — body
`{ agentId, qa: 'accept' | 'reject', feedback?: string }` (`feedback` required
when rejecting → 400 otherwise). Validation: caller is a `qa`-mode agent whose
assignment's `targetAssignmentId === :id`; target assignment is `in-qa`
(atomic claim). Sets `qaStatus`/`qaFeedback` on the target, then
`TaskDispatcher.assignmentAssured(assignment)` (no-op until part 7 — which
owns accept/reject consequences). The QA agent's own assignment → `succeeded`
and the QA agent is completed (same completion path, summary = the verdict). 200.

### 3. MCP tools (`tasks-tools.service.ts`)

Follow `interactions-tools.service.ts` structurally (per-request `McpServer`,
zod schemas, prompts/descriptions from jsonc, audit events via
`AuditClientService`, error strings from prompts):

- `describe_server` — describes the three tools **per the caller's mode**
  where possible; the static description text embeds the relevant
  `MODE_PROMPTS` texts from `@lcp/shared` so the prompt and the service
  description can never drift.
- `create_plan` — input: `{ assignments: { prompt, role, expected[], materials?[] }[] }`
  (+ injected `agentId`/`companyId`). Resolves the caller's assignment; error
  if not plan mode; proxies to the plan endpoint; relays validation errors
  verbatim; success returns a short confirmation naming the created assignment
  count.
- `complete_assignment` — input: `{ summary: string, prepared: { type, value }[] }`.
  Proxies to the complete endpoint; a 422 gate failure is returned as a normal
  tool result (not an exception) so the model can correct itself.
- `assure_assignment` — input: `{ qa: 'accept' | 'reject', feedback?: string }`.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.
- Do not add dependencies unless truly needed; if unavoidable, latest version,
  license/health checked. Do not update existing dependencies. No unrequested
  changes outside this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Never `--no-verify`.

Write unit/integration/e2e/API tests alongside each unit of code — main, edge,
and failure cases; verify HTTP response codes explicitly. Update existing tests
as code changes (grep `test/` directories by class name when changing
constructors or behaviour).

Standing instructions:

- If the work becomes exceedingly complex or a problem resists solution, HALT
  and inform the user.
- If you discover a beneficial alteration to this plan, HALT and inform the
  user before proceeding.
- Document any agreed deviations by appending dated notes to this file.
