# 10.3.1 feedback

There's a little feedback from this implementation. Please don't implement yet - instead, please adjust docs/prompts/010.02.03 and docs/prompts/010.02.05, which we'll be implementating next.

## `create-task` without a planner

Right now, when creating a task, if there's no planner role for the task, or on the company, then `--start` will fail.

### implement `set-planner`

Ideally, we'd have a `set-planner` verb for a company which allows the user to specify a role to be the planner, and either a company or a task to have it set on. (Tasks should only be editable if not started yet.)

## editing and starting tasks

Similarly, if not started, lcp-cli doesn't offer an easy way to:

- edit the task
- start the task

### `set-task` verb

Let's also add a `set-task` verb that allows task editing (similar to `set-company` and `set-role` it would allow provision of a deep-partial of the entity and updates the entity in place). (Only unstarted tasks should be editable.)

### `start-task` verb

Let's also add a `start-task` verb that can initiate a task if it's not already started.

### `-e` unrecognised

This was unexpected - please review the expected outputs parameter. Ideally, it would also be a repeatable parameter, eg. `-e 'some-file.txt' -e 'some-other-file.md'`

## tracing improvement

> `eavesdrop --task-id` doesn't trace consultations spawned mid-assignment (they're orphan assignments with no FK back to the task)

That's interesting - it makes sense, we're not really giving assignments a parent assignment - but I think we should, as it's something that happens during a task for the task.

For task-initiated assignments, the `task` and `taskId` properties are still suitable.

Let's add a nullable `parentAssignmentId` property to assignment, and let's also inherit `taskId` and `task` of the parent assignment. That way, when there's a consultation, the parent assignment's id can be applied. This should make it easier to include consultations, and maybe also QA and finalisation assignments in the trace of a task.

Design opinion: Should we add nullable `task`/`taskId` and `assignment`/`assignmentId` properties to the `AuditEvent` model and copy them from the agent's assignment? Technically that information is reachable from the agent (eg. `event.agent.assignment` and `event.agent.assignment.task`) but it might be easier to see at a glance, or to compose quick queries, and easier to index the audit logs, if we add them to the model itself. Please offer advice based on common and best practices.
