# Task orchestration: overview (010.01.03)

This document is the map for the task-orchestration work, synthesised from
`010.01.00.prompt - knowledge management.md` and `010.01.01.prompt - task orchestration planning.md`.
It is **not** an implementation prompt. The implementation is divided into nine
ordered, self-contained sub-plans — each one is implemented in its own session
with the instruction "Please implement the plan laid out at: `<path>`". (Part 8
was added after part 4 shipped, to consolidate the chat and worker agent paths;
see its row below.)

## Shared design decisions

These were agreed during planning (see the review notes at the end). Every
sub-plan restates the parts it needs; this section is the authoritative record.

### Storage layout

```
{company_slug}/
  tasks/
    {task_id}/
      materials/               ← user-submitted inputs; read-only for agents
      completed/               ← final outputs of the task
      assignments/
        {orderIndex}/
          working/             ← private working area for the assignment's agent
          completed/           ← files promoted from working/ when QA accepts
  assignments/
    {assignment_id}/
      working/                 ← working area for ORPHAN assignments (agents outside any task)
  knowledge/
    {role_slug}/               ← OKF docs for RAG indexing (per-role knowledge)
    shared/                    ← OKF docs for RAG indexing (whole-company knowledge)
```

Notes:

- Knowledge folders move from `role.name` to `role.slug`; `shared` is a reserved
  role slug.
- **Orphan assignments** (assignments with no task — plain conversations,
  consultations) get a working directory under `{company_slug}/assignments/{assignment_id}/working/`.
  This is an addition to 010.01.00's tree: without it, removing the general
  `write_file` tool would leave chat agents unable to write anything.

### Artifact model

No artifact table. Artifacts are `{ type, value }[]` stored in `simple-json`
columns, constrained by TypeScript union types:

```ts
type LcpArtifactType =
  | 'task-materials-path' // → {company_slug}/tasks/{task_id}/materials/{value}
  | 'task-completed-path' // → {company_slug}/tasks/{task_id}/completed/{value}
  | 'assignment-working-path' // → .../assignments/{orderIndex}/working/{value} (or the orphan working dir)
  | 'assignment-completed-path' // → .../assignments/{orderIndex}/completed/{value} — orderIndex resolved as the
  //   MOST RECENT prior assignment listing the value in its approved list
  | 'inline-text'; // literal text; as an expectation, value is blank (any text) or a regex

interface LcpArtifact {
  type: LcpArtifactType;
  value: string;
}

type LcpMaterialArtifact = LcpArtifact & {
  type: 'task-materials-path' | 'assignment-completed-path' | 'inline-text';
};
type LcpAssignmentWorkingArtifact = LcpArtifact & {
  type: 'assignment-working-path' | 'inline-text';
};
type LcpAssignmentCompletedArtifact = LcpArtifact & {
  type: 'assignment-completed-path' | 'inline-text';
};
type LcpTaskCompletedArtifact = LcpArtifact & {
  type: 'task-completed-path' | 'inline-text';
};
```

The `assignment-materials-path` type from 010.01.01's draft union is dropped
(user-confirmed: leftover from an older revision). The example's `materials-path`
and `finished-path` map to `task-materials-path` and `task-completed-path`.

### Entities (summary — full definitions in 010.01.06)

- `LcpTask`: request, companyId, plannerRoleId, status, materials/expected/completed
  artifact arrays.
- `LcpAssignment`: taskId (nullable — null = orphan), companyId, mode
  (`plan | implement | qa | chat`; `chat` added in 010.01.11), orderIndex
  (nullable — set only for implement assignments in a task plan), prompt,
  roleId, status, agentId,
  targetAssignmentId (qa mode: the assignment under review),
  materials/expected/prepared/approved arrays, qaStatus, qaFeedback, qaAttempts.
- `LcpAgent` gains a non-nullable `assignmentId`. **Mode lives on the assignment
  only** — the agent derives it via its assignment (no duplicate `mode` column).
- No `LcpAssignmentPlan` entity: a plan is the task's implement-mode assignments
  ordered by `orderIndex`. All "what runs next / is the plan complete" logic is
  isolated in one pure function (`selectNextAssignments`) commented as the
  extension point for future DAG-shaped (branch/join) plans.

### State machines

`LcpAssignment.status`: `ready → in-progress → in-qa → succeeded | failed | cancelled`
(reject during QA returns it to `in-progress`; `qaStatus`/`qaFeedback` are
cleared on re-entry to `in-progress`, `qaAttempts` is kept).

`LcpTask.status`: `ready | planning | in-progress | succeeded | failed | cancelled`.
`planning` is an addition to 010.01.01 (its derivation rules cannot distinguish
"not started" from "planner running"): set when the planner agent is dispatched,
left when `create_plan` lands (→ `in-progress`) or the planner fails (→ `failed`).
Otherwise derived from the implement-mode assignments per 010.01.01's rules:
failed/cancelled propagate; any `in-progress`/`in-qa` → `in-progress`;
all `succeeded` → `succeeded`; else `ready`.

State transitions use **atomic conditional UPDATEs** (the `pausedAt` claim
pattern in `apps/lcp-server/src/api/agent-orchestration.service.ts`).

### QA cycle (user-decided)

`complete_assignment` on a **task** assignment sets the implementing agent to
`Paused` (not `Completed`) while QA runs. Accept → agent `Completed`; reject →
the existing resume machinery injects the QA feedback as the resume message.
On an **orphan** assignment there is no QA: `complete_assignment` completes the
agent directly (this is the successor of `complete_task`, so consultations and
conversations keep resolving exactly as before).

`maxQaAttempts` follows the run-config precedence: `AgentRunConfig.maxQaAttempts`
on the assignment's role → company → env `TASK_MAX_QA_ATTEMPTS` → default 3,
resolved via the existing `resolveRunConfig` helper.

QA is one agent per assignment reviewing all `prepared` items; per-item QA
micro-loops are future work.

### Modes and prompts

- Mode prompt texts (implement/plan/qa; `chat` added in 010.01.11) live in
  `@lcp/shared` as constants — the single source used by lcp-agent's prompt
  assembly, lcp-server's chat path (010.01.11), and lcp-mcp-tasks'
  `describe_server` text.
- The mode prompt is an **additional prompt part** in the N-part assembly
  (alongside the assignment presentation, in the part-4 position) — it does
  **not** replace the system prompt (which keeps role identity).
- `requiredToolCalls` per mode: plan → `create_plan`, implement →
  `complete_assignment`, qa → `assure_assignment`, chat → none (empty — a chat
  turn ends with narrated text and the agent returns to `Idle`).
- lcp-mcp-tasks tools are mode-gated **in the handler** (each looks up the
  calling agent's assignment/mode via an lcp-server internal endpoint), because
  MCP servers are built per request without agent context.

### Storage tool policy (user-decided)

Agents keep the read-only general tools (`describe_server`, `describe_folder`,
`list_files`, `read_file`, `search_files`, `get_file_properties`,
`get_file_summary`). The general write tools (`write_file`, `delete_file`,
`restore_file`, `copy_file`, `move_file`) are removed from agent exposure and
replaced by assignment-scoped working-file tools (010.01.09).

### Knowledge change detection (user-decided)

Two layers: (1) a hook in lcp-server's `StorageService` on writes/deletes/restores
under `knowledge/*` (the fast path — all lcp-server-mediated changes, user or
agent); (2) a reconciliation poller (repeatable BullMQ job, default 60 s) that
fingerprints each scope's MinIO listing and rebuilds on drift — this catches
edits made directly in the MinIO web console. Rebuilds are per scope
(company+role or company+shared) with a generation counter giving
restart-on-change semantics.

### CLI (user-decided)

- New knowledge verbs `list-knowledge` / `get-knowledge` / `store-knowledge` /
  `delete-knowledge` replace `store-role-documents` / `list-role-documents` /
  `remove-role-documents`.
- `upload-shared-document` / `download-shared-document` / `validate-shared-document`
  are **kept**.
- New task verbs: `create-task`, `list-tasks`, `get-task`. Cancellation is
  future work.

## Deliberate deviations from 010.01.00 / 010.01.01

Recorded so the source prompts don't need editing:

1. Naming normalised: `lcp-mcp-tasks` (not `lcp-mcp-assignment`), snake_case
   tool names, `create_plan` (not `create-plan`), artifact union names as above.
2. `assignment-materials-path` dropped (stale draft type).
3. Task status gains `planning`.
4. Mode prompt augments (not replaces) the system prompt.
5. Mode prompt text is defined once in `@lcp/shared` rather than served by
   lcp-mcp-tasks over HTTP.
6. Orphan assignments get a working directory (`{company_slug}/assignments/{id}/working/`).
7. Mode is a column on `LcpAssignment` only; `LcpAgent` links to its assignment
   and derives the mode (the prompt allowed either copy-or-derive).
8. Existing knowledge files/chunks are not migrated to the new slug-based paths:
   the migration truncates `knowledge_chunk` and existing MinIO knowledge files
   must be re-uploaded (per 010.01.01's "migrations may destroy data").
9. QA reject resumes the same (paused) implementing agent rather than creating
   a fresh agent per attempt.

## Deferred (out of scope for all sub-plans)

- Task/assignment cancellation endpoint (and halting a running agent on cancel).
- Plan review/revision by agents; DAG-shaped plans (extension point left).
- Per-item QA agent loops.
- Finalisation beyond "copy all assignment `completed/` files to the task's
  `completed/` directory".
- MinIO bucket-notification-based change detection (poller chosen instead).
