# Doc-Type Validations & Storage Centralization — LCP

## Context

`docs/prompts/009.02.00.prompt - common document type validations.md` asks for two intertwined workstreams:

1. **Storage centralization/DRY-up**: today two independent, inconsistently-configured S3 clients exist — `apps/lcp-server/src/storage/minio.service.ts` (`MinioService`, env `MINIO_ENDPOINT`/`MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY`/`MINIO_BUCKET_PREFIX`, default bucket `lcp`, hard-delete) and `apps/lcp-mcp-storage/src/mcp/storage-tools.service.ts` (`StorageToolsService`, env `MINIO_BUCKET` with different defaults `minioadmin`/`http://localhost:9000`, soft-delete via `_deleted/` prefix). Neither is a general storage abstraction — both are concrete S3/MinIO clients wired directly into business logic, which blocks future storage backends (e.g. Google Drive) and duplicates path-validation, glob-matching, content-summarization, and not-found-detection logic. Audit attribution for storage actions today is also fake: `storage-tools.service.ts`'s `emitAudit` always uses a nil-UUID placeholder `companyId` and `agentId: null`, regardless of who actually invoked the tool.
2. **Write-time document validation**: there is currently **no validation of any kind** on documents written to shared storage — any bytes an agent or user sends via `write_file`/`POST /api/storage`/`POST /api/role/:roleId/documents` are accepted verbatim. This is a real quality/safety gap for OKF knowledge documents (malformed front-matter silently corrupts RAG ingestion) and for any structured config-like documents agents might write.

This plan sequences both workstreams together because the natural enforcement point for validation (`StorageService`, one abstraction) is also the artifact of the centralization work — building validation against the two existing scattered clients would mean implementing it twice and then deleting one copy.

Two additional per-format decisions come along for free once centralization happens: (a) originators (`user`/`agent`/`task`) become trackable in one place instead of two, since only one service will ever touch S3; (b) health-check pings can be trimmed to the app(s) that actually still talk to storage.

**Decisions confirmed with the user before writing this plan** (see full risk list below for the reasoning behind each):

- All 5 new validation dependencies are approved: `js-yaml` (5.2.1), `ajv` (8.20.0), `ajv-formats` (3.0.1), `fast-xml-parser` (5.9.3), `csv-parse` (7.0.1) — all MIT-licensed, all with releases in the last two weeks as of 2026-07-07, no red flags found. If any single one turns out to be unsuitable at implementation time (e.g. an unexpected transitive vuln), it becomes a no-op matcher for that format instead of blocking the rest of the pass.
- Delete semantics are **unified to soft-delete everywhere**, including `deleteKnowledgeFile` (today hard-delete). This is deliberate groundwork for `docs/prompts/010.02.00`'s planned RAG-consistency work, where restoring a knowledge file should trigger re-chunking/re-embedding — a hard-deleted file can never support that; a soft-deleted one can.

## Risks / flags surfaced during planning

Recorded for visibility even though the two biggest open questions (deps, delete semantics) are now resolved above.

1. **Soft-delete unification changes `RoleDocumentService.deleteDocuments`'s contract.** Today it hard-deletes via `MinioService.deleteKnowledgeFile` and simultaneously removes RAG chunks. After unification, the storage side becomes soft-delete (recoverable), but RAG-chunk removal still happens immediately at delete time (unchanged) — meaning between a delete and a hypothetical future restore, there's a window where the file is recoverable but its chunks are gone until 010.02.00's re-indexing work exists. Mark the restore path with an explicit intervention comment (see Phase 4) so 010.02.00 has an obvious hook rather than needing to rediscover this gap.
2. **JSON-Schema `$schema` resolution must not fetch arbitrary URLs — detailed threat model.**
   - **What could actually happen**: `lcp-server` runs inside the Docker Compose network and (in a real deployment) potentially on cloud infrastructure. If `validateDocument` fetched whatever URL a document's `$schema`/`$ref` field named, an attacker (a malicious user, or a compromised/adversarially-prompted agent — the whole point of MCP tools is that an LLM can write arbitrary content) could point it at: (a) **internal-only services** reachable from lcp-server's network position but not from outside (MinIO's admin API, Postgres, Keycloak's admin endpoints) — classic SSRF, using lcp-server as a confused deputy to probe/reach things the actual caller couldn't reach directly; (b) **cloud instance-metadata endpoints** (e.g. `http://169.254.169.254/...` on AWS/GCP) if ever deployed there — the textbook SSRF-to-credential-theft chain; (c) **denial of service** via a slow-loris/infinite-response endpoint, tying up a request (and, without a timeout, potentially a worker) per write; (d) **data exfiltration via the error channel** — if a fetched-but-invalid "schema" response body ever leaked into `errors[].llmHint` (which is deliberately sent back to the calling agent to be actionable), that could echo internal-service response data back out through a channel nobody was watching for exfiltration.
   - **Could it be protected against?** Yes, in principle, with real engineering effort: an exact-URL allow-list (not domain-based — path-based bypasses are common), resolved through an SSRF-safe fetcher that blocks RFC1918/loopback/link-local ranges _after_ DNS resolution (not just string-matching the URL, since DNS rebinding defeats that), a hard timeout + response-size cap, and never following redirects. That's a meaningful chunk of security-sensitive infrastructure to build and maintain for a feature whose primary ask was "validate documents," so it's disproportionate for v1.
   - **Is there a trusted public allow-list already?** Not one that helps here. `json-schema.org`'s own meta-schema URLs (`.../draft-07/schema`, `.../2020-12/schema`, etc.) are the closest thing to "trusted," but they're identifiers for _which JSON Schema spec version a document targets_ — Ajv already bundles all of these locally (no network call needed to recognize and use one). There is no broader trusted registry of arbitrary third-party/company schemas that would be safe to auto-fetch from; that's exactly why real remote-schema support would need a per-deployment, operator-configured allow-list, not a general list anyone could point at.
   - **Recommendation for v1 (what this plan implements)**: `$schema` is resolved **only** when it's (a) a relative/local path — resolved against the same shared-storage namespace the document itself lives in, so it's under the same access control as the document being validated, or (b) a recognized `json-schema.org` meta-schema URL string — pattern-matched to pick the Ajv dialect, **never dereferenced over the network** (Ajv's bundled copy is used). Any other absolute URL is treated as "schema not resolvable" — the file still gets structural JSON-syntax validation, just not schema validation, and this is called out explicitly in the `llmHint` so it doesn't look like a silent skip. Remote, operator-allow-listed schema fetching is left as a clearly marked future intervention point in `json-validator.ts` (`// TODO(remote-schema): would need an SSRF-safe fetcher + operator allow-list, see docs/prompts/009.02.01 §Risks — deliberately not built for v1`), not implemented now.
3. **XML/CSV have weak "self-describing schema location" conventions.** Unlike JSON (`$schema` keyword) and YAML/OKF (front-matter), XML's schema-location convention (`xsi:noNamespaceSchemaLocation`/DTD) and CSV (no standard schema-in-file convention at all — CSVW exists but is niche and unseen anywhere in this codebase) don't have a low-risk local-resolution story. **v1 ships well-formedness checks only for XML and CSV**, with each validator explicitly commented `// TODO(schema-validation): ... intentionally deferred, see docs/prompts/009.02.01 §Risks` — shaped but not implemented, per the user's explicit allowance.
4. **OKF-vs-plain-Markdown dispatch must be path-aware, not extension-only.** Both are `.md`. OKF is defined by _destination_ (`{company}/knowledge/{role}/*.md`, written only via `RoleDocumentController`/`RoleDocumentService`). The validator registry's dispatch needs to accept an optional write-context (destination path pattern), not just a filename/extension — a naive extension-keyed registry would silently misclassify every OKF file as plain Markdown.
5. **`originators.user` stays `null` for all agent/MCP-initiated storage calls in this pass.** No mechanism exists today to trace an MCP tool call back to the human who ultimately requested the task (`McpToolContext` only carries `agentId`/`companyId`; `jwt.strategy.ts`'s `req.user` stopgap is a separate, JWT-only path used solely by direct human/CLI calls through `StorageProxyController`/`RoleDocumentController`). `originators.user` is populated **only** for those two JWT-guarded controllers (from `req.user.sub`), and stays `null` for every MCP-tool-initiated call — matches what the user said was acceptable. `originators.task` stays `null` everywhere (no task concept exists yet).
6. **The nil-UUID audit placeholder in `storage-tools.service.ts` is a live, silently-swallowed bug today, not just a placeholder to replace.** Confirmed directly: `AuditEvent.company` is `@ManyToOne(() => LcpCompany, { nullable: false, onDelete: 'CASCADE' })` — a real FK, not just a UUID column — and no `lcp_company` row with id `00000000-0000-0000-0000-000000000000` exists anywhere. `AuditClientService.record()` is fire-and-forget over HTTP (`axios.post(...).catch(err => logger.warn(...))` — confirmed by reading the file) so the resulting FK-violation 500 from `POST /internal/audit` is caught and merely logged as a warning. **Every `write_file`/`delete_file`/`restore_file`/`copy_file`/`move_file` audit call today almost certainly fails against the DB and is silently swallowed** — no storage audit trail exists in the DB today despite the code appearing to write one. This pass's originators work must not just add richer `payload` fields on top of a still-broken write — it needs to either (a) resolve a real `companyId` before writing (from the MCP context once wired, see #7) or (b) skip the audit call entirely (with a visible `logger.warn`) when no real company can be resolved, rather than perpetuate a silently-failing insert.
7. **Storage MCP tools currently declare no `agentId`/`companyId` in their tool schemas at all.** `McpClientService`'s `McpToolContext` → `fixedArgs` injection (the existing "who is the agent" plumbing) is a no-op for storage tools today because none of `write_file`/`delete_file`/`restore_file`/`copy_file`/`move_file`'s `inputSchema`s declare those keys. Getting real `originators.agent` requires adding `agentId`/`companyId` fields to those tool schemas (mirroring `interactions-tools.service.ts`'s existing pattern exactly) — call this out as a concrete implementation task in the MCP-proxy phase, not a given.
8. **`InternalApiKeyGuard` is duplicated verbatim** between `apps/lcp-server/src/audit/internal-api-key.guard.ts` and a private class inside `apps/lcp-mcp-storage/src/mcp/storage-check.controller.ts`. Since this plan adds several _new_ internal-API-key-guarded endpoints on lcp-server, promote the guard to `libs/lcp-shared` now rather than writing a third copy.
9. **The CLI's "return 404/500/200" requirement, read literally, doesn't map onto OS process exit codes.** Interpret this as describing **the new lcp-server endpoint's HTTP response codes**, with the CLI verb behaving like every other verb today: `apiRequest` throws on non-2xx (existing behavior), `runCommand` catches and exits 1, and a 2xx response (even one whose body reports validation errors) prints JSON to stdout and exits 0.
10. **Confirmed, no action needed**: `apps/lcp-cli`'s `open-document-store.action.ts` only reads `MINIO_CONSOLE_URL` to print/open a browser link — out of scope. `apps/lcp-agent`'s `config.schema.ts` requires `MINIO_ENDPOINT`/`MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` as env vars but lcp-agent never constructs an `S3Client` anywhere (grep-confirmed) — dead required config, likely leftover from an earlier design. Not fixed in this pass; noted for Phase Z's docs sweep as an optional follow-up.
11. **No new TypeORM migration is expected** for this entire pass — `AuditEvent.payload` is already `jsonb` (free-form), so `originators` nests inside it with no schema change, and no new tables/columns are otherwise required. If implementation discovers an actual need for one, treat that as new scope requiring separate sign-off.

## Recommended execution order

Dependency-ordered; Phase 2 (validation) has no storage dependency and can be built alongside Phase 1, but Phase 3 (wiring) cannot start until both are done.

**-1. Pre-step (blocking, do first): fix the currently-failing API test suite, and the tooling gap that let it pass locally.**

- **The fixture bug**: `test/api/api.spec.ts` fails in CI today, unrelated to this plan — confirmed root cause: `test/api/helpers/ApiHelper.ts`'s `createTestRole()` (line ~119-140) POSTs to `/api/role` without a `slug` field. `CreateRoleDto.slug` (`apps/lcp-server/src/api/dto/role.dto.ts:19`) is required (`slug!: string`, no `@IsOptional()`), so the request now 400s on validation — this is the exact "required column breaks every hand-written fixture" bug class from `docs/prompts/009.01.01` Phase Z (see `feedback-manual-migration-registration.md` in project memory), just in a fixture the 009.01.01 sweep didn't catch (`test/api/**` wasn't in its grep list). The failure cascades: role creation fails → every subsequent test depending on a created role (`PUT /api/role/:id`, `GET /api/company/:id/roles`, `POST /api/agent/chat/start`, `DELETE /api/agent/:id`) fails too, since they all depend on `createTestRole()`'s return value. Fix: add a `slug` (e.g. `'test-role'`) to `createTestRole`'s request body, then re-run `test/api/api.spec.ts` in isolation to confirm all 8 tests pass.
- **Why it passed locally but failed in CI (confirmed, not just theorized)**: `scripts/run-all-tests.sh`'s API-test step calls `start-deployment.sh` **without** `--rebuild` (`run-all-tests.sh:119-121`), and `start-deployment.sh` only runs `docker compose up -d --build` when that flag is passed — otherwise it's a plain `docker compose up -d` (`start-deployment.sh:114-117`), which reuses whatever image is already tagged for that Compose project. The `docker system prune -f` step immediately before it (`run-all-tests.sh:112`) doesn't help — plain `prune` only removes dangling/untagged images, never a tagged image still referenced by a project. So on a developer machine with a pre-existing `lcp-api`-project image built before `LcpRole.slug` became required, `run-all-tests.sh` silently starts that **stale server binary** — pre-slug-requirement — against which the under-specified fixture happens to pass. CI has no such leftover image, builds fresh, runs current code, and gets the real (correct) 400. The fixture bug is real in both environments; only the masking is local-only.
- **The tooling fix**: update `scripts/run-all-tests.sh`'s API/smoke deployment step to always pass `--rebuild` to `start-deployment.sh` (`run-all-tests.sh:119-121`), so a full local `run-all-tests.sh` run can never again silently validate against a stale image — trading a slower local run (one Docker rebuild) for a trustworthy pass/fail signal, which is the entire point of the script. Document the change in `docs/development.md`'s existing testing-conventions notes if that script's behavior is described there.
- Do all of this before Phase 0 — it's an unrelated, pre-existing regression plus a masking gap in the test tooling, not part of this plan's actual scope, but both must be fixed first so every subsequent phase's `./scripts/run-all-tests.sh` run gives a signal that's actually trustworthy.

> **Implementation note (resolved during the pre-step)**: fixing the fixture surfaced a second, related issue — `test/api/api.spec.ts` calls `createTestRole()` twice with the identical `name` under the same company (once in a top-level `it`, once in a nested `beforeAll`). Setting `slug` equal to `name` verbatim made the second call collide on the per-company-unique `(companyId, slug)` index, and the **role-creation endpoint returned a raw 500 instead of a proper 409/400 on a duplicate-slug conflict** — an unhandled DB constraint violation. Fixed in the fixture by deriving a unique slug per call (`${name}-${randomUUID().slice(0, 8)}`) rather than reusing `name`. The underlying "duplicate slug 500s instead of returning a proper conflict response" behavior in `RoleController`/`DbService.setRole` was **not** fixed — it's a real, separate quality gap outside this plan's scope, noted here so it isn't lost.

## Phase 3 — Write-path wiring: validation gates writes, `originators` threaded through, audit bug fixed

- `MinioStorageAdapter.putByKey`/`putKnowledgeFile`/`writeFile` all route through a private `validateBeforeWrite(path, content): Promise<void>` calling `validateDocument`, throwing `DocumentValidationException` (extends `BadRequestException`, **422 Unprocessable Entity** — the request is well-formed, the payload content is rejected) carrying the structured `ValidationError[]`.
- `storage-proxy.controller.ts`'s `upload()` and `role-document.controller.ts`/`role-document.service.ts`'s `storeDocument()` surface `DocumentValidationException` as `{ statusCode: 422, message: 'Document failed validation', errors: ValidationError[] }` (check whether lcp-server has a global exception filter at implementation time; a local try/catch per controller is sufficient if not — don't add a new global filter just for this).

- **Tests**: 422-on-invalid-content cases for both controllers; `minio-storage.adapter.spec.ts` cases for `validateBeforeWrite` (valid passes, invalid throws with populated `errors`); audit-skip-when-unresolvable-company case.
- **Docs**: `docs/shared-storage.md` — new "Write validation" section describing the 422 shape and that `errors[].llmHint` is meant to be relayed into the calling agent's context; `docs/database.md` or `docs/schema.md` — document the `originators` convention now appearing inside `audit_event.payload`.

## Phase 7 — Standalone validation path: endpoint + `validate-shared-document` CLI verb

- New `apps/lcp-server/src/api/storage-validation.controller.ts` (separate from `storage-actions.controller.ts` since this is JWT-guarded human/CLI-facing, not internal-key-guarded): `@UseGuards(JwtAuthGuard)`, `@Controller('api/storage/validate')`.
  - `POST /api/storage/validate` `{ path: string; recursive?: boolean }` →
    ```ts
    {
      query: { path: string; recursive: boolean };
      validations: { path: string; found: boolean; size: number; valid: boolean; errors: string[] }[],
    }
    ```
  - Path resolution: glob characters (`*`/`?`) → expand via `listFiles`/`searchFiles` (reuse `globToRegex`); a specific key with no glob chars → check existence directly.
  - **404** (real `NotFoundException`, not embedded in the 200 body) only when the caller's `path` has **no glob characters at all** — i.e. it's asserting a specific file/directory must exist. Any path containing `*`/`?` is always treated as "search," never 404s on zero matches (per the explicit requirement that a glob matching zero files is still a success).
  - **500** for genuinely unexpected errors (S3 connectivity, etc.) — let Nest's default exception handling produce this.
  - **200** otherwise; `validations[].errors` are `llmHint` strings flattened to plain strings (per the requested output shape, not the full `ValidationError` objects).
- New lcp-cli verb (existing 3-layer convention):
  - `apps/lcp-cli/src/commands/validate-shared-document.ts` — flags `--path <path>` (required), `--recursive`, `--json` (check `read-query.action.ts`'s existing `--json` convention for consistency).
  - `apps/lcp-cli/src/lib/storage/validate-shared-document.action.ts` — calls `apiRequest(opts, 'POST', '/api/storage/validate', { path, recursive })`; a 404/500 naturally becomes `runCommand`'s existing `Error: ...` + exit 1 (no new code needed); a 200 response prints and exits 0 **even if individual `validations[].valid` entries are `false`** — the action must not itself treat validation failures as a reason to exit non-zero.
  - Register in `apps/lcp-cli/src/main.ts`.
- **Tests**: `storage-validation.controller.spec.ts` (glob-zero-match-is-200, specific-missing-file-is-404, missing-directory-is-404, mixed valid/invalid results); `validate-shared-document.action.spec.ts`; new e2e `test/e2e/lcp-server/storage-validation.e2e-spec.ts` covering all three response codes against a running app with real MinIO.
- **Docs**: `docs/lcp-cli.md` — new verb section (flags, example output, exit-code semantics per Risk #9); `docs/shared-storage.md` — why this endpoint exists independently of write-time validation (direct-to-MinIO bypass protection).
