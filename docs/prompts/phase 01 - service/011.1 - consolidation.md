## Graceful and forced shutdown

It would be good to be able to run an orderly shutdown that doesn't break running tasks or waste tokens by quitting before currently running LLM work completes, ie.

1. a user initiates a shutdown through lcp-cli, which calls the lcp-server API
2. the shutdown is suspended until all running tasks have paused
3. each running task pauses at the next resumable point (ie. after the LLM next responds)

Similarly, it would be good to be able to force an immediate shutdown, ie.

1. a user initiates a shutdown through lcp-cli, which calls the lcp-server API
2. lcp-server and lcp-agent halt any running LLM work, pause any running agents, and halt

The default would be graceful. Examples of shutdown commands:

```
./lcp-cli.sh shutdown
./lcp-cli.sh shutdown --force
```

(If you're aware of a better or more conventional structure for this, please recommend it.)

## Code quality improvements

There are a variety of ways to discover opportunities for improvement, listed below. For each, perform the discovery as a part of the planning exercise, and write recommendations into the sub-plan.

### Discovery (aislop)

Re-run the aislop tool, and look for issues that we've left outstanding because we've been 'forgiving' of ourselves, or have left to later because they weren't in scope for the work we were doing.

Non-controversial issues can be dealt with directly, for example:

- `File too large (max: 400)`
- `Function too long (max: 80)`

For size limits find ways to break out functions and move support functions into supporting files. Use this to help make the code clearer.

For issues that conflict with our coding standards (eg. we comment our code wherever possible, and we use the comments to describe intent), follow coding standards.

### Discovery (memory)

Have we recorded memories of issues to return to? If so, list them out and offer means of addressing them.

### Discovery (code review)

Review the code base at large. Go into depth. Look for opportunities to make improvements:

- Where code can be made clearer by deduplicating, and offering shared code or a shared service in lcp-shared, even if it's only used twice, it's worth it
- Where code can be made more readable by breaking out named functions from tracts of code, it's worth it
- Where functions contain a bunch of special cases, break out special case handling into separate logic
- Where business logic (ie. key behavioural code) can be broken out, making it easier to find, and easier to understand, it's worth doing - aim for readability again (clear function names, clear decision making functions)
