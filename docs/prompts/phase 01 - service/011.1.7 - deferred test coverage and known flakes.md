## Unit 0 — Integration-tier schema ownership

**The defect.** Six integration specs build the shared tier database with TypeORM
`synchronize: true`. That leaves it carrying TypeORM's auto-generated constraint
names rather than the migrations' hand-written ones, so any spec that later boots
a real `AppModule` (which runs migrations on startup) fails its baseline migration
with `relation "tcp_company" already exists`.

Nothing enforces the ordering that currently avoids this. Jest's default sequencer
orders by cached timing data, so it varies between machines and between runs.
Adding a single spec file in 011.1.6 flipped it and broke `task-flow`.

**`task-flow`'s isolation does not work — do not trust its comment.** It makes a
`task_flow_<pid>` database and sets `process.env.DATABASE_URL` in `beforeAll`, but
`ConfigModule.forRoot()` snapshots the environment when `app.module.ts` is
**imported** — at the top of the spec file, long before `beforeAll` runs. So
`TcpServerAppModule` migrates the **shared** database regardless. This was
confirmed empirically during 011.1.6: the throwaway database is still empty at the
moment the migration fails against the shared one. The spec passes only when it
runs before anything that has synchronised.

Three isolation techniques already exist in this one tier, each invented
independently — which is the clearest sign the tier needs a single answer:

| Spec              | Technique                                               | Works?                        |
| ----------------- | ------------------------------------------------------- | ----------------------------- |
| `baseline-schema` | dedicated Postgres **schema** (`baseline_verification`) | yes                           |
| `shutdown-drain`  | throwaway **database**, URL passed explicitly           | yes                           |
| `task-flow`       | throwaway **database**, via `process.env`               | **no**                        |
| six others        | `synchronize: true` onto the shared `public` schema     | n/a — these are the polluters |

### Preferred fix: migrate once in `globalSetup`, as the e2e tier already does

`test/e2e/global-setup.ts` already runs `MIGRATIONS` against the shared database
once, before any spec — see the comment there about tcp-server being the sole
migration owner. Do the same in `test/integration/global-setup.ts`, then remove
`synchronize: true` from every integration spec.

This deletes the whole class rather than working around it: no spec owns the
schema, so no spec can corrupt it for another, and `task-flow` no longer needs a
throwaway database at all. It should be a mostly-deletion change.

**The thing that could push you off this path:** the specs register entity
_subsets_ (the tcp-agent ones register five entities), whereas migrations create
every table. Extra tables are harmless in principle, but check each spec before
assuming it. If one genuinely depends on a partial schema, say so rather than
bending the tier around it.

**Fallback:** extract a `withThrowawayDatabase()` helper into `test/support/` and
route the affected specs through it, following `shutdown-drain`'s shape (create
and drop the database, pass its URL **explicitly** to `TypeOrmModule.forRoot` —
never via `process.env`). Strictly worse: it keeps the pattern and repeats the
boilerplate in every spec. Take it only if the preferred fix is genuinely blocked.

> [!WARNING]
> Do **not** "fix" this by renaming spec files, pinning a custom `testSequencer`,
> or otherwise making a particular order load-bearing. The ordering is incidental;
> depending on it is the defect, not the cure.

### Verification is structural, not empirical

"The tier passes" is not evidence here — you cannot easily force an adversarial
order, and the current order already passes. The check that means something is
that **no spec points a `synchronize: true` config at the ambient `DATABASE_URL`**.
Grep for it and confirm zero hits. Then run the tier three times per this
sub-plan's rule, and `run-all-tests.sh` once.

### While you are there

`baseline-schema.integration-spec.ts` uses a dedicated Postgres schema
specifically to dodge the polluted `public` one — its comment says so. Once the
tier is migration-built, check whether that workaround is still earning its keep
or can be simplified. Don't remove it speculatively; it is also testing that the
baseline applies to an _empty_ schema, which is a separate and legitimate reason
to isolate.

`test/integration/tcp-agent/task-flow.integration-spec.ts`,

## Unit 1 — Consultation-cycle integration test

The `waitForAgentCompletion` Redis pub/sub path and its race-condition polling
fallback have **no automated coverage**. The only way a regression surfaces today
is during manual testing with `manual-verify.sh` — and one race-condition bug (a
blank response when a fast local LLM completed before the subscriber was set up)
has already been found there and diagnosed by hand.

This is execution, not design — the design was worked out when the test was
deferred. Test the full cycle:

1. The calling agent's `ChatService.sendMessage()` runs; a `FakeListChatModel`
   returns a `request_agent_consultation` tool call.
2. The MCP tool fires `POST /internal/pause` → the agent goes `Paused`, and the
   consulted agent's BullMQ job is dispatched.
3. `waitForAgentCompletion` subscribes to Redis.
4. The consulted agent's `AgentLoopService.run()` fires with its own
   `FakeListChatModel`, returns a response, and completes its assignment.
5. `resumeAgent(callerId)` dispatches the caller's resume job.
6. The caller's resume run produces the real answer → `publishCompletion` fires.
7. `waitForAgentCompletion` resolves with the correct content — **not blank**.

**Also cover the race-condition path explicitly:** publish fires _before_ subscribe,
and the poll loop finds `agent.output` in the database.

What it needs:

- Real Redis — already in the integration Docker stack.
- Real BullMQ workers in-process, following `agent-worker.integration-spec.ts`.
- SQLite for the DB, as integration tests already do.
- Either a real tcp-mcp-interactions server, or a mock of the MCP tool's HTTP call
  to `/internal/pause` returning "Paused. Consultation dispatched."
- Two `FakeListChatModel` instances, one per agent, each wired to the appropriate
  `AgentLoopService` run.

Best home: a new file beside
`test/integration/tcp-agent/agent-loop.integration-spec.ts`, or an extension of
`test/e2e/tcp-mcp-interactions/cross-service.e2e-spec.ts`, which already starts
both tcp-server and the interactions MCP server.

Relevant files: `apps/tcp-server/src/api/chat.service.ts`
(`waitForAgentCompletion`, the polling loop), `apps/tcp-agent/src/agent/agent-loop.service.ts`
(`publishCompletion`), `apps/tcp-server/src/api/agent-orchestration.service.ts`
(`resumeAgent`).

**Gate:** `./dev-environment/scripts/check.sh` + `./scripts/run-integration-tests.sh`,
run three times to confirm the new test is not itself flaky.

## Unit 2 — e2e JWT flake investigation (time-boxed)

> [!IMPORTANT]
> **Budget: stop and report after a focused investigation.** This is a
> single-occurrence, non-reproducing flake. If you have not found a root cause
> within the budget, write up what you ruled out and stop. Do not let this unit
> block the others — it can be skipped entirely without affecting them.

**Symptom.** `KnowledgeController (e2e) > reindex > POST
/api/company/:companyId/knowledge/reindex returns 404 for an unknown company`
returned **401** instead of 404. Seen only inside a full `./scripts/run-all-tests.sh`
run; two immediate isolated re-runs passed cleanly. The test is pre-existing and
was not modified by the work in progress at the time.

**Already ruled out by reading the code — do not redo this work:**

- `test/e2e/__mocks__/jwks-rsa.ts` is fully synchronous and stateless
  (`done(null, 'stub-secret')`) — no cache, no rate limit, no async delay, so it
  cannot explain a timing-dependent race.
- No e2e spec mutates `OIDC_ISSUER_URL`/`OIDC_CLIENT_ID` at runtime;
  `test/e2e/e2e-setup.ts` only sets `OIDC_JWKS_URI`/`TCP_STORAGE_URL`, both with
  `||=`. `makeTestJwt()`'s `iss`/`aud` claims are identical across every call.
- `makeTestJwt()`'s `exp` window is 3600s — not an expiry race.

**Leading theory (unconfirmed).** `test/jest-e2e.json` sets `maxWorkers: 1`, so all
22 e2e spec files run sequentially in one Node process, each building and tearing
down a full Nest `TestingModule`/`AppModule`. Under `run-all-tests.sh` the e2e tier
runs after the unit and integration tiers have already loaded the Docker daemon and
CPU, so it is under far heavier sustained contention than a standalone run.
Best guess: a construction-order or timing hazard in Nest's Passport/`JwtStrategy`
bootstrap for one app instance, surfacing only under real contention.

**One data point from Unit 0.** Another member of this class — order-dependent
failures under a full run — has now been root-caused: shared-database schema
ownership in the integration tier. It is _not_ a shared cause with this flake
(different tier, different mechanism), but it does show that these failures can
be real, structural, and findable rather than cosmic rays. Treat that as a reason
to look properly, not as a lead.

**Recorded approach:** temporarily instrument `JwtStrategy`/`JwtAuthGuard` to log
the raw token and the verification error on failure, then run the full e2e suite
(all 22 files, `maxWorkers: 1`) back-to-back several times **without** the preceding
unit and integration tiers. That isolates whether cross-file sequencing alone
triggers it, or whether it genuinely needs the extra CPU pressure.

**Related observations (same class).** On 2026-07-24 a single `run-e2e-tests.sh`
showed two failures — `task.e2e-spec.ts`'s cancel-cascade test (a `beforeEach`
`POST /api/task` returned an empty body, so `task.id` was `undefined`) and
`knowledge.e2e-spec.ts`'s role-scope round-trip (DELETE got 400). An immediate
clean re-run passed 196/196. **Rule of thumb: a reproducing failure in these is
real; a one-off is this flake class.**

Acceptable outcomes, in preference order:

1. Root cause found and fixed.
2. Root cause not found, but a mitigation identified (e.g. an ordering or setup
   fix that removes the hazard) — propose it, do not apply speculative changes.
3. Neither — write up what was ruled out and recommend whether to keep tolerating it.

**Remove all temporary instrumentation before finishing.**

**Gate:** `./dev-environment/scripts/check.sh`; no instrumentation left behind.

## Unit 3 — Test tier for `tcp-mcp-tasks`

`tcp-mcp-tasks` has **unit and smoke tests only**. The other three MCP servers each
have an integration/e2e testcontainers tier. ADR-016 records this in its
"Outstanding" column.

Add a tier matching the existing pattern — look at
`test/e2e/tcp-mcp-interactions/` and `test/e2e/tcp-mcp-memory/` for the shape, and
follow the repo's test-structure convention: nested `describe` blocks where each
level's `beforeAll` creates its own fixtures, no borrowing state between sibling
`it`s, and an api token shared downward from a parent `beforeAll` only.

Cover the three mode-gated tools and their state transitions:

- `create_plan` — plan mode only; validation of expected/material artifacts.
- `complete_assignment` — implement/finalise modes; the artifact canonicalisation
  and output-gate paths.
- `assure_assignment` — qa mode only; accept advances, reject retries up to
  `runConfig.maxQaAttempts`.
- Mode gating itself: calling a tool from the wrong mode is refused.
- The 4xx relay path — a validation failure comes back as a **readable message the
  model can self-correct from**, not an exception.

**Note the dependency:** if **011.1.3** has landed, `tcp-mcp-tasks` now uses the
shared tool-result kit and internal API client. Write the tests against the
current shape, not the historical one.

Wire the new tier into `scripts/run-e2e-tests.sh` (or integration, per where it
belongs) and confirm `./scripts/run-all-tests.sh` picks it up.

**Gate:** `./dev-environment/scripts/check.sh` + `./scripts/run-all-tests.sh`.

## Code quality requirements

Route via `AGENTS.md` → `dev-environment/guidance/index.md`; read
`process/before-coding.md` first, `standards/testing.md` (directly relevant), and
`process/after-coding.md` when done. State the filename of each guidance doc you read.

- **After every unit**, run `./dev-environment/scripts/check.sh` and fix what it
  reports before starting the next. Never bypass a hook with `--no-verify`.
- Zero compiler and linter **errors and warnings**.
- **Never cast to `any`, especially in test mocks — type the mock instead.** This
  is the single most-repeated failure mode in test code.
- Test the **intent**, not line coverage. Cover edge cases and failure paths, not
  just the happy path.
- Test structure: nested `describe` blocks; each level's `beforeAll` creates its own
  fixtures; no sibling-`it` state borrowing; api token shared downward from a
  parent `beforeAll` only.
- Unit tests use in-memory SQLite and wire TypeORM directly via
  `Test.createTestingModule` — never through `AppModule`.
- **Every BullMQ `Queue`/`Worker` in a test needs an `.on('error')` handler.** An
  unhandled "Connection is closed" has previously crashed an unrelated e2e suite,
  because the suites share one `maxWorkers: 1` process. Unit 1 creates real workers,
  so this applies directly.
- Comments state **intent**, not mechanics; no decorative separator comments.
- New tests must not be flaky — run each new suite at least three times.
- Full suite via `./scripts/run-all-tests.sh`; e2e via `./scripts/run-e2e-tests.sh`,
  never bare `npm run test:e2e`.
- aislop is opinionated and can disagree with these standards. Where they conflict,
  **the documented standards win**.
