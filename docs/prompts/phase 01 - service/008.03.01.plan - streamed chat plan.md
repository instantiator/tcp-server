# Plan 008.03.01 — ADR-015 (amended) + streamed chat observability

## Context

`lcp-cli chat` currently blocks a long-poll POST for the whole LLM turn (up to 35 min) and shows nothing while the agent works — no state changes, no tool activity, no reasoning, and no visibility into consulted agents. ADR-015 (Proposed, unimplemented) proposed replacing the long-poll with SSE completion; prompt 008.03.00 goes further: full live observability (agent state, LLM activity, token-by-token reasoning and response) rendered in colour by the CLI, iterative follow of consulted agents, a stray-`>` prompt bug fix, and manual-verify script cosmetics.

**User decisions (binding):**

1. `POST /api/agent/:id/message` **always returns 202**; the turn runs detached and ALL output arrives via the existing SSE endpoint `GET /api/agent/:id/events`. The long-poll (`waitForAgentCompletion`) is deleted. ADR-015 updated to match.
2. **No `completionMessage` column** — recovery reuses existing `LcpAgent.output` + `status` via `GET /api/agent/:id`. No migration.
3. **Iterative follow**: the caller's SSE stream emits `consultation_started {agentId, roleName}`; the CLI opens additional (recursive) SSE streams to consulted agents, prefixing their lines with the role name.

**Key facts (verified):**

- lcp-agent's `streamAndAudit` ([agent-loop.service.ts:345-405](apps/lcp-agent/src/agent/agent-loop.service.ts#L345)) already iterates `graph.streamEvents(…, {version:'v2'})` and sees `on_chat_model_start/end`, `on_tool_start/end`. The model already streams under streamEvents v2 (the `AIMessageChunk` comment at :368-371 proves it) — `on_chat_model_stream` deltas exist, just unconsumed. Chunks carry `content` and `additional_kwargs.reasoning_content` (LM Studio supplies reasoning deltas; official OpenAI doesn't — degrade gracefully). Verify at implementation time that chunks carry `reasoning_content`; if only the final message does, fall back to emitting one `reasoning` event on `on_chat_model_end`.
- chat turns run **in-process in lcp-server** via `graph.invoke` ([chat.service.ts:248](apps/lcp-server/src/api/chat.service.ts#L248), non-streaming) — must switch to `streamEvents`.
- `AgentEventService` ([agent-event.service.ts](apps/lcp-server/src/events/agent-event.service.ts)) is an in-memory per-agent `Subject` bus feeding `@Sse(':id/events')` ([api.agent.controller.ts:122](apps/lcp-server/src/api/api.agent.controller.ts#L122)); its own `ponytail:` note (line 32) says "switch to Redis pub/sub".
- Only Redis channel today: `agent:completed:{agentId}` — publisher `publishCompletion` ([agent-loop.service.ts:695-711](apps/lcp-agent/src/agent/agent-loop.service.ts#L695)); sole subscriber `waitForAgentCompletion` ([chat.service.ts:346-434](apps/lcp-server/src/api/chat.service.ts#L346)). Both are deleted.
- No colour library in the CLI (commander + undici only) — use raw ANSI codes, no new dependency.

## Architecture

- **Vocabulary** shared in `libs/lcp-shared` (new `events/agent-events.ts`) — server, agent, and CLI use one union.
- **In-process producers** (chat.service, context-manager, pause-and-resume — all lcp-server) call `AgentEventService.emit()` directly, as today.
- **Out-of-process producer** (agent-loop in lcp-agent) publishes JSON events to Redis channel `agent:events:{agentId}` via a persistent-connection publisher service.
- **Relay**: `AgentEventService` lazily SUBSCRIBEs `agent:events:{agentId}` on one shared ioredis connection when the first SSE observer for that agent attaches (refcounted; unsubscribe on last detach) and re-emits into the existing per-agent Subject.
- **Terminal events originate in lcp-server**: `completeAgent`/`failAgent` (pause-and-resume.service) emit `completed`/`failed` in-process. `publishCompletion` and the `agent:completed:{agentId}` channel are retired.
- **Recovery**: the SSE endpoint synthesizes a terminal event for late subscribers from DB `status`+`output`; the CLI falls back to polling `GET /api/agent/:id` if its stream dies mid-turn.

### Event union (sketch)

```ts
// libs/lcp-shared/src/events/agent-events.ts
export type AgentEvent = { timestamp: string } & (
  | {
      kind: 'agent_status';
      data: { status: AgentStatus; reason?: string; conversationSlug?: string };
    }
  | {
      kind: 'llm';
      data: {
        activity:
          | 'request_started'
          | 'request_complete'
          | 'tool_started'
          | 'tool_complete';
        tool?: string;
      };
    }
  | { kind: 'reasoning'; data: { delta: string } }
  | { kind: 'response'; data: { delta: string } }
  | {
      kind: 'consultation_started';
      data: { agentId: string; roleName: string };
    }
  | {
      kind: 'completed';
      data: { response: string; compactionReport?: CompactionReport };
    }
  | { kind: 'failed'; data: { error: string } }
  | {
      kind: 'compaction_started' | 'compaction_complete';
      data?: Record<string, unknown>;
    } // payloads unchanged
);
export const agentEventsChannel = (agentId: string) =>
  `agent:events:${agentId}`;
```

`processing_started`/`processing_complete` are dropped (subsumed by `agent_status: running` / `completed`). Token deltas: one event per chunk, no coalescing (local Redis; YAGNI).

### Stray `>` root cause

`rl.prompt()` fires unconditionally at [chat.ts:295](apps/lcp-cli/src/commands/chat.ts#L295) the moment the POST resolves, while the 3-s-delayed SSE observer and cancellation paths can still write to stderr afterwards — readline's `> ` gets orphaned/duplicated. In the redesign all output flows through the turn's stream, streams close before the single `rl.prompt()` per turn, and no output source outlives the turn. Manual retest step goes in `docs/manual-testing/03-chat-agents.md` (one consultation turn + one Ctrl+C cancel; exactly one `>` after each).

## YAGNI — deliberately cut

- `completionMessage` column + migration (user decision).
- Token-delta coalescing over Redis — per chunk; revisit only if it measurably lags.
- SSE auto-reconnect with backoff — single poll-fallback instead.
- Sharing the whole streamEvents loop between chat.service and agent-loop — only the pure mapper is shared.
- `psubscribe` — plain per-channel `subscribe` on one connection.
- String back-compat for scenarios `checks`; SSE heartbeats; replay buffers beyond terminal-state synthesis.

## Risks

- Terminal events depend on fire-and-forget `notifyComplete`/`notifyFailed` HTTP reaching pause-and-resume; if lost, replay-on-subscribe + CLI poll fallback still terminate the turn (same exposure as today's DB-poll fallback).
- Duplicate `completed` events possible (live + replay merge) — CLI treats the first as terminal, ignores repeats.
- Reasoning deltas only on LM Studio; OpenAI path never emits `reasoning` events. If chunks turn out not to carry `reasoning_content`, emit one `reasoning` event from the final message on `on_chat_model_end` instead.

## As-built notes

Two non-obvious issues surfaced during implementation (both now fixed):

- **`streamEvents` forces the model to stream.** Under LangGraph `streamEvents`
  v2, LangChain sets `callbackHandlerPrefersStreaming`, so `boundModel.invoke()`
  streams under the hood. The integration `docker/stub-llm/server.js` had to be
  taught to emit OpenAI-style SSE when the request body has `stream:true`, or
  ChatOpenAI receives an empty response. (agent-loop integration was unaffected —
  it uses LangChain's `FakeListChatModel`, which streams natively.) The stub is
  built from a Dockerfile, so `docker compose … build stub-llm` is needed to pick
  up edits.
- **Don't double-provide `AgentEventService` in test modules.** `ContextModule`
  provides and exports it; the chat-llm integration test also listed it locally,
  creating two instances — ChatService emitted on one, the test observed the
  other, so the detached turn's `completed` event never arrived. Fixed by relying
  on the imported module's export. Production wiring (single instance via
  `ContextModule` import) was always correct.
