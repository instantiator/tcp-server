## Context

The parent prompt asks for two shutdown modes:

**Graceful** (the default) — a user runs `./tcp-cli.sh shutdown`, which calls the
API; the shutdown is suspended until all running tasks have paused; each running
task pauses at its next resumable point, i.e. after the LLM next responds. The
point is to avoid breaking running tasks or wasting tokens by quitting mid-call.

**Forced** — `./tcp-cli.sh shutdown --force`; running LLM work is halted
immediately, agents are paused, and the system stops.

## Design — read before implementing

> [!IMPORTANT]
>
> ## The API drains; the host wrapper halts
>
> The prompt says tcp-server and tcp-agent should "halt". Two facts change how:
>
> 1. **Every Docker Compose service is `restart: unless-stopped`.** A process that
>    calls `process.exit()` is restarted by Docker seconds later. In-process
>    suicide does not achieve a halt — it achieves a bounce.
> 2. **`tcp-cli.sh` runs on the host and already shells out to `docker compose`**
>    (it runs `docker compose -p tcp-dev up -d` to sync env vars), and
>    `scripts/stop-dev.sh` already exists.
>
> So: the **API owns draining** — the genuinely hard, valuable part — and the
> **host wrapper owns halting**, via `docker compose stop`, which stops containers
> and leaves them stopped. Do not build process-suicide logic that fights the
> restart policy.
>
> Draining must still work when the stack is _not_ under Docker (a bare
> `npm run start:dev`), where the operator stops the process themselves. The API
> contract is the same either way.

### Decisions to make in Unit 0 — do not guess

1. **How does tcp-agent learn that a drain has started?**
   The recommended answer is **it doesn't need a new channel for graceful mode**:
   tcp-server marks running agents `Paused`, and the agent loop's existing
   `checkTerminalStatus` poll notices at the next boundary and exits cleanly with
   its LangGraph `PostgresSaver` checkpoint intact. That is the whole graceful
   mechanism, and it reuses a proven path.
   **Forced mode does need a channel**, because aborting an in-flight LLM call
   requires reaching the `AbortController`s that live in tcp-agent's memory.
   Establish whether an tcp-server → tcp-agent path exists today (dispatch is via
   BullMQ; MCP servers call _into_ tcp-server, not the reverse). If none exists,
   the two candidates are a Redis pub/sub message (the codebase already uses Redis
   pub/sub for agent events) or a new internal endpoint on tcp-agent guarded by
   `InternalApiKeyGuard`. **Prefer Redis pub/sub** — it needs no new service-to-service
   URL configuration and matches how completion events already travel.

2. **How is a shutdown-pause distinguished from an input-pause?**
   `AgentStatus.Paused` currently means "waiting for user input or a consultation",
   and `resumeAgent` gates on zero outstanding consultations. A shutdown-paused
   agent has none, so it would look resumable.
   Recommended: add a **nullable `pauseReason` column** rather than a new
   `AgentStatus` value. A new enum value would force updates to every exhaustive
   status check across the codebase (and the CLI's renderers) for no gain, whereas
   a reason column is additive and gives the CLI something useful to display.
   Confirm with the user.

3. **What happens on restart — auto-resume, or stay paused?**
   Recommended: **stay paused.** Auto-resuming on boot would burn tokens the moment
   someone starts the stack, which is the opposite of this feature's purpose. The
   user resumes explicitly. Offer `--resume-on-start` only if the user asks.

Put all three to the user before writing code — `AGENTS.md` requires that planning
be collaborative on data structures and key business logic.

## Non-goals

- Stopping the infrastructure services (Postgres, Redis, MinIO, Zitadel). Draining
  concerns the simulation, not its backing stores.
- A distributed multi-host shutdown. Single deployment only.
- Changing how pause/resume works for user input or consultations.

## Unit 1 — Shutdown state and the intake guard

In tcp-server, introduce a single source of truth for "is the system draining?" —
a small `SystemShutdownService` holding the state, plus whatever persistence the
user's answer to question 3 requires.

While draining:

- New agent starts (`POST /api/agent/start`, `/api/agent/chat/start`) and new task
  starts (`POST /api/task/:id/start`) are refused with **503 Service Unavailable**
  and a message saying the system is shutting down.
- `AgentOrchestrationService` stops enqueueing new BullMQ jobs, including resumes.
- Already-running work is untouched by this unit.

**Tests:** unit tests for the state transitions (idle → draining → quiesced, and
that draining is idempotent); e2e tests that the guarded endpoints return 503 while
draining and normal responses when not.
**Gate:** `./dev-environment/scripts/check.sh`.

## Unit 2 — The drain endpoint

Add a fleet-level controller — **none exists today**; every current lifecycle
endpoint is per-agent or per-task. Follow the existing conventions: `@ApiTags` /
`@ApiOperation` decorators, `@UseGuards(JwtAuthGuard)` (this is user-facing), and
`@HttpCode(202)` for an asynchronous transition.

```
POST /api/system/shutdown        -> 202, begins draining, returns a status snapshot
POST /api/system/shutdown?force  -> 202, forced path (Unit 4)
GET  /api/system/shutdown        -> current state: idle | draining | quiesced,
                                     plus the count of agents still running
DELETE /api/system/shutdown      -> cancel a drain in progress (recommended;
                                     confirm with the user)
```

Graceful drain:

1. Mark the system draining (Unit 1 guards take effect immediately).
2. Mark every `Running` agent `Paused`, with the shutdown reason. The agent loop's
   existing `checkTerminalStatus` poll picks this up at each agent's next iteration
   boundary — i.e. after the LLM next responds — and exits cleanly with its
   checkpoint intact.
3. Report progress via `GET`, driven by how many agents remain non-terminal.

`GET` must be cheap enough to poll every second or so.

**Tests:** e2e covering the full transition, including that a running agent reaches
`Paused` and that `GET` reports quiesced once none remain.
**Gate:** `./dev-environment/scripts/check.sh` + `./scripts/run-e2e-tests.sh`.

## Unit 3 — Agent-side cooperative pause

Verify — and only extend if genuinely necessary — that tcp-agent stops correctly:

- `checkTerminalStatus` already exits the loop on `Paused`. Confirm the checkpoint
  is persisted such that `resumeAgent` picks up cleanly afterwards.
- `AgentRegistryService.deregister` runs so `activeCount()` falls to zero.
- The BullMQ worker uses the **graceful** `worker.close()` on module destroy, so
  in-flight jobs finish rather than being killed.
- Confirm what happens to an agent mid-LLM-call when the pause is set: it should
  finish that call (that is the point — not wasting the tokens already spent) and
  then exit at the boundary.

If `activeCount()` is not currently exposed to tcp-server, decide how the drain
endpoint observes it. Preferred: derive quiescence from agent **status in the
database**, which tcp-server already owns, rather than adding a cross-service
query for a number it can compute itself.

**Tests:** integration tests in `test/integration/tcp-agent/` — start a loop
against the stub LLM, set the agent `Paused` mid-run, assert the loop exits at the
next boundary, the checkpoint survives, and a subsequent resume continues rather
than restarting.
**Gate:** `./dev-environment/scripts/check.sh` + `./scripts/run-integration-tests.sh`.

## Unit 4 — The forced path

1. tcp-server signals a forced stop over the channel chosen in Unit 0.
2. tcp-agent aborts every in-flight run via the `AbortController`s already held in
   `AgentRegistryService`, marks those agents `Paused` (via the existing
   server-side path, so status handling stays in one place), and closes its worker
   with `worker.close(true)` — the forced variant already used by
   `knowledge-reindex.service.ts`.
3. `GET /api/system/shutdown` reports quiesced.

Aborting mid-call **will** waste the tokens spent on that call. That is the
documented trade-off of `--force`; make sure the CLI says so.

**Tests:** integration test that a forced drain terminates a running loop promptly
without waiting for the LLM, and that the agent still ends in a resumable state.
**Gate:** `./dev-environment/scripts/check.sh` + `./scripts/run-integration-tests.sh`.

## Unit 5 — CLI verb

Add `shutdown` following the established CLI shape exactly: a thin registrar in
`apps/tcp-cli/src/commands/shutdown.ts` that delegates to an action in
`apps/tcp-cli/src/lib/system/shutdown.action.ts`, calling `apiRequest` from
`lib/core/api.ts`. Register it in `main.ts` alongside the other verbs.

```
./tcp-cli.sh shutdown              # graceful: drain, wait, then stop containers
./tcp-cli.sh shutdown --force      # abort in-flight LLM work, then stop containers
./tcp-cli.sh shutdown --no-stop    # drain only; leave containers running
./tcp-cli.sh shutdown --timeout <s> # give up waiting and report (default: sensible)
```

Behaviour:

1. `POST` the drain.
2. Poll `GET` with clear progress output — how many agents are still running. A
   graceful drain can legitimately take minutes if an LLM call is slow; the user
   must be able to see it working.
3. On quiesce, stop the stack via `docker compose stop` using the same project name
   the wrapper already resolves. Skip with `--no-stop`, and skip automatically if
   Docker is not in use, reporting that the system is drained and safe to stop.
4. On timeout, report what is still running and exit non-zero. **Do not silently
   escalate to `--force`.**

Because the halting step is host-side, put it in `tcp-cli.sh` (or a small helper it
calls) rather than in the Node CLI, matching how the wrapper already handles
`docker compose up -d`. Reuse `TokenManager` from `lib/auth/token.ts` if the drain
may outlive a token's lifetime.

**Tests:** unit tests for the action with a mocked API — graceful path, forced
path, timeout path, `--no-stop`. Add a `shellcheck`-clean wrapper change.
**Gate:** `./dev-environment/scripts/check.sh` (runs `shellcheck` over `*.sh`).

## Unit 6 — Restart and recovery

Verify the system comes back correctly:

1. Bring the stack up after a graceful shutdown. `reconcileTask()` runs at
   `onModuleInit` — confirm it handles shutdown-paused agents sensibly and does not
   mistake them for dead ones and fail their tasks.
2. Confirm the shutdown state resets on boot (the system must not come up still
   refusing work).
3. Confirm an explicit resume continues an agent from its checkpoint rather than
   restarting it.
4. Repeat for a forced shutdown.

> [!NOTE]
> The four MCP apps do **not** call `app.enableShutdownHooks()` — only tcp-server
> and tcp-agent do. **011.01.03 Unit 5** adds it via the shared MCP bootstrap. If
> that has landed, verify it; if not, add the call here and tell 011.01.03 not to
> duplicate it.

**Tests:** an e2e or integration scenario covering shutdown → restart → resume.
**Gate:** `./dev-environment/scripts/check.sh` + `./scripts/run-all-tests.sh`.
