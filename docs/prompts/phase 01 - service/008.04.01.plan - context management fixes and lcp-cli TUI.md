# Plan 008.04.01 — Context management fixes + lcp-cli TUI

## Context

008.03.01 shipped streamed chat observability (ADR-015 amended). The user then ran a
real end-to-end test — chicken assistant asked to offer cat assistant some
kibble via `lcp-cli chat` — and hit two classes of problem, captured in
`docs/prompts/008.04.00.prompt - streaming issues.md` and a real captured LLM request in
`docs/prompts/008.04.00 - task-completion-context.json`:

1. **Context management is unreliable.** "Context size has been exceeded"
   recurred, a compaction protection that should have caught it didn't, and
   the chicken agent's final response was lost entirely — `complete_task` had
   already succeeded, but the model never got to say anything after it.
2. **The streamed CLI output is unreadable once agents overlap.** With a
   consultation in flight, the caller's and the consulted agent's events,
   reasoning, and responses interleave into one scrolling stream distinguished
   only by colour and a `[Role]` text prefix. A TUI (tabs + scrollback) is
   needed.

Both themes were investigated in depth before writing this plan (file:line
citations below come from that investigation, not speculation). The plan is
ordered so the reliability fixes (Theme 1) land first — they fix an active
bug — and the cosmetic rewrite (Theme 2) follows. Given the size, treat these
as two implementation passes if that's more manageable; nothing in Theme 2
depends on Theme 1 being deployed first, but Theme 1 does depend on itself
being sequential (each context phase builds on the last).

---

## Theme 1 — Context management

### Root cause: the reported bug, precisely

Chicken's run has two segments: the initial chat turn runs inline in
`ChatService.runTurn` ([chat.service.ts](apps/lcp-server/src/api/chat.service.ts)),
which pauses it for consultation; after cat (the consulted agent) completes,
lcp-server enqueues a **resume** BullMQ job — resume jobs are _always_ handled
by `AgentLoopService.runLoop` ([agent-loop.service.ts](apps/lcp-agent/src/agent/agent-loop.service.ts)),
never by `chat.service.ts` again (see `docs/queue.md` use case 3). So chicken's
final segment — the one that called `complete_task` and then needed one more
model turn — ran entirely in the lcp-agent worker.

Two independent, compounding gaps in that worker path:

1. **`agent-loop.service.ts` runs zero context-budget checks, ever.** Grepping
   for `ContextBudget`/`ContextCompactor`/`ContextManager` in `apps/lcp-agent`
   returns nothing. Only `chat.service.ts` calls `contextManager.prepare()`
   ([chat.service.ts:194](apps/lcp-server/src/api/chat.service.ts#L194)), and
   only **once, before the turn's first `streamEvents` call** — never again
   mid-turn, and never at all in the worker. This is why "compaction should
   have run" didn't: the worker that ran chicken's final segment has no
   compaction path to run.
2. **The early-exit-on-pause/complete break doesn't cancel the underlying
   graph.** `streamAndAudit` re-reads agent status after every `on_tool_end`
   and `break`s the consumer loop when it's `Paused`/`Completed`
   ([agent-loop.service.ts:400-409](apps/lcp-agent/src/agent/agent-loop.service.ts#L400)) —
   but unlike the `max_iterations` branch three lines above it (which calls
   `abortController.abort('max_iterations')`), this branch never aborts. The
   captured JSON (`008.04.00 - task-completion-context.json`) shows a request
   whose message history **already includes** `complete_task`'s successful
   tool response — i.e. this is the graph's `tools → agent` edge invoking the
   model _again_ after `complete_task` returned, with the full conversation
   history, blowing the context. Breaking our own consumer loop stops _us_
   from reading more stream events, but doesn't necessarily stop LangGraph's
   internal execution from having already dispatched (or being about to
   dispatch) that next `agent` node call — only an aborted `AbortSignal`
   reliably does that, and `buildAgentGraph`'s `agentNode` already forwards
   `signal` into every `boundModel.invoke()`
   ([build-agent-graph.ts:36,49-50](libs/lcp-shared/src/llm/build-agent-graph.ts#L36)) —
   it's just never triggered here. This also explains "the cli tool showed
   `tool_started: interactions__complete_task` but it never succeeded or
   failed": the orphaned call's rejection isn't awaited by anything once
   `streamAndAudit` has already returned, so no `on_chat_model_end`/`failed`
   event is ever produced for it.
3. **`chat.service.ts` has neither of the above at all.** No on-`tool_end`
   status check, no abort controller. So a chat-turn agent that pauses mid-turn
   (any consultation or user-input request) also risks the graph continuing to
   invoke the model with the "Paused. Consultation request dispatched..."
   tool message in history — the exact wasted, potentially context-length-
   exceeded LLM cycle the user flagged under "Blank responses" in the prompt
   doc, and the source of the blank `{"role":"assistant","content":""}`
   message visible in the captured JSON.

Fixing these three (below, phases 1–3) removes the observed failure mode
directly, independent of everything else in this theme.

### Other confirmed facts informing this theme

- Every MCP tool's full JSON schema is sent to the LLM on **every** request
  for the whole run, regardless of whether `describe_server` was ever called —
  `McpClientService.loadTools` loads all tools once per run/turn, `bindTools`
  binds them once in `buildAgentGraph` ([build-agent-graph.ts:37-38](libs/lcp-shared/src/llm/build-agent-graph.ts#L37)),
  and the bound model is reused for the whole run. A comment already
  acknowledges this is invisible to budgeting: _"tool-level detail is
  deliberately omitted since LangChain's `bindTools` already sends the full
  tool schema for every loaded MCP tool on every turn"_
  ([agent-loop.service.ts:718-719](apps/lcp-agent/src/agent/agent-loop.service.ts#L718)).
  `ContextBudgetService.countMessages` only counts message content, confirming
  the tool-schema overhead is completely outside today's token budget.
- `interactions__complete_task` ([interactions-tools.service.ts:272-328](apps/lcp-mcp-interactions/src/mcp/interactions-tools.service.ts#L272))
  requires `finalAnswer` (string) + optional `outputFiles`; it POSTs directly
  to `/internal/agent/:id/complete` → `PauseAndResumeService.completeAgent`,
  storing `finalAnswer` as `LcpAgent.output`.
- A **separate** LLM call, `generateAndRecordCompletionSummary`
  ([agent-loop.service.ts:607-670](apps/lcp-agent/src/agent/agent-loop.service.ts#L607)),
  runs _after_ `complete_task` succeeds, bypassing the graph
  (`model.invoke([new HumanMessage(prompt)])`, retried once), to produce a JSON
  `{"summary": "..."}` stored as an audit event — entirely separate from
  `LcpAgent.output`. This is a second LLM round-trip doing similar work to
  `finalAnswer`, for an audit-only record.
- Every assistant message in the captured trace has empty or near-empty
  `content` (`""`, `"\n\n"`) — this model puts all real content inside tool
  call arguments, never in message text. This matters for the "Finishing"
  decision below.
- `interactions__list_available_users`/`list_available_roles`
  ([interactions-tools.service.ts:65-78](apps/lcp-mcp-interactions/src/mcp/interactions-tools.service.ts#L65))
  are two thin registrations over one identical generic handler
  (`registerCompanyListTool`, :100-128) parameterised only by which internal
  endpoint/collection (`users` vs `roles`) they hit — merging is mechanical.
- The duplicate `"Consultation response: ..."` message the user saw is
  consistent with a **race**, not a structural double-append: `resumeAgent`
  ([agent-orchestration.service.ts:117-166](apps/lcp-server/src/api/agent-orchestration.service.ts#L117))
  reads `pausedAt`, aggregates replies via `collectRepliesSince`, then clears
  `pausedAt` — but nothing makes that read-aggregate-clear sequence atomic, so
  two near-simultaneous completion notifications for the same pause episode
  (e.g. a retried fire-and-forget HTTP notification) could both pass the
  "outstanding == 0" check before either clears `pausedAt`, each enqueueing its
  own `resume` job with the same aggregated text.

### Phase 1 — relocate context services to `libs/lcp-shared`

`ContextBudgetService` and `ContextCompactorService`
([context-budget.service.ts](apps/lcp-server/src/context/context-budget.service.ts),
[context-compactor.service.ts](apps/lcp-server/src/context/context-compactor.service.ts))
have no lcp-server-specific dependencies (tiktoken + langchain messages only)
— move them verbatim into `libs/lcp-shared/src/context/`. `ContextManagerService`
([context-manager.service.ts](apps/lcp-server/src/context/context-manager.service.ts))
depends on `AgentEventService` (in-memory SSE bus, lcp-server-only) and
`AuditService` (direct TypeORM writes, lcp-server-only) — generalise these two
behind small structural interfaces (`ContextEventSink { emit(agentId, event) }`,
`ContextAuditSink { record(companyId, roleName, agentId, type, payload) }`) and
move the class into shared too. Both lcp-server's `AgentEventService`/`AuditService`
and lcp-agent's `AgentEventPublisherService`/`AuditClientService` already have
matching method shapes (`streamAndAudit` already calls
`this.auditClient.record(...)` with the identical signature — see
[agent-loop.service.ts:357](apps/lcp-agent/src/agent/agent-loop.service.ts#L357)) —
this should be close to a drop-in reuse via TS structural typing, not a new
plugin system.

Also add `ContextBudgetService.countTools(tools)` — stringifies each bound
tool's name/description/JSON schema and tiktoken-counts it — and fold this
into every "current tokens" calculation in `ContextManagerService`. This makes
the previously-invisible tool-schema overhead visible to budgeting immediately,
independent of Phase 6's gating work.

`IncomingDataGuardService` stays in `apps/lcp-server/src/context/` — it exists
to guard _newly incoming_ text (user message, RAG chunks) before injection,
which is a chat-turn-only concept; the worker has no equivalent injection
point today. (Oversized tool _results_ in the worker are a related but
separate risk, addressed indirectly by Phase 3's per-iteration check — not
guarded proactively in this pass; flagged as a follow-up, not built now.)

Update `ApiModule`/`ContextModule` (lcp-server) and the lcp-agent agent module
to import the relocated classes from `@lcp/shared` and provide the two sink
adapters. Existing `context-*.service.spec.ts` files move/adapt with the
classes; no behaviour change expected for lcp-server in this phase alone.

### Phase 3 — extract a shared supervised graph runner, with abort-on-pause, per-iteration compaction, and a reactive backstop

008.03.01 deliberately kept `chat.service.ts`'s and `agent-loop.service.ts`'s
stream-consumption loops separate ("tracker/audit/pause logic differs too
much" to share the whole loop). That call was reasonable when the only shared
concern was mapping/emitting observability events. It no longer holds: this
phase and Phase 6 both add non-trivial _control flow_ (abort timing,
break-compact-restream, break-rebuild-restream) that has to behave
**identically** in both files — and the bug this whole plan exists to fix is
exactly a case of one file having a piece of logic the other silently didn't.
Duplicating four break-conditions across two files is asking for that same
class of bug to recur. Instead, extract the outer loop itself into
`libs/lcp-shared`:

```ts
// libs/lcp-shared/src/llm/run-supervised-graph.ts
export interface SupervisedGraphHooks {
  /** Rebuild the compiled graph against a (possibly narrowed) tool subset. */
  buildGraph: (tools: DynamicStructuredTool[]) => CompiledStateGraph;
  /** Per-event side effects (audit recording, tracker updates, SSE/Redis emit). */
  onEvent: (event: StreamEvent) => void;
  /** Re-reads the agent's DB status; non-null triggers the matching exit. */
  checkTerminalStatus: () => Promise<AgentStatus | null>;
  /** Optional — agent-loop only: enforced iteration ceiling. */
  maxIterations?: number;
  /** Optional — Phase 6: current tool-visibility subset, recomputed per iteration. */
  resolveVisibleTools?: (
    allTools: DynamicStructuredTool[],
  ) => DynamicStructuredTool[];
}

export async function runSupervisedGraph(
  allTools: DynamicStructuredTool[],
  input: typeof MessagesAnnotation.State,
  config: RunnableConfig,
  contextManager: ContextManagerService,
  windowSize: number,
  hooks: SupervisedGraphHooks,
): Promise<{
  lastAiMessage?: AIMessage;
  terminalStatus: AgentStatus | null;
  aborted: boolean;
}>;
```

The function owns: the `AbortController`, the outer while-loop, and all four
break-and-continue/break-and-exit conditions (below). Each caller supplies
only its own side effects (`onEvent`) and app-specific extras
(`maxIterations`, tracker updates folded into `onEvent`, required-tools
enforcement stays in `agent-loop.service.ts`'s caller code — it runs _after_
`runSupervisedGraph` returns, unchanged from today). `chat.service.ts`'s
`runTurn` and `agent-loop.service.ts`'s `streamAndAudit`/`runLoop` both shrink
to: build initial tools/state, call `runSupervisedGraph`, then handle the
returned terminal status exactly as their existing post-stream code already
does. This is the single place all four conditions live and are tested once:

1. **Abort properly on Paused/Completed.** Create an `AbortController` in
   `chat.service.ts` (it has none today) and pass its signal into
   `buildAgentGraph({..., signal})` at graph-build time (this is how
   `agent-loop.service.ts` already gets cancellation into `boundModel.invoke`,
   per `build-agent-graph.ts:36`,`49-50` above). In _both_ files, when the
   post-`on_tool_end` status check finds `Paused`/`Completed`, call
   `abortController.abort('agent_paused_or_completed')` **before** breaking —
   not just break. This is the direct fix for the wasted-cycle/blank-message
   bug and the orphaned-request bug described above.
2. **Per-iteration budget check.** After each `on_tool_end` (i.e. once per
   tool-loop iteration, not just once per turn/run), call a new
   `ContextManagerService.checkBudget(agentId, graph, config, windowSize)` —
   same Tier-1/Tier-2 compaction machinery as `prepare()`, but checking the
   _current_ checkpoint only (no incoming message). If compaction runs and
   this is the **first** compaction this turn/run, break the current stream,
   loop back, and start a fresh `streamEvents` call against the same
   `thread_id` to continue from the compacted checkpoint. If a compaction was
   **already** attempted this cycle and the budget is still exceeded, fail
   the run cleanly (`Failed`, reason `"Context window exceeded even after
compaction"`) instead of proceeding to a doomed model call. This directly
   satisfies "compaction should run once; if that's still no good, the agent
   should fail and stop," and fixes the "did we check at every iteration?"
   question — until now the answer was no.
3. **Reactive backstop.** Wrap the `streamEvents` consumption in a
   `try/catch` with a new `isContextLengthError(err)` classifier (new file in
   `libs/lcp-shared`, checking common substrings across providers —
   `"context_length_exceeded"`, `"maximum context length"`, `"context size has
been exceeded"` per the literal error text observed here, `"context
window"`). On a match: if not yet compacted this cycle, compact once and
   retry the same `streamEvents` call; otherwise fail cleanly with the same
   message as above. This is a backstop for cases the tiktoken-based estimate
   underestimates (defense in depth alongside Phase 1's `countTools` fix, not
   a replacement for it).

This is one architectural change (turn a single pass into a supervised,
resumable loop) with three independent trigger conditions, applied
consistently in both files — not three unrelated patches. Phase 6 (tool
gating) reuses the same break-and-restream mechanism for a fourth condition.

**Verification:** the bulk of the logic (all four break-conditions) now lives
in one place — `libs/lcp-shared/src/llm/run-supervised-graph.spec.ts` gets
the thorough table-driven coverage: (a) abort is called before break on
Paused/Completed, (b) a single compaction-and-retry cycle when over budget,
(c) clean failure when still over budget after one compaction, (d)
`isContextLengthError` classifier specs (table-driven, one case per provider
error string) plus a spec proving the reactive catch path compacts once then
fails on a second consecutive context-length error, (e) `maxIterations`
enforcement when the hook is provided, absent when it isn't. `chat.service.spec.ts`
and `agent-loop.service.spec.ts` then only need thinner specs proving they
call `runSupervisedGraph` with the right hooks/config and handle its returned
`terminalStatus` correctly — not re-testing the loop logic itself. Run
`format` → typecheck → lint → `build` → `./scripts/run-unit-tests.sh`. This
changes the core turn-execution contract in both apps — update
`test/integration/lcp-server/chat-llm.integration-spec.ts`,
`test/integration/lcp-agent/agent-loop.integration-spec.ts`, and any e2e spec
that drives a full pause/resume or consultation cycle, to assert no orphaned
post-pause LLM call occurs (e.g. assert exactly one `on_chat_model_end`-style
audit event after the pausing tool call, not two). Run
`./scripts/run-integration-tests.sh`, `./scripts/run-e2e-tests.sh`, and
`./scripts/run-api-tests.sh`. Run `./scripts/run-all-tests.sh` at the end of
this phase — this is the phase that fixes the originally reported bug, so
also manually reproduce the kibble-consultation scenario end-to-end via
`lcp-cli chat` against the real dev stack and confirm the fix (no wasted

message).

### Phase 4 — cut `completion_summary_prompt`'s LLM call

Replace `generateAndRecordCompletionSummary`'s `model.invoke(...)` + retry
path with a deterministic template built from data already tracked in
`AgentLoopTracker` (`tracker.actions`, `tracker.storage.created/modified/deleted/moved`
— see [loop-tracker.ts](apps/lcp-agent/src/agent/loop-tracker.ts)), matching
the shape already used by the existing `buildFallbackSummary` path:

```text
Task completed.

Actions taken (in order):
{{actionLines}}

Storage changes:
- Created: {{created}}
- Modified: {{modified}}
- Deleted: {{deleted}}
- Moved: {{moved}}
```

**Reasoning (per the user's request to justify the choice):** this removes
one entire extra LLM round-trip per completed run for no loss of information
— the tracked actions/storage changes are already precise and complete; the
LLM-authored abstractive version added narrative framing but no new facts.
Low risk, clear win — implement immediately, no further discussion needed.

**On the "Finishing" suggestions** (`add_completion_item` replacing
`complete_task`, dropping `finalAnswer`): **not implementing either.**
`complete_task.outputFiles` already covers the stated need ("if the task is
finding files, this is available in structured form") — `add_completion_item`
would be a second, overlapping mechanism for the same job, adding a tool + a
new completion-item store for marginal benefit (YAGNI). Dropping the
_required_ `finalAnswer` in favour of "the content itself" is actively risky
given the evidence in the captured trace: every assistant message in this
run's history has empty/near-empty `content` — this model (and likely others
prompted the same way) puts all real content inside tool-call arguments, not
message text. Making `finalAnswer` optional would risk silently losing the
final answer for exactly the models this system targets. `complete_task`
keeps its current required-`finalAnswer` shape unchanged.

**Verification:** unit spec replacing the old
`generateAndRecordCompletionSummary` LLM-call assertions with assertions on
the deterministic template output (given a tracker fixture, expect exact
templated string); delete the now-dead retry-once/`model.invoke` mocking from
that spec. Run `format` → typecheck → lint → `build` →
`./scripts/run-unit-tests.sh`. This changes the audit payload shape for
`AgentLoopCompletion` events — check and update
`test/integration/lcp-agent/agent-loop.integration-spec.ts` if it asserts on
the summary's shape/content, then run `./scripts/run-integration-tests.sh`.

### Phase 6 — tool-schema gating (describe-then-reveal)

The biggest lever for "retain support for models running with smaller
context windows." Design (all in-memory, no new persisted/checkpointed
state — deliberately, to avoid a new LangGraph state-schema channel), built
as the fourth condition on Phase 3's shared `runSupervisedGraph`:

- A new small `ToolVisibilityTracker` (in `libs/lcp-shared`, alongside
  `run-supervised-graph.ts`) maintains a plain
  `Map<serverName, iterationsRemaining>` for the duration of one run/turn
  (not persisted — if a process restart drops it, the agent simply
  re-describes on the retried run; acceptable and cheap). Both callers
  construct one instance and pass its `resolveVisibleTools` method as the
  `SupervisedGraphHooks.resolveVisibleTools` hook from Phase 3 — no
  per-app duplication of the tracking logic itself.
- The visible tool subset is computed as: every server's `describe_server`
  tool (always visible) **plus** the tools of any server currently in the
  map. Initial state: map is empty, so only `*__describe_server` tools are
  visible at run start.
- On `on_tool_end` for a `*__describe_server` call, the tracker sets
  `map.set(serverName, 3)` (TTL constant, `ponytail:` comment noting 1–3 was
  the range considered and 3 chosen to tolerate a wrong call or two without
  re-describing; easy to retune later). On each `on_chat_model_start`
  (one per agent-node iteration), it decrements every entry and deletes
  entries that hit 0.
- When the visible set changes (an entry added or removed),
  `runSupervisedGraph` detects this via `resolveVisibleTools` returning a
  different set than the graph was last built with — it breaks the current
  stream, rebuilds via `hooks.buildGraph(newVisibleSet)`, and continues with
  a fresh `streamEvents` call. This is exactly the same break-rebuild-restream
  mechanism Phase 3 already built for compaction retries; no new control-flow
  branch needed in either app, only in the shared runner.
- Update each MCP server's `describe_server` response text (`storagePrompts`,
  `memoryPrompts`, `interactionsPrompts` in their respective `prompts.jsonc`
  files) from a full tool catalogue down to a short (1–2 sentence) usage-
  guidance blurb — the full tool list/schemas now arrive via the `tools` array
  itself once revealed, so restating them in prose is pure duplication.
- Update the "services available" prompt section in both
  `chat.service.ts`'s `buildServicesMessage`
  ([chat.service.ts:372-392](apps/lcp-server/src/api/chat.service.ts#L372))
  and `agent-loop.service.ts`'s equivalent (around
  [agent-loop.service.ts:719](apps/lcp-agent/src/agent/agent-loop.service.ts#L719))
  to explain the new behaviour: call `describe_server` before using a
  service's other tools; its full tool set stays available for a few turns;
  be sparing — only describe services actually needed for the current task.

This is the most structurally invasive phase in Theme 1 — flag it clearly
when starting; if it turns out more complex in practice than this design
implies, the fallback is to ship Phases 1–5 + 7 alone (still a large
reliability win) and defer this one.

**Verification:** unit specs for `ToolVisibilityTracker` in isolation

describe-tools always present), in `libs/lcp-shared` next to the class
itself, plus a `run-supervised-graph.spec.ts` case proving the graph is

typecheck → lint → `build` → `./scripts/run-unit-tests.sh`. This changes what
tools are visible to the LLM turn-by-turn — a cross-component behaviour

`chat-llm.integration-spec.ts` and any e2e scenario that calls a

## Theme 2 — lcp-cli TUI

### Library decision

Evaluated OpenTUI (Bun-first; Node path needs experimental FFI on Node
≥26.3 — not viable), rezitui (low-adoption single-maintainer beta, no
confirmed tab/scrollback widgets), ink (no built-in scrollback/virtualisation,
ESM-only conflicting with this repo's CJS-oriented `nodenext` tsconfig), and
blessed (has every needed primitive but unmaintained since ~2016). **Decision:
`terminal-kit`** (actively maintained, MIT) — its document/widget model
already provides `TextBox` (scrollable, `.appendLog()`, word-wrap, mouse/
scrollbar) and `InputField` (text input), plus `Container`/`Layout` for
nesting; only the tab-switching layer (show/hide containers, keybinding
routing, enabling the input box per active tab) needs to be hand-written —
a thin layer on top of built-in widgets, not a full custom stack.

### Current state (reused, not replaced)

`apps/lcp-cli/src/lib/render.ts`'s `createRenderer` is a clean block-state
machine (tracks `currentBlock: 'reasoning' | 'response' | null`, prefixes once
then appends deltas, blank-line-separates discrete events) — this state-
machine _shape_ is reused for the TUI's per-pane formatting, but the actual
output format changes (3-column `hh:mm:ss | kind | text` instead of the
current `[colour]Agent state: running` style), so it's a new sibling module,
not a direct reuse of `render.ts`'s text output. `render.ts` itself is kept
unchanged and continues to serve the one case a full-screen TUI genuinely
can't handle: **stdout piped to a file or another process** (no real
terminal to draw to). `chat.ts`'s existing `streamAgent(id, renderer, signal,
onConnected)` recursive-follower architecture (opens SSE, spawns a follower
stream on `consultation_started`) is reused as-is — only the renderer it's
given changes for TUI mode.

### `-q`/`--query` handling

Originally scoped `--query` to always keep the old plain-text path. Revised:
**the TUI is shown for `--query` too whenever stdout is a real TTY**, exactly
as for the interactive `chat` loop — same panes, same tabs, same scrollback.
The only differences for `--query`: the one message is submitted
automatically on startup (no input box needed/shown), and as soon as the
root agent's turn reaches a terminal event, the TUI tears down (restores the
normal terminal/alternate-screen-buffer exit) and the final response is
printed to stdout exactly as today, then the process exits. This keeps a
single TUI implementation serving both entry points instead of maintaining
two rendering paths for "interactive" vs "one-shot" — the only branch is
"was a TTY available at all," which is also the exact test that already
decides colour-on/off today. When stdout is **not** a TTY (truly piped),
`--query` (and non-interactive `chat` invocations generally) fall back
entirely to the existing `render.ts` plain path, unchanged — this is the
only case where the TUI is skipped altogether, and it's the same case the
existing pipe-compatible tests (`--query | cat`, manual-verify scenarios)
already rely on.

### Phase 8 — TUI scaffold

Add `terminal-kit` (+ its bundled types) as a dependency of `apps/lcp-cli`.
New module `apps/lcp-cli/src/lib/tui.ts`:

- One `Container` per monitored agent ("pane"), each holding a `TextBox`
  (scrollable log) sized to fill the space between a tab bar row and a bottom
  input row.
- A hand-written tab bar (row of labelled `Text` elements, current tab
  highlighted) plus keybindings (e.g. `Tab`/`Shift+Tab` or number keys) to
  switch which pane's `Container` is visible — only the active pane's
  `TextBox` is shown; others keep accumulating content invisibly.
- One `InputField`, shown/enabled only when the active tab is the "talkable"
  agent (the one the user is directly chatting with via the command line) —
  disabled/hidden for consultation-follower panes, per the spec ("input box
  for the tab of agents the user can talk to, rather than those being
  consulted"), and hidden entirely in `--query` mode (nothing to type).
- Screen-resize handling (terminal-kit re-flows on terminal resize; verify
  `TextBox` re-wraps existing content or needs an explicit re-render trigger).

**Verification:** unit tests for the scaffold's pure logic (pane
creation/removal, active-tab state transitions, input-enabled-for-talkable-
tab-only) using a stubbed/mock terminal-kit screen object — do not require a
real TTY in CI. Run `format` → typecheck → lint → `build` →
`./scripts/run-unit-tests.sh`. No cross-component contract changes yet
(nothing outside `apps/lcp-cli` is affected) — integration/e2e/api suites are
not expected to need changes this phase, but run
`./scripts/run-e2e-tests.sh` once to confirm CLI-driving e2e specs still
pass against the (still wired to the old renderer) `chat.ts`.

### Phase 9 — event formatter (3-column + reasoning special case)

New formatting function (in `tui.ts` or a sibling `tui-format.ts`) implementing
exactly the spec in `docs/prompts/008.04.00.prompt - streaming issues.md`:

- Discrete events (`agent_status`, `llm`, `consultation_started`,
  `compaction_*`) render as `hh:mm:ss | event_type | text`, blank-line
  separated, `text` trimmed/word-wrapped/trailing-linebreaks-stripped to the
  pane's current width.
- `reasoning` deltas: no time/type columns, 2-space indent, grey, word-wrapped
  to width; a blank line is inserted both when a discrete event interrupts an
  in-progress reasoning block and when reasoning resumes/continues after one.
- `response` deltas render as a `response` "event" per the column format
  (time/type once, then the streamed text).
- Word-wrap: no existing dependency provides this — write a small (~10-line)
  greedy word-wrap helper against the pane's current column width; no new
  dependency for something this size (YAGNI).

**Verification:** this formatter is a pure function (`AgentEvent[]` in,
rendered lines out) — table-driven unit spec covering: each discrete-event
kind's column formatting, reasoning interrupted-by-event blank-line
insertion, reasoning-continues blank-line insertion, word-wrap at a given
width, and trailing-linebreak stripping. No live terminal-kit screen needed
for these tests. Run `format` → typecheck → lint → `build` →
`./scripts/run-unit-tests.sh` before moving to Phase 10.

### Phase 10 — wire `chat.ts` to the TUI

- Interactive `lcp-cli chat` sessions (TTY detected, matching the existing
  colour-disable-when-non-tty pattern) launch the TUI: root pane = the agent
  given on the command line (talkable), additional panes created dynamically
  when `consultation_started` fires for a followed agent (spectate-only, tab
  added live).
- `--query` at a TTY also launches the TUI per the design above (auto-submit,
  no input box, tears down and prints the final response on the root agent's
  terminal event). `--query` piped (non-TTY) and any other non-TTY invocation
  keep using the existing plain `render.ts` path unchanged.
- Add a `--no-tui` escape hatch forcing the plain renderer even on a TTY
  (useful for debugging terminal-kit issues, screen readers, unusual
  terminals, or CI-adjacent manual runs).
- Input submitted via the `InputField` posts to the talkable agent exactly as
  today's `postMessage`/`runTurn` does; Ctrl+C semantics (abort in-flight vs.
  clean exit when idle) carry over from the existing interactive loop.

**Verification:** unit tests on `chat.ts`'s TTY/`--no-tui`/`--query` branch
selection (which rendering path gets constructed for each flag/TTY
combination), using a mocked TTY-detection point — extend
`apps/lcp-cli`'s existing command specs. Run `format` → typecheck → lint →
`build` → `./scripts/run-unit-tests.sh`. This phase changes what the CLI
actually renders in its primary path — update any e2e/api spec that asserts

## Per-phase quality gate (every phase, both themes)

Same standing gate as the 008.03.01 plan, restated here since every phase above
already spells out its specific instance of it:

1. **Coding standards** — per `docs/development.md`/AGENTS.md routing: strict
   TS, no `any` casts, `/** */` doc comments on methods/classes, `//` intent
   comments inside bodies, no changes outside plan scope.
2. **Unit tests for everything** — every new/changed service, helper,
   formatter, classifier gets spec coverage in the same phase; run
   `./scripts/run-unit-tests.sh` immediately after each phase's code lands,
   not batched up.
3. **Gate commands** — `npm run format` → typecheck → lint (0 errors) →
   `npm run build` → `./scripts/run-unit-tests.sh` before moving on.
4. **Cross-component changes** — phases that change behaviour across
   components (server↔agent↔CLI contracts, MCP tool schemas, Redis/SSE
   payloads) must update the affected integration/e2e/api specs in that phase
   and run `./scripts/run-integration-tests.sh` / `./scripts/run-e2e-tests.sh`
   / `./scripts/run-api-tests.sh` as relevant.
5. **Full suite on significant changes** — run `./scripts/run-all-tests.sh`
   (not just the targeted suites above) at the checkpoints called out in
   Phases 2, 3, 6, 7, and 10 — these are the phases with cross-component or
   user-facing behaviour changes. Isolated per-suite runs miss cross-layer
   regressions (per standing project guidance).

## YAGNI — deliberately cut

- `add_completion_item` MCP tool (redundant with existing `outputFiles`).
- Making `complete_task.finalAnswer` optional (unsafe given this model's
  empty-message-content behaviour, evidenced in the captured trace).
- Full essential-information-anchoring compaction classification — stays as
  the existing ADR-013 TODO; the phases above reduce how often it'd matter.
- Proactive incoming-data guarding of tool _results_ in the worker — the
  per-iteration reactive check (Phase 3) catches this one cycle later instead.
- Persisting tool-visibility state in the LangGraph checkpoint — kept
  in-memory/per-run only; a lost map on crash just costs one extra
  `describe_server` call on retry.
- Ink and blessed as TUI choices (see library decision above).
- Two separate rendering paths for interactive `chat` vs. `--query` — unified
  behind one TTY-detection branch (see `-q`/`--query` handling above).
