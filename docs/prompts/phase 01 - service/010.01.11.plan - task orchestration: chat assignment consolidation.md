# Task orchestration 8/9: chat assignment consolidation

Part 8 of the task-orchestration work (map: `010.01.03.plan - task orchestration: overview.md`).
Added **after** part 4 shipped, to close a gap it deliberately left: part 4
gave every agent an assignment and a mode-specific prompt part, but only on the
**lcp-agent worker path** (`AgentLoopService.buildInitialState`). The
**lcp-server chat path** (`ChatService`) still has its own duplicate prompt
assembly and renders a bare user message as prompt part 4 — a chat agent has no
idea it is in a conversation, and the two operation paths have drifted.

Depends on part 4 (`LcpAssignment`, `assignmentId`, `MODE_PROMPTS`,
`prompt-assembly.ts`). Independent in content from parts 5–7, but delivered
after them so the prompt-assembly relocation lands once the tasks/QA parts have
stopped churning the loop — and delivered before part 9 (final consolidation),
so that sweep reviews this part's work too instead of leaving it unreviewed.

> **Recommended implementing model: Opus.** This crosses two services'
> agent-operation paths and moves shared prompt/loop logic; behaviour of the
> live chat and worker flows must be preserved exactly apart from the added
> chat-mode framing.

## Goal

Two outcomes:

1. **A first-class `chat` mode and chat assignment.** Conversational agents
   (created by `/api/agent/chat/start`) get a `chat`-mode orphan assignment
   whose mode prompt makes their expected behaviour **explicit** — so it can be
   refined over time rather than living implicitly in whatever the role prompt
   happens to say.
2. **One prompt-assembly and one supervised-run spine, shared by both
   operation paths.** `ChatService` (lcp-server, in-process turns) and
   `AgentLoopService` (lcp-agent, BullMQ worker runs) stop duplicating prompt
   construction and loop wiring; each becomes a thin wrapper over a common core
   that supplies only its caller-specific concerns (HTTP turn vs. queue job;
   idle-between-turns vs. run-to-completion).

The end state we are moving toward: **agents are created and operated through
one path, not several.** Creation already consolidated onto
`DbService.createAgent` in part 4; this part consolidates operation as far as is
sensible and names what genuinely must stay per-caller.

## Implementation

### 1. `chat` mode in `@lcp/shared`

- Add `'chat'` to `LcpAssignmentMode` (`libs/lcp-shared/src/models/LcpAssignment.model.ts`):
  `'plan' | 'implement' | 'qa' | 'chat'`. **No DB migration** — `mode` is a
  `varchar` column; only the TypeScript union widens.
- Add `MODE_PROMPTS.chat` (`libs/lcp-shared/src/prompts/mode-prompts.ts`). It
  must state the chat agent's expected behaviour explicitly. Base text (refine
  for LLM clarity):
  - You are in a **conversation** with a user. Interact naturally: answer their
    questions, offer advice and options, and think out loud when it helps.
  - Draw on your knowledge base and episodic memory, and read from the shared
    storage service (read-only), to ground your answers in real material rather
    than guessing.
  - When a question needs another role's expertise, or needs the user to
    decide something, **consult** them (agent consultation / user query) rather
    than inventing an answer.
  - When the user asks you to **do** something, take the action using the tools
    available to you; don't just describe what you would do.
  - There is **no completion tool** and no fixed deliverable — the conversation
    continues until the user ends it. End each turn with your reply and wait
    for the next message.
- Change `requiredToolForMode` to return `string[]` (the full
  `requiredToolCalls` list) rather than a single tool name: `plan` →
  `['create_plan']`, `implement` → `['complete_assignment']` (still
  `['complete_task']` until part 5 lands — keep the `TODO(010.01.08)`), `qa` →
  `['assure_assignment']`, **`chat` → `[]`** (no mandatory tool; a chat turn
  ends with narrated text). Update the single call site in
  `DbService.createAgent` (`template.requiredToolCalls ?? requiredToolForMode(mode)`)
  and its unit tests.

### 2. `chat/start` creates a chat-mode assignment

- `api.agent.controller.ts` `startChat`: pass `mode: 'chat'` to `createAgent`
  (the orphan assignment becomes chat mode with an empty prompt and
  `requiredToolCalls: []`). No other caller changes — `/api/agent/start` and
  consultations stay `implement`.

### 3. Consolidate prompt assembly (the concrete first step)

- **Move** `apps/lcp-agent/src/agent/prompt-assembly.ts` (and its spec) into
  `@lcp/shared` (e.g. `libs/lcp-shared/src/prompts/prompt-assembly.ts`),
  parameterising the two lcp-agent-specific dependencies it currently closes
  over: `agentPrompts` strings and the MCP registry lookup. Pass those in (a
  small `PromptStrings`/`serviceUsage` argument), so the pure builders live in
  one place and both apps supply their own strings.
- `AgentLoopService.buildInitialState` imports the builders from `@lcp/shared`
  (thin change — it already delegates to them).
- **`ChatService`**: delete its duplicate `buildServicesMessage` /
  `buildRagMessage` and inline first-turn assembly; build the first-turn message
  list from the shared builders, and render **prompt part 4 via
  `buildAssignmentMessage`** using the agent's (chat-mode) assignment. Result: a
  chat agent's first turn now carries the chat mode prompt. Load the assignment
  on the chat agent the same way part 4 does for the worker
  (`relations: { assignment: { task: true } }`).
- Preserve chat behaviour otherwise: SSE streaming, per-turn user message on
  resume turns (checkpoint holds history), and **the agent returns to `Idle`
  after each turn** (chat agents never auto-`Completed`). `requiredToolCalls: []`
  keeps the required-tool enforcement out of the chat turn.

### 4. Reduce the two operation paths to thin wrappers over a common core

`ChatService.sendMessage` and `AgentLoopService.runLoop` already share
`runSupervisedGraph`, but each re-implements the surrounding orchestration
(initial-state build, budget check, required-tool enforcement, completion /
summary / empty-output fallback). Extract that spine into one shared unit
(e.g. `@lcp/shared` `runAgentTurn` / a small `AgentTurnRunner`), leaving each
caller to supply only:

- **Chat**: the resolved model/tools for an HTTP turn; terminal handling that
  returns the agent to `Idle` and streams the reply over SSE.
- **Worker**: the BullMQ job envelope (abort controller, timeout, dispatch);
  terminal handling that sets `Completed`/`Paused`/`Failed` and notifies
  lcp-server.

Name explicitly what stays per-caller (it is genuinely different, not
duplication to be removed): job lifecycle/dispatch vs. request lifecycle;
run-to-completion vs. idle-between-turns terminal semantics; who owns the abort
signal. If full extraction of the loop spine balloons beyond the prompt-assembly
consolidation in section 3, **HALT and report** — section 3 plus the chat mode
are the required deliverable; the loop-core extraction is the direction and may
be delivered partially with the remainder noted as follow-up.

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.

  license/health checked. Do not update existing dependencies. No unrequested

## Implementation notes

_2026-07-13._

Sections 1–3 and the `chat` mode delivered in full:

- `chat` added to `LcpAssignmentMode` (union widening, no migration);
  `MODE_PROMPTS.chat` states the conversational behaviours explicitly;
  `requiredToolForMode` now returns `string[]` (`[]` for chat). Its two
  display-only callers in `lcp-mcp-tasks/tasks-tools.service.ts` (not just the
  `DbService.createAgent` call site the plan named) were updated to `.join(', ')`.
- `chat/start` creates a `chat`-mode orphan assignment.
- Prompt-assembly moved to `libs/lcp-shared/src/prompts/prompt-assembly.ts`
  (with its spec), parameterised on a `PromptAssemblyStrings` argument. The MCP
  lookup uses the already-shared `MCP_REGISTRY`, so only the fixed strings are
  passed in (lcp-agent passes `agentPrompts`; lcp-server passes an equivalent
  const). `ChatService` deletes its duplicate builders, loads the chat-mode
  assignment (`relations: { assignment: { task: true } }`), and renders part 4
  via `buildAssignmentMessage`. Chat behaviour otherwise preserved (SSE, resume
  message, RAG overflow-guard, return-to-`Idle`). The stub-LLM gained a
  `GET /stub/last-request` capture so the integration test can assert
  `MODE_PROMPTS.chat` reaches the model.

Section 4 (loop-spine extraction) — **deferred as follow-up**, per this plan's
own allowance ("the loop-core extraction is the direction and may be delivered
partially"). Rationale: the two paths already share the real execution core
(`runSupervisedGraph`). The surrounding "spine" the section lists —
required-tool enforcement, empty-output retry, deterministic completion
summary, `Completed`/`Failed` terminal handling — is almost entirely
**worker-only**; the chat path deliberately does none of it (a chat turn ends
with narrated text and returns to `Idle`). A shared `runAgentTurn` would
therefore be a wrapper that immediately branches on caller type — a
one-behaviour-per-arm abstraction, not consolidation. What genuinely stays
per-caller is named in the ADR-010 010.01.11 amendment. Extraction can be
revisited if a third operation path appears.
