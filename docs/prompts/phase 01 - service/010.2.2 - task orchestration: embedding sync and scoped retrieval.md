# Task orchestration 2/8: embedding sync and scoped retrieval

Part 2 of the task-orchestration work (map: `010.2.0 - task orchestration: overview.md`;
prerequisite: part 1 — slug-based knowledge folders, `shared/` scope, and a
nullable `KnowledgeChunk.roleId` are already in place).

> **Recommended implementing model: Opus.** The generation-counter/
> restart-on-change semantics and the queue/poller concurrency need careful
> reasoning; the retrieval-scoping changes ripple across three services.

## Goal

1. Keep RAG embeddings automatically in sync with the contents of the
   `knowledge/{role_slug}/` and `knowledge/shared/` folders, whoever changes
   them (user via API/CLI, agent via storage tools, or a user editing directly
   in the MinIO web console).
2. Scope every knowledge retrieval to the querying role's chunks **plus** the
   company-shared chunks.

## Design (agreed — do not re-derive)

**Reindex unit** is a _scope_: `(companyId, roleId)` or `(companyId, shared)`.
A rebuild lists every file under the scope's knowledge prefix, re-chunks and
re-embeds all of them via `RagIndexService`, and replaces that scope's rows in
`knowledge_chunk`.

**Two triggers, one queue** (`knowledge-reindex`, BullMQ):

1. _Write hook (fast path)_: lcp-server's `StorageService` is the chokepoint for
   all lcp-server-mediated writes (the storage MCP service is a thin proxy to
   `/internal/storage/*`). After any successful write/delete/restore whose key
   is under `{companySlug}/knowledge/`, resolve the scope from the key and
   enqueue a rebuild.
2. _Reconciliation poller (safety net)_: a repeatable BullMQ job (interval env
   `KNOWLEDGE_POLL_INTERVAL_MS`, default 60000) that, for each company with an
   `embeddingConfig`, lists each knowledge scope's files and compares a
   **fingerprint** (sorted `key:etag:size:lastModified` lines, hashed) against
   the fingerprint recorded at the end of the last successful rebuild. Drift →
   enqueue a rebuild. This catches direct MinIO-console edits.

**Restart-on-change semantics** via a generation counter:

- New entity `KnowledgeIndexState` (`libs/lcp-shared/src/models/`), one row per
  scope: `id`, `companyId`, `roleId` (nullable — null = shared), `generation`
  (int, default 0), `fingerprint` (text, nullable), `updatedAt`. Unique index on
  `(companyId, roleId)` (mind NULL semantics in Postgres — enforce uniqueness
  for the shared row too, e.g. a partial unique index where `roleId IS NULL`).
  Migration registered **by hand** in `apps/lcp-server/src/app.module.ts` (and
  any other app.module listing migrations); written by hand (ignore
  `migration:generate` phantom drift).
- Every trigger **increments `generation` atomically** (upsert) and enqueues a
  job carrying the new generation value.
- The worker, on picking up a job: if `job.generation < current generation`,
  skip (a newer job is queued). During the rebuild, re-read the generation
  between documents; if it changed, abort and re-enqueue with the current
  generation. On successful completion, store the fingerprint of the listing it
  just indexed.

Worked example: a user uploads 3 files in quick succession to
`knowledge/analyst/`. Upload 1 sets generation 1 and enqueues G1; uploads 2 and
3 set generations 2 and 3 and enqueue G2, G3. The worker takes G1, notices
current generation is 3 → skips. Same for G2. G3 runs, lists all 3 files,
indexes them, records the fingerprint. If upload 4 lands mid-rebuild, the
generation check between documents aborts G3's run and re-enqueues; nothing is
half-indexed because a rebuild only deletes/replaces rows per document as it
goes and the follow-up rebuild re-processes everything.

The queue and worker both live in lcp-server (it owns `RagIndexService` and
`StorageService`). Follow the BullMQ patterns in
`apps/lcp-server/src/api/agent-orchestration.service.ts` (fail-fast Redis
probe, graceful close). **Every new `Queue`/`Worker` must register an
`.on('error')` handler** — a missing one lets a "Connection is closed" crash
unrelated test suites.

## Implementation

### 1. `KnowledgeIndexState` entity + migration

As specified above. Export from `libs/lcp-shared/src/models/index.ts`.

### 2. `KnowledgeReindexService` (lcp-server)

New `apps/lcp-server/src/rag/knowledge-reindex.service.ts`:

- `bump(scope)` — atomic generation increment (upsert) + enqueue.
- Worker handler `rebuild(job)` — the skip/abort/fingerprint logic above;
  rebuild = list scope prefix via `StorageService` → for each file, read +
  `RagIndexService.ingestDocument` → remove chunks for documents that no longer
  exist (compare listed keys against distinct `documentPath` for the scope) →
  record fingerprint.
- No-op (log once, skip) for companies with no `embeddingConfig`.
- The poller: a BullMQ repeatable job registered on module init; handler
  computes fingerprints per scope and calls `bump` on drift. Scopes = every
  role of the company plus the shared scope.

### 3. Write hook

In `StorageService` (`apps/lcp-server/src/storage/storage.service.ts`) — after
successful write/delete/restore/move/copy operations, if the affected key(s)
parse as a knowledge path (`{companySlug}/knowledge/{segment}/{filename}`),
resolve companyId + roleId (segment `shared` → null; otherwise look up the role
by slug within the company) and call `KnowledgeReindexService.bump`. Mind
module dependencies/circularity — if wiring the reindex service into the
storage module is awkward, an event (Nest `EventEmitter` is NOT currently a
dependency — prefer a direct provider injection; HALT and discuss if that
proves circular).

`KnowledgeService.store/delete` (from part 1) currently call `RagIndexService`
synchronously — replace those direct calls with the same `bump` path so there
is exactly one way embeddings get rebuilt.

### 4. Scoped retrieval (role + shared)

Change the chunk queries from `roleId = $x` to
`(("roleId" = $x) OR ("roleId" IS NULL AND "companyId" = $y))` — i.e. the
agent's role's chunks plus its company's shared chunks — in **all three**
retrieval paths:

1. `apps/lcp-agent/src/rag/agent-rag.service.ts` (`retrieve` — used for the
   initial-prompt RAG part). Its callers must now pass `companyId` too.
2. `apps/lcp-mcp-memory/src/mcp/memory-tools.service.ts` — the
   `search_knowledge` tool's `knowledgeSearch` query.
3. `apps/lcp-server/src/rag/rag-retrieval.service.ts`.

Update each service's spec; add a case proving shared chunks surface for any
role of the company and never for another company.

### 5. Manual reindex trigger

- `POST /api/company/:companyId/knowledge/reindex` (JWT-guarded) — bumps every
  scope of the company; 202 response; 404 unknown company.
- CLI verb `reindex-knowledge --company <slug-or-id>` following the CLI
  patterns from part 1.

## Implementation notes (2026-07-11)

- **The write hook is the single bump site.** Rather than have both the
  `StorageService` write hook _and_ `KnowledgeService.store/delete` call
  `bump`, the hook lives entirely in `MinioStorageAdapter` (the true
  chokepoint — every knowledge write, whether via `putKnowledgeFile`,
  `writeFile`, `deleteFile`, `restore`, `move`, or `copy`, funnels through
  it). `KnowledgeService` therefore just drops its old synchronous
  `RagIndexService` calls; it no longer references the reindex path for
  store/delete. This still satisfies "exactly one way embeddings get rebuilt"
  and avoids double-bumping. `KnowledgeService` gains `KnowledgeReindexService`
  only for the manual `reindexCompany` (all-scopes) trigger.
- **Module cycle resolved with `forwardRef`.** `StorageModule` ↔ `RagModule`
  form a deliberate cycle (adapter injects `KnowledgeReindexService`; the
  reindex worker injects `StorageService`). Resolved with NestJS `forwardRef`
  on both module imports and the adapter constructor — no `EventEmitter`
  dependency was needed, so no HALT.
- **stub-llm gained a `/v1/embeddings` endpoint** (`docker/stub-llm/server.js`)
  returning deterministic 1536-dim vectors (honouring `encoding_format`), so
  the end-to-end reindex integration test can exercise real embedding →
  pgvector writes. Retrieval-signature change threaded `companyId` through
  `AgentRagService.retrieve`/`RagRetrievalService.retrieve` and their callers.
- **Poller is an in-process `unref`'d `setInterval`, not a BullMQ repeatable
  job** (deviation from the plan's "repeatable BullMQ job" wording). A
  repeatable job persists in Redis; in the shared-Redis e2e run (`maxWorkers:1`,
  ~13 lcp-server apps booting/tearing down) a job scheduled by an early spec
  fired ~60s in under whatever app was alive then, running `poll()` over all
  accumulated companies (incl. the `embeddingConfig` one from
  `storage-validation-gating`) → cascading 5s test timeouts and a non-exiting
  Jest process. A per-instance interval is scoped to the app's lifetime (never
  fires within a sub-60s test app) and `unref`'d (never keeps the process
  alive); the rebuild worker is force-closed on destroy. Verified stable across
  ~18 e2e runs incl. under heavy CPU load. `poll()` also wraps each scope in
  try/catch so one bad company can't abort the cycle.
