Please prepare a new plan to consolidate LLM provider configuration.

At the moment, the LLM provider keys are stored in config, but all other LLM provider config is in the database (in `LcpCompany` and `LcpRole`) and this makes more sense: a user will want to configure their company or role to use a particular LLM provider, and the configuration of the key is a part of that config.

## Consolidation

Let's consolidate and shift the provider key into the database, too - into `LlmConfig`.

Let's also move `LlmConfig` out of the `LcpRole` model file and into its own.

## Controller update endpoints: deep partial params

Looking at the controllers, I suspect they're not quite right. For the update endpoints, I think they should accept a `DeepPartial<T>` (still omitting `id` and `company` in `LcpRole` (as seen in `LcpRoleTemplate`)). That way, it's possible to also update only part of, eg. the llm config.

`LcpRole` update: should accept a `DeepPartial<LcpRole>` omitting `id` and `company` (both cannot be changed and so should not be included)

`LcpCompany` update: should accept a `DeepPartial<LcpCompany>` omitting `id`.

It's interesting that `LcpCompany` doesn't have a `roles` property - but I think that's ok for now. Please explain what the common practices are around these sort of relationships. I appreciate that `LcpRole.company` best reflects how this is represented in a database, but I'd be interested to know if it's common to have the collection on the parent object, too - so that it can be retrieved in a single query (if needed), for instance.
