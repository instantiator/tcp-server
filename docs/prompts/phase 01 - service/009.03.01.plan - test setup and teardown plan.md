# Test Setup & Teardown — Testcontainers Evaluation (009.03.01)

## Context

Today, five test tiers (`unit`, `integration`, `e2e`, `api`, `smoke`) are orchestrated by ~600 lines of bash across `scripts/run-*-tests.sh`, `scripts/start-deployment.sh`, and `scripts/run-all-tests.sh`, all wrapping the root `docker-compose.yml`. The user asked me to evaluate whether moving this orchestration into Jest itself via the `testcontainers` library (`DockerComposeEnvironment`, which can drive an existing compose file directly from TypeScript) would make testing more conventional and easier for new developers to reason about — and, if warranted, to plan the migration; if not, to recommend leaving things as-is and explain why.

Research (two parallel deep-dives over the shell scripts/compose file, and over the test suites themselves, plus a third targeted dive into BullMQ/Redis connection code) surfaced concrete, already-documented fragility in the **integration** and **e2e** tiers specifically:

- `run-integration-tests.sh` hardcodes and pauses/resumes a **specific container name** (`lcp-dev-lcp-agent-1`) from a _different_ script's compose project, purely to stop a competing BullMQ worker stealing queue jobs off the same shared Redis — a cross-script coupling via naming convention.
- Both `run-integration-tests.sh` and `run-e2e-tests.sh` carry **two divergent teardown code paths** depending on whether a dev stack is "already running" (an opportunistic reuse fast-path), roughly doubling the logic surface to reason about.
- Host ports are fixed, so **no two stacks can run concurrently on one machine** (`docs/scripts.md` documents this explicitly) — `run-all-tests.sh` pre-flight-checks for stray `lcp-*` containers and hard-fails rather than resolving the conflict.
- `test/e2e/e2e-setup.ts` contains an explicit warning comment: running e2e tests directly (bypassing the wrapper script) **hangs rather than fails** — BullMQ enqueue calls block forever against an unreachable Redis. Confirmed at the root cause: neither `apps/lcp-server/src/api/agent-orchestration.service.ts`'s `Queue` nor `apps/lcp-agent/src/worker/agent-worker.service.ts`'s `Worker` sets any bounded retry/timeout options — both pass `{ connection: { url } }` and nothing else, so ioredis/BullMQ's defaults (indefinite reconnect retries, `enableOfflineQueue: true`) mean a call against an unreachable Redis blocks forever rather than failing. `AgentWorkerService`'s `await this.worker.waitUntilReady()` has no timeout at all, so this can hang **application startup itself**, not just tests.
- Integration specs **silently skip** (`console.log('Skipping...'); return;`) rather than fail when required env vars are absent — a false-positive risk if the wrapper script's wiring ever breaks silently.
- `--forceExit` is required for `test:integration`, signalling lingering open handles. Traced: `test/integration/lcp-agent/agent-worker.integration-spec.ts`'s `afterAll` only calls `module.close()`, relying entirely on Nest's `onModuleDestroy` cascade (no explicit ordering/verification that the `Worker` and TypeORM `DataSource` are actually closed before Jest inspects handles). Separately, and more significantly: **neither `apps/lcp-server/src/main.ts` nor `apps/lcp-agent/src/main.ts` calls `app.enableShutdownHooks()`** — confirmed via grep — meaning the existing, correctly-written `onModuleDestroy()` hooks that close the Queue/Worker/pub-sub Redis clients never actually run on a production `SIGTERM` today either. This is a real production gap, not just a test artifact.

By contrast, the **api** and **smoke** tiers are pure black-box HTTP tests against the _fully built, deployed, multi-container stack_ — including a real Keycloak realm bootstrapped via ~80 lines of idempotent `kcadm.sh` logic executed inside the container. `run-api-tests.sh`/`run-smoke-tests.sh` are **already thin** (they do no orchestration themselves) — they are pure clients against a `--base-url`-style already-running target. The **unit** tier needs no Docker at all (SQLite in-memory) and is unaffected either way.

## Recommendation

**Partial adoption**, confirmed with the user after discussing the CI build-cache trade-off in detail (see below). Migrate the **integration** and **e2e** tiers to `testcontainers`' `DockerComposeEnvironment`, driven from new Jest `globalSetup`/`globalTeardown` modules, pointed at the existing root `docker-compose.yml` (unmodified). **Leave `api`, `smoke`, and `unit` exactly as they are.**

Why partial, not full, and not "leave everything as-is":

- For integration/e2e, testcontainers is a straight improvement, not a lateral abstraction swap: it **removes** real bespoke code (hand-rolled `wait_for()` polling, the reuse-detection branch, the hardcoded dev-container-name hack) rather than relocating it. It also **structurally eliminates** two whole bug classes at once — ephemeral, dynamically-port-mapped containers per test run mean no host-port collisions and no shared-Redis-queue race with a dev stack, so the container-name-pause hack and the port pre-flight check (for these two tiers) simply stop being necessary.
- For api/smoke, testcontainers would not remove complexity — it would relocate the Keycloak `kcadm.sh` bootstrap logic from bash into TypeScript with no functional simplification, and **would lose a real, confirmed CI-time optimization**: `.github/workflows/ci.yml`'s `api-test` job builds all 5 app images once via `docker/build-push-action` with `cache-from/cache-to: type=gha` (BuildKit's GitHub Actions cache backend — persists layer cache across ephemeral, otherwise-empty-cache CI runner VMs, so unchanged `npm ci`/build layers are skipped rather than rebuilt from scratch every run), then calls `start-deployment.sh --project lcp-api` **without** `--rebuild` — confirmed by reading both files — so it reuses those already-loaded tags via a plain `docker compose up -d` rather than double-building. `testcontainers-node`'s compose/build support has no equivalent `cache-from`/`cache-to` wiring; moving these builds onto it would mean a full from-scratch 5-image build on every CI run — a real regression, not a hypothetical one.
- **API/smoke must remain instance-agnostic — a permanent invariant, not just this migration's scope boundary.** Per explicit user direction: these tiers are designed to run against _any_ already-running instance (local, CI-deployed, or a remote environment via `--base-url`), so they must never take on responsibility for starting, stopping, or otherwise managing that instance's lifecycle. This migration must not blur that line even incidentally.
- `testcontainers` (npm, MIT license, actively maintained — `12.0.4` used, the latest at implementation time) is a well-established, purpose-built library for exactly the integration/e2e use case (ephemeral dependency containers for a test run), making the adopted portion **more conventional**, not less.

## What's NOT changing

- `scripts/run-unit-tests.sh`, `test/jest-*.json` for unit (embedded in `package.json`) — untouched.
- `scripts/run-api-tests.sh`, `scripts/run-smoke-tests.sh`, `scripts/start-deployment.sh`, `start-dev.sh`/`stop-dev.sh` — untouched. These stay on docker-compose + bash, including the Keycloak bootstrap, and remain pure black-box clients against an already-running instance (see invariant above).
- `docker-compose.yml` and all `Dockerfile`s — **not modified**, per the user's explicit constraint (also useful for deployments). A small new **test-only overlay file** is added alongside them (see below) — additive, not a change to the originals.
- `.github/workflows/ci.yml`'s `api-test` job (image builds + GHA cache) — untouched.

## Implementation plan

### 0. Save this plan

Write this plan verbatim to `docs/prompts/009.03.01.plan - test setup and teardown plan.md` as the first step, mirroring the `009.02.01` precedent.

### 1. Add the dependency

`testcontainers` `^12.0.4` (MIT) as a root devDependency (the latest at implementation time; the plan originally assumed `^11.14.0`). Verify license/audit at install time per standing convention.

### 2. New port-override compose overlay (the load-bearing piece)

`test/support/docker-compose.dynamic-ports.yml` — a small **additive** overlay (not an edit to the real `docker-compose.yml`) using the Compose Spec's `!reset` tag to clear each relevant service's fixed host-port bindings down to container-port-only, so Docker assigns random host ports:

```yaml
services:
  postgres: { ports: !reset ['5432'] }
  redis: { ports: !reset ['6379'] }
  minio: { ports: !reset ['9000', '9001'] }
  stub-llm: { ports: !reset ['3002'] }
```

Without this, `DockerComposeEnvironment` would inherit the same fixed bindings as today (Compose merges `ports:` by dedup, not replace), silently defeating the whole point of the migration. **Validate this overlay works as intended in a first spike before building anything else on top of it.**

### 3. Shared test-support helper

`test/support/testcontainers-env.ts` — `startComposeTier({ services, profiles?, startupTimeoutMs? })` / `stopComposeTier(environment)`, wrapping `DockerComposeEnvironment(repoRoot, ['docker-compose.yml', 'test/support/docker-compose.dynamic-ports.yml']).withEnvironmentFile('.env.testing')`. Resolves `DATABASE_URL`/`REDIS_URL`/`MINIO_ENDPOINT`(/`STUB_LLM_URL`) from `getHost()`/`getMappedPort()` on the started containers. Lives under `test/support/` (test-only tooling), not `libs/lcp-shared` (a runtime library with no existing test-orchestration concern).

**Diagnostics, built in as a v1 requirement, not an afterthought:**

- On any startup failure, capture each service's container logs and **persist them to disk** (`test-results/<tier>-compose-logs/<service>.log`, mirroring the existing `test-results/*.xml` junit-output convention) before rethrowing — not just a console dump, so they survive as artifacts for later analysis rather than scrolling out of a CI log. CI (§9) uploads this directory via `actions/upload-artifact` on failure (`if: failure()`).
- **Distinguish and clearly message common failure modes**, rather than one generic timeout error: (a) a service container that starts but immediately exits/crash-loops (e.g. a misconfigured env var) — detect via the container's exit code/status and surface its logs directly in the thrown error, not just "timed out waiting for healthy"; (b) a port-binding failure — even with the dynamic-ports overlay (§2) this can still surface as a distinct failure mode (overlay misapplied, Docker's ephemeral port range momentarily exhausted) and should be reported as "port binding failed" rather than being folded into an opaque timeout, so the two are never confused during debugging.

### Reuse fast-path: deliberately not carried forward

Today's "reuse an already-running dev stack" fast-path is **not** being replicated — confirmed with the user as the right call, not a regression to mitigate. Integration and e2e tests should run against their own freshly-built, isolated services every time; trading a few seconds of startup time for that isolation guarantee is the correct default, not a compromise.

### 4. Redis/BullMQ fail-fast (production code + test-level, per explicit user request)

**Application-level** (the actual root-cause fix, not just a test workaround):

- `apps/lcp-server/src/api/agent-orchestration.service.ts`'s `onModuleInit()`: before constructing `this.queue = new Queue(...)`, add a bounded Redis-reachability pre-check and throw a clear `Error` (failing app startup — correct behavior for a required dependency) if it fails within a short timeout. Reuse the pattern already proven in this codebase at `apps/lcp-agent/src/health/health.controller.ts`'s `pingRedis()` (the `redis` package's `createClient({url}).connect()`/`.ping()`, unconditionally `.destroy()`d in `finally`), adding an explicit bounded timeout that check currently lacks.
- `apps/lcp-agent/src/worker/agent-worker.service.ts`: same pre-check before `new Worker(...)`/`waitUntilReady()`, which today has no timeout at all and can hang app startup indefinitely.
- Add a Redis health indicator to `apps/lcp-server/src/health/health.controller.ts` (currently checks DB/MinIO/OIDC only — a real, confirmed asymmetry, since lcp-server's `AgentOrchestrationService` and `AgentEventService` both depend on Redis but `/health` can't detect it being down), mirroring lcp-agent's existing `pingRedis()`.
- **Explicitly out of scope**: mid-run resilience (Redis dropping _after_ a successful startup) — a materially larger circuit-breaker/degraded-mode design question, and not what's motivating this work (which is about eliminating hangs when Redis was never reachable to begin with). Document this boundary in code comments so it isn't mistaken for an oversight.

**Test-level** (defense in depth, in addition to the app-level fix):

- Each new `global-setup.ts` (integration and e2e, see §5) performs its own bounded Redis-reachability check immediately after `startComposeTier()` resolves, throwing a clear, actionable error at global-setup time rather than relying on any individual spec later hitting the app-level fix's error path indirectly.

### 5. Jest global setup/teardown (per tier), including fail-loud env vars

- `test/integration/global-setup.ts` / `global-teardown.ts` — starts `postgres`, `redis`, `minio`, `stub-llm` (profile `integration`); performs the Redis pre-check from §4; stores the started environment on `global` for teardown to retrieve (the accepted cross-ecosystem pattern for passing non-serializable state between Jest's `globalSetup`/`globalTeardown`, which share one orchestrator-process context distinct from test workers).
- `test/e2e/global-setup.ts` / `global-teardown.ts` — same, minus `stub-llm`/profile.
- Wire both pairs into `test/jest-integration.json`/`test/jest-e2e.json` via `globalSetup`/`globalTeardown` keys. Keep `maxWorkers: 1` in both (still needed — all workers in a run share one compose environment, so cross-worker races over the same DB/queue remain possible regardless of orchestration mechanism). `testTimeout` is unaffected (it doesn't bound global setup); use `.withStartupTimeout()` in the helper instead (~120s integration for stub-llm's cold-cache build, ~90s e2e).
- **Fail loudly on missing required env vars — done now, as part of this same phase, not deferred.** New `test/support/require-env.ts` (`requireEnv(name): string`, throws if unset) replaces the silent `if (!url) { console.log('Skipping...'); return; }` guards across all `test/integration/**/*.integration-spec.ts` files, and any similarly-optional-looking env reads in e2e specs. `db-factory.integration-spec.ts` keeps its deliberate save/override/restore structure (it exists specifically to test the sqlite-fallback path) — just gated by `requireEnv` for the parts needing real Postgres.
- Trim `test/e2e/e2e-setup.ts`: remove the now-dead `||=` fallbacks for `DATABASE_URL`/`REDIS_URL`/`MINIO_ENDPOINT` and update its header comment — the documented "hangs if run directly" footgun is now fixed at two layers (global setup guarantees infra; the app-level Redis pre-check from §4 fails fast if it's ever unreachable anyway).

### 6. Reduce wrapper scripts

`scripts/run-integration-tests.sh` and `scripts/run-e2e-tests.sh` shrink to the same ~20-line shape as `scripts/run-unit-tests.sh` (help text + arg passthrough + one `npm run test:<tier>` call). Drop: `.env.testing` sourcing, `wait_for()`, `INFRA_ALREADY_UP` detection and its parallel teardown branch, the `lcp-dev-lcp-agent-1` pause/resume hack — all now handled inside Jest's own lifecycle.

### 7. `scripts/run-all-tests.sh`

Sequencing unchanged. Update the pre-flight "no stray `lcp-*` containers" check's justifying comment: it no longer protects the integration/e2e steps (now isolated on dynamic ports), only the later `start-deployment.sh --project lcp-all` step for api/smoke, which still uses fixed ports.

### 8. Close lingering open handles, remove `--forceExit`

- **Diagnose first, don't guess**: run `jest --config test/jest-integration.json --detectOpenHandles` (Jest's built-in diagnostic for exactly this) to identify concretely what's keeping the process alive.
- Hypotheses to test, in likelihood order (per research into current teardown code): (a) `agent-worker.integration-spec.ts`'s `afterAll` relies entirely on Nest's `onModuleDestroy` cascade via `module.close()`, with no explicit ordering guarantee that the `Worker` and TypeORM `DataSource` finish closing before Jest inspects handles — try explicit, ordered closes in `afterAll` before `module.close()`; (b) lingering ioredis reconnect/keepalive timers surviving nominal `.close()`/`.quit()` — try a bounded hard `.disconnect()` fallback if graceful close doesn't fully release within a short window.
- **Related production-code fix, same category of problem**: add `app.enableShutdownHooks()` to both `apps/lcp-server/src/main.ts` and `apps/lcp-agent/src/main.ts` — confirmed missing via grep, meaning the existing correctly-written `onModuleDestroy()` hooks (which do close the Queue/Worker/pub-sub clients) never run on a real production `SIGTERM` today. One line per file, real production value beyond just cleaning up tests.
- **Goal**: remove `--forceExit` from the `test:integration` npm script; verify by running without it and confirming Jest exits on its own.

### 9. CI (`.github/workflows/ci.yml`)

Remove the `if: always()` → `docker compose down -v` cleanup steps in `integration-test` and `e2e-test` (superseded by `globalTeardown`'s explicit `.down({removeVolumes:true})` plus testcontainers' Ryuk reaper for ungraceful exits — and these steps already target the wrong compose project name today, a pre-existing latent no-op being removed anyway). No DinD/socket changes needed — `ubuntu-latest` already has a working Docker Engine, proven by the current scripts. Add a temporary `docker compose version` diagnostic step during the migration PR to catch CLI-version drift early (testcontainers-node's compose support shells out to the `docker compose` CLI, which has had version-sensitivity issues historically). Add an `actions/upload-artifact` step, `if: failure()`, uploading `test-results/<tier>-compose-logs/` for both `integration-test` and `e2e-test` jobs — so the persisted-to-disk diagnostics from §3 are retrievable from a failed CI run, not just visible in a local terminal.

### 10. Migration order

1. Spike + validate the dynamic-ports overlay in isolation.
2. Convert **integration** first (smaller — 43 tests; no in-process app boot; contains the highest-risk sub-problem, the `stub-llm` profile+build service, so the hardest unknown is de-risked earliest; also removes the most accumulated hackiness). Includes: the Redis fail-fast app-level fix (§4), `requireEnv` cleanup (§5), and the open-handles investigation (§8), since all three concentrate in this tier. Run `./scripts/run-integration-tests.sh` (without `--forceExit`, per §8's goal) to prove parity before continuing.
3. Convert **e2e** second, reusing the now-proven helper unchanged apart from dropping `stub-llm`. Includes trimming `e2e-setup.ts` and its own `requireEnv` cleanup pass. Run `./scripts/run-e2e-tests.sh`, and additionally prove the "hang" footgun is fixed by running `jest --config test/jest-e2e.json` **directly** (no wrapper).

## Key risks (carried into the ADR)

1. The dynamic-ports overlay is the single point of failure for the entire integration/e2e rationale — validate first, before building anything on top.
2. Default failure diagnostics from testcontainers are weaker than today's `wait_for()`+log-dump by default — §3's persisted-logs-plus-distinguished-failure-modes behavior must be built into the shared helper as a v1 requirement, not assumed or deferred.
3. `testcontainers`' compose support shells out to the `docker compose` CLI (version-sensitive) rather than talking to the Engine API directly — verify the CLI version in CI explicitly during rollout.
4. The open-handles root cause is not yet confirmed — `--detectOpenHandles` must be run before committing to a specific fix, per this repo's standing "diagnose before fixing" convention.
5. The Redis fail-fast fix is scoped to startup-time reachability only; mid-run Redis loss is explicitly not addressed by this pass — a future, separate piece of work if needed.
