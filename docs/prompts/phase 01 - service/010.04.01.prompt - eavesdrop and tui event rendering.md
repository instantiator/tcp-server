## Rendering in `tui`, `eavesdrop`, `chat`

This is an opportunity to consolidate the rendering, too.

- the content of an assignment pane in the TUI should look like the eavesdrop of an assignment
- the eavesdrop of a task should look like a combination of eavesdropped assignments, with additional headings and task events

Shared rendering classes should be able to support both eavesdrop and tui, for historical and live events. (Caveat: streamed text like reasoning and response should _look_ similar in format, but I recognise it needs separate code to be able to render as it is streamed.)

Some may also need to be able to render a live stream as well as an audit event, and so the classes should implement either or both of the interfaces.

These classes (above) can then be used by history or stream rendering management classes to render the individual items. Propose a set of classes that line up to the tui/eavesdrop/chat, historical-audit/live-audit/streamed-live-event combinations of requirements.

Re-use as much code as possible from what we have. Prioritise DRYing up, and getting the rendering to look right.

### Rendering patterns

At the moment, things aren't consistently rendered. Here's my preference:

```text
<time> | <AuditEventType>[:kind[:activity[:tool]]] |

  <text content>

```

- If present, content is always indented and wrapped.
- If text content is JSON it's always formatted, ie. with json indenting.

A heading block each time the agent/assignment/task changes. It should appear in both. eg.

```text
Task id:              <id>
Task shortcode:       <shortcode>
Assignment id:        <id>
Assignment role:      <role name> (<role slug>)
Assignment role id:   <id>
Assignment mode:      <mode>
Assignment shortcode: <shortcode>
Agent id:             <id>
```

- The heading and each event entry are all separated by a blank line.

### Some specifics

Let's be more cautious about when to render entire json blocks. I think eavesdrop became significantly less useful as soon as we started rendering json blocks containing the full message history, for instance. Better to just render the content part of the event - ie. the text of an input, a tool call, reasoning text, response text, etc.

For many events, there needn't be text content. Things like state changes can be shown as just the event line:

```text
<time> | <AuditEventType>[:kind[:activity[:tool]]] [| <new state>]
```

However, some contain text data:

- `tool_call` / `tool_result` (or `tool_started` / `tool_complete`) - this should be preserved as the json of the call
- `response` - just the text of the response
- `reasoning` - just the text of the reasoning
- `input` - just the text of the input (either from the user, from a consultation, the corrective inputs provided like 'you narrated a tool call but...', etc.)

Those can be rendered with the text content spaced and indented, ie. the pattern shown above:

```text
<time> | <AuditEventType>[:kind[:activity[:tool]]] |

  <text content>

```

### Iterations (x2)

Let's increase the default number of iterations an agent can go through. IIRC you mentioned in an earlier conversation that an earlier failed task was trying to do the right thing (although reasoning under difficult circumstances that we're going to fix), when it ran out of iterations. You mentioned a default of 10 iterations, which feels small for more complex tasks. However, the `.env.testing` and `.env.example` files suggest the default is 20 (ie. `# AGENT_ITERATIONS=20`). Please clarify and double the default from whatever it currently is - reflecting the new value across the `.env*` files, too.

### Storage tools and planning hints

The issue that the agent encountered in the example mentioned above is that it was in finalisation mode, trying to reconcile a markdown file that should have been a csv file. The planner is partially responsible, it should have provided required outputs to individual tasks that matched the final output type - but really this is because we're not hinting well enough. We should help the planner and individual tasks to get this right by:

- Hinting to the planner that the final expected output files and their types should be woven into the plan, ie. to direct agents to create those files during the plan, rather than rely on a separate reconciliation process at the end
- Adding a file replacement tool (the agent can use this instead of trying to do a string replacement, or a sequence involving deleting and then creating a new file)
- Making it easier to use the tools by adding a file creation tool, too, that accepts content -- At the moment, the append tool serves both create and append (and it should continue to create a file if it doesn't exist), but providing a create file tool that will attempt to create a new file (and can overwrite the file if an overwrite flag is set, or fail with a warning if that flag is not set and the file exists), makes it easier for the agent (hopefully) by reducing the amount of reasoning it needs to do

NB. Please offer an alternative approach if you perceive a better way to support the agents here, or to help reduce the reasoning they need to do. We originally limited the tools provided to the agent because we wanted to support agents with smaller context windows, and we still do - so there's a balance to be found.

### Failure reasons

When assignment fail, they're given a failed status.

It would be helpful also to track a nullable `failureReason` property on the assignment, too. It should be used to explain why they failed in simple terms, eg.

- `timed out after ${secs} seconds`
- `exceeded ${maxIterations} iterations`
- `created a plan with 0 assignments`
- `did not call required tools: ${csvOfRequiredToolCalls}`
- `did not pass QA`
- `unexpected LLM failure`
