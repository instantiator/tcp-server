# Task orchestration 6/8: assignment-scoped storage tools

Part 6 of the task-orchestration work (map: `010.2.0 - task orchestration: overview.md`;
parts 1–5 are in place — in particular every agent has an assignment, and
`GET /internal/agent/:agentId/assignment` exists on lcp-server).

> **Recommended implementing model: Sonnet.** The tools are thin,
> fully-specified proxies following the existing storage-tools pattern; the
> scoping rules below leave no design decisions open.

## Goal

Replace the permissive general **write** tools in `lcp-mcp-storage` with
assignment-scoped working-file tools, and add material-file tools. The LLM
supplies only a filename; the directory prefix is derived server-side from the
calling agent's assignment — fewer parameters for the model to get wrong, and
no way to write outside its own working area.

Policy (user-decided):

- **Kept, unchanged (read-only)**: `describe_server`, `describe_folder`,
  `list_files`, `read_file`, `search_files`, `get_file_properties`,
  `get_file_summary` — agents may still explore shared storage.
- **Removed from agent exposure**: `write_file`, `delete_file`, `restore_file`,
  `copy_file`, `move_file`. (The lcp-server `/internal/storage/*` endpoints
  behind them remain — the knowledge API, storage proxy endpoints, and future
  orchestration copying still use them.)
- **New (assignment-scoped)**: the tools below.

## Scoping rules (agreed — do not re-derive)

The working directory for an assignment (helpers exist from part 3):

- task assignment: `{companySlug}/tasks/{taskId}/assignments/{orderIndex}/working/`
- orphan assignment (`taskId` null): `{companySlug}/assignments/{assignmentId}/working/`

Per caller mode (from the caller's assignment, fetched via
`GET /internal/agent/:agentId/assignment`; `agentId` is auto-injected by
`McpClientService`, never model-supplied):

- `implement` / `plan`: working tools target the agent's **own** assignment's
  working directory (read and write).
- `qa`: working tools target the **target assignment**'s
  (`targetAssignmentId`) working directory, **read-only** — the mutating
  working tools (`append_working_file`, `replace_in_working_file`,
  `delete_working_file`, `restore_working_file`) return a clear "not available
  in qa mode" error.

Material files: the caller's assignment's `materials` array resolved to
concrete storage keys via `resolveArtifactKey` (part 3 — most-recent-version
rule for `assignment-completed-path`). `inline-text` materials are returned as
literal content by `read_material_file` (keyed by a stable synthetic name,
e.g. `inline-1`, as listed by `list_material_files`). For qa-mode callers the
materials view is the **target** assignment's materials.

Filename safety: tools accept a relative filename (subdirectories allowed).
Normalise and reject absolute paths and any `..` segment with a corrective
error. Never let the resolved key escape the working prefix.

## New tools (register in `apps/lcp-mcp-storage/src/mcp/storage-tools.service.ts`)

| Tool                           | Input (besides injected identity) | Behaviour                                                                                                                                                                               |
| ------------------------------ | --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list_working_files`           | —                                 | list the working directory (same entry shape as `list_files`)                                                                                                                           |
| `get_working_file_properties`  | `filename`                        | like `get_file_properties`, scoped                                                                                                                                                      |
| `read_working_file`            | `filename`                        | read; friendly error if missing                                                                                                                                                         |
| `append_working_file`          | `filename`, `content`             | append; **creates the file if absent**; content validation runs on the resulting document (existing validators)                                                                         |
| `replace_in_working_file`      | `filename`, `find`, `replace`     | replaces **all** occurrences of the literal string `find`; error stating so if the file is missing or `find` occurs zero times; reports the replacement count; validation on the result |
| `delete_working_file`          | `filename`                        | soft delete (same `_deleted/` mechanism as `delete_file`)                                                                                                                               |
| `restore_working_file`         | `filename`                        | restore a soft-deleted working file                                                                                                                                                     |
| `list_material_files`          | —                                 | resolved materials list: storage-backed entries + inline-text entries                                                                                                                   |
| `get_material_file_properties` | `filename`                        | properties of a material file                                                                                                                                                           |
| `read_material_file`           | `filename`                        | read a material file (or return the inline text)                                                                                                                                        |

Implementation shape: like the existing tools, each is a thin proxy —
resolve scope via the internal assignment endpoint, then call
`/internal/storage/*`. Cache the assignment lookup per tool call only (no
cross-request state; servers are per-request).

New lcp-server internal storage primitives (in the internal storage controller

- `StorageService`): **append** (`POST /internal/storage/append` —
  read-modify-write with validation of the result) and **string-replace**
  (`POST /internal/storage/replace` — body `path`, `find`, `replace`; returns the
  occurrence count). Reuse the existing write/validation/audit/origination
  plumbing — these are variants of `write`, not a new subsystem.

## Ripple effects (verify each)

- **Storage-change tracking**: `apps/lcp-agent/src/agent/loop-tracker.ts`
  (`applyStorageResult`, `generateActionString`) maps storage tool names to the
  created/modified/deleted tracking on `LcpAgent.storageChanges`. Add the new
  tool names (append → created-or-modified, replace → modified, delete/restore
  accordingly) and remove mappings for tools that no longer exist. Grep
  `loop-tracker` and its spec for the old names.
- **Prompts and descriptions**: `storage-prompts.ts` / `prompts.jsonc`,
  `storage-tool-descriptions.ts` / `tools.jsonc`, and the `describe_server`
  text must present the new toolset (and stop mentioning removed tools).
  The implement-mode prompt in `@lcp/shared` (`MODE_PROMPTS`) should mention
  working files as the place to produce outputs.
- **Existing tests**: grep `write_file|delete_file|restore_file|copy_file|move_file`
  across `apps/`, `test/integration/`, `test/e2e/`, `test/api/`, `test/smoke/`,
  stub-llm fixtures, and docs — anything driving agent writes through the old
  tools needs migrating to the new ones.
- **lcp-cli**: no CLI change expected (the CLI talks to lcp-server REST, not
  the MCP tools) — confirm with a grep for the removed tool names under
  `apps/lcp-cli/`.

## Tests

- Unit: filename normalisation/traversal rejection; qa-mode read-only
  enforcement; scope resolution for task vs orphan vs qa; inline-text material
  listing/reading; replace-count/zero-occurrence behaviour.
- Integration: append/replace internal endpoints (create-on-append, validation
  failure on a result that breaks the document's format, audit events,
  origination fields); working-file round-trip via the MCP tool handlers
  (public methods on the tools service, per the existing testing approach).
- e2e: an implement-mode agent (stub-llm) produces a file via
  `append_working_file` and it lands under the correct working prefix; a
  qa-mode agent can read but not modify.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.
- Do not add dependencies unless truly needed; if unavoidable, latest version,
  license/health checked. Do not update existing dependencies. No unrequested
  changes outside this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Never `--no-verify`.

Write unit/integration/e2e/API tests alongside each unit of code — main, edge,
and failure cases; verify HTTP response codes explicitly. Update existing tests
as code changes (grep `test/` directories by class name when changing
constructors or behaviour).
