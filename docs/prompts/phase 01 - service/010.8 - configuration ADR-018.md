## Thoughts for discussion

I'm leaning towards our preparing a setup script for a deployment that walks the user through all their first-time choices, and records their choices in the `.env` of their choice. Suggest we prepare it as a small node/ts application, eg.

_For each question, the prompt also indicates that the user may press `?` for an explanation._

"What is the name of this instance? (default: lcp-dev)"
"What is the name of the .env file to hold this configuration? (default: .env.dev)"
"Do you wish to provide LLM configuration at application level for an embedding model? (y/n)"
"Do you wish to provide LLM configuration at application level for an inference model? (y/n)"
"Will you be using a third party OIDC authentication provider? (y/n)"
"What is the maximum number of iteration an agent can perform? (default: <drawn from .env.defaults>)"
"What is the maximum number of concurrent agents? (default: <drawn from .env.defaults>)"

> If the user wishes to provide LLM configuration, that would open up a separate set of questions for them to fill out.
> Each LLM model config would be tested to ensure the model is reachable before proceeding.
> The embedding model config would also take steps to establish the vector size for the embedding model and provide that as config that lcp-server can use when migrating the database on startup if required.
> It should explain the implications of changing an embedding model after the fact, and we should break out the "set embedding model" work into a separate script so the user can modify the config later

> Similarly, if the user wishes to provide config for an OIDC server, this also opens a separate set of questions.

I'm also starting to think we ought to support multiple `.env` settings, eg. instead of assuming `.env` by default, lcp-dev should work from `.env.dev` (by default) and no code should ever try to read from / use / export `.env` automatically - instead, it should use the specified env file. (This has the benefit that `.env` won't be automatically exported by a locally running tool.)

Ideally, the configuration would be able to use multiple env files, with an order of precedence.

lcp-dev would use these by default:

- .env.dev (overrides or provides missing values)
- .env.defaults (fallbacks for anything not specified in .env.dev)

The testing suites would use these by default:

- .env.testing (overrides or provides missing values)
- .env.defaults (fallbacks for anything not specified in .env.dev)
