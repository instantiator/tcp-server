> [!IMPORTANT]
>
> ## The guardrail — read this before touching anything
>
> **Split along real seams — a cohesive responsibility moving to its own module —
> not to hit a line count.** The 400-line limit is aislop's opinion. Our standards
> say readability wins, and `dev-environment/guidance/standards/readability.md`
> asks for short single-purpose functions and grouping by purpose or concept.
>
> If a file resists a natural split, **leave it and record why** in your report.
> A 500-line file with one coherent responsibility is better than two 250-line
> files that have to be read together to make sense. Do not create
> `foo-helpers.ts` dumping grounds, and do not extract a function whose only
> caller is one line away.
>
> **Behaviour must not change.** These files contain atomic state transitions,
> optimistic-concurrency claims and idempotency guarantees. The existing suites are
> your safety net; run them constantly.

## Non-goals

  do not fix it inside a refactor commit, where it will be invisible in review.
- The 4 CLI/TUI files (011.1.5).

# Units of development

**One file per unit.** Each unit ends with the full test suite green and a quality
gate. Do not start the next until the current one is green. **Commit per unit** —
if a regression surfaces later, you want to bisect to a single file's refactor.

Suggested order: hardest and highest-value first, while attention is freshest.

## Unit 7 — `db.service.ts` (477 lines)

## Code quality requirements

Route via `AGENTS.md` → `dev-environment/guidance/index.md`; read
`process/before-coding.md` first, `standards/readability.md` (directly relevant
here), and `process/after-coding.md` when done. State the filename of each
guidance doc you read.

- **After every unit**, run `./dev-environment/scripts/check.sh` **and the full
  test suite** before starting the next. Never bypass a hook with `--no-verify`.
- Zero compiler and linter **errors and warnings**.
- Never cast to `any`, especially in test mocks — type the mock instead.
- Comments state **intent**, not mechanics. Every new module, class and exported
  function gets a TSDoc comment saying what it is for; `{@link}` for type
  references; no decorative separator comments.
- **No unrequested abstractions.** Moving code into a module is not licence to add
  an interface, a factory, or a config option along the way.
- Function names should state the decision being made — the parent prompt asks
  specifically for "clear function names, clear decision making functions".
- When changing a class's constructor or behaviour, grep `test/integration/` and
  `test/e2e/` by class name too, not just the owning app's `src/`.
- Migrations: none expected. If you find yourself needing one, you have changed
  behaviour — stop.
- Full suite via `./scripts/run-all-tests.sh`; e2e via `./scripts/run-e2e-tests.sh`,
  never bare `npm run test:e2e`.
- aislop is opinionated and can disagree with these standards. Where they conflict,
  **the documented standards win** — including its 400-line limit.
