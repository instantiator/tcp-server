## Agent consultations

I took a look at the current request flow.

It looks like `InteractionsToolsService.registerRequestAgentConsultation` really does accept a `roleName` parameter which, in turn, is passed to the `/internal/pause` controller method. True enough, `InternalController.pause` accepts a `PauseDto` parameter, which contains `roleName`.

In turn, this controller calls `PauseAndResumeService.pauseForConsultation` which also expects `roleName` and does the work of pausing the calling agent, and initiating a new agent based on the new role. It uses `this.roleRepo.findOne` to locate the role it should contact. I suspect I've tripped over this issue because the company I'm using to test has more than one copy of the same role, and so the role name is not unique (and so `findOne` won't succeed).

I believe the role **id** should be passed through these calls, so that it's unambiguous which role the message is for. (We can keep the role name so it's easy to log and audit log what's happening.)

## User queries

I suspect this is very likely to also affect the user querying capability, ie. `InteractionsToolsService.registerRequestUserInput` and, in fact, I note that this function doesn't accept any indication of the user / users to consult at all. I suspect it was first written before there was expected to be any kind of multi-user involvement in the system. Please also update the user input request to allow an agent to specify one or more users to request a response from.

I believe there was an intention that any of the specified users may respond, so resuming the agent with their response. If the LLM wishes to consult more than one user and get all their responses, it should submit separate requests.

## Resume conditions

There's an implied additional step there - the agent should only resume if it has no outstanding agent consultations or user requests.
