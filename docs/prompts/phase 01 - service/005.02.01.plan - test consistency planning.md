## 0. Why `GET /api/company/:id/roles` test passes (it shouldn't)

Two coincidences stack:

1. `expect(companies.some(...))` **has no matcher** — Jest creates an Expect object but never calls `.toBeTruthy()` or similar. The test makes no assertion. This is the primary cause.
2. Even if the matcher existed: `c.id === company.id` is always `false` (role UUID ≠ company UUID), so `&&` short-circuits before `c.roles.some(...)` runs. If it did run, it would throw `TypeError: undefined is not a function` because `LcpRole` has no `roles` property.

The `ApiHelper.listRoles` return type is also wrong (`{ id, name, roles }[]` instead of `LcpRole[]`) but TypeScript types are erased at runtime, so the wrong type doesn't cause a runtime error — it just means the TypeScript compiler accepted the broken assertion.

## 3. Refactor e2e tests to `describe / with / it` pattern

### The pattern

Fixtures are created in `beforeEach` (not inline in `it`), so each test is self-contained:

```typescript
describe('with a company', () => {
  let company: LcpCompany;

  beforeEach(async () => {
    // create fixture — fresh for each it, afterEach will clean up
    const res = await request(app.getHttpServer())
      .post('/api/company')
      .set('Authorization', `Bearer ${jwt}`)
      .send({ slug: 'acme', name: 'Acme Corp', description: '...' });
    company = await companyRepo.findOneByOrFail({ slug: 'acme' });
  });

  describe('GET /api/company/:id', () => {
    it('returns the company by UUID', async () => {
      const res = await request(app.getHttpServer())
        .get(`/api/company/${company.id}`)
        .set('Authorization', `Bearer ${jwt}`)
        .expect(200);
      expect((res.body as { slug: string }).slug).toBe('acme');
    });
    // ... more its, each gets a fresh company from beforeEach
  });
});
```

**Key difference from `api.spec.ts`:** E2E tests use `beforeEach` (not `beforeAll`) for fixtures because the outer `afterEach` deletes all records after every `it`. Using `beforeAll` would mean only the first `it` in a `describe('with a X')` block sees the fixture.

### Target structure for `test/e2e/app.e2e-spec.ts`

```text
describe('CompanyController (e2e)')
  beforeAll: boot NestJS app
  afterEach: delete all records
  afterAll: close app

  describe('POST /api/company')
    it('returns 201')
    it('returns 401 without a token')

  describe('POST /api/company (slug replacement)')
    it('replaces an existing company with the same slug on a second POST')

  describe('with a company')
    beforeEach: POST /api/company → company
    describe('GET /api/company/:id')
      it('returns the company by UUID')
      it('returns the company by slug')
      it('returns 200 with empty body for an unknown UUID')
    describe('PUT /api/company/:id')
      it('updates the company name')

  describe('with a company that has llmDefault')  [for the 400 guard test]
    beforeEach: POST company with llmDefault
    describe('with a role that inherits llmDefault')
      beforeEach: POST role with no llmConfig
      describe('PUT /api/company/:id')
        it('returns 400 when removing llmDefault would leave role without config')

describe('RoleController (e2e)')
  beforeAll: boot NestJS app
  afterEach: delete all records
  afterAll: close app

  describe('with a company')
    beforeEach: POST /api/company → company
    describe('POST /api/role')
      it('returns 201 when role has explicit llmConfig')
      it('returns 400 when role has no llmConfig and company has no llmDefault')

  describe('with a company that has llmDefault')
    beforeEach: POST company with llmDefault
    describe('POST /api/role')
      it('returns 201 when role has no llmConfig but company has llmDefault')
```

## 4. CI integration (`.github/workflows/ci.yml`)

### Add `api-test` job

Run parallel to `e2e-test` (both depend on `smoke-test`):

```text
build ─┐
       ├─→ unit-test → integration-test → smoke-test ─┬─→ api-test
lint  ─┘                                              └─→ e2e-test
```

```yaml
api-test:
  name: API tests
  needs: [smoke-test]
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v7
      with:
        submodules: true
    - uses: actions/setup-node@v6
      with:
        node-version: '24'
        cache: npm
    - uses: docker/setup-buildx-action@v4
    - name: Build lcp-server image
      uses: docker/build-push-action@v7
      with:
        context: .
        file: apps/lcp-server/Dockerfile
        push: false
        load: true
        tags: lcp-server:latest
        cache-from: type=gha,scope=lcp-server
        cache-to: type=gha,scope=lcp-server,mode=max
    - name: Build lcp-agent image
      uses: docker/build-push-action@v7
      with:
        context: .
        file: apps/lcp-agent/Dockerfile
        push: false
        load: true
        tags: lcp-agent:latest
        cache-from: type=gha,scope=lcp-agent
        cache-to: type=gha,scope=lcp-agent,mode=max
    - run: npm ci
    - run: ./scripts/run-api-tests.sh
    - if: always()
      run: docker compose --profile auth down -v
```

Also fix the **version inconsistency in `smoke-test`**: the lcp-server build step uses `docker/build-push-action@v6` while lcp-agent uses `@v7`. Standardise both to `@v7`.

## 5. UUID type changes — risk assessment

`UUID` from Node's `crypto` is `\`${string}-${string}-${string}-${string}-${string}\``— a branded string,`string` at runtime. TypeORM uses column decorators, not the TS type, for DB column behaviour. **No runtime risk.**

Minor inconsistencies to address while touching related files:

- `api.agent.controller.ts:140` — `streamEvents(@Param('id') id: string)` → `UUID`
- `AuditEvent.model.ts` id fields — `string` → `UUID` for consistency
- `db.service.ts` — `updateAgentStatus(id: string, ...)` → `UUID`

These are mechanical changes with no behavioural effect. Include as a tidy-up pass.
