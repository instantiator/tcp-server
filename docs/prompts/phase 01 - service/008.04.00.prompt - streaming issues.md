Thanks! I ran my own test with `lcp-cli`, and asked chicken assistant to offer cat assistant some kibble. The system largely did the right thing, but there are a few issues we should talk through...

Let's draft a new plan to address the points below. There are two major themes to this plan:

1. Context management
2. Cosmetic improvements to lcp-cli

Both are reasonably sized - the cosmetic improvements likely invoke use of a TUI library or framework.

As with other plans - please incorporate suggestions into the plan where you see opportunities to improve on the goals.

## Context management

`docs/prompts/008.04.00 - task-completion-context.json` contains the context window for chicken assistant right before task completon.

I've noted some parts that stood out for attention below.

The context window defined in LM Studio is `8192` and I think that agrees with our default configuration, `DEFAULT_LLM_CONTEXT_WINDOW` in `defaults.ts`

### Some issues relating to that

- "Context size has been exceeded" happened again, similar to what you saw
  - This suggests that one of our protections didn't step in and try to compact the context
  - This almost certainly led to the final response from chicken assistant not appearing (ie. wasn't generated)
  - The cli tool showed `LLM state: tool_started: interactions__complete_task` but it never succeeded or failed

- We should detect when we exceed context window size issues
  - Compaction should run once
  - If that's still no good, the agent should fail and stop

### Speculation

- The context window always contains a full defintion of every available tool from all MCP services.
  - Each MCP service offers describe, which then offers the full description
  - This takes up a lot of the context
    We want to retain support for models running with smaller context windows

### Suggestions

- Is it possible to have the full list of tools for an MCP service included in the context _only after it has been described?_ (Before that, we'd just list the service and the describe tool)
  - We should explain in the prompt that the LLM should be sparing about which tools it chooses to describe and invoke, to avoid clutter in the context
  - To avoid duplication, an MCP service's describe should return a short sentence or two about when to use it / advice about which tools to use for certain tasks (rather than the full description of all tools - because it activates the full list of tools for the MCP service only after the describe has been called)
  - Then, after the describe has been called, the MCP service's full set of tools can be included in the context
  - These should be guaranteed shown for a small number of iterations (what's best? 1-3?), and considered ok to switch off again (ie. go back to just the describe tool) during compaction after that - so if the LLM doesn't call a tool from the MCP service immediately, it may have to call describe again to learn about the tools again
    - maybe keeping the tools showing for a few iterations is good, in case it makes an incorrect call, or needs to iterate on what it found

- Did compaction fail to run?
  - It's possible our logic for when compaction should run missed an opportunity (perhaps because it was the first iteration for the LLM, or perhaps because we don't check the context size at every iteration? eg. are tool results treated differently?)
  - Equally, I don't think compaction would have helped because so much of the context was the tools info, which doesn't get compacted

### Finishing

We finish tasks in several ways.

- The last thing the agent says
- `complete_task`
- `completion_summary_prompt`

`complete_task` asks for `finalAnswer` and `outputFiles` - output files is necessary, so that (eg.) if the task is finding files then this is available in a structured form. Final answer could come from the content itself?

This is an opportunity for optimisation (either to reduce the number of iterations for the LLM, or the amount of content it needs to either consume or generate) - although I'm not yet sure how is best.

Please propose 1 or more options. If choosing implement a suggestion below (or not), please explain your reasoning in the plan.

Suggestions:

1. Instead of making a final `complete_task` call, the agent could make calls to `add_completion_item`
   - completion items could be: file paths, pieces of information
   - a summary isn't needed, just the items
   - then when the LLM ends the chat naturally, the completion items could be bundled together with the last thing the LLM says as a task completion record

2. Passing `completion_summary_prompt` to the LLM (and waiting for its response) feels like an unnecessary extra cycle
   - It's probably enough, for now, to store a simple version of the current completion summary prompt. eg.

   ```text
   Task completed.\n\nActions taken (in order):\n{{actionLines}}\n\nStorage changes:\n- Created: {{created}}\n- Modified: {{modified}}\n- Deleted: {{deleted}}\n- Moved: {{moved}}
   ```

If both implemented, this is 2 MCP tools that are made redundant and could also reduce the size of the context.

### Possible (smaller) optimisations / fixes

- Combine list users and list roles
  - This could be a single tool, which would reduce the number of iterations the LLM needs to figure out who it can consult with

- Blank responses
  - When the consultation begins and an agent is paused, the tool adds a message to that effect, and the assistant adds an empty response. This feels like wasted context and could be either:
    - immediately removed from the context
    - prioritised for deletion during compaction

      ```json
      {
        "role": "tool",
        "content": "Paused. Consultation request dispatched to 'Cat as... <Truncated in logs> ... automatically when the consulting agent responds.",
        "name": "interactions__request_agent_consultation",
        "tool_call_id": "113213332"
      },
      {
        "role": "assistant",
        "content": ""
      }
      ```

  - Running the LLM cycle on a message to tell it that it has been paused and that it'll be resumed when there's a response also feels like a waste of time and resources (especially if the LLM service is billed).

- Duplicate consultation response
  - The consultation response seemed to have been added to the context twice:

    ```json
    {
      "role": "user",
      "content": "Consultation response: Meow-mew! Cluck-cluck back ... <Truncated in logs> ... kindly from one young furry friend to another! 😻"
    },
    {
      "role": "user",
      "content": "Consultation response: Meow-mew! Cluck-cluck back ... <Truncated in logs> ... kindly from one young furry friend to another! 😻"
    },
    ```

### Additional suggestions

- Compaction could be cleverer
  - We should try to mark things that are inessential, things that can be shortened, and things that must remain - so that our compaction can choose between removing, summarising, and preserving each part of the context.

## Cosmetic improvement

The two streams became quickly mingled when things happened concurrently, and the source of various messages and reasoning wasn't clear. It could be time to switch to some kind of TUI.

Possible examples:

- <https://opentui.com/>
- <https://rezitui.dev/>

(I'm leaning towards OpenTUI, but please evaluate all options.)

Please plan out an implementation that:

- Creates a tab for each agent it is monitoring
- Enables the user to scroll up and down inside each tab
- Shows events, reasoning, and responses from agents in the appropriate tab
- Provides an input box at the bottom of the screen for the tab of agents the user can talk to (rather than those being consulted)

- Format events into 3 columns (column headers not required):
  - Time (hh:mm:ss)
  - Event type
  - Event text

Events should be separated by a blank line.

Event text should be whitespace trimmed, word wrapped, and have line breaks removed at the end.

- Reasoning is a special case.
  - Print it in grey, indent a couple of spaces, and word wrap
  - It doesn't need time or event type
  - It can be interrupted by an event, and when it is
    - there should be line breaks between the event and the reasoning
    - and similarly line breaks if reasoning continues

eg. tabs at top, events and reasoning in between

```text
 _______________
| Cat assistant | Chicken assistant |
========================================================
                                                       ⬆️
hh:mm:ss | some_event | text of the event

  reasoning begins and is interrupted by an event...

hh:mm:ss | some_event | text of the event

  reasoning continues here and is word wrapped at the
  end of the line, it is also indented and printed in
  grey

hh:mm:ss | response | text of the response




                                                       ⬇️
________________________________________________________
| > user input here                                    |
________________________________________________________
```

The UI should fill the available space in the terminal as best it can.

(Excuse the aesthetics - actual rendering of tabs, boxes, scroll bars, etc. is expected to look better and be handled by the TUI library of choice.)
