> [!IMPORTANT]
>
> ## The guardrail
>
> **Split along real seams — a cohesive responsibility moving to its own module —
> not to hit a line count.** The 400-line limit is aislop's opinion; our standards
> say readability wins. If a file resists a natural split, **leave it and record
> why**. No `tui-helpers.ts` dumping grounds.
>
> **Behaviour must not change.** The TUI's rendering and key handling are the part
> of this product a human actually looks at, and its failure mode is "renders
> nothing", which no type checker will catch.

> [!WARNING]
>
> ## terminal-kit rules — violating these is how the 008.7 bug shipped
>
> The TUI uses terminal-kit 3.1.3's Document widgets, whose real API differs from
> what `@types/terminal-kit` (2.5.7) describes. A local ambient
> `terminal-kit-document.d.ts` declares them, written against the real sources in
> `node_modules/terminal-kit/lib/document/`.
>
> - Elements default to **1×1** without an explicit width/height.
> - `Container.resize()` resizes only the internal ScreenBuffer, **not** the drawn
>   element (only `moveTo` moves it). Avoid Containers; size TextBoxes directly
>   with `setSizeAndPosition()`.
> - A Document pins itself at `outputDst` (1,1); child coordinates are 0-based
>   rows `0..H-1`. That off-by-one offset is why test ScreenBuffers are one row
>   and column larger than the terminal.
> - **Never reposition an `InlineInput`** — its prompt TextBox is positioned at
>   construction only. Rebuild it instead, preserving `getValue()` as a draft.
> - `InlineInput` consumes TAB, CTRL_LEFT/RIGHT and UP/DOWN; Enter submits and is
>   reusable (`submitted` is never set); ESC-cancel is off by default.
> - `disabled = true` blocks submit but **not** typing.
> - A focused TextBox scrolls natively and emits `'scroll'`.
>
> **How to test — mandatory:** never fake the widget classes. That is precisely how
> the never-renders bug shipped: the fakes agreed with the wrong API assumptions.
> `Tui` accepts `term` (an EventEmitter plus width/height and
> fullscreen/grabInput/processExit stubs) and `outputDst` (a `ScreenBuffer` one
> row and column larger than the term). Feed synthetic
> `emitter.emit('key', name, [name], { isCharacter, codepoint })` events and
> **assert on `screen.dumpChars()`**. Follow `makeTui()` in
> `apps/tcp-cli/src/lib/tui/tui.spec.ts`.

# Units of development

**One file per unit.** Each ends with the full suite green and a quality gate.
Leave the work uncommitted. Existing specs — `tui.spec.ts`, `tui-format.spec.ts`,
`tui-state.spec.ts`, `commands/tui.spec.ts` — are your safety net; most assert with
`toContain`, so they survive reasonable churn.

## Unit 1 — `panes.ts` (652 lines)

Do this first: it is the cleanest split and it de-risks the others.

The file holds a `Pane` base class plus four subclasses. **One file per pane class**
is the obvious seam:

- `Pane` base (66–110) — `redraw`, `renderErrorBanner`, `afterRedraw`, `scrollLineIntoView`
- `AssignmentPane` (113) — event log, paging, `atBottom`
- `RosterPane` (209) — roles + tasks lists, selection, `rebuildLists`
- `TaskPane` (322) — assignments list, selection
- `InitiateTaskPane` (444) — the form: rows, editing, `typeChar`/`backspace`/`commitEdit`, submission

011.1.3 Unit 7 item 2 introduces an intermediate `abstract class MultiListPane`
shared by `RosterPane` and `TaskPane` (identical `render`/`afterRedraw`, including
fragile selected-line offset arithmetic). That should already exist — put it in the
base-class module beside `Pane`.

`InitiateTaskPane` is the largest and most self-contained; if only one thing moves,
move that.

**Tests:** existing TUI specs, plus a `dumpChars()` assertion per pane type
confirming it still renders after the move.
**Gate:** `./dev-environment/scripts/check.sh` + `./scripts/run-all-tests.sh`.

## Unit 2 — `tui.ts` (1269 lines)

The largest file in the repo. Seams, in order of confidence:

1. **Pure module-level helpers** (lines 98–238) — `interpretKey`, `isNavigableList`,
   `resolveTaskListEntryMaxLines`, `fitHints`. Trivially extractable, fully
   unit-testable without a terminal, and `tui-format.spec.ts` already covers some.
   Start here.
2. **Key handling / input interpretation** — `interpretKey` plus the key-event
   dispatch inside the class. A cohesive "translate keystrokes into intents" concern.
3. **Pane lifecycle** — `addPane`, `addRosterPane`, `buildTaskPane`, `addTaskPane`,
   `replaceWithTaskPane`, `addInitiateTaskPane`, `removePane`, `switchToPane`,
   `hasPane`.
4. **Pane content updates** — `updateTaskPaneAssignments`, `updateTaskPaneStatus`,
   `updateRosterRoles`, `updateRosterTasks`, `appendEvent`, `showPaneError`.
5. **Help overlay** — `showHelp` and its hint strings.
6. **The 12 `onX` handler registrations** (`onSubmit`, `onQuit`, `onSelectRole`,
   `onRefreshRoster`, `onCloseTab`, `onSelectTask`, `onSelectAssignment`,
   `onCancelTask`, `onStartTask`, `onOpenInitiateTask`, `onSubmitInitiateTask`) —
   ~70 lines of near-identical setter boilerplate. A typed handler map would
   collapse it.

> [!NOTE]
> Item 6 is the one place in this sub-plan where a small abstraction is justified,
> because the repetition is mechanical and the map is typed. **Only do it if the
> result is genuinely more readable at the call sites** — if it makes the public
> API of `Tui` harder to discover, leave the explicit setters. Ask rather than
> guess if it is marginal.

Keep `Tui` as the public class the commands construct; move clusters behind it.

**Tests:** the existing TUI specs plus new coverage for any extracted pure helper.
Use real widgets and `dumpChars()`, per the rules above.
**Gate:** `./dev-environment/scripts/check.sh` + `./scripts/run-all-tests.sh`.

## Code quality requirements

Route via `AGENTS.md` → `dev-environment/guidance/index.md`; read
`process/before-coding.md` first, `standards/readability.md` (directly relevant),
and `process/after-coding.md` when done. State the filename of each guidance doc
you read.

- **After every unit**, run `./dev-environment/scripts/check.sh` **and the full
  test suite** before starting the next. Never bypass a hook with `--no-verify`.
- Zero compiler and linter **errors and warnings**.
- **Never cast to `any`, especially in test mocks — type the mock instead.** This
  matters more here than anywhere: the terminal-kit types are already partly
  hand-written, and an `any` cast in a TUI test is how wrong API assumptions get
  laundered into passing tests.
- Never fake the terminal-kit widget classes. Real widgets, synthetic key events,
  `dumpChars()` assertions.
- Comments state **intent**, not mechanics; TSDoc on new modules and exported
  functions; `{@link}` for type references; no decorative separator comments.
- **No unrequested abstractions** — the one candidate is the `Tui` handler map in
  Unit 2, and only if it reads better.
- When changing a class's constructor or behaviour, grep `test/integration/` and
  `test/e2e/` by class name too, not just `apps/tcp-cli/src/`.
- Full suite via `./scripts/run-all-tests.sh`; e2e via `./scripts/run-e2e-tests.sh`,
  never bare `npm run test:e2e`.
- aislop is opinionated and can disagree with these standards. Where they conflict,
  **the documented standards win** — including its 400-line limit.
