# Plan: Consolidate LLM Provider Configuration

## Context

`LlmConfig` is currently defined inline in `LcpRole.model.ts` and imported from there by `LcpCompany.model.ts`. The API key is stored as an environment-variable name (`apiKeyEnvVar`), while all other LLM config (provider, model, baseUrl) lives in the database. This splits a single concern across two locations and requires callers to keep env vars in sync with DB records.

The goal is to:

1. Move `LlmConfig` to its own file
2. Replace `apiKeyEnvVar` with `apiKey` so the full LLM config (including key) lives in the DB
3. Tighten the update endpoint types to `DeepPartial` so nested JSONB fields (e.g. just `llmConfig.model`) can be patched without overwriting the whole object

---

## Security Note (flag before implementing)

Replacing `apiKeyEnvVar` with a literal `apiKey` stored in the database is a trade-off:

| Current                                                    | Proposed                                            |
| ---------------------------------------------------------- | --------------------------------------------------- |
| Key stays in env, only the var name is in DB/API responses | Key lives in DB and is returned by GET endpoints    |
| Compromise of the DB exposes no keys                       | Compromise of DB or API responses exposes live keys |

**Mitigations in scope for this plan:**

- Response masking: `apiKey` is replaced with `'***'` in all API responses when `LCP_MASK_API_KEYS=true` (the default) — see step 10–11 below
- Ensure PostgreSQL has encryption at rest (filesystem or TDE) — operational requirement, not a code change
- Document that backups will contain live keys

---

## Parent–child relationship question (LcpCompany / LcpRole)

It is very common in TypeORM to also declare `@OneToMany(() => LcpRole, role => role.company) roles?: LcpRole[]` on `LcpCompany`. This enables:

```typescript
companyRepo.findOne({ where: { id }, relations: { roles: true } });
// → single JOIN query returning company + all its roles
```

The trade-off:

- **Without `roles` on LcpCompany (current):** roles are always queried separately; no risk of accidentally eager-loading large arrays. The `GET /company/:id/roles` endpoint makes the intent explicit.
- **With `roles` on LcpCompany:** convenient for any code that needs both in one go; TypeORM lazy-loads by default so you only pay when you opt in to `relations: { roles: true }`.

Both patterns are standard. The current approach (separate query) is cleaner for a REST API where role listing is its own endpoint. **No change is proposed here** — noted as something to add if a single-query company-with-roles fetch becomes a real need.

```typescript
async updateRole(id: string, partial: DeepPartial<Omit<LcpRole, 'id' | 'company'>>): Promise<LcpRole | null> {
  const existing = await this.roleRepo.findOneBy({ id });
  if (!existing) return null;
  const merged = {
    ...existing,
    ...partial,
    id,
    llmConfig: partial.llmConfig !== undefined
      ? { ...existing.llmConfig, ...partial.llmConfig }
      : existing.llmConfig,
  };
  return this.roleRepo.save(merged);
}
```

### 10. `apps/lcp-server/src/config/config.schema.ts`

Add optional boolean env var:

```typescript
LCP_MASK_API_KEYS: Joi.boolean().default(true),
```

Set `LCP_MASK_API_KEYS=true` in `.env.example` with a comment explaining it. When `false`, the raw key is returned in API responses (useful for debug).

### 11. Global response interceptor: `apps/lcp-server/src/utils/mask-secrets.interceptor.ts`

A small `NestInterceptor` that, when `LCP_MASK_API_KEYS=true`, recursively walks the response value and replaces any `apiKey` string with `'***'`. Register it globally in `AppModule` via `APP_INTERCEPTOR`.

Because `LlmConfig` is a plain interface inside JSONB, class-based `@Exclude()` can't reach it. The recursive-walk interceptor is the minimal approach — one small utility, one provider registration.

## Migration

No SQL migration needed — `llmConfig` and `llmDefault` are JSONB columns; the schema doesn't change. Existing stored JSON objects that contain `apiKeyEnvVar` will simply have an unknown field that is ignored. The `buildChatModel` factory will look for `config.apiKey` (new field), so existing stored configs must be updated manually:

```sql
-- Example data migration for roles
UPDATE lcp_role
SET "llmConfig" = jsonb_set(
  "llmConfig" - 'apiKeyEnvVar',
  '{apiKey}',
  to_jsonb('<actual-key-value>'::text)
)
WHERE "llmConfig" ? 'apiKeyEnvVar';
```

Because there is no production data yet, this is a note rather than a committed migration file.
