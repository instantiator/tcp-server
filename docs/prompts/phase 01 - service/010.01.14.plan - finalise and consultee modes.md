# Task orchestration 8.3: finalise & consultee modes

Follow-on to `010.01.13`. After a full task ran end-to-end on the local model
(plan → implement → QA → finalise → `succeeded`), a few gaps remained. This part
adds a **`finalise` mode** (a task-level QA-and-fix step that guarantees the
task's stated expectations), a **`consultee` mode** (a first-class mode for an
agent receiving a consultation, replacing the implement-mode + suffix hack), a
**file-rename storage tool**, and several readability/robustness fixes.

The assignment mode set becomes:
`plan | implement | qa | chat | consultee | finalise`.

## 1. `finalise` mode

### Why

Today `TaskOrchestrationService.finalise()` is purely mechanical: copy each
assignment's `completed/` → the task `completed/`, set `task.completed`, mark
`succeeded`. Nothing checks the deliverables against the **task's** `expected`
outputs (observed: a task created with `--expected chicken-food.txt` succeeded
with a file named `chicken-diet-report.txt`). A finalise agent closes that gap.

### Flow

When all implement assignments succeed **and the task has a non-empty
`expected`**:

```
promote assignment completed/ → task completed/   (mechanical, as today — files always exist)
  → dispatch a finalise-mode agent scoped to the task completed/ area
      • read / write / replace / rename / delete the deliverables
      • consult a role (interactions) for anything it can't resolve itself
      • its "expected outputs" = the task's expected
  → completes (expectations met/exceeded): task → succeeded
  → run fails (can't meet, exhausts iterations): task → failed, files stay promoted
```

Promoting **before** the agent runs is what satisfies "if it cannot complete,
the task should fail but still promote the files it has". When `task.expected`
is empty, skip the finalise agent and finalise mechanically as today.

### Implementation

- **Mode + prompt.** Add `'finalise'` to `LcpAssignmentMode`; add
  `MODE_PROMPTS.finalise`: "Your job is to make the task's completed deliverables
  meet or exceed the task's expected outputs (listed below). You may read, edit,
  rename and delete the completed files, and consult another role for changes you
  can't make confidently yourself. When the expected outputs are satisfied, hand
  them over with `complete_assignment`." `requiredToolForMode('finalise') =
['complete_assignment']`.
- **Dispatch.** In `TaskOrchestrationService`, add `dispatchFinalise(task)`:
  create a `finalise`-mode assignment (`taskId`, `orderIndex: null`, `expected =
task.expected`, `materials =` the promoted task-completed files) and dispatch
  its agent (`requiredToolCalls: ['complete_assignment']`). Called from `advance`
  when the plan is complete and `task.expected` is non-empty, **after** the
  mechanical promotion.
- **Storage scope.** `resolveStorageScope` gains a `finalise` branch: the agent's
  working area is the **task `completed/` directory** (`taskCompletedKey` prefix),
  read-write. So `append/replace/rename/delete_working_file` operate on the task
  deliverables. (Artifact-key resolution for the gate uses the same prefix.)
- **Completion.** `complete_assignment` gains a `finalise` branch in
  `AssignmentService`: run the (shape) output gate against the finalise
  assignment's `expected` (= task expected) over the task `completed/` dir; on
  pass → set `task.completed` from the completed files + `task → succeeded` +
  complete the agent; on gate failure → 422 corrective (agent retries). No QA
  after finalise.
- **Failure.** `handleAgentFailed` gains a `finalise` branch: task → `failed`,
  but `task.completed` is still populated from whatever is in `completed/` (files
  stay promoted). Recovery (`reconcileTask`) handles a dead finalise agent the
  same way.
- `// ponytail:` finalise gets **no QA of its own** — it _is_ the final check.
  A QA-of-finalise is the upgrade path if it proves necessary.

## 2. `rename_working_file` storage tool

`StorageService.moveFile(source, destination)` already exists — the tool just
needs wiring:

- New MCP tool `rename_working_file` (`{ agentId, from, to }`) in
  `storage-tools.service.ts`, subject to the same read-only guard as the other
  mutators.
- Internal endpoint + `AssignmentService` handler that resolves the caller's
  storage scope and calls `moveFile(workingPrefix+from, workingPrefix+to)`.
- Add to `storage-tool-descriptions` / `tools.jsonc`, and to the storage write
  tool set (item 5) so read-only modes don't get it.

## 3. `consultee` mode

Replace the "consultation runs in `implement` mode + `CONSULTATION_PROMPT_SUFFIX`"
hack with a first-class mode:

- Add `'consultee'` to `LcpAssignmentMode`; `MODE_PROMPTS.consultee` carries the
  reframed consultation prompt (currently `CONSULTATION_PROMPT_SUFFIX` in
  `pause-and-resume.service.ts`): a consultation is usually a question, not a
  document; answer concisely in the `summary`; only create files if genuinely
  needed; actually invoke `complete_assignment`. Delete the suffix const.
- `pause-and-resume.service.ts` creates the consultee agent with
  `mode: 'consultee'` (its orphan assignment is consultee-mode) instead of
  `implement` + suffix. `requiredToolForMode('consultee') =
['complete_assignment']`; storage access = read-write (item 5).

## 4. Control-char escaping

`get-task`/`list-tasks` JSON occasionally isn't parseable by strict parsers
(`jq` failed on task `98c2f6de` — a `summary`/`qaFeedback` with control chars).
The CLI already uses `JSON.stringify` (which escapes `U+0000–U+001F`), so
investigate where the raw control char survives — most likely the model's output
is stored with a literal control character and re-emitted somewhere that bypasses
`JSON.stringify`, or via a field the API serializes differently. Fix: sanitize
control characters out of agent-produced text (`summary`, `qaFeedback`) on the
way in (they carry no meaning), or ensure the serialization path escapes them.
Reproduce with a unit test feeding a summary containing `\x00`–`\x1F`.

## 5. `MODE_TOOLS` (positive form, replacing `MODE_DENIED_*`)

`mode-tools.ts` currently exports `MODE_DENIED_SERVERS` / `MODE_DENIED_TOOLS`
(a denylist, only `plan` populated). Replace with a **positive** map that states,
per mode, the servers available and the storage access level — more readable and
the single source of truth for **both** client-side tool filtering and the
server-side read-only scope:

```ts
export interface ModeToolAccess {
  /** MCP servers offered to this mode. */
  servers: readonly McpServerName[]; // 'tasks' | 'storage' | 'memory' | 'interactions'
  /** Storage tools offered: mutating + read (read-write) or read-only. */
  storage: 'read-write' | 'read-only';
}
export const MODE_TOOLS: Record<LcpAssignmentMode, ModeToolAccess> = {
  plan: { servers: ['tasks', 'storage', 'memory'], storage: 'read-only' },
  implement: {
    servers: ['tasks', 'storage', 'memory', 'interactions'],
    storage: 'read-write',
  },
  qa: {
    servers: ['tasks', 'storage', 'memory', 'interactions'],
    storage: 'read-only',
  },
  chat: {
    servers: ['tasks', 'storage', 'memory', 'interactions'],
    storage: 'read-write',
  },
  consultee: {
    servers: ['tasks', 'storage', 'memory', 'interactions'],
    storage: 'read-write',
  },
  finalise: {
    servers: ['tasks', 'storage', 'memory', 'interactions'],
    storage: 'read-write',
  },
};
```

- `serverNamesForMode(names, mode)` → intersect with `MODE_TOOLS[mode].servers`.
- `filterToolsForMode(tools, mode)` → drop the storage **write** tools (one
  `STORAGE_WRITE_TOOLS` set: `append`/`replace`/`delete`/`restore`/`rename`
  `_working_file`) when `MODE_TOOLS[mode].storage === 'read-only'`.
- `resolveStorageScope` → `readOnly = MODE_TOOLS[mode].storage === 'read-only'`
  (replaces the hard-coded `mode === 'qa'`), unifying the two enforcement points.
- `STORAGE_WRITE_TOOLS` is the single list the read-only message (item 6) inverts
  to name the _read_ tools.

## 6. `getReadOnlyMessage(toolName, readOnlyTools)` in `storage-prompts.ts`

Replace the `QA_READONLY_MESSAGE` const (which names the mode and directory) with
a function in `storage-prompts.ts` (no templating engine — plain function):

```ts
export function getReadOnlyMessage(
  toolName: string,
  readOnlyTools: string[],
): string {
  return (
    `${toolName} is not available in this mode. The directory is read-only. ` +
    `Use these tools to inspect files: ${readOnlyTools.join(', ')}.`
  );
}
```

The write-tool handlers call `getReadOnlyMessage(toolName, <read tools for this
scope>)` where the read tools are the storage server's non-write tools.
