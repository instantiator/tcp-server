# Repairs completed (2026-07-04)

The TUI never rendered because `tui.ts` was written against an imagined
terminal-kit widget API, and its tests faked that same imagined API, so they
agreed with the wrong assumptions. Root causes, all fixed:

1. **Elements default to 1×1** when constructed without `width`/`height` —
   the pane `TextBox` was never sized (the stray "down-arrow" was a 1×1
   scrollbar).
2. **`Container.resize()` only resizes the internal ScreenBuffer**, not the
   element's drawn position/size — `layout()` was visually a no-op. The
   rewrite drops Containers entirely and sizes `TextBox`es directly with
   `setSizeAndPosition()`.
3. **The tab bar was written directly with `term()`** — wiped by any Document
   redraw (hence vanishing on resize). Now it's a Document widget.
4. **The input box sat at `y = term.height`** — one row off-screen (child
   coordinates are 0-based rows `0..height-1`).
5. **Ctrl+Left/Right collided** with the input's word-navigation bindings;
   tab-switching is now Tab/Shift+Tab (safe: the focused input's Tab binding
   is a no-op without an auto-completer).
6. `InlineInput`'s `> ` prompt is positioned at construction only, so the
   input is constructed at its final position and rebuilt (draft preserved)
   on terminal resize.

**Testing approach (the "creative solution"):** the specs drive the _real_
terminal-kit widgets — the `Tui` accepts a `term` (an EventEmitter with a
size, faking only key/resize event delivery) and an `outputDst` override (a
`ScreenBuffer`), so tests feed synthetic `key` events in and assert on the
actual rendered characters dumped from the buffer (`dumpChars()`). One
gotcha: the Document pins itself at outputDst coordinates (1,1), so the
buffer is created one row/column larger and reads apply that offset. See
`apps/lcp-cli/src/lib/tui.spec.ts` (21 tests: rendering, tab switching,
typing/editing/submit, Alt+Enter newlines, draft preservation, busy
submit-blocking, scroll-follow, resize, quit).

Also delivered while in there (trivial): the **bottom hint row** (improvement
4 below), a **busy state** (Enter won't submit while a turn is in flight;
typing still works), **scroll-follow** (PgUp detaches from the tail, paging
back to the bottom reattaches), and **draft preservation** across tab
switches. `--no-tui` and piped `--query` still use the plain renderer,
unchanged.

# Plan: remaining TUI improvements (for Sonnet/Opus)

Improvement 4 (bottom-row key guidance) is already done — see above. The
remaining three change `chat`'s entry semantics and make panes dynamic.

## Phase A — company-scoped chat entry

- `chat`'s `--role-id` becomes optional; add `--company-id <uuid>`. Exactly
  one must be given: with `--role-id`, resolve the company from the role
  (`GET /api/role/:id` already returns `companyId`) and behave as today
  (root agent tab opened immediately). With `--company-id` only, open the
  TUI with **no agent tab** — just the company pane (Phase B) — and create
  no agent up front.
- `-q/--query` still requires `--role-id` (a one-shot needs a target role);
  reject `-q` + `--company-id`-only with a clear error.
- Restructure `chat.ts` so agent creation happens per-pane rather than once
  before the TUI opens: extract the current create-agent + `streamAgent`
  wiring into a `startAgentPane(roleId)` helper, used both by the
  `--role-id` startup path and by Phase B's "initiate chat".
- Cleanup on exit must delete **all** agents created during the session, not
  just one (`agentId` becomes a set).

## Phase B — company pane: role list + initiate chat

- Pane 0 (label = company name) lists the company's roles via the existing
  `GET /api/company/:id/roles` endpoint.
- Selection UI: reuse the ScreenBuffer test harness to drive whichever
  widget is chosen. Recommended: a plain `TextBox` listing roles with an
  up/down-moved highlight and Enter to select, handled with a per-pane
  key route (the company pane has no InlineInput, so arrows/Enter are free
  there) — terminal-kit's menu widgets (`ColumnMenu`/`SelectList`) are an
  alternative but need new ambient declarations and their own focus
  handling; only adopt one if the hand-rolled highlight proves fiddly.
- Enter on a role → `POST /api/agent/chat/start { companyId, roleId }` →
  add a **talkable** pane for the new agent and switch to it (this is
  "initiate chat"). `r` (or re-selecting the company tab) shows the list
  again; add a `refresh roles` key.
- **Multiple talkable panes** now exist, so:
  - `Tui.onSubmit` must tell the handler _which_ pane submitted (add the
    active pane id to the callback signature); `chat.ts` posts the message
    to that pane's agent.
  - `busy` becomes per-pane (`Pane.busy`), not TUI-global: a turn in flight
    on one agent must not block submitting to another. `setBusy(paneId,
busy)`; the hint row reflects the _active_ pane's state.
  - The input draft should be stored per-pane, not in a single `Tui.draft`.
- Consultation follower panes keep working unchanged (spectate-only).

## Phase C — polish (optional, last)

- Colour via terminal-kit markup (`setContent(text, true)`): grey reasoning
  blocks, highlighted active tab. **Must escape `^` as `^^` in all
  model/user-provided text** before enabling markup, or carets in output
  corrupt the display.
