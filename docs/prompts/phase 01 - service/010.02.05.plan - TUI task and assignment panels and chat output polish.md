# lcp-cli 010.02.05: TUI task & assignment panels + chat output polish

Part 3 of the 010.02.00 lcp-cli improvements (map: `010.02.00 - lcp-cli improvements for
tasks and assignments.md`). Depends on `010.02.01` (the `POST /api/task/:id/cancel`
path, `eavesdrop`, and `render.ts`) and `010.02.03` (the task SSE endpoint, the
multi-list panel model, `TASK_LIST_ENTRY_MAX_LINES`, and `parentAssignmentId`).

> **2026-07-16 — scope added from `010.02.01` implementation feedback**
> (`docs/prompts/10.3.1.1 feedback.md`): hands-on use of `eavesdrop` surfaced
> rendering problems (a timestamp-formatting bug, unwrapped/undifferentiated
> full-JSON dumps, no indication of which agent a line belongs to, a
> misleading completion message, and a live-follow gap that left later
> assignments in a task silently untailed). §3 is expanded from "TUI chat
> output polish" into a shared rendering overhaul so `eavesdrop`, TUI chat, and
> non-TUI chat all get the fix — most of the new work is in shared,
> non-TUI-dependent modules, even though this doc's other sections are TUI-only.

> **2026-07-16 — scope added from `010.02.03` implementation feedback**
> (`docs/prompts/010.02.04.prompt - feedback.md`): three more items folded in. §4 is a
> new **initiate task** panel, opened from the company panel's Tasks list,
> that hands off into this doc's own §1 task panel once the task is created.
> §5 splits the `chat` verb's implicit "company-only → launch the TUI on the
> roster" behaviour out into a dedicated `tui` verb, so `chat` always means a
> talkable agent session. §6 is unrelated to the TUI — it improves the
> agent-loop's required-tool-call reminder (`apps/lcp-agent`) to quote a
> `<tool_call>...</tool_call>` block back to the model when one is found in
> its last response, rather than a generic nudge; included here only because
> the feedback doc asked for it to land in this plan.

> **2026-07-16 — scope added from a full `010.01.02`–`010.02.00` test-coverage audit**
> (user-requested directly, not from a feedback doc): four parallel audits
> compared every plan in the `010.01.02`, `010.01.xx`, and `010.02.00` series against the
> current test suite. §7 is the result — grouped, deduplicated gaps across
> knowledge/RAG, task/assignment entities, mcp-tasks + mode wiring, storage
> scoping, the orchestration state machine, consultation/consultee mode, and
> lcp-cli/TUI. It's cross-cutting (touches `apps/lcp-server`, `apps/lcp-agent`,
> `apps/lcp-mcp-storage`, `apps/lcp-mcp-tasks`, `apps/lcp-cli`) and sizeable
> enough that the implementer should consider splitting it into its own
> follow-on plan rather than folding it into the same PR as §1-§6 — flagged
> here per the request, not prescribing that split.

> **Recommended implementing model: Opus.** New interactive panels, live SSE,
> colour attributes, and real-widget tests.

## Goal

1. **Task panel** — opened by selecting a task in the company panel; shows the
   task and its assignments, live via the task SSE, with an in-view cancel
   shortcut.
2. **Assignment chat panel** — opened by selecting a begun assignment; a
   read-only view of that assignment's conversation, live if still running.
3. **Output rendering overhaul** — shared fixes across `eavesdrop`, TUI chat,
   and non-TUI chat: per-agent heading blocks, JSON-delta formatting, line
   wrapping, a short-id convention, a timestamp bug fix, a clearer completion
   message, and `eavesdrop`'s live multi-agent follow gap — plus the
   already-planned user-prompt echo and blank-response marker.
4. **Initiate task panel** — opened from the company panel's Tasks list; a
   form for a prompt, a planner role, and expected output filenames, with an
   optional "start immediately" checkbox; hands off into the task panel (§1)
   on success.
5. **`chat` / `tui` verb split** — `tui <company>` becomes the dedicated way to
   open the full-screen TUI on a company's roster; `chat` no longer accepts a
   bare company and always means a talkable session with a role.
6. **Required-tool reminder quoting** (`apps/lcp-agent`, not TUI) — when the
   agent loop's required-tool-call reminder fires, quote back a
   `<tool_call>...</tool_call>` block if one is found in the model's last
   response, instead of a generic "you didn't call it" nudge.
7. **Test coverage hardening** (cross-cutting, not TUI) — closes gaps found by
   auditing the `010.01.02`-`010.02.00` plan series against the current test suite:
   knowledge/RAG round-trips, mode-tool-restriction wiring, storage-scope
   edge cases, orchestration state-machine branches, consultation/consultee
   assertions, and lcp-cli's untested `ChatSession`.

All paths under `apps/lcp-cli/src/lib/tui/` unless noted (§3, §5, §6, and §7
touch shared/non-TUI modules — called out inline).

## 1. Task panel

Selecting a task entry in the company panel (the tasks list from `010.02.03`) opens
a new pane. Add a `TaskPane` (subclass of `Pane` in `panes.ts`, non-talkable);
open it via the existing pane-management path (`Tui.addPane`-style, like the
help/chat panes), selectable back to the company panel with Tab/Shift-Tab.

Layout:

```
Id:     <task id>
Prompt: "<task prompt in full, word-wrapped, each subsequent line indented>"

Assignments

> 1. <role> <status> "<full prompt when highlighted>"

  2. <role> <status> "<truncated prompt>"
  3. ...
```

- `Id:` / `Prompt:` header (reuse `renderPaneHeading`-style helpers; word-wrap the
  prompt, indent continuation lines).
- **Assignments** as a `SelectableList` (the `010.02.03` model) — ordered plan
  assignments by `orderIndex`, then the rest by `createdAt` (the ordering
  `GET /api/task/:id` already returns).
- Each row: `n. <role> <status> "<prompt>"`, truncated with ellipsis; when
  highlighted, expand + word-wrap the prompt up to `TASK_LIST_ENTRY_MAX_LINES`
  with spacing (same behaviour as the company task list).
- **Status colours** (terminal-kit markup like the existing grey reasoning
  style): waiting = grey, in-progress = cyan, succeeded = green, failed = red,
  cancelled = yellow. Put the status→colour map in `tui-format.ts` (shared with
  the company task list's state indicator).
- **Selectability**: only assignments that **have begun** (status not `ready` /
  waiting) are selectable — mark not-yet-begun rows non-selectable in the
  `SelectableList` so the `>` skips them.

### Live updates

Open the **task SSE** (`GET /api/task/:id/events`, `010.02.03`) when the pane opens
(reuse the shared SSE-reader helper). On `task_changed` / `assignment_changed`,
update the in-memory task/assignments and redraw if active. Close on pane/TUI
close.

### Cancel from the task panel

- A cancel keyboard shortcut (pick a free key in `Tui.handleKey`; document it):
  calls `POST /api/task/:id/cancel` (`010.02.01`) for the panel's task.
- Show the shortcut in the bottom hint bar **only while the task is running**
  (active status), via `fitHints`; always show it in `HELP_TEXT`.
- After cancel, the SSE stream drives the panel to the cancelled state (no manual
  refetch needed).

### Start from the task panel

> Added from `010.02.04` feedback: a task created via §4's initiate-task panel
> without the "start immediately" checkbox lands here in `ready` status, so
> this panel needs its own way to start it.

- A start keyboard shortcut (another free key in `Tui.handleKey`; document it):
  calls `POST /api/task/:id/start` (`202`, `apps/lcp-server/src/api/task.
controller.ts`, transitions `ready` → `planning`).
- Show it in the bottom hint bar **only while the task is `ready`** (mirrors
  the cancel shortcut's status-gating); always show it in `HELP_TEXT`.
- After starting, the SSE stream drives the panel to the new status, same as
  cancel — no manual refetch.

### Tests

- `tui-format.spec`: task-panel header/prompt wrapping; assignment row rendering,
  truncation, highlight expansion; status→colour mapping.
- `tui.spec` (real widgets → `ScreenBuffer`): opening a task panel from the
  company list; `>` skips not-yet-begun assignments; status colours via
  `attrAt`/`get()`; the cancel shortcut appears only when running and issues the
  request (mock the API); the start shortcut appears only when `ready` and
  issues `POST /api/task/:id/start`; an SSE `assignment_changed` updates the row.

## 2. Assignment chat panel

Selecting a **begun** assignment in the task panel opens a **read-only** chat
panel for that assignment's conversation.

- Reuse `ChatPane` / `PaneEntryLog` rendering, but **without an input box**
  (`talkable = false`) — a read-only scrollback.
- Source the conversation: the assignment's working agent id (from the
  assignment record). If the assignment/agent is **still running**, follow the
  existing per-agent SSE (`GET /api/agent/:id/events`, reuse `session.ts`
  `streamAgent` / the shared reader) so it stays live; if complete, render its
  final state (fetch the historical events — use the `010.02.01` history endpoint,
  `GET /api/agent/:id/history`, mapped into the same `AgentEvent` shapes, so a
  completed assignment still shows its full conversation).
- Back to the task panel with Tab/Shift-Tab.

### Tests

- `tui.spec`: opening an assignment chat panel from a task panel; a running
  assignment streams events into the read-only pane (no input box rendered); a
  completed assignment renders its history.

## 3. Output rendering overhaul

Mirror the non-TUI fixes in `010.02.01 §4` so all three surfaces (`eavesdrop`,
TUI chat, non-TUI chat) behave the same. Most of this lives in a new shared,
non-TUI-dependent module so `eavesdrop.action.ts` (plain stdout, no
terminal-kit) and `tui-format.ts` (terminal-kit markup) can both use it without
duplicating logic.

### Shared module: `apps/lcp-cli/src/lib/core/agent-log-format.ts`

New file, no terminal-kit dependency (parallel to how `render.ts` is already
plain-stdout):

- `shortId(uuid: string): string` — first 8 hex chars. No existing convention
  for this in the codebase (checked); this establishes it. Use it everywhere a
  full agent/assignment UUID is currently printed in a log-line prefix.
- `agentHeading(ctx: { assignmentId, assignmentRole, agentId, roleId,
roleSlug }): string` — the 5-line block from the feedback:
  ```
  Assignment id: <id>
  Assignment role: <role>
  Agent id: <id>
  Agent role id: <id>
  Agent role slug: <slug>
  ```
- A per-agent-id `Map`-based tracker (e.g. `class LogHeadingTracker`) with
  `shouldPrintHeading(agentId): boolean` — true the first time an agent id is
  seen or whenever it differs from the last-printed one, false otherwise. One
  instance per output stream (a fresh one per `eavesdrop` invocation; per pane
  for TUI surfaces that can interleave more than one agent — the
  consulted-agent follower panes mentioned below).
- `formatJsonDelta(kind: 'llm_request' | 'llm_response', agentId: string,
payload: unknown): string` — pretty-printed (`JSON.stringify(_, null, 2)`,
  2-space-indented under the heading, matching the feedback's mockup), showing
  only what's new since the last call _for that `kind` and `agentId`_:
  - `llm_request`: the payload's `input.messages` array only grows turn over
    turn (each request re-sends the full running history). Track the last-seen
    message count per agent; print only the newly appended message objects,
    not the whole array. First call for an agent prints everything (nothing to
    diff against).
  - `llm_response`: one response per turn, nothing to diff against — print the
    full payload, formatted.
  - Keep the diff **per-`kind`** (a request diff and a response diff for the
    same agent are independent state).
- A wrap helper: extract the pure word-wrap function already in `tui-format.ts`
  into a shared, non-terminal-kit-dependent module (e.g. `core/text-wrap.ts`);
  re-export it from `tui-format.ts` for existing callers so nothing there
  changes. Use it to wrap long free-text lines (reasoning, response bodies) to
  `process.stdout.columns ?? 80` in both `eavesdrop.action.ts` and `render.ts`
  (today neither wraps).

### `eavesdrop` fixes (`apps/lcp-cli/src/lib/observability/eavesdrop.action.ts`)

- **Timestamp bug** ("`Invalid | llm_response | {...}`"): `formatAuditRow`
  (`eavesdrop.action.ts:43`) does `new Date(row.timestamp).toTimeString()
.slice(0, 8)` with no validity guard — an unparsable/missing timestamp
  yields `"Invalid Date"` → `"Invalid "`. Guard it the same way
  `tui-format.ts`'s `clockTime()` already does (`Number.isNaN(date.getTime())`
  → fallback), rather than introducing a third copy of that check.
- **Full-JSON-dump lines**: `llm_request`/`llm_response`/`tool_call`/
  `tool_result` currently all fall through a `default: JSON.stringify(payload
).slice(0, 200)` (`:58-59`) — truncated, not formatted, not diffed. Route
  `llm_request`/`llm_response` through `formatJsonDelta`; keep `tool_call`/
  `tool_result` as single-line JSON (no growth pattern to diff) but pretty and
  untruncated, wrapped via the shared wrap helper.
- **Heading block on agent change**: before each line, check
  `LogHeadingTracker.shouldPrintHeading(agentId)`; if true, print
  `agentHeading(...)` first. Requires `eavesdrop` to resolve and carry
  assignment/role context per agent (it already fetches assignments to build
  its target list — thread that through to `followAgent`/the history printer
  instead of re-deriving it).
- **Short id in the line prefix**: `[<shortId(agentId)> (<roleSlug>)]` instead
  of the full-UUID `rolePrefix: agentId` (`:136`).
- **Live multi-agent follow gap**: `resolveTarget` for `--task-id`
  (`:110-121`) fetches the task's assignments **once** and never learns about
  assignments that appear afterward (the reported "planner observed, then
  silence" bug — the QA/implement/finalise agent that starts next is never
  picked up). Fix: for `--tail --task-id`, subscribe to the task SSE stream
  (`GET /api/task/:id/events`, `010.02.03 §2`) alongside the initial
  `followAgent` calls; on an `assignment_changed` event for a **new**
  assignment with an agent, start `followAgent` for it too. This is also where
  consultations now show up live, once `010.02.03 §5`'s `parentAssignmentId`/
  `taskId` inheritance lands (a consultation's `assignment_changed` now fires
  on its parent's task stream).

### Chat surfaces (TUI + non-TUI)

- **Echo the user's prompt** (unchanged from the original plan). TUI: append a
  new `PaneEntry` (style `user`) with a distinct indicator + colour on submit
  (`submitHandler` → `session.runTurn` currently never appends it); same
  standard inter-item spacing. Also apply to consulted-agent follower panes
  where a prompt is shown, using `agentHeading`/`shouldPrintHeading` when more
  than one agent's output can appear in the same pane (e.g. a follower pane
  that spans a consultation).
- **Blank responses** (unchanged from the original plan). `response` entry
  with empty/whitespace text → header `hh:mm:ss | response | (blank)` in
  `PaneEntryLog.renderEntry` (`tui-format.ts` ~L186). Share the "is-blank"
  check with `render.ts` if practical; otherwise a `// ponytail:`-noted
  two-line guard in each is fine.
- **Wrap long lines** in the non-TUI renderer (`render.ts`) using the shared
  wrap helper — today it doesn't wrap at all, same gap as `eavesdrop`.

### Misleading "Task completed." message

`AgentLoopService.recordCompletionSummary` builds the deterministic string
`"Task completed.\n\nActions taken (in order):\n{{actionLines}}..."`
(`apps/lcp-agent/src/prompts.jsonc:46`, rendered in `agent-loop.service.ts:
770-808`) and records it as the `agent_loop_completion` event's payload — but
this is the _agent loop's_ (i.e. one assignment's) completion, not the task's;
the task itself may have several more assignments to go. Don't change the
prompt template (the deterministic text is also the actual summary content,
consumed elsewhere) — fix it at **render time**: wherever
`agent_loop_completion` is mapped to a display line (`render.ts`,
`tui-format.ts`, `eavesdrop.action.ts`), use a fixed header label such as
`"assignment complete"` instead of echoing the payload's leading line as the
header. The full text can still appear as the body.

### Tests

- Unit (`agent-log-format.spec.ts`): `shortId`, `agentHeading` output shape,
  `LogHeadingTracker` (prints on first sight and on change, not on repeat),
  `formatJsonDelta` (first-call-prints-all, subsequent-calls-print-only-new for
  `llm_request.input.messages`, full-payload-every-time for `llm_response`,
  independent per-`kind` state).
- Unit: `text-wrap.ts` extraction — existing `tui-format.spec` coverage for the
  wrap function still passes unchanged (it's a re-export).
- `eavesdrop.action.spec.ts`: timestamp guard (malformed/missing timestamp
  doesn't produce `"Invalid"`); heading block prints once per agent-change, not
  per line; `--tail --task-id` picks up a new assignment's agent after an SSE
  `assignment_changed` event (mock the SSE stream).
- `tui-format.spec`: a `user` entry renders with its indicator/colour and
  spacing; a whitespace `response` renders `(blank)`; `agent_loop_completion`
  renders the fixed "assignment complete" header, not the payload's text.
- `render.spec`: wrapping applied to long lines; the completion-message label
  fix.

### Docs

- `docs/lcp-cli.md`: the `eavesdrop` output format (heading block, short ids,
  JSON-delta formatting, wrapping), the corrected completion-message wording,
  and the `--tail --task-id` live-follow fix.

## 4. Initiate task panel

> Added from `010.02.04` feedback. Opened by a dedicated key (pick a free one
> in `Tui.handleKey`; document it) while the company panel's (`RosterPane`,
> `panes.ts`) Tasks list is focused — not by selecting an existing task
> (`Enter` there opens §1's task panel instead).

A new non-talkable `Pane` subclass, e.g. `InitiateTaskPane` (`panes.ts`),
opened via a new `Tui.addInitiateTaskPane(companyId)`-style method mirroring
`addRosterPane` (`tui.ts:333-358`). There is no existing multi-field form
panel in this codebase (`ChatPane`/`RosterPane`/`TextPane` are the only
`Pane` subclasses) — this establishes the pattern; keep it to this panel's
fixed field list rather than a general form framework.

Fields:

- **Prompt** — free text, required. Maps to `CreateTaskDto.request`.
- **Planner role** — a `SelectableList` of the company's roles, fetched the
  same way the roster pane does (`GET /api/company/:id/roles`, reuse
  `ChatSession.fetchRoles()`-style helper from `lib/chat/session.ts`).
  Pre-select the company's default (`LcpCompany.plannerRoleId`, already on the
  model) if it has one; the user can change it. Maps to
  `CreateTaskDto.plannerRoleId`.
- **Expected outputs** — an add/remove list of filenames (start empty; 0 is
  valid). Each becomes a `TaskExpectedArtifactDto` with `type:
'task-completed-path'` and `value: <filename>`. No materials field yet — out
  of scope per the feedback ("we'll add materials in a later improvement").
- **Start task** — a checkbox/toggle, default off.

Validation before submit: prompt non-empty, and a role selected (even though
`plannerRoleId` is optional on the DTO, this panel always requires an
explicit choice — pre-filled from the company default when there is one, but
if the company has none and the user hasn't picked one, block submission with
an inline message). Zero expected outputs is fine.

Submit: `POST /api/task` (`apps/lcp-server/src/api/task.controller.ts`) with
`{ companyId, request, plannerRoleId, expected }`. `CreateTaskDto` has no
"start immediately" flag — a created task always lands in `ready` status. If
the Start task toggle was on, immediately follow with `POST
/api/task/:id/start` (`202`, `ready` → `planning`).

On success, replace this panel with §1's task panel for the newly created
task (same pane slot, not a new Tab stop) — reuse whatever
`addTaskPane`/`switchToPane` mechanism §1 lands.

### Tests

- `tui.spec` (real widgets → `ScreenBuffer`): opening the panel from the
  company panel's Tasks list; submit blocked with an empty prompt or no role

## 5. `chat` / `tui` verb split

> Added from `010.02.04` feedback. Today, `chat --company <c>` (no role) is
> the only way to open the TUI on a company's roster without a talkable agent
> pane already open — an implicit, easy-to-miss mode of a verb whose name
> says "chat". Split it into its own verb.

- New `apps/lcp-cli/src/commands/tui.ts`: `registerTui(program)`, registered
  from `main.ts` alongside the other `register*(program)` calls. Takes only
  `addCompanyOptions` (`lib/entity-ref.ts`) — no role options, no `--no-tui`
  (the verb's entire point is the TUI). Opens straight onto the roster pane,
  same as `chat --company <c>` does today, with no agent pane started.
- Extract the roster-pane-construction part of `chatAction`
  (`lib/chat/action.ts`, the `tui = new Tui(...)` /
  `tui.addRosterPane(...)` steps) into a shared helper used by both the
  existing `chatAction`'s TUI path and the new `tuiAction`, rather than
  duplicating it.
- `chat` verb: drop the bare-company (no role) case. `validateChatFlags`
  (`lib/chat/flags.ts:29-75`) currently rejects `companyGiven && !roleGiven &&
!useTui`; change it to reject `companyGiven && !roleGiven` unconditionally,
  with an error message pointing at `tui <company>`. `chat` now always means:
  a role was given (optionally disambiguated by company), TUI or plain per
  today's `shouldUseTui`.
- Docs: `docs/lcp-cli.md`'s `chat` section (~L279-483) — move the bare-company
  example/behaviour out into a new `tui` section; update the flags table.

### Tests

- `commands/tui.spec` (or wherever verb registration is tested): `tui`
  registers with only company options.
- `flags.spec`: bare company without a role now errors for `chat` (was
  previously valid under `--tui`).
- `tui.spec`/action test: `tuiAction` opens the roster pane with no agent pane
  started, for both `--tui`-implicit (TTY) invocation.

## 6. Required-tool reminder: quote the described tool call

> Added from `010.02.04` feedback. Not a TUI change — `apps/lcp-agent`. When
> `enforceRequiredTools` (`agent-loop.service.ts:562-587`) nudges a model that
> ended its turn without the required tool call, today's reminder
> (`required_tools_reminder`, `prompts.jsonc:25`) is generic. Some models
> instead write out a `<tool_call>...</tool_call>` block as plain text in
> their reasoning/response rather than actually invoking the tool — when that
> happens, quote it back so the model doesn't have to re-derive the call from
> scratch.

- New pure-text helper, e.g. `detectDescribedToolCall(text: string): string |
null` in `apps/lcp-agent/src/agent/loop-tracker.ts` (colocated with the
  module's other text helpers like `extractResultText`) — finds the first
  `<tool_call>` and its matching `</tool_call>` (case-insensitive tag) and
  returns the substring between them; `null` if no complete pair is found.
  No need for a full parser — a straightforward substring search is enough.
- `AgentLoopTracker` (`loop-tracker.ts:10-17`) gains a `lastResponseText:
string` field. `buildOnEvent` (`agent-loop.service.ts:485-527`) doesn't
  currently capture any text from `on_chat_model_end` (it's only used for
  audit recording via `EVENT_TYPE_MAP`, `:70`) — add a case that stores the
  event's output text onto the tracker, overwriting on each turn.
- New `prompts.jsonc` template, e.g. `required_tools_reminder_with_described_
call` — quotes `{{describedCall}}` and adds a hint that the model doesn't
  need to think it through again, just invoke the tool with the information
  already in the quoted block.
- Wire into `enforceRequiredTools`: when building `nudge` (`:581-587`), call
  `detectDescribedToolCall(tracker.lastResponseText)` first. If it returns a
  match, render the new template with it; otherwise render today's
  `required_tools_reminder` unchanged. Leave `required_tools_call_failed`
  (the "call fired but didn't succeed" branch) as-is — nothing to quote
  there, the tool call already happened.

### Tests

- Unit (`loop-tracker.spec` or similar): `detectDescribedToolCall` —
  well-formed block found; no `<tool_call>` present → `null`; unclosed tag →
  `null`.
- `agent-loop.service.spec`: `enforceRequiredTools` sends the augmented
  reminder (containing the quoted block) when `tracker.lastResponseText`
  contains one; sends the plain reminder when it doesn't.

No `docs/lcp-cli.md` changes for this section — it's an internal prompt
template, not user-facing CLI behaviour.

## 7. Test coverage hardening (`010.01.02`–`010.02.00` audit)

> Added at the user's request: a full audit comparing every plan in the
> `010.01.02`, `010.01.xx`, and `010.02.00` series against the current test suite. Items

### 7.1 Knowledge & RAG (`010.01.00`, `010.01.04`, `010.01.05`)

- Knowledge REST CRUD round-trips (`apps/lcp-server/src/api/knowledge.
controller.ts`/`knowledge.service.ts`): `test/e2e/lcp-server/knowledge.
e2e-spec.ts` asserts only 401-without-token for every verb — there is no
  authenticated round-trip test anywhere. Add (e2e, or a new integration spec
  against a real `StorageService`): 200 list (role + company scope), 200 get,
  404 get-unknown-file, 201 store, 204 delete, 204 idempotent re-delete, 404
  unknown role/company on every verb.
- Upload `filename` override (`knowledge.controller.ts:95,155`, `body.
filename ?? file.originalname`) — untested anywhere. Add: upload `file`
  named `x.md` with body `filename: y.md`, assert it's stored/retrievable as
  `y.md`.
- Overwrite-on-same-filename — untested end-to-end (the docstring promises
  replace + reindex). Add: upload the same filename twice, assert the second
  `GET` returns the new content.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.
- Do not add dependencies unless truly needed; if unavoidable, latest version,
  license/health checked. Do not update existing dependencies. No unrequested
  changes outside this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Never `--no-verify`.

Write unit/integration/e2e/API tests alongside each unit of code — main, edge,
and failure cases. TUI tests drive **real** terminal-kit widgets into a
`ScreenBuffer` and assert via `dumpChars()`/`get()` — never fake the widget API
(see the project's terminal-kit testing note). Update existing tests as code
changes.

Documentation:

- `docs/lcp-cli.md`: the TUI task panel, assignment chat panel, their shortcuts
  (jump-between-lists, cancel), and the user-prompt/blank-response output.

Standing instructions:

- If the work becomes exceedingly complex or a problem resists solution, HALT
  and inform the user.
- If you discover a beneficial alteration to this plan, HALT and inform the
  user before proceeding.
- Document any agreed deviations by appending dated notes to this file.
