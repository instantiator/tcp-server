Migration plan for [ADR-017](../ADRs/ADR-017-oidc-provider-selection.md): replace Keycloak with
Zitadel as the bundled OIDC provider.

This is a plan, not yet executed. Nothing described below has been implemented.

## Goal

Replace the `keycloak` Docker Compose service with `zitadel`, running its classic embedded login
(not Login V2), while preserving today's shape: one optional (`--profile auth`) service, sharing
the existing `postgres` container, scripted realm/client/test-user-equivalent bootstrap from
`scripts/start-deployment.sh`, and no change to `lcp-server`'s generic OIDC-discovery auth code
beyond what's listed below.

## 1. `docker-compose.yml`

Replace the `keycloak` service block with something like:

```yaml
zitadel:
  image: ghcr.io/zitadel/zitadel:latest
  restart: unless-stopped
  profiles: [auth]
  command: start-from-init --masterkeyFromEnv --tlsMode disabled
  environment:
    ZITADEL_DATABASE_POSTGRES_HOST: postgres
    ZITADEL_DATABASE_POSTGRES_PORT: 5432
    ZITADEL_DATABASE_POSTGRES_DATABASE: zitadel
    ZITADEL_DATABASE_POSTGRES_USER_USERNAME: lcp
    ZITADEL_DATABASE_POSTGRES_USER_PASSWORD: ${POSTGRES_PASSWORD}
    ZITADEL_DATABASE_POSTGRES_USER_SSL_MODE: disable
    ZITADEL_DATABASE_POSTGRES_ADMIN_USERNAME: lcp
    ZITADEL_DATABASE_POSTGRES_ADMIN_PASSWORD: ${POSTGRES_PASSWORD}
    ZITADEL_DATABASE_POSTGRES_ADMIN_SSL_MODE: disable
    ZITADEL_MASTERKEY: ${ZITADEL_MASTERKEY}
    ZITADEL_EXTERNALDOMAIN: localhost
    ZITADEL_EXTERNALPORT: 8080
    ZITADEL_EXTERNALSECURE: 'false'
    ZITADEL_DEFAULTINSTANCE_FEATURES_LOGINV2_REQUIRED: 'false'
    ZITADEL_FIRSTINSTANCE_ORG_NAME: lcp
    ZITADEL_FIRSTINSTANCE_ORG_HUMAN_USERNAME: admin
    ZITADEL_FIRSTINSTANCE_ORG_HUMAN_PASSWORD: ${ZITADEL_ADMIN_PASSWORD}
  depends_on:
    postgres:
      condition: service_healthy
  ports:
    - '8080:8080'
  healthcheck:
    test:
      ['CMD-SHELL', 'curl -sf http://localhost:8080/debug/healthz || exit 1']
    interval: 10s
    timeout: 5s
    retries: 10
    start_period: 20s
```

Notes:

- No separate management port — `/debug/healthz` (liveness) and `/debug/ready` (readiness) are
  both on the main port, unlike Keycloak's 8080/9000 split. The `start_period`/`retries` values
  above are a starting guess; tune down from Keycloak's 360s-of-headroom once real boot times are
  measured (expected to be seconds, not tens of seconds, given the single-Go-binary architecture —
  this is the whole point of the migration).
- `ZITADEL_MASTERKEY` (a 32-byte key used to encrypt secrets at rest) and `ZITADEL_ADMIN_PASSWORD`
  are new required secrets — add them to `.env.example` alongside the existing
  `KEYCLOAK_ADMIN_PASSWORD` (which can then be removed), and to the env-file schema wherever
  `KEYCLOAK_ADMIN_PASSWORD` is currently validated/documented.
- Keep the `--profile auth` gating and the `required: false` dependency shape on `lcp-server`
  exactly as they are today — no other service needs to change beyond referencing `zitadel`
  instead of `keycloak` for its `depends_on`.
- Verify `start-from-init` is the right one-shot bootstrap command for a single-container compose
  setup at whatever Zitadel version is pinned (pin a specific version rather than `:latest`, since
  the current `keycloak:latest` is itself an unpinned-version smell worth not repeating).

## 2. `docker/postgres-init/`

Add a `CREATE DATABASE zitadel;` statement in whichever init script currently creates the
`keycloak` database (`docker/postgres-init/create-databases.sh`), alongside it (or replacing it,
once Keycloak is fully retired).

## 3. `scripts/start-deployment.sh`

Replace the `kc()`/`kcadm.sh` block (roughly lines 107–199 today: realm creation, confidential
client with service-account + direct-access-grants, test user + password) with:

- **First-boot bootstrap via env vars** — `ZITADEL_FIRSTINSTANCE_ORG_NAME` /
  `_HUMAN_USERNAME` / `_HUMAN_PASSWORD` (set in the compose block above) create the org and an
  initial admin human user automatically on first start. This replaces the realm-creation step;
  Zitadel's "organization" is the realm-equivalent.
- **Application (client) + test user creation via the Zitadel v2 REST API**, using a
  machine-user Personal Access Token (PAT) obtained the same way `kcadm.sh` obtains an admin
  session today. Mirror the existing idempotency pattern (`kc get ... || kc create ...`) using
  `curl` against `POST /v2/users`, `POST /management/v1/projects`, `POST /management/v1/projects/{id}/apps/oidc`,
  etc. — check-then-create, matching today's script's shape and log-line style ("Created realm:
  ...", "already exists").
- The `serviceAccountsEnabled` / `directAccessGrantsEnabled` client flags map to: a machine user
  - API application with `client_credentials` support (service-account-equivalent) plus a
    **separate** human test user (see §4 — the test user's login can no longer go through a
    password grant, so what "test user" is used for changes).
- Update the script's documented env vars (`KEYCLOAK_ADMIN_PASSWORD`, `KEYCLOAK_REALM`) to their
  Zitadel equivalents (`ZITADEL_ADMIN_PASSWORD`, no realm/org-name env var needed beyond what's
  already in the compose block, or add one if org name should stay configurable).

## 4. CLI login flow rework (largest item)

Zitadel does not support the ROPC (`grant_type=password`) grant under any configuration (see
ADR-017). Today:

- `apps/lcp-server/src/auth/auth-token.controller.ts` exposes `POST /api/auth/token` and
  `POST /api/auth/refresh`.
- `apps/lcp-server/src/auth/auth-token.service.ts` proxies these to the IdP's ROPC/refresh grants
  so the client secret never leaves the server.
- `lcp-cli get-token` (`apps/lcp-cli/src/lib/auth/token.ts`, `get-token.action.ts`) calls those
  endpoints with a username/password.

Replace this with the **OAuth 2.0 Device Authorization Grant** (RFC 8628), which Zitadel supports
natively:

1. `auth-token.service.ts` gains a method that calls the IdP's `device_authorization` endpoint
   (from the discovery doc) to get a `device_code`/`user_code`/`verification_uri`.
2. `auth-token.controller.ts` exposes this as a new endpoint (e.g. `POST /api/auth/device`),
   returning the `user_code` and `verification_uri` to the CLI.
3. `lcp-cli get-token` prints the `verification_uri`/`user_code` for the user to open in a
   browser and complete login against Zitadel directly, then polls a new
   `POST /api/auth/device/token` endpoint (proxying the `device_code` token-polling grant) until
   the user completes the flow, exactly mirroring how `gh auth login` / `docker login` work today.
4. `POST /api/auth/refresh` can likely be kept as-is (Zitadel supports the standard
   `refresh_token` grant) — only the initial-login grant changes.
5. **Test-tier impact**: `test/api/helpers/ApiHelper.ts`'s `postCredentialsForToken()` needs a
   non-interactive replacement for automated tests, since device flow requires a human in a
   browser. Use a **machine user + `client_credentials` grant** for test-token acquisition
   instead — Zitadel supports this natively and it doesn't require any interactive step. This
   changes what "test user" bootstrap in `start-deployment.sh` needs to provision (a machine user
   with a generated client secret, rather than a human username/password).

## 5. `apps/lcp-server/src/auth/jwt.strategy.ts`

- Re-verify the issuer/JWKS-rebasing logic (`discoverJwksUri`) against Zitadel's actual discovery
  document when fetched via `OIDC_INTERNAL_ISSUER_URL` vs. `OIDC_ISSUER_URL` — confirm whether
  Zitadel advertises a fixed external hostname (via `ZITADEL_EXTERNALDOMAIN`) in its discovery doc
  regardless of which URL it was reached on (same class of problem as Keycloak's `KC_HOSTNAME`).
  If so, keep the rebase logic but generalize its comment away from Keycloak-specific wording. If
  Zitadel instead reflects the request's `Host` header, this code may become unnecessary — verify
  before deleting.
- Remove the `aud=account`-specific comment/guidance — Zitadel includes the requesting client ID
  in `aud` by default, so `OIDC_AUDIENCE` can likely be set unconditionally without a custom
  mapper.

## 6. `apps/lcp-server/src/health/health.controller.ts` + smoke/api test defaults

Drop the hardcoded "master realm" discovery URL assumption
(`http://localhost:8080/realms/master/.well-known/openid-configuration`); Zitadel's discovery
document lives at `{ZITADEL_EXTERNALDOMAIN}/.well-known/openid-configuration` with no
realm-equivalent path segment. Update:

- `health.controller.ts`'s OIDC reachability probe.
- `scripts/run-api-tests.sh` / `scripts/run-smoke-tests.sh`'s `--keycloak-url` /
  `--oidc-discovery-url` default values (the flags themselves can likely be renamed, or kept as
  generic `--oidc-discovery-url` only, since `--keycloak-url` is Keycloak-specific naming).
- `test/smoke/smoke.spec.ts`'s default `OIDC_DISCOVERY_URL`.

## 8. Suggested execution order

1. Stand up `zitadel` in `docker-compose.yml` + shared-DB init change, get it healthy standalone
   (manual `docker compose --profile auth up zitadel`, confirm discovery doc + login UI work)
   before touching any application code.
2. Rewrite `start-deployment.sh`'s bootstrap block; confirm idempotent re-runs behave like
   today's.
3. Do the device-authorization-grant rework (§4) — the biggest and riskiest piece — behind
   `lcp-cli get-token`, with the machine-user/`client_credentials` path for tests landing at the
   same time so `test/api` isn't broken mid-migration.
4. Update `jwt.strategy.ts`/`health.controller.ts` (§5–6) and re-run the full suite
   (`./scripts/run-all-tests.sh`).
5. Sweep documentation (§7) last, once the implementation details are settled (avoids writing
   docs for an API shape that changes during implementation).
