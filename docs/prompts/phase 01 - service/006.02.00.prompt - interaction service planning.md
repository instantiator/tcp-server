## Interactions with `lcp-mcp-interactions`

The agent should know that it can (and should) consult with users and other agents when additional input is required. This may be because it has reached a decision point where it can gain more certainty about which option to select by presenting them to a user or another agent with appropriate expertise. It may be because essential information is missing before it can start the task. It may be because the user has explicitly asked to be consulted at certain decision points.

A succinct explanation of this should be included as a part of MCP information and company information in the prompt structure provided to the agent.

## Agent-agent interactions

Agents should already have their knowledge domains listed. There are a few parts of this problem to implement:

- Provide data about the available roles to the agent (not including its own role by default, but make this configurable)
  - I suggest providing this as an MCP function (ie. the agent requests a list of roles it can consult, when ready to do so)
  - The agent should generate a request that provides sufficient context for another agent to read and understand what it is working on, why it is asking for support, and how it should respond
  - Initiating an agent interaction by initiating an agent with the selected role and passing the message to the selected agent as if it were a user prompt
    - Add a little fixed supplementary context to ensure the circumstances are clear
      - This is a request from another agent
      - It should give as full an answer as it can, as succinctly as possible
      - It can create and refer to files in the shared storage if necessary to support its answer
      - It should aim to resolve the conversation in a single response

## Human user interactions

There may be more than one human user associated with a company, that agents can request to speak to through the `lcp-mcp-interactions` service. This is asynchronous, and there are a few additional parts of this problem to implement:

- Knowing which user to route the interaction to
- Providing data about the available users to the agent
  - I suggest providing this as an MCP function
- Allowing users to see outstanding requests
- Allowing users to respond to outstanding requests

Users may or may not declare their expertise to the system, or their roles, or their expectations about consultation.

Storing this information will require changes to the models, and a new migration to reflect the new data.

There should always be

- a company creator (the user who created the company), store this on `LcpCompany`
- 1 or more company owners (a list of users - if empty, this is assumed to be the company creator), store on `LcpCompany`
- 0 or more additional users (perhaps with specific expertise that queries can be routed to), store on `LcpCompany`

Each user should be recorded with:

- identifier (a way to know which user a query is being routed to, their authenticated identity)
- name (a way to address the user although, if left null or blank, it's ok to use a non-pronoun to address them)
- roles (a series of roles that indicate the user's involvement with the company, and can be used to infer when to consult a particular user - if left empty, assume the user can respond to any query)
- knowledge domains (a list of additional domains that the user is considered to have expertise in and can consult on)

Queries should be routable to more than 1 user, and then the first response is treated as the response (closing the query). It's expected that humans will consult with each other (if necessary) before sending a response. If the agent geniuinely needs several different users to respond to the request, it should submit several different requests for interaction (even if it is asking the same question).

Queries can contain references to the shared storage.

Once a response is received, this should be added to the agent's conversational prompts, and the agent should be resumed.

Queries should be assigned a simple slug that's unique but human readable, eg. `<role-slug>-<query-index>` eg. `senior-dev-12` - this makes it easy for a human to respond to a query by naming it. That involves tracking query indices for each role. This is worth doing for readability and ease of interaction.

Queries and responses should be audit logged.

## Examples

In a single user project, a company might be set up and the owning user is the only user. In that case, all queries would be routed to that user. eg. "Should be implement AA or AAA accessibility standards for this web page? Recommendation is AA. AAA would be tricky because ..." (goes into detail)

In a project where there are multiple users, there may be a single user who has 'accessibility' listed amongst their domain knowledge, or 'web development'. Those are clues that the agent should route the query to one of those users, who can comment on the accessibility question.

## CLI extension

The cli should have some additional verbs to support these user interactions:

- `list-open-queries` (shows a list, or table, or csv of queries with: query-slug, role name, short 1-sentence summary) depending on the output format specified
- `read-query <query-slug>` (displays the full query)
- `respond <query-slug> "message"` (responds to the query and resumes the agent)
- `download-shared-document --source <shared/storage/path/filename> [--target <target/path/filename>]` (retrieves a file from minio. if target not provided, assume `./<filename>`)
- `upload-shared-document --source <source/path/filename> --target <shared/storage/path/filename>` (stores a doc in minio)

For all CLI interactions, the stdout should be the data, and the stderr should show progress, warnings, etc. (So it can be used in other processes / pipes.)
