# Task orchestration 7/8: orchestration flow

Part 7 of the task-orchestration work (map: `010.2.0 - task orchestration: overview.md`;
parts 1–6 are in place: entities + task API with a no-op `TaskDispatcher`,
agents always have assignments, `lcp-mcp-tasks` tools and internal endpoints
perform validated state transitions and call the dispatcher hooks, and
assignment-scoped storage tools exist).

> **Recommended implementing model: Opus.** This is the most demanding part:
> a multi-agent state machine with races, failure propagation, recovery, and
> cross-service integration testing.

## Goal

Implement `TaskOrchestrationService` in lcp-server — the real `TaskDispatcher` —
so the full lifecycle runs end-to-end:

```
user creates task → start → planner agent (plan mode) → create_plan
  → assignment 0 agent (implement mode) → complete_assignment → QA agent (qa mode)
    → accept → promote files → next assignment … → finalisation → task succeeded
    → reject → resume implementing agent with feedback (up to maxQaAttempts) → …
```

## Prerequisite model addition

`AgentRunConfig` (`libs/lcp-shared/src/models/AgentRunConfig.model.ts`) gains
optional `maxQaAttempts?: number` (JSDoc: maximum QA rejections per assignment
before it fails). No migration — `runConfig` columns are jsonb. Resolved via
the existing `resolveRunConfig` chain: assignment's role → company → env
`TASK_MAX_QA_ATTEMPTS` → code default `DEFAULT_TASK_MAX_QA_ATTEMPTS = 3`
(define beside the other defaults in `@lcp/shared`).

## `TaskOrchestrationService` (`apps/lcp-server/src/api/task-orchestration.service.ts`)

Replaces the no-op `TaskDispatcher` provider (keep the interface; bind the real
implementation). All state changes use atomic conditional UPDATEs (the
`pausedAt`-claim pattern in `agent-orchestration.service.ts`) and are
idempotent — every handler re-reads current state and no-ops if the transition
already happened. Record an `AuditEventType.StateChange` event for each task
and assignment transition (follow existing audit usage).

### `dispatchPlanner(task)` — from `POST /api/task/:id/start`

1. Resolve the planner role: `task.plannerRoleId ?? company.plannerRoleId`
   (the start endpoint already 422s when neither is set).
2. Create a **plan-mode assignment** for the task: `{ taskId, companyId,
mode: 'plan', prompt: task.request, roleId: plannerRole, status: 'in-progress',
materials: task.materials, expected: [] }`.
3. Create + dispatch the agent for it via the existing
   `AgentOrchestrationService` (assignment-first, then agent with
   `requiredToolCalls: ['create_plan']`, then back-link `agentId` — the part-4
   `createAgent` flow already does this given an `assignmentId`).

### `taskPlanned(task)` — from `POST /internal/task/:taskId/plan`

Dispatch the first ready assignment (see `selectNextAssignments` below).

### `dispatchAssignment(assignment)`

1. Compute materials: task materials ⊕ for each **prior succeeded** implement
   assignment (lower `orderIndex`), its `approved` `assignment-completed-path`
   items ⊕ the planner's hint materials already stored on the assignment.
   Deduplicate by `(type, value)`; for duplicate `assignment-completed-path`
   values the **most recent** (highest orderIndex) version wins — this is the
   same rule `resolveArtifactKey` implements; reuse, don't re-implement.
   Persist the merged list to `assignment.materials`.
2. Atomically claim `ready → in-progress` (also the re-entry path after QA
   rejection is `in-progress` already — see below); clear `qaStatus`/`qaFeedback`.
3. Create + dispatch the implement-mode agent for the assignment
   (`requiredToolCalls: ['complete_assignment']`).

### `assignmentReadyForQa(assignment)` — from `POST /internal/assignment/:id/complete`

Create a **qa-mode assignment**: `{ taskId, companyId, mode: 'qa',
targetAssignmentId: assignment.id, roleId: assignment.roleId, status: 'in-progress',
prompt: <rendered QA presentation: the target's prompt, its expected list, and
its prepared list>, materials: assignment.materials }` and dispatch its agent
(`requiredToolCalls: ['assure_assignment']`).

Decision (recorded): the QA agent uses the **same role** as the assignment
under review — a fresh agent instance of the role with the domain expertise.
A dedicated company QA role is future work.

### `assignmentAssured(assignment)` — from `POST /internal/assignment/:id/assure`

The assure endpoint (part 5) has already set `qaStatus`/`qaFeedback` and
completed the QA agent. React:

**Accept:**

1. For each `prepared` item of type `assignment-working-path`: copy the file
   `working/ → completed/` for that assignment (via `StorageService` — the
   copy primitive already exists internally).
2. Set `approved`: each working-path item becomes
   `{ type: 'assignment-completed-path', value }`; `inline-text` items are
   copied as-is.
3. Atomically transition the assignment `in-qa → succeeded`.
4. Complete the paused implementing agent: status `Paused → Completed`, output
   = the summary recorded at `complete_assignment` time (stored on
   `assignment.summary`), through the same internal completion path as normal
   completions (so SSE/consultation behaviour stays consistent).
5. Recompute + persist the task status (`deriveTaskStatus`), then dispatch the
   next assignment or finalise (below).

**Reject:**

1. Increment `qaAttempts`.
2. If `qaAttempts >= resolvedMaxQaAttempts`: assignment `in-qa → failed`
   (record the last feedback in the audit event), fail the paused implementing
   agent (existing internal failure path, reason "assignment failed QA after N
   attempts"), recompute the task status (→ `failed`), and set
   `task.failureReason`.
3. Otherwise: assignment `in-qa → in-progress`, clear `qaStatus`/`qaFeedback`
   (per the state rules; `qaAttempts` is kept), and resume the paused
   implementing agent with a feedback message via
   `AgentOrchestrationService.resumeAgent(agentId, replyContent)` — the
   rendered message explains the prepared artifacts were judged insufficient
   and quotes the QA feedback (template string in lcp-server prompt/template
   conventions, not hard-coded English in the service).

### `selectNextAssignments(task, planAssignments)` — pure function

New pure, unit-tested function (place beside `deriveTaskStatus` in
`@lcp/shared`):

- If any plan assignment is `in-progress` or `in-qa` → `[]` (something is running).
- Else the single `ready` assignment with the lowest `orderIndex` → `[it]`.
- Else `[]` (nothing to run: plan complete, failed, or empty).

Comment it as **the DAG extension point**: future branch/join plans change the
selection logic here (and may return several assignments); `orderIndex` is the
linear-plan implementation detail. The orchestrator must treat the return value
as a set (dispatch each) even though it is 0-or-1 items today.

### Finalisation

When all plan assignments are `succeeded` (i.e. `selectNextAssignments`
returns `[]` and `deriveTaskStatus` yields `succeeded`):

1. Copy every file under every assignment's `completed/` directory into the
   task's `completed/` directory. On filename collision, the **highest
   orderIndex wins** (consistent with the most-recent rule).
2. Set `task.completed`: one `{ type: 'task-completed-path', value }` per
   distinct copied filename, plus every approved `inline-text` item from the
   plan assignments.
3. Task → `succeeded`.

### Failure propagation

Hook the existing internal agent-failure path (where `notifyFailed` lands in
lcp-server — the same place consultations are resolved as failed): when the
failed agent's assignment is task-linked:

- plan-mode agent, task `planning` → task `failed`
  (`failureReason: 'planner failed: …'`).
- implement-mode agent, assignment `in-progress` → assignment `failed` →
  task `failed`.
- qa-mode agent → the **target** assignment `failed` → task `failed`
  (reason "QA agent failed"). `// ponytail: no QA-retry — a failed QA agent
fails the task; re-dispatching QA once is the upgrade path if this proves
noisy.`

### Startup recovery

`reconcileTask(task)` — idempotent, called for every non-terminal task on
module init (and unit/integration-testable directly):

- `planning` with no live planner agent (agent missing, `Failed`, or
  `Completed` without a plan) → task `failed`.
- `in-progress`: assignment `in-progress` whose agent is `Failed` → propagate
  failure; assignment `in-qa` with no live qa agent → dispatch a fresh QA
  assignment/agent; no assignment running and one `ready` → dispatch it; all
  `succeeded` but task not finalised → finalise.
- Agents in `Running`/`Paused` states are left alone (BullMQ + pause/resume
  already own their recovery).

## Tests

- Unit: `selectNextAssignments` (every branch); materials merge + most-recent
  rule; accept/reject reaction logic with repos/storage mocked; recovery
  decision table; `maxQaAttempts` resolution precedence.
- Integration (primary coverage — drive the **internal endpoints** directly to
  simulate agent behaviour, no LLM): full lifecycle
  create → start → (plan endpoint) → assignment 0 dispatched → (complete
  endpoint) → in-qa + QA assignment created → (assure accept) → files promoted,
  next assignment dispatched → … → finalisation, task `succeeded`, files in the
  task `completed/` directory. Plus: reject → resume-with-feedback →
  re-complete → accept; reject × maxQaAttempts → task failed; planner failure →
  task failed; double-complete/double-assure races (atomic claims hold);
  recovery scenarios via `reconcileTask`.
- e2e (stub-llm): attempt one full small task (1–2 assignments) with scripted
  stub responses driving the real agent loop and MCP tools. **First check what
  the stub-llm can script** (see how existing e2e suites configure it; note the
  full consultation-cycle e2e was previously deferred for similar reasons). If
  scripting the multi-agent tool-call sequence is infeasible, HALT and discuss
  with the user rather than sinking time — the integration suite above is the
  load-bearing coverage.
- Remember the BullMQ rule: every new `Queue`/`Worker`/queue-events object
  registers `.on('error')`.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.
- Do not add dependencies unless truly needed; if unavoidable, latest version,
  license/health checked. Do not update existing dependencies. No unrequested
  changes outside this plan.

Quality gates — run at each stage, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` and
   `./dev-environment/scripts/check.sh` — fix everything reported.
5. Never `--no-verify`.

Write unit/integration/e2e/API tests alongside each unit of code — main, edge,
and failure cases; verify HTTP response codes explicitly. Update existing tests
as code changes (grep `test/` directories by class name when changing
constructors or behaviour).
