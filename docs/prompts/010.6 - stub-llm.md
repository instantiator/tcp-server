## Stub-LLM

We already have a primitive stub-llm at `docker/stub-llm/server.js`

Please develop this into a more extensive application, `lcp-stub-llm`. It should simulate a standard LLM API, responding in an expected way with pre-defined responses to prompts. It shouldn't share any code with any other applications in this suite - as it will eventually be exported as an independent application to support development of other LLM / agentic systems.

It should accept an input file on launch, or through a separate configuration API endpoint, specifying prompt and response list pairs, and a list of default responses, eg.

```jsonc
{
  "key": "some-api-key-goes-here",
  "minDelay": 50, // lower bound of random delay per token 'generated' (ms)
  "maxDelay": 100, // upper bound of random delay per token 'generated' (ms)
  "prompts": [
    {
      "match": "What is the capitol of", // any prompt containing this string or regex
      "responses": [
        {
          "text": "London",
          "tools": [
            {
              "tool": "some-tool-name",
              "data": {/* some object */},
            },
          ],
        },
        { "text": "Paris", "tools": [] },
      ], // could contain regex groups
      "mode": "loop", // could be 'loop' | 'random' | 'sequence' (default)
    },
  ],
  "defaults": {
    "responses": [
      {
        "text": "Hi there, I am a deterministic testing tool. I didn't recognise your prompt, so I've returned this.",
        "tools": [],
      },
      {
        "text": "I still didn't recognise your prompt, so I've returned this.",
        "tools": [],
      },
      {
        "text": "I guess we're finished",
        "tools": [
          {
            "tool": "the-assignment-completion-call",
            "data": {/* some object */},
          },
        ],
      },
    ],
    "mode": "sequence", // could be 'loop' | 'random' | 'sequence' (default)
  },
}
```

If the key is not provided in the config, it shouldn't be required. Otherwise, it's essential and the API should respond with an accurate simluation of authentication failure from the API it's simulating.

If the prompt received doesn't match any of the matches, then it should fall back to the defaults, and if the defaults don't match anything then the API should respond with an error code.

Responses can contain text and tool calls - and in the case of a tool call, the service will make a call to an MCP tool. This may involve some additional configuration, passed in through the configuration json or as parameters when invoking the tool, to ensure that calls to the services can be made.

In `loop` mode, responses are issued in sequence, and restart from the beginning after the responses are exhausted.

In `sequence` mode (the default - needn't be specified), responses are issued in sequence and the API will respond with an error code if the list is exhausted.

In `random` mode the response is selected at random from those available.

The response returned is delayed by a random number of ms between `minDelay` and `maxDelay` to simulate an LLM service's generation time. If not provided or `0`, this implies instantaneous generation (helpful for testing).

### Streaming

Although lcp-cli can use streaming responses, it's ok not to simulate as little as possible of this. `lcp-stub-llm` should present any required streaming endpoints, but needn't actually stream any reasoning other than a fixed string saying something like "Streaming simulation is not currently supported."

## Testing

As with other applications in this suite, ensure that there are unit tests, and e2e tests as required to ensure it will behave as expected.

Separate these reasonably cleanly so that `lcp-stub-llm` and its tests can be exported to a separate repository in future, as this will very likely prove to be a useful tool for developing and testing other AI-adjacent applications.

Add a thin wrapper script to launch the new application to make it easier to incorporate into manual testing.

### Update LCP tests

Some testing could make use of the stub LLM. Identify all tests that would benefit from it, and all tests that currently make use of the existing stub-llm, and adjust those tests to configure and use the new stub-llm.

Write new e2e tests that exercise the system and can step through whole task processes using pre-defined LLM responses and tool calls to enact successful (and failed) assignments and tasks.

Use test-containers to launch the application when working with it in tests.
