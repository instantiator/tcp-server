## Coding Standards (Mandatory Throughout)

All code written in this plan **must** comply with these standards from `dev-environment/guidance/`:

### Non-negotiable rules (from `AGENTS.md`)

1. Less is more: concise, readable code and simple interfaces. No unrequested abstractions.
2. Comments state intent, not mechanics. Comment classes, functions, and consts; skip trivial ones.
3. Zero compiler errors and warnings; zero linter errors and warnings.
4. Never cast to `any` (or equivalent type escapes), especially in test mocks.
5. Never store secrets in the code base.
6. Only change code you have been asked to change; ask permission otherwise.

### TypeScript standards (from `dev-environment/guidance/languages/typescript.md`)

- Use strict mode (`"strict": true` in tsconfig).
- Avoid casting to `any` — enable `@typescript-eslint/no-explicit-any` with targeted disables only where genuinely unavoidable.
- Prefer TSDoc multi-line comments; link to types with `{@link TheType}`.
- Run ESLint (flat config) + typescript-eslint recommended-type-checked.
- Run Prettier via eslint-plugin-prettier.
- Expose `typecheck`, `lint`, `format` as npm scripts.

### NestJS standards (from `dev-environment/guidance/frameworks/nestjs.md`)

- One module per domain concept; keep controllers thin — business logic lives in services.
- Use constructor injection everywhere.
- Validate configuration at startup with Joi schemas so a bad env fails fast.
- Validate inputs at boundary with DTOs + `class-validator`.
- Use exception filters / built-in HTTP exceptions.
- Unit test services with `@nestjs/testing`, typed mocks (no `any`).
- Share entities/DTOs via `@app/shared` with explicit exports from a single `index.ts`.

### Shell script standards (from `dev-environment/guidance/languages/shell.md`)

- Write in **bash**, targeting **bash 3.2** (macOS default).
- Shebang: `#!/usr/bin/env bash`. Start with `set -euo pipefail`.
- Quote all variable expansions (`"$var"`); prefer `$(...)` over backticks.
- Run `shellcheck` on every script and fix all findings.

### Node scripting standards (from `dev-environment/guidance/languages/node-scripting.md`)

- Zero dependencies where possible: use `node:fs`, `node:path`, `node:util` (`parseArgs`), `fetch`.
- Single-file ESM scripts: `scripts/thing.mjs`, run with `node scripts/thing.mjs`.
- TypeScript only if the project already has a TS toolchain (run via `tsx` or `ts-node`).
- Self-documentation: `--help`, usage on bad input.
- Exit non-zero on failure; print errors to stderr.

### Readability standards (from `dev-environment/guidance/standards/readability.md`)

- Keep functions and methods short — one purpose each.
- Break supporting functions out into their own files; keep calling code readable as narrative.
- Group functions by purpose; group directories logically.
- Prefer boring, conventional solutions over clever ones.
- Delete dead code rather than commenting it out.

### Common pitfalls to avoid (from `dev-environment/guidance/standards/pitfalls.md`)

- No swallowed exceptions (empty catch blocks or catch-and-log-only when operation failed).
- No narrative comments ("added a check for null").
- No stale comments — when editing code, re-read its comment.
- Every `TODO`/`LATER`/`qq` MUST say WHEN or under WHAT CONDITIONS it will be dealt with.
- No dead code — unused functions, unreachable branches, commented-out blocks.
- No casting to `any` — type the mock instead.
- No oversized functions.

### Testing standards (from `dev-environment/guidance/standards/testing.md`)

- Separate test suites by tier: unit, integration, e2e, browser, api, smoke.
- Provide one launch script per suite: `scripts/run-<suite>-tests.sh`.
- Unit tests need no external services and run fast.
- Test the _intent_ of the code — passing tests mean correct behaviour.
- Cover edge cases, not only the happy path.
- Write or update tests for all new and modified code.

### Documentation standards (from `dev-environment/guidance/standards/documentation.md`)

- Every high-level part of the system gets a doc describing what it does and why.
- Keep `docs/index.md` that lists every doc with a one-line description.
- Document important flows step by step.
- Illustrate with mermaid diagrams where a diagram beats prose.
- Use GitHub-flavoured markdown with language-tagged code fences and relative links.
- Documentation describes _current_ behaviour; update docs in the same change.

### Dependency standards (from `dev-environment/guidance/standards/dependencies.md`)

- Prefer standard library, then platform features, then already-installed dependency.
- Vet candidates on npm: license, last update, download count, vulnerabilities.
- Use latest version of new dependency (no known vulnerabilities).
- List candidates to user with details, make recommendation, ask how to proceed.

### Process standards

- **Before coding**: read `dev-environment/guidance/process/before-coding.md`. Present options before committing to libraries/approaches.
- **After every change**: run `dev-environment/scripts/check.sh` and fix what it reports.
- **When done**: apply judgment items from `dev-environment/guidance/process/after-coding.md` — tests for intent/edge cases, simplification, comment accuracy, documentation updates.
- **Testing loop**: make small changes, test, then move on. Run unit tests after every change.

### Unit 1.2: Create `lib/load-env.sh` helper library [ ] Complete

**Status**: ✅ Implemented

Create a reusable shell library for loading env files with precedence:

```bash
#!/usr/bin/env bash
# lib/load-env.sh — Load env files with precedence (first value wins).

# Usage: load_env_files <file1> [file2] [file3] ...
# Later files provide fallbacks; earlier files take precedence.
load_env_files() {
  local loaded=()
  for file in "$@"; do
    if [[ -f "$file" ]]; then
      # shellcheck disable=SC1090
      source "$file"
      loaded+=("$file")
    fi
  done
  echo "Loaded env files: ${loaded[*]}" >&2
}
```

- [ ] Target bash 3.2 compatibility
- [ ] All variable expansions quoted (`"$var"`)
- [ ] `shellcheck` passes with zero findings

- [ ] No stale comments

### Testing

### Documentation
