# 008.2 — Completion assurance: required tool call tracking + consultation failure propagation

## Context

From `docs/prompts/008.1 - completion assurance planning.md` and ADR-012's deferred items.

Two gaps today:

1. **Silent fallback completions.** `AgentLoopService.runLoop` accepts the last narrated AI message as the agent's output when the stream ends without `complete_task` having fired (agent-loop.service.ts L252-291). ADR-012 (L111, L248) *claims* a completion-enforcement loop exists — it doesn't; there is only a single generic empty-output retry. LLMs that narrate a tool call instead of invoking it complete "successfully" with placeholder text.
2. **Consultation failures hang the caller forever.** All four failure exits in the loop (no LLM config L112-118, abort/timeout L228-233, empty-after-retry L272-283, catch-all L292-297) set `AgentStatus.Failed` directly with no notification. The `PendingConsultation` row stays `pending`, `countOutstanding` never reaches 0, the calling agent never resumes, and `chat.service` blocks until the 30-minute timeout then returns `''`.

**User decisions (confirmed):**
- `requiredToolCalls` enforcement applies to **all loop-run agents** by default (`null` field → default `['complete_task']`; explicit `[]` → opt out). `pauseForConsultation` sets `['complete_task']` explicitly.
- Retry limit: **2 nudges**, `DEFAULT_REQUIRED_TOOL_RETRIES = 2` with `AGENT_REQUIRED_TOOL_RETRIES` env override (mirrors `AGENT_ITERATIONS` pattern in `run()` L120-126).
- No "summary" tool exists — `complete_task`'s `finalAnswer` is the summary; enforcement targets `complete_task` only.
- An agent that *declines* to answer does so via `complete_task` (its answer text) — already flows back; only hard failures need the new path.
- Chat's initial in-process turn (`chat.service` builds the graph itself, L163) never passes through `AgentLoopService` — enforcement structurally doesn't apply there; resumed chat agents DO run through the loop and are enforced.

## Design

### A. Required tool call tracking

- `LcpAgent.requiredToolCalls?: string[] | null` — `simple-json` nullable column (mirrors `storageChanges`). Unprefixed names (`complete_task`, not `interactions__complete_task`).
- Loop resolves effective list: `agent.requiredToolCalls ?? ['complete_task']`; empty array disables enforcement. Guard: any required tool not present in the loaded toolset is dropped with a warning (a role without the interactions server must not fail inevitably).
- `AgentLoopTracker` gains `firedTools: Set<string>`, populated in `on_tool_start` (agent-loop.service.ts L356-362) via a shared `baseToolName()` extracted in `loop-tracker.ts` (dedupes the prefix-strip logic already duplicated at L36-38 / L123-125).
- Post-stream restructure in `runLoop`: after the existing Paused/Completed re-read (L236-250), enforced agents enter an enforcement loop **instead of** the narrated-text fallback:
  ```
  retries = config AGENT_REQUIRED_TOOL_RETRIES ?? DEFAULT_REQUIRED_TOOL_RETRIES  // 2
  for attempt in 1..retries:
    missing = required not in tracker.firedTools
    nudge = missing.length ? required_tools_reminder(missing)
                           : required_tools_call_failed(required)   // fired but call errored — status never flipped
    await streamAndAudit(graph, { messages: [HumanMessage(nudge)] }, ...)
    if signal.aborted → failRun(reason); return
    re-read agent: Paused → return; Completed → summary + publishCompletion; return
  failRun(agent, "Agent ended without successfully calling required tool(s): X after N reminder(s)")
  ```
  Nudges reuse `streamAndAudit` exactly like the existing empty-output retry (L257-265). When `complete_task` fires during a nudge round, its HTTP callback flips status to Completed and the normal completed path runs (summary + `publishCompletion` of `agent.output`).
- Opted-out agents (`requiredToolCalls: []` or tool unavailable) keep the existing fallback path verbatim.
- Two new prompt templates in `apps/lcp-agent/src/prompts.jsonc` (+ interface in `agent-prompts.ts`): `required_tools_reminder` and `required_tools_call_failed`. Wording: task is NOT complete; name the exact callable tool(s) with the `interactions__` prefix; narrating a call is not sufficient — actually invoke the tool.

### B. Failure propagation

- `AuditClientService.notifyFailed(agentId, reason)` — mirror of `notifyComplete`, fire-and-forget `POST /internal/agent/:agentId/fail` with `{ reason }`.
- New route in `internal.controller.ts`: `@Post('agent/:agentId/fail') @HttpCode(204)` → `PauseAndResumeService.failAgent` (+ `FailDto { reason }` in internal DTOs).
- `failAgent(agentId, reason)`:
  - Load agent; if status !== Completed, set Failed (don't clobber — `complete_task` may have won the race).
  - Find `PendingConsultation { consultationAgentId, status: 'pending' }`; none → return (non-consultation failure, nothing to propagate).
  - Update to `{ status: 'failed', result: reason }`; if caller is Paused, fire-and-forget `orchestration.resumeAgent(callingAgentId)` (same tail as `completeAgent` L210-221).
- `ConsultationStatus` gains `'failed'` (PendingConsultation.model.ts L12). `status` is a plain varchar, no CHECK constraint → no migration needed for the value.
- `AgentOrchestrationService.collectRepliesSince` (L176-217): fetch `status: In(['complete','failed'])`; complete → existing `Consultation response: ...`; failed → `Consultation FAILED: ${result ?? 'no reason given'}. Use your own judgement about how to proceed; if a response is essential, consider escalating to a user via request_user_input.` `countOutstanding` unchanged ('failed' ≠ 'pending' → resume gate opens).
- In the loop, new private `failRun(agent, reason)` helper: `recordStateChange('failed', reason)` + `updateStatus(Failed)` + `auditClient.notifyFailed(agent.id, reason)` + `publishCompletion(agent.id, '')` — `''` is already `chat.service`'s failure sentinel (its DB poll resolves `''` on Failed), so the Redis publish just makes the chat wait resolve immediately. Wire all four failure exits through it, plus a catch in `run()` around `checkpointer.setup()`/`runLoop` (a setup throw currently escapes to BullMQ, leaving the agent stuck Running and the consultation pending forever). `worker.on('failed')` stays log-only.

## Risks
- Small local LLMs may ignore nudges during manual verify → run fails after 2 reminders. That is the intended behaviour (failure now propagates; caller can escalate). Reminder wording is the tuning knob.
- Each nudge round gets a fresh `maxIterations` budget inside `streamAndAudit`; the wall-clock timeout (`AGENT_LOOP_TIMEOUT_MS`) still bounds the whole run, and the post-nudge abort check prevents nudging a dead stream.
- `notifyFailed` is fire-and-forget like `notifyComplete`: a lost HTTP call still leaves the caller paused until chat timeout — unchanged exposure, documented in ADR-012.
- Enforcement default-on changes behaviour for resumed chat agents (must now call `complete_task` rather than completing via narrated text) — the nudge loop covers models that forget; manual-verify exercises this path.
- Migration drift checks: remember `check-migrations.sh` phantom-drift caveat — the new migration follows the git-scoped pre-push heuristic (a genuinely new entity column with a matching migration passes).
