## 1. DRY and simplification review

Review the code introduced across parts 1–8 for duplication and
over-complexity, and fix what you find (each fix followed by the quality
gates). Specific places to inspect, based on how the work was divided:

- **Prompt/template rendering**: parts 4, 5 and 7 each render prompt-ish text
  (assignment presentation, QA presentation, rejection-feedback resume message,
  tool descriptions embedding `MODE_PROMPTS`); part 8 moved prompt-assembly
  into `@lcp/shared` and made the chat and worker paths share it. Confirm one
  rendering helper and one home per string; no near-duplicate templates, and
  that `ChatService` has no leftover duplicate assembly.
- **State transitions**: parts 5 and 7 both perform atomic conditional
  UPDATEs on assignments/tasks. Extract a shared claim helper if the pattern is
  copy-pasted three or more times.
- **Artifact handling**: dedup/most-recent logic must exist exactly once
  (`resolveArtifactKey` + the materials merge) — check the orchestrator, the
  storage material tools, and finalisation all reuse it.
- **Internal HTTP proxying**: the three MCP services (`storage`, `interactions`,
  `tasks`) each carry an axios + `X-Internal-Api-Key` + error-extraction layer.
  If they've diverged, unify into a small shared helper in `@lcp/shared`
  (only if genuinely identical in behaviour — don't force it).
- **Dead code**: anything the retirements left behind — grep for
  `complete_task`, `RoleDocument`, `store-role-documents`, `knowledgeKey` with
  a role _name_, removed storage tool names (`write_file` etc. in prompts/
  descriptions), unused prompt strings in the `prompts.jsonc` files, unused
  exports from `@lcp/shared`.

Keep changes behaviour-preserving; if a simplification would change behaviour,
HALT and discuss it instead.

## Working practices (mandatory)

Coding standards:

- Strict TypeScript; no `any` casts. Comments: `/** ... */` on classes/methods/
  functions describing intent (not implementation), `//` inside bodies,
  `{@link}` for type references. Match the surrounding code's style.
- No new dependencies in this part. No behaviour changes — consolidation only.

Quality gates — after every change, not just at the end:

1. `npm run format` (always before checks)
2. `npm run typecheck` && `npm run lint` && `npm run build` && `npm run test`
3. e2e via `./scripts/run-e2e-tests.sh` (never bare `npm run test:e2e`)
4. Before declaring done: `./scripts/run-all-tests.sh` and
   `./dev-environment/scripts/check.sh`.
5. Never `--no-verify`.

Update or add tests for any code you consolidate (a refactor that loses test
coverage is a regression). Grep `test/integration/` and `test/e2e/` by class
name whenever a constructor or behaviour moves.

Standing instructions:

- If the work becomes exceedingly complex or a problem resists solution, HALT
  and inform the user.
- If you discover a beneficial alteration to this plan, HALT and inform the
  user before proceeding.
- Document any agreed deviations by appending dated notes to this file.
